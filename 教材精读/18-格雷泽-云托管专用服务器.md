## 机制

### 托管决策（§13.1）

| 弊端 | 优点 |
|---|---|
| 复杂度：要写进程/VM 管理代码、适应云商 API | 可靠、可扩展、高带宽——需要时在需要的地点开机 |
| 成本非零：省掉前期投入，不省账单 | **防作弊**：所有服务器是自己发布的未修改版本（排行榜/进度才可信） |
| 依赖第三方：云商全宕机时 SLA 安慰不了玩家 | **事实 DRM**：服务器可执行文件不发给玩家，破解服务器无从谈起；还能校验登录凭据 |
| 硬件可能无警告变更（最低规格之上） | — |
| 丧失玩家所有权：自建服务器社区（Minecraft 式）消失 | — |

### 术语金字塔与两个"要不要共享"（§13.3）

**游戏实例 ⊂ 游戏服务器进程 ⊂ 游戏服务器（机器/VM）⊂ 硬件。** "server"一词三种歧义由此拆开。

- **一个进程装多个实例？** 收益：大型不可变资源（碰撞几何、导航网格、动画）共享一份，省内存；实例更新节奏完全自控（不归 OS 调度器）。代价：**一个实例崩可能带走全进程**；共享资源被一个实例毁掉 = 全灭；未跑到的代码路径缺测试覆盖。结论（原文）：**最常见的还是一进程一实例**。
- **一台机器装多个进程？** OS 有保护内存，一进程崩不连坐；单机单进程太浪费（OS 本身吃掉大量资源）。结论：**多进程、跑到性能上限**。

**VM 为什么存在**：云商把一台 16 核物理机切给多个客户（例：4 个各需 4 核的《使命召唤》VM；深夜闲时缩容，EA 的 8 核《模拟城市》需求来了正好填空）。VM 镜像整包含 OS+应用——硬件故障时整包迁移到别的物理机即可恢复。便宜档 = 共享硬件 + 闲时休眠 → 性能不稳；贵档 = 指定物理配置。

**玩家视角的部署流程**：客户端向匹配服务请求 → 无可用服务器则部署系统启动新的 → 匹配服务把 IP:port 发回 → 客户端直连。**部署模块与匹配模块要分离**：自建部署不妨碍接第三方匹配（Steam/Xbox/PSN），部署系统启动后只是"到匹配系统注册自己"，两边各自可换。

### LSPM：机器内的进程管理器（§13.4）

**本地服务器进程管理器** = 一个监听 REST 请求的进程：按需 spawn 游戏服务器进程、记录、监控。核心机制（Node/Express 示例，机制与语言无关）：

- `POST /processes/`：状态闸（`empty/partial/full/shuttingDown` 四态）→ `child_process.spawn(游戏exe, [--processUUID, --lspmURL, --json 配置])` → 登记 `{child, params, state:'starting', lastHeartbeat}` → 挂 `close` 事件监听（退出即从表里删、更新机器状态）；
- `POST /process/:uuid/kill`：主动杀；

**清单 13.1 —— 起进程与记账（状态机骨架）**

```javascript
var gProcesses = {};
var gProcessCount = 0;
var gProcessPath = process.env.GAME_SERVER_PROCESS_PATH;
var gMaxProcessCount = process.env.MAX_PROCESS_COUNT;

var eMachineState =
{
    empty: "empty",
    partial: "partial",
    full: "full",
    shuttingDown: "shuttingDown",
};
var gMachineState = eMachineState.empty;

router.post('/processes/', function(req, res)
{
    if(gMachineState === eMachineState.full)
    {
        res.send(
        {
            msg: 'Already Full',
            machineState: gMachineState,
            sequenceIndex: ++gSequenceIndex
        });
    }
    else if(gMachineState === eMachineState.shuttingDown)
    {
        res.send(
        {
            msg: 'Already Shutting Down',
            machineState: gMachineState,
            sequenceIndex: ++gSequenceIndex
        });
    }
    else
    {
        var processUUID = uuid.v1();
        var params = req.body.params;
        var child = childProcess.spawn(gProcessPath,
        [
            '--processUUID', processUUID,
            '--lspmURL', " http://127.0.0.1 :" + gListenPort,
            '--json', JSON.stringify(params)
        ]);
        gProcesses[processUUID] =
        {
            child: child,
            params: params,
            state: 'starting',
            lastHeartbeat: getUTCSecondsSince1970()
        };
        ++gProcessCount;
        gMachineState = gProcessCount === gMaxProcessCount?
            eMachineState.full: eMachineState.partial;
        child.stdout.on('data', function (data) {
            console.log('stdout: ' + data);
        });
        child.stderr.on('data', function (data) {
            console.log('stderr: ' + data);
        });
        child.on('close', function (code, signal)
        {
            console.log('child terminated by signal '+ signal);
            //were you at max process count?
            var oldMachineState = gMachineState;
            --gProcessCount;
            gMachineState = gProcessCount > 0 ?
                eMachineState.partial: eMachineState.empty;
            if(oldMachineState !== gMachineState)
            {
                console.log("Machine state changed to " + gMachineState);
            }
            delete gProcesses[processUUID];
        });
        res.send(
        {
            msg: 'OK',
            processUUID: processUUID,
            machineState: gMachineState,
            sequenceIndex: ++gSequenceIndex
        });
    }
});
```
- **每局结束尽可能关掉重启进程**——内存泄漏不积压、状态重置不当的风险也不复存在。

**心跳监控**（清单 13.2 的参数就是全套设计）：

```javascript
var gMaxStartingHeartbeatAge = 20;
var gMaxRunningHeartbeatAge = 10;
var gHeartbeatCheckPeriod = 5000;

router.post('/processes/:processUUID/heartbeat', function(req, res)
{
    var process = gProcesses[req.params.processUUID];
    if(process)
    {
        process.lastHeartbeat = getUTCSecondsSince1970();
        process.state = 'running';
        res.sendStatus(200);
    }
    else { res.sendStatus(404); }
});

function checkHeartbeats()
{
    var processesToKill = [];
    var time = getUTCSecondsSince1970();
    for(processUUID in gProcesses)
    {
        process = gProcesses[processUUID];
        heartbeatAge = time - process.lastHeartbeat;
        if(heartbeatAge > gMaxStartingHeartbeatAge ||
        (heartbeatAge > gMaxRunningHeartbeatAge
        && process.state !== 'starting'))
        {
            processesToKill.push(process.child);
        }
    }
    processesToKill.forEach(function(toKill) { toKill.kill(); });
}

setInterval(checkHeartbeats, gHeartbeatCheckPeriod);
```

要点：`starting` 态给 **20 秒**宽限（初始化慢），`running` 态 **10 秒**没心跳即杀，每 **5 秒**巡检一轮。C++ 游戏进程发心跳 = 裸 TCP 手写一行 `POST /api/processes/<uuid>/heartbeat HTTP/1.1\r\n\r\n`（双换行收尾），或用 C++ REST SDK 三行搞定。心跳通道的备选（原文注释）：原生 TCP/UDP 小包免 HTTP 开销、或进程写日志由 LSPM 盯日志——但选 REST 的理由是**复用已有监听 + 纯文本可调试**。

> **原文警告**：产品化必须给 LSPM 加鉴权（IP 白名单或请求头安全令牌），否则任何人都能替你开机器。

### VMM：机器间的编排者（§13.5）

VMM 跟踪所有 LSPM，忙不过来时让云供应商从 **VMI**（虚拟机镜像 = 引导盘：OS + 游戏可执行 + 初始化脚本 + LSPM）起新 VM，闲时回收。三条纪律：**供应商 API 抽象成接口**（换云商/多地区不改核心）；**请求者-VMM-LSPM 的异步交互有竞态与乱序**（每个 REST 请求独立 TCP 连接，先后不保证）；LSPM/VMM 都要限权。原文 2017 年注："云商可能很快会提供标准化的 Docker 容器格式"——这条已经是现在时。

## 作者省略的前提

> [!note] 本节是补出来的，不在原文里。
> 每条句尾标来源：`（推演）` / `（见 §X.X）` / `（工程经验）`

| 省略了什么 | 补出来是什么 | 来源 |
|---|---|---|
| "每局重启"治的不只是泄漏 | 长命进程的**不变量侵蚀**（状态漂移、碎片、缓慢分叉）同样随重启归零。短命进程 = 把"全局状态永远正确"的证明义务降为"一局内正确"——与全量快照的幂等思想同源 | 工程经验 |
| LSPM/VMM 分层的本质 | **故障域分层 + 超时分级**：心跳杀进程是秒级自愈（机器还在），VMM 换 VM 是分钟级自愈（机器没了）。任何一层的问题由上一层兜底，不跨层灭火 | 推演 |
| 部署与匹配分离的接口形状 | 部署系统只暴露"启 / 停 / 向注册表登记"三个动词，匹配系统只认注册表——两边可各自换供应商而不惊动对方。窄接口是分离可行的前提 | 推演 + §13.3 |
| Node"没有竞争条件"的正确读法 | 单线程事件循环免的是**数据竞争**（无需锁），不是逻辑竞态——原文 §13.5 自己承认"异步交互为各种竞争条件提供了充分的机会"。跨请求的状态变更仍要 sequenceIndex/版本号这类手段 | 见 §13.2.3 与 §13.5 的张力 |
| Docker 注记的现在时 | 2017 年作者展望的容器标准化已成主流——本项目 `otf-server/Dockerfile` 就是 VMI 思想的轻量实现（OS + 可执行 + 入口脚本打进一个镜像） | 见 `技术参考.md` §1 |

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 游戏实例可无状态重启 | 每局重启 = 泄漏与漂移的自愈 | 实例间有长生命周期共享状态 → 重启策略要重新设计 |
| 心跳通道与游戏流量分离 | 监控独立于负载 | 心跳与应用同队列 → 过载时先死的是监控，故障被掩盖 |
| LSPM 有鉴权 | 供应系统只受自己人调遣 | 裸奔 → 任何人可烧你的云账单（DDoS 你的钱包） |
| 供应商 API 已抽象 | 换云商 = 换适配器 | 直调供应商 SDK → 迁移 = 重写部署层 |
