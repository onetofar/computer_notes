## 机制

### UE4：Actor 复制 + 三种角色

- **分层映射**：`ISocketSubsystem`（平台套接字抽象，≈第 3 章的跨平台封装）→ `FSocket`（**TCP/UDP 不分独立的类**，同一套 Send/Recv）→ `UNetDriver`（收包/过滤/发包，≈第 6 章的 NetworkManager，更底层一点，且按底层是 IP 还是 Steam 传输分实现）。
- **类层次**：`Actor`（一切游戏对象基类）→ `Pawn`（可被控制的 Actor）↔ `Controller`（`PlayerController` / `AIController`）。控制链：PlayerController 收输入 → 通知 Pawn → Pawn 生成 DodgeBall（Actor 子类）。

```text
             Actor
            /     \
          Pawn <-> Controller
                   /     \
         AIController   Player
                         Controller
```

（图 11.1。`Controller` 自己也是 `Actor`——理由是"Controller 仍然是需要被更新的游戏对象"：控制类与实体类同层，这不是命名巧合而是更新模型的一致性。）
- **拓扑：只有 C/S**。专用服务器（独立进程/机器）或监听服务器（一个实例既服务器又客户端）。
- **Actor 复制是单向的**：服务器 → 客户端，客户端永远不能把 Actor 复制给服务器。相关性三层手段：①引擎判定相关集合（Tribes ghost 同思路）；②**纯客户端本地 Actor**（临时粒子效果）——服务器根本不知道它存在；③`bAlwaysRelevant` 标记——**名字说 always，实际并不保证永远相关**（流量压力下仍会被优先级挤掉）。
- **三种角色**（按实例查询，同一 Actor 在不同实例上角色不同）：

| 角色 | 含义 | 例子（网络版躲避球） |
|---|---|---|
| 权威 authority | 本实例是这个 Actor 的最终权威 | 服务器查它生成的球 → 权威 |
| 模拟代理 simulated proxy | 服务器是权威，本端只模拟 | 客户端上的球 |
| 自治代理 autonomous proxy | 同模拟代理，但**吃本机玩家输入** | 客户端上自己的 Pawn |

- **属性级复制**：UE4 的游戏代码是 C++，引擎用**复杂的宏集合**在头文件里给变量标注复制信息（条件复制、"每当该属性从服务器复制过来就在客户端执行自定义函数"）；另有**蓝图**（基于流程图的脚本系统），大部分多人功能也能从蓝图访问。只复制"正确模拟所必需的"属性省带宽。`bReplicateMovement` 打开后引擎内置移动的客户端预测，可重写。
- **三种 RPC**：

| 类型 | 谁调 → 谁执行 | 关键纪律 |
|---|---|---|
| 服务器函数 | 客户端 → 服务器 | **只有该 Actor 的 owner（关联 PlayerController 的客户端）能调**；在别人的 Pawn 上调直接被忽略——引擎层面内置了 §10.2 的命令归属验证 |
| 客户端函数 | 服务器 → owner 的客户端 | 服务器判定"玩家 C 被消灭"后通知 C 的客户端 |
| 多播函数 | 服务器 → 服务器 + 所有客户端 | 全员本地生成粒子效果这类广播 |

  RPC 可标注可靠/不可靠——低优先级事件标不可靠，丢包时省性能。

### Unity UNET：通道 QoS + 属性同步

- **传输层**（`NetworkTransport`）：建连接不指定 UDP/TCP，而是按**用途**选通道 QoS——这是第 1 章"四类数据"的直接工业化：

| QosType | 语义 | 对应四类数据 |
|---|---|---|
| `Unreliable` | 无任何保证 | 非保障 |
| `UnreliableSequenced` | 不保证到达，**乱序直接丢** | 最近状态（旧值本来就无用） |
| `Reliable` | 连接不断就必达 | 保障 |
| `ReliableFragmented` | 可靠 + 大消息分片重组 | 保障（大载荷） |

  注意四档里**没有**"最快保障"——移动类数据在引擎里通常走 Unreliable/UnreliableSequenced + 客户端预测，"尽快"是靠发送频率和优先级实现而不是通道承诺。
- **对象模型**：`GameObject` = 组件容器，行为挂 `MonoBehaviour` 组件（行为描述更模块化，但组件间有依赖时编程变难——原文的优缺点并举）；网络行为必须继承 `NetworkBehaviour`。`NetworkManager` 三模式：纯客户端 / 纯（专用）服务器 / 主机（监听服务器）。
- **生成与复制**：服务器 `NetworkServer.Spawn` 生成并按**预制体（prefab）**注册表在客户端重生。属性同步两条路、**二选一**：
  - `[SyncVar]`：自动把变化复制到客户端（无需手动标脏）；但**结构体整块传输**——10 个成员动 1 个也传 10 个；
  - 重写 `OnSerialize/OnDeserialize` 手工读写——细粒度控制，但不能与 SyncVar 混用。
- **RPC**：`[Command]`（客户端 → 服务器，**只对玩家控制的对象有效**，方法名 `Cmd` 前缀）+ `[ClientRpc]`（服务器 → 客户端，`Rpc` 前缀）。与 Unreal 的"服务器函数"一样，Command 的"只许自己控制的对象"就是归属验证。
- **匹配**：`NetworkMatch`（`OnMatchCreate/OnMatchList/OnMatchJoined` 回调）——轻量比赛安排，指向第 12 章的玩家服务。

## 原书的数字与工程建议

| 原文位置 | 数字 / 建议 |

> 每条句尾标来源：`（推演）` / `（见 §X.X）` / `（工程经验）`

| 省略了什么 | 补出来是什么 | 来源 |
|---|---|---|
| 为什么两个引擎都**只做 C/S**、不做 P2P | §10.2 已证：P2P 下客户端无法验证彼此、全量状态人手一份（信息作弊无解）、带宽 O(n²)。引擎把拓扑收窄到 C/S = 把最难的验证问题和作弊面在架构上封死。这是"架构选择消灭一整类问题"的教科书案例 | 见 §10.2 + §1.2 |
| owner 与 authority 的区别为什么重要 | authority 是"谁说了算"（模拟归属），owner 是"谁的输入驱动它"（操作归属）。服务器 RPC 认 owner 不认 authority：向权威实例求证"这个客户端有没有权操作"没有意义——它自己就是权威；归属验证锚在操作者上 | 推演，依据 §11.1.4 的提醒 |
| SyncVar 整块传输的解法 | 第 5 章的属性脏位方案（按位标记哪些成员变了）就是给这个浪费设计的；手工 `OnSerialize` + 脏位 = 自制细粒度 SyncVar | 见 §5 + 工程经验 |
| UNET 高层 API 的时效 | 本书成文时 UNET 高层 API 是 Unity 主推；其后 Unity 官方已弃用该层（转向新 Netcode 与第三方方案）。**机制理解（通道 QoS、SyncVar 粒度、Command 归属）仍然成立**，API 名字按历史文献读 | 工程经验（时效标注） |
| 为什么 UE4 的移动预测默认内建 | 移动是"最快保障"类数据（§1.2），预测是它的标准配套（§8.3）；引擎把这对搭档做成一个开关，因为几乎所有 C/S 动作游戏都需要 | 见 §1.2 + §8 |

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 用引擎自带复制 | 中小工作室省掉传输/序列化/相关性整套自研 | 需要非 C/S 拓扑、自定义权威边界、或服务器逻辑与引擎解耦（如独立 C++ 进程）时，引擎网络层反而成为约束——本项目即此类 |
| 属性改动频率低且结构小 | SyncVar 省心 | 高频大结构 → 整块复制浪费带宽，手工序列化 + 脏位 |
| 服务器逻辑活在引擎对象模型里 | Role/RPC 声明式好用 | 服务器是独立进程（专用服务器跑无头逻辑）时，这些 API 的前提就被抽掉一半 |
