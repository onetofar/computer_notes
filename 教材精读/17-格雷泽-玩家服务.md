## 机制

### 接入与设计：pImpl 隔离（§12.1–12.2）

接入三步：同意 Steamworks SDK 条款 → 注册合作伙伴（NDA）→ 拿 AppID（开发期用 `steam_appid.txt` 顶替，但仍须登录 Steam 客户端；多账号测试必须多机/虚拟机——一台机器跑不了两个 Steam 实例）。

**设计红线：业务代码不认识 Steam。** 直调 SDK 函数散落全工程的两个代价：人人得懂 Steamworks；换平台（Steamworks→PSN）时处处动刀。解法 = **指向实现的指针**：

```cpp
class GamerServices
{
public:
  //lots of other stuff omitted
  //...

  //forward declaration
  struct Impl;
private:
  //pointer to implementation
  std::unique_ptr<Impl> mImpl;
};
```

`GamerServices.h` 零 Steam 引用；所有 `steam_api.h` 调用关进 `GamerServicesSteam.cpp`。将来接 Xbox Live = 新增一个 `GamerServicesXbox.cpp`，理论上一行业务代码不改。**性能论证**（原文自答）：pImpl 每个调用多一次指针解引用——渲染设备这类每帧海量调用的类不可接受，但玩家服务每帧调用寥寥，用灵活性换这点开销划算。功能膨胀时再拆（如独立 `GamerServiceSocket` 类），不要往一个类里堆。

**生命周期三条**：①`SteamAPI_Init` 必须在**渲染器初始化之前**——Steam overlay 挂钩 OpenGL，挂钩晚了叠加渲染就坏；②`SteamAPI_RunCallbacks()` **每帧一次**，回调靠它驱动；③专用服务器另有 `SteamGameServer_Init`（匿名登录模式，不要求用户账号）。

### 身份：服务分配，不再自造（§12.2.2）

第 6 章主对等体分配玩家 ID 的代码**整段删除**——玩家带着平台身份进场。`CSteamID` ↔ `uint64_t` 互转，工程上直接用 64 位整数：

```cpp
uint64_t GamerServices::GetLocalPlayerId()
{
  CSteamID myID = SteamUser()->GetSteamID();

  return myID.ConvertToUint64();
}

string GamerServices::GetLocalPlayerName()
{
  return string(SteamFriends()->GetPersonaName());
}
string GamerServices::GetRemotePlayerName(uint64_t inPlayerId)
{
  return string(SteamFriends()->GetFriendPersonaName(inPlayerId));
}
```

名字也改用平台 persona。原文的自我提醒值得保留：64 位假设只是 Steam 的现实，别家可能用 128 位 UUID——真要跨服务就再抽一层 `GamerServiceID`。

### 大厅与匹配（§12.3）

标准四步：按参数搜大厅 → 加入（或没有就创建）→ 大厅内配置/聊天/等人 → 启动并离开。Steamworks 的异步模式两个件：

- **调用句柄 + 回调配对**：异步调用返回 `SteamAPICall_t`，用 `CCallResult` 成员把句柄和回调绑在一起；**每个回调都带 `ioFailure` 布尔，为真直接 return**；
- **通用回调 = 事件订阅**：`STEAM_CALLBACK` 宏注册"有人进出大厅"（`LobbyChatUpdate_t`）这类不针对单次调用的通知——玩家表就靠它每变必刷（`UpdateLobbyPlayers`），因为握手包已被大厅功能替代，这是对等体获知成员变动的唯一通道。

**清单 12.3 / 12.4 —— 搜索与回调配对（异步模式的原型）**

```cpp
const char* kGameName = "robocatrts";

void GamerServices::LobbySearchAsync()
{
  //make sure it's Robo Cat RTS!
  SteamMatchmaking()->AddRequestLobbyListStringFilter("game",
                            kGameName, k_ELobbyComparisonEqual);

  //only need one result
  SteamMatchmaking()->AddRequestLobbyListResultCountFilter(1);

  SteamAPICall_t call = SteamMatchmaking()->RequestLobbyList();
  mImpl->mLobbyMatchListResult.Set(call, mImpl.get(),
                        &Impl::OnLobbyMatchListCallback);
}
```

```cpp
void GamerServices::Impl::OnLobbyMatchListCallback(LobbyMatchList_t* inCallback,
                               bool inIOFailure)
{
  if(inIOFailure) {return;}

  //if we find a lobby, enter, otherwise create one
  if(inCallback->m_nLobbiesMatching > 0)
  {
    mLobbyId = SteamMatchmaking()->GetLobbyByIndex(0);
    SteamAPICall_t call = SteamMatchmaking()->JoinLobby(mLobbyId);
    mLobbyEnteredResult.Set(call, this, &Impl::OnLobbyEnteredCallback);
  }
  else
  {
    SteamAPICall_t call = SteamMatchmaking()->CreateLobby( k_ELobbyTypePublic,
                                    4);
    mLobbyCreateResult.Set(call, this, &Impl::OnLobbyCreateCallback);
  }
}
```

两个件在这一对清单里齐全：`SteamAPICall_t` 句柄经 `CCallResult::Set` 绑到回调；回调首行先查 `inIOFailure` 再分派"有大厅就进、没有就建"——每个分支又是一个新的异步调用、新的句柄配对，链式到大厅就绪为止。

启动阶段的正确姿势（P2P 游戏）：`SetLobbyReady`（关闸不再进人）→ 对等体互开 P2P 会话 → 开赛 → `LeaveLobby`（人走光大厅自动销毁）。C/S 游戏则用 `SetLobbyGameServer` 把大厅绑到服务器（IP 或 Steam ID），全员收到 `LobbyGameCreated_t` 回调后连接。

### 联机路由：Steam 全包 NAT（§12.4）

```cpp
bool GamerServices::SendP2PReliable(const OutputMemoryBitStream&
                    inOutputStream, uint64_t inToPlayer)
{
  return SteamNetworking()->SendP2PPacket(inToPlayer,
                    inOutputStream.GetBufferPtr(),
                    inOutputStream.GetByteLength(),
                    k_EP2PSendReliable);
}
```

- **所有网络函数没有 IP 地址参数**——只认 Steam ID。两个原因（原文）：用户 IP 不暴露给其他用户（安全）；更重要的是 **NAT 穿越与中继由 Steam 处理**：能穿就穿，不能穿走中继服务器——"只要目标在线就有路由"。§6.3 的集中服务器方案被平台做成了基础设施。
- 传输模式四档：`k_EP2PSendReliable`（可靠，单包最多 **1MB** 自动分片重组）、`k_EP2PSendUnreliable`（类 UDP）、连接已建立的不可靠、带 Nagle 缓冲的可靠。
- **首包延迟几秒**：第一次给某人发包时 Steam 要协商路由；对端还会收到**会话请求回调**，必须 `AcceptP2PSessionWithUser`（收包前先验对方在游戏中，防陌生人骚扰），失败有对应回调。

```cpp
void GamerServices::Impl::OnP2PSessionRequest(P2PSessionRequest_t* inCallback)
{
  CSteamID playerId = inCallback->m_steamIDRemote;
  if(NetworkManager::sInstance->IsPlayerInGame(playerId.ConvertToUint64()))
  {
    SteamNetworking()->AcceptP2PSessionWithUser(playerId);
  }
}
```

由此倒逼启动流程改造：主对等体按回车后**不立即倒计时**，先进"就绪"态互发就绪包，全员会话建立后才"启动"——否则回合 0 的数据包要几秒才到，人人开局即高延迟。

### 统计 / 成就 / 排行榜（§12.5–12.8）

四个服务同一套骨架：请求（异步）→ 回调落地缓存 → 本地累积 → 显式提交。成就 ≈ 布尔型统计；排行榜 = 上传/下载条目列表；另有好友/游戏邀请等"其他服务"。细节全是 API 目录，机制没有超出本篇已记的异步回调模式——用到时回查 SDK 文档即可（成书于 2017，函数名以现行 SDK 为准）。

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 发布平台绑定玩家服务 | 身份/大厅/路由白拿 | 非平台渠道发行 → 这些基建要自建（§13 的服务器 + 自研匹配） |
| 平台服务可用（在线） | 大厅/路由零成本 | Steam 客户端离线/服务故障 → P2P 路由失效，需自有兜底 |
| pImpl 隔离彻底 | 换平台 = 换一个 .cpp | 业务代码混入 SDK 类型 → 迁移成本回到全工程 |
| 建联预热完成 | 开局无协商延迟 | 直接开打 → 回合 0 延迟几秒，体验崩坏 |

## 原文证据

> "所有这些网络函数中都没有涉及 IP 地址或套接字地址。这是故意的，因为 Steamworks 只允许通过 Steam ID 给特定的用户发送数据包……这使得 Steam 完全可以处理网络地址转换。"（§12.4）

> "当使用指向实现的指针时，意味着这个对象大量的成员函数调用都需要额外的指针引用。……但是，对于 GamerServices 对象每帧没有特别多的函数调用。因此在这种情况下，为了灵活降低一点性能是可以接受的。"（§12.2）
