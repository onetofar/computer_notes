## 1. 双缓冲指针交换

**做法**：帧读写用两个缓冲区 + 交换指针，不要每帧 `std::copy`。

**为什么**：每帧 memcpy 的成本与"缓冲区大小 × 帧率"成正比。缓冲区越大越吃亏，
而缓冲区大小往往由"单条最大消息"决定——这条成本会随着你支持的消息类型增长
而静默上升。指针交换是 O(1)。

**阈值**：缓冲区小（几 KB）时差异可忽略；超过 64KB 或帧率 >100 时开始值得。

## 2. 最小时间堆

**做法**：计时器种类 >10 时，从"每个对象各存一个倒计时"换成**一个全局最小时间堆**。

**为什么**：逐帧遍历所有倒计时是 O(对象数 × 计时器数)。对象数和计时器数相乘，
而两者都会增长。最小时间堆把这个乘积降成 O((n+m)log n)。

**阈值**：本项目（4 人房间、Boss 只有一套状态机计时器）**用简单倒计时**。
换时间堆是"计时器种类 >10"之后的事，不是"要做多人了"就该换。

**附带要求**：时间堆通常伴随"超时回调"，回调里做销毁要配合
[[01-彭放-epoll-Reactor工程规范]] 里的**增删延迟应用**——堆的 pop 过程本身也是一次遍历。

## 3. 对象池

**做法**：`Session` / `Room` 高频创建销毁时用池；**要做就配 `pool-show` 运行时可观测**。

**为什么**：池的价值不只是省 malloc。更重要的是**消除"分配失败"这个分支**——
内存紧张时的行为从"崩"变成"复用"。

**为什么必须可观测**：池的经典事故是"对象归还后仍被引用"，
症状是隔几十秒出现一次的诡异状态，**没有池的时候根本不会有这个 bug**，
所以出问题时没人会想到它。没有 `pool-show` 你连怀疑对象是哪个都做不到。

**阈值**：不是"有频繁创建"，是"创建频率 × 单次成本"已经能在 profile 里看见。

## 4. 消息按 msgId 建索引

**做法**：分发表用 `handler[msgId]`，不要每帧遍历所有消息做类型匹配。

**为什么**：前者的成本是 O(消息数)，后者是 O(消息数 × 消息类型数)。
9 条消息时两者都无所谓，几十条时差一个数量级。

**附带**：分发给目标实体时加 filter（只发给关心这个消息的实体），
否则每个包都要遍历房间内所有人，房间一大就是 O(包数 × 连接数)。

## 5. 信号只置标志，安全退出

**做法**：`signal` handler 里只 `g_running = false`，主循环看到后走正常的清理流程。

**为什么不是过度设计**：**Linux 下所有分析工具（gdb / valgrind / strace /  sanitizer）
都需要进程能安全退出**。在信号处理函数里直接 `exit()` 或做复杂清理会导致
- 锁处于不一致状态 → valgrind/helgrind 报假阳性甚至死锁
- 缓冲区里的数据没刷出去 → core dump 不完整
- 析构顺序不确定 → 关停时的崩溃比运行时的崩溃更难查

**这条是"调试基础设施要求业务代码"的典型例子**：不这么写，
线上出问题时你连一份可信的 core dump 都拿不到。

## 成立条件 / 失效边界

| 模式 | 引入阈值 | 不满足时套用的代价 |
|---|---|---|
| 双缓冲 | 缓冲区 >64KB 或帧率 >100 | 多一层缓冲管理状态，收益为负 |
| 时间堆 | 计时器种类 >10 | 多一个数据结构 + 一类并发 bug |
| 对象池 | 创建频率在 profile 里可见 | **多一类"归还后仍被引用"的 bug** |
| 消息索引 | 消息类型 >20 | 索引表与注册流程，收益为负 |
| 信号安全退出 | 用任何分析工具 | **core dump 不可信 / 停机崩溃** |

## 明确拒绝的做法

| 做法 | 来源 | 为什么拒绝 |
|---|---|---|
| 一次上全套（Actor + 无锁队列 + 对象池 + 时间堆） | "高性能服务器框架"类材料 | 本项目的瓶颈论点是**状态一致性**不是吞吐，带宽余量 20×、CPU 余量几个数量级。为不存在的压力加复杂度是负价值 |
| 契约生成器（protocol/gen.py） | 早期方案 | 规格就住在文档里，双端各一份 + 协议哈希握手校验，漂移在**连接握手上当场爆掉**。维护生成器的成本高于它防的风险 |

## 易错点

- **"没出问题"和"该上这个模式"是两回事**。本节的模式大多是**预防性**的，
  提前上会引入比它防的更隐蔽的 bug（对象池的悬垂引用、堆的并发问题）。
- **对象池的 bug 特征是"低频、随机、看起来像别的模块出错"**。
  遇到无法复现的诡异状态，先怀疑池和时间堆，再怀疑业务逻辑。
