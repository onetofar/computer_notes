## 原理

### 感知延迟 = ½RTT + IP

一个远端实体的画面从"服务器生成"到"玩家看到"，经历：

```
服务器生成状态 ──(½RTT 下行)──→ 客户端收到第 N 帧快照
                                        ↓
                              缓存，等第 N+1 帧到齐才能插值
                                        ↓
                              插值周期 IP（等 1000/snapshot_rate ms）
                                        ↓
                                   玩家看到
```

**为什么要等一帧才能插值**：只收到一个快照时，你只能显示它或猜它的下一状态。
收到两个之后才能在两点之间插值——这就是"插值"的前提。所以缓冲至少装两帧，
`IP ≥ 2 × 1000/snapshot_rate` 是**公式下限，不是调优建议**。

> 本项目：snapshot 10 Hz → 下限 200ms。`test_smoke.cpp` 断言
> `interpolation_delay_ms >= 2 * (1000/snapshot_rate)`。
> 调低会抖——**不是"抖一点点"，是退化成外推然后卡住**。

### RTT 只能用回环算

**正确做法**：客户端在发 `PlayerInput` 时把自己的 `timestamp` 打进包里，
服务器**原样回传**（放在下一个快照里），客户端收到时用
`now - 回传的 timestamp` 算 RTT。

**错误做法**：`now_客户端 - 服务器给的服务器时间`。

**为什么错**：两端时钟**不同源**。Windows 与 WSL/Linux 的时钟各有漂移和时区处理，
差值里混着的是"时钟偏移"而不是"网络延迟"。这个数看起来是个合理的几十毫秒，
**但它会随时间漂移**，且漂移量无法与真实延迟区分——用它做自适应插值会得到
"延迟时高时低但找不到原因"的行为。

> ⚠️ 这条在两本书里都是散落在正文的一句话，**没有代码**。
> 所以它必须被写进规格，否则下一个人会凭直觉写"用服务器时间"。

### 外推必须切成小步

丢包时客户端要外推（extrapolate）远端实体的位置。**不能一步算到位**，
要切成 ≤33ms 的小步重跑。

**为什么**：一步外推用的是恒定速度假设。一步跨 200ms 时，
撞墙/转向/边界这些非线性约束全被跳过，结果是**穿墙**。
切成小步重跑，每步都会重新应用约束。

> 格雷泽给的 1/30s 是硬编码经验值。**本项目 tick = 50ms，比它大**，
> 所以分段必须 ≤33ms（至少 2 段/tick），不能照抄 1/30s。

### 冗余发送输入

客户端发最近 3 条输入（不只是最新一条），服务器按 `seq` **幂等去重**。

**为什么**：丢一个输入包会让玩家"顿一下"——服务器那一 tick 收到的是上一条输入，
玩家按键的那一 tick 没生效。冗余发送让丢失被后续包自动补上。

`seq` 的幂等去重是必须的：**重传或乱序到达的旧输入不能被二次应用**，
否则玩家会莫名倒退。

## 关键数字

| 量 | 值 | 来源 |
|---|---|---|
| MSS | 1500 − 20(IP) − 20(TCP) = 1460 | 格雷泽 |
| 安全载荷建议 | **≤1300** | 格雷泽（留对齐余量） |
| 传播延迟 | 0.3 ns/m（光纤中） | 格雷泽 |
| 容忍度 VR | <20ms | VR 游戏 |
| 容忍度 FPS | 16–150ms | 第一人称射击 |
| 容忍度 **RTS** | **可到 500ms** | 即时战略 |
| 外推分段 | 1/30s（书里的经验值） | 需按 tick 频率重算 |
| 外推上限 | **必须有** | 无上限外推比卡住更糟 |

## 成立条件 / 失效边界

| 结论 | 成立条件 | 越界会怎样 |
|---|---|---|
| `IP ≥ PP` | 插值渲染 | 插值退化为外推，丢包即穿墙 |
| RTT 回环算 | 客户端与服务器时钟不同源 | 混入时钟偏移，随时间漂移且无法与延迟区分 |
| 外推 ≤33ms 分段 | 有碰撞/边界约束的实体 | 一步外推跳过约束 → 穿墙 |
| 输入冗余 3 条 | 输入包可能丢失 | 丢包 → 玩家按键那一 tick 不生效（"顿一下"） |
| 外推有上限 | 长时间丢包 | 无上限 → 实体飞到墙外，看起来像 bug |

## 明确拒绝的做法

| 做法 | 为什么拒绝 |
|---|---|
| 用服务器时钟戳算 RTT | 时钟不同源，差值混入时钟偏移。**看起来合理但会漂移** |
| 调低 `interpolation_delay_ms` 换"手感实时" | 低于公式下限就退化成外推，丢包即穿墙 |
| 照抄 1/30s 外推分段 | 本项目 tick 50ms > 33ms，**书的经验值是按它自己的 tick 定的** |
| 无上限外推 | 实体飞到墙外。**看起来像 bug 而不是网络问题** |

## 易错点

- **"感知延迟"和"RTT"混用**是最常见的错误。RTT 是网络指标，感知延迟是玩家指标，
  两者差一个插值周期。**用 RTT 论证"这延迟可以接受"是错的论证**。
- **冗余发送不等于重传**。冗余是"每包都带最近 3 条"（防丢），
  重传是"丢了再发"（需要超时判断）。前者更简单也更可靠。
- **丢包常成串出现**（burst），不是均匀随机。做网络条件模拟时
  必须能配"连续丢 N 个包"，否则测不出插值缓冲被打穿时的行为。
