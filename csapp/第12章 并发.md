## 🧱 主线基础层【对应12.1~12.2】※※※
### 1. 并发编程基础定义（12.1）
#### 1.1 核心概念
- **并发**：多个逻辑流在时间上重叠执行，宏观同时推进（单核/多核均可）
- **并行**：多个逻辑流在**同一时刻**同时执行，是并发的真子集（仅多核）
- **逻辑流**：程序执行的一条独立路径，可以是进程、线程或事件处理函数
#### 1.2 并发核心价值
- I/O重叠 → 提升吞吐量（一个流等待I/O时，其他流可执行）
- 多核并行 → 提升计算效率
- 事件驱动 → 提升响应速度
#### 1.3 并发编程的3个核心挑战
| 挑战         | 说明                   | 后果                     |
| --------- | ---------------------- | ------------------------ |
| 竞争条件     | 多线程并发修改共享数据 | 结果不可预测，数据损坏   |
| 调度不可控   | 内核调度顺序不确定     | bug难以复现，调试困难    |
| 并发特有故障 | 死锁、饥饿、活锁       | 仅在并发场景出现，定位难 |
#### 1.4 逻辑流的3种形态（对应三种并发模型）
- **进程级逻辑流**：内核调度，独立地址空间（隔离性最强，开销最大）
- **事件驱动逻辑流**：用户态调度，单地址空间（I/O多路复用）
- **线程级逻辑流**：内核调度，共享进程地址空间（平衡开销与通信）
### 2. 基于进程的并发编程
#### 2.1 核心原理
- 父进程`accept`客户端连接 → `fork`子进程 → 子进程处理请求，父进程继续监听
#### 2.2 标准实现流程
```c
listenfd = open_listenfd(port);
while (1) {
    connfd = accept(listenfd, ...);
    if (fork() == 0) {
        close(listenfd);      // 子进程关闭监听fd
        echo(connfd);         // 处理请求
        close(connfd);
        exit(0);
    }
    close(connfd);            // 父进程关闭已连接fd（引用计数-1）
}
```
#### 2.3 核心特性
- **独立地址空间**：一个进程崩溃不影响其他进程（高隔离性）
- **高fork开销**：每次连接都要创建新进程（不适合高并发短连接）
- **IPC复杂**：进程间通信需要管道、共享内存、消息队列等
#### 2.4 关键注意点
- **文件描述符引用计数**：`fork`后父子进程共享文件表项，必须互相关闭冗余fd，否则资源泄漏
- **僵尸进程回收**：必须通过`wait`/`waitpid`处理`SIGCHLD`信号，非阻塞循环回收避免漏回收
- **信号中断**：`accept`等系统调用可能被信号中断，需处理`EINTR`错误
#### 2.5 落地选型
- **适用**：强隔离业务（CGI、容器化服务、安全要求高的场景）
- **不适用**：高并发短连接（fork开销过大）
- **Java关联**：`ProcessBuilder`创建子进程，容器化微服务
### 3. 基于I/O多路复用的并发编程
#### 3.1 核心原理
- 通过`select`/`poll`/`epoll`监听多个文件描述符，就绪时触发事件处理，单线程串行驱动所有逻辑流
#### 3.2 标准实现流程
```c
listenfd = open_listenfd(port);
FD_ZERO(&read_set);
FD_SET(listenfd, &read_set);
while (1) {
    ready_set = read_set;
    select(..., &ready_set, ...);
    for (fd in ready_set) {
        if (fd == listenfd) {
            connfd = accept(listenfd, ...);
            FD_SET(connfd, &read_set);
        } else {
            echo(fd);
            FD_CLR(fd, &read_set);
            close(fd);
        }
    }
}
```
#### 3.3 核心特性
- **无进程/线程创建开销**：单线程处理所有连接
- **单地址空间**：无共享变量竞争（天然线程安全）
- **事件驱动**：精细控制I/O事件
- **无法利用多核**：CPU密集型任务会阻塞所有连接
#### 3.4 事件触发模式
| 模式         | 触发条件             | 特点                      | 典型应用             |
| ------------ | -------------------- | ------------------------- | -------------------- |
| 水平触发(LT) | fd有数据就持续触发   | 编程简单，不易丢事件      | select, poll         |
| 边缘触发(ET) | fd状态变化时触发一次 | 必须搭配非阻塞I/O，高性能 | epoll (Nginx, Redis) |
#### 3.5 五种I/O模型（原书隐含，Java NIO基础）
| 模型        | 阻塞阶段           | 数据准备阶段 | 通知方式 |
| ----------- | ------------------ | ------------ | -------- |
| 阻塞I/O     | 全程阻塞           | 阻塞         | 无       |
| 非阻塞I/O   | 不阻塞             | 轮询         | 主动查询 |
| I/O多路复用 | 阻塞在select/epoll | 不阻塞       | 事件通知 |
| 信号驱动I/O | 不阻塞             | 不阻塞       | 信号通知 |
| 异步I/O     | 不阻塞             | 不阻塞       | 完成通知 |
#### 3.6 工业落地
- **主从Reactor多线程模型**：Netty核心架构，主线程监听连接，从线程池处理I/O事件
- **select限制**：最大fd由`FD_SETSIZE`限制（默认1024），epoll无上限
- **Java关联**：Java NIO的`Selector`，Netty的`EventLoop`
### 4. 基于线程的并发编程
#### 4.1 线程定义
- 进程内的轻量级执行流，内核调度的最小单位（LWP，轻量级进程）
#### 4.2 线程组成
| 组成部分       | 说明                 | 共享/私有            |
| -------------- | -------------------- | -------------------- |
| 程序计数器(PC) | 指向下一条执行指令   | 私有（每个线程独立） |
| 寄存器组       | 线程上下文           | 私有                 |
| 线程栈         | 局部变量、函数调用栈 | 私有                 |
| 代码段         | 程序指令             | 共享                 |
| 数据段         | 全局/静态变量        | 共享                 |
| 堆             | 动态分配内存         | 共享                 |
| 文件描述符表   | 打开的文件           | 共享                 |
#### 4.3 核心特性
- **中等创建开销**（比进程轻量，比事件驱动重）
- **共享地址空间** → 通信简单（直接读写共享变量），但需要同步
- **可利用多核** → 真正并行
- **需处理同步问题**：竞争条件、死锁、可见性
#### 4.4 线程两种属性
| 属性               | 说明                       | 资源回收         | 可被join |
| ------------------ | -------------------------- | ---------------- | -------- |
| 可结合态(joinable) | 默认，终止后不自动释放资源 | 需`pthread_join` | 是       |
| 分离态(detached)   | 终止后系统自动回收         | 自动             | 否       |
#### 4.5 Java关联
- Java `Thread`类本质是对内核轻量级进程的封装
- JVM线程模型：1:1映射到操作系统线程（Linux NPTL）

## ⚙️ 核心原理层：线程与共享变量【对应12.3~12.4】※※※

### 1. Posix线程(Pthread)核心机制

#### 1.1 线程生命周期
- 创建 → 就绪 → 运行 → 阻塞 → 终止

#### 1.2 线程终止方式
| 方式     | API                | 说明                 |
| -------- | ------------------ | -------------------- |
| 正常返回 | `return`           | 线程入口函数返回     |
| 主动终止 | `pthread_exit`     | 调用后终止自身       |
| 被取消   | `pthread_cancel`   | 其他线程发送取消请求 |
| 进程终止 | `exit`或`main`返回 | 所有线程随之终止     |

#### 1.3 线程取消机制（12.9节核心）
- **取消点**：内核预设的安全取消位置（如系统调用、`pthread_testcancel`）
- **取消状态**：
  - 可取消（默认）：收到取消请求后在下一个取消点终止
  - 不可取消：`pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, ...)`
- **取消类型**：
  - 延迟取消（默认）：到达取消点才终止
  - 异步取消（极少用）：立即终止，可能导致资源泄漏
- **坑点**：未处理取消点会导致资源泄漏、死锁（如持有锁时被取消）

#### 1.4 核心API
| API                  | 作用                   |
| -------------------- | ---------------------- |
| `pthread_create`     | 创建线程               |
| `pthread_join`       | 等待线程终止，回收资源 |
| `pthread_detach`     | 设置分离态             |
| `pthread_self`       | 获取线程ID             |
| `pthread_equal`      | 比较线程ID             |
| `pthread_cancel`     | 取消线程               |
| `pthread_testcancel` | 设置取消点             |

#### 1.5 线程传参核心规范与坑点
- **错误场景**：循环中传递局部变量`i`的地址，主线程修改`i`导致子线程读取错误值
- **正确方案**：
  1. `malloc`独立内存块，每个线程传独立地址，子线程内`free`
  2. 值传递（强转`void*`，注意平台兼容性）
  3. 主线程等待子线程读取完成后再修改（需同步）
- **练习题12.13/12.14结论**：禁止主线程提前`free`传参的内存块，必须子线程读取完成后再释放

#### 1.6 线程私有存储(TSD)
- **作用**：为每个线程分配独立私有数据，解决静态变量共享问题
- **API**：`pthread_key_create`、`pthread_setspecific`、`pthread_getspecific`
- **Java关联**：完全对应`ThreadLocal`

### 2. 多线程共享变量与内存模型

#### 2.1 共享变量判定规则
| 变量类型     | 存储位置 | 是否共享 | 说明                 |
| ------------ | -------- | -------- | -------------------- |
| 全局变量     | 数据段   | 是       | 所有线程共享         |
| 静态变量     | 数据段   | 是       | 所有线程共享         |
| 局部自动变量 | 线程栈   | 否       | 私有（指针逃逸除外） |
| 局部静态变量 | 数据段   | 是       | 所有线程共享         |
| 堆内存       | 堆       | 是       | 通过指针共享         |

#### 2.2 临界区
- 定义：访问共享变量的代码片段，必须保证同一时间只有一个线程进入执行

#### 2.3 竞争条件(Race Condition)
- **定义**：多个线程并发访问共享变量，执行结果依赖于线程调度顺序
- **判定规则**：多线程并发访问共享变量，且至少有一个执行写操作
- **产生原因**：非原子的读-修改-写操作被多线程交替执行
- **典型场景**：多线程累加全局计数器 `counter++`
  - 汇编层面：`mov counter, %rax; add $1, %rax; mov %rax, counter`（3步）
  - 两个线程交替执行可能导致丢失更新
- **核心危害**：结果不可预测，难以复现和调试

#### 2.4 内存可见性问题
- **问题本质**：编译器优化（寄存器缓存）和CPU缓存（多核私有L1/L2）导致一个线程的修改对其他线程不可见
- **示例**：
  ```c
  int flag = 0;  // 共享变量
  void thread1() { flag = 1; }
  void thread2() { while (flag == 0); }  // 可能永远看不到flag=1
  ```
- **解决方案**：
  - 互斥锁（`pthread_mutex_lock`）强制刷新缓存
  - 内存屏障（`asm volatile("" ::: "memory")`）
  - Java `volatile`关键字
- **Java关联**：JMM（Java内存模型）定义了`volatile`的内存屏障语义

## 🔮 灵魂机制层：同步与线程安全【对应12.5~12.7】※※※

### 1. 信号量与线程同步核心机制

#### 1.0 进度图（Progress Graph）——并发正确性的理论基础（原书 §12.5.1）※※※
- **核心思想**：将 n 个线程的执行建模为 n 维空间中的轨迹（trajectory）
- 每个维度代表一个线程的指令执行进度
- 轨迹从原点出发，沿坐标轴方向移动（同一时刻只有一个线程前进）
- **临界区**在进度图上对应**禁区（Forbidden Region）**——两个线程同时进入临界区对应的矩形区域
- **安全轨迹**：不穿越任何禁区的轨迹。不安全轨迹=至少一个时刻两线程同时处于临界区
- 关键结论（原书 Figure 12.19）：互斥信号量（初始值=1）将进度图分为安全区域和不安全区域——信号量操作相当于在轨迹与禁区边界处设置"旋转门"，保证轨迹永远不会进入禁区
- **Java 关联**：`synchronized` 的 monitorenter/monitorexit 等价于在进度图上自动插入禁区检查

#### 1.1 信号量定义与 PV 操作的形式化语义（原书 §12.5.2）※※※

- **本质**：非负整数全局变量，提供两个原子操作P（wait）和V（post）
- **P操作**（`sem_wait`）：信号量减1，结果<0时线程阻塞
- **V操作**（`sem_post`）：信号量加1，若有阻塞线程则唤醒一个
- **原子性**：由内核保证，不会被中断打断

#### 1.2 信号量两种类型
| 类型       | 存储     | 用途                             |
| ---------- | -------- | -------------------------------- |
| 无名信号量 | 内存     | 同一进程内线程间同步（原书示例） |
| 有名信号量 | 文件系统 | 不同进程间同步                   |

#### 1.3 核心API
```c
#include <semaphore.h>
sem_init(sem_t *sem, int pshared, unsigned int value);
sem_wait(sem_t *sem);   // P操作
sem_post(sem_t *sem);   // V操作
sem_destroy(sem_t *sem);
```

#### 1.4 两种核心用法
| 用法               | 初始值 | 作用                     |
| ------------------ | ------ | ------------------------ |
| 互斥锁(二元信号量) | 1      | 保护临界区，保证互斥访问 |
| 计数信号量         | N      | 资源计数，控制并发数量   |

#### 1.5 唤醒顺序与饥饿问题
- POSIX信号量**无强制FIFO唤醒顺序**，默认随机唤醒
- 可能导致线程饥饿（某些线程长期不被调度）
- **栈(LIFO)信号量**：最早阻塞的线程永远不被唤醒，是饥饿的极端场景

#### 1.6 Java关联
- 二元信号量 → `synchronized`、`ReentrantLock`
- 计数信号量 → `java.util.concurrent.Semaphore`

### 2. 条件变量+互斥锁（工业界主流方案）

#### 2.1 核心本质
- 用于等待某个条件成立，避免轮询消耗CPU
- 必须与互斥锁配合使用

#### 2.2 核心API
```c
pthread_mutex_lock(&mutex);
while (!condition) {
    pthread_cond_wait(&cond, &mutex);  // 释放锁并阻塞
}
// 条件满足，执行操作
pthread_mutex_unlock(&mutex);
```
- `pthread_cond_signal`：唤醒一个等待线程
- `pthread_cond_broadcast`：唤醒所有等待线程

#### 2.3 标准使用模式
```c
// 等待方
pthread_mutex_lock(&mutex);
while (!condition) {
    pthread_cond_wait(&cond, &mutex);
}
// 条件满足
pthread_mutex_unlock(&mutex);

// 通知方
pthread_mutex_lock(&mutex);
condition = 1;
pthread_cond_signal(&cond);
pthread_mutex_unlock(&mutex);
```

#### 2.4 Java关联
- 完全对应 `Object.wait()`/`notify()`/`notifyAll()`
- `java.util.concurrent.locks.Condition`

### 3. 经典同步模型实现

#### 3.1 生产者-消费者（有界缓冲区）
- **信号量设计**：
  - `mutex` = 1（保护缓冲区）
  - `empty` = n（空槽位数）
  - `full` = 0（满槽位数）
- **执行逻辑**：
  ```c
  // 生产者
  sem_wait(&empty);
  sem_wait(&mutex);
  put(item);
  sem_post(&mutex);
  sem_post(&full);
  
  // 消费者
  sem_wait(&full);
  sem_wait(&mutex);
  get(item);
  sem_post(&mutex);
  sem_post(&empty);
  ```
- **注意**：`mutex`必须在`empty`/`full`之后P，否则可能导致死锁
- **Java关联**：`BlockingQueue`（`ArrayBlockingQueue`, `LinkedBlockingQueue`）

#### 3.2 读者-写者模型
| 模型     | 规则                               | 问题     | Java对应                               |
| -------- | ---------------------------------- | -------- | -------------------------------------- |
| 读者优先 | 有读者时写者阻塞，新读者可直接进入 | 写者饥饿 | `ReentrantReadWriteLock`（非公平模式） |
| 写者优先 | 有写者等待时新读者阻塞             | 读者饥饿 | 自定义实现                             |
| 公平模型 | 按到达顺序排队                     | 无饥饿   | `ReentrantReadWriteLock`（公平模式）   |

#### 3.3 哲学家就餐问题（死锁经典）
- **场景**：5个哲学家，5根筷子，每人需同时拿左右两根筷子才能吃饭
- **死锁场景**：所有人同时拿起左边筷子 → 永远等不到右边筷子
- **解决方案**：
  1. 统一加锁顺序（先拿编号小的筷子）
  2. 最多允许4个哲学家同时拿筷子
  3. 必须同时拿到两根筷子才能执行（原子获取）

### 4. 线程安全与可重入性

#### 4.1 线程安全4个等级
| 等级         | 说明                            | 示例                     |
| ------------ | ------------------------------- | ------------------------ |
| 不可线程安全 | 多线程并发一定出问题            | `strtok`（使用静态变量） |
| 条件线程安全 | 特定场景下安全                  | 单线程或加锁后           |
| 线程安全     | 任意多线程调用正确              | `strtok_r`（可重入版本） |
| 异步信号安全 | 线程安全+可在信号处理函数中调用 | `write`, `_exit`         |

#### 4.2 4类线程不安全函数
| 类型  | 问题                   | 典型示例                     | 解决方案                       |
| ----- | ---------------------- | ---------------------------- | ------------------------------ |
| 第1类 | 不保护共享变量         | 多线程累加计数器             | 加互斥锁                       |
| 第2类 | 跨多次调用保持状态     | `rand()`/`srand()`           | 改用可重入版本`rand_r()`       |
| 第3类 | 返回指向静态变量的指针 | `ctime()`, `gethostbyname()` | 线程私有存储或调用者提供缓冲区 |
| 第4类 | 调用了不安全函数       | 同上                         | 修改被调用函数或用锁保护       |

#### 4.3 可重入性
- **定义**：函数被多个线程调用时，不访问任何共享资源，仅依赖调用者传入的状态
- **分类**：
  - **显式可重入**：所有参数值传递，所有数据为局部自动变量
  - **隐式可重入**：允许访问共享变量，但用互斥锁保护
- **关系**：可重入函数一定是线程安全的，但线程安全函数不一定是可重入的
- **典型示例**：`rand_r()`（可重入随机数函数）
- **注意**：可重入仅保证无共享资源竞争，不保证业务结果唯一性（如相同种子产生相同序列）

#### 4.4 异步信号安全函数
- **定义**：在信号处理函数中调用也不会出现问题（必须是可重入的）
- **规则**：信号处理函数中只能调用异步信号安全函数（如`write`, `_exit`），禁止调用`printf`, `malloc`等
- **Java关联**：JVM内部信号处理也遵循此规则

### 5. 死锁核心原理与规避

#### 5.1 死锁定义
- 多个线程互相等待对方持有的资源，所有线程永久阻塞，无法推进

#### 5.2 死锁产生的4个必要条件（Coffman条件）
| 条件       | 说明                       | 破坏方法                 |
| ---------- | -------------------------- | ------------------------ |
| 互斥       | 资源一次只能被一个线程持有 | 无锁编程、只读共享       |
| 持有并等待 | 持有资源同时请求其他资源   | 一次性申请所有资源       |
| 不可抢占   | 资源只能由持有者释放       | 申请失败时释放已持有资源 |
| 循环等待   | 线程间形成循环等待链       | 统一加锁顺序（全序）     |

#### 5.3 死锁可视化：进度图
- 横轴/纵轴：两个线程的执行进度（P/V操作）
- 禁止区：信号量临界区
- 死锁状态：轨迹进入的死点，所有方向被禁止区阻挡

#### 5.4 死锁规避方案
- **统一加锁顺序**：给所有互斥锁定义全局全序，所有线程按相同顺序获取锁（原书核心方案）
- **银行家算法**：避免死锁（操作系统课程）
- **死锁检测+恢复**：超时机制、`jstack`检测

#### 5.5 活锁（与死锁并列的并发故障）
- **定义**：线程没有阻塞，但一直在重复相同操作，无法推进
- **典型场景**：两个线程互相谦让，同时释放锁又同时尝试获取，无限循环
- **解决方案**：随机退让时间、固定优先级

#### 5.6 优先级反转（补充）
- **定义**：低优先级线程持有锁，高优先级线程等待，导致高优先级被阻塞
- **典型场景**：实时系统
- **解决方案**：优先级继承协议（如POSIX `pthread_mutexattr_setprotocol`）

#### 5.7 Java关联
- 死锁排查：`jstack`命令查看线程栈，检测死锁
- JUC锁的公平性设计（`ReentrantLock`公平/非公平）
- 分布式锁的死锁规避（超时、心跳）

## 🛠️ 落地实操层：并发服务器与性能优化

### 1. 经典并发服务器落地实现

#### 1.1 动态线程并发服务器
- **逻辑**：`accept`后立即创建线程处理连接
- **优缺点**：响应快，无进程开销；但频繁创建销毁有开销，无连接数控制

#### 1.2 预线程化(Prethreading)服务器（线程池）
- **核心组件**：
  - 主线程（生产者）：`accept`连接，放入共享缓冲区
  - 共享缓冲区(SBUF)：有界队列，用信号量实现
  - 工作线程池（消费者）：从缓冲区取连接处理
- **进阶优化**：核心线程数、最大线程数、空闲超时、拒绝策略
- **领导者-追随者模型**：
  - 一个领导者监听事件，收到后选举新领导者，自己处理事件
  - 避免共享缓冲区锁竞争，性能更高
  - 应用：Redis、Memcached
- **Java关联**：`ThreadPoolExecutor`线程池，`ExecutorService`

### 2. 并发程序性能与并行性优化

#### 2.1 核心性能指标
| 指标             | 公式                             | 说明                    |
| ---------------- | -------------------------------- | ----------------------- |
| 加速比(Speedup)  | S_p = T_1 / T_p                  | p核并行速度提升倍数     |
| 效率(Efficiency) | E_p = S_p / p                    | 并行资源利用率          |
| Amdahl定律       | S_p ≤ 1 / (α + (1-α)/p)          | 串行部分α决定加速比上限 |
| 强扩展           | 固定问题规模，增加核心           | 衡量加速比              |
| 弱扩展           | 每核心规模固定，总规模随核心增加 | 衡量并行效率            |

#### 2.2 并行程序性能瓶颈
- 串行部分占比（Amdahl定律）
- 锁竞争：频繁加锁导致线程阻塞，CPU利用率低
- 线程切换开销：过多线程导致内核频繁上下文切换
- 缓存一致性开销：多核缓存同步（MESI协议）
- 伪共享：多核修改同一缓存行内不同变量，导致缓存行反复失效

#### 2.3 性能优化方案
| 问题       | 优化方向                                              |
| ---------- | ----------------------------------------------------- |
| 串行部分   | 重构代码，最大化并行区域                              |
| 锁竞争     | 细粒度锁、读写锁、线程本地存储(ThreadLocal)、无锁编程 |
| 线程数量   | 匹配CPU核心数（通常设为核心数×1~2）                   |
| 伪共享     | 缓存行填充（`@Contended`）                            |
| 内核态切换 | 批量操作，减少系统调用                                |

#### 2.4 无锁编程：CAS原子操作
- **本质**：Compare And Swap，CPU硬件级原子操作（如x86的`lock cmpxchg`）
- **执行逻辑**：比较内存值是否等于预期旧值，相等则更新为新值，否则重试
- **优势**：无内核态切换，高并发下性能优于锁
- **缺陷**：
  - ABA问题（值被改回原值，CAS误认为未修改）
  - 高竞争下重试消耗CPU
  - 只能保证单个变量的原子性
- **Java关联**：`AtomicInteger`、`Unsafe.compareAndSwapInt()`

#### 2.5 内存屏障与JMM
- **内存屏障**：`mfence`（全屏障）、`lfence`（读屏障）、`sfence`（写屏障）
- **作用**：强制刷新CPU缓存，保证内存可见性，阻止指令重排序
- **Java关联**：
  - `volatile`：写前插入`StoreStore`，写后插入`StoreLoad`；读前插入`LoadLoad`，读后插入`LoadStore`
  - JMM（Java内存模型）定义了`happens-before`规则

### 3. 本章核心易错点与避坑指南

| 易错点         | 说明                     | 解决方案                           |
| -------------- | ------------------------ | ---------------------------------- |
| 线程传参竞争   | 循环传局部变量地址       | 独立内存块或值传递                 |
| 信号量顺序错误 | 互斥锁P在资源计数P之后   | 互斥锁P必须在资源计数P之后         |
| 加锁顺序相反   | 不同线程按不同顺序加锁   | 统一全序（如按地址大小）           |
| 线程不安全函数 | 使用含静态变量的库函数   | 改用`_r`可重入版本                 |
| 僵尸线程       | 未join或detach           | `pthread_join`或`pthread_detach`   |
| 内存可见性     | 共享变量未用锁或volatile | 用锁保护或加`volatile`             |
| 死锁隐蔽性     | 难以复现                 | `jstack`检测，统一加锁顺序         |
| 多线程与信号   | 信号递送到任意线程       | 专门创建信号处理线程               |
| i++非原子      | 读-改-写三步             | 用锁或原子操作                     |
| 线程取消坑点   | 未处理取消点             | 设置清理函数`pthread_cleanup_push` |

### 4. 标准临界区代码模板

#### 4.1 互斥锁保护共享变量
```c
pthread_mutex_lock(&mutex);
// 临界区
pthread_mutex_unlock(&mutex);
```

#### 4.2 生产者-消费者模板（信号量）
见3.1节

#### 4.3 读者-写者模板（读者优先）
```c
int readcnt = 0;
sem_t mutex, w;
sem_init(&mutex, 0, 1);
sem_init(&w, 0, 1);

// 读者
sem_wait(&mutex);
readcnt++;
if (readcnt == 1) sem_wait(&w);
sem_post(&mutex);
// 读操作
sem_wait(&mutex);
readcnt--;
if (readcnt == 0) sem_post(&w);
sem_post(&mutex);

// 写者
sem_wait(&w);
// 写操作
sem_post(&w);
```

#### 4.4 信号阻塞临界区模板（防止信号中断）
```c
sigset_t mask, prev;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigprocmask(SIG_BLOCK, &mask, &prev);
// 临界区
sigprocmask(SIG_SETMASK, &prev, NULL);
```

## 📐 线程安全四级分类（原书 §12.7.1）※※※

原书提出了经典的线程安全四级分类法，是判断一个函数能否在多线程环境中安全调用的标准框架：

| 级别 | 名称 | 定义 | 示例 | Java 对应 |
|------|------|------|------|----------|
| 1 | **线程安全（Thread-Safe）** | 多线程并发调用总能产生正确结果 | 无共享状态的函数、正确同步的函数 | `ConcurrentHashMap`, `AtomicInteger` |
| 2 | **有条件线程安全（Conditionally Safe）** | 调用者遵守特定约束时线程安全 | `malloc` 在单线程时，但分配器内部有锁 | 需外部同步的集合（`Collections.synchronizedList`） |
| 3 | **线程不安全（Thread-Unsafe）** | 完全未保护共享状态 | `strtok`（使用静态缓冲区保存 token 位置） | `SimpleDateFormat`（共享时线程不安全） |
| 4 | **不可重入（Non-Reentrant）** | 未释放锁时重入导致死锁（比不安全更危险） | 递归调用 P 操作在同一信号量上 | `synchronized` 是可重入的（JVM 设计保障） |

### 可重入（Reentrancy）精确定义（原书 §12.7.2）※※※
- **可重入函数**：即使在被中断后（信号处理器或其他线程）再次被调用，仍能产生正确结果
- 两类可重入函数：
  1. **显式可重入**：所有状态由调用者通过指针传入（无全局/静态变量），如 `rand_r(seed)` vs 线程不安全的 `rand()`
  2. **隐式可重入**：通过互斥锁保护共享状态，调用者透明
- **关键测试**：如果一个函数 A 正在执行时，信号处理器中又调用了 A，且 A 的两个调用互不干扰 → A 是可重入的

### 死锁（原书 §12.7.5）※※※
- **定义**：多个线程各自持有对方等待的资源，形成循环等待，所有线程永久阻塞
- **形成条件**（四个条件同时满足）：
  1. 互斥（Mutual Exclusion）：资源一次只能分配给一个线程
  2. 持有并等待（Hold and Wait）：线程已持有资源，还在等待其他资源
  3. 不可抢占（No Preemption）：资源不能被强制剥夺
  4. 循环等待（Circular Wait）：存在线程-资源的循环依赖链
- **规避策略**：
  - 全局锁序（Lock Ordering）：所有线程按相同顺序获取锁（原书推荐方法）
  - `pthread_mutex_trylock`：尝试获取锁，失败则释放所有已持锁重试
  - 减少锁粒度（Lock Granularity）：用多个小锁代替一个大锁

## ❌ 避坑层【全章易错点速查】

1. **线程传参**：禁止循环传局部变量地址，必须用独立内存块或值传递
2. **信号量顺序**：互斥锁P必须在资源计数P之后，否则死锁
3. **加锁顺序**：多个锁必须按统一全序获取
4. **线程不安全函数**：避免使用含静态变量的库函数，优先用`_r`可重入版本
5. **僵尸线程**：必须`join`或`detach`线程
6. **内存可见性**：共享变量必须用锁保护或`volatile`
7. **死锁**：统一加锁顺序，用`jstack`检测
8. **多线程与信号**：信号会递送到任意线程，需专门处理
9. **i++不是原子**：必须用锁或原子操作
10. **线程取消**：必须设置清理函数，防止资源泄漏

## ☕ Java开发者最终认知闭环

### 1. Java并发与C/Pthread的映射
- Java `Thread` 本质是内核轻量级进程的封装
- `synchronized` 底层使用`monitor`（基于互斥锁）
- `volatile` 强制内存屏障，保证可见性
- `AtomicXXX` 使用CAS（CPU `cmpxchg`指令）
- `ThreadLocal` 对应TSD

### 2. JVM并发优化的底层原理
- 锁消除（逃逸分析）：检测到锁对象不逃逸，JIT直接去掉锁
- 锁粗化：多个连续加锁合并为一次
- 偏向锁→轻量级锁→重量级锁（锁升级）
- 自旋锁：短暂等待，避免线程切换

### 3. 高并发架构落地
- Netty：主从Reactor（基于epoll）
- Tomcat NIO：线程池 + 事件驱动
- Disruptor：无锁环形缓冲区（CAS + 内存屏障）

### 4. 线上问题排查
- `jstack` 查看线程栈，检测死锁
- `jstat` 监控GC
- `jmap` 分析堆内存
- `perf` 分析CPU缓存不命中

### 5. 核心结论
- **理解三种并发模型** = 根据场景正确选型
- **掌握信号量/锁/条件变量** = 写出正确同步代码
- **理解线程安全等级** = 写出健壮并发程序
- **本章是后端高并发架构的核心基础**，与第10章（I/O）、第11章（网络）构成全栈知识闭环
