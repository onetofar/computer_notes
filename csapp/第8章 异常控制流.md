## 🧱 基础层：硬件异常与进程基础【对应 8.1~8.3】※※※
### 1. 硬件异常（8.1）—— ECF的底层硬件机制
#### 四类异常（按控制流切换方式分类）
| 类型     | 触发源                     | 同步/异步 | 返回行为             | 典型例子                      |
| ----- | -------------------------- | --------- | -------------------- | ----------------------------- |
| **中断** | 外设（键盘、磁盘、定时器） | 异步      | 返回到下一条指令     | 网卡接收数据包                |
| **陷阱** | 系统调用（`syscall`指令）  | 同步      | 返回到下一条指令     | `read()`, `write()`, `fork()` |
| **故障** | 指令执行错误（可恢复）     | 同步      | 可能重新执行当前指令 | 缺页异常、除零错误            |
| **终止** | 指令执行错误（致命）       | 同步      | 不返回，进程终止     | 非法指令、硬件错误            |
- **核心本质**：异常触发内核接管CPU → 内核处理 → 返回用户程序（或终止进程）
- **Java关联**：
  - Java的`NullPointerException`底层是CPU的缺页故障（虚拟地址未映射）或段故障
  - Java的`ArithmeticException`（除零）底层是CPU的除零故障
  - JVM捕获异常后，通过异常表查找handler，模拟了故障的“重新执行”语义（`catch`块）
#### 系统调用（陷阱）的本质
- 用户程序通过`syscall`指令主动陷入内核，执行特权操作
- 示例：`write(1, "hello", 5)` 在x86-64汇编中是：
  ```asm
  mov $1, %rax      # 系统调用号write=1
  mov $1, %rdi      # 参数1: 文件描述符1(stdout)
  lea hello(%rip), %rsi  # 参数2: 字符串地址
  mov $5, %rdx      # 参数3: 长度
  syscall           # 陷阱指令
  ```
- **Java关联**：`FileInputStream.read()`、`Socket.send()`等native方法，底层最终都通过JNI调用C库，再由C库执行系统调用
### 2. 进程核心概念（8.2）
#### 进程定义
- 独立地址空间（虚拟内存） + 内核调度的执行实体（一个或多个线程）
#### 进程的核心特性
- **写时复制（COW, Copy-on-Write）**：`fork()`后父子进程共享物理页，只有写入时才真正复制
- **父子并发**：`fork()`后父子进程是独立的调度实体，执行顺序不确定
- **PID唯一性**：每个进程有唯一标识符
- **共享文件描述符**：`fork()`后父子进程共享打开的文件偏移量
#### 进程三态（简化）
- **运行态**：正在执行或可被调度
- **阻塞态**：等待某事件（如I/O完成），信号无法唤醒阻塞态进程（需等待事件完成）
- **终止态**：进程已结束，但未被父进程回收（僵尸进程）
### 3. 进程四大基础调用（8.3）
| 函数               | 功能               | 关键特性                                                   | 返回值                       |
| ------------------ | ------------------ | ---------------------------------------------------------- | ---------------------------- |
| `fork()`           | 创建子进程         | 子进程复制父进程的地址空间、文件描述符、信号掩码           | 父进程返回子PID；子进程返回0 |
| `execve()`         | 替换当前进程的程序 | PID不变，不创建新进程；重设信号处理为默认                  | 成功不返回；失败返回-1       |
| `exit()`           | 终止进程           | 刷新stdio缓冲区，关闭打开的文件描述符，发送SIGCHLD给父进程 | 无返回                       |
| `wait()/waitpid()` | 回收子进程         | 释放僵尸进程的内核资源；可阻塞等待子进程终止               | 返回终止子进程的PID          |
#### 经典`fork()`示例
```c
#include <unistd.h>
#include <stdio.h>
int main() {
    pid_t pid = fork();
    if (pid == 0) {
        printf("child: pid=%d, parent=%d\n", getpid(), getppid());
    } else {
        printf("parent: child=%d, my pid=%d\n", pid, getpid());
    }
    return 0;
}
```
- **注意**：父进程和子进程的执行顺序不确定，需要同步机制（如信号或`wait`）
#### `execve`与`fork`的配合：创建新进程的标准模式
```c
if (fork() == 0) {
    execve("./new_prog", argv, envp);  // 子进程变身
    perror("execve failed");           // 只有失败才执行
    exit(1);
}
wait(NULL);  // 父进程等待子进程结束
```
#### 僵尸进程与孤儿进程
- **僵尸进程**：子进程终止但父进程未调用`wait`，内核保留进程表项（PID、退出状态等）
- **孤儿进程**：父进程先于子进程终止，子进程被`init`进程（PID=1）收养，自动回收
- **避坑**：长期不回收僵尸进程会耗尽PID资源，导致无法创建新进程

- **x86-64 异常号速查表**（原书 Figure 8.2 + §8.1.3）：
  | 异常号 | 名称 | 类别 | 典型触发场景 |
  |--------|------|------|-------------|
  | 0 | Divide Error | 故障 | 除零 (`idiv` 除数为0) |
  | 13 | General Protection Fault | 故障 | 非法内存访问、段权限违规 |
  | **14** | **Page Fault** | 故障 | 缺页——虚拟地址未映射到物理页 |
  | 18 | Machine Check | 终止 | 硬件错误（致命） |
  | 32-255 | OS-defined | 中断/陷阱 | 可编程中断控制器、系统调用 |

- **缺页异常（#PF）详细分类**（原书 §8.1.3）：
  - 内核通过错误码（error code）区分两种情况：
    - bit 0 = 0：页不存在（需从磁盘加载）
    - bit 0 = 1：页保护违规（权限不足 → SIGSEGV）
  - 触发 #PF 时 CPU 将故障地址写入 CR2 寄存器，内核读取后决定处理方式

## ⚙️ 原理层：信号基础机制【对应 8.4】※※※

### 1. 信号本质
- **软件中断**：内核通知进程发生了异步事件（如用户按Ctrl+C、除零、子进程退出）
- **生命周期**：产生 → 内核暂存（pending） → 递送（delivery） → 处理
- **信号排队规则**：每种信号在进程的pending位图中只有一个bit，多个相同信号同时到达时，**只排队一次**，后续会合并丢失（不同于可靠队列）

### 2. 信号掩码（mask / block set）
- **作用**：临时阻塞某些信号，内核会暂存被阻塞的信号，待掩码解除后递送
- **掩码继承**：子进程通过`fork()`继承父进程的信号掩码；`execve`会保留掩码（但会将已pending的信号重置）
- **关键API**：`sigprocmask(SIG_BLOCK, &new_mask, &old_mask)`

### 3. 信号三种处理方式
| 处理方式      | 宏/函数                   | 说明                                   |
| ------------- | ------------------------- | -------------------------------------- |
| 忽略          | `SIG_IGN`                 | 信号被丢弃，不递送                     |
| 默认行为      | `SIG_DFL`                 | 进程终止、暂停或忽略（取决于信号类型） |
| 自定义handler | `signal()`或`sigaction()` | 用户函数被调用                         |

### 4. 信号注册API

#### 老式`signal()`（不安全）
```c
void (*signal(int signo, void (*handler)(int)))(int);
```
- 问题：不同Unix实现行为不一致，系统调用可能被信号中断后不会自动重启

#### 现代`sigaction()`（POSIX标准，推荐）
```c
struct sigaction act;
act.sa_handler = handler;
sigemptyset(&act.sa_mask);
act.sa_flags = SA_RESTART;  // 自动重启被中断的系统调用
sigaction(SIGINT, &act, NULL);
```

#### Stevens包装`Signal()`（封装`sigaction`+`SA_RESTART`）
```c
typedef void (*Sigfunc)(int);
Sigfunc Signal(int signo, Sigfunc handler) {
    struct sigaction act, oact;
    act.sa_handler = handler;
    sigemptyset(&act.sa_mask);
    act.sa_flags = SA_RESTART;
    if (sigaction(signo, &act, &oact) < 0) return SIG_ERR;
    return oact.sa_handler;
}
```

#### `sa_mask`的作用
- 在handler执行期间，自动阻塞`sa_mask`中指定的信号，防止嵌套重入
- 典型用法：`sigaddset(&act.sa_mask, SIGINT)`，处理SIGINT时自动阻塞再次到来的SIGINT

## 🔮 机制层：信号高级问题与竞态条件【对应 8.4~8.5】※※※

### 1. 信号的核心特性：异步性
- 信号可随时抢占当前执行流，在两条机器指令之间插入handler执行
- **后果**：handler执行时机不可预测，可能破坏主程序的临界区

### 2. 信号重入问题
- 同一信号多次快速触发，若未设置`sa_mask`阻塞自身，handler可能嵌套执行
- 嵌套会导致共享数据错乱（如全局计数器被多次加减）

### 3. 竞争条件（Race Condition）—— 本章灵魂难点

#### 典型场景1：`fork()` + 任务列表的时序竞争
```c
void add_job(pid_t pid) { /* 将子进程加入全局列表 */ }
void delete_job(pid_t pid) { /* 从全局列表删除 */ }

void handler(int sig) {  // SIGCHLD handler
    pid_t pid = wait(NULL);
    delete_job(pid);
}

int main() {
    Signal(SIGCHLD, handler);
    pid_t pid = fork();
    if (pid == 0) {
        /* 子进程执行任务后退出 */
        exit(0);
    } else {
        add_job(pid);  // 父进程添加任务
        // 漏洞：若子进程在add_job之前就退出并发送SIGCHLD，handler会先调用delete_job
        // 此时任务尚未加入列表，导致删除失败，产生僵尸进程
    }
}
```
- **解决方案**：在`fork()`前阻塞SIGCHLD，完成`add_job`后再解除阻塞

#### 典型场景2：`pause()`与信号到达的竞争
```c
int flag = 0;
void handler(int sig) { flag = 1; }

int main() {
    Signal(SIGUSR1, handler);
    // 漏洞：若信号在pause()之前到达，flag=1，但pause()永远不会返回
    while (!flag) pause();
    // 正确做法：使用sigsuspend
}
```
- **根源**：检查`flag`和调用`pause()`不是原子操作
- **解决方案**：`sigsuspend(&mask)` 原子地「解除信号掩码 + 等待信号 + 恢复掩码」

### 4. 原子性解决方案

#### 标准临界区保护模板（使用`sigprocmask`）
```c
sigset_t mask, prev;
sigemptyset(&mask);
sigaddset(&mask, SIGCHLD);
sigprocmask(SIG_BLOCK, &mask, &prev);  // 进入临界区
// 操作共享数据（如add_job）
sigprocmask(SIG_SETMASK, &prev, NULL); // 退出临界区
```

#### `sigsuspend` —— 等待信号的原子操作
```c
sigset_t mask, prev;
sigemptyset(&mask);
sigaddset(&mask, SIGUSR1);
sigprocmask(SIG_BLOCK, &mask, &prev);  // 阻塞SIGUSR1
if (flag == 0) {
    sigsuspend(&prev);  // 原子：恢复旧掩码 + 等待信号 + 重新阻塞
}
sigprocmask(SIG_SETMASK, &prev, NULL);
```

### 5. 异步信号安全函数（Async-Signal-Safe）

- **允许**：`_exit()`, `read()`, `write()`, `wait()`, `signal()`, `sigprocmask`, `sigsuspend` 等（可重入或系统调用）
- **禁止**：`malloc()`, `printf()`, `exit()`, `fprintf()` 等（可能持有锁或使用全局状态）
- **规则**：handler中只能调用异步安全函数，否则可能导致死锁或数据损坏

#### 在handler中安全打印日志的方法
```c
void handler(int sig) {
    write(STDERR_FILENO, "signal caught\n", 14);  // 直接使用系统调用
}
```

### 6. 全局标志与`volatile`
- 如果handler与主程序共享全局变量（如`int flag`），必须加`volatile`修饰，防止编译器优化（如将变量缓存在寄存器中）
```c
volatile sig_atomic_t flag;  // sig_atomic_t保证读写是原子的
```

## 🛠️ 落地实操层【对应 8.5~8.6】※※

### 1. 信号阻塞标准模板
```c
sigset_t mask, prev;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);
sigprocmask(SIG_BLOCK, &mask, &prev);
// 临界区代码（不会被SIGINT中断）
sigprocmask(SIG_SETMASK, &prev, NULL);
```

### 2. 非本地跳转（`setjmp`/`longjmp`）—— 绕过正常函数调用栈

#### 核心作用
- 在深层嵌套函数中，直接跳回上层调用点，用于错误恢复（类似Java的异常）

#### API
```c
#include <setjmp.h>
int setjmp(jmp_buf env);   // 保存当前栈上下文，返回0
void longjmp(jmp_buf env, int val);  // 跳回setjmp点，setjmp返回val
```

#### 典型示例：信号处理中跳回主循环
```c
jmp_buf env;
void handler(int sig) {
    longjmp(env, 1);  // 从信号handler跳回主程序
}

int main() {
    Signal(SIGINT, handler);
    if (setjmp(env) == 0) {
        // 正常执行路径
        while (1) {
            /* 可能被中断的操作 */
        }
    } else {
        // 从信号handler跳转回来，执行清理
        printf("Interrupted! Cleaning up...\n");
        exit(0);
    }
}
```
- **注意**：`setjmp`的返回值区分第一次调用（0）和`longjmp`跳回（非0）
- **限制**：只能跳转回调用栈上层（不能跳转到已返回的函数），且会恢复寄存器状态但不会恢复信号掩码（需手动管理）

#### Java关联
- Java的`try-catch-finally`底层在JVM中使用了类似`setjmp/longjmp`的机制
- `throw`会沿着调用栈展开，找到对应的`catch`块，本质是栈帧的“非本地跳转”
- 区别：Java异常会执行`finally`块，而`longjmp`不会自动执行清理代码（需要手动调用）

### 3. 系统调用错误处理
- 大多数系统调用失败时返回-1，并设置`errno`
- 推荐使用包装函数（如Stevens的`Fork`, `Signal`）统一检查错误
```c
pid_t Fork(void) {
    pid_t pid;
    if ((pid = fork()) < 0) {
        perror("fork error");
        exit(1);
    }
    return pid;
}
```

## 🔗 拓展层：Java关联与系统设计思想

### 1. Java异常与硬件异常的映射
| Java异常                     | 底层硬件/OS机制                  |
| ---------------------------- | -------------------------------- |
| `NullPointerException`       | 缺页故障/段故障                  |
| `ArithmeticException` (除零) | 除零故障                         |
| `StackOverflowError`         | 缺页故障（栈溢出）               |
| `InterruptedException`       | 信号（如`SIGINT`）或线程中断标志 |
| `IOException` (文件不存在)   | 系统调用返回错误码               |

### 2. Java线程与进程的关系
- Java线程是用户级线程（1:1映射到内核线程，如Linux的NPTL）
- `Thread.start()` 最终调用`pthread_create`，底层使用`clone()`系统调用（类似`fork`但共享地址空间）

### 3. Java信号处理的限制
- JVM会拦截`SIGINT`（Ctrl+C）用于关闭钩子（`Runtime.addShutdownHook`）
- 普通Java代码无法直接注册原生信号handler（除非通过JNI调用`sigaction`）
- JVM内部使用信号实现`Thread.stop()`（已废弃）和`sun.misc.Signal`

### 4. 操作系统ECF思想在上层的复用
- **数据库事务**：类似于`setjmp/longjmp`，遇到错误回滚到savepoint
- **Go语言的`defer`+`panic`/`recover`**：类似`setjmp/longjmp` + 栈展开
- **Node.js的事件循环**：异步I/O本质上是对信号/中断的抽象

## ❌ 避坑层【全章易错点速查】

1. **`fork()`后子进程与父进程的执行顺序不确定**，必须用同步机制
2. **僵尸进程必须通过`wait()`回收**，否则消耗内核资源
3. **`execve`成功后不返回**，后续代码仅用于错误处理
4. **信号处理函数中禁止调用`printf`、`malloc`等非异步安全函数**
5. **多个相同信号会合并丢失**，不能依赖信号计数（如用信号实现生产者-消费者是错误的）
6. **`pause()`存在竞态条件**，应使用`sigsuspend`
7. **`setjmp/longjmp`不会自动恢复信号掩码**，需手动`sigprocmask`
8. **全局标志必须加`volatile`**，否则编译器优化可能导致主程序看不到更新
9. **`wait`与`SIGCHLD`配合时，必须在`fork`前阻塞SIGCHLD**，防止子进程先退出
10. **`exit()`会刷新stdio缓冲区，`_exit()`不会**，在`fork`后的子进程中慎用`exit`

- 进程地址空间隔离、写时复制、信号量同步都依赖ECF

### 5. 核心结论
- **ECF打破了程序顺序执行的假设**，让系统能够响应异步事件、实现多任务、处理错误
- **写健壮的系统程序，必须精通信号和进程控制**，避免竞态条件和资源泄漏
