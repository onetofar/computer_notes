# CMS(Concurrent Mark Sweep) 标记-清除收集器 深度全解
## 🎯 CMS 核心定位与前世今生
CMS 是 HotSpot 虚拟机第一款**并发式老年代垃圾收集器**，核心设计目标是**获取最短回收停顿时间**，是经典分代回收体系中低延迟方案的代表。
- 别名：**并发低停顿收集器（Concurrent Low Pause Collector）**
- 核心搭档：新生代 ParNew 收集器，组成低延迟分代回收组合
- 历史定位：JDK 1.4 推出，JDK 9 标记为废弃，JDK 14 正式移除，被 G1 收集器全面替代
- 核心价值：首次实现 GC 线程与用户线程并发运行，彻底打破老年代全 STW 回收的限制
## ⚙️ CMS 完整工作流程（核心阶段）
### 🔹 初始标记（CMS initial mark）
- 执行方式：**STW 单线程执行**
- 核心任务：仅标记 GC Roots 能直接关联到的老年代对象
- 执行逻辑：
  - 从 GC Roots（线程栈、寄存器、静态变量、JNI 引用）出发，遍历直接引用的对象
  - 将这些对象标记为灰色，加入标记队列
  - 不递归扫描引用链，仅处理直接关联对象
- 核心特点：
  - 扫描范围极小，停顿时间极短（微秒级）
  - 是 CMS 两次 STW 阶段中耗时最短的环节
  - 为后续并发标记提供初始标记队列
- 关联三色标记：完成初始灰色对象标记，启动三色标记流程
### 🔹 并发标记（CMS concurrent mark）
- 执行方式：**与用户线程并发运行，无 STW**
- 核心任务：从初始标记的灰色对象出发，遍历整个对象图，完成全堆存活对象标记
- 执行逻辑：
  - 从灰色对象队列中取出对象，遍历其所有引用字段
  - 将引用的白色对象标记为灰色，加入标记队列
  - 当前对象所有引用扫描完成后，标记为黑色
  - 全程与用户线程并行，不暂停业务
- 关联核心机制：
  - 触发**增量更新写后屏障**，拦截「黑色对象→白色对象」的非法引用
  - 当出现黑→白引用时，将黑色对象重新标灰，置位 `cms_need_rescan` 等控制 Flag
  - 标记卡表脏页，记录引用变更
- 核心特点：
  - 耗时较长，但完全无停顿，不影响业务运行
  - 并发期间用户线程持续修改引用，产生漏标风险
  - 支持多 GC 线程并行执行，提升标记效率
#### ✨ 并发预清理（核心优化，思维导图未显式标注）
- 执行方式：**与用户线程并发运行**
- 核心任务：**提前处理并发标记期间的引用变更，降低重新标记阶段的 STW 压力**
- 执行逻辑：
  - **扫描卡表脏页，处理被重新标灰的对象**
  - **尝试清空 `has_dirty_cards` 等控制 Flag**
  - 等待新生代回收，减少重新标记时的跨代引用扫描量
- 退出条件：
  - 脏卡数量低于阈值
  - 等待时间超时
  - 新生代达到回收条件
---

### 🔹 重新标记（CMS remark）
- 执行方式：**STW 多线程执行**
- 核心任务：修正并发标记期间的引用变动，补全漏标对象，完成最终标记
- 执行逻辑（多级 Flag 精准扫描）：
  1.  暂停所有用户线程，杜绝引用再变更
  2.  必扫 GC Roots，补全并发期间新增的根引用
  3.  仅当 `cms_need_rescan = true` 时，扫描所有被重新标灰的对象，补全引用链
  4.  仅当 `has_dirty_cards = true` 时，扫描所有脏卡页对应的对象
  5.  按需扫描新生代，处理跨代引用变更
  6.  处理弱引用、软引用等特殊引用队列
- 关联核心机制：
  - 增量更新写屏障的最终兜底，修复并发期间的漏标问题
  - 多级 Flag 控制扫描范围，避免无脑全堆扫描
- 核心特点：
  - 是 CMS 两次 STW 阶段中耗时较长的一次，但远短于全堆扫描
  - 停顿时间受并发期间引用变更量、脏卡数量影响
  - 多线程并行执行，缩短停顿时间
- 优化手段：`-XX:+CMSScavengeBeforeRemark`，重新标记前执行一次 Minor GC，减少新生代扫描压力

---

### 🔹 并发清除（CMS concurrent sweep）
- 执行方式：**与用户线程并发运行，无 STW**
- 核心任务：清除所有标记为白色的垃圾对象，释放内存空间
- 执行逻辑：
  - 遍历老年代内存区域，识别未被标记的白色对象
  - 释放这些对象占用的内存，将空闲内存加入空闲链表
  - 不移动对象、不整理内存碎片
- 核心特点：
  - 完全无停顿，与用户线程并行执行
  - 标记-清除算法的核心体现，无需移动对象
  - 并发期间新产生的垃圾（浮动垃圾）无法回收，需等待下一次 GC

#### ✨ 并发重置（收尾阶段，思维导图未显式标注）
- 执行方式：**与用户线程并发运行**
- 核心任务：重置所有标记状态、清空控制 Flag、重置卡表
- 执行逻辑：
  - 清空对象三色标记
  - 重置 `cms_need_rescan`、`has_dirty_cards` 等控制 Flag
  - 重置卡表、标记队列
  - 为下一次 GC 循环做准备

## 🛡️ CMS 底层核心实现
### 🔹 增量更新写后屏障（解决并发漏标）
```c++
// 全局控制 Flag 定义
bool cms_need_rescan = false;  // 总开关：是否存在被重新置灰的对象
bool has_dirty_cards = false;  // 卡表标记：是否存在脏卡页

// CMS 增量更新写后屏障（赋值完成后触发）
void cms_post_write_barrier(oop* field, oop new_obj) {
    // 获取被修改引用的所属对象
    oop owner_obj = get_owner_object(field);
    
    // 核心判断：黑色对象 引用 白色对象 → 触发漏标修复
    if (owner_obj->color == BLACK && new_obj->color == WHITE) {
        // 1. 将黑色对象重新标记为灰色，补全标记
        owner_obj->color = GRAY;
        // 2. 置位总开关 Flag，标记需要重扫
        cms_need_rescan = true;
        // 3. 标记对象所在卡页为脏页
        size_t card_idx = addr_to_card_idx((address)owner_obj);
        card_table->set_dirty(card_idx);
        has_dirty_cards = true;
        // 4. 将对象加入灰色标记队列
        add_to_grey_queue(owner_obj);
    }
}
```

### 🔹 重新标记阶段 Flag 判定逻辑
```c++
void cms_remark_phase() {
    // 1. 暂停所有用户线程，进入 STW
    stop_all_user_threads();
    
    // 2. 必扫：GC Roots，补全并发期间的根引用变更
    scan_gc_roots();
    
    // 3. 按 Flag 精准扫描，无变更则直接跳过
    if (cms_need_rescan) {
        // 扫描所有被重新标灰的对象，补全引用链
        rescan_grey_objects();
    }
    if (has_dirty_cards) {
        // 扫描所有脏卡页对应的对象，处理引用变更
        scan_dirty_cards();
    }
    
    // 4. 按需扫描新生代，处理跨代引用
    if (need_scan_young_gen()) {
        scan_young_generation();
    }
    
    // 5. 处理特殊引用队列
    process_reference_queues();
    
    // 6. 重置所有 Flag，为下一次 GC 做准备
    cms_need_rescan = false;
    has_dirty_cards = false;
    
    // 7. 恢复用户线程
    resume_all_user_threads();
}
```

### 🔹 卡表与跨代引用处理
- 核心作用：避免 Minor GC 时扫描全老年代，仅扫描脏卡页
- 实现逻辑：
  - 写后屏障拦截「老年代对象→新生代对象」的跨代引用
  - 将引用所在卡页标记为脏页
  - 预清理阶段处理脏卡，减少重新标记阶段的扫描压力
- 内存占用：卡表大小 = 老年代大小 / 512（默认卡页大小 512 字节），内存开销极低

## ✅ CMS 核心优点
- 并发收集
  - 绝大多数阶段（并发标记、并发清除）与用户线程并行运行
  - 仅两次短 STW，大幅降低业务停顿时间
- 低停顿
  - 初始标记、重新标记两次 STW，总停顿时间极短
  - 别名「并发低停顿收集器（Concurrent Low Pause Collector）」
  - 适合交互型互联网应用，对用户体验影响小
- 适配老年代特性
  - 老年代对象存活率高，复制算法效率低，标记-清除无需移动对象
  - 并发清除阶段无停顿，适合大老年代回收

---

## ❌ CMS 核心缺点
### 🔹 对处理器资源非常敏感
- 并发阶段需要占用 CPU 资源执行 GC 线程，挤占用户线程资源
- 多核 CPU 下可通过多线程并行提升效率，单核 CPU 下性能下降明显
- 并发线程数默认等于 CPU 核心数，可通过 `-XX:ConcGCThreads` 调整

### 🔹 无法处理「浮动垃圾」

### CMS 浮动垃圾的**唯一两个真实来源**

我们沿着 CMS 四阶段时间线看，一清二楚：

```
初始标记(STW) → 并发标记 → 重新标记(STW) → 并发清除
```

#### 来源 1：并发标记 / 重新标记期间**新创建的对象**

- 时间点：GC 已经启动（初始标记完成），用户线程还在跑

- 行为：用户线程新 `new` 出对象 C、D、E

- CMS 处理规则：

  这些新对象直接被标记为黑色（视为存活），不会进入三色标记扫描

- 结果：

  哪怕这些新对象刚创建就变成垃圾（引用立刻置 null），本次 GC 也不会清因为它们已经是黑色，清除阶段只清白色。

👉 这就是**第一类浮动垃圾**

完全和增量更新无关，只是 CMS 对 “GC 期间新分配对象” 的保守处理策略。

#### 来源 2：**重新标记结束后**才变成垃圾的对象

- 时间线：

  1. 并发标记 + 重新标记：对象 B 被标记为**黑色（存活）**

     （因为标记阶段它确实有引用，增量更新也确认了它存活）

  2. 重新标记完成 → 并发清除开始：**用户线程把 B 的所有引用全部切断**

     B 变成真正的垃圾

- CMS 处理规则：

  标记阶段已经结束，不会再重新扫描引用关系并发清除只看颜色：B 是黑色 → 视为存活 → 不清除

👉 这就是**第二类浮动垃圾**

增量更新管的是「标记过程中的引用变化」，**管不了标记结束后的引用变化**。

- 并发标记期间，用户线程新产生的垃圾对象，无法被本次 GC 回收
- 这些垃圾只能等待下一次 GC 回收，称为浮动垃圾
- 需要预留足够内存给用户线程使用，避免「并发模式失败」（Concurrent Mode Failure）
- 可通过 `-XX:CMSInitiatingOccupancyFraction` 设置老年代回收阈值，提前触发 GC

### 🔹 标记-清除算法导致的内存不连续（内存碎片）

#### 	原因：

1. **新生代用复制**：因为对象死得快、复制少、速度快、能接受空间浪费
2. **老年代不能用复制**：因为对象活得多、复制量大、STW 爆炸、内存利用率崩盘
3. **CMS 选标记 - 清除**：是为了**不移动对象、实现并发回收、极致低 STW**，主动接受内存碎片的代价

- 标记-清除算法不整理内存，回收后产生大量内存碎片
- 大对象分配时，无法找到连续的内存空间，触发 Full GC
- 优化手段：
  - `-XX:+UseCMSCompactAtFullCollection`：开启 Full GC 时的内存整理
  - `-XX:CMSFullGCsBeforeCompaction`：设置多少次 Full GC 后执行一次整理

---

## 🎯 CMS 核心调优参数
- `-XX:+UseConcMarkSweepGC`：开启 CMS 收集器
- `-XX:CMSInitiatingOccupancyFraction`：老年代回收阈值，默认 92%
- `-XX:+CMSScavengeBeforeRemark`：重新标记前执行 Minor GC，缩短 STW
- `-XX:ConcGCThreads`：并发 GC 线程数，默认 = CPU 核心数 / 4
- `-XX:+UseCMSCompactAtFullCollection`：Full GC 时整理内存
- `-XX:CMSFullGCsBeforeCompaction`：多少次 Full GC 后执行一次整理
- `-XX:CMSScheduleRemarkEdenSizeThreshold`：新生代扫描阈值，默认 2M

---

## 🎯 最终总结
- CMS 是 HotSpot 第一款并发老年代收集器，核心目标是最短回收停顿时间
- 基于三色标记 + 增量更新写屏障解决并发漏标，通过多级 Flag 控制重扫范围
- 两次短 STW，并发标记与清除，实现低延迟回收
- 核心缺点：CPU 敏感、浮动垃圾、内存碎片，最终被 G1 收集器全面替代
