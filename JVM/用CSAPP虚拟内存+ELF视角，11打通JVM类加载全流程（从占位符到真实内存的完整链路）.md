# 🔥LD链接器 × JVM类加载 全流程逐帧对照
**严格分阶段、分角色、分动作、分状态、分底层依赖**，彻底分清：哪一步是LD干的、哪一步是JVM干的、原理为何同源、实现为何不同，无任何模糊点。
## 📚 前置知识铺垫（必看·消除认知盲区）
### 核心概念定义
| 概念     | LD（GNU链接器）场景解释                                 | JVM类加载场景解释                                        |
| -- | ------------------------------------------------------- | -------------------------------------------------------- |
| 符号引用 | `.symtab`中记录的函数/变量名（如`printf`）              | 运行时常量池中类/方法/字段的名称（如`java.lang.String`） |
| 直接引用 | 符号对应的虚拟内存地址（如0x400500）                    | 指向方法区/堆的内存指针/偏移量（JVM内部地址）            |
| 虚拟内存 | 编译期LD仅规划地址（写入ELF），运行期内核映射到物理内存 | JVM通过`mmap`/`malloc`向内核申请，直接关联物理页         |
| 重定位   | 修正`.text`机器码中的地址占位符，替换为真实虚拟地址     | 修正常量池符号引用为直接引用，不修改字节码               |
| 零初始化 | LD标记`.bss`节属性，内核`execve`时清零                  | JVM直接为静态变量赋默认值（int=0、null等）               |

| --------------- | --------------------------------------- | -------------------------------------------- |
| `readelf -h/-S` | 查看ELF文件头、节头部表，验证LD链接结果 | 无（JVM无磁盘产物）                          |
| `nm -n`         | 查看ELF符号表及虚拟地址，验证符号解析   | 无（JVM符号在运行时常量池）                  |
| `javap -v`      | 无（LD不处理Class文件）                 | 查看Class文件常量池、方法表，验证加载前结构  |
| `jinfo/jmap`    | 无                                      | 查看JVM方法区/堆内存分布，验证类加载后的内存 |
| `ldd`           | 查看可执行文件依赖的.so，验证动态链接   | 无（JVM依赖rt.jar等，通过类路径加载）        |

| ------------ | ------------------------------------------- | ------------------------------------------------------------ |

| 输出产物     | ELF可执行文件 / 共享库（`.so`）             | 方法区+堆内存结构（无磁盘文件）                              |

| 性能影响     | 仅影响编译速度，不影响程序运行时性能        | 影响程序启动速度，懒解析缓解运行时性能损耗                   |

# 逐阶段全细节对照（5大阶段+子步骤，1:1拆解+实操+排错）
## 阶段1：加载（Loading）—— 读取文件+构建元数据+偏移占位
### 子步骤1：读取二进制文件
- **LD做什么**
  1. 读取磁盘上的**`.o`可重定位目标文件**（通过GCC`-c`生成，如`gcc -c main.c -o main.o`）
  2. 解析ELF Header（验证魔数`0x7F 45 4C 46`）、节头部表（Section Header Table）
  3. 提取核心节：`.text`（机器码）/`.data`（已初始化全局变量）/`.bss`（未初始化全局变量）/`.symtab`（符号表）/`.rel.text`（重定位条目）
  ✅ 实操验证：`readelf -S main.o` 可查看提取的节信息。

- **JVM做什么**
  1. 读取磁盘/网络/JAR包中的**`.class`文件**（通过`ClassLoader.loadClass("com.test.Demo")`触发）
  2. 解析Class文件结构：魔数（0xCAFEBABE）、版本号、常量池（**偏移量**）、字段表、方法表、属性表
  3. 提取核心数据：方法字节码、静态变量描述符、符号引用（如`Ljava/lang/System;`）、方法访问标志（public/static）
  ✅ 实操验证：`javap -v Demo.class` 可查看解析后的常量池和方法表。

### 子步骤2：构建元数据
- **LD做什么**
  构建**链接上下文（Link Context）**：内存中临时记录所有输入`.o`文件的节大小、节内偏移、重定位条目数量，不分配虚拟地址。
  📌 底层逻辑：LD核心代码（`ld/ldmain.c`）通过`ldfile`模块遍历输入文件，填充`struct elf_section`结构体。

- **JVM做什么**
  在方法区（JDK8+元空间）构建**类元数据（Klass对象）**：C++层创建`instanceKlass`实例，记录类名、父类指针、字段描述数组、方法字节码指针、常量池副本、**类元数据里有【字段偏移表】**（编译期写入 class，加载后进元数据）
  📌 底层逻辑：JVM源码`ClassLoader::load_class`调用`SystemDictionary::resolve_instance_class`构建Klass对象。

### 子步骤3：偏移/逻辑占位
- **LD做什么**
  仅记录**节内相对偏移**（如`.text`中`main`函数起始偏移0x10），无任何虚拟地址分配（编译期不涉及OS内存管理）。
  📌 关键：偏移仅用于LD内部计算，最终写入ELF节头部表，不关联物理内存。

- **JVM做什么**
  为类的字节码、静态变量分配**方法区逻辑空间占位**：仅在Klass对象中标记“静态变量区域需占用16字节”，不调用`mmap`申请OS虚拟内存页。
  📌 关键：逻辑占位仅为内存规划，无页表映射、无物理内存分配。

### 子步骤4：符号表初始化
- **LD做什么**
  读取各`.o`的`.symtab`并暂存到LD内部符号表（`struct elf_sym`数组），**阶段4才合并为全局符号表**，此时符号状态为“未解析”。
  ❌ 常见问题：若`.o`引用未定义符号（如`func()`未实现），本阶段不报错，阶段4才触发`undefined reference`。

- **JVM做什么**
  构建**运行时常量池**（Class常量池的内存版）：将Class文件中的常量池（字面量、符号引用）拷贝到方法区，所有符号均为**符号引用（占位符）**（如`com/test/Demo.print`）。
  ❌ 常见问题：若符号引用格式非法（如类名拼写错误），本阶段不报错，阶段2验证才触发`ClassFormatError`。

### 全流程隐藏细节

1. **加载不做任何内存分配（除元数据结构体）**

   只解析结构、不申请虚拟内存页、无地址、无赋值

2. **双亲委派是加载的执行规则，不是独立阶段**

   先委托父加载器，父加载器找不到才自己加载，保证核心类不被篡改

3. **原始运行时常量池 = 磁盘 class 常量池的 1:1 内存拷贝**

   只读、永久不变、不存地址、只存符号 / 字面量

4. **Class 对象是占位，未分配真实堆内存**

   仅在 JVM 内部注册，准备阶段才真正分配内存

5. **字段表 / 方法表 / 偏移量 在此阶段载入元空间**

   偏移量编译期写死，加载后永久存在 Klass，运行时不改

6. **加载不触发任何解析、不绑定符号、不修改数据**

### 本阶段核心状态对比
| 状态项            | LD                         | JVM                                          |
| ----------------- | -------------------------- | -------------------------------------------- |
| 静态变量（.data） | 仅节内偏移，**无虚拟地址** | 仅字段描述，**无内存、无值**                 |
| 代码段（.text）   | 机器码，节内偏移           | 字节码，逻辑地址占位                         |
| 符号状态          | 未解析，暂存于各`.symtab`  | 未解析，存于运行时常量池                     |
| 内存属性          | 无任何OS内存操作           | 无真实OS内存（仅逻辑占位）                   |
| 报错类型          | 无（仅文件读取失败报错）   | 仅Class文件读取失败（FileNotFoundException） |

### 本阶段共性/差异
- **共性**：都只读文件、建元数据、**不分配真实内存、不解析符号、不修改数据**
- **差异**：
  1. LD处理ELF节结构，仅记录偏移；JVM处理Class表结构，划分逻辑占位
  2. LD符号暂存于多个`.symtab`，JVM符号统一存入运行时常量池
  3. LD无跨文件依赖校验，JVM本阶段不校验类依赖存在性

## 阶段2：验证（Verification）—— 合法性校验

在验证前，加载后，内存会生成cp_cache存储常量池， 专门存以后解析出来的**直接引用（地址 / 偏移）**

### 子步骤1：格式校验
- **LD做什么**
  1. 校验ELF魔数（0x7F 45 4C 46）是否合法，拒绝非ELF文件
  2. 校验节大小 ≤ 文件总大小、节偏移不越界，拒绝损坏的`.o`文件
  ✅ 实操验证：`readelf -h main.o` 可验证ELF魔数和文件格式。

- **JVM做什么**
  1. 校验Class魔数（0xCAFEBABE），拒绝非Class文件（如`.java`源文件）
  2. 校验Class版本号（如52.0对应JDK8）≤ JVM版本，拒绝高版本Class文件
  3. 校验常量池索引（如`#10`）不超过常量池总数，拒绝索引越界
  ✅ 实操验证：`javap -v Demo.class` 可查看版本号（minor version/major version）。

### 子步骤2：元数据校验
- **LD做什么**
  1. 校验符号类型（如FUNCTION/DATA）与节类型匹配（`.text`对应FUNCTION）
  2. 校验节权限（如`.text`为RX、`.data`为RW），拒绝非法权限配置
  3. 校验重定位类型（如R_X86_64_PC32）与CPU架构匹配，拒绝跨架构重定位

- **JVM做什么**
  1. 校验类继承合法性（如不能继承`final`类、接口不能继承类）
  2. 校验字段/方法修饰符合法性（如`static final`字段必须有初始值）
  3. 校验方法描述符（如`(I)V`）与参数/返回值类型匹配，拒绝语法错误

### 子步骤3：指令/代码校验
- **LD做什么**
  1. 校验`.text`机器码无非法指令（如x86非法操作码0xFF）
  2. 校验机器码无越界内存访问（如引用`.data`外的偏移）
  📌 补充：LD仅做基础校验，运行时非法指令由CPU触发`SIGILL`信号。

- **JVM做什么**
  1. 字节码验证器（Bytecode Verifier）校验数据流合法性（如栈顶类型与指令匹配）
  2. 校验栈操作无溢出/下溢（如`pop`空栈）
  3. 校验类型转换合法性（如不能将`String`强转为`int`）
  📌 补充：JDK1.6后默认开启验证，可通过`-Xverify:none`关闭（不推荐）。

### 子步骤4：符号引用校验
- **LD做什么**
  校验外部符号引用格式合法（如符号名无特殊字符、长度≤ELF符号名限制），**不检查符号是否存在**。

- **JVM做什么**
  校验常量池符号引用格式合法（如类名符合`com/test/Demo`格式、方法名无非法字符），**不检查类/方法是否存在**。

### 全流程隐藏细节

1. **验证分 4 步，缺一不可（非可选优化）**

   - 格式校验：魔数、版本、常量池索引合法性
   - 元数据校验：继承、修饰符、语法合法性
   - 字节码校验：栈平衡、类型匹配、无非法跳转
   - 符号引用校验：符号格式合法（不查是否存在）

2. **验证全程不分配内存、不修改数据、不计算地址**

3. **关闭验证（-Xverify:none）会跳过此阶段**

   提升启动速度，但失去安全保护，生产环境禁用

4. **验证失败直接抛 VerifyError/ClassFormatError**

   阻止非法类进入 JVM，防止内存崩溃

### 本阶段核心状态对比
| 状态项   | LD                          | JVM                          |
| -------- | --------------------------- | ---------------------------- |
| 静态变量 | 仍为节内偏移，无变化        | 仍为字段描述，无变化         |
| 内存状态 | 无任何OS内存操作            | 无真实OS内存                 |
| 符号状态 | 未解析                      | 未解析                       |
| 核心报错 | ELF格式错误（如魔数不匹配） | ClassFormatError/VerifyError |

### 本阶段共性/差异
- **共性**：都是**安全校验**，保证二进制文件合法，不分配内存、不修改数据
- **差异**：
  1. LD校验ELF机器码和节属性，JVM校验Class字节码和类继承规则
  2. LD校验轻量（仅格式），JVM校验深度（数据流、栈操作、类型）
  3. LD校验失败直接终止链接，JVM校验失败抛出运行时异常

## 阶段3：准备（Preparation）—— 分配虚拟地址+零初始化规则
### 子步骤1：虚拟地址分配/OS虚拟内存申请
- **LD做什么**
  1. 合并所有输入`.o`的同名节（如合并所有`.text`），计算总大小
  2. 为合并后的`.text`/`.data`/`.bss`分配**进程虚拟地址空间的虚拟地址**（如`.text`基地址0x400000）
  3. 计算：`虚拟地址 = 加载基地址 + 节偏移`（如`.text`内`main`函数地址=0x400000+0x10=0x400010）
  4. 将虚拟地址规划写入ELF**程序头部表（Program Header Table）**（编译期规划，不调用`mmap`申请OS内存）
  ✅ 实操验证：`readelf -l a.out` 可查看程序头部表的虚拟地址规划。

- **JVM做什么**
  1. 通过`mmap(MAP_PRIVATE|MAP_ANONYMOUS)`向Linux内核申请**虚拟内存页**（元空间/堆），或通过`malloc`分配
  2. 准备阶段分配了 Class 对象的基地址
  3. 逻辑划分存储区域：
     - 逻辑`.text`：方法区（元空间）存储字节码、Klass对象
     - 静态变量：JDK8+存储于Java堆（对应Klass对象的`static_fields`指针指向堆地址）
  4. 为静态变量分配**虚拟内存地址**（如`static int a`分配地址0x7f8000001000），地址非固定（随堆/元空间动态扩容调整）
    📌 底层细节：JVM通过`os::malloc`/`os::pd_mmap`封装系统调用，不同OS（Linux/Windows）实现不同。

### 子步骤2：零初始化（默认值）
- **LD做什么**
  1. 仅在ELF程序头标记`.bss`节为`PT_LOAD + PF_RW`，并标记`p_filesz=0、p_memsz=xxx`（表示文件中无数据，内存中需分配xxx字节并清零）
  2. LD本身不执行初始化，**内核执行`execve`系统调用加载可执行文件时**，会为`.bss`节分配内存并清零
  📌 补充：`.data`节数据已存储在ELF文件中，内核加载时直接拷贝到内存，无需零初始化。

- **JVM做什么**
  1. 直接为静态变量赋**JVM默认零值**（int=0、long=0L、引用=null、boolean=false、float=0.0f）
  2. 不执行任何用户代码（如静态代码块、`static int a=10`中的10暂不赋值）
    📌 关键：零初始化由JVM的`InstanceKlass::initialize_static_fields`方法完成，无需内核参与。

### 全流程隐藏细节

1. **内存分配分两块，严格分离**

   - 元空间（方法区）：mmap 申请，存 Klass / 原始常量池
   - Java 堆：malloc 申请，存 Class 对象 + 静态变量

2. **虚拟内存必须按 4KB/2MB 页对齐**

   由 Linux 内核强制，JVM 不能自定义大小

3. **只分配 Class 对象整块基地址，不分配单个字段地址**

   字段位置 = 基地址 + 偏移，运行时计算，不预存

4. **零初始化是 JVM 强制行为，与代码无关**

   static int=0、引用 = null、boolean=false，不执行用户代码

5. **准备阶段绝对不碰：原始常量池、cp_cache、符号绑定**

   静态变量的 0 值，直接写堆内存，不进任何池

6. **分配的是虚拟内存，无物理内存**

   首次读写触发缺页异常，内核才分配物理页

### 本阶段核心状态对比
| 状态项   | LD                             | JVM                               |
| -------- | ------------------------------ | --------------------------------- |
| 静态变量 | 分配虚拟地址，内核后续零初始化 | 分配虚拟内存地址，JVM直接零初始化 |
| 代码段   | 分配虚拟地址，机器码就位       | 分配虚拟内存地址，字节码就位      |
| 内存属性 | 编译期虚拟地址规划，写入ELF    | 运行时OS虚拟内存，仅存于JVM进程   |
| 符号状态 | 仍未解析                       | 仍未解析                          |
| 底层调用 | 无系统调用（仅文件IO）         | 调用`mmap`/`malloc`系统调用       |

### 本阶段共性/差异
- **共性**：完成地址规划/分配、确定存储位置、零值初始化、符号未解析
- **差异**：
  1. LD仅“规划”虚拟地址并写入ELF，初始化由内核完成；JVM“申请”真实虚拟内存并自行初始化
  2. LD地址固定（编译期确定），JVM地址动态（运行期分配，可扩容）
  3. LD零初始化仅针对`.bss`，JVM零初始化覆盖所有静态变量（无论是否初始化）

## 阶段4：解析（Resolution）—— 符号解析+重定位（核心链接动作）
### 子步骤1：符号查找
- **LD做什么**
  1. 合并所有`.o`的`.symtab`生成**全局符号表**，按“静态符号→全局符号”优先级排序
  2. 遍历重定位条目（`.rel.text`），匹配**符号引用↔符号定义**（如`printf`引用匹配libc的`printf`定义）
  3. 找不到符号定义则抛出`undefined reference to 'xxx'`，终止链接
  ✅ 实操验证：`nm a.out | grep printf` 可查看`printf`的虚拟地址（解析后）。

- **JVM做什么**
  1. 遍历运行时常量池的符号引用，按“启动类加载器→扩展类加载器→应用类加载器”（双亲委派模型）查找类元数据
  2. 匹配**符号引用↔类元数据**（如`java/lang/System`匹配方法区的System类Klass对象）
  3. 找不到类则抛出`NoClassDefFoundError`，找不到方法/字段则抛出`NoSuchMethodError`/`NoSuchFieldError`
  📌 补充：JVM懒解析（Lazy Resolution）：默认仅在**第一次使用符号**时执行查找（如第一次调用方法），而非加载时。

### 子步骤2：重定位计算+地址填充
- **LD做什么**
  1. 处理`.rel.text`/`.rel.data`重定位条目，读取重定位类型（如R_X86_64_PC32）
  2. 计算：`目标地址 = 符号虚拟地址 - 当前指令地址 + 偏移`
  3. 将`.text`机器码中的“符号占位符”（如0x000000）替换为计算后的虚拟地址，修正机器码
  📌 底层：重定位由LD的`bfd/elflink.c`模块实现，直接修改ELF文件的`.text`节数据。
- **JVM做什么**
  1. 处理运行时常量池的符号引用，将其替换为**直接引用**：
  2. 通过**Class对象基地址****（准备阶段分配）+**类元数据里有【字段偏移表】**（编译期写入 class，加载后进元数据）
     - 类引用→指向方法区Klass对象的指针
     - 方法引用→指向方法区方法表的偏移量
     - 字段引用→指向堆中静态变量的内存地址
  3. 仅修正常量池*cp_cache*的引用指向，**不修改原始字节码**（字节码只读，已经加载进jvm内存中的）
    📌 底层：JVM通过`ConstantPool::resolve_field_ref`/`resolve_method_ref`完成重定位，修改常量池的`cp_cache`数组。

### 子步骤3：延迟绑定（可选）
- **LD做什么**（仅动态链接`.so`时）
  1. 为动态符号（如`printf`）创建GOT（全局偏移量表）/PLT（过程链接表）
  2. 第一次调用`printf`时，PLT触发`dl_runtime_resolve`函数，解析符号并填充GOT，后续调用直接读取GOT地址
  ✅ 实操验证：`objdump -d a.out | grep plt` 可查看PLT表。

- **JVM做什么**
  1. 采用**懒解析**：仅在第一次调用方法/访问字段时解析符号引用（而非加载类时）
  2. 无GOT/PLT结构，通过`InterpreterRuntime::resolve_method`在解释执行时触发解析
  3. 解析后缓存直接引用，后续访问无需重复解析
    📌 补充：可通过`-XX:+UnlockDiagnosticVMOptions -XX:+PrintResolution`打印懒解析日志。

### 全流程隐藏细节

1. **解析分 4 类，按固定顺序执行**

   类 / 接口解析 → 字段解析 → 方法解析 → 接口方法解析

2. **cp_cache 与原始常量池索引一一对应**

   字节码只带索引，JVM 用同一索引查缓存

3. **直接引用存偏移，不存完整虚拟地址**

   GC 移动 Class 对象时，仅更新基地址，cp_cache 无需修改

4. **解析后永久缓存，不重复计算**

   对标 Linux GOT/PLT 延迟绑定

5. **全程不修改原始常量池、不修改字节码**

   原始符号永久保留，用于反射 / 报错 / 调试

6. **静态 / 实例字段解析逻辑完全一致**

   仅基地址来源不同（Class 对象 / 实例对象）

### 本阶段核心状态对比
| 状态项     | LD                              | JVM                             |
| ---------- | ------------------------------- | ------------------------------- |
| 符号状态   | 符号引用 → 虚拟地址             | 符号引用 → 直接引用（内存地址） |
| 代码修改   | 修正`.text`机器码中的地址占位符 | 仅修正常量池，不修改原始字节码  |
| 重定位依赖 | 依赖ELF重定位节（.rel.text）    | 依赖运行时常量池                |
| 结果       | 机器码可被CPU直接执行           | 字节码可被JVM执行引擎执行       |
| 延迟绑定   | 仅动态链接，依赖GOT/PLT         | 所有符号，懒解析（无GOT/PLT）   |

### 本阶段共性/差异
- **共性**：核心链接动作，将“符号名”转为“内存地址”，完成可执行前提
- **差异**：
  1. LD重定位修改机器码（磁盘文件），JVM仅修正常量池（内存结构）
  2. LD静态链接无延迟绑定，JVM全量懒解析
  3. LD符号查找基于全局符号表，JVM基于双亲委派模型

## 阶段5：初始化（Initialization）—— 赋自定义值+执行初始化代码
### 子步骤1：执行初始化逻辑
- **LD做什么**
  1. 将用户编写的全局构造函数、全局变量初始化代码合并到ELF的`.init`节（初始化入口）
  2. LD不执行`.init`节，由**用户态运行时库（crt0/crti）** 在程序启动时调用（内核`execve`后，`main`函数前）
  3. 作用：初始化全局变量（如`int a=10`）、执行`__attribute__((constructor))`标记的函数
  📌 补充：可通过`objdump -s a.out | grep .init` 查看`.init`节内容。

- **JVM做什么**
  1. 执行类的`<clinit>()`方法（由静态代码块+静态变量赋值语句合并生成）
  2. **多线程加类初始化锁（Class Initialization Lock）**：保证`<clinit>()`在多线程下仅执行1次
  3. 作用：为静态变量赋用户自定义值、执行静态代码块（如`static { System.out.println("init"); }`）
  📌 底层：JVM通过`InstanceKlass::call_class_initializer`执行`<clinit>()`，锁由`ObjectMonitor`实现。

### 子步骤2：赋用户定义值
- **LD做什么**
  1. `.data`节中存储编译期确定的初始值（如`int a=10`的10）
  2. 内核加载可执行文件时，将`.data`节数据从磁盘拷贝到虚拟内存地址，完成赋值
  📌 补充：`.bss`节无初始值，仅内核清零。

- **JVM做什么**
  1. 执行`<clinit>()`中的赋值语句，将用户定义的初始值（如`static int a=10`的10）写入堆中静态变量的内存地址
  2. 覆盖阶段3的零值（如零值0→自定义值10）
  📌 关键：仅`<clinit>()`执行后，静态变量才达到“用户预期值”。

### 子步骤3：并发安全
- **LD做什么**
  程序启动前（`main`函数前）单线程执行`.init`节，无并发问题，无需锁保护。

- **JVM做什么**
  1. 类初始化锁保证：即使多个线程同时触发类初始化，`<clinit>()`仅执行1次
  2. 若线程A正在执行`<clinit>()`，线程B会阻塞等待，直到初始化完成
    ❌ 常见问题：`<clinit>()`死循环会导致其他线程永久阻塞（如`static { while(true); }`）。

### 全流程隐藏细节

1. **`<clinit>()` 由 javac 自动生成**

   合并：静态变量赋值语句 + 静态代码块，按代码顺序执行

2. **线程安全强制锁**

   多线程同时初始化时，只有 1 个线程执行`<clinit>()`，其余阻塞

3. **初始化触发的 4 种情况（JVM 规范强制）**

   - new 对象
   - 访问静态字段 / 方法
   - 反射调用
   - 子类初始化触发父类初始化

4. **初始化一定在解析之后**

   保证赋值时，字段地址已绑定到 cp_cache

5. **只执行 1 次，执行完类进入 “已初始化” 状态**

   类卸载前不再执行

6. **无`<clinit>()`则跳过此阶段**

   

   无静态变量、无静态代码块的类直接完成加载

### 本阶段核心状态对比
| 状态项   | LD                    | JVM                          |
| -------- | --------------------- | ---------------------------- |
| 静态变量 | 赋用户定义初始值      | 赋用户定义初始值             |
| 代码状态 | 可直接被CPU执行       | 可直接被JVM执行引擎执行      |
| 并发控制 | 无（单线程）          | 有（类初始化互斥锁保护）     |
| 执行主体 | 运行时库（crt0）      | JVM执行引擎（解释/编译执行） |
| 最终状态 | ELF可执行文件完全就绪 | 类加载全流程完成，可正常使用 |

### 本阶段共性/差异
- **共性**：执行初始化逻辑、完成最终赋值、链接/类加载流程结束
- **差异**：
  1. LD依赖运行时库执行`.init`，JVM自行执行`<clinit>()`
  2. LD无并发控制，JVM通过锁保证多线程安全
  3. LD初始化在程序启动前，JVM初始化在类第一次使用时（懒初始化）

# 🎯 深度补充：核心差异的底层根源

1. **设计目标不同**：
   - LD：为“静态编译型程序”生成可执行文件，追求运行时零开销（编译期完成所有链接）。
   - JVM：为“动态解释型程序”提供运行时链接，追求灵活性（类可动态加载/卸载）。
2. **内存模型不同**：
   - LD：基于“静态虚拟地址”，编译期确定所有地址，运行期无内存调整。
   - JVM：基于“动态内存池”，堆/元空间可动态扩容，地址随内存分配变化。
3. **生命周期不同**：
   - LD：单次链接→生成文件→退出，与程序运行解耦。
   - JVM：类加载→使用→卸载（或JVM退出），与程序运行全程绑定。

# 🎯 一句话终极总结（第一性原理）
1. **LD是编译期ELF链接器**：仅做磁盘文件拼接、虚拟地址规划、规则写入，不申请OS内存、不参与运行，初始化由内核/运行时库完成。
2. **JVM类加载是运行期Java链接器**：全程在JVM进程内完成，主动向OS申请虚拟内存、自行执行初始化、解析符号，无磁盘文件写入。
3. **两者原理100%同源**：加载→校验→地址规划/分配→符号解析→初始化，是计算机系统**链接**的标准流程。
4. **唯一核心区别**：**LD做「编译期磁盘文件构建」，JVM做「运行期内存结构构建」**。
