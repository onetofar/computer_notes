# **卡表和记忆集深化**
**记忆集（RSet）** 是 **逻辑抽象层**（谁引用谁），
**卡表（Card Table）** 是 **物理实现层**（哪块内存脏了）。
**深层逻辑不是“记录跨代引用”，而是“防止跨代引用漏扫”，并配合写屏障实现动态更新。**
# 一、Deep 拆解：卡表（Card Table）是什么？
### 1. 硬件底层定义（内存布局）
在 JVM 中，堆被切分为固定大小的**卡页（Card Page）**，通常大小为 **512 bytes**（或 2^9 bytes）。
- **卡表数组**：`byte[]`
- **索引计算**：`card_index = address >> card_table_shift`（右移运算，位运算极快）。
- **值含义**：
  - `0`：干净（无跨代引用）。
  - `1`：**变脏（Dirty）** → 这是核心！
### 2. 为什么它是“变脏”机制？
> 你笔记说“只要卡页包含跨代引用就变脏”，**Deep 修正：是“产生指向老年代的引用”瞬间变脏**。
**真实流程：**
1. **正常情况**：新生代对象只引用新生代（Eden -> Eden），卡表不动。
2. **写操作瞬间**：
   ```java
   // 假设：oldObj (老年代) -> youngObj (新生代)
   // 或者反过来：youngObj -> oldObj
   ref.field = newRef; 
   ```
3. **写屏障（Write Barrier）介入**：
   - JVM 拦截这个赋值指令。
   - 计算 `newRef` 指向的内存地址属于哪个**卡页**。
   - 将卡表数组中对应位置的值 **置为 1（变脏）**。
   - **注意**：不管是不是跨代引用，只要写了引用，JVM 都可能标记（但 GC 时只处理跨代）。
# 二、Deep 拆解：记忆集（Remembered Set）与卡表的关系
### 1. 逻辑 vs 物理
| 维度     | 记忆集 (RSet)                                           | 卡表 (Card Table)                                |
| :------- | :------------------------------------------------------ | :----------------------------------------------- |
| **层级** | **逻辑抽象**（JVM 规范层面）                            | **物理数据结构**（HotSpot 实现）                 |
| **内容** | 记录：**谁引用了我** (From-space pointers)              | 记录：**哪块内存脏了** (Card dirty bits)         |
| **精度** | 高精度（精确记录某个对象）                              | 低精度（模糊匹配，整个卡页只要有一个指针就算脏） |
| **位置** | 通常存在于**被引用方**（如老年代每个 Region 都有 RSet） | 存在于**JVM 全局堆**中，与内存地址一一对应       |
### 2. 真实工作流程（以 G1 为例）
> **Minor GC 为了快，默认不扫描整个老年代**
>
> → 老年代指向新生代的引用**没被 GC 看见**
>
> → 新生代对象被误判成垃圾 → 被错误回收
>
> 
**这才是卡表 / 记忆集存在的唯一意义。**
假设现在发生 **Minor GC**（只回收新生代）：
1. **GC 开始**：
   - 正常扫描 **GC Roots**（栈、静态变量、JNI）。
   - 发现这些 Roots 引用了新生代对象 → 没问题。
   - **关键问题**：**老年代对象也引用了新生代对象！** 如果不扫描老年代，这些引用就会漏网，导致对象误回收。
2. **使用卡表**：
   - GC 遍历整个 **卡表**。
   - 筛选出所有 **值为 1（变脏）** 的卡页索引。
   - 计算这些卡页对应的**内存地址范围**。
3. **精准扫描**：
   - 把这些**脏卡页内的所有对象**，暂时当作 **GC Roots** 加入扫描链。
   - 扫描这些老年代对象，找出它们指向的新生代对象。
4. **完成**：
   - 这样就不漏扫了！
   - 不需要扫描整个老年代，只扫脏卡页，效率飞升。

# 三、深层痛点：为什么需要卡表？（解决 O(n) 灾难）
如果没有卡表，做跨代引用扫描会怎样？
### 1. 错误做法（全量扫描）
- **每次 GC**，都遍历 **整个老年代** 的所有对象。
- 老年代越大，STW 越长。
- 这是**Parallel GC** 早期的做法（虽然它本身不分代精细扫），效率极低。

### 2. 正确做法（卡表 + 写屏障）
- **写时记录**：只有在发生**赋值操作**时，才更新卡表。
- **扫时只扫脏**：GC 时只扫那些在运行时**发生过引用写入**的区域。
- **效率公式**：`扫描次数 << 老年代大小`。

# 四、硬核细节：卡表是怎么更新的？（写屏障）
这是 JVM 最核心的黑魔法之一。

### 1. 伪代码逻辑（C++ 层面）
当执行 `obj.field = ref` 时：
```c++
void oop_field_store(oop* addr, oop new_val) {
    // 1. 保存旧值
    // 2. 写入新值
    *addr = new_val; 

    // 3. 写屏障核心：更新卡表
    if (new_val != NULL) {
        // 计算卡页索引
        size_t card_idx = (size_t)new_val >> CardTable::card_shift;
        // 置为脏
        Universe::heap()->card_table()->mark_dirty(card_idx);
    }
}
```
### 2. 为什么要用 `>>`（右移）？
- 卡页大小固定（比如 512B）。
- 512 = 2^9。
- 地址是 8 字节对齐的。
- **右移 9 位** 等价于 **除以 512**，位运算比除法极快！
- 这保证了**计算卡表索引是 O(1) 且极快**。

### 3. 伪共享（False Sharing）优化
- 卡表是 `byte[]`，非常小。
- 多线程并发写时，可能会同时修改同一个 Cache Line 里的卡表项。
- JVM 内部会做优化（比如填充），减少性能损耗。

### 4. JVM 怎么极快判断对象在新生代 / 老年代？

根本不用查对象头、不用查表，靠内存地址区间！
HotSpot 对堆内存做了物理分段，新生代、老年代的地址范围是固定连续、启动时就确定的：
新生代地址范围：[YoungStart, YoungEnd]
老年代地址范围：[OldStart, OldEnd]
判断一个对象指针属于哪一代，只需要一次数值比较：

```c
// 判断指针是否在老年代
bool is_old(oop p) {
    return (uintptr_t)p >= OldStart && (uintptr_t)p <= OldEnd;
}

// 判断指针是否在新生代
bool is_young(oop p) {
    return (uintptr_t)p >= YoungStart && (uintptr_t)p <= YoungEnd;
}
```

纯 CPU 寄存器运算，纳秒级，没有任何 IO / 内存遍历开销。

# 五、进阶：记忆集（RSet）是如何组织卡表的？
你可能会问：*“卡表是全局的，G1 是怎么做到只看某个 Region 的跨代引用？”*

这就是 **记忆集（RSet）** 的作用！

### 1. 结构
在 G1 中，每个 **Region（分区）** 都有一个 `Remembered Set`。
- **RSet 的内部**：
  - 它不是直接存卡表，而是存 **卡表的索引** 或者 **具体的对象地址**。
  - 简单说：**RSet = 该 Region 所有脏卡页的索引集合**。

### 2. 流程
1. **写操作**：
   - 写屏障更新**全局卡表**（置 1）。
   - 同时，更新**被引用对象所属 Region** 的 **RSet**（把这个卡页索引加进去）。
2. **GC 扫描**：
   - GC 拿到当前要回收的 Region。
   - 直接查该 Region 的 **RSet**。
   - 通过 RSet 找到全局卡表中对应的脏卡页。
   - 只扫描这些脏卡页内的对象。

### 3. 为什么这样设计？
- **空间优化**：全局卡表只有一份，所有 Region 共用。
- **时间优化**：RSet 只记录关键索引，不用全量存。
