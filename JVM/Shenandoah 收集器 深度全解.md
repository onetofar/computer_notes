# Shenandoah 收集器 深度全解
## 🎯 核心定位与前世今生
Shenandoah 是由 Red Hat 主导开发、OpenJDK 原生集成的**全堆并发低延迟垃圾收集器**，核心设计目标是**实现「亚毫秒级STW + 无内存碎片 + 全平台兼容」**，是 CMS、G1 的下一代低延迟替代方案，也是 ZGC 的开源平替。
- 核心定位：**并发整理式全堆收集器**，彻底打破「移动对象必须STW」的传统枷锁
- 历史演进：JDK12 正式集成，JDK15 稳定，OpenJDK 全平台支持（Windows/Linux/ARM 等）
- 核心差异：不依赖 ZGC 的染色指针技术，通过 **Brooks 转发指针** 实现并发对象移动，兼容性拉满
- 核心价值：在保持极低STW的同时，彻底解决 CMS 内存碎片、G1 筛选回收STW不可控的痛点，适配现代大堆、低延迟业务场景
## ⚙️ 完整工作流程（全阶段详解，1:1贴合思维导图）
Shenandoah 的核心突破是**全程几乎无STW的并发回收**，完整流程分为9个核心阶段，其中仅初始标记、最终标记等为极短STW，其余阶段全部与用户线程并发运行：
### 1. 初始标记（Initial Mark）
- 执行方式：**极短STW单线程执行**
- 核心任务：仅标记 GC Roots 直接关联的对象，初始化三色标记队列
- 特点：停顿时间微秒级，几乎无感知，为后续并发标记提供起点
- 补充：流程与 G1 初始标记逻辑基本一致
### 2. 并发标记（Concurrent Mark）
- 执行方式：**与用户线程并发运行，无STW**
- 核心任务：从初始标记的灰色对象出发，遍历全堆对象图，递归标记所有存活对象
- 核心逻辑：
  - **依然是 SATB（原始快照 / Stab-the-Beginning），和 G1 同属 SATB 体系，而非 CMS 的增量更新**；你提到的「记录并发期间的引用变更」，正是 SATB 写前屏障的核心职责。
  - 触发读写屏障，记录并发期间的引用变更
  - 统计每个 Region 的存活对象数量，为后续并发回收做准备
- 特点：耗时较长但完全无停顿，不影响业务运行
### 3. 最终标记（Final Mark）
- 执行方式：**极短STW多线程执行**
- 核心任务：补全并发标记期间的引用变更，完成最终存活对象标记
- 特点：STW时长极短（毫秒级以内），仅处理标记收尾，无全堆扫描
- 补充：流程与 G1 最终标记逻辑基本一致
### 4. 并发清理（Concurrent Cleanup）
- 执行方式：**与用户线程并发运行，无STW**
- 核心任务：清理**完全无存活对象的空Region**（即思维导图中「一个对象也存活不了的Region」）
- 特点：直接释放整块空Region内存，无需复制，效率极高，提前释放空间
### 5. 并发回收（Concurrent Evacuation / 核心差异阶段）
- 执行方式：**与用户线程并发运行，无STW**
- 核心定位：Shenandoah 与传统收集器的**核心本质差异**
- 核心逻辑：
  - 选择回收价值最高的 Region，将其中的存活对象**并发复制**到其他未被使用的空 Region 中
  - 全程不STW，通过**读屏障+转发指针**解决对象移动后的引用指向问题
- 核心价值：在并发状态下完成对象移动，彻底打破「移动对象必须STW」的传统限制，同时天然消除内存碎片
### 6. 初始引用更新（Initial Reference Update）
- 执行方式：**极短STW线程集合点**
- 核心任务：建立所有用户线程的集合点，确保所有线程的并发回收阶段已经彻底完成
- 特点：仅做线程同步，无实际扫描/复制操作，停顿时间极短
### 7. 并发引用更新（Concurrent Reference Update）
- 执行方式：**与用户线程并发运行，无STW**
- 核心任务：遍历堆中所有指向旧对象的引用，将其批量更新为新对象的地址
- 特点：耗时与堆中引用数量正相关，全程并发，不影响业务
### 8. 最终引用更新（Final Reference Update）
- 执行方式：**极短STW单线程执行**
- 核心任务：修正 GC Roots 中的引用，将根引用从旧对象地址更新为新对象地址
- 特点：仅处理根引用，停顿时间微秒级
### 9. 并发更新（Concurrent Update）
- 执行方式：**与用户线程并发运行，无STW**
- 核心任务：收尾全堆引用更新，重置标记状态、转发指针，为下一次GC做准备
- 特点：全程无停顿，完成GC全流程闭环
### 🧩 核心技术：对象转发的两种实现方案（对应思维导图「怎么转发的？」）
Shenandoah 实现并发对象移动的核心是**转发指针技术**，思维导图中明确了两种实现方案：
#### 方案一：设置内存保护陷阱（Memory Protection Trap）（和csapp中断异常强相关，可以看思维导图对应文档）
- 原理：将旧对象所在的内存页设置为「不可访问」状态，当用户线程访问旧对象时，触发内存访问异常
- 处理逻辑：JVM 捕获异常后，将访问转发到新对象地址，同时修正该引用
- 核心缺陷：
  - 必须依赖操作系统层面的直接支持，兼容性差
  - 会导致用户线程频繁切换到内核态，上下文切换代价极大
  - 无法预紧使用，性能损耗严重，生产环境几乎不采用
#### 方案二：引入 Brooks Pointer（Brooks Forwarding Pointer，生产唯一方案）
- 原理：在**原有对象布局的最前面，统一增加一个新的引用字段（Brooks Pointer）**，该指针默认指向对象自身
```
【 Brooks Pointer（8字节） 】→ 固定加在最前面！ 
【 原有对象头：mark word 】 
【 原有对象头：klass pointer 】 
【 实例数据（用户字段） 】 
【 对齐填充 】
```
- 核心逻辑：
  - 正常状态（对象未移动）：Brooks Pointer 指向对象自身，访问无额外开销
  - 并发回收（对象移动）：将 Brooks Pointer 的值修改为新对象的地址
  - 所有对该对象的访问，都会先通过 Brooks Pointer 转发，自动跳转到新对象
- 核心优势：
  - 不依赖操作系统特性，全平台兼容
  - 仅需修改指针值，无需内核态切换，性能损耗可控
  - 所有访问自动转发，彻底解决并发移动后的引用一致性问题

### ⚠️ 并发问题的解决方案（对应思维导图「并发问题」）
在并发回收过程中，用户线程可能同时修改对象的字段，导致引用不一致。Shenandoah 采用 **CAS（Compare-And-Swap）原子操作** 解决该问题：
- 核心逻辑：当用户线程修改对象字段时，同时判断「修改字段」和「更新转发指针」两个操作的原子性
- 规则：两个操作只能有一个成功，避免并发修改导致的数据不一致
- 效果：保证并发回收期间，对象的引用一致性和数据完整性，无需STW

## 🛡️ 底层核心实现：Brooks 转发指针与读写屏障
### 1. Brooks 转发指针结构
- 对象内存布局：`[Brooks Pointer 转发字段] + [对象头] + [实例数据] + [对齐填充]`
- 转发字段作用：
  - 未移动：指向自身，访问无额外开销
  - 已移动：指向新对象地址，所有访问自动转发
- 内存开销：每个对象额外增加一个指针大小（64位系统下8字节），整体内存开销约5%-10%

### 2. 读写屏障实现
- 读屏障：读取对象时，**先检查 Brooks Pointer**，自动转发到新对象地址，保证引用一致性
- 写屏障：修改对象引用时，**触发CAS操作，保证并发修改的原子性，避免数据不一致**

#### 🌏深化写屏障

GC 正在**并发转移对象**（旧对象 A → 新对象 A'），用户线程**同时修改对象引用**。

此时存在**两大致命风险**：

1. 用户线程把数据写入**即将被回收的旧对象** → **数据丢失**
2. 用户线程修改字段 + GC 修改 Brooks 转发指针 → **并发冲突、数据错乱**

##### 核心解决方案：CAS 无锁原子操作

Shenandoah 用 **CAS（Compare-And-Swap）** 绑定两个操作的**原子性**：

> **检查对象是否已转移 + 执行引用赋值**
>
> 两个操作要么全部成功，要么全部失败，绝对不中断、不穿插。

##### 底层执行逻辑（深化到硬件级）

写屏障会做 4 件原子事：

1. **读取对象的 Brooks 转发指针**

2. **判断对象是否已被转移**（是否指向新地址）

3. **如果已转移：强制将赋值操作定向到新对象**

4. **CAS 原子替换引用值**，不允许并发打断

   ```c
   //伪代码实现
   void cas_write_barrier(obj, field, new_value) {
       // 1. 原子获取 Brooks 转发指针（对象真实地址）
       forward_ptr = CAS_load(obj.brooks_ptr); 
       
       // 2. 跳转到真实新对象（杜绝写入旧对象）
       real_obj = forward_ptr; 
       
       // 3. CAS 原子赋值：保证"检查+写入"不可分割
       while (!CAS(real_obj.field, old_value, new_value)) {
           // 并发冲突则自旋重试，全程无锁、无STW
           old_value = real_obj.field;
       }
   }
   ```

   ##### 为什么是 CAS，而不是加锁？

   - **加锁**：需要内核态互斥锁，触发上下文切换，**毁掉低延迟**

   - **CAS**：硬件级原子指令（`CMPXCHG`），**纯用户态、无切换、无阻塞**

     完全符合 GC 低延迟、高并发的设计目标。

     

- 核心优势：屏障逻辑简单，性能损耗远低于ZGC的染色指针对读屏障的重度依赖

### 3.双层写屏障 + 读屏障 = 完整并发安全闭环

Shenandoah 是**业界唯一的读写双屏障收集器**，三者分工天衣无缝：

1. **SATB 写屏障**：管**标记** → 保证哪些对象存活
2. **CAS 写屏障**：管**修改** → 保证并发修改不丢数据、不冲突
3. **Brooks 读屏障**：管**读取** → 保证访问自动跳转到新对象

## ✅ 核心优点（贴合思维导图）
Shenandoah 继承了 G1 的核心优势，同时实现了更低延迟、更优的并发能力：
1. **极致低延迟**
   - 全程仅4次极短STW，总停顿亚毫秒级，用户完全无感知
   - 停顿时间与堆大小完全无关，支持TB级大堆
2. **无内存碎片**
   - 并发回收阶段采用复制算法，存活对象被规整复制到空Region，天然消除内存碎片
   - 彻底解决CMS标记-清除的碎片痛点，杜绝大对象分配失败
3. **全平台兼容**
   - 不依赖ZGC的染色指针技术，支持32位/64位系统、Windows/Linux/ARM等全平台
   - OpenJDK原生集成，开源免费，适配各类硬件环境
4. **并发整理能力**
   - 唯一实现「并发对象移动+并发整理」的开源收集器，彻底打破传统GC的「移动=STW」枷锁
5. **回收效率高**
   - 并发清理空Region，提前释放内存，降低内存压力

## ❌ 核心缺点（贴合思维导图）
### 1. 高运行负荷下吞吐量下降（思维导图核心缺点）
- 核心原因：读写屏障、Brooks Pointer的转发操作会占用大量CPU资源，在高并发、高负荷场景下，CPU开销显著上升，导致业务吞吐量下降
- 思维导图佐证：Shenandoah 对200G数据进行ES索引搜索的运行数据显示，高负荷下吞吐量明显低于G1/Parallel系列
### 2. 额外内存开销
- 每个对象需要额外存储Brooks Pointer，64位系统下每个对象增加8字节，整体内存开销约5%-10%
- 维护转发指针、读写屏障需要额外的内存空间，小堆场景下开销占比更高
### 3. CPU开销较高
- 并发回收、引用更新、屏障检查会持续占用CPU核心，挤占业务线程资源
- 高并发场景下，CPU利用率上升，业务响应速度受影响
### 4. 调优复杂度较高
- 涉及并发线程数、屏障参数、Region大小等多个调优维度，新手调优难度高于G1

## 🎯 核心调优参数
- `-XX:+UseShenandoahGC`：开启Shenandoah收集器（JDK12+支持）
- `-XX:ShenandoahGCHeuristics=adaptive`：设置GC启发式算法（默认自适应，可选择static/aggressive等）
- `-XX:ShenandoahRegionSize`：设置Region大小（默认自动计算，可手动指定）
- `-XX:ConcGCThreads`：并发阶段GC线程数
- `-XX:ParallelGCThreads`：STW阶段并行GC线程数
- `-XX:ShenandoahInitFreeThreshold`：设置初始空闲Region阈值，控制GC触发时机

## 🎯 最终总结
1. Shenandoah 是**开源全平台兼容的极致低延迟收集器**，通过Brooks转发指针实现并发对象移动，彻底打破传统GC的「移动=STW」枷锁
2. 核心流程：9个阶段，仅4次极短STW，全程几乎无停顿，支持TB级大堆
3. 核心Trade-off：用**少量内存开销+CPU开销+高负荷吞吐量下降**，换取**亚毫秒级STW+无碎片+全平台兼容**
4. 适用场景：OpenJDK生态、全平台环境、中等-大堆（4G-64G）、低延迟刚需业务（如金融、实时服务）
5. 与ZGC的定位差异：ZGC主打TB级大堆、极致低延迟，Shenandoah主打全平台兼容、开源平替
