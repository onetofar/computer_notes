# ZGC 收集器 深度全解
## 🎯 核心定位与前世今生
ZGC 是由 Oracle 官方研发的**超低延迟、高并发、TB级堆全堆垃圾收集器**，核心设计目标是**实现「亚毫秒级STW + 停顿与堆大小无关 + 无内存碎片 + 极致并发」**，是 JVM 垃圾回收的终极形态之一，主打超大堆、极致低延迟场景，为云原生、金融交易、实时计算而生。
- 核心定位：**全并发着色指针式低延迟收集器**，彻底打破「堆越大停顿越长」的传统GC魔咒
- 历史演进：JDK11 引入实验性支持 → JDK15 正式生产可用 → JDK21 推出**分代ZGC**，兼顾低延迟与吞吐量
- 核心差异：不依赖 Brooks 转发指针，通过**染色指针（Colored Pointers）+ 纯读屏障**实现并发对象移动，64位系统专属优化
- 核心价值：实现**STW<10ms**（实际多为微秒级）、停顿时间与堆大小完全解耦，支持TB级堆内存，无内存碎片
## ⚙️ 完整工作流程（全阶段深度完善版）
### 流程前置基础
ZGC 启动时会完成堆内存的**动态Page划分**（Small:2MB / Medium:32MB / Large:N*2MB），并初始化核心数据结构：重分配表（Relocation Table）、标记队列、GC线程池。所有流程基于「染色指针+纯读屏障」驱动，全程仅2次极短STW，其余阶段完全并发。
ZGC 完整流程分为**6个核心阶段+分代扩展逻辑**，阶段间通过「染色指针标记位」和「核心数据结构」衔接，形成无间断的并发闭环：
| 阶段序号 | 阶段名称                    | 执行方式             | STW状态   | 核心依赖                     | 阶段目标                                 |
| ----- | --------------------------- | -------------------- | --------- | ---------------------------- | ---------------------------------------- |
| 1        | 初始标记（Initial Mark）    | 单线程               | 微秒级STW | GC Roots、染色指针（初始态） | 标记根对象，为并发标记提供起点           |
| 2        | 并发标记（Concurrent Mark） | 多线程与用户线程并发 | 无STW     | SATB算法、读屏障、染色指针   | 全堆遍历标记存活对象，统计Region存活数据 |
| 3        | 并发预备重分配              | 多线程与用户线程并发 | 无STW     | 存活统计数据、重分配集       | 筛选高价值回收Region，生成重分配集       |
| 4        | 重分配（Relocate）          | 多线程               | 微秒级STW | GC Roots、重分配集           | 根对象初始重分配，完成最后一次STW        |
| 5        | 并发重分配                  | 多线程与用户线程并发 | 无STW     | 染色指针、读屏障、重分配表   | 全堆并发移动对象，自动转发旧对象访问     |
| 6        | 并发重映射                  | 多线程与用户线程并发 | 无STW     | 染色指针、读屏障             | 批量更新旧引用，重置GC状态，回收旧Region |
| 扩展     | 分代ZGC年轻代优先回收       | 多线程与用户线程并发 | 无额外STW | 分代标记位、年轻代Page池     | 优先回收年轻代，降低全堆回收开销         |
### 1. 初始标记（Initial Mark）【首次STW】
#### 执行细节
- 触发时机：GC阈值触发（如堆使用率达阈值）后立即执行
- 执行线程：VM主线程（单线程）
- 核心步骤：
  1. 暂停所有用户线程（微秒级STW）；
  2. 扫描所有GC Roots（栈引用、静态变量、JNI引用等），标记根对象的染色指针为「Marked0/Marked1」；
  3. 初始化标记队列，将根对象地址写入队列，作为并发标记的起点；
  4. 恢复所有用户线程，结束STW。
#### 关键边界
- 仅扫描根集合，不遍历对象图，停顿时间与根数量正相关（通常<1ms）；
- 标记位初始选择「Marked0」或「Marked1」（交替使用，避免与上一次GC标记冲突）。
#### 核心输出
- 标记完成的根对象队列；
- 染色指针标记位初始化完成。
### 2. 并发标记（Concurrent Mark）【核心并发阶段】
#### 执行细节
- 触发时机：初始标记完成后立即启动
- 执行线程：GC并发线程池（数量由`-XX:ConcGCThreads`控制）
- 核心步骤：
  1. 从根对象队列出发，遍历全堆对象图；
  2. 读取对象时触发读屏障，通过**SATB（原始快照）算法**记录对象引用快照，杜绝并发漏标；
  3. 对存活对象的染色指针标记为「Marked0/Marked1」，垃圾对象不标记；
  4. 实时统计每个动态Page的存活对象数量、内存占比；
  5. 标记完成后，输出「存活对象统计报表」。
#### 关键保障
- 读屏障为原子操作，并发访问时保证标记唯一性，无锁竞争；
- SATB算法通过“快照”避免用户线程修改引用导致的漏标，无需写屏障。
#### 性能特点
- 耗时与堆大小正相关（TB级堆可能耗时数秒），但完全不阻塞用户线程；
- 可与后续“并发预备重分配”阶段部分重叠执行，优化总耗时。
### 3. 并发预备重分配（Concurrent Prepare for Relocate）【回收筛选阶段】
#### 执行细节
- 触发时机：并发标记完成（或部分完成）后启动
- 执行线程：GC并发线程池
- 核心步骤：
  1. 读取并发标记的「存活对象统计报表」；
  2. 筛选“回收价值最高”的Page（存活占比低、碎片率高、大对象Page优先）；
  3. 将筛选出的Page加入「重分配集（Relocation Set）」，记录到核心数据结构；
  4. 预分配新Page（同规格），为并发重分配做内存准备。
#### 筛选规则（核心优化点）
- 小对象Page：存活占比<20%优先回收；
- 中对象Page：存活占比<30%优先回收；
- 大对象Page：只要包含垃圾就优先回收（避免大对象碎片）；
- 分代ZGC：年轻代Page无条件加入重分配集（优先回收）。
#### 核心输出
- 重分配集（待移动的Page列表）；
- 预分配的新Page池。
### 4. 重分配（Relocate）【最后一次STW】
#### 执行细节
- 触发时机：重分配集生成完成后
- 执行线程：多线程GC线程池（并行执行，提升效率）
- 核心步骤：
  1. 暂停所有用户线程（微秒级STW）；
  2. 扫描GC Roots，找到根对象中属于「重分配集」的对象；
  3. 将这些根对象复制到预分配的新Page中，更新重分配表（旧地址→新地址）；
  4. 标记根对象的染色指针为「Remapped」（正常访问态）；
  5. 恢复所有用户线程，结束STW。
#### 关键价值
- 仅处理根对象的初始重分配，将99%的对象移动开销放到并发阶段；
- 多线程并行执行，进一步压缩STW时长（通常<1ms）。
#### 核心输出
- 根对象完成重分配，指向新Page；
- 重分配表初始化完成（旧地址与新地址映射）。
### 5. 并发重分配（Concurrent Relocate）【ZGC核心差异阶段】
#### 执行细节
- 触发时机：重分配阶段完成后立即启动
- 执行线程：GC并发线程池
- 核心步骤（并发对象移动核心逻辑）：
  1. 遍历重分配集中的所有Page，逐个复制存活对象到新Page；
  2. 每复制一个对象，更新「重分配表」（旧地址→新地址），并将旧对象的染色指针标记为「Marked0/Marked1」；
  3. 用户线程访问旧对象时，触发读屏障：
     - 解析染色指针标记位（Marked0/Marked1）；
     - 从「重分配表」读取新地址，原子更新指针为新地址；
     - 自动转发访问到新对象，无感知；
  4. 对象复制完成后，立即释放旧Page（无碎片）。
#### 核心优势（对比Shenandoah）
| 特性           | ZGC 并发重分配              | Shenandoah 并发回收       |
| -------------- | --------------------------- | ------------------------- |
| 对象移动触发   | 读屏障自动转发              | Brooks指针被动转发        |
| 旧Page释放时机 | 复制完成立即释放            | 需等待所有引用更新后释放  |
| 内存碎片控制   | 天然无碎片（复制+即时释放） | 无碎片但释放延迟          |
| 大堆适配性     | TB级无压力                  | 64G内最优，超大堆开销上升 |
#### 性能特点
- 全程无STW，对象移动与用户线程完全并行；
- 读屏障开销极低（纯用户态操作），高并发场景下性能损耗<5%。
### 6. 并发重映射（Concurrent Remap）【流程闭环阶段】
#### 执行细节
- 触发时机：并发重分配完成80%后（可与下一次GC并发标记重叠）
- 执行线程：GC并发线程池
- 核心步骤：
  1. 遍历全堆所有对象引用，批量将指向旧地址的指针更新为新地址；
  2. 将所有对象的染色指针标记位重置为「Remapped」（正常访问态）；
  3. 清空重分配表、标记队列，重置GC状态；
  4. 回收所有已完成重映射的旧Page，释放内存。
#### 优化逻辑
- 可与下一次GC的「并发标记」阶段重叠执行（无需等待重映射完全完成）；
- 分代ZGC中，年轻代重映射优先执行，老年代按需延迟执行。
#### 流程闭环
- 重映射完成后，本次GC流程结束；
- 堆内存回到「干净态」，染色指针均为「Remapped」，等待下一次GC触发。
### 扩展：JDK21+分代ZGC流程补充
#### 核心变更
- 堆内存逻辑划分为「年轻代Page池」和「老年代Page池」，物理Page仍为动态大小；
- 新增「年轻代标记位」（染色指针扩展位），标记对象所属代；
#### 流程差异
1. 初始标记：额外标记根对象的「代信息」；
2. 并发标记：优先统计年轻代Page的存活数据；
3. 并发预备重分配：年轻代Page无条件加入重分配集（优先回收）；
4. 并发重分配：年轻代对象移动优先级高于老年代；
5. 并发重映射：年轻代引用优先更新，老年代可延迟到下一次GC。
#### 核心收益
- 年轻代对象存活率低，优先回收可降低全堆回收开销；
- 吞吐量提升10%-20%，兼顾低延迟与高吞吐。

### 🧩 核心技术：对象转发的实现方案（对应思维导图「怎么转发的？」）
ZGC 实现并发对象移动的核心是**染色指针（Colored Pointers）**，摒弃内存保护陷阱、Brooks 指针，采用纯指针级软件方案，为生产唯一最优解：
#### 方案：染色指针（Colored Pointers）+ 纯读屏障

- 核心流程：

 - 1. | 流程阶段       | 染色指针作用                             | 读屏障作用                       |
       | -------------- | ---------------------------------------- | -------------------------------- |
       | 初始标记       | 标记根对象为 Marked0/Marked1             | 无（STW 阶段，无用户线程访问）   |
       | 并发标记       | 存储对象存活状态，避免重复标记           | 触发 SATB 快照，杜绝并发漏标     |
       | 并发预备重分配 | 无（仅筛选 Page）                        | 无                               |
       | 重分配         | 标记根对象为 Remapped（正常态）          | 无（STW 阶段）                   |
       | 并发重分配     | 标记旧对象为 Marked0/Marked1（触发转发） | 解析标记位，自动转发到新对象地址 |
       | 并发重映射     | 重置为 Remapped（完成地址更新）          | 原子更新指针，保证引用一致性     |

- 原理：利用64位系统指针的**高4位闲置空间**，存储对象的GC标记状态（Marked0/Marked1/Remapped/Finalizable），不修改对象头、不新增对象字段
- 核心逻辑：
  - 正常状态：指针标记为**Remapped**，直接访问对象，无额外开销
  - 并发重分配：对象被移动后，指针标记为**Marked0/Marked1**，读屏障自动转发到新地址
  - 所有对象访问通过**指针本身的标记位**完成转发，无额外内存开销、无内核态切换
- 核心优势：
  - 64位系统原生支持，无操作系统依赖，纯用户态实现
  - 不修改对象布局、不新增字段，**无额外内存开销**
  - 转发逻辑极简，仅靠读屏障解析指针标记位，性能损耗极低
  - 彻底解决并发对象移动的引用一致性问题，无数据错乱风险

### ⚠️ 并发问题的解决方案（对应思维导图「并发问题」）
ZGC 全程仅依赖**读屏障+染色指针**解决并发标记、并发重分配的所有线程安全问题，无复杂CAS操作、无锁竞争：
- 核心逻辑：读取对象时，读屏障解析染色指针标记位，自动完成**标记/转发/重映射**，所有操作原子化
- 规则：读屏障为**原子操作**，并发访问时保证标记、转发、重映射的唯一性，无并发冲突
- 效果：全程无STW、无锁、无CAS自旋，完美解决并发移动、并发标记的引用一致性问题

## 🛡️ 底层核心实现：染色指针与纯读屏障
### 1. 染色指针（Colored Pointers）结构
- 64位指针布局：**高4位（GC标记位）+ 低60位（对象地址）**
- 4个核心标记位：
  - Marked0/Marked1：标记存活对象，交替使用避免重复标记
  - Remapped：对象未移动/已完成重映射，正常访问状态
  - Finalizable：需执行finalize方法的对象标记
- 核心特性：
  - 标记信息存在**指针本身**，而非对象头/对象字段
  - 无对象修改、无内存开销，转发逻辑由指针直接承载

### 2. 纯读屏障（Load Barrier）实现
- 触发时机：**仅读取对象引用时触发**，ZGC**无写屏障**，这是核心优势
- 核心逻辑：
  1. 读取对象指针，解析高4位染色标记位
  2. 标记为Remapped：直接访问对象，无额外操作
  3. 标记为Marked0/Marked1：通过重分配表找到新对象地址，自动转发访问
  4. 原子完成标记/转发/重映射，无并发冲突
- 底层执行逻辑（硬件级）：
  ```c
  // ZGC 读屏障伪代码
  void z_load_barrier(ref *p) {
      ref o = *p;
      // 解析染色指针标记位
      if (is_marked(o)) {
          // 查找重分配表，获取新对象地址
          ref new_o = relocate_table_get(o);
          // 原子更新指针为新地址
          cas(p, o, new_o);
          o = new_o;
      }
      return o;
  }
  ```
- 核心优势：
  - 仅读屏障，无写屏障开销，CPU损耗远低于Shenandoah
  - 纯指针操作，无对象修改、无内核切换
  - 原子操作无锁，并发性能极致

### 3. 动态Region（Page）设计
- 堆内存划分为**动态大小Page**，而非固定Region：
  - Small Page：2MB（小对象）
  - Medium Page：32MB（中对象）
  - Large Page：N*2MB（大对象，按需分配）
- 核心特性：
  - 无固定分代（JDK21分代ZGC新增逻辑分代）
  - 大对象专属Page，无碎片、无分配失败
  - 动态扩容/收缩，内存利用率极高

## ✅ 核心优点（贴合思维导图）
ZGC 是目前JVM生态**低延迟性能天花板**，全面超越CMS/G1/Shenandoah：
1. **极致低延迟**

4. **纯读屏障，CPU开销更低**
   - 仅读屏障，无写屏障、无CAS复合操作
   - 高并发场景下性能优于Shenandoah
5. **超大堆友好**
   - 支持TB级堆内存，是超大内存服务器的唯一GC选择
   - JDK21分代ZGC，兼顾低延迟与吞吐量

## ❌ 核心缺点（贴合思维导图）
### 1. 仅支持64位系统
- 染色指针依赖64位指针的高4位闲置空间，**32位系统完全不支持**
- 嵌入式、32位服务器场景无法使用

### 2. 吞吐量略有下降
- 读屏障存在固定CPU开销，高吞吐批处理场景下，吞吐量比Parallel/G1低5%-15%
- 极致低延迟的必然trade-off

### 3. 调优复杂度中等
- 涉及Page大小、停顿目标、并发线程数、分代参数等
- 新手需理解染色指针、重分配逻辑才能精准调优

### 4. 早期版本无分代（JDK21前）
- 全堆回收，存活对象极多时并发开销略高
- JDK21分代ZGC已解决该问题

## ❓答疑点

64位虚拟内存寻址只有48位有效吧，而且jvm还做了指针缩短，够用吗？详解；

**完全够用，而且空间极其富余；但 ZGC 必须付出一个代价：彻底放弃指针压缩（Compressed OOPs）**
你记得的「64位只用到48位有效地址」完全正确，这正是 ZGC 染色指针能成立的**硬件底层底气**。

---

#### 一、先把 3 个关键前提钉死（不绕晕）
1. **x86_64 真实虚拟地址：只有 48 位有效**
   高 16 位（bit48～bit63）是**符号扩展位**，必须全 0 或全 1，**硬件 MMU 完全无视这 16 位**，不参与地址翻译。
2. **JVM 指针压缩（Compressed OOPs）**
   堆 ≤32GB 时，用 **32 位偏移量**存指针（8字节→4字节），省内存、提缓存命中率。
3. **ZGC 硬性规则：不支持、也不能开指针压缩**
   染色指针必须用 **完整 64 位指针** 存标记位，32 位根本没地方塞。

---

#### 二、ZGC 64 位指针布局（一眼看懂）
```
64位指针结构：
[ 高4位：染色标记位 ] + [ 低60位：真实地址位 ]
bit63～bit60        bit59～bit0
```
##### 1. 高4位（标记位）—— 放你说的 4 种状态
- Marked0 / Marked1：交替标记存活（解决并发漏标）
- Remapped：已重映射、指向新对象（正常访问）
- Finalizable：需执行 finalize 方法
→ **4 位刚好存 4 个状态，不多不少**

##### 2. 低60位（地址位）—— 到底够不够用？
- 硬件只用到 **48 位有效地址** → 可寻址 **256TB** 虚拟空间
- ZGC 用 **60 位地址** → 可寻址 **1EB**（1024TB）
→ **60位 远大于 48位，地址空间冗余1024倍，完全用不完**

##### 3. 为什么不会和硬件冲突？
高4位属于**硬件闲置的高16位符号扩展区**
MMU 翻译地址时**直接忽略高16位**，只看低48位
→ 标记位不影响寻址、不触发异常、不占有用地址位

---

#### 三、灵魂拷问：指针压缩呢？JVM 默认不是会缩指针吗？

## 关键结论：**ZGC = 染色指针 → 必须禁用指针压缩**
### 1. 为什么冲突？
- 指针压缩：**32位**存指针 → 没任何多余位放标记
- 染色指针：必须 **64位** → 高4位存标记，低60位存地址
→ 两者**天生互斥**，ZGC 直接放弃压缩

### 2. 代价是什么（架构师必知 trade-off）
- 堆内存占用**上涨 15%～20%**（指针从4字节→8字节）
- 缓存命中率略微下降
- 但换来：**亚毫秒STW、并发对象移动、无碎片、TB级堆**

### 3. 和 Shenandoah 对比（你最关心的差异）
| 收集器     | 指针方案        | 支持压缩 | 标记存在哪    | 内存开销     |
| ---------- | --------------- | -------- | ------------- | ------------ |
| ZGC        | 染色指针        | ❌ 不支持 | 指针高4位     | 高（无压缩） |
| Shenandoah | Brooks 转发指针 | ✅ 支持   | 对象头前8字节 | 中（有压缩） |

#### 四、回到你的问题：**够用吗？详解**
##### 1. 地址位够不够？
✅ **极度富余**
48位硬件 → 256TB
ZGC 60位地址 → 1EB
→ 就算未来硬件升级到 56位寻址，ZGC 依然够用

##### 2. 标记位够不够？
✅ **刚好4位=4个状态，完美匹配**
Marked0/Marked1/Remapped/Finalizable
→ 不需要更多位，设计刚刚好

##### 3. 会不会浪费空间？
❌ **完全不浪费**
用的是**硬件本来就闲置、永远用不到的高位**
不是抢有效地址位，是**白嫖闲置空间**



| 问题现象                  | 根因                            | 解决方案                                     |
| ------------------------- | ------------------------------- | -------------------------------------------- |
| STW 时长超过 10ms         | 根对象数量过多 / 并发线程数不足 | 减少静态变量 / JNI 引用，调大`ConcGCThreads` |

## 🎯 核心调优参数

- ### 1. 核心参数（流程相关）

  |             参数             |          作用          | 推荐值（64G 堆示例）  |
  | :--------------------------: | :--------------------: | :-------------------: |
  |        `-XX:+UseZGC`         |        开启 ZGC        |         必开          |
  |     `-XX:+ZGenerational`     | 开启分代 ZGC（JDK21+） |   必开（兼顾吞吐）    |
  |  `-XX:MaxGCPauseMillis=10`   |   最大 STW 停顿目标    | 1-10ms（低延迟场景）  |
  |    `-XX:ConcGCThreads=8`     |     并发 GC 线程数     |   CPU 核心数的 50%    |
  | `-XX:ZCollectionInterval=30` |   GC 触发间隔（秒）    | 10-60s（避免频繁 GC） |
  |     `-XX:ZHeapSize=64g`      |       最大堆内存       |  物理内存的 70%-80%   |

  ### 2. 流程优化原则

  - 低延迟场景：调小`MaxGCPauseMillis`（1-5ms），调大`ConcGCThreads`；
  - 高吞吐场景：开启分代 ZGC，调大`ZCollectionInterval`；
  - 超大堆（TB 级）：禁用分代 ZGC（年轻代优势弱化），调大`ConcGCThreads`。

## 🎯 最终总结

1. ZGC 是**Oracle官方顶级低延迟GC**，通过**染色指针+纯读屏障**实现全程并发对象移动，是JVM GC的终极形态
2. 核心流程：6个阶段，仅2次微秒级STW，停顿与堆大小完全无关，支持TB级超大堆
3. 核心Trade-off：用**极低的CPU读屏障开销+小幅吞吐量下降**，换取**微秒级STW+无碎片+无额外内存开销**
4. 适用场景：64位系统、云原生、金融交易、实时计算、8G+超大堆、低延迟刚需核心业务
5. 定位差异：ZGC主打**超大堆+极致低延迟**，Shenandoah主打**全平台兼容开源平替**，G1主打**通用可控停顿**，CMS已被全面淘汰
