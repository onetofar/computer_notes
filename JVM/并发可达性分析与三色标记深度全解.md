# 并发可达性分析与三色标记深度全解
## 🔍 三色标记：并发GC的核心可达性算法
三色标记是 HotSpot 解决并发标记阶段 GC 线程与用户线程并行运行、引用关系动态变化的核心算法，是 [[CMS(Concurrent Mark Sweep) 标记-清除收集器 深度全解|CMS]]、[[G1(Garbage-First) 垃圾收集器 深度全解|G1]] 等并发收集器的理论基石，也是《深入理解 Java 虚拟机》中并发 GC 的理论基石，彻底替代传统二色标记的并发缺陷。
## 🎨 三色对象状态严格定义
| 颜色       | 精准定义                                               | 状态角色                               |
| 
---

| ⚪ 白色对象 | GC 线程未访问、未标记；标记周期结束仍为白 = 不可达垃圾 | 初始默认状态，待判定存活 / 垃圾        |
| ⚫ 灰色对象 | 已被 GC 访问标记，但引用字段未全部扫描完成             | GC 标记工作队列，黑 / 白对象的中间桥梁 |
| ⚫ 黑色对象 | 已被 GC 访问标记，且所有引用字段扫描完毕               | 绝对存活对象，不会被二次处理           |

## ⛓️ 三色标记核心不变性
三色标记保证标记结果 100% 正确的绝对准则：
- 黑色对象绝对不能直接指向白色对象
- 灰色→白色：合法状态，灰色对象后续会将白色对象标灰，无漏标风险
- 白色→任意颜色：合法状态，不影响标记规则
- 黑色→白色：非法状态，黑色对象已完成扫描，不会再次处理，直接导致白色对象漏标

串行 GC 中用户线程完全暂停，引用关系无变更，该不变性天然成立，标记无任何错误。

## ⚙️ 串行三色标记标准流程

无并发干扰下，GC 线程按固定流程推进，全程严守三色不变性：
1.  初始标记
    - 从 GC Roots 出发，遍历所有直接引用的对象
    - 将这些直接引用的对象标记为灰色，其余对象默认保持白色
2.  扫描推进
    - 从灰色对象队列中取出一个对象
    - 遍历该对象的所有引用字段
    - 将引用的白色对象标记为灰色，加入标记队列
    - 当前对象所有引用扫描完成后，将其标记为黑色
3.  标记结束
    - 灰色对象队列完全清空，无待处理对象
    - 黑色对象 = 全部存活对象
    - 白色对象 = 待回收垃圾

## ⚠️ 并发场景：对象消失（漏标）问题
并发 GC 中，用户线程（赋值器）会动态修改引用关系，破坏三色不变性，导致存活对象被误判为垃圾回收，即书中定义的「对象消失」，本质是漏标。

### ❌ 漏标本质
本该存活的白色对象，既无法被 GC 线程扫描标记，又无有效存活路径，最终被错误回收。

### 📝 漏标产生的充要条件
漏标必须同时满足两个条件，缺一不可：
1.  条件一：用户线程插入黑色对象 → 白色对象的新引用
    - 直接打破「黑不指白」不变性
2.  条件二：用户线程删除该白色对象所有来自灰色对象或者还未扫描的白色的引用
    - 白色对象失去被扫描的唯一路径

单一条件均不会漏标：
- 仅条件一：白色对象仍被灰色对象引用，会被正常标记
- 仅条件二：白色对象无任何引用，属于真实垃圾，回收合理

### 🔄 漏标完整流程推演
1.  初始引用链：GC Roots(黑) → 对象A(黑) → 对象B(灰) → 对象C(白)
    - 此时满足三色不变性，无非法引用关系
2.  用户线程操作 1：B.next = null
    - 删除灰→白引用，满足条件二
3.  用户线程操作 2：A.next = C
    - 新增黑→白引用，满足条件一
4.  GC 标记收尾
    - 对象 B 扫描完成，标记为黑色
    - 灰色对象队列清空，标记结束
5.  最终结果：对象 C 仍为白色，被误回收，出现对象消失

## 🛠️ 漏标解决方案一：增量更新（CMS 回收器）
### 💡 核心原理
破坏漏标条件一：禁止黑色对象直接引用白色对象，当黑→白新引用产生时，将黑色对象重新标记为灰色，放回扫描队列补全标记，恢复三色不变性。

### 🧩 实现机制：写后屏障
基于赋值操作完成后触发的写后屏障，具体流程：
- 拦截所有引用赋值操作
- 判断当前赋值是否为黑→白引用
- 若命中，将黑色对象回退为灰色，等待 GC 二次扫描
- 最终标记阶段 STW 扫描所有回退的灰色对象，彻底避免漏标

### 🔧 补充点：代码层面如何实现以及和记忆集的写屏障实现有什么不同

-  CMS 增量更新写屏障（三色标记专用）

```c
// 赋值操作：给对象字段赋值
void oop_store(oop* field, oop new_obj) {
    // 1. 执行基础赋值
    *field = new_obj;

    // 2. 增量更新写屏障：仅关注 黑色对象 → 白色对象 引用
    oop owner_obj = get_owner_object(field);
    if (is_black(owner_obj) && is_white(new_obj)) {
        // 核心逻辑：将黑色对象重新标记为灰色
        mark_as_grey(owner_obj);
        // 加入GC扫描队列，等待重新扫描
        add_to_mark_queue(owner_obj);
    }
}
```

- 卡表 / 记忆集 写后屏障（跨代引用专用）

```c
  // 赋值操作：给对象字段赋值

      // 1. 执行基础赋值
```

### ⛰️为什么STW会很长？

#### 前提：

**无变更 → 无 Flag → 不扫描**

只要没有对象被置灰，`cms_need_rescan=false`，Remark 阶段直接跳过重扫

**有变更 → 置 Flag → 精准扫**

仅触发对应变更区域的扫描，**不扫描全堆**

**预清理优化**

提前并行处理脏数据，尽量在 STW 前把 Flag 清空，让 STW 时间更短

```c
// CMS 并发预清理（无 STW，用户线程并行运行）
void cms_preclean_phase() {
    // 仅当有脏卡时才处理
    if (has_dirty_cards) {
        // 遍历所有脏卡页，扫描灰色对象
        scan_all_dirty_cards();
        // 处理完成，清空卡表标记
        has_dirty_cards = false;
    }

    // 预清理完成后，判断是否还需要重扫
    // 如果没有任何灰色对象，关闭总开关
    if (get_grey_object_count() == 0) {
        cms_need_rescan = false;
    }
}
```

**总开关兜底**

`cms_need_rescan` 作为核心 Flag，只要有一个对象被置灰，就开启重扫

  #### 1. 增量更新写屏障的**天然缺陷**

  CMS 写后屏障只做一件事：

  > 发现**黑→白新引用** → 把黑色对象**重新标灰**，丢进 GC 标记队列

  但它**不做集中化日志收集**，存在两个致命问题：

  1. **并发期间用户线程持续修改**

     

     标灰的对象，可能在 GC 线程处理前，又被用户线程新增 / 删除引用，产生新的黑→白引用

  2. **待扫描对象散落在全堆，无统一清单**

     

     重新变灰的对象、线程栈动态引用、新生代晋升对象，

     随机散布在整个堆内存

     ，CMS 没有一个集中队列记录 “哪些对象需要重扫”

  #### 2. CMS 重新标记 (Remark) 阶段的强制 STW 逻辑

  并发标记结束后，GC 线程不知道：

  - 还有哪些灰对象没扫描
  - 还有哪些黑→白引用没修复
  - 线程栈 / 寄存器里的引用又变了哪些

  为了**绝对不漏标**，CMS 只能：

  1. **STW 暂停所有用户线程**（杜绝引用再变更）

  2. **全范围扫描**：

     - 扫描全部**GC Roots**（栈、静态变量、JNI）
     - 扫描整个**新生代**（跨代引用）
     - 扫描全堆中**所有被写屏障标灰的对象**
     - 扫描并发期间**所有发生引用变更的内存区域**

  3. 一次性把所有待扫描对象处理完

### ⚖️ 特性与权衡
- ✅ 优点：写屏障开销极低，无额外队列，内存占用小
- ❌ 缺点：最终标记阶段 STW 时长较长
- 🎯 适用：CMS 传统分代并发 GC，优先保证内存效率

## 🛠️ 漏标解决方案二：原始快照 SATB（G1/Shenandoah）
### 💡 核心原理
破坏漏标条件二：保留 GC 启动时的对象引用快照，当灰→白引用被删除时，记录被删除的旧引用，作为临时 GC Roots 参与标记，保证白色对象必然被扫描。

### 🧩 实现机制：写前屏障
基于赋值操作执行前触发的写前屏障，具体流程：
- 赋值前捕获即将被覆盖的旧引用
- 若旧引用非空，将其存入 SATB 队列
- GC 标记阶段将 SATB 队列对象作为临时根，标记关联白色对象
- 无需二次扫描黑色对象，全程低 STW

### 🔧写前屏障代码实现

```c
// 对象引用赋值操作
void oop_field_store(oop* field, oop new_ref) {
    // 第一步：写前屏障，捕获旧引用（SATB 核心）
    oop old_ref = *field;
    if (old_ref != nullptr) {
        // 旧引用入队，作为临时 GC Roots
        satb_queue->push(old_ref);
    }

    // 第二步：执行真实赋值操作
    *field = new_ref;
}

// GC 并发处理 SATB 队列
void process_satb_queue() {
    while (!satb_queue->empty()) {
        oop obj = satb_queue->pop();
        // 以该对象为根，递归标记白色对象
        mark_white_to_grey(obj);
    }
}
```

### ⛰️深入讲解

#### ⚡ 为什么 SATB 能实现极低 STW？

##### 1. 屏障逻辑极轻量

- 写前屏障仅做**旧引用判空 + 入队**
- 无地址区间判断、无颜色状态修改、无循环操作
- 单赋值操作开销远小于增量更新

##### 2. 最终标记仅处理 SATB 队列

- CMS 增量更新需要 STW 扫描**全堆变更**
- SATB 仅需 STW 处理 SATB 队列中剩余对象
- 队列长度远小于全堆对象数量，STW 毫秒级

##### 3. 无黑色对象回退与二次扫描

- 不修改黑色对象的颜色状态
- 不需要重新扫描已完成扫描的黑色对象
- 无冗余扫描，标记阶段全程并行度极高

##### 4. 队列处理可并行化

- SATB 队列支持多 GC 线程并行处理
- 用户线程与 GC 线程可同时操作队列
- 最大程度减少停顿等待

### ❓ 核心疑问解答：是否会产生无效游离对象？

你的理解**完全正确**，这种场景确实会出现**本应回收却未回收的对象**，但这不是内存泄漏 / 游离对象，而是**浮动垃圾**，是 SATB 预期内的设计妥协。

#### 浮动垃圾的本质

- 快照中存活、并发标记期间变为垃圾的对象
- SATB 为了绝对避免漏标，会将其一并标记存活
- 仅存活**当前一个 GC 周期**，下次 GC 会正常回收

#### 为什么这是可接受的设计？

1. **正确性优先**：漏标会导致程序崩溃，浮动垃圾仅降低一点点内存利用率
2. **空间代价极小**：并发标记期间产生的浮动垃圾数量有限
3. **低 STW 收益远大于代价**：对高实时性服务（金融、网关）不可替代
4. **无内存泄漏风险**：浮动垃圾不会长期堆积，下一轮 GC 必然清理

### ⚖️ 特性与权衡

- ✅ 优点：最终标记 STW 极短，适配低延迟场景
- ❌ 缺点：需维护 SATB 队列，内存开销高，产生浮动垃圾
- 🎯 适用：G1/Shenandoah 现代分区低延迟 GC

| 对比维度       | 增量更新（CMS）            | 原始快照 SATB（G1/Shenandoah） |
| -------------- | -------------------------- | ------------------------------ |

| STW 开销       | 较高，最终标记耗时久       | 极低，仅短暂 STW               |

| 浮动垃圾       | 极少                       | 较多，快照机制天然产生         |

## 🔗 HotSpot 工程化深度联动
三色标记并非孤立算法，与 HotSpot 底层核心组件深度绑定，构成完整并发 GC 体系。

### 🔗 与写屏障、卡表 / RSet 联动
- 三色标记写屏障 + 卡表 / RSet 写屏障为同一套底层拦截机制
- 卡表 / RSet：解决跨代 / 跨 Region 引用漏扫
- 三色标记写屏障：解决并发标记漏标
- G1 会同时叠加两种屏障，兼顾扫描精度与并发正确性

### 🔗 与安全点、安全区域、OopMap 联动
- 初始 / 最终标记必须在安全点 STW，保证 OopMap 引用位置准确
- 阻塞线程无法到达安全点时，依赖安全区域稳定引用关系，GC 直接读取 OopMap 标记
- OopMap 为三色标记提供精准 GC Roots 枚举，是并发标记的底层支撑

### 🗑️ 浮动垃圾本质与权衡
浮动垃圾是 SATB 空间换时间的工程妥协：
- 快照中存活、实际已废弃的对象，本次 GC 不回收
- 无内存泄漏风险，下次 GC 周期会正常清理
- 是低延迟 GC 必然付出的微小代价

## 🎯 终极总结
- 三色标记是并发 GC 的理论核心，「黑不指白」是保证标记正确的绝对准则
- 对象消失（漏标）是严格的充要条件问题，仅双条件同时满足才会触发
- 增量更新与 SATB 是两种对立设计哲学：前者用 STW 换内存，后者用内存换低 STW
- 三色标记与写屏障、卡表、安全点、OopMap 深度联动，是 HotSpot 现代 GC 的底层枢纽
