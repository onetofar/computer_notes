# 字节码执行引擎下的方法调用（架构师底层全链路笔记）
## 🟢 模块1：方法调用的基础执行流程（对应思维导图上方「基础流程」分支）
### 1.1 完整执行步骤（纯解释执行逻辑，无JIT）
对应你思维导图中「栈帧创建/参数传递/程序计数器跳转/方法返回」的流程节点：
1.  **指令触发**：执行`invokexxx`字节码指令，从常量池读取目标方法的**符号引用**（如`com.example.Cat#speak()`）。
2.  **栈帧准备**：为被调用方法创建新栈帧，包含4个核心部分（对应思维导图中「栈帧结构」节点）：
    - 局部变量表：存储方法参数（含`this`引用）和局部变量
    - 操作数栈：存储方法执行过程中的中间结果
    - 动态链接：指向常量池中的方法符号引，后续解析为直接引用
    - 方法出口：记录调用方的程序计数器位置，用于方法返回
3.  **参数传递**：将调用方栈帧操作数栈中的参数，传递到被调用方栈帧的局部变量表。
    - 实例方法：`this`引用作为第0个参数传递，是底层约定
    - 静态方法：无`this`引用，直接传递方法参数
4.  **程序计数器跳转**：将程序计数器指向被调用方法的字节码起始地址，开始执行方法逻辑。
5.  **方法返回**：被调用方法执行完成后，将返回值压入调用方栈帧的操作数栈，弹出被调用方栈帧，恢复调用方的程序计数器，继续执行原方法。
### 1.2 架构师必懂的基础细节
- 栈帧的「动态链接」字段，是后续解析阶段的入口，对应你图中「动态链接」的前置节点。
- 方法调用的性能开销，本质来自栈帧切换、参数传递和指令跳转，这也是JIT方法内联优化的核心目标。
## 🟡 模块2：字节码调用指令体系（对应思维导图中「5种调用指令」分支）
完全对应你图中`invokestatic`/`invokespecial`/`invokevirtual`/`invokeinterface`/`invokedynamic`的分支，每个指令展开细节：
**懒加载是「什么时候解析」的问题；**
**vtable 是「运行时怎么找方法」的问题；**
- 懒加载：**全方法通用**，是链接 / 解析的时机策略
- 虚方法表：**仅多态方法需要**，是运行时分派的查找结构
二者正交无关：
- 懒加载可以不用 vtable（静态方法、Lambda）
- vtable 也可以关闭懒解析（JVM 参数强制提前解析）
最关键：**Lambda 这种懒加载，跟虚方法表一毛钱关系都没有**
| 指令              | 对应思维导图场景            | 适用场景             | 解析方式                               | 与后续分派的关联                              |
| -------------- | --------------------------- | -------------------- | -------------------------------------- | --------------------------------------------- |
| `invokestatic`    | 静态方法调用                | 类静态方法           | **非虚方法**，解析阶段直接绑定         | 无分派步骤，直接执行                          |
| `invokespecial`   | 构造方法/私有方法/父类方法  | 不可重写的实例方法   | **非虚方法**，解析阶段直接绑定         | 无分派步骤，直接执行                          |
| `invokevirtual`   | 普通实例方法（可重写）      | 可被重写的实例方法   | **虚方法**，解析阶段仅绑定vtable偏移量 | 需动态分派确定最终方法                        |
| `invokeinterface` | 接口方法调用                | 接口定义的方法       | **虚方法**，解析阶段绑定偏移量         | 需动态分派查找实现类                          |
| `invokedynamic`   | 动态方法（Lambda/方法引用） | 运行时动态绑定的方法 | 基于`CallSite`实现，无固定目标         | 无传统分派逻辑，由Bootstrap方法动态生成调用点 |
### 补充：`invokedynamic`的特殊细节（对应思维导图底部「动态方法」分支）
- 核心作用：打破Java早期方法调用的静态绑定限制，支持动态语言特性（如Lambda、方法引用、动态脚本）。
- 底层流程：由Bootstrap方法在第一次调用时生成`CallSite`（调用点），后续调用直接使用该调用点，无需重复解析，是一种「运行时动态绑定」的特殊实现。

#### invokedynamic 核心引擎：Bootstrap 方法（BSM）底层全解析
（思维导图专属深化：定位→底层流程→核心组件→与JVM解析/分派的关系→与LD链接的对标）
---

##### 一、核心底层定位（思维导图：动态链接顶级节点）
1. **全称**：Bootstrap Method（BSM，引导方法）
2. **唯一身份**：`invokedynamic` 指令的**专属动态链接器**，是 JVM 规范定义的**底层钩子方法**
3. **核心使命**：在**第一次调用**时，为 `invokedynamic` 生成并绑定 `CallSite`（调用点），完成**JVM级别的动态符号解析**
4. **本质区别**：
   - 普通方法：靠 `vtable` + 动态分派 固定绑定
   - `invokedynamic`：靠 **BSM 运行时自定义绑定**，彻底脱离JVM默认分派逻辑
5. **架构师结论**：BSM = **JVM内部实现的、轻量级的、动态链接入口**（对标系统LD链接器的初始化逻辑）

---

##### 二、底层三要素（BSM 运行必须依赖的JVM底层组件）
全是思维导图底层分支的核心：
1. **MethodType（方法类型）**
   描述方法的**参数+返回值**（签名），是动态绑定的「匹配规则」
2. **MethodHandle（方法句柄）**
   JVM底层的**直接可执行指针**（比反射轻10~100倍），是最终要执行的目标代码
3. **CallSite（调用点）**
   BSM的输出结果，包装了 `MethodHandle`，是**动态链接的最终直接引用**

---

##### 三、完整底层执行流程（1:1 对应思维导图「解析→动态链接→分派」链路）
###### 阶段1：字节码与常量池（类加载阶段，无执行）
1. 编译生成 `invokedynamic` 指令
2. 常量池生成 `InvokeDynamic` 项：绑定 **BSM方法 + MethodType + 附加参数**
3. **类加载解析阶段：不做任何解析！**（和普通方法完全不同，纯懒加载）

###### 阶段2：第一次调用（JVM主动触发BSM，动态链接核心）
1. 执行 `invokedynamic` → JVM检查：无绑定CallSite
2. **JVM主动调用 Bootstrap Method**（不是普通方法调用，不走栈帧分派）
3. BSM 执行核心逻辑：
   - 接收参数：MethodType + 附加参数
   - 查找/生成目标方法的 **MethodHandle**
   - 创建 `CallSite`，将 MethodHandle 注入
4. BSM 返回 `CallSite` 给 JVM
5. JVM **永久缓存**这个CallSite（常量池级别的缓存）
6. 跳转执行 CallSite 中的 MethodHandle

###### 阶段3：后续调用（零解析、零开销）
1. 直接使用缓存的 CallSite
2. 直接执行 MethodHandle
3. **无分派、无解析、无动态查找**，性能等价于直接方法调用

---

##### 四、BSM 与 JVM 原生机制的底层关系（思维导图必考点）

###### 1. 与「解析阶段」的关系
- 普通方法：解析阶段 → 生成直接引用（指针/偏移量）
- `invokedynamic`：**解析阶段完全不工作**
- BSM：**替代了JVM原生解析阶段**，成为动态解析的唯一入口

###### 2. 与「动态分派」的关系
- 普通虚方法：vtable偏移量 + 动态分派 = 固定多态
- BSM：**完全自定义分派逻辑**
  可以绑定任意方法、任意逻辑、任意条件，不受vtable限制
- 结论：BSM 是 **动态分派的终极形态**

---

##### 五、BSM 与 系统LD动态链接 的深度对标（你最关注的底层关联）
##### 🔴 设计思想：1:1 完全一致（广义强相关）
| JVM Bootstrap Method     | 系统 LD 动态链接器 (ld-linux.so) | 核心思想                 |
| ------------------------ | -------------------------------- | ------------------------ |
| 第一次调用触发执行       | 第一次函数调用触发PLT/GOT绑定    | 延迟绑定（Lazy Binding） |
| 生成CallSite并缓存       | 解析符号写入GOT表并永久缓存      | 运行时符号解析+缓存      |
| 输出MethodHandle直接执行 | 输出虚拟内存地址直接执行         | 符号→直接可执行目标      |

##### 🟢 底层实现：完全无关
- BSM：JVM内部纯Java层钩子，运行在JVM抽象层
- LD：操作系统内核级链接器，操作虚拟内存/ELF文件

---

##### 六、架构师必须知道的实战底层（极简硬核）
1. **Lambda 表达式底层**：JDK8 所有 Lambda 都是靠 `invokedynamic` + BSM 实现
2. **性能**：BSM仅执行一次，后续调用**零开销**，远超反射
3. **灵活性**：BSM可以实现**运行时动态修改CallSite**（MutableCallSite），实现热替换
4. **定位**：BSM 是 Java 迈向动态语言的**底层基石**

---

##### 七、思维导图一句话闭环
**Bootstrap方法是invokedynamic的专属动态链接器，替代JVM原生解析阶段，在第一次调用时生成CallSite完成动态绑定，是JVM层面延迟绑定的终极实现，与系统LD链接器设计思想完全同源、底层实现完全独立。**

## 🔵 模块3：解析阶段：符号引用→直接引用（对应思维导图中「常量池解析」分支）
这部分融入我们之前聊的核心误区，完全对应你图中「解析阶段」的节点，纠正关键认知：

### 3.1 核心概念澄清（对应你之前的误区疑问）
- **符号引用**：常量池中以字符串形式存在的方法签名（如`Ljava/lang/String;toString()`），仅描述方法的“身份”，无实际内存地址。
- **直接引用**：解析阶段转换后的结果，**不是所有场景都是CPU可直接跳转的内存地址**，分为两种情况（对应你图中「非虚方法/虚方法解析差异」节点）：
  1.  **非虚方法（`invokestatic`/`invokespecial`）**：
      - 解析逻辑：方法不可被重写，编译期已确定目标方法，解析阶段直接转换为**方法区中`Method`对象的指针**，该指针直接指向方法字节码的入口地址。
      - 执行时：方法调用直接跳转到该地址，无额外步骤。
  2.  **虚方法（`invokevirtual`/`invokeinterface`）**：
      - 解析逻辑：方法可被重写，编译期无法确定运行时的实际调用目标，因此解析阶段仅完成两步：
        1.  解析出方法的**虚方法表（vtable）偏移量**（如`Animal.speak()`在vtable中的索引为8）；
        2.  建立符号引用与该偏移量的绑定关系。
      - 关键：**此时的“直接引用”只是一个偏移量，不是具体的内存地址，同一个偏移量在不同子类的vtable中，对应的地址完全不同。**

### 3.2 与类加载的关联（对应思维导图中「类加载解析阶段」节点）
解析阶段是类加载的最后一步，将常量池中的符号引用，在运行时转换为直接引用，为后续方法调用提供依据。解析默认采用**懒解析**（延迟绑定），仅在方法第一次调用时完成转换，避免启动时一次性解析所有符号，减少启动开销。

## 🟣 模块4：方法分派：静态分派+动态分派（对应思维导图中「分派」分支）
完全对应你图中「静态分派（重载）/动态分派（重写）」的分支，融入我们聊的「分派不是形式上的过程」的核心结论：

### 4.1 静态分派：编译期确定的方法选择（对应思维导图中「重载」节点）
- 核心场景：方法重载（Overload），根据方法的**静态类型**（声明类型），**在编译期确定调用的方法**。
- 底层逻辑：编译期根据参数的静态类型，直接绑定到对应的重载方法，解析阶段仅需将符号引用转换为该方法的直接引用（非虚方法的指针），无运行时额外步骤。
- 示例：
  ```java
  public class DispatchExample {
      static class Animal {}
      static class Cat extends Animal {}
      public void feed(Animal animal) { System.out.println("Feed Animal"); }
      public void feed(Cat cat) { System.out.println("Feed Cat"); }
      public static void main(String[] args) {
          Animal animal = new Cat();
          new DispatchExample().feed(animal); // 编译期确定调用feed(Animal)，静态分派
      }
  }
  ```
- 误区澄清：静态分派看起来像“形式上的过程”，本质是编译期绑定的结果，和解析阶段配合完成调用，无运行时动态选择。

### 4.2 动态分派：运行时基于实际类型的方法查找（核心中的核心，对应思维导图中「重写/vtable」节点）
这部分纠正你之前的认知，说明动态分派不是形式上的过程，而是真正的地址查找步骤：
- **核心场景**：方法重写（Override），根据对象的**实际类型**（对象的真实类型），在运行时确定调用的方法，是Java多态的底层实现。
- **底层依赖：虚方法表（vtable）**（对应你图中「虚方法表」节点）：
- vtable 是元空间里类元数据的连续指针数组，所有实例共享；对象只存指向它的指针，不存表本身；和 cp_cache 完全无关
  - 每个**类在加载时，会构建自己的虚方法表，表中存储了所有可重写方法的入口地址**。
  - 继承自父类的方法，会继承父类的vtable偏移量；重写的方法，会替换为自己的方法入口地址。
  - 接口方法的实现，会在实现类的vtable中，绑定对应的接口方法偏移量。
- **完整执行流程（对应你图中动态分派的链路节点）**：
  1.  解析阶段：拿到`Animal.speak()`的vtable偏移量（如8）。
  2.  运行时：获取对象的实际类型（如`Cat`，而非声明的`Animal`）。
  3.  动态分派：找到`Cat`类的虚方法表，使用偏移量8，查到`Cat.speak()`的真正入口地址（子类重写的方法，在子类虚方法表（vtable）中的偏移量，和父类中该同名方法的偏移量**严格保持一致**。）。
  4.  执行：跳转到该地址执行方法。
- 关键结论：解析阶段仅提供了“偏移量”，而动态分派则完成了“用偏移量查实际类型的vtable，拿到最终执行地址”的核心步骤，二者是前后依赖的关系，动态分派不是形式上的过程。

## 🟤 模块5：动态链接：JVM与系统级LD的深度关联（对应思维导图中「动态链接对比」分支）
这是你重点关注的部分，完全对应你图中「JVM动态链接 vs 系统级LD」的分支，从底层实现和设计思想两个维度展开：

### 5.1 底层实现：完全无关的两套机制（对应思维导图中「底层实现差异」节点）
| 维度         | JVM动态链接（解析+分派）                         | 系统级LD动态链接                        | 核心差异                                                     |
| ------------ | ------------------------------------------------ | --------------------------------------- | ------------------------------------------------------------ |
| 作用层级     | 虚拟机内部机制，运行在JVM抽象层之上              | 操作系统级工具，直接与CPU、虚拟内存交互 | JVM的所有操作都在自己的内存空间中，不直接接触系统的链接器    |
| 处理对象     | 字节码中的JVM符号引用（常量池中的方法签名）      | ELF文件中的原生符号（如C函数名）        | 处理的符号体系完全不同，JVM的符号是虚拟机内部定义的          |
| 解析结果     | 非虚方法：`Method`对象指针；虚方法：vtable偏移量 | GOT表中的虚拟内存地址                   | JVM的解析结果不是CPU可直接跳转的机器码地址，而LD的解析结果是直接的内存地址 |
| 延迟绑定实现 | 虚方法表（vtable）+动态分派                      | PLT/GOT表（过程链接表/全局偏移量表）    | 实现机制完全独立，无任何底层交互                             |

### 5.2 设计思想：高度相似的三大核心逻辑（对应思维导图中「设计思想关联」节点）
虽然底层实现无关，但二者在解决“如何找到目标代码”的问题上，有高度一致的设计思想：
1.  **符号引用→直接引用的解析逻辑**：
    - 核心目标一致：都是将“字符串形式的符号”转换为“可直接访问的地址/偏移量”，解决“如何定位目标代码”的问题。
    - JVM：常量池解析 → 直接引用（指针/偏移量）；
    - LD：ELF符号表解析 → GOT表中的虚拟内存地址。
2.  **延迟绑定（Lazy Binding）的思想**：
    - 核心目标一致：避免启动时一次性解析所有符号，减少启动开销，仅在方法第一次调用时完成解析。
    - JVM：解析阶段默认采用懒解析，仅在方法第一次调用时完成符号引用到直接引用的转换；
    - LD：通过PLT/GOT表实现延迟绑定，第一次调用时解析符号并写入GOT表，后续调用直接跳转。
3.  **多态/多版本兼容的支持**：
    - 核心目标一致：支持根据运行时上下文选择不同的目标实现。
    - JVM：通过vtable和动态分派，支持多态（同一个方法签名，不同子类的不同实现）；
    - LD：通过动态链接的多版本`.so`库，支持同一个符号的不同版本实现，根据运行时环境选择加载。

## ⚠️ 模块6：架构师视角的关键边界与常见误区（对应思维导图中「误区/调优」节点）
完全对应你图中「常见误区/调优边界」的分支，纠正我们之前聊的所有核心误区：
1.  **误区1：解析阶段会拿到虚方法的最终执行地址**
    - 纠正：虚方法在解析阶段仅拿到vtable偏移量，最终地址必须通过动态分派获取，解析阶段无法提前确定对象的实际类型。
2.  **误区2：动态分派是形式上的过程**
    
    - 纠正：动态分派是虚方法调用的核心步骤，负责用偏移量查对象实际类型的vtable，拿到最终执行地址，是Java多态的底层实现，不是可有可无的形式。
3.  **误区3：JVM的方法调用和系统级LD链接底层相关**
    - 纠正：仅设计思想相似，底层实现完全无关，二者是独立的两套机制，JVM的动态链接不依赖系统级LD。
4.  **误区4：静态分派和动态分派都和解析阶段无关**
    - 纠正：静态分派的结果在编译期已确定，解析阶段仅需转换符号引用；动态分派依赖解析阶段的vtable偏移量，二者都和解析阶段强关联。
5.  **调优边界：高频虚方法调用的动态分派开销，可通过JIT的方法内联消除**
    
    - 动态分派的vtable查找会带来性能开销，JIT的方法内联可以直接将方法体嵌入调用方，消除动态分派的开销，这也是架构师调优高频接口的关键手段。
    
    # 详解：JIT 方法内联如何消除动态分派开销（架构师调优核心）
    先纠正一个**90%开发者的误区**：
    **动态分派的性能开销，根本不是 vtable 数组寻址慢（O(1) 纯内存寻址，纳秒级）**
    真正开销是：**间接跳转 + 编译器优化阻断 + CPU 分支预测失败**
    JIT 方法内联的核心价值，就是**彻底干掉这三类开销**，而不是简单“省去查表”。
    
    下面结合 HotSpot 底层逻辑、你之前学的 vtable/动态分派全链路，逐层级拆解。
    
    ---
    
    ## 一、先明确：原生动态分派的真实性能开销
    在**无 JIT 优化、纯解释执行**的动态分派流程中：
    1. 通过对象头 `_klass` 找到元空间的类元数据
    2. 通过**解析阶段固定的偏移量**索引 vtable 数组
    3. 拿到方法地址后，执行**CPU 间接跳转**（`jmp *%reg`）
    
    这三步的**真实开销**只有 3 点（架构师只需要关注这 3 点）：
    1. **间接跳转开销**
       CPU 执行直接跳转是零开销，但**间接跳转（跳向寄存器中的地址）**会打断流水线，产生 10~30 个时钟周期停顿。
    2. **编译器优化阻断**
       因为方法地址是运行时从 vtable 查出来的，**编译期无法确定具体方法**，所以无法做：常量传播、死代码消除、循环优化等后续优化。
    3. **多态分支预测失败**
       如果一个接口有多个实现类，CPU 分支预测器会猜错实际类型，导致**流水线清空**，开销暴增 100 倍以上。
    
    > 总结：vtable 查表本身几乎无开销，**动态分派的开销全在“间接跳转+无法优化+预测失败”**。
    
    ---
    
    ## 二、JIT 方法内联消除动态分派的核心底层流程
    仅**C2 重度优化器**能做到（C1 仅做简单内联），核心是两步：
    **运行时类型推导 → 激进方法内联**
    
    ### 步骤1：JIT 收集运行时类型信息（Profile  profiling）
    JVM 在解释执行/C1 阶段，会统计**调用点的实际类型分布**：
    ```java
    // 高频调用代码
    Animal animal = new Cat();
    for(;;) animal.speak(); 
    ```
    JIT 发现：**100% 的实际类型都是 Cat**，没有其他子类。
    
    ### 步骤2：锁定实际类型，跳过 vtable 动态分派
    JIT 直接判定：
    > 这个调用点的实际类型 = Cat，不需要再查 vtable。
    
    于是**直接放弃动态分派逻辑**，不再走：
    `对象_klass → vtable → 偏移量索引 → 间接跳转`
    
    ### 步骤3：执行方法内联（核心优化）
    JIT 把 **Cat.speak() 的方法机器码，直接嵌入到调用方方法体中**，相当于代码改写：
    ```java
    // 原始代码（有动态分派）
    animal.speak();
    
    // JIT 内联后（无任何分派、无跳转）
    {
        // 直接嵌入 Cat.speak() 的全部执行逻辑
        System.out.println("喵喵");
    }
    ```
    
    ---
    
    ## 三、内联后：动态分派开销被彻底消除的 3 个结果
    1. **无 vtable 查表、无间接跳转**
       直接执行内联后的本地代码，CPU 流水线零停顿。
    2. **开启后续链式优化**
       方法内联后，JIT 可以继续做：
       常量传播、死代码消除、循环展开、寄存器分配，性能再提升 50%~300%。
    3. **消灭分支预测失败**
       没有多态选择，CPU 100% 预测正确，无流水线清空开销。
    
    > 最终效果：**高频虚方法调用，内联后性能 ≈ 直接调用静态方法**
    
    ---
    
    ## 四、方法内联能消除动态分派的**关键前提**（架构师调优必背）
    不是所有虚方法都能被内联，必须满足以下条件，否则优化失效：
    1. **调用点实际类型单一（单态）**
       一个接口/父类引用，**99% 以上都是同一个子类**（JIT 阈值）。
    2. **方法体足够小**
       HotSpot 默认：
       - 小方法（< 35 字节）强制内联
       - 中等方法（< 65 字节）可内联
       - 大方法禁止内联
    3. **方法非抽象、非接口过度分散**
       `invokeinterface` 比 `invokevirtual` 更难内联（需要 itable 查找）。
    4. **未被频繁去优化（Deoptimization）**
       如果运行中突然出现新子类（多态），JIT 会回退到解释执行，重新 profiling。
    
    ---
    
    ## 五、内联失效：动态分派开销无法消除的场景（高频接口卡顿元凶）
    架构师遇到**高频接口慢**，90% 是以下场景导致内联失效：
    1. **调用点多态泛滥**（一个接口 5+ 实现类）
       JIT 无法锁定单一类型，只能保留 vtable 动态分派。
    2. **方法体过大**
       超出 JIT 内联阈值，无法嵌入，只能间接跳转。
    3. **反射/动态代理过度使用**
       阻断类型推导，内联完全失效。
    4. **频繁创建不同子类实例**
       导致 JIT 反复去优化，始终无法稳定内联。
    
    ---
    
    ## 六、架构师调优边界（实战可落地，不碰底层源码）
    ### 1. 代码层优化（最有效）
    - 高频调用的虚方法，**尽量保证调用点单态**（减少多态实现）。
    - 高频接口方法**设计为小方法**，避免大方法禁止内联。
    - 避免在核心链路用过多动态代理/反射。
    
    ### 2. JVM 参数调优（慎用）
    ```bash
    # 扩大内联阈值，允许更大方法内联
    -XX:MaxInlineSize=100
    -XX:FreqInlineSize=200
    
    # 关闭不必要的类型虚化，强化单态推断
    -XX:-TypeProfile
    ```
    
    ### 3. 架构设计边界
    - 核心高性能链路：**少用多层虚方法继承**，优先用静态方法、final 方法（直接内联）。
    - final 方法/类：JIT 直接判定无重写，**100% 内联，彻底消除动态分派**。
    
    ---
    
    ## 七、一句话闭环（回扣你之前的所有底层逻辑）
    动态分派靠**vtable 偏移量**实现多态，但其开销源于**间接跳转与优化阻断**；
    JIT 方法内联通过**运行时类型推导锁定实际类型**，直接将方法体嵌入调用方，
    **跳过 vtable 查表、干掉间接跳转、开启链式优化**，
    从根源上消除动态分派的全部性能开销，是高频接口架构调优的核心手段。
    
    
    
    - 你说：Spring 全是接口虚方法，没法优化
    
      真相：Spring 单例 = 调用点单态
    
      JIT：**去虚化 → 跳过 vtable → 完全内联**

## 📌 思维导图链路闭环（对应你图中从定义到执行的完整链路）
方法调用的完整流程，是「字节码指令触发 → 栈帧创建与参数传递 → 解析阶段符号引用转换 → 静态/动态分派 → 执行方法逻辑 → 栈帧弹出」的闭环：
- 解析阶段为虚方法提供了vtable偏移量，是动态分派的前提；
- 动态分派基于偏移量和对象实际类型，拿到最终执行地址，是多态的核心；
- 它与系统级LD链接在底层实现上完全无关，但在设计思想上共享了符号解析、延迟绑定的核心逻辑，是虚拟机实现与原生执行实现的共性体现。
