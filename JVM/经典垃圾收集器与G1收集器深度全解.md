# 经典垃圾收集器与G1收集器深度全解
## 📌 经典垃圾收集器总览
经典垃圾收集器是HotSpot虚拟机早期的分代垃圾收集实现，基于分代回收思想设计。包含 [[CMS(Concurrent Mark Sweep) 标记-清除收集器 深度全解|CMS]]、[[G1(Garbage-First) 垃圾收集器 深度全解|G1]] 等收集器。
- 将堆内存划分为新生代与老年代，针对不同代的对象存活特性，匹配不同回收算法
- 新生代对象存活率低，采用复制算法，回收效率高
- 老年代对象存活率高，采用标记-清除或标记-整理算法
- 核心目标：在停顿时间、吞吐量、内存利用率之间做工程权衡

## 进化的原因：吞吐率VS短STW？极致的业务代码以及利用率还是服务的绝对稳定舒适取舍；
## 直观对比：低STW的CMS vs 高吞吐的Parallel
假设服务总运行时间为 **1小时（3600秒）**，1小时内各执行10次GC，用真实数字一眼看懂差异：
### 🔹 Parallel Scavenge + Parallel Old（高吞吐，全STW）
- 每次GC STW时长：1秒（全STW，GC线程串行执行，无并发开销）
- 总STW时间 = 10次 × 1秒 = **10秒**（= GC总运行时间）
- 用户代码运行时间 = 3600 - 10 = **3590秒**
- 吞吐量 = 3590 / 3600 ≈ **99.72%**
### 🔹 ParNew + CMS（低延迟，并发）
- 每次GC两次STW，总STW时长：0.2秒（初始标记+重新标记）
- 总STW时间 = 10次 × 0.2秒 = **2秒**（STW仅为Parallel的1/5，看起来延迟极低）
- 但并发标记、并发清除阶段，GC线程占用20%的CPU资源（和用户抢CPU）
- GC总运行时间 = 3600秒 × 20% = **720秒**（是Parallel GC总时间的72倍！）
- 用户代码运行时间 = 3600 - 720 = **2880秒**
- 吞吐量 = 2880 / 3600 = **80%**
### 🔹 对比结论
CMS的**STW总时间远短于Parallel**，但**吞吐量远低于Parallel**，核心原因就是：
> 并发GC的「GC总运行时间」远长于全STW的高吞吐GC，大量CPU被GC线程占用，用于业务的时间占比大幅下降

## 🛠️ 并发GC拉低吞吐量的核心原因

### 🔹 1. 并发阶段的CPU抢占

- CMS的并发标记、并发清除，G1的并发标记，都是GC线程和用户线程并行执行
- GC线程会抢占CPU核心，导致用户线程可使用的CPU资源减少，业务执行速度变慢
- 比如CMS默认并发GC线程数为CPU核心数的1/4，相当于25%的CPU被GC占用，直接拉低25%的吞吐量

### 🔹 2. 写屏障的额外开销

- CMS的增量更新写后屏障、G1的SATB写前屏障，每次引用赋值都要执行额外逻辑
  - CMS：判断黑→白引用、标灰对象、标记脏卡
  - G1：记录旧引用、入SATB队列、更新RSet
- 这些逻辑会占用用户线程的CPU时间，属于GC相关开销，直接减少用户代码的有效运行时间

### 🔹 3. 记忆集/卡表的维护开销

- CMS的卡表、G1的RSet，每次跨代/跨Region引用变更都要更新
- 卡表的脏卡扫描、RSet的维护，都需要额外的CPU时间，增加GC总耗时

### 🔹 4. 浮动垃圾与内存碎片的额外开销

- CMS的浮动垃圾需要提前触发GC，增加GC执行次数
- 内存碎片导致Full GC，触发全堆STW整理，额外增加GC总时间

## 🎯 两种设计哲学的本质对立

### 🔹 高吞吐优先（Parallel系列）

- 核心目标：最大化CPU用于业务的时间占比
- 设计思路：**全STW串行执行GC**，GC线程和用户线程不抢CPU，GC总时间最短
- 代价：长STW，用户感知延迟高
- 适用场景：批处理、大数据计算、后台任务等对延迟不敏感、对CPU利用率要求高的场景

### 🔹 低延迟优先（CMS/G1/ZGC）

- 核心目标：最小化用户感知的STW停顿时间
- 设计思路：**并发执行GC**，GC线程和用户线程抢CPU，用额外的GC时间换用户不停顿
- 代价：GC总时间长，吞吐量低
- 适用场景：互联网交互型应用、微服务等对延迟敏感、对用户体验要求高的场景

## 🧩 新生代垃圾收集器

### 🔍 Serial收集器
#### 🎯 基础定位
- 最基础、历史最悠久的新生代收集器
- 单线程、串行执行的复制算法收集器
- 核心特点：简单高效，无多线程调度开销

#### ⚙️ 核心流程
1.  暂停所有用户线程，进入STW状态
2.  从GC Roots出发，标记新生代中所有存活对象
3.  将存活对象复制到Survivor区的To空间
4.  清空Eden区与From空间，交换Survivor区的角色
5.  恢复所有用户线程

#### 🧩 底层实现细节
- 采用**复制算法**，默认Eden:Survivor=8:1:1的空间比例
- 存活对象超过Survivor容量时，直接晋升老年代
- 单线程执行，无锁竞争，内存分配逻辑简单
- 无额外并发控制成本，内存占用极低

#### ✅ 核心优点
- 实现极简，无多线程调度开销
- 内存占用低，运行稳定可靠
- 复制算法无内存碎片，对象分配效率高

#### ❌ 核心缺点
- 全程STW，停顿时间随堆大小线性增长
- 单线程执行，无法利用多核CPU资源
- 高并发场景下，业务停顿影响严重

#### 🎯 适用场景
- 客户端应用、小内存虚拟机
- 对停顿时间不敏感的后台任务
- 单核CPU设备的嵌入式场景

---

### 🔍 ParNew收集器
#### 🎯 基础定位
- Serial收集器的多线程并行版本
- 新生代并行复制算法收集器
- 核心目标：利用多核CPU，缩短STW停顿时间
- 是CMS收集器的默认新生代搭档

#### ⚙️ 核心流程
1.  暂停所有用户线程，进入STW状态
2.  多线程并行执行GC Roots枚举与存活对象标记
3.  多线程并行将存活对象复制到Survivor To空间
4.  清空Eden与From空间，交换Survivor角色
5.  恢复所有用户线程

#### 🧩 底层实现细节
- 采用**并行复制算法**，并行线程数可通过参数控制
- 核心回收逻辑与Serial完全一致，仅执行方式从串行改为并行
- 写屏障与卡表逻辑完全兼容CMS，支持跨代引用标记
- 多线程执行，利用多核CPU，大幅缩短STW时间

#### ✅ 核心优点
- 多线程并行，STW时间远短于Serial
- 完全兼容CMS收集器，支持并发老年代回收
- 复制算法无内存碎片，对象分配效率高
- 实现简单，无复杂并发控制逻辑

#### ❌ 核心缺点
- 仍需全程STW，无法与用户线程并发
- 多核CPU下性能提升明显，单核下性能弱于Serial
- 无吞吐量优先优化，不适合高吞吐量场景

#### 🎯 适用场景
- 服务端多核CPU环境
- 搭配CMS收集器，实现低延迟分代回收
- 对停顿时间敏感的互联网应用

### 🔍 Parallel Scavenge收集器
#### 🎯 基础定位
- 新生代并行复制算法收集器
- 核心目标：**最大化吞吐量**，而非缩短停顿时间
- 又称「吞吐量优先收集器」
- 是JDK 1.6+默认的新生代收集器

#### ⚙️ 核心流程
1.  暂停所有用户线程，进入STW状态
2.  多线程并行标记存活对象、复制到Survivor区
3.  清空Eden与From空间，交换Survivor角色
4.  自适应调整堆大小与Survivor比例
5.  恢复所有用户线程

#### 🧩 底层实现细节
- 采用**并行复制算法**，支持自适应调节策略
- 核心优化：吞吐量优先，可通过参数控制最大停顿时间
- 自适应调节：根据应用运行情况，动态调整Eden/Survivor比例、对象晋升阈值
- 写屏障逻辑与ParNew兼容，支持分代回收体系

#### ✅ 核心优点
- 多线程并行，吞吐量极高，适合后台批处理
- 自适应调节策略，无需手动调优堆参数
- 复制算法无内存碎片，对象分配效率高
- 多核CPU下性能优异，资源利用率高

#### ❌ 核心缺点
- 仍需全程STW，停顿时间长于ParNew
- 低延迟场景下表现差，不适合交互型应用
- 自适应调节可能导致堆大小波动，稳定性略差

#### 🎯 适用场景
- 后台批处理、大数据计算等吞吐量优先场景
- 多核CPU服务器，对停顿时间不敏感
- 无需手动调优的自动化运维场景

## 🧩 老年代垃圾收集器
### 🔍 Serial Old收集器
#### 🎯 基础定位
- Serial收集器的老年代版本
- 单线程、串行执行的标记-整理算法收集器
- 核心特点：简单稳定，适用于老年代回收

#### ⚙️ 核心流程
1.  暂停所有用户线程，进入STW状态
2.  从GC Roots出发，标记老年代所有存活对象
3.  将存活对象向内存一端移动，整理内存碎片
4.  清空存活区域外的所有内存
5.  恢复所有用户线程

#### 🧩 底层实现细节
- 采用**标记-整理算法**，解决老年代内存碎片问题
- 单线程执行，无多线程开销，实现简单
- 常搭配Serial收集器，组成完整分代回收体系
- 适用于客户端、小内存老年代回收场景

#### ✅ 核心优点
- 实现简单，无多线程调度开销
- 标记-整理算法无内存碎片，内存分配效率高
- 稳定可靠，无并发风险

#### ❌ 核心缺点
- 全程STW，停顿时间极长，随老年代大小线性增长
- 单线程执行，无法利用多核CPU
- 高并发场景下，业务停顿影响严重

#### 🎯 适用场景
- 客户端应用、小内存虚拟机
- 老年代内存较小的场景
- 单核CPU设备的嵌入式场景

#### 🎯 基础定位
- Serial Old收集器的多线程并行版本

- 核心目标：最大化吞吐量，搭配Parallel Scavenge使用

#### 🧩 底层实现细节
- 采用**并行标记-整理算法**，多线程执行标记与整理
- 核心目标：吞吐量优先，搭配Parallel Scavenge组成高吞吐量分代回收体系
- 自适应调节策略，动态调整老年代回收阈值

#### ✅ 核心优点

### 🔍 CMS(Concurrent Mark Sweep)收集器
#### 🎯 基础定位
- 老年代并发标记-清除算法收集器
- 核心目标：**最短STW停顿时间**，实现低延迟回收
- 基于三色标记+增量更新写屏障解决并发漏标问题
- 是HotSpot经典低延迟老年代收集器

#### ⚙️ 完整工作流程（7个阶段）
##### 1. 初始标记阶段
- 执行方式：STW单线程执行
- 核心任务：仅标记GC Roots直接关联的老年代对象
- 特点：速度极快，停顿时间微秒级
- 关联三色标记：将直接引用对象标记为灰色

##### 2. 并发标记阶段
- 执行方式：与用户线程并发运行
- 核心任务：遍历灰色对象队列，递归标记所有存活对象
- 执行逻辑：
  - 从灰色对象出发，扫描所有引用字段
  - 白色对象→灰色对象，完成扫描→黑色对象
  - 全程无停顿，不影响业务线程
- 关联机制：触发增量更新写后屏障，记录黑→白引用

##### 3. 并发预清理阶段
- 执行方式：与用户线程并发运行
- 核心任务：提前处理并发标记期间的引用变更
- 执行逻辑：
  - 扫描卡表脏页，处理被置灰的对象
  - 尝试清空`has_dirty_cards`等控制Flag
  - 减少最终标记阶段的扫描压力
- 优化目标：最大限度降低Remark阶段的STW时长

##### 4. 并发可中止预清理阶段
- 执行方式：与用户线程并发运行
- 核心任务：等待新生代回收、等待脏卡数量降低
- 退出条件：
  - 脏卡数量低于阈值
  - 等待时间超时
  - 新生代达到回收条件
- 作用：进一步减少最终标记的扫描范围

##### 5. 重新标记阶段
- 执行方式：STW多线程执行
- 核心任务：修正并发期间的标记误差，完成全堆最终标记
- 执行逻辑：严格按照多级Flag精准扫描
  - 必扫：GC Roots
  - Flag判定：仅`cms_need_rescan=true`扫描灰色对象
  - Flag判定：仅`has_dirty_cards=true`扫描脏卡
  - Flag判定：按需扫描新生代、引用队列
- 关联理论：增量更新兜底重扫，解决并发漏标

##### 6. 并发清除阶段
- 执行方式：与用户线程并发运行
- 核心任务：回收所有白色对象（垃圾对象）
- 执行逻辑：
  - 遍历老年代，释放未标记对象的内存
  - 不移动对象、不整理内存
- 特点：无停顿，不影响业务线程

##### 7. 并发重置阶段
- 执行方式：与用户线程并发运行
- 核心任务：重置CMS标记状态、清空所有控制Flag
- 执行逻辑：
  - 清空对象三色标记
  - 重置`cms_need_rescan`/`has_dirty_cards`等Flag
  - 重置卡表、标记队列
- 为下一次GC循环做准备

#### 🧩 底层核心实现
##### 1. 增量更新写后屏障 + Flag控制
```c++
// 全局控制Flag
bool cms_need_rescan = false;
bool has_dirty_cards = false;

// CMS增量更新写后屏障
void cms_write_barrier(oop* field, oop new_obj) {
  oop owner = get_owner(field);
  if(owner->color == BLACK && new_obj->color == WHITE){
    // 修复三色状态
    owner->color = GRAY;
    // 置位扫描控制Flag
    cms_need_rescan = true;
    has_dirty_cards = true;
  }
}
```

##### 2. 重新标记阶段Flag判定逻辑
```c++
void cms_remark(){
  stop_the_world();
  // 必扫GC Roots
  scan_gc_roots();
  // 按Flag精准扫描
  if(cms_need_rescan) rescan_grey_objects();
  if(has_dirty_cards) scan_dirty_cards();
  // 重置Flag
  cms_need_rescan = false;
  has_dirty_cards = false;
  resume_threads();
}
```

##### 3. 卡表与跨代引用处理
- 采用卡表记录老年代→新生代的跨代引用
- 写后屏障标记脏卡页，避免Minor GC扫描全老年代
- 预清理阶段处理脏卡，减少Remark阶段扫描压力

#### ✅ 核心优点
- 绝大多数阶段与用户线程并发，STW时间极短
- 低延迟特性优异，适合交互型互联网应用
- 基于增量更新解决并发漏标，标记正确性高
- 多级Flag控制扫描范围，最小化停顿时间

#### ❌ 核心缺点
- CPU资源敏感，并发阶段占用CPU资源，吞吐量下降
- 标记-清除算法产生内存碎片，大对象分配困难
- 存在浮动垃圾，并发期间产生的新垃圾需下次GC回收
- 并发模式失败：回收速度跟不上分配速度，触发Full GC

#### 🎯 适用场景
- 互联网交互型应用，对停顿时间敏感
- 多核CPU服务器，老年代内存较大
- 搭配ParNew收集器，实现低延迟分代回收

## 🧩 G1垃圾收集器(G1GC)深度详解
#### 🎯 基础定位
- 面向服务端的全堆垃圾收集器，替代CMS与Parallel系列
- 核心目标：**可控的停顿时间 + 高吞吐量**，兼顾低延迟与高吞吐
- 基于分区(Region)的分代回收思想，不再严格划分新生代与老年代
- 基于三色标记+SATB写前屏障解决并发漏标问题
- 是HotSpot中最复杂的垃圾收集器

#### ⚙️ 核心设计思想
- 分区(Region)设计：将堆内存划分为多个大小相等的Region
- 每个Region可动态扮演新生代或老年代角色
- 采用**标记-整理算法**（整体），局部采用复制算法
- 核心特性：**可预测的停顿时间模型**，通过参数控制最大停顿时间

#### ⚙️ 完整工作流程（4个阶段）
##### 1. 初始标记阶段
- 执行方式：STW单线程执行
- 核心任务：标记GC Roots直接关联的对象
- 特点：速度极快，停顿时间微秒级
- 关联SATB：启动SATB写前屏障，开始记录引用变更

##### 2. 并发标记阶段
- 执行方式：与用户线程并发运行
- 核心任务：遍历全堆对象，标记所有存活对象
- 执行逻辑：
  - 基于三色标记算法，递归标记存活对象
  - 触发SATB写前屏障，记录所有被删除的旧引用
  - 全程无停顿，不影响业务线程
- 关联机制：SATB写前屏障，解决并发漏标问题

##### 3. 最终标记阶段
- 执行方式：STW多线程执行
- 核心任务：处理SATB队列剩余对象，完成最终标记
- 执行逻辑：
  - 处理SATB队列中所有未处理的旧引用
  - 标记关联的白色对象，补全标记
  - 计算每个Region的存活对象数量与回收价值
- 特点：STW时间极短，仅处理队列剩余对象

##### 4. 筛选回收阶段
- 执行方式：STW多线程执行
- 核心任务：选择回收价值最高的Region，执行回收
- 执行逻辑：
  - 根据停顿时间目标，选择一组Region进行回收
  - 将存活对象复制到空Region，清空原Region
  - 整理内存，无碎片产生
- 特点：STW时间可控，可通过参数调整

#### 🧩 底层核心实现
##### 1. SATB写前屏障实现
```c++
// SATB写前屏障
void g1_satb_write_barrier(oop* field, oop new_ref) {
  // 赋值前捕获旧引用
  oop old_ref = *field;
  if(old_ref != nullptr){
    // 旧引用入SATB队列，作为临时GC Roots
    satb_queue.push(old_ref);
  }
  // 执行赋值操作
  *field = new_ref;
}
```

##### 2. 记忆集(RSet)与跨Region引用处理
- 每个Region维护独立的记忆集(RSet)，记录其他Region对当前Region的引用
- 写后屏障更新记忆集，避免回收时扫描全堆
- 基于卡表实现，精准记录跨Region引用，缩小扫描范围

##### 3. 三色标记与SATB结合
- 核心不变性：黑色对象不能直接指向白色对象
- SATB通过写前屏障记录被删除的灰→白引用，破坏漏标条件二
- 最终标记阶段处理SATB队列，补全标记，保证无漏标

#### ✅ 核心优点
- 可控的停顿时间模型，可预测STW时长
- 标记-整理算法无内存碎片，大对象分配效率高
- 兼顾低延迟与高吞吐量，适合大堆内存服务
- 基于SATB解决并发漏标，标记正确性高
- 分区设计，支持部分Region回收，回收效率高

#### ❌ 核心缺点
- 实现复杂，调优难度高
- 写屏障开销高于CMS，存在浮动垃圾
- 内存占用高，需要维护记忆集与SATB队列
- 小堆内存下性能不如CMS，大堆下优势明显

#### 🎯 适用场景
- 大堆内存服务端应用，堆大小≥8GB
- 对停顿时间有明确要求的互联网应用
- 替代CMS，解决CMS内存碎片与并发模式失败问题
- 多核CPU服务器，需要兼顾低延迟与高吞吐量
