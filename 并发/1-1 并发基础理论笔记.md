## 🎯 总纲：三层联动的并发认知逻辑
所有Java并发知识点，均需从「硬件底层（CSAPP）→ JVM实现层 → Java应用层」三层拆解，三者的映射关系如下：

| 层级         | 核心研究对象                      | 解决的核心问题                               |
| ------------ | --------------------------------- | -------------------------------------------- |
| CSAPP硬件层🌏 | CPU缓存、指令集、内存屏障         | 并发的物理本质（上下文切换、原子性硬件支撑） |
| JVM实现层⛰️   | 内存模型（JMM）、线程模型、字节码 | 屏蔽硬件差异，提供统一的并发语义             |
| Java应用层   | 关键字、JUC组件、线程安全类       | 面向业务的并发编程实现                       |

## 🧩 模块1：并发的本质（从硬件到应用）【对应JCiP 1.1-1.4；并发艺术 2.1】
### 1.1 并发与并行（三层拆解）
#### 🔹 机制层（CSAPP 硬件原理）🌏
- 多核CPU的并行本质：每个核心拥有独立的L1/L2缓存、寄存器和执行单元，可同时执行不同指令流；单核CPU仅能通过时间片轮转实现"伪并发"。
- 上下文切换的硬件本质：CPU通过`CR3`寄存器切换页表基地址，实现不同线程/进程的地址空间隔离；切换时需保存寄存器、程序计数器、栈指针，加载新线程状态。
- 时间片轮转：操作系统内核通过定时器中断，强制剥夺当前线程CPU使用权，切换到就绪线程。

#### 🔹 实现层（JVM 线程模型）⛰️
Java采用**1:1内核线程模型**：每个Java线程直接映射到操作系统内核线程，由内核负责调度和上下文切换。
- **线程创建流程**：`new Thread()` → JVM调用`pthread_create`创建内核线程 → 内核分配栈空间 → 线程启动。
- 线程开销的JVM体现：
  1. 上下文切换：JVM需配合内核完成线程状态保存/恢复
  2. 内存开销：每个线程默认分配1MB栈空间
  3. 缓存失效：线程切换导致CPU缓存行失效，需从主存重新加载数据

#### 🔹 基础层（JCiP 设计定义）
- **并发**：多个任务在**同一时间段内交替执行**，单核CPU即可实现（CPU时间片轮转的"伪并行"）。
- **并行**：多个任务在**同一时刻同时执行**，必须依赖多核CPU（核心独立执行，无上下文切换）。
- 并发的核心价值与风险：

| 核心价值                               | 核心风险                     |
| -------------------------------------- | ---------------------------- |
| 提高CPU利用率（避免IO等待闲置）        | 竞态条件（结果依赖线程时序） |
| 降低系统响应时间（异步执行耗时操作）   | 死锁（线程互相等待释放锁）   |
| 提升系统吞吐量（单位时间处理更多任务） | 活跃性问题、数据不一致       |

### 1.2 JMM内存模型（并发的核心抽象，打通三层）【对应JCiP 3.1；并发艺术 3.1-3.4】
#### 🔹 机制层（CSAPP 硬件背景）🌏
不同CPU架构的内存模型差异是JMM诞生的根源：
- x86：强TSO模型，仅允许"写读"重排序，天然支持`LoadLoad`/`StoreStore`/`LoadStore`屏障；
- ARM/ARM64：弱内存模型，允许所有类型重排序，需显式插入内存屏障；
- JMM的硬件适配逻辑：以最弱硬件模型为基准，通过内存屏障屏蔽硬件差异。

#### 🔹 实现层（JVM 内存语义）⛰️
JMM定义线程与主存的抽象关系，核心目标是"在保证正确性的前提下最大化性能"：
- 存储模型：所有共享变量存于主存，线程有私有工作内存（映射CPU缓存），变量操作仅能在工作内存执行，线程间通信需通过主存。
- 核心实现手段：
  1. 内存屏障：禁止编译器/CPU的有害重排序；
  2. happens-before规则：定义操作间的可见性保证。

#### 🔹 基础层（JCiP+《艺术》联合定义）
JMM解决并发的三大核心问题：原子性、可见性、有序性，是所有Java并发关键字/组件的设计依据。

### 1.2.1 as-if-serial语义（重排序的底层约束）【对应JCiP 3.1；并发艺术 3.3】
#### 🔹 机制层（CSAPP 硬件逻辑）🌏
CPU流水线重排序的前提：仅对**无数据依赖**的指令重排序，保证单线程执行结果不变。

#### 🔹 实现层（JVM 编译逻辑）⛰️
JVM的编译器/即时编译器（JIT）重排序需遵守as-if-serial：仅重排无数据依赖的指令，保证单线程语义不变。

#### 🔹 基础层（严格定义）
> 不管编译器/CPU如何重排序，**单线程程序的执行结果必须与代码顺序执行的结果一致**。

#### 🔹 数据依赖的三层约束
| 依赖类型                                                     | 示例        | 硬件层能否重排序🌏 | JVM层能否重排序⛰️ | 应用层影响 |
| ------------------------------------------------------------ | ----------- | ----------------- | ---------------- | ---------- |
| 写后读                                                       | `a=1; b=a;` | ❌ 不能            | ❌ 不能           | 无         |
| 写后写                                                       | `a=1; a=2;` | ❌ 不能            | ❌ 不能           | 无         |
| 读后写                                                       | `a=b; b=1;` | ❌ 不能            | ❌ 不能           | 无         |
| ⚠️ 关键：数据依赖仅针对**单线程内的单个处理器**，多线程间的依赖不被硬件/JVM考虑。 |             |                   |                  |            |

---
### 1.2.2 重排序的三层分类（从编译到执行）【对应JCiP 3.1；并发艺术 3.2】
```
源代码 → 编译器优化重排序（javac） → JIT即时编译重排序 → CPU硬件重排序 → 最终执行指令
```

| 重排序层级      | 发生时机            | 硬件/VM实现逻辑                 | 应用层约束             |
| ---------- | --------------- | ------------------------- | ----------------- |
| 编译器优化重排序   | javac编译阶段       | 调整指令顺序、消除冗余计算             | 禁止对volatile变量读写重排 |
| JIT即时编译重排序 | JVM运行时（字节码→机器码） | 方法内联、循环展开、激进指令重排          | 通过内存屏障禁止有害重排      |
| CPU硬件重排序   | CPU执行机器码阶段      | 流水线乱序执行、指令预取（x86/ARM差异）🌏 | JVM插入硬件级内存屏障适配    |

### 1.2.3 happens-before规则（JMM的核心灵魂）【对应JCiP 3.1；并发艺术 3.4】
#### 🔹 机制层（CSAPP 硬件支撑）🌏
happens-before的底层实现依赖：
- 锁规则：解锁时刷新缓存到主存，加锁时失效本地缓存；
- volatile规则：写后插入`mfence`（x86）/`dmb ish`（ARM）屏障，强制刷回主存。

#### 🔹 实现层（JVM 内存语义）⛰️
JVM通过内存屏障和缓存刷新机制，保证happens-before的可见性承诺。

#### 🔹 基础层（《艺术》严格定义）
> 如果A happens-before B，JMM保证A操作的结果对B操作可见，且A的执行顺序"逻辑上"排在B之前（非物理执行顺序）。

#### 🔹 8条核心规则（三层联动版）
| 规则名称         | 规则内容                                       | 硬件层支撑🌏                 | JVM层实现⛰️                  | 应用层保证                      |
| ---------------- | ---------------------------------------------- | --------------------------- | --------------------------- | ------------------------------- |
| 程序顺序规则     | 单线程内，前序操作happens-before后续操作       | CPU数据依赖约束             | JVM遵守as-if-serial         | 单线程结果与代码顺序一致        |
| 锁规则           | 解锁操作happens-before后续对同一锁的加锁操作   | 解锁刷缓存+加锁失效缓存     | synchronized的内存屏障      | 解锁前的修改对加锁线程可见      |
| volatile变量规则 | volatile写happens-before后续volatile读         | StoreLoad屏障（x86:mfence） | 插入LoadLoad/StoreStore屏障 | volatile写的结果对后续读可见    |
| 线程启动规则     | Thread.start() happens-before线程B的任意操作   | 主线程缓存刷主存            | JVM刷新主线程工作内存到主存 | 启动前的修改对新线程可见        |
| 线程终止规则     | 线程A的操作happens-before其他线程检测到A终止   | 线程终止刷缓存              | JVM刷新线程A工作内存到主存  | 线程A的修改对检测终止的线程可见 |
| 线程中断规则     | interrupt() happens-before被中断线程检测到中断 | 中断标志位volatile语义      | JVM保证中断标志位的可见性   | 调用前的修改对被中断线程可见    |
| 终结器规则       | 构造方法完成happens-before finalize()开始      | 构造完成刷缓存              | JVM插入StoreStore屏障       | 构造方法的修改对finalize()可见  |
| 传递性规则       | A→B且B→C → A→C                                 | 硬件缓存一致性协议（MESI）  | JMM逻辑推导                 | 可见性可通过传递性传递          |

#### 🔹 经典示例：传递性规则的三层验证
```java
int a = 0;
volatile boolean flag = false;
// 线程A
public void writer() {
    a = 1; // 操作1
    flag = true; // 操作2（volatile写）
}
// 线程B
public void reader() {
    if (flag) { // 操作3（volatile读）
        System.out.println(a); // 操作4
    }
}
```
- 硬件层🌏：操作2的volatile写触发`StoreLoad`屏障，将a=1刷回主存；操作3的volatile读从主存加载flag和a；
- JVM层⛰️：1→2（程序顺序）、2→3（volatile规则）、3→4（程序顺序），通过传递性1→4；
- 应用层：线程B看到flag=true时，必然看到a=1。

## 🧩 模块2：线程安全（从定义到实践）【对应JCiP 2.1-2.4；并发艺术 2.2】
### 2.1 线程安全的严格定义（三层拆解）
#### 🔹 机制层（CSAPP 硬件原理）🌏
无状态对象的线程安全本质：状态存储于线程私有栈帧（栈指针`RSP`隔离），无共享状态，天然隔离。

#### 🔹 实现层（JVM 底层）⛰️
线程安全的本质：**保证共享可变状态的原子性、可见性、有序性**。
- 无状态对象：天生安全（无共享状态）；
- 不可变对象：天生安全（状态不可修改）；
- 有状态对象：需同步机制保护共享状态。

#### 🔹 基础层（JCiP 设计定义）
> 当多个线程同时访问一个对象时，无论调度方式/线程交替方式如何，且调用端无额外同步，对象仍能表现出正确行为，则该对象线程安全。

### 2.2 线程安全的5级分级（三层联动）
| 安全级别     | 定义                                     | 典型示例                             | 硬件/JVM支撑                           | 应用层注意事项                            |
| ------------ | ---------------------------------------- | ------------------------------------ | -------------------------------------- | ----------------------------------------- |
| 不可变       | 对象创建后状态永久不可修改               | String、Integer、BigInteger          | 无共享可变状态，栈/缓存天然隔离🌏       | final域通过StoreStore屏障保证可见性⛰️      |
| 绝对线程安全 | 任何调用方式下都能表现出正确行为         | 几乎不存在                           | 需全量锁保护，上下文切换开销大🌏        | 无实用价值，性能成本过高                  |
| 相对线程安全 | 单个操作线程安全，复合操作需额外同步     | Vector、Hashtable、ConcurrentHashMap | 单个方法由synchronized/锁保护⛰️         | 复合操作（如if(!contains()) put()）需加锁 |
| 线程兼容     | 本身不安全，调用端加同步可安全使用       | ArrayList、HashMap                   | 需调用端通过lock指令/缓存刷新保证安全🌏 | 所有操作需外部加锁                        |
| 线程对立     | 无论如何加同步，都无法在多线程下安全使用 | System.setOut()、Thread.stop()       | 破坏JVM内部状态，硬件级无法隔离🌏       | 绝对禁止多线程使用                        |

#### 🔹 关键示例（JVM层拆解Vector的线程安全）⛰️
```java
// Vector的伪代码实现（JVM层视角）
public class Vector<E> {
    // 单个方法用synchronized修饰：通过monitorenter/monitorexit保证原子性
    public synchronized boolean contains(Object o) { /* ... */ }
    public synchronized boolean add(E e) { /* ... */ }
    // ❌ 复合操作：无锁保护，存在竞态条件
    public boolean putIfAbsent(E x) {
        if (!contains(x)) { // 线程A执行完此处，线程B可能抢先add
            add(x);
            return true;
        }
        return false;
    }
}
```
- 硬件层🌏：复合操作的中间状态会被其他线程看到（缓存未同步）；
- JVM层⛰️：单个方法的synchronized保证原子性，但跨方法无锁；
- 应用层：需调用端加锁（如`synchronized(vector) { vector.putIfAbsent(e); }`）。

### 2.3 竞态条件（三层拆解）【对应JCiP 2.2；并发艺术 2.3】
#### 🔹 机制层（CSAPP 硬件原理）🌏
竞态条件的硬件本质：多个核心同时操作同一内存地址，缓存一致性协议无法处理"读-改-写"复合操作。

#### 🔹 实现层（JVM 底层）⛰️
竞态条件的本质：**复合操作的原子性被打破**，中间状态被其他线程看到。

#### 🔹 基础层（JCiP 设计定义 + 代码示例）
竞态条件：程序执行结果依赖线程执行时序，核心类型如下：
1. 先检查后执行（Check-Then-Act）
```java
// 懒加载单例的竞态（硬件：多核心同时执行检查；JVM：无锁保护；应用层：创建多个实例）
public class LazySingleton {
    private static LazySingleton instance;
    public static LazySingleton getInstance() {
        if (instance == null) { // 多线程同时进入此处
            instance = new LazySingleton();
        }
        return instance;
    }
}
```
2. 读-改-写（Read-Modify-Write）
```java
// 自增操作的竞态（硬件：核心间缓存不同步；JVM：无原子性保证；应用层：数据丢失）
public class Counter {
    private int count;
    public void increment() { count++; }
}
```

#### 🔹 解决方案（三层联动）
- 硬件层🌏：通过`lock`指令保证复合操作原子性；
- JVM层⛰️：通过synchronized/CAS保证原子性；
- 应用层：加锁将复合操作打包为原子操作（如懒加载单例加synchronized）。

## 🧩 模块3：对象的共享（关键字与发布策略）【对应JCiP 3.1-3.5；并发艺术 2.1、3.5-3.6】
### 3.1 volatile关键字（三层全量拆解）【对应JCiP 3.2；并发艺术 2.1、3.5】
#### 🔹 机制层（CSAPP 硬件指令集）🌏
| 内存屏障类型 | 作用               | x86实现                           | ARM64实现   |
| ------------ | ------------------ | --------------------------------- | ----------- |
| LoadLoad     | 禁止前读与后读重排 | 天然支持（无需指令）              | `dmb ishld` |
| StoreStore   | 禁止前写与后写重排 | 天然支持（无需指令）              | `dmb ishst` |
| LoadStore    | 禁止前读与后写重排 | 天然支持（无需指令）              | `dmb ish`   |
| StoreLoad    | 禁止前写与后读重排 | `mfence`/`lock; addl $0x0,(%rsp)` | `dmb ish`   |

#### 🔹 实现层（JVM 内存语义 + 字节码）⛰️
volatile的屏障插入规则：
- volatile写：写前插`StoreStore`，写后插`StoreLoad`；
- volatile读：读后插`LoadLoad`+`LoadStore`。

#### 🔹 基础层（JCiP 设计定义 + 经典应用）
volatile核心语义：保证可见性、禁止指令重排序，**不保证原子性**。

#### 🔹 易错点：volatile不能保证原子性的底层原因
```java
public class VolatileAtomicTest {
    private static volatile int count = 0;
    public static void increment() { count++; } // 非原子
    
    public static void main(String[] args) throws InterruptedException {
        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) increment();
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();
        System.out.println(count); // 结果<10000
    }
}
```
- 硬件层🌏：`count++`拆分为"读→改→写"，lock指令未覆盖全流程；
- JVM层⛰️：volatile仅保证单次读写的可见性/有序性，不保证复合操作原子性；
- 应用层：需用AtomicInteger（CAS）或synchronized保证原子性。

#### 🔹 volatile与synchronized的性能对比（三层视角）
| 特性     | volatile                                  | synchronized                          |
| -------- | ----------------------------------------- | ------------------------------------- |
| 原子性   | ❌ 不保证                                  | ✅ 保证（lock指令覆盖代码块）🌏         |
| 可见性   | ✅ 保证（缓存刷主存）🌏                     | ✅ 保证（解锁刷缓存+加锁失效缓存）🌏    |
| 有序性   | ✅ 保证（内存屏障）🌏                       | ✅ 保证（代码块内禁止重排）⛰️           |
| 性能开销 | 极低（仅写有StoreLoad屏障开销）           | 较高（锁竞争+上下文切换）🌏            |
| 硬件适配 | x86读无开销，写有mfence开销；ARM全有开销🌏 | 依赖操作系统锁实现，上下文切换成本高🌏 |
| 适用场景 | 状态标志、DCL单例、独立变量读写           | 复合操作、临界区保护                  |

### 3.2 final关键字（三层拆解）【对应JCiP 3.5；并发艺术 3.6】
#### 🔹 机制层（CSAPP 硬件原理）🌏
x86架构天然支持`StoreStore`/`LoadLoad`屏障，final域读写无额外性能开销；ARM需显式插入屏障。

#### 🔹 实现层（JVM 内存语义）⛰️
final的线程安全语义通过内存屏障实现：
- 写final域：构造方法末尾插`StoreStore`屏障，禁止final写与对象引用赋值重排；
- 读final域：读对象引用后插`LoadLoad`屏障，禁止读引用与读final域重排。

#### 🔹 基础层（JCiP 设计定义 + 易错点）
final修饰引用类型时，仅保证引用不可变，不保证引用对象内容不可变：
```java
public final class FinalExample {
    private final List<String> list = new ArrayList<>();
    public void add(String s) { list.add(s); } // ✅ 允许修改内容
    public void setList(List<String> newList) { this.list = newList; } // ❌ 编译错误
}
```
⚠️ 破坏final语义的唯一情况：构造方法中发布this引用（其他线程看到未初始化的final域）。

### 3.3 安全发布（三层拆解）【对应JCiP 3.3；并发艺术 3.1】
#### 🔹 机制层（CSAPP 硬件原理）🌏
不安全发布的硬件本质：对象初始化的"写"与引用赋值的"写"重排，其他核心读取到未初始化的对象（缓存未同步）。

#### 🔹 实现层（JVM 底层）⛰️
不安全发布的根源：对象引用赋值与初始化操作重排序（1.分配内存→2.默认值→4.赋值引用→3.构造方法初始化）。

#### 🔹 基础层（JCiP 设计定义 + 正确模式）
安全发布：对象的引用和内部状态同时对其他线程可见，核心模式如下：
1. 静态初始化器发布（JVM保证线程安全，类加载阶段完成初始化）；
2. volatile修饰引用变量（禁止重排）；
3. final域引用（构造方法完成后可见）；
4. 锁保护的域（加锁保证原子性/可见性）。

栈封闭的本质：线程私有栈帧（栈指针`RSP`隔离），栈内存不被其他核心访问。

#### 🔹 实现层（JVM 底层）⛰️

#### 🔹 基础层（JCiP 设计定义 + 示例）

  1. 栈封闭（局部变量，天然安全）：
     ```java
     public void safeMethod() {
     ```

## 🧩 模块4：对象的组合（JCiP 第4章 全量内容）【对应JCiP 4.1-4.5；并发艺术 2.3-2.4】
### 4.1 设计线程安全类的三要素（三层联动）【对应JCiP 4.1；并发艺术 2.4】
#### 🔹 机制层（CSAPP 硬件约束）🌏
不变性条件的硬件支撑：锁（lock指令）保证复合操作的原子性，避免多核心同时修改破坏约束。

#### 🔹 实现层（JVM 同步策略）⛰️
同步策略的核心：将所有共享状态的访问收敛到同一把锁的保护下，通过monitorenter/monitorexit保证原子性。

#### 🔹 基础层（JCiP 设计定义 + 示例）
设计线程安全类需包含三要素：
1. 找出所有状态变量；
2. 找出约束状态的不变性条件；
3. 建立并发访问的同步策略。
```java
@ThreadSafe
public class NumberRange {
    // 1. 状态变量：lower和upper（共享可变）
    @GuardedBy("this")
    private int lower;
    @GuardedBy("this")
    private int upper;
    // 2. 不变性条件：lower <= upper（业务约束）
    public NumberRange(int lower, int upper) {
        if (lower > upper) throw new IllegalArgumentException();
        this.lower = lower;
        this.upper = upper;
    }
    // 3. 同步策略：this锁保护所有操作（硬件：lock指令覆盖；JVM：synchronized保证原子性）
    public synchronized void setRange(int lower, int upper) {
        if (lower > upper) throw new IllegalArgumentException();
        this.lower = lower;
        this.upper = upper;
    }
    public synchronized int getLower() { return lower; }
    public synchronized int getUpper() { return upper; }
}
```
⚠️ 关键纠正：拆分setLower/setUpper仍保证线程安全（同一把锁），但会破坏"lower<=upper"的业务不变性条件（分步修改）。

### 4.2 实例封闭（核心设计模式）【对应JCiP 4.2；并发艺术 2.3】
#### 🔹 机制层（CSAPP 硬件原理）🌏
实例封闭的硬件本质：通过锁（lock指令）将共享状态的访问限制在单个核心的执行流中（同一时刻仅一个核心操作）。

#### 🔹 实现层（JVM 底层）⛰️
实例封闭的本质：将非线程安全对象的访问收敛到同一把锁的保护下，外部无法直接访问内部对象。

#### 🔹 基础层（JCiP 设计定义 + 正反示例）
✅ 正确：组合模式（实例封闭）
```java
@ThreadSafe
public class SafeList<E> {
    private final List<E> list; // 封闭非线程安全对象
    public SafeList(List<E> list) { this.list = list; }
    // 同步策略：this锁保护所有操作（硬件：lock指令；JVM：synchronized）
    public synchronized boolean putIfAbsent(E x) {
        boolean absent = !list.contains(x);
        if (absent) list.add(x);
        return absent;
    }
}
```
❌ 错误：继承扩展Vector（依赖父类锁策略，脆弱）
```java
public class BetterVector<E> extends Vector<E> {
    public synchronized boolean putIfAbsent(E x) {
        boolean absent = !contains(x);
        if (absent) add(x);
        return absent;
    }
}
```
- 硬件层🌏：父类锁策略变化会导致lock指令覆盖范围失效；
- JVM层⛰️：子类依赖父类的monitorenter/monitorexit指令，耦合性高；
- 应用层：父类锁策略修改（如改用内部锁）会导致子类同步失效。

### 4.3 线程安全的委托【对应JCiP 4.3；并发艺术 2.3】
#### 🔹 机制层（CSAPP 硬件原理）🌏
JUC组件（如[[2阶段-Java并发容器和框架：ConcurrentHashMap|ConcurrentHashMap]]）的硬件支撑：CAS指令（compare-and-swap）替代锁，减少上下文切换。

#### 🔹 实现层（JVM 底层）⛰️
委托的本质：将线程安全的实现委托给JUC组件（基于CAS/锁），JVM层保证组件的原子性/可见性/有序性。

#### 🔹 基础层（JCiP 定义 + 失效场景）
线程安全委托：将线程安全实现委托给一个/多个线程安全组件，示例如下：
```java
@ThreadSafe
public class DelegatingVehicleTracker {
    private final ConcurrentHashMap<String, Point> locations;
    private final Map<String, Point> unmodifiableMap;
    public DelegatingVehicleTracker(Map<String, Point> points) {
        this.locations = new ConcurrentHashMap<>(points);
        this.unmodifiableMap = Collections.unmodifiableMap(locations);
    }
    public Point getLocation(String id) { return locations.get(id); } // 委托给ConcurrentHashMap
    public void setLocation(String id, int x, int y) {
        if (locations.replace(id, new Point(x, y)) == null) {
            throw new IllegalArgumentException("无效的车辆ID");
        }
    }
}
```

#### 🔹 委托失效场景（三层拆解）
当多个线程安全组件间存在约束关系时，委托失效：
```java
@NotThreadSafe
public class NumberRange {
    private final AtomicInteger lower = new AtomicInteger(0);
    private final AtomicInteger upper = new AtomicInteger(10);
    public void setLower(int i) {
        if (i > upper.get()) throw new IllegalArgumentException();
        lower.set(i); // 硬件：CAS仅保证单次写原子性；JVM：无锁保护约束；应用层：竞态
    }
}
```
- 硬件层🌏：两个AtomicInteger的CAS操作未被lock指令覆盖，多核心可同时修改；
- JVM层⛰️：无锁保护"lower<=upper"的约束，组件间无同步；
- 应用层：需用synchronized将检查+修改打包为原子操作。

### 4.4 在现有的线程安全类中添加功能【对应JCiP 4.4；并发艺术 2.3】
#### 🔹 基础层（JCiP 设计定义）
为现有线程安全类添加原子操作，有**两种实现方式**，优劣差异极大：
1. **客户端加锁**：使用外部锁保护复合操作，锁必须与类本身使用的锁一致
2. **组合模式**：将现有类作为私有成员封装，新增自定义同步策略

#### 🔹 实现层（JVM 底层）⛰️
- 客户端加锁：依赖原有类的锁对象（如`Vector`的`this`锁），耦合度极高
- 组合模式：使用自定义私有锁，与原有类锁策略完全解耦，JVM层锁隔离无冲突

#### 🔹 机制层（CSAPP 硬件原理）🌏
组合模式的硬件优势：锁对象独立，减少锁竞争范围，降低CPU缓存行失效概率

#### 🔹 联系层（并发+JVM+CSAPP 打通）
- 并发设计（JCiP）：优先组合，避免客户端加锁的脆弱性
- JVM底层⛰️：私有锁对象独立，`monitorenter/monitorexit`指令互不干扰
- CSAPP硬件🌏：独立锁对应独立缓存行，减少`lock`指令的总线锁定范围

同步策略是线程安全类的**核心契约**，必须明确标注：

## 🧩 模块5：JMM深度强化（《艺术》第三章核心）【对应并发艺术 3.1-3.7】
### 5.1 锁的内存语义（三层拆解）【对应并发艺术 3.7；JCiP 2.3】
#### 🔹 基础层（JCiP+《艺术》联合定义）
锁的两个核心内存语义：
1. 加锁时：线程会失效自己的本地缓存，从主存加载最新的共享变量
2. 解锁时：线程会把自己的本地缓存刷新到主存

#### 🔹 实现层（JVM 底层）⛰️
锁规则：**一个锁的解锁操作，happens-before于后续对同一个锁的加锁操作**
- 加锁：执行`lock cmpxchg`指令，锁定缓存行，同时失效本地缓存
- 解锁：执行`lock addl $0x0,(%rsp)`空操作指令，触发内存屏障，强制刷新缓存到主存

#### 🔹 机制层（CSAPP 硬件原理）🌏
锁的内存语义底层完全依赖CPU的两个核心能力：
1. 原子指令执行：`lock`前缀指令锁定总线/缓存行，保证指令不可分割
2. 缓存一致性同步：`lock`前缀指令触发MESI协议的缓存同步，保证修改对其他核心立即可见

### 5.2 final域的内存语义补充【对应并发艺术 3.6；JCiP 3.5】
#### 🔹 基础层（JSR-133规范定义）
Java 5为final域新增了完整的内存语义，保证：**只要对象是正确构造的（构造方法中没有逸出this引用），那么不需要任何同步，所有线程都能看到final域在构造方法中初始化的正确值**。

#### 🔹 实现层（JVM 屏障插入规则）⛰️
1. **写final域**：在构造方法return之前，插入一个`StoreStore`屏障，禁止final域的写操作与对象引用的赋值操作重排序
2. **读final域**：在读final域的操作之前，插入一个`LoadLoad`屏障，禁止读对象引用与读final域的操作重排序

#### 🔹 机制层（CSAPP 硬件原理）🌏
x86架构下，final域的读写无额外性能开销；ARM架构需显式插入内存屏障指令，保证重排序规则不被破坏。
