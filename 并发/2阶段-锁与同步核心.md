## 🧩 模块1：同步容器类与并发容器（对应JCiP 5.1、5.2；《Java并发编程的艺术》6.1-6.3）
### 1.1 同步容器类的问题（对应JCiP 5.1）
同步容器类：JDK早期提供的线程安全容器，包括`Vector`、`Hashtable`、`Collections.synchronizedXXX`包装的容器，核心实现是**所有方法用`synchronized`修饰，锁对象为容器本身**。
#### 🔹 核心问题1：复合操作的非原子性（基础层 JCiP 5.1.1）
##### 基础层（书本定义）
同步容器的单个方法是线程安全的，但**「先检查后执行」「读-改-写」等复合操作，在多线程下依然存在竞态条件**，必须通过客户端加锁保证原子性。
典型复合操作示例：
```java
// 经典"先检查后执行"竞态，即使Vector是线程安全的，依然会抛出ArrayIndexOutOfBoundsException
public static Object getLast(Vector list) {
    int lastIndex = list.size() - 1; // 线程A执行完此处，CPU切换到线程B执行removeLast
    return list.get(lastIndex); // 线程A切回后，下标已失效
}

public static void removeLast(Vector list) {
    int lastIndex = list.size() - 1;
    list.remove(lastIndex);
}
```
##### 实现层（JVM底层）
复合操作被拆分为多个独立的`synchronized`方法，每个方法的`monitorenter/monitorexit`指令是独立的，方法之间的间隙会被其他线程抢占，无法保证复合操作的原子性。
##### 机制层（CSAPP硬件原理🌏）
多个CPU核心可交替执行容器的不同同步方法，缓存行的刷新存在间隙，复合操作的中间状态会被其他核心读取，触发竞态条件。

#### 🔹 核心问题2：迭代器与ConcurrentModificationException（基础层 JCiP 5.1.2）
##### 基础层（书本定义）
同步容器的迭代器设计遵循**「快速失败」（fail-fast）** 机制：迭代过程中如果容器被修改（增/删/改），会立即抛出`ConcurrentModificationException`。
- 迭代器创建时会记录容器的`modCount`修改次数
- 每次迭代都会校验`modCount`是否与初始值一致，不一致则抛出异常
- 即使加锁，若迭代过程中修改容器，依然会触发异常
##### 实现层（JVM底层⛰️）
`modCount`是容器的`volatile`成员变量，每次修改操作都会对其进行自增，迭代器的校验逻辑依赖volatile的可见性保证。
##### 机制层（CSAPP硬件原理🌏）
多线程迭代时，修改操作的`volatile`写会触发MESI协议缓存失效，迭代线程读取到最新的`modCount`，触发快速失败校验。

#### 🔹 核心问题3：隐藏迭代器（基础层 JCiP 5.1.3）
##### 基础层（书本定义）
除了显式的`iterator()`迭代，Java中很多操作会隐式触发迭代器，称为**隐藏迭代器**，同样会触发`ConcurrentModificationException`。
触发隐藏迭代器的场景：
- 容器的`toString()`、`hashCode()`、`equals()`方法
- `containsAll()`、`removeAll()`、`retainAll()`等集合操作
- 字符串拼接时自动调用`toString()`
##### 实现层（JVM底层⛰️）
上述方法的底层实现均会创建迭代器遍历容器，执行与显式迭代完全一致的`modCount`校验逻辑。
##### 机制层（CSAPP硬件原理🌏）
隐藏迭代器的遍历操作同样会加载`modCount`缓存行，若其他线程修改了容器，缓存行失效会触发校验失败。

### 1.2 并发容器的设计与选型（对应JCiP 5.2；《Java并发编程的艺术》6.1-6.3）
并发容器是JDK 1.5+专为高并发场景设计的容器，核心优化思路是**缩小锁的粒度、替代独占锁、弱一致性迭代器**，彻底解决同步容器的性能与迭代异常问题。

#### 🔹 ConcurrentHashMap 设计思想（对应《Java并发编程的艺术》6.1）
##### 基础层（书本定义）
- **JDK 1.7**：采用**分段锁（Segment）** 设计，整个哈希表被拆分为16个默认分段，每个分段独立加锁，多线程可同时访问不同分段，并发度等于分段数。
- **JDK 1.8**：废弃分段锁，采用**数组+链表+红黑树**结构，用`CAS+synchronized`替代独占锁，锁粒度细化到哈希桶的头节点，**无哈希冲突时完全无锁，并发性能进一步提升**。
- 迭代器采用**弱一致性**设计，迭代过程中容器修改不会抛出`ConcurrentModificationException`，迭代器只能看到创建时已完成的修改。
##### 实现层（JVM底层⛰️）
- JDK1.7：`Segment`继承`ReentrantLock`，通过分段隔离实现并发安全，`HashEntry`的`value/next`用`volatile`修饰保证可见性，实现无锁读。
- JDK1.8：通过`Unsafe`的`CAS`操作实现无锁节点插入，`synchronized`仅锁定哈希桶头节点，红黑树转换保证哈希冲突严重时的查询性能。
##### 机制层（CSAPP硬件原理🌏）
- 分段锁/细粒度桶锁：减少`lock`指令的总线锁定范围，降低CPU缓存行失效概率，减少多核心竞争。
- volatile无锁读：依赖MESI缓存一致性协议保证可见性，避免加锁带来的上下文切换开销。

#### 🔹 CopyOnWriteArrayList 适用场景（对应JCiP 5.2.2）
##### 基础层（书本定义）
**写时复制（Copy-On-Write, COW）容器**，核心思想：**所有读操作完全无锁，写操作时复制一份新数组，修改完成后替换原数组引用**。
- 核心特性：线程安全、读操作无锁、写操作加独占锁、迭代器永远不会抛出`ConcurrentModificationException`
- 适用场景：**读多写少、遍历操作远多于修改操作**的场景，如白名单、黑名单、配置列表
- 不适用场景：写操作频繁、数据量巨大的场景（数组复制开销极大）
##### 实现层（JVM底层⛰️）
- 内部维护一个`volatile`修饰的数组引用，保证修改后的新数组对所有读线程立即可见。
- 写操作通过`ReentrantLock`加独占锁，避免多线程同时复制数组。
- 迭代器持有创建时的数组快照，遍历的是不可变的快照数组，无修改风险。
##### 机制层（CSAPP硬件原理🌏）
- 读操作无锁：完全避免`lock`指令与缓存行锁定，读操作的CPU开销与普通ArrayList几乎一致。
- 数组复制：写操作会触发新数组的内存分配与拷贝，大数组会导致频繁的内存申请与GC开销。

#### 🔹 ConcurrentLinkedQueue 无锁队列设计（对应《Java并发编程的艺术》6.2）
##### 基础层（书本定义）
基于**无锁CAS算法**实现的高性能并发无界队列，遵循FIFO原则，核心设计是**头尾指针的松弛滞后更新**，通过`hops`阈值控制头尾指针的更新频率，减少volatile写操作。
- 核心特性：全程无锁、高并发下性能远超阻塞队列、无界设计
- 适用场景：高并发下的非阻塞任务排队、无界数据传递
##### 实现层（JVM底层⛰️）
- 节点的`item`与`next`用`volatile`修饰，保证可见性。
- 入队/出队通过`Unsafe`的`CAS`操作实现节点的挂载与修改，无独占锁。
- 头尾指针不实时更新，仅当遍历步数达到`HOPS`阈值时才批量更新，减少CAS写操作。
##### 机制层（CSAPP硬件原理🌏）
- CAS操作依赖CPU的`cmpxchg`原子指令，避免内核态上下文切换。
- 松弛更新设计：用低成本的volatile读操作，替换高成本的volatile写CAS操作，符合「volatile写开销远大于读」的硬件特性。

## 🧩 模块2：synchronized底层原理与锁升级全流程（对应《Java并发编程的艺术》2.2）
### 2.1 Java对象头与Mark Word结构⛰️
#### 🔹 基础层（书本定义）
`synchronized`用的锁对象存在于Java对象头中，Java对象由**对象头、实例数据、对齐填充**三部分组成，对象头包含两部分：
1. **Mark Word**：存储对象的哈希码、分代年龄、锁状态标志、线程ID、偏向时间戳等，是锁实现的核心。
2. **Class Metadata Address**：存储对象指向类元数据的指针，JVM通过该指针确定对象属于哪个类。
32位JVM的Mark Word结构（核心）：
| 锁状态   | 25位                    | 4位分代年龄 | 1位是否偏向锁 | 2位锁标志位 |
| -------- | ----------------------- | ----------- | ------------- | ----------- |
| 无锁状态 | 对象哈希码              | 分代年龄    | 0             | 01          |
| 偏向锁   | 线程ID+Epoch            | 分代年龄    | 1             | 01          |
| 轻量级锁 | 指向栈中锁记录的指针    | 无          | 无            | 00          |
| 重量级锁 | 指向Monitor监视器的指针 | 无          | 无            | 10          |
| GC标记   | 空                      | 无          | 无            | 11          |

#### 🔹 实现层（JVM底层⛰️）
Mark Word是**动态的数据结构**，会根据锁状态复用存储空间，JVM通过Mark Word的锁标志位判断当前锁状态，执行对应的加锁/解锁逻辑。

#### 🔹 机制层（CSAPP硬件原理🌏）
Mark Word存储在对象的内存起始位置，CPU可通过对象指针直接加载到缓存行，锁状态的修改通过`lock cmpxchg`原子指令完成，保证多核心下的操作原子性。

### 2.2 Monitor监视器原理⛰️
#### 🔹 基础层（书本定义）
Monitor是**操作系统级别的同步原语**，是`synchronized`重量级锁的底层实现，每个Java对象都对应一个唯一的Monitor监视器。
Monitor核心结构：
- `_owner`：指向持有锁的线程
- `_EntryList`：入口队列，存放等待获取锁的阻塞线程
- `_WaitSet`：等待队列，存放调用`wait()`进入等待的线程
- `_recursions`：记录锁的重入次数

#### 🔹 实现层（JVM底层⛰️）
- 线程获取锁时，JVM会尝试将Monitor的`_owner`设置为当前线程，若设置成功则获取锁；若失败则进入`_EntryList`阻塞。
- 线程释放锁时，将`_owner`置空，唤醒`_EntryList`中的等待线程。
- `synchronized`的可重入性，通过`_recursions`计数器实现，同一个线程多次加锁时计数器自增，解锁时自减，计数器归0才真正释放锁。

#### 🔹 机制层（CSAPP硬件原理🌏）
重量级锁的阻塞与唤醒，需要操作系统从**用户态切换到内核态**，上下文切换开销极大，这也是早期`synchronized`性能差的核心原因。

### 2.3 锁升级全流程（对应《Java并发编程的艺术》2.2.3）
JDK 1.6对`synchronized`做了极致优化，引入了**锁升级机制**，锁会随着竞争程度从低到高依次升级，且锁只能升级不能降级。
锁升级路径：**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**

#### 🔹 1. 无锁状态
对象刚创建，未被任何线程加锁，Mark Word为无锁状态，标志位`01`，偏向锁标志`0`。

#### 🔹 2. 偏向锁（无竞争场景）
##### 基础层（书本定义）
核心设计思想：**无竞争时，消除整个同步操作，连CAS操作都不做**。
当第一个线程访问同步块时，通过CAS将线程ID写入Mark Word，进入偏向锁状态，标志位`01`，偏向锁标志`1`。
- 后续同一个线程再次进入同步块时，只需检查Mark Word中的线程ID是否为当前线程，无需任何CAS操作，性能几乎与无锁一致。
- 当有第二个线程竞争锁时，偏向锁立即撤销，升级为轻量级锁。
##### 实现层（JVM底层⛰️）
偏向锁的撤销需要等待全局安全点（STW），暂停持有偏向锁的线程，检查线程是否存活，若线程已退出则将对象恢复为无锁状态；若线程仍存活则升级为轻量级锁。
##### 机制层（CSAPP硬件原理🌏）
偏向锁完全消除了同步操作的原子指令开销，无竞争场景下，CPU无需执行`lock`前缀指令，无缓存行锁定与总线同步开销。

#### 🔹 3. 轻量级锁（低竞争场景）
##### 基础层（书本定义）
核心设计思想：**多线程交替执行同步块，无长时间竞争，用CAS自旋替代重量级锁的阻塞**。
线程进入同步块时，若对象为无锁/偏向锁撤销状态，会在当前线程的栈帧中创建**锁记录（Lock Record）**，存储Mark Word的拷贝，然后通过CAS将对象的Mark Word替换为指向锁记录的指针，成功则获取轻量级锁，标志位`00`。
- 若CAS失败，说明有其他线程竞争，当前线程通过自旋重试获取锁。
- 当自旋次数达到阈值（JDK1.6为适应性自旋，由前一次自旋结果决定）仍未获取锁，锁升级为重量级锁。
##### 实现层（JVM底层⛰️）
轻量级锁的解锁通过CAS将栈帧中的Mark Word拷贝还原到对象头，若成功则解锁成功；若失败说明存在竞争，锁已升级为重量级锁，进入重量级锁的解锁流程。
##### 机制层（CSAPP硬件原理🌏）
轻量级锁通过用户态自旋避免内核态上下文切换，短时间自旋的开销远小于线程阻塞唤醒的开销；但长时间自旋会浪费CPU资源，因此竞争加剧时必须升级为重量级锁。

#### 🔹 4. 重量级锁（高竞争场景）
锁升级为重量级锁后，Mark Word存储指向Monitor监视器的指针，标志位`10`，所有竞争失败的线程都会进入Monitor的`_EntryList`，进入内核态阻塞，不再自旋。

### 2.4 JVM锁优化技术（对应《Java并发编程的艺术》2.2.4）
1. **适应性自旋**：自旋时间不固定，由前一次在同一个锁上的自旋结果与锁持有者状态决定，减少无效自旋。
2. **锁消除**：JIT编译时，通过逃逸分析检测到不可能存在共享竞争的锁，直接消除该锁，比如方法内局部`StringBuffer`的同步锁。
3. **锁粗化**：JVM检测到连续多次对同一个对象加锁解锁，会将锁的范围粗化到整个操作序列的外部，减少频繁加锁解锁的开销。

## 🧩 模块3：Lock体系与AQS队列同步器核心（对应《Java并发编程的艺术》5.1-5.7）
### 3.1 Lock接口设计思想（对应《Java并发编程的艺术》5.1）
#### 🔹 基础层（书本定义）
Lock是JDK 1.5+提供的显式锁接口，与`synchronized`相比，提供了更灵活的锁特性，核心方法：
```java
public interface Lock {
    void lock(); // 阻塞获取锁，不可中断
    void lockInterruptibly() throws InterruptedException; // 可中断获取锁
    boolean tryLock(); // 非阻塞尝试获取锁，立即返回结果
    boolean tryLock(long time, TimeUnit unit) throws InterruptedException; // 超时尝试获取锁
    void unlock(); // 释放锁
    Condition newCondition(); // 获取等待队列
}
```
#### 🔹 核心设计优势（与synchronized对比）
| 特性         | synchronized           | Lock                                |
| ------------ | ---------------------- | ----------------------------------- |
| 锁释放       | 自动释放，异常也会释放 | 必须手动unlock()，通常写在finally中 |
| 可中断性     | 不可中断               | 支持lockInterruptibly()中断         |
| 非阻塞获取   | 不支持                 | 支持tryLock()非阻塞获取             |
| 超时获取     | 不支持                 | 支持超时获取                        |
| 公平锁       | 仅支持非公平锁         | 支持公平/非公平锁可选               |
| 多个等待队列 | 仅1个等待队列          | 支持多个Condition独立等待队列       |
| 锁类型       | 可重入、独占锁         | 支持独占锁、共享锁、读写锁          |

#### 🔹 实现层（JVM底层⛰️）
Lock接口的核心实现均基于**AQS队列同步器**，通过`Unsafe`的CAS操作实现锁的抢占，通过`LockSupport.park/unpark`实现线程的阻塞与唤醒，无需依赖操作系统的Monitor原语。

#### 🔹 机制层（CSAPP硬件原理🌏）
Lock的非阻塞获取通过CPU的`cmpxchg`原子指令实现，避免了`synchronized`重量级锁的用户态/内核态切换开销；可中断、超时特性避免了线程无限阻塞，减少无效的CPU上下文切换。

### 3.2 AQS队列同步器核心原理（对应《Java并发编程的艺术》5.2）
#### 🔹 基础层（书本定义）
AQS（AbstractQueuedSynchronizer）队列同步器，是**整个JUC锁体系的底层框架**，`ReentrantLock`、`ReentrantReadWriteLock`、`CountDownLatch`、`Semaphore`等所有同步工具均基于AQS实现。
AQS核心设计：

1. **核心状态变量`volatile int state`**：表示同步状态，`state=0`为空闲，`state>0`为已被持有。
2. **CLH变体双向同步队列🌏**：等待获取锁的线程会被封装为`Node`节点，加入双向队列尾部，等待被唤醒。
3. **两种模式**：独占模式（同一时刻仅一个线程持有锁，如ReentrantLock）、共享模式（同一时刻多个线程可持有锁，如Semaphore）。
4. **模板方法设计模式**：子类只需实现`tryAcquire/tryRelease`（独占）、`tryAcquireShared/tryReleaseShared`（共享）等核心方法，AQS负责实现线程排队、阻塞、唤醒等通用逻辑。

#### 🔹 核心数据结构
```java
// AQS核心内部类Node
static final class Node {
    static final Node SHARED = new Node(); // 共享模式
    static final Node EXCLUSIVE = null;    // 独占模式
    static final int CANCELLED =  1; // 线程已取消
    static final int SIGNAL    = -1; // 后继线程需要被唤醒
    static final int CONDITION = -2; // 节点在Condition等待队列
    static final int PROPAGATE = -3; // 共享模式下唤醒需要传播
    
    volatile int waitStatus; // 节点等待状态
    volatile Node prev;      // 前驱节点
    volatile Node next;      // 后继节点
    volatile Thread thread;  // 封装的线程
    Node nextWaiter;         // Condition等待队列的后继节点
}
```

#### 🔹 独占模式核心流程：加锁→排队→解锁（学习重点）
##### 1. 加锁流程（acquire(int arg)）
```java
public final void acquire(int arg) {
    // 1. 尝试获取锁，成功则直接返回
    if (!tryAcquire(arg) &&
        // 2. 获取失败，封装为Node节点加入同步队列尾部
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))
        selfInterrupt();
}
```
**完整执行步骤**：
1. 调用子类实现的`tryAcquire()`尝试CAS获取锁，成功则直接返回；
2. 获取失败，调用`addWaiter()`将当前线程封装为独占模式的Node节点，通过CAS加入同步队列尾部；
3. 调用`acquireQueued()`，节点在队列中自旋，检查前驱节点是否为头节点，若是则再次尝试获取锁；
4. 若前驱不是头节点/获取锁失败，调用`LockSupport.park()`阻塞当前线程，等待前驱节点释放锁时被唤醒；
5. 线程被中断时，会在获取锁后调用`selfInterrupt()`补上中断标记。

##### 2. 解锁流程（release(int arg)）
```java
public final boolean release(int arg) {
    // 1. 尝试释放锁
    if (tryRelease(arg)) {
        Node h = head;
        // 2. 头节点状态有效，唤醒后继节点
        if (h != null && h.waitStatus != 0)
            unparkSuccessor(h);
        return true;
    }
    return false;
}
```
**完整执行步骤**：
1. 调用子类实现的`tryRelease()`释放锁，将`state`置为0，成功则继续；
2. 获取同步队列的头节点，若头节点的`waitStatus=SIGNAL`，调用`LockSupport.unpark()`唤醒头节点的后继节点；
3. 被唤醒的线程会再次尝试获取锁，重复加锁流程。

#### 🔹 实现层（JVM底层⛰️）
- `state`变量用`volatile`修饰，保证多线程间的可见性，所有对`state`的修改均通过CAS操作完成。
- 节点的`waitStatus`、`prev`、`next`均为`volatile`修饰，保证队列操作的可见性，避免多线程下队列结构混乱。
- 线程的阻塞与唤醒通过`LockSupport.park/unpark`实现，底层调用JVM的`Unsafe`类的`park/unpark`本地方法。

#### 🔹 机制层（CSAPP硬件原理🌏）
- **CLH队列设计**：双向链表结构，节点自旋时仅检查前驱节点的状态，避免多线程同时轮询同一个变量导致的缓存行颠簸，符合CPU缓存局部性原理。
- **CAS操作**：队列的入队、节点状态修改均通过`cmpxchg`原子指令完成，无内核态切换开销。
- **park/unpark**：相比`synchronized`的Monitor阻塞，`park/unpark`可精准唤醒指定线程，避免了唤醒所有等待线程的**惊群效应**，减少无效的CPU上下文切换。

### 3.3 ReentrantLock核心特性（对应《Java并发编程的艺术》5.3）

`ReentrantLock`是Lock接口最常用的实现，**可重入的独占锁**，与`synchronized`语义一致，同时支持公平/非公平锁可选。

#### 🔹 1. 可重入性

##### 基础层（书本定义）

同一个线程可以多次获取同一把锁，不会出现自己阻塞自己的情况，与`synchronized`的可重入语义完全一致。

##### 实现层（JVM底层⛰️）

通过AQS的`state`变量实现：`state=0`表示锁空闲，线程获取锁时通过CAS将`state`从0改为1；同一个线程再次获取锁时，`state`自增；解锁时`state`自减，归0时真正释放锁。

#### 🔹 2. 公平锁与非公平锁

##### 基础层（书本定义）

- **非公平锁（默认）**：线程获取锁时，先直接CAS抢占锁，抢占失败再进入同步队列排队，不保证先等待的线程先获取锁。
- **公平锁**：线程获取锁时，先检查同步队列是否有等待线程，有则直接进入队列排队，严格遵循FIFO顺序，保证先等待的线程先获取锁。

##### 性能差异：非公平锁的吞吐量远高于公平锁

##### 机制层（CSAPP硬件原理🌏）

非公平锁可直接CAS抢占，避免了线程入队阻塞的上下文切换开销；公平锁严格排队，会导致频繁的线程阻塞与唤醒，CPU缓存行失效概率更高，性能更低。

#### 🔹 3. 可中断锁与超时锁

- `lockInterruptibly()`：线程阻塞等待锁时，可被`interrupt()`中断，抛出中断异常，避免无限等待。
- `tryLock(long timeout)`：在指定时间内尝试获取锁，超时未获取到则返回false，支持中断，适合防止死锁的场景。

### 3.4 读写锁ReentrantReadWriteLock设计（对应《Java并发编程的艺术》5.5）
#### 🔹 基础层（书本定义）
读写锁维护一对锁：**读锁（共享锁）**、**写锁（独占锁）**，核心规则：
1. 读-读不互斥：多个线程可同时持有读锁，读操作完全并发；
2. 读-写互斥：读锁持有期间，写锁无法获取；写锁持有期间，读锁无法获取；
3. 写-写互斥：同一时刻仅一个线程可持有写锁。
适用场景：**读多写少**的场景，相比独占锁，可大幅提升并发吞吐量。

#### 🔹 实现层（JVM底层⛰️）
基于AQS实现，将32位的`state`变量拆分为两部分：
- 高16位：记录读锁的持有次数，每个线程获取读锁时高16位自增；
- 低16位：记录写锁的持有次数，与ReentrantLock一致，支持可重入。

#### 🔹 机制层（CSAPP硬件原理🌏）
读-读不互斥的设计，消除了读操作的锁竞争，减少了CPU缓存行锁定与总线同步开销，读密集场景下性能远超独占锁。

### 3.5 LockSupport与Condition接口（对应《Java并发编程的艺术》5.6、5.7）
#### 🔹 LockSupport
##### 基础层（书本定义）
LockSupport是JUC提供的线程阻塞唤醒工具类，核心方法：
- `park()`：阻塞当前线程，直到被`unpark()`唤醒、被中断或超时；
- `unpark(Thread thread)`：唤醒指定的阻塞线程。
核心优势：
- 可先调用`unpark()`再调用`park()`，线程不会阻塞，解决了`wait/notify`必须先等待再唤醒的时序问题；
- 可精准唤醒指定线程，不会产生惊群效应。
##### 实现层（JVM底层⛰️）
底层调用`Unsafe`类的本地方法，每个线程关联一个许可，`unpark()`发放许可，`park()`消费许可，无许可则阻塞。

#### 🔹 Condition接口
##### 基础层（书本定义）
Condition是Lock配套的等待/通知工具，替代`synchronized`的`wait/notify`，核心优势是**一个Lock可创建多个独立的Condition等待队列**，实现精准唤醒。
核心方法：
- `await()`：释放锁，阻塞当前线程，进入Condition等待队列；
- `signal()`：唤醒等待队列中的第一个线程，线程被唤醒后会重新尝试获取锁；
- `signalAll()`：唤醒等待队列中的所有线程。
典型应用：ArrayBlockingQueue的`notEmpty`、`notFull`双等待队列，分别等待队列非空、队列非满。
##### 实现层（JVM底层⛰️）
每个Condition对象维护一个独立的单向等待队列，节点复用AQS的Node类，`await()`将线程加入等待队列，`signal()`将等待队列的节点转移到AQS同步队列，等待获取锁。

## 🧩 模块4：阻塞队列与生产者-消费者模式（对应JCiP 5.3；《Java并发编程的艺术》6.3）
### 4.1 阻塞队列核心接口与特性（对应JCiP 5.3）
#### 🔹 基础层（书本定义）
阻塞队列是支持**阻塞插入、阻塞移除**的队列，核心特性：
1. 队列满时，插入元素的线程会被阻塞，直到队列有空位；
2. 队列空时，获取元素的线程会被阻塞，直到队列有元素。
是**生产者-消费者模式**的天然载体，无需手动实现等待/通知逻辑，彻底避免竞态条件。
BlockingQueue核心方法（4类行为）：
| 操作类型 | 抛出异常  | 特殊值   | 阻塞等待 | 超时等待                |
| -------- | --------- | -------- | -------- | ----------------------- |
| 插入     | add(e)    | offer(e) | put(e)   | offer(e, timeout, unit) |
| 移除     | remove()  | poll()   | take()   | poll(timeout, unit)     |
| 检查     | element() | peek()   | 不支持   | 不支持                  |

#### 🔹 实现层（JVM底层⛰️）
所有阻塞队列均基于**锁+Condition等待队列**实现，通过`ReentrantLock`保证线程安全，通过两个Condition分别实现队列满/空的等待唤醒。

#### 🔹 机制层（CSAPP硬件原理🌏）
阻塞队列的线程阻塞与唤醒通过`LockSupport.park/unpark`实现，精准唤醒指定线程，避免了`synchronized`的`notifyAll()`导致的惊群效应，减少CPU上下文切换开销。

### 4.2 常用阻塞队列实现与选型
| 队列实现              | 边界     | 锁机制                | 核心特性与适用场景                                           |
| --------------------- | -------- | --------------------- | ------------------------------------------------------------ |
| ArrayBlockingQueue    | 有界     | 单锁双Condition       | 数组实现的有界队列，必须指定容量，适合固定容量的生产消费场景 |
| LinkedBlockingQueue   | 可选有界 | 双锁（入队/出队分离） | 链表实现，默认无界，入队出队用两把独立锁，并发性能高于ArrayBlockingQueue |
| PriorityBlockingQueue | 无界     | 单锁                  | 支持优先级排序的无界队列，适合按优先级处理任务的场景         |
| DelayQueue            | 无界     | 单锁                  | 延迟队列，元素必须实现Delayed接口，仅当延迟到期才能取出，适合定时任务调度 |

### 4.3 ArrayBlockingQueue双Condition设计原理（对应《Java并发编程的艺术》6.3）
#### 🔹 基础层（书本定义）
ArrayBlockingQueue是数组实现的有界阻塞队列，核心设计是**一把独占锁 + 两个独立的Condition等待队列**：
- `lock`：ReentrantLock独占锁，保证队列操作的线程安全；
- `notEmpty`：Condition队列，存放等待队列非空的消费者线程；
- `notFull`：Condition队列，存放等待队列非满的生产者线程。

#### 🔹 核心源码实现
```java
// 入队put()方法
public void put(E e) throws InterruptedException {
    checkNotNull(e);
    final ReentrantLock lock = this.lock;
    lock.lockInterruptibly();
    try {
        // 队列满，生产者线程进入notFull等待队列阻塞
        while (count == items.length)
            notFull.await();
        // 队列有空位，插入元素
        enqueue(e);
        // 唤醒等待的消费者线程
        notEmpty.signal();
    } finally {
        lock.unlock();
    }
}

// 出队take()方法
public E take() throws InterruptedException {
    final ReentrantLock lock = this.lock;
    lock.lockInterruptibly();
    try {
        // 队列空，消费者线程进入notEmpty等待队列阻塞
        while (count == 0)
            notEmpty.await();
        // 队列有元素，取出元素
        E x = dequeue();
        // 唤醒等待的生产者线程
        notFull.signal();
        return x;
    } finally {
        lock.unlock();
    }
}
```

#### 🔹 实现层（JVM底层⛰️）
两个Condition队列完全独立，生产者唤醒消费者、消费者唤醒生产者，不会出现无效唤醒，彻底避免了`wait/notify`的惊群效应。

### 4.4 生产者-消费者模式（对应JCiP 5.3.2）
#### 🔹 基础层（书本定义）
生产者-消费者模式是并发编程的基础设计模式，通过阻塞队列解耦生产者与消费者，两者无需直接通信，仅通过队列传递数据，核心优势：
1. 解耦：生产者与消费者代码完全解耦，可独立修改、扩展；
2. 削峰填谷：队列可缓存生产的任务，应对突发流量，避免系统过载；
3. 平衡生产消费速度：生产快消费慢时，生产者阻塞；消费快生产慢时，消费者阻塞，自动平衡速度。

#### 🔹 标准实现示例
```java
// 生产者
class Producer implements Runnable {
    private final BlockingQueue<Integer> queue;
    public Producer(BlockingQueue<Integer> queue) { this.queue = queue; }
    @Override
    public void run() {
        for (int i = 0; i < 100; i++) {
            try {
                queue.put(i);
                System.out.println("生产：" + i);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
    }
}

// 消费者
class Consumer implements Runnable {
    private final BlockingQueue<Integer> queue;
    public Consumer(BlockingQueue<Integer> queue) { this.queue = queue; }
    @Override
    public void run() {
        while (true) {
            try {
                Integer i = queue.take();
                System.out.println("消费：" + i);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
        }
    }
}
```

## 🧩 模块5：线程中断与活跃性问题（对应JCiP 5.4、13.1-13.5）
### 5.1 线程中断机制（对应JCiP 5.4、13.1.2）
#### 🔹 基础层（书本定义）
Java线程中断是一种**协作式的线程停止机制**，没有强制终止线程，只是给线程设置一个中断标记，由线程自身决定是否响应中断、何时停止执行。
核心方法：
1. `Thread.interrupt()`：给目标线程设置中断标记，若线程正阻塞在`wait()`、`sleep()`、`join()`、`Lock.lockInterruptibly()`等方法，会立即抛出`InterruptedException`，并清除中断标记；
2. `Thread.isInterrupted()`：检查当前线程的中断标记，不会清除标记；
3. `Thread.interrupted()`：静态方法，检查当前线程的中断标记，**调用后会清除中断标记**。

#### 🔹 实现层（JVM底层⛰️）
中断标记存储在Thread对象的`volatile boolean interrupted`成员变量中，保证多线程间的可见性；阻塞方法的中断响应由JVM底层实现，检测到中断标记后抛出异常。

#### 🔹 机制层（CSAPP硬件原理🌏）
中断标记是`volatile`变量，修改时会触发MESI协议缓存失效，目标线程读取中断标记时能立即看到最新值，无锁保证可见性。

#### 🔹 最佳实践（JCiP 5.4）
1. 捕获`InterruptedException`后，要么立即向上抛出，要么在catch块中重新设置中断标记（`Thread.currentThread().interrupt()`），不能吞掉中断；
2. 长时间运行的任务，应定期检查中断标记，响应停止请求。

### 5.2 活跃性问题（对应JCiP 13.1-13.3）
活跃性问题：并发程序中，线程无法继续执行的问题，核心分为三类：死锁、活锁、饥饿。

#### 🔹 1. 死锁（JCiP 13.1）
##### 基础层（书本定义）
死锁：多个线程互相等待对方持有的锁，永远无法释放，所有线程都无限阻塞。
死锁发生的四个必要条件（Coffman条件）：
1. **互斥条件**：锁同一时刻只能被一个线程持有；
2. **请求与保持条件**：线程持有一个锁，同时请求另一个被其他线程持有的锁；
3. **不可剥夺条件**：锁只能被持有者主动释放，不能被其他线程强制剥夺；
4. **循环等待条件**：线程之间形成循环等待链，每个线程都等待下一个线程持有的锁。

##### 死锁示例
```java
// 典型死锁：线程A持有lock1，请求lock2；线程B持有lock2，请求lock1
public class DeadLockDemo {
    private static final Object lock1 = new Object();
    private static final Object lock2 = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (lock1) {
                System.out.println("线程A持有lock1，请求lock2");
                try { Thread.sleep(100); } catch (InterruptedException e) {}
                synchronized (lock2) { System.out.println("线程A持有lock2"); }
            }
        }).start();

        new Thread(() -> {
            synchronized (lock2) {
                System.out.println("线程B持有lock2，请求lock1");
                try { Thread.sleep(100); } catch (InterruptedException e) {}
                synchronized (lock1) { System.out.println("线程B持有lock1"); }
            }
        }).start();
    }
}
```

##### 死锁预防与解决（JCiP 13.1.3）
破坏四个必要条件中的任意一个，即可预防死锁：
1. **破坏循环等待**：所有线程按照固定的全局顺序获取锁，是最常用的死锁预防方案；
2. **破坏请求与保持**：一次性获取所有需要的锁，获取失败则释放已持有的锁；
3. **破坏不可剥夺**：持有锁的线程请求其他锁失败时，主动释放已持有的锁（Lock.tryLock()实现）；
4. **破坏互斥**：使用无锁编程替代锁，仅适用于特定场景。

#### 🔹 2. 活锁（JCiP 13.2）
##### 基础层（书本定义）
活锁：线程没有阻塞，一直在运行，但始终无法推进任务，一直在重复相同的操作。
典型场景：两个线程互相响应对方的操作，不断修改状态，导致谁都无法继续执行。
##### 解决方案：在重试机制中引入随机的等待时间，打破同步的重试节奏。

#### 🔹 3. 饥饿（JCiP 13.3）
##### 基础层（书本定义）
饥饿：线程始终无法获取到需要的资源，无法执行任务。
Java中饥饿的典型场景：
1. 非公平锁下，线程始终抢占不到锁；
2. 线程优先级设置不当，低优先级线程始终得不到CPU调度；
3. 线程始终处于等待队列的尾部，一直被其他线程插队。
##### 解决方案：使用公平锁、避免设置极端的线程优先级、保证等待队列的FIFO顺序。

## 🧩 模块6：同步工具类全解析（对应JCiP 5.5；《Java并发编程的艺术》8.1-8.4）
同步工具类是JUC提供的用于协调多线程执行流程的工具，核心分为四类：`CountDownLatch`、`CyclicBarrier`、`Semaphore`、`Exchanger`，所有工具均基于AQS实现。

### 6.1 CountDownLatch（闭锁）（对应JCiP 5.5.1；《Java并发编程的艺术》8.1）
#### 🔹 基础层（书本定义）
CountDownLatch是**一次性使用的同步工具**，核心作用是**让一个/多个线程等待其他一组线程完成操作后，再继续执行**。
核心设计：
- 构造方法传入一个int类型的计数`count`；
- 每个线程完成操作后，调用`countDown()`方法，计数减1；
- 等待线程调用`await()`方法，阻塞直到计数变为0，或被中断、超时。
典型场景：
1. 主线程等待多个子线程完成初始化后，再启动服务；
2. 压测场景中，让所有线程同时启动，模拟高并发。

#### 🔹 实现层（JVM底层⛰️）
基于AQS的**共享模式**实现：
- 构造方法的`count`赋值给AQS的`state`变量；
- `countDown()`调用`releaseShared()`，将`state`减1，减到0时唤醒所有等待的线程；
- `await()`调用`acquireSharedInterruptibly()`，`state>0`时阻塞线程。

---

### 6.2 CyclicBarrier（循环栅栏）（对应JCiP 5.5.3；《Java并发编程的艺术》8.2）
#### 🔹 基础层（书本定义）
CyclicBarrier是**可循环使用的同步工具**，核心作用是**让一组线程到达栅栏时被阻塞，直到所有线程都到达栅栏，栅栏才会打开，所有线程同时继续执行**。
核心特性：
- 构造方法传入参与的线程数`parties`，可传入一个栅栏打开时执行的`barrierAction`；
- 线程到达栅栏时调用`await()`方法，阻塞等待其他线程；
- 所有线程到达后，栅栏打开，执行`barrierAction`，所有线程同时继续执行；
- 栅栏可循环使用，下一轮执行会重置计数。
典型场景：多线程并行计算，所有线程完成计算后，汇总结果。

#### 🔹 与CountDownLatch的核心区别
| 特性       | CountDownLatch            | CyclicBarrier                      |
| ---------- | ------------------------- | ---------------------------------- |
| 可复用性   | 一次性，计数归0后无法重置 | 可循环使用，计数自动重置           |
| 等待对象   | 主线程等待其他线程完成    | 线程之间互相等待                   |
| 计数规则   | 线程完成后计数减1         | 线程到达后计数加1，直到等于parties |
| 自定义动作 | 不支持                    | 支持栅栏打开时执行barrierAction    |

#### 🔹 实现层（JVM底层⛰️）
基于`ReentrantLock`+`Condition`实现，通过`lock`保证计数修改的原子性，通过`Condition`实现线程的等待与唤醒。

---

### 6.3 Semaphore（信号量）（对应JCiP 5.5.2；《Java并发编程的艺术》8.3）
#### 🔹 基础层（书本定义）
Semaphore是**基于计数的信号量**，核心作用是**控制同时访问特定资源的线程数量**，实现流量控制。
核心设计：
- 构造方法传入许可数量`permits`，支持公平/非公平模式；
- 线程访问资源前，调用`acquire()`方法获取许可，无可用许可时阻塞；
- 线程使用完资源后，调用`release()`方法释放许可，唤醒等待的线程。
典型场景：
1. 数据库连接池，限制同时连接的线程数；
2. 接口限流，限制同时处理的请求数。

#### 🔹 实现层（JVM底层⛰️）
基于AQS的**共享模式**实现：
- 构造方法的`permits`赋值给AQS的`state`变量；
- `acquire()`调用`acquireSharedInterruptibly()`，尝试CAS减少`state`，失败则阻塞；
- `release()`调用`releaseShared()`，增加`state`，唤醒等待的线程。

---

### 6.4 Exchanger（交换器）（对应《Java并发编程的艺术》8.4）
#### 🔹 基础层（书本定义）
Exchanger是**两个线程之间的数据交换工具**，核心作用是**让两个线程在同步点交换数据，只有两个线程都到达交换点，才能完成数据交换**。
核心特性：
- 线程调用`exchange(V x)`方法，传入要交换的数据，阻塞等待另一个线程；
- 另一个线程调用`exchange(V x)`方法，两个线程交换数据，同时返回对方的数据；
- 若只有一个线程到达交换点，会一直阻塞，直到另一个线程到达，或超时、被中断。
典型场景：两个线程间的双向数据传递、遗传算法、校对场景。

#### 🔹 实现层（JVM底层⛰️）
基于`volatile`变量+CAS自旋+`LockSupport.park/unpark`实现，通过一个`Node`对象存储交换的数据，保证两个线程的数据交换原子性。

## 🧩 模块7：可伸缩结果缓存的设计思路（对应JCiP 5.6）
### 7.1 需求背景（JCiP 5.6）
设计一个高并发场景下的结果缓存，用于缓存耗时计算的结果，避免重复计算，核心要求：
1. 线程安全，多线程并发访问无竞态条件；
2. 高伸缩性，高并发下性能不会急剧下降；
3. 避免重复计算，同一个计算任务不会被多个线程同时执行；
4. 处理计算异常，避免异常结果被缓存。

### 7.2 从基础实现到高并发优化的全流程
#### 🔹 版本1：HashMap+同步方法（基础但性能差）
```java
public class BasicCache<A, V> implements Computable<A, V> {
    private final Map<A, V> cache = new HashMap<>();
    private final Computable<A, V> c;

    public BasicCache(Computable<A, V> c) { this.c = c; }

    // 全方法加synchronized，同一时刻仅一个线程可访问，并发性能极差
    @Override
    public synchronized V compute(A arg) throws InterruptedException {
        V result = cache.get(arg);
        if (result == null) {
            result = c.compute(arg);
            cache.put(arg, result);
        }
        return result;
    }
}
```
**缺陷**：全方法加独占锁，高并发下所有线程阻塞，伸缩性极差。

#### 🔹 版本2：ConcurrentHashMap替代HashMap（优化并发读）
```java
public class ConcurrentCache<A, V> implements Computable<A, V> {
    private final Map<A, V> cache = new ConcurrentHashMap<>();
    private final Computable<A, V> c;

    public ConcurrentCache(Computable<A, V> c) { this.c = c; }

    @Override
    public V compute(A arg) throws InterruptedException {
        V result = cache.get(arg);
        if (result == null) {
            result = c.compute(arg);
            cache.put(arg, result);
        }
        return result;
    }
}
```
**优化点**：ConcurrentHashMap的读操作完全无锁，写操作细粒度加锁，并发性能大幅提升。
**缺陷**：存在重复计算问题，多个线程同时计算同一个参数时，会重复执行耗时计算。

#### 🔹 版本3：FutureTask避免重复计算（最终可伸缩方案）
```java
public class FinalCache<A, V> implements Computable<A, V> {
    private final ConcurrentHashMap<A, Future<V>> cache = new ConcurrentHashMap<>();
    private final Computable<A, V> c;

    public FinalCache(Computable<A, V> c) { this.c = c; }

    @Override
    public V compute(A arg) throws InterruptedException {
        while (true) {
            Future<V> future = cache.get(arg);
            // 1. 无缓存，创建计算任务
            if (future == null) {
                Callable<V> eval = () -> c.compute(arg);
                FutureTask<V> ft = new FutureTask<>(eval);
                // 2. 原子性放入缓存，仅当key不存在时才放入
                future = cache.putIfAbsent(arg, ft);
                if (future == null) {
                    future = ft;
                    ft.run(); // 执行计算
                }
            }
            // 3. 等待计算完成，获取结果
            try {
                return future.get();
            } catch (CancellationException e) {
                // 计算被取消，移除缓存
                cache.remove(arg, future);
            } catch (ExecutionException e) {
                // 计算异常，移除缓存，抛出异常
                cache.remove(arg, future);
                throw new RuntimeException(e.getCause());
            }
        }
    }
}
```
**核心优化点（JCiP 5.6）**：
1. 用`ConcurrentHashMap`保证缓存操作的线程安全与高并发；
2. 用`FutureTask`封装计算任务，避免多个线程重复计算同一个参数；
3. 用`putIfAbsent()`原子性放入任务，避免竞态条件；
4. 处理计算异常与取消，避免无效的Future被永久缓存；
5. while循环重试，处理任务被取消的场景，保证缓存的正确性。

### 8.2 核心知识点全链路拆解
#### 8.2.1 synchronized 全链路打通
- 并发设计（JCiP）：Java内置独占锁，可重入，保证原子性/可见性/有序性
- JVM底层⛰️：对象头Mark Word、锁升级流程、Monitor监视器、monitorenter/monitorexit字节码
- CSAPP硬件🌏：lock cmpxchg原子指令、用户态/内核态切换、MESI缓存一致性
- 联动结论：synchronized是JVM封装硬件原子指令与操作系统同步原语的内置锁方案

#### 8.2.2 ReentrantLock + AQS 全链路打通
- 并发设计（JCiP/艺术）：显式独占锁，支持可中断、公平锁、超时获取，灵活度远超synchronized
- JVM底层⛰️：AQS同步器、CLH双向队列、volatile state变量、LockSupport.park/unpark
- CSAPP硬件🌏：cmpxchg CAS指令、CLH队列缓存局部性优化、避免惊群效应、减少上下文切换
- 联动结论：ReentrantLock是基于AQS框架、纯用户态CAS实现的高性能显式锁方案

#### 8.2.3 并发容器锁优化 全链路打通
- 并发设计（JCiP/艺术）：缩小锁粒度、读写分离、无锁CAS、弱一致性迭代器
- JVM底层⛰️：分段锁、volatile无锁读、CAS节点操作、COW写时复制
- CSAPP硬件🌏：减少lock指令总线锁定范围、降低缓存行颠簸、避免频繁上下文切换
- 联动结论：并发容器的核心优化是贴合硬件特性，用最小的同步开销保证线程安全

## 🧩 模块9：阶段2 终极易错点汇总
1. ❌ 错误：同步容器的单个方法线程安全，复合操作也线程安全
   ✅ 正确：同步容器仅单个方法原子性，复合操作存在竞态条件，必须通过客户端加锁保证原子性
2. ❌ 错误：CopyOnWriteArrayList适合所有读多写少的场景
   ✅ 正确：仅适合写操作极少、数据量小的场景，频繁写会导致大量数组复制与GC开销
3. ❌ 错误：synchronized是非公平锁，ReentrantLock默认是公平锁
   ✅ 正确：两者默认都是非公平锁，ReentrantLock可通过构造方法指定公平模式
4. ❌ 错误：AQS的同步队列是单向链表
   ✅ 正确：AQS的同步队列是CLH变体双向链表，Condition等待队列是单向链表
5. ❌ 错误：Lock的unlock()会自动执行，和synchronized一样
   ✅ 正确：Lock必须手动在finally块中调用unlock()，否则会导致锁泄漏，其他线程永远无法获取锁
6. ❌ 错误：CountDownLatch和CyclicBarrier可以互相替代
   ✅ 正确：CountDownLatch是一次性的，主线程等待其他线程；CyclicBarrier可循环使用，线程之间互相等待，适用场景完全不同
7. ❌ 错误：捕获InterruptedException后，直接吞掉异常不做处理
   ✅ 正确：捕获中断异常后，要么向上抛出，要么重新设置当前线程的中断标记，不能吞掉中断，否则会导致上层无法感知中断请求
8. ❌ 错误：公平锁的性能比非公平锁好
   ✅ 正确：非公平锁的吞吐量远高于公平锁，公平锁严格排队会导致频繁的线程阻塞与上下文切换，仅在顺序性要求极高的场景使用
9. ❌ 错误：读写锁的读锁可以和写锁同时持有
   ✅ 正确：读写锁遵循读-写互斥规则，读锁持有期间，写锁无法获取；写锁持有期间，读锁无法获取，仅读-读不互斥
10. ❌ 错误：ConcurrentHashMap的迭代器是强一致性的，会抛出ConcurrentModificationException
    ✅ 正确：ConcurrentHashMap的迭代器是弱一致性的，迭代过程中容器修改不会抛出异常，只能看到迭代器创建时已完成的修改
