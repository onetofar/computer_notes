## 一眼看懂的横向结论

- **阻塞 vs 非阻塞**：阻塞版一次 `recv` 拿到 4 字节但会睡着；非阻塞版全程不睡死，
  代价是 40 次白问换 5 次命中（空问占比 ~89%）。
- **select vs poll vs epoll**：同样 64 个 socket、同样 64 次就绪，
  select 每轮重塞 512 次 fd、poll 每次扫描 512 个 fd、epoll 只注册 64 次。
- **线程 vs 进程 vs Actor**：40 万次计数，加锁 / 进程 / Actor 三种写法结果都对，
  代价分别是 40 万次锁、64 字节管道、40 万次邮箱出入队；不加锁那种每次运行结果都不同。
- **new vs 对象池**：构造次数从 20 万降到 1024；但池子不保证数据干净——
  忘了 `BackToPool()` 就会把上一个用户的账号名带给下一个。
- **OOP vs ECS**：同样 100 帧，继承模型 6400 次虚调用里 87.5% 是空转，ECS 只调 800 次。
- **查一行**：扫描比 20 万次、哈希索引比 1 次、二分比 17 次；SQL 不预处理则多付约 1400 倍解析量。

## 环境约定

- **无 MySQL / Redis**：服务器上没有这两个的客户端与服务端，
  相关主题一律做**纯逻辑模拟**，不真连数据库。
- **只用回环**：网络示例一律走 `127.0.0.1`（或 `socketpair`），
  端口由内核临时分配，**不占用固定端口**。
- **必然退出**：每个网络示例都带 `SO_RCVTIMEO` 超时与 `alarm(15)` 兜底，
  跑完即退，不留挂起进程。
- **零警告**：`g++ -std=c++20 -O2 -Wall -Wextra -pthread` 零警告零报错（已在
  服务器 g++ 16.2.1 上验证 22/22 通过）。
- **无 `@ub: yes` 文件**：本批没有能被 valgrind/ASan 检出的未定义行为演示；
  `thread-process-actor/02` 是数据竞争（需 ThreadSanitizer），按仓库既有约定不标
  `@ub: yes`，改用 `// @note:` 标出。
