# 缓存局部性：访问顺序与数据布局

> 来源讲义：`书籍/教材讲义/深入理解计算机系统/第6章 存储器层次结构（讲义）.md` §6.5 / §6.6.1 / §6.6.3

局部性不是感觉，是**可以算出来的不命中率**：
设块大小是 B 字节、步长为 k（以机器字计），每次循环迭代的平均不命中次数是 `min(1, (字长 × k) / B)`。
**k = 1 时最小** —— 这就是下面四个文件各自在做的事。

## 对照表

| 文件 | 差异点 | 预期输出 |
| --- | --- | --- |
| `01-row-major.c` | 内层循环 stride = 1，按行顺序遍历 | 32MB 工作集下 **3 ms**；`sum` 与 `02` 完全相同 |
| `02-column-major.c` | 内层循环 stride = N，按列顺序遍历 | 同样数据 **22 ms**（约 7 倍；讲义在桌面机上实测 25 倍） |
| `03-packed-vs-unpacked.c` | 结构体数组 vs 字段拆开分别存（SoA） | 要扫的字节数 **128MB vs 64MB**（确定性的证据）；两者都是顺序扫描，耗时差别不大 |
| `04-vectorized-vs-scalar.c` | 累加器加不加 `volatile` | `volatile` 版 **5~6 倍**慢——编译器不敢把它改写成 SIMD |

`01` 与 `02` 访问的是**完全相同的一批元素**，`sum` 必须相等；差别只在访问顺序。

## 教材原话

> 设块大小是 B 字节，步长为 k（以机器字计），那么每次循环迭代的平均不命中次数是 `min(1, (字长 × k) / B)`。**这个值在 k = 1 时最小。**
>
> —— §6.5

> **反复引用局部变量是好的** —— 因为编译器会把它们放进寄存器文件（层次的最高层）。`sum`、`i` 就是这样。
>
> **stride-1 是好的** —— 因为层次里**每一层**都按连续块存数据。
>
> —— §6.5

> 原书在桌面机上实测：`sumarrayrows` 比 `sumarraycols` **快 25 倍**。
>
> —— §6.5

> 即使工作集大到装不进任何缓存（主存脊上），**坡的顶端比谷底仍高 8 倍** —— 也就是说，时间局部性很差时，空间局部性还能救场。
>
> —— §6.6.1

> stride = 1 处有一道异常平坦的高原：即使工作集超出 L1 和 L2，吞吐仍稳定在 12 GB/s。这归功于 Core i7 的**硬件预取**（prefetching）机制——它能自动识别顺序 stride-1 模式，在被访问之前就把块拉进缓存。
>
> —— §6.6.1

> 1. **把注意力集中在内层循环上** —— 大部分计算和内存访问都发生在那儿。
> 2. **尽量最大化空间局部性** —— 顺序地、以 stride 1、按内存里的存放顺序读数据。
> 3. **尽量最大化时间局部性** —— 一个数据对象读进来之后，尽可能多地用它。
>
> —— §6.6.3

讲义 §6.5 关于"指针追逐"的补充，说明为什么"步长固定"还不够：

> 链表就是典型：每个节点告诉你下一个节点在哪，于是你**必须先读到当前节点，才能知道下一个地址**。
> CPU 无法提前发起访存，只能一个指针一个指针地等 —— 这叫**依赖链**（pointer chasing），是所有局部性都救不了的情况，因为下一个地址根本事先不知道。
>
> —— §6.5（推演）

## 跑法

```bash
bash tools/run_all.sh

cd books/csapp/cache-locality
gcc -std=c11 -O2 -Wall -Wextra 01-row-major.c -o /tmp/01 && /tmp/01
gcc -std=c11 -O2 -Wall -Wextra 02-column-major.c -o /tmp/02 && /tmp/02
```

**对比 `01` 和 `02` 的耗时**——这是本主题的结论。
`03` 看的是**布局**（同样的数据怎么摆），`04` 看的是**编译器能不能利用这个布局**。
