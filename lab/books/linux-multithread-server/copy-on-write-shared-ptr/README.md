# 读要不要加锁：普通 mutex vs shared_ptr copy-on-write

> 来源讲义：`书籍/教材讲义/Linux多线程服务端编程/第2章 线程同步精要（讲义）.md` §2.8

## 对照表

四个文件围绕同一件事：**一个共享的可变列表，读者怎么读、写者怎么写。**

| 文件 | 策略 | 预期输出 |
| --- | --- | --- |
| `01-plain-mutex-read-write.cpp` | 普通 mutex，读者**全程持锁**遍历 | 写者等待 ≈ 180000 us（被读者堵住） |
| `02-shared-ptr-copy-on-write.cpp` | `shared_ptr` copy-on-write，读者只拷一次指针 | 写者等待 ≈ 40 us（几乎不被阻塞） |
| `03-cow-atomicity-broken.cpp` | 复制—修改—替换**拆成两个临界区**（讲义「错误三」） | 最终 `size=1`（丢失更新） |
| `04-cow-in-place-mutation-race.cpp` | 写端**无视 `unique()` 原地修改**（讲义「错误一」） | 读者迭代器失效 → 悬垂读（UB，检测器报错） |

## 教材原话

讲义 §2.8 开篇（这一节要解决三个悬案）：

> 本节解决§2.1的几个未决问题：

> ·§2.1.1post()和traverse()死锁。

> ·§2.1.2把Request::print()移出Inventory::printAll()临界区。

> ·§2.1.2解决Request对象析构的race condition。

> 然后再示范用普通mutex替换读写锁。解决办法都基于同一个思路，那就是用shared_ptr来管理共享数据。

讲义 §2.8 讲「原理：四步」：

> ·shared_ptr是引用计数型智能指针，如果当前只有一个观察者，那么引用计数的值为1。

> ·对于write端，如果发现引用计数为1，这时可以安全地修改共享对象，不必担心有人正在读它。

> ·对于read端，在读之前把引用计数加1，读完之后减1，这样保证在读的期间其引用计数大于1，可以阻止并发写。

> ·比较难的是，对于write端，如果发现引用计数大于1，该如何处理？sleep()一小段时间肯定是错的。

讲义 §2.8 讲「read 端：traverse()」：

> 在read端，用一个栈上局部FooListPtr变量当做“观察者”，它使得g_foos的引用计数增加(L6)。traverse()函数的临界区是L4～L8，临界区内只读了一次共享变量g_foos（这里多线程并发读写shared_ptr，因此必须用mutex保护），比原来的写法大为缩短。而且多个线程同时调用traverse()也不会相互阻塞。

讲义 §2.8 讲「write 端：post()」，以及那一段题眼：

> 注意这里临界区包括整个函数（L20～L27），其他写法都是错的。

讲义 §2.8 讲「三个错误写法」的共同病因：

> **这三个错误例子合起来说明了一件事：copy-on-write 的正确性全部押在「复制—修改—替换」这三步的原子性上。** 也就是说——**它其实还是需要一把锁的**。`shared_ptr` 没有消除锁，它消除的是**「读者要抢锁」这件事**。

讲义 §2.8 讲「用普通 mutex 替换读写锁：CustomerData」，其中读者那一侧：

> MapPtr data = getData();
> // data 一旦拿到，就不再需要锁了。
> // 取数据的时候只有 getData() 内部有锁，多线程并发读的性能很好。

## 讨论点

1. **`01` 与 `02` 是这节最核心的对照。** 同样是 1000 个元素的列表、同样是一个 200ms 的长遍历，
   普通 mutex 下写者等了 **约 180ms**（读者一直持锁），copy-on-write 下只等了 **几十微秒**。
   这就是讲义说的「把「读」从「需要同步」变成「不需要同步」」。
2. **但讲义明确说「它其实还是需要一把锁的」。** `shared_ptr` 消除的是
   **「读者要抢锁」这件事**，不是锁本身。写端反而需要更强的锁纪律。
   `02` 的写端就是讲义那个「临界区包括整个函数」的写法。
3. **`03` 演示「错误三」的丢失更新。** 复制被放到临界区之外，两个写者都读到同一份旧值，
   后写的覆盖先写的 → 最终 `size=1` 而不是 2。这是**逻辑错误**，不是内存错误，
   所以它能稳定复现、也能稳定退出。
4. **`04` 演示「错误一」的直接后果。** 写端无视 `unique()` 原地 `push_back`，
   `vector` 扩容让读者手里的迭代器失效，读者读到已释放的内存 → **UB**。
   这正是讲义说的「它根本没有检查 `unique()`……迭代器失效、数据竞争，全都回来了」。
   `04` 是 UB 文件，默认构建跳过。

## 跑法

```bash
bash tools/run_all.sh          # 跳过 ub 文件, 01/02/03 会跑
bash tools/run_all.sh --ub     # 连 04 一起跑, 期望检测器报错
```

正常文件的输出可以直接横向对比：

```
普通 mutex: 写者等待=180501 us (读者持锁, 写者被阻塞), size=1001
copy-on-write: 写者等待=43 us (读者不在临界区, 不被阻塞), size=1001
最终 size=1 (正确应为 2; 丢失更新说明复制—修改—替换不原子)
```
