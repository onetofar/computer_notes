# 条件变量: 等待时用 `while` 还是 `if`

> 对照问题: 线程被唤醒之后, 能不能直接往下走? 一次"假唤醒"会把生产者-消费者写成什么样?

| 文件 | 差异点 | 预期输出 |
| --- | --- | --- |
| [01-while-loop.c](./01-while-loop.c) | 等待用 `while (g_count == 0)` 重新检查条件 | `while 版结局: 消费 3 个元素, 被唤醒 4 次(其中 1 次是假唤醒), 退出码=0` |
| [02-if-loop.c](./02-if-loop.c) | 等待用 `if (g_count == 0)`(故意写错, 标 `@ub: yes`) | `runtime error: 空队列被取走一次(if 版漏了重新检查), g_count=-1`, 退出码 1 |

两个文件的**线程结构完全一样**: 1 个生产者 + 1 个消费者 + 1 个"噪声线程"(专门发一次假唤醒)。唯一差别是等待那一行写 `while` 还是 `if`。

`02` 是故意演示未定义行为: 队列被取空后 `--g_count` 变成 -1, `g_buf[-1]` 越界读取。默认跑法会跳过它(`run_all.sh` 会跳过 `@ub: yes` 的文件), 用 `run_all.sh --ub` 才会去触发它。

## 教材原话

> **提示（原书提示框）：对条件变量使用 while（不是 if）。**
>
> if 是否正确取决于发信号的语义；**while 永远正确**。另外 while 也顺手解决了**假唤醒（spurious wakeup）**——某些线程库的实现细节可能导致一次 signal 唤醒两个线程，重新检查条件就能挡住。
>
> —— 《操作系统导论》第 30 章讲义 §30.2「翻车一：Mesa 语义」([[30-第30章 条件变量]])

> **根因**：发信号只是把线程从"睡"变成"就绪"，**并不保证它在运行之前状态还符合预期**。这叫 **Mesa 语义**（Mesa 是 Lampson 和 Redell 造的一个系统，条件变量的老家）。与之相对的是 **Hoare 语义**——保证被唤醒的线程**立刻**执行，但实现难度大得多。**几乎所有真实系统用的都是 Mesa 语义。**
>
> —— 《操作系统导论》第 30 章讲义 §30.2

> 被唤醒后**再检查一遍**条件，不满足就接着睡。改动一行，语义从"听到信号就冲"变成"听到信号再确认一次"。
>
> —— 《操作系统导论》第 30 章讲义 §30.2

> **为什么睡前要释放锁**：不释放，被唤醒的线程就拿不到锁，谁也走不了——一起卡死。
>
> —— 《操作系统导论》第 30 章讲义 §30.1

> **信号是边沿触发，状态是持久的**——去掉 `done` 变量，信号就会发给空气；
>
> —— 《操作系统导论》第 30 章讲义 §30.4 小结

## 跑法

```bash
# 正确版本: 正常退出
bash tools/check_one.sh books/os-concepts/condvar-while-vs-if/01-while-loop.c

# 错误版本: 故意演示 UB, 默认跳过
bash tools/check_one.sh books/os-concepts/condvar-while-vs-if/02-if-loop.c --ub
bash tools/run_all.sh --ub
```

## 讨论点

1. 假唤醒在这两个文件里是**被显式造出来的**(噪声线程在队列为空时发信号), 不是靠运气撞上——所以每次跑结果都一样。
2. `01` 的"被唤醒 4 次(其中 1 次是假唤醒)"能直接看出 `while` 多做了一次重新检查。
3. 讲义 §30.2 还有第二类翻车: 一个条件变量区分不了"该叫谁", 修法是**两个条件变量(empty/fill)**。这一组实验刻意只留 `while` 这一个变量, 方便归因。
