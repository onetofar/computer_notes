# 对照讨论：状态怎么复制过去（全量快照 / 增量 / 相关性裁剪）

**问题**：服务器内存里的世界，怎么搬到另一台机器上？
整包寄照片，还是只寄变化？还是先想想**该寄给谁**？

## 对照表

| 文件 | 差异点 | 预期输出 |
| --- | --- | --- |
| `01-full-snapshot.cpp` | 全量快照：整个世界塞进一个包，每包自足 | tick1 `包字节=79 创建=6`；tick3 对象少了 → `销毁=1`（缺席即销毁） |
| `02-incremental-delta.cpp` | 增量：只寄变化，动作 = 创建/更新/销毁 | 场景A 更新生效 `x=222`；场景B 创建包丢失 → 更新被跳过 `必须整段跳过=8 字节`；79 字节 → 27 字节 |
| `03-area-of-interest.cpp` | 相关性裁剪：先决定发给谁 | 半径 1000 → `48 字节(占全量字节 37%)`；半径翻倍 → 64 字节 |
| `04-lost-create-overrun-ub.cpp` | 创建包丢失 + 复制头没有 size 字段 → 读头被带偏 | `runtime error: 猜出的记录长度 239 字节 ... 越过包长 13 -> 未定义行为`（`@ub: yes`） |

横向看：01 与 02 是同一份世界的两条路——**79 字节/包 vs 只寄变化**；
但 02 的正确性建立在"接收方现状已知"上，04 就是这个前提塌了的样子。
03 是更前面的一道闸：**先决定发给谁，再谈发什么**。

## 教材原话（逐字引文）

> 有了三元组，复制整个世界最直接的做法：**把世界里的每个对象都塞进一个包**。

> 第三步是全量快照的免费赠品：**缺席即销毁**。对象消失根本不需要显式的"销毁消息"——对个账就知道谁没了。没有任何簿记、没有重传请求，每包自足，丢一包也不影响下一包。简单得漂亮。

> 但天花板也在这：**整个世界必须装进一个包。** 世界一大，这条路就死了——下一节换思路。

> 既然不必每包都发全世界，那就只发**变化**。

> 每个包是世界状态增量，每条增量是一个对象状态增量，只有三种动作：**创建、更新、销毁**。

> 一个值得背下来的协议细节：**销毁动作不序列化 classId**——对象都要没了，类型信息再无用处。协议设计里每个字段都要问一句"还有人需要它吗"。

> 看接收端处理 `RA_Update` 的现场：**更新到达时，对象可能根本不存在**——前面的创建包丢了或乱序了。这时不能直接读进对象，必须想办法把这段数据从流里"读掉"，否则流位置错位，后面所有数据全部报废。

> 原文的警告说得更透：增量复制的正确性建立在**发送方精确知道接收方现状**之上，而互联网不保证你上次发的包对方收到了——所以增量方案要么走 TCP，要么在 UDP 上自己补可靠性。

> **相关性**（relevance）的定义很朴素：对一个特定客户端，"应该通知它更新信息的对象"就是在范围内的。

> 但要先认清一个现实 ⚠️：**相关性很少是二元的**。记分牌要显示所有人的血量——血量与距离无关地永远相关，而这个玩家对象的其他信息（位置、朝向）可能不相关。

> **狙击枪故事**（原文最生动的例子）：按"突击步枪射程"定范围，测试时带宽刚好达标；后来策划加了把射程翻倍的狙击枪——相关对象数量暴涨，带宽超了。**业务假设写死在底层机制里，改需求就穿帮。**

> 所以本章的主旋律一句话：**先决定"发给谁"，再谈"发什么、发多勤"。**

—— 第5章《对象复制（讲义）》§5.3 / §5.4、第9章《可扩展性（讲义）》§9.1
