# 对照讨论：传输层怎么选（TCP 可靠有序 / UDP 不可靠无序 / 队头阻塞）

> **问题**：同一份状态更新，走**可靠有序**通道还是**不可靠无序**通道，接收端分别看到什么？
> 可靠有序这个"好事"，在实时游戏里到底要付多少代价？

> 本组三个文件共用一个**离线链路模型**（按教材 §7.7 的四步：丢包判定 → 到达时间打标 →
> 按模拟到达时间排入有序队列 → 到点放行），所以**不占端口、不挂进程、每次跑结果都一样**。
> 随机数用 `std::mt19937` 的整数输出直接换算，跨平台结果一致。

## 对照表

| 文件 | 差异点 | 预期输出 |
| --- | --- | --- |
| `01-tcp-reliable-ordered.cpp` | TCP：丢失就重传，接收端**严格按序**交付 | `交付 5/5 个分段, 重传 1 次`；净荷 500 字节但总线上 600 字节 |
| `02-udp-unreliable-unordered.cpp` | UDP：不重传、不保序，丢了就永远丢 | `收到 4 个, 丢失 1 个, 乱序 1 次` |
| `03-head-of-line-blocking.cpp` | 同一条字节流上跑低优先级音效 + 高优先级枪声 | TCP：枪声包 `40ms` 就到却 `多等了 120.0ms`；UDP：枪声 `t=40.0ms` 交付，音效永远不到 |

横向看：01 和 02 是**同一颗种子、同一批包**的两种命运——
差别不在网络，在传输层策略。03 把代价摆到台面上：**可靠有序把低优先级数据的命运绑在高优先级数据上**。

## 教材原话（逐字引文）

> 8 字节头，发出去就忘。不保证到达、不保证顺序、不流量控制。

> TCP 在两机之间建立**有状态的可靠字节流**。

> **流量控制**：接收方用"接收窗口"字段喊话"我缓冲区只剩这么多了，别发"。带宽 ≈ 窗口 ÷ RTT，窗口太小自己就是瓶颈。

> **罪一：低优先级数据堵死高优先级数据。** 远处火箭爆炸的音效包丢了，TCP 会卡住后面"敌人正对你开枪"的动作包，等音效重传到位才放行。玩家根本不在乎那个音效，却要为它挨枪子。

> **罪三：过期状态的重传。** 服务器每秒发 5 个玩家 B 的位置包，途中丢了几个；等重传到位时，补发的是 B 走到 x=0 附近的**旧位置**，而 B 实际已经跑到 x=100——玩家 A 看到的 B 严重过时，还没看到人就已经被射中。

> **选型判据一句话**：游戏里的每一条数据都必须送达、且必须全局有序吗？是（回合制游戏）→ TCP；不是（绝大多数动作游戏，**更在意最新值而非完整值**）→ UDP + 应用层自定义可靠性。

> ```
> ① 丢包判定：随机数 < 丢包率 → 直接扔，不进队列
> ② 到达时间打标：现在 + 平均延迟 + (随机-0.5)×双倍最大抖动
> ③ 按【模拟到达时间】插入有序队列 ← 不按实际到达顺序！
> ④ 每帧放行：模拟到达时间 ≤ 当前时间的才交给游戏
> ```

> ③ 是灵魂：包可能后发先到，队列按"真实世界里它该何时到"排序，抖动和乱序就都被模拟出来了。

—— 第2章《互联网（讲义）》§2.6、第7章《延迟、抖动和可靠性（讲义）》§7.4 / §7.7
