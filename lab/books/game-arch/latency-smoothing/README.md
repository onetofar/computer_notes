# 对照讨论：网络慢怎么让玩家感觉不到（冗余重发 / 插值 / 航位推测）

**问题**：延迟消不掉（光速和物理距离说了算），那在**显示端**能做什么？
三种从保守到激进的手段，各自把多少"猜"的风险交给了玩家？

## 对照表

| 文件 | 差异点 | 预期输出 |
| --- | --- | --- |
| `01-redundancy-latest-value.cpp` | 丢包后**重发最新值**（§7.6），而不是重发旧字节 | 旧字节方案客户端停在 `x=30`；重批最新值客户端看到 `x=50` |
| `02-client-interpolation.cpp` | 客户端插值，IP（插值周期）与 PP（包周期）的关系 | `IP=66.70 ms 卡住帧数=0`；`IP=33.35 ms 卡住帧数=6`（滑到一半没目标） |
| `03-dead-reckoning.cpp` | 航位推测（乐观）与沉默终端（保守）对照 + 三档纠偏 | 沉默终端误差 `0.50`；航位推测误差 `0.00`；玩家转向后误差 `0.33` |

横向看：02 是**保守算法**（只显示服务器两个真实状态之间的状态，永不猜测）；
03 是**乐观算法**（猜对多数，猜错就纠）。01 则是传输层的补救——
**丢包后重传最新值，不是旧字节**。

## 教材原话（逐字引文）

> TCP 式的可靠重传对游戏是浪费（罪三）。把第 5 章的 `ReplicationManager` 和 DNM 接起来，能做得更好：**包丢了，不重发当时的字节，而是重发这些数据现在的最新状态**——可能已经新了半秒。

> - **Create 丢了** → 重新 BatchCreate，**但先查对象还在不在**——不在就别补，重发 create 等于复活死者；
> - **Update 丢了** → 把脏位重新记回去，**也要查现状**，对象没了就作废；
> - **Destroy 丢了** → **无条件重批**——销毁必须送达，不管对象现在的状态如何。

> 规则只有一条：**插值周期 IP 不能小于数据包周期 PP**。IP < PP 的话，滑到一半没有新目标，又卡住——那还不如不滑。IP = PP 时，每次滑完恰好下一个状态也到了，无缝续上，**永远不卡**。

> 这笔账的代价：玩家看到的更滞后了——**1/2 RTT + IP**。但换来的是丝般顺滑，而"恒定的延迟"远没有"忽快忽慢"难受（第6章锁步同样的道理）。所以 IP 就取 PP，不加大，这是最优解。

> 注意插值仍是保守算法：它显示的是服务器两个真实状态**之间**的状态，从未猜测，不会错得离谱。

> 思路一句话：收到的是 1/2 RTT 前的旧状态 → **在本地把模拟再往前跑 1/2 RTT** → 展示给玩家。

> 它是**乐观算法**：猜对多数，猜错就纠。分歧纠正三档，按错误大小选用：
>
> - **即时更新**：直接跳到正确状态。会闪跳，但好过持续错误；
> - **插值**：几帧内平滑滑过去，小误差用这个；
> - **二阶调整**：连加速度都平滑修正，最看不出痕迹，数学也最重——适合慢节奏的飞机/机甲游戏。

—— 第7章《延迟、抖动和可靠性（讲义）》§7.6、第8章《改进的延迟处理（讲义）》§8.2 / §8.3
