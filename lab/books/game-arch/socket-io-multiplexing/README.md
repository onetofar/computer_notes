# 对照讨论：一个进程怎么同时伺候一堆连接（阻塞 / select / poll / epoll）

> **问题**：服务器同时有几十上百条连接。**在一条连接上没数据的时候，能不能不影响别的连接？**
> 四种做法，分别把代价付在了哪里？

> 本组是**用户态对照演示**：用纯 C++ 把四种就绪模型的语义与数据结构原样实现一遍，
> 不调用内核接口，所以**在任何机器上跑结果都一样**，也不会占端口或挂起进程。

## 对照表

| 文件 | 差异点 | 预期输出 |
| --- | --- | --- |
| `01-blocking-recv-model.cpp` | 阻塞式 recv：没数据就睡死 | 场景A 三轮下来 `完成 recv 0 次 ... 模拟帧数=0`；场景B 一次循环收满 5 条 |
| `02-select-readiness-model.cpp` | select：位图集合，一次问一批 | 第一轮返回 2 个，集合被改写成就绪子集 → `集合里只剩 2 个 fd`；忘重建 → `返回 0 个 -> 漏事件`；`fd=1024 放不进去` |
| `03-poll-readiness-model.cpp` | poll：数组 + 事件掩码 | `fd=5000 fd=5001 都能放进去`（无 1024 上限）；1 次系统调用 + 用户态遍历 5 项 |
| `04-epoll-interest-list.cpp` | epoll：内核长期保管兴趣表 | 水平触发第 2 轮仍报；边缘触发 `还剩 10 字节永远等不到(漏事件)` |

横向看：**select 把"挨个问"变成"一次性报一批"，但集合上限和每轮重建的代价都还在**；
poll 换掉位图换掉上限，没换来内核保管；
epoll 把这份兴趣表交给内核长期持有，于是省掉每轮重建——
代价是**边缘触发必须一次读到 EAGAIN**，否则事件就丢了。

## 教材原话（逐字引文）

> 默认模式下，`recv` 没数据就**睡在原地**。

> 你在 1 号连接上 `recv`，恰好它没发东西 → 整个线程睡死 → 2~5 号没人管、新连接没人接、**游戏模拟也停了**。

> 一个慢客户端就能冻住全服。

> - 配合主循环每帧轮询：游戏不卡了；
> - 但 socket 一多，挨个问一遍 = O(N) 次系统调用，大半是白问。

> 把"挨个问"升级成"一次性报一批"：

> 三个集合（可读/可写/出错）+ 一个超时。返回后用 `FD_ISSET` 挑出就绪的挨个处理。

> 注意 select 返回时**会把你传进去的集合改掉**（只留就绪的）——所以每次循环要重新 FD_ZERO/FD_SET，这是个经典坑。

> select 只是把 O(N) 白问变成"一次批量问"，集合上限、每次重建集合的代价都还在。Linux 上的答案叫 **epoll**——不过那是本书之外的故事了，而你自己的服务器已经在用它：

—— 第3章《伯克利套接字（讲义）》§3.6
