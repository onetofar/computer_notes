## 对象池 —— 从 valgrind 的泄漏清单长出来的组织方式

> 原文锚点：第 5 章「性能优化与对象池」§5.5（配 §5.2.2 刷新型数据结构）。
> 工具侧（valgrind/gprof 怎么用）属 §5.1/§5.3 的操作手册，本篇不展开；核心是池的**结构与生命周期纪律**。

### 0 动机：一个真实的泄漏现场

原文从 valgrind 的输出切入：login 进程里每次新账号登录都 `new` 一个 LoginObj，**用完从不释放**——泄漏清单直接指向 `LoginObjMgr::AddPlayer → Account::HandleAccountCheck` 的分配点。此前所有示例代码「为突出重点只创建不释放」——对象池就是把这笔欠账连本带利还清的组织方式。

定义一句话：**提前生成若干对象放池中，需要时取、不需要时归**——免去频繁的创建与销毁。原文还给了第二个动机：框架后期几乎所有对象都从池里走，池因此成为**内存中全部对象的监控点**（谁在用、谁空闲一目了然）。

### 1 结构：两个集合 + 一个刷新器

`DynamicObjectPool<T>` 管两个集合：

```cpp
std::queue<T*>   _free;          // 空闲对象（全局共享 → 操作要加锁）
CacheRefresh<T>  _objInUse;      // 在用对象（交给刷新型数据结构维护）
```

在用侧不直接用容器，而是 §5.2.2 的 **CacheRefresh 三队列**：

```
Add 队列 ──▶ Reader 队列 ──▶ Remove 队列
（对象被唤醒）   （稳定工作区）     （生命周期结束，待回收）
```

三队列的存在理由是**延迟应用**：遍历 Reader 的中途不许增删（遍历中修改容器是经典崩溃），Add/Remove 先排队，刷新点统一应用——和 epoll 事件增删延迟到帧尾是同一个模式（[[第2章 网络IO多路复用|2.2 epoll-Reactor工程纪律]] §4）。

### 2 生命周期契约：BackToPool

所有入池对象继承 `ObjectBlock`，核心契约是一个纯虚函数：

```cpp
class ObjectBlock : virtual public SnObject, virtual public IDisposable {
public:
    virtual void BackToPool() = 0;   // 归还前清空自身数据，怎么清由对象自己决定
protected:
    IDynamicObjectPool* _pPool;
};
```

**清空的责任下放给对象自己**——ConnectObj 归还时清收发缓冲、Packet 归还时清协议体，池不关心内部结构。这条契约把「复用对象残留上一任数据」这一整类 bug 变成了每个类的显式义务：**忘了清 = 下一任看到上一任的鬼魂**。

### 3 两个关键函数

- **`MallocObject(Targs...)`**：变参模板——每个对象唤醒时要的初始化参数不同，池透传给构造；`_free` 有就取，没有才 new；
- **`FreeObject(ObjectBlock*)`**：归还，进 Remove 队列等刷新点回收回 `_free`。

图 5-16 的状态机：`_free 4 格 / _objInUse 空` → Malloc 取一格 → `_free 3 格 / _objInUse 1 格` → FreeObject 归还 → 还原。**池的容量在峰值处定型**——稳态运行后 new 的次数趋近于零。

### 4 判据表

| 决策点 | 判据 |
|---|---|
| 什么进池 | 主循环里高频生灭的对象（连接、包、会话）；一次性对象不值得 |
| 清空责任 | BackToPool 由对象自己实现——池不做反射式清扫 |
| 在用集合 | 三队列延迟增删；遍历中永远不修改容器 |
| 加锁粒度 | `_free` 是跨线程共享 → 加锁；各线程的 CacheRefresh 独立 |
| 引入时机 | **先有 valgrind 证据再池化**——原文的顺序是工具发现问题、结构解决问题，不是上来就池化 |

一句话结论：**对象池 = 两个集合（_free 加锁、_objInUse 三队列延迟刷新）+ 一条契约（BackToPool 自清）；它同时解决性能（免 new/delete）与监控（全部对象有账本）两个问题——但引入的依据永远是性能工具的实测证据，不是直觉。**
