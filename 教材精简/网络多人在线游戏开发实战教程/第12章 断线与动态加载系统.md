# 第12章 断线与动态加载系统

> 本章处理全书架构的最后一块硬骨头:**断线**——分玩家断线与进程间断线两种;外加动态加载 System(不改 libserver 就能加新系统)。

## 12.1 玩家断线:一个连接断了,四处要打扫

玩家数据横跨 **3 个进程、4 种实体**:login 的 Account、game 的 Lobby 与 WorldProxy、space 的 World。断线协议 `MI_NetworkDisconnect` 由网络底层发往各线程,**每个实体各自处理自己那份**:

| 实体 | 断线动作 | 特别之处 |
|---|---|---|
| login·Account | 销毁玩家数据,**连带销毁 Redis 里的数据** | ⚠️ login 还有 HTTP 连接(平台验证用)——**先判 Socket 类型,只有 TCP 断线才处理** |
| game·Lobby | 移除玩家数据(最简单) | — |
| game·WorldProxy | 移除 + **转发断线协议给 space**(`SendPacketToWorld(MI_NetworkDisconnect, player)`) | 断线是**跨进程事件**:game 不私了,space 的地图世界必须知道 |
| space·World | 玩家从地图移除(真身在这) | — |

**机制要点**:①断线处理**按连接类型分**(HTTP 断线与游戏 TCP 断线是两回事,不判类型就误清验证中的玩家);②断线的传播是**显式转发**——WorldProxy 把事件沿链路推给 space,而不是让 space 自己超时(快且准);③**四处各自的清理互不依赖**,哪一处漏了,那一份玩家数据就成了跨进程的幽灵(第 10 章 Redis 里的登录态就是最典型的幽灵位)。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.2]] 的幂等握手 + [[第12章 玩家服务|第12章]] 的「断线由平台面兜住」对照:单进程时代断线是一个回调,分布式时代断线是**一次跨进程的分布式事务**——每个持有该玩家状态副本的进程都要参与清理。本章的策略是「立刻销毁」,四处打扫的清单是同一张。

## 12.2 进程间断线

进程之间的连接断了(game↔space、login↔appmgr)与玩家断线是两类:**前者要重连+状态对账**(第 10 章的全连接拓扑在此兑现——宕机立刻以断线协议暴露,而不是等发包失败);**后者按 §12.1 清单处理**。

## 12.3 动态加载 System

在不修改 libserver 的情况下**动态加载新的 System**(示例:给 space 加一个移动系统)。价值:框架库冻结,业务扩展走「注册新系统」——与第 6 章「业务差异 = 注册哪些实体」一脉相承,把扩展面进一步收窄到运行期。

## 章末判据

| 决策点 | 判据 |
|---|---|
| 断线清理 | 列出**所有持有该玩家状态副本的实体**,逐一处理;漏一处 = 幽灵数据 |
| 断线传播 | 显式转发给下游持有者(space),不靠下游超时猜 |
| 连接类型 | HTTP 断线与游戏 TCP 断线分开处理,先判类型 |
| 扩展 | 新 System 走注册,不动框架库 |

一句话结论:**分布式断线的本质是「一次隐式的跨进程事务」——把「谁持有这个玩家的副本」列成清单,断线协议逐站转发、逐站打扫;清单不全,幽灵数据就在你看不见的那个进程里过夜。**
