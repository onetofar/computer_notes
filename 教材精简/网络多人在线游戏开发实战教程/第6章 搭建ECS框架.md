# 第6章 搭建ECS框架

> **小节地图**:§6.1 一个简单 ECS 工程 / §6.2 基于 ECS 的 libserver / §6.3 login+robots 工程 / §6.4 YAML 配置 / §6.5 log4cplus 日志 / §6.6 总结——全章精读(工程细节收骨架)。

## 6.1 为什么需要 ECS:从一个空函数说起

ECS = Entity(实体)/ Component(组件)/ System(系统):实体容纳任意多组件,具备某组件便具有某功能,System 控制组件的动作。

**动机是一条具体的痛点**:旧框架里线程上的对象都继承 `ThreadObject`,必须实现 `Update()`——而 login 工程的 Account 类**根本不需要每帧更新**,只能写一个空函数。空函数 = 接口强迫对象声明它没有的行为。

解法:**动作变成接口**——`InitializeSystem` / `UpdateSystem` 各是一个接口,对象**按需实现**:需要初始化就实现前者,需要 Update 就实现后者。于是 UpdateSystem 只更新真正实现了该接口的对象(E2 和 C),Account 不再被迫空转。

**三类角色**(§6.1.1–6.1.2 的骨架):

```cpp
class Component {                    // 组件:SN 唯一标识 + 父指针
    virtual void Dispose() = 0;
    Entity* _parent;                 // 组件的父一定是实体;组件不能做组件的父
};
class Entity : ...                   // 实体:容纳组件(有组件即实体)
// System:InitializeSystem / UpdateSystem 等动作接口
```

原文自评:这不是 ECS 的最终模型,是**从面向对象过渡到组件式的折中方案**——价值在「为什么会变成这样」的过程,不在最终形态。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.1]] 的三层分叉(共享库/Server/Client)解决的是「同一份代码两端要的东西不同」;ECS 解决的是「同一份线程循环里对象要的节奏不同」——**两个方向都在消灭「被迫实现的空函数」**。Unity 的组件模型([[第11章 真实世界的引擎|第11章 §11.2.2]])正是本章思路的工业形态。

## 6.2–6.3 libserver 与 login/robots 工程(骨架)

- §6.2:把第 2–5 章的网络/线程/对象池代码重组成 **libserver 库**(ECS 化:Network/ThreadMgr 等变成实体+系统);
- §6.3:login(登录服务)与 robots(机器人)两个工程**共用 libserver**,各自只写自己的实体与协议处理——库与业务的边界自此成型。

**架构读法**:第 1–5 章的代码一直在「一个 demo 一个框架」地复制;ECS 之后,框架收敛成一个库,业务差异变成「注册哪些实体」。这为第 9–11 章的多进程(每个进程 = 同一库 + 不同实体组合)铺平了路。

## 6.4 YAML 配置

配置从硬编码/命令行迁到 **YAML 文件**(端口、线程数、路径等)。要点:读取一次、启动期生效;**配置项必须有单一来源**——与本项目「参数一律走 GameConfig/game_config.h」([[00-项目领读|00-领读]] L7)是同一条纪律的两种载体。原文顺便记录了 PyYAML 在该环境的可用性问题(本项目服务端后来也因此走 header-only 配置)。

## 6.5 log4cplus 日志

日志库引入:分级(TRACE→FATAL)+ 按格式输出。架构价值:**日志是框架级设施**,各实体直接调用而不是各自 printf——为第 9 章的「服务器管理进程」提供统一的可观测面。本项目的对应物是单行 JSON logger(`src/common/logger.cpp`),取舍不同(log4cplus 功能全 vs 单行 JSON 好解析),纪律相同:**日志走一个口**。

## 章末判据

| 决策点 | 判据 |
|---|---|
| 对象要不要进帧循环 | 实现了 UpdateSystem 才进;空函数 = 接口强迫对象撒谎 |
| 库与业务边界 | 业务差异 = 注册哪些实体;业务代码不复制框架 |
| 配置 | 启动期一次读、单一来源;运行时参数不散落 |
| 日志 | 框架级一个口;分级可开关 |

一句话结论:**ECS 在本书里不是教条,是「消灭空函数」的工程结论——把「对象有什么行为」从继承结构里解耦成按需实现的接口;框架自此收敛成一个库,后面所有的多进程故事都建立在这次收敛上。**
