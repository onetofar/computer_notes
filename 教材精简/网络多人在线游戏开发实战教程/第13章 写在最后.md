# 第13章 写在最后——如何构建自己的框架

> 全书方法论收尾。架构「没有衡量标准,难有对错之分」——你的架构可能性能更优,别人的开发速度更快;本书给的是**一条演化路径**(网络层→多线程→ECS→多进程),不是终点。

## 一个 1000 行函数的故事

一位策划拿到改数据的权限,却写出了**整整 1000 行**的技能伤害函数,主体是这种模式:

```cpp
if (player.hasPassiveSkill(123) && !player.hasBuff(321)) {
    player.addBuff(456);
}
```

千行 if,条件五花八门(技能 Id/角色 Id/BUFF Id/血量值)。**为什么它会坏掉**:321 与 456 号 BUFF 的效果一旦变化,这些代码全部偏离预期——**规则散落在没有结构的地方**。

## 线性思维 vs 规律思维

原文的诊断:初写者的通病是**线性思维**——「按轨迹寻求解决方案,遇到问题解决问题」;而程序设计是**分析问题的规律,找到较佳的方案**。同一问题见过越多处理方式,当前问题的更优解越容易成形——**认知来自源码量,不是语法量**。「学了语法就会编程」的代价:100 行能完成的工作写数倍,且不可维护。

**与本知识库的映射**:这个诊断正是「精简教材」这件事的理由——把书里的**规律形态**(判据、失效边界、机制链)从线性叙述里拆出来组织好,看的「同一问题的处理方式」才可计数。

## 对框架构建者的三条落点

1. **框架是演化出来的**:第 1 章阻塞 echo → 第 2 章 epoll → 第 6 章 ECS → 第 10 章多进程——每一步都是上一步痛点的直接回应(呼应 [[第3章 线程、进程以及Actor模型|第3章]]/[[第6章 搭建ECS框架|第6章]]);
2. **规则进数据,结构进代码**:千行 if 的反面教材与第 11 章 CSV 配置表是同一枚硬币——「有规律性」的问题交给数据与结构,不留给 if;
3. **没有对错,只有取舍**:性能 vs 开发速度是真实的设计自由度——先写判据([[第8章 深入学习组件式编程|第8章]] 的引入阈值思想),再选边。

一句话结论:**框架构建 = 识别问题的规律性 + 把规律放对地方(数据/结构/接口);思维差距的根源是「见过多少同问题的处理方式」——这正是读教材、拆判据的意义。**
