# 第6章 网络拓扑和游戏案例

> **小节地图**：§6.1 拓扑选型 / §6.2 权威 C/S 实现（机器猫行动）/ §6.3 对等实现（机器猫 RTS）——全章精读。
> 两大原型的定调在第 1 章（[[第1章 网络游戏概述]]）；延迟补偿见 [[第8章 改进的延迟处理]]。

## 6.1 网络拓扑：连接数与带宽的硬账

| | 客户端-服务器 | 对等网络 |
|---|---|---|
| 连接结构 | 星形：服务器 O(n)，客户端各 1 条 | 全互联：每个对等体 O(n−1) 条，全网 O(n²) |
| 带宽负担 | **全部压在服务器**（进 b×n / 出 c×n），客户端恒定 | 对称：每人上传=下载，随人数线性涨 |
| 延迟 | 客户端 A → 服务器 → 客户端 B = ½RTT_A + 处理 + ½RTT_B | 直连，最坏 ½RTT，无中介 |
| 权威归属 | 清晰：服务器即真相 | 模糊：通常全员共享命令、各自模拟（输入共享） |

带宽的结论容易被记反：客户端-服务器的服务器带宽**线性**涨，但每个客户端的带宽**基本不变**——这正是它可扩展的原因；对等网络把线性涨摊到每个人头上。而 C/S 的延迟代价（B 看到的是 A 的动作绕了一圈）是第 8 章全部补偿技术的动机。

**专用 vs 监听**（§6.1.1）：专用服务器无外设、与客户端进程完全分离，可在一台机器上跑多个进程；监听服务器由某个玩家的机器兼任——省部署成本，但**权威数据在玩家手里（可作弊）**、服务器断线即全场崩、主机迁移（host migration）要求客户端之间也有通信，是 C/S 与 P2P 的混合模型。原文还纠正一个常见误称：监听服务器不是对等网络，是「对等托管」——**仍然有一台服务器，只是恰巧由玩家托管**。

**权威的落地定义**：不是口号，是一条可执行判据（扔线球例子）——**客户端不能自己决定结果**。客户端通知服务器「我想扔线球」，服务器决定允不允许、命中与否；客户端发现本地状态与服务器不同，**以服务器为准更新自己**。代价是每个动作都有 RTT，收益是全体客户端共享同一份真相。

## 6.2 客户端-服务器的实现：权威骨架三件套

### 6.2.1 代码分离

权威模型直接决定代码结构——服务器和客户端要的东西不一样：

- **变量**：`mHealth` 服务器要（归零进重生），客户端也要（右上角 UI）——两边都存，但只有服务器那份是权威的，客户端的是**显示副本**；
- **函数**：分「仅服务器 / 仅客户端 / 共享」三类。

组织手段：共享库 + 两个可执行程序。`GameObject` 层次里每个游戏类三层分叉——共享基类 / `RoboCatServer` / `RoboCatClient`，用继承与虚函数分流（原文自评：性能不是最优，易用性最简单）。

### 6.2.2 入会状态机：重传免费

四步握手，两个四字符包类型：

```
客户端                          服务器
  │── HELO{名字} ──────────────▶│ 分配玩家ID、记录地址
  │◀───────────── WLCM{玩家ID} ─│
  │  （未收到 WLCM 就继续发 HELO） │ （收到已知地址的 HELO → 重发 WLCM）
```

它漂亮在**丢包处理是免费的**：WLCM 丢了 → 客户端继续 HELO → 服务器看到已知地址的 HELO 就再回一次 WLCM。两个包都是幂等的，**状态机 + 幂等 = 不需要任何显式重传协议**。配套两个细节：客户端限制 HELO 发送频率（检查距上次发送的时间）；处理包前先核对状态（welcomed 之后又收到 WLCM 不能让它产生效果——包会迟到但不会缺席）。

### 6.2.3 客户端代理与 Move 流：上行只有输入

权威模型下的上行流量被压到极致：**客户端不发任何对象复制命令，只发输入**。三种数据各走一条道：

```
服务器 ──STAT 状态包（对象复制：创建/更新/销毁）──▶ 客户端
客户端 ──INPK 输入包（Move 序列）──────────────▶ 服务器
```

**三层封装：InputState → Move → MoveList**

- **`InputState`**：某一帧的输入快照（例子里只有四向移动量 + 是否开火，两个 delta 辅助函数把「A+D 同按」归零）；
- **`Move`** = `InputState` + `timestamp` + `deltaTime`——时间戳是移动重放与 RTT 测量的原料（第 8 章的整套机制都建立在它上面）；
- **`MoveList`**：累积未确认动作，`AddMove` 用「上一个时间戳」算 delta，首个动作 delta 为 0。

原文的取舍：按帧上发 InputState 不现实，但例子里**不做帧间合并**——每隔 x 秒取当前 InputState 成 Move，图省事；真正的游戏会合并几个帧的输入再报。

**客户端代理（ClientProxy）**：**服务器用来跟踪特定客户端的对象**。收到的输入状态存进对应的代理，服务器每 tick 推进模拟时读所有代理里攒的输入。它实际是三样东西的合体：

1. **输入缓冲**——该客户端想干什么的时间线；
2. **复制账本的挂点**——按客户端分别决定「给谁发什么」（每个客户端的相关性集合不同）；
3. **延迟补偿的锚点**——第 8 章回退判定要用的「这个客户端当时看见什么」就从它的输入时间线推。

「按客户端一份」这个形状是权威服务器代码的通用模式：凡是「对世界一份」的东西（世界状态、碰撞）放全局，凡是「对每个客户端一份」的东西（输入、待确认、视野）放代理。

## 6.3 对等网络的实现：不发状态，只发命令

### 6.3.0 模型与主对等体

输入共享模型下，**每个对等体运行完整的世界模拟，对象不以任何方式复制**——网络上跑的只有「轮数据包」，内容是各对等体在该轮发出的命令列表。与权威模型完全相反的形状：

| | 权威 C/S | P2P 锁步 |
|---|---|---|
| 传输内容 | 状态（STAT）↓ / 输入（Move）↑ | 仅命令（轮数据包）↔ |
| 谁模拟真相 | 只有服务器 | **所有人各自模拟，必须逐位一致** |
| 代码组织 | 共享库 + 两个可执行 | **一个可执行**，所有对等体相同 |

带宽对等且与命令量成正比（通常远小于状态量）——这是 RTS 选它的原因；代价是把「状态一致性」从服务器的一个断言变成了全体机器的分布式共识问题。

**主对等体**解决两个竞争点：提供已知对等体的 IP 地址清单（对接游戏匹配服务只认一个地址）、**唯一**有权给新玩家分配玩家 ID（避免两个对等体同时迎接新玩家时 ID 撞车）。除此之外它与任何对等体行为一致——因为每个对等体都存有完整游戏状态，**主对等体断线游戏照常继续**（对比监听服务器的单点崩溃）。

**入会协议**（§6.3.1）比 C/S 多两种响应：HELO 的回包可能是 `WLCM`（欢迎，含玩家 ID + 全体名单与地址）、`NOJN`（已开赛/满员）、`NOMP`（你找的不是主对等体——附上主对等体地址，重定向）。收到 WLCM 还没完：新对等体要向**其余每个对等体**发介绍包 `INTR`——C/S 里「服务器知道你」就够了，P2P 里**每个人都要认识你**。

一个真实的坑：各对等体的地址表来自**收包时的来源地址**——局域网内的对等体会把 192.x.x.x 这样的私网地址写进表里发给外网玩家，对方永远连不上。解法是**集中服务器（rendezvous server）**：只做初始化阶段的地址交换，保证各方拿到的是公网可达地址；更彻底的变体是中央路由服务器（所有包经它转发），顺带获得「互不知晓对方公网 IP」的防 DDoS 属性。

### 6.3.2 锁步：命令在第 x 轮产生、第 x+2 轮执行

时间被切成固定小节（原文例子：30fps 锁定、33ms 子轮 × 3 = 100ms 一轮）。规则三条：

1. **命令 ≠ 输入**：只有影响游戏状态的输入产生命令（选中单位不算——它不改状态；移动/攻击算）。Command 是继承结构（基类持 `mNetworkId + mPlayerId`，纯虚 `ProcessCommand`），工厂函数 `StaticReadAndCreate` 按类型枚举建子类；
2. **本轮命令不执行**：每轮结束时把本轮命令列表发给所有对等体，**第 x 轮产生的命令在第 x+2 轮执行**——留出的 100ms 就是收包窗口；
3. **一致延迟不是坏延迟**：从命令产生到生效约 200ms，但它**恒定**，RTS 的操作粒度下无感。

双重验证是命令的纪律：`StaticCreate` 创建时验一次（对象存在、是猫、归我指挥），`ProcessCommand` 执行时**再验一次**——200ms 的时差里世界可能已经变了（命令指向的猫可能已死）。

**缺口检测**：网络管理器持有 `vector[轮号] → map[玩家ID → TurnData]`，每个对等体每轮交付自己的 `TurnData`（命令列表 + 随机数心跳 + 全局 CRC）。第 x+2 轮开始时查表：任一玩家的轮数据缺席 → 全体等待，谁也不推进——**锁步的本质就是「最慢的缺席者决定全局节奏」**。

**清单 6.11 的发送侧细节**：子轮计数到 3（一轮结束）→ 构造 `TurnData(mPlayerId, 随机数, ComputeGlobalCRC(), 命令列表)` → 包内写 **`mTurnNumber + 2`**（这批命令的执行轮号）→ 广播给所有对等体 → **本地先存自己的轮数据再清空命令列表**。**负轮号设计**：开局轮序号设为 −2——第 −2 轮发出的命令在第 0 轮执行，头 200ms 没有命令执行是**锁步回合制的固有属性**，无从避免。

**清单 6.12 的推进侧 `TryAdvanceTurn`**（「Try」是因为不保证能推进）：

```cpp
if (mTurnData[mTurnNumber + 1].size() == mPlayerCount) {
    if (mState == NMS_Delay) {
        InputManager::sInstance->ClearCommandList();  // 丢掉延迟期间积攒的输入
        mState = NMS_Playing;
        SDL_Delay(100);                               // 给慢对等体一个追赶窗口
    }
    mTurnNumber++;
    if (CheckSync(mTurnData[mTurnNumber]))
        for (auto& iter : mTurnData[mTurnNumber])
            iter.second.GetCommandList().ProcessCommands(iter.first);
    else
        Engine::sInstance->SetShouldKeepRunning(false);  // desync = 直接终局
} else {
    mState = NMS_Delay;   // 缺谁的轮数据就全体停
}
```

三个状态机细节：**延迟态攒的输入直接丢弃**（它们属于错乱的时间线，重放会扩大分歧）；恢复时 **SDL_Delay(100) 给慢对等体追赶窗口**；**CheckSync 失败不做任何挽救——直接结束游戏**。延迟态期间每收到新轮数据就重试 `TryAdvanceTurn`，直到缺口填满；若延迟中某对等体被重置移除，其余对等体继续（全员状态在手，这正是 P2P 的韧性）。

### 6.3.3 保持同步：两根支柱

所有人各自模拟，不同步的根源只有一类——**任何一处「相同的输入产生不同输出」**。

**支柱一：同步伪随机数（PRNG）**。确定性 = **同种子 + 同调用序**。两条纪律：

- 种子统一：主对等体在开始包里带一个种子，全体在第 −2 轮以相同种子重置；
- **调用次数、顺序、位置必须逐轮一致**——「几乎不能让不同版本的游戏用不同次数的随机数」（跨平台分支是天然的雷）。

而 C 的 `rand()/srand` **整体出局**：C 标准不规定算法，不同平台/编译器的实现可以是完全不同的序列——种子相同也没用，且熵质量无保证。替代：C++11 的 MT19937（梅森旋转，周期 2^19937），封装在 `RandGen` 单例里。

配套一个**每轮心跳校验**：每轮结束各对等体生成一个随机数放进轮数据包——任一方的 PRNG 序列跑偏，下一轮就对不上。以及一个反向纪律：**不影响游戏状态的随机**（比如模拟丢包测试）必须用**另一个生成器**——否则全体对等体会在同一时刻「随机」模拟出丢包。

**支柱二：全局检验和**。更隐蔽的不同步源：浮点运算**跨硬件不保证逐位一致**（SIMD 指令与标量结果可能不同、IEEE 754 严格模式可开关），加上程序员的无心之失。防线是**每轮结束算一次全局状态检验和**随轮包发送，逐轮比对——分歧当场暴露，而不是演变成「在玩不同的游戏」。

《机器猫 RTS》的实现：`ComputeGlobalCRC` 用 zlib 的 `crc32`（不重造轮子，且为大规模数据优化过）——每个游戏对象按**网络 ID 升序** `WriteForCRC` 写进比特流，最后对整个缓冲区算 CRC。**升序**是关键：遍历顺序不确定时，相同的世界也会算出不同的校验和，白白报警。

## 章末判据

| 决策点 | 判据 |
|---|---|
| 拓扑 | 连接数/带宽可中心化、需要统一裁决 → C/S；人数少、低延迟直连、可接受确定性工程 → P2P |
| 专用 or 监听 | 有预算/反作弊要求 → 专用；省成本可容忍作弊与断线风险 → 监听 |
| 上行发什么 | 权威模型下**只发输入**（Move 流）；发状态=客户端抢权威 |
| 握手协议 | 用「幂等包 + 状态机」拿到免费重传；别为入会单独发明可靠层 |
| 传输什么（P2P） | 只传命令——前提是模拟完全确定 |
| 随机数 | MT19937 起步；`rand()` 因跨平台算法未定义出局；非游戏随机独立生成器 |
| 同步校验 | 每轮双保险：PRNG 心跳值 + 全局 CRC（对象按 ID 升序写入） |

一句话结论：**权威路线 = 单向状态流 + 单向输入流 + 每客户端一个代理对账；锁步路线把「一致性」从运行时裁决换成了构造时纪律（确定性代码 + 种子/调用序/遍历序全约束），再用每轮 CRC 对账兜底——命令少而一致延迟恒定是它的红利，「同种子同调用序」是它的税。**
