## 云托管专用服务器 —— 「每局结束重启进程」治一切

> 原文锚点：第 13 章「云托管专用服务器」§13.1–§13.5。
> 上游：[[第9章 可扩展性]]（分区调度的 infra 答案）；[[第10章 安全性]]（防作弊与 DDoS 的落地环境）。

### 0 托管与否：五弊三利的账

云把「买硬件赌人数」的时代送走了（高估→机器闲置；低估→付费玩家连不上→差评）。剩下的账：

| 弊 | 利 |
|---|---|
| 复杂度：仍要自写进程/VM 管理代码、追着云 API 变化跑 | 可靠可扩展：需要时按需开，上行带宽不再赌玩家谁在线 |
| 成本：非免费，兴趣未必覆盖 | **防作弊**：服务器版本由你控制，排名/进度可信（[[第10章 安全性]] §2 的「不让玩家主持」） |
| 依赖第三方：全服同时宕机时 SLA 安慰不了用户 | **事实 DRM**：不发服务器可执行文件，破解服无从架起 |
| 意外硬件改动：规格以上随便换，没测过的配置可能出问题 | |
| 丧失玩家所有权：自定义服务器社区(Minecraft 式)的种子玩家没了 | |

### 1 行业工具三件套（§13.2）

REST（HTTP 动词的一贯语义，自包含请求 = 天然可调试）+ JSON（比 XML 少标签、可直接粘进 JS 调试）+ Node/Express（单线程事件循环 + 异步作业，无竞争条件地处理并发 REST 请求）。工具可换，概念不变——它们只是本章管理器的粘合剂。

### 2 术语金字塔（§13.3）：四层，别混着说

```text
服务器游戏实例   一场 16 人战役（比赛安排眼里的一场比赛）
 ⊂ 游戏服务器进程  OS 层面的进程；可以承载多个实例
   ⊂ 游戏服务器(机器)  一台机器跑多个进程
     ⊂ 硬件/VM      云上机器镜像 = 虚拟机，与其他租户共享物理机
```

三个关键取舍：

- **进程内多实例**：共享不可变大资源（碰撞几何/导航网格/动画），省内存、更新调度更细——但一崩全崩、测试覆盖出现无人走过的路径。**主流选择仍是单进程单实例**；
- **一机多进程**：单机单进程浪费（OS 自身吃掉大量资源），现代 OS 受保护内存保证进程崩溃不互相传染——**通常跑到性能上限**；
- **VM 的意义**：云供应商用它切分硬件（16 核跑 4 个 4 核租户，闲了关两个再塞别人 8 核）+ 硬件故障时整机镜像迁移。低价方案共享硬件会睡眠 → 性能不稳；高价方案指定物理配置。

**架构纪律**：比赛安排服务与部署系统**分离**——部署系统启好服务器后只是向安排系统注册自己，之后匹配归安排系统管（第三方匹配如 Steam/Xbox 可能是平台强制的，[[第12章 玩家服务]]）。

### 3 LSPM：本地服务器进程管理器（§13.4）

每台 VM 上跑一个 LSPM（Node/Express 实现），职责三件事：**听命令生成进程、记账（machineState: empty/partial/full/shuttingDown）、盯心跳**。心跳机制是全章的核心模式：

| 参数 | 值 | 语义 |
|---|---|---|
| `gMaxStartingHeartbeatAge` | **20s** | starting 态的宽限——初始化慢的进程不被误杀 |
| `gMaxRunningHeartbeatAge` | **10s** | running 态超时 = 挂起/僵死 → LSPM 主动 kill |
| `gHeartbeatCheckPeriod` | **5s** | 检查周期（进程侧心跳发送频率 ≥ 此值） |

进程侧就是一句 C++：往 LSPM 端口发一条 HTTP POST（裸 TCP 发字符串都行，或用 C++ REST SDK）：

```text
POST /api/processes/<uuid>/heartbeat HTTP/1.1
```

心跳一收，状态从 starting 转 running；超时即杀，杀掉后由关闭事件从账本删除。

### 4.5 VMM：虚拟机管理器（§13.5）——同一套模式再套一层

LSPM 只管本机进程，「提供机器本身」是 **VMM** 的活：跟踪所有 LSPM、按需让 LSPM 生成进程、启动/关闭 VM。要点四个：

- **VMI（虚拟机镜像）**：引导盘的全部内容——OS + 游戏服务器可执行文件 + LSPM + 初始化脚本。云供应商各有自己的 VMI 格式与创建工具；VMM 代码里要**把供应商 API 抽象出来**（你可能要换供应商或多地区多供应商）；原文的注释预言了标准化方向：Docker 容器格式；
- **机器状态机比 LSPM 多两态**：`empty / partial / full / **pending** / shuttingDown / **recentLaunchUnknown**`——后两态处理云的现实：VM 启动慢（pending）、刚下发启动命令但结果未知（recentLaunchUnknown）——**分布式调度必须给「未知」留状态**；
- **可用 VM 索引**：`gAvailableVMs` 只收 `partial` 状态的机器（有空位）——`updateVMState` 在进出 partial 时维护这个索引，调度时 `getFirstAvailableVM` 直接取；
- **同样的竞争条件战场**：Node 单线程但「请求者→VMM→LSPM」的异步链 + TCP 上每个 REST 请求独立连接 = **乱序到达是常态**——状态机与心跳超时是唯一防线。

结构上 VMM 与 LSPM 完全同构：心跳、状态记账、超时清理——**LSPM 管进程对 VMM 汇报，VMM 管机器对云端汇报，两级心跳金字塔**。

### 4.6 为什么「每局结束重启进程」是底线动作

即使是最精心设计的游戏，**发布期带着少量内存泄漏上线是常态**。治法不是修完再发：

> **每次比赛结束就关闭并重启服务器进程**——泄漏不积聚、游戏状态重置不当的问题一并消失。

配合 LSPM 的心跳监控，这套机制让「进程随时可以死」成为系统假设——而死进程的重建是 LSPM 的本职。VMM 层（§13.5）用完全相同的模式再套一层：**每个 VM 跑一个 VMM**，与中心调度器用 REST/JSON 通信、同样按机器状态记账、同样用心跳超时判 VM 死活——LSPM 管进程对 VMM 汇报，VMM 管机器对云端汇报，**同构的两级心跳金字塔**。

### 5 判据表

| 决策点 | 判据 |
|---|---|
| 托管与否 | 要排名可信/防作弊/DRM → 专用服务器；预算极低且可容忍玩家托管 → 监听 |
| 进程:实例 | 默认 1:1（崩溃隔离+可测试）；共享大资源压力极大才考虑 1:N |
| 机器:进程 | 跑到性能上限（OS 是固定开销，摊薄它） |
| 监控 | 两级心跳同构：进程→LSPM(20/10/5s)，VM→VMM→云 |
| 泄漏 | 不追求修完再发——每局结束重启进程，把泄漏封顶在单局内 |
| 部署与匹配 | 分离：部署系统只管开/关，注册后匹配归安排系统 |

一句话结论：**云托管把「买硬件赌人数」换成「写管理代码赌健壮性」——LSPM/VMM 两级同构心跳金字塔保证进程随时可死可生，而「每局结束重启」是整个体系的地基纪律：它把内存泄漏、状态污染、长尾劣化全部封顶在一局之内。**
