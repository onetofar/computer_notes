## 玩家服务 —— 把平台能力隔离在一层后面

> 原文锚点：第 12 章「玩家服务」§12.1–§12.4。案例：机器猫 RTS 接入 Steamworks。
> 前置：[[第6章 网络拓扑和游戏案例]]（被改造的入会/启动流程）。

### 0 pImpl：整章的第一设计决策

接入 Steamworks 最差的写法是「哪里需要哪里调」——Steamworks 代码撒满全工程，每个开发者都得懂它，**换平台（移植到 PlayStation Network）时处处是手术**。正解是**指向实现的指针（pImpl）**：

```cpp
// GamerServices.h —— 看不见任何 Steamworks
class GamerServices {
public:
  // ...
private:
  struct Impl;                    // 前向声明
  std::unique_ptr<Impl> mImpl;    // 实现细节全藏在 .cpp 里
};
```

Steamworks 的全部调用只活在 `GamerServicesSteam.cpp` 一个文件里；接 Xbox Live 就加一个 `GamerServicesXbox.cpp`，**其余代码理论上零修改**。性能批注原文给得很准：pImpl 每次调用多一层指针引用，渲染设备那种高频类扛不住，但 GamerServices 每帧没几次调用——**灵活性值得这点开销**。功能多了别堆在一个类里，按域拆（如 GamerServiceSocket 对标 TCPSocket）。

**初始化顺序有个隐蔽约束**：`SteamAPI_Init` 必须在渲染器初始化**之前**——Steam 的 overlay（游戏内叠加聊天/浏览器）挂钩 OpenGL，渲染先起来 overlay 就废了。配套三件事：开发期用 `steam_appid.txt` 免 Steam 客户端启动（但客户端进程仍须登录着）；异步回调靠每帧调 `SteamAPI_RunCallbacks` 驱动；多账号测试必须多台机器/虚拟机（一台机器跑不了两个 Steam 实例）。

### 1 玩家 ID：平台已经发过了，别再发明

旧版机器猫 RTS 里主对等体给玩家分配 uint32 ID——接 Steamworks 后这段代码**整体删除**：每个玩家已有服务发的唯一 ID（`CSteamID`，可转 uint64）。改动是把玩家 ID 类型换成 uint64、初值来自 `GetLocalPlayerId()`。原文的边界提醒：**uint64 是 Steam 的实现细节不是通例**——有的服务用 128 位 UUID，真要跨平台就得再包一层 `GamerServiceID`。玩家名字同理直接用 Steam 的 persona，不再让玩家手输。

### 2 大厅与比赛安排（§12.3）：入会协议外包

第 6 章那套 HELO/WLCM/INTR 入会代码被**整体删掉**——Steam 大厅提供了更丰富的等价物。标准流程四步：

```
按参数搜大厅 → 无则建、有则加入 → 大厅内配置/聊天/等人 → 开赛离厅（建 P2P 会话或连服务器）
```

实现模式是 Steamworks 通用的异步三板斧：`SteamAPICall_t`（异步句柄）→ `CCallResult` 绑定回调 → 回调里先查 `inIOFailure` 再分支（找到就进、没找到就建）。**「唯一入口」的入会协议从此不是你的问题**——搜索过滤（游戏名/技能段）、创建、加入、广播全在平台上。

### 3 Steam P2P（§12.4）：只认 ID，不认 IP

`SendP2PPacket(toPlayer, ...)` 的签名里**没有任何 IP 地址**——只收 Steam ID。这不是隐私洁癖，是一石二鸟：

1. 用户 IP 永不暴露给其他用户；
2. **NAT 穿越整个外包给 Steam**：能打洞就打洞，打不通走 Steam 中继服务器——只要对方在线，包就有路（对照 [[第6章 网络拓扑和游戏案例]] §1 的 rendezvous 服务器：那是自建中继，这是平台送）。

传输模式四档（可靠 1MB 自动分片 / 不可靠 / 假定已连的不可靠 / Nagle 缓冲的可靠——又是 [[第1章 网络游戏概述]] 四类数据的平台版）。两个运行时纪律：

- **首个包要几秒**——Steam 在两端之间协商路由；对方还要**接受会话请求**（回调里校验「这人确实在本局」再 Accept，防骚扰包）；
- 会话失败回调 → 直通 `HandleConnectionReset`，对等体掉线统一走这条。

### 4 就绪握手：把建联成本移出开局

因为首个包要几秒，启动流程必须改造——直接开赛 = 第 0 轮数据全体迟到几秒 = 开局即卡：

```
主对等体按回车 ──▶ 不倒计时，广播「就绪」包
每个对等体收到就绪包 ──▶ 向其余对等体广播自己的就绪包
                          （全体两两会话建立中……）
主对等体收齐全体就绪 ──▶ 广播「启动」→ 倒计时 → 开赛
```

**就绪状态的存在意义**：在开赛前把「几秒的路由协商 + 会话请求接受」全部消耗掉——建联成本移出开局，倒计时才开始算真时间。没有这一步，锁步照转但第 0 轮人人卡几秒。

### 5 §12.5–12.8 玩家统计/成就/排行榜：API 目录 + 一个真机制

统计/成就/排行榜是平台 API 的目录性功能（Steamworks 侧：统计与成就的定义在合作伙伴网站上配置，代码里按 **API 名称字符串**调用），本节只收一个真正有机制含量的技巧——**X 宏**：

**三种统计类型**：整数 / 浮点 / **平均率（AVGRATE）**——滑动窗口平均，更新时提供「值+区间」，Steam 自动重算；即使玩家玩了很久，「每小时黄金数」这类统计仍会明显变化。

**X 宏解决的问题**：同一份统计清单要同步出现在**枚举、API 名称字符串数组、脚本**三处——手改三处必然漂移。解法是把定义收敛到一个 `Stats.def` 文件：

```text
STAT(NumGames,INT)
STAT(FeetTraveled,FLOAT)
STAT(AverageSpeed,AVGRATE)
```

```cpp
enum Stat
{
  #define STAT(a,b) Stat_##a,     // ## 拼接:STAT(NumGames,INT) → Stat_NumGames
  #include "Stats.def"            // def 文件被宏展开"复制粘贴"进枚举
  #undef STAT
  MAX_STAT                        // 白赚一个总数
};
```

**一处定义、处处展开**——统计清单变更只改 def 文件，三处同步错误从结构上消失。这条技巧的价值超出统计本身：**任何「枚举 + 字符串 + 元数据」三联表都可以用 X 宏收敛**（协议消息 ID 表是下一个现成场景）。

### 6 判据表

| 决策点 | 判据 |
|---|---|
| 平台代码放哪 | pImpl 单文件隔离；高频路径不用 pImpl |
| 初始化时机 | 平台 overlay/钩子依赖什么，就先于它初始化 |
| 玩家 ID | 用平台发的；类型按平台封装一层再进自己的代码 |
| 入会协议 | 有平台大厅就外包；自建 HELO/INTR 只在无平台时写 |
| P2P 地址 | 只认平台 ID 不认 IP——NAT/中继是平台的责任 |
| 开局节奏 | 建联成本（路由协商/会话接受）必须在就绪阶段消耗完 |
| 多处同步的清单 | X 宏收敛到单一 def 文件（统计/成就/消息 ID 表通用） |

一句话结论：**玩家服务层的全部价值在「边界画对」——pImpl 把平台锁进一个 .cpp，平台 ID 顶替自造 ID，大厅顶替入会协议，平台 P2P 顶替 NAT 穿越；你自己的代码里剩下的只有就绪握手这一件事：在开局前把平台会话建完。**
