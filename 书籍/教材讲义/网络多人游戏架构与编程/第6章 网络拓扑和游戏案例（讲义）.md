## 0. 开局：两条完全相反的路

多人游戏要把几台机器连起来，只有两种根本不同的连接方式，而且它们的世界观是**反的**：

- **客户端-服务器（C/S）**：选一个人当裁判，其他所有人都是**显示器**。你的电脑只负责两件事：告诉服务器"我按了前进键"，然后把服务器告诉你的一切画出来。**真相只有一份，在服务器手里。**
- **对等网络（P2P）**：没有裁判。每个人电脑里都跑着**完整的世界模拟**，网络上只传递"我打算做什么"（命令），不传"世界是什么样"（状态）。**真相有 N 份，全靠大家算得一模一样。**

一个靠中心权威，一个靠全员纪律。这一章就是把这两条路各自走到能玩，你会发现每一处设计都是从这两个世界观里**必然长出来的**。

## 1. §6.1 选拓扑：先算两笔账

### 你进了一个 8 人的房间

**连接数账**：

```
C/S 星形                          P2P 全互联
        服务器                    1─2  1─3  1─4
      ╱  │  ╲                     1─5 ... 每人 7 条线
     7 个客户端各 1 条             全网共 8×7÷2 = 28 条
8 条连接                           28 条连接
```

P2P 的连接数是 **n(n−1)/2**——人数翻倍，连接数大约翻 4 倍。

**带宽账**（这笔账的结论最容易被记反）：

- C/S：服务器的带宽**随人数线性涨**（8 个人的进出流量全过它的手），但**每个客户端恒定**（只连服务器一条线）——这就是它**可扩展**的原因：加人只苦服务器，不苦玩家；
- P2P：把"线性涨"**摊到每个人头上**——8 人房间里，你的上传 = 把你的动作发给其他 7 个人。人人平等地苦。

**延迟账**：C/S 里 A 的动作要 A→服务器→B 绕一圈，P2P 直连。这是 C/S 交的税，也是第 8 章一整章"延迟补偿"存在的原因。

### 监听服务器：省钱的混合体

专用服务器要租机器、要运维。省钱的办法：**让某个玩家的电脑兼任服务器**（监听服务器）。代价三个，一个比一个疼：权威数据在玩家手里（**开挂的是服务器本身**）；他一断线全场崩；他退出还得"迁移主机"。原文特别纠正一个误称：监听服务器**不是**对等网络——它仍然有一台服务器，只是恰巧被玩家托管了。

### 「权威」不是口号，是一条可执行判据

扔线球的例子最清楚。客户端点"扔球"后：

1. 客户端对服务器说：**"我想扔球"**（申请，不是执行）；
2. **服务器**决定扔不扔得出去、砸没砸中；
3. 客户端发现本地演的结果和服务器说的不一样？**以服务器为准改自己**。

判据就一句话：**客户端不能自己决定结果**。代价是每个动作都要等一个来回（RTT），收益是所有人共享同一份真相。

## 2. §6.2 权威服务器落地：机器猫行动

### 2.0 先看全图：两条路上各跑着什么 ⚠️（高频困惑点）

读到这里很容易冒出一个疑问：客户端发的是"我想干什么"，P2P 对等体发的也是"我想干什么"——**那 C/S 和 P2P 的区别到底在哪？**

你的观察完全正确：**两边上行跑的都是"意图"，区别全在回程**。

```
C/S（机器猫行动）：
  上行  客户端 ──输入：按了什么键（INPK，很小）──────────▶ 服务器
  下行  客户端 ◀──状态：每只猫在哪、多少血、谁出现谁消失（STAT，大头）── 服务器
        客户端不跑世界模拟，收到结果直接画

P2P（机器猫 RTS）：
  对等体 ◀──命令：我打算干什么（轮数据包）──▶ 对等体
        没有下行！世界状态从未上过网，每台机器自己算出来
```

判别式一句话：**看网络上传没传过"世界现在是什么样"**。C/S 传（服务器→客户端，单向）；P2P 永远不传。

一个厨房类比（推演）：C/S 是点外卖——你下订单（输入），店里的厨房做好**成品**送上门（状态），你不会做菜也能吃；P2P 是发菜谱——每人照同一份菜谱（命令）在自家厨房做菜，**菜从不快递**——所以每家厨房必须一模一样（确定性），差一点都不行（§3.5 两根支柱存在的全部原因）。

### 2.1 为什么客户端只发输入？

先做个反事实。假设客户端连"猫的位置"都自己说了算：A 说猫在 x=10，B 的电脑收到时已经晚了 100ms，B 也按自己的理解说猫在哪——**两台显示器开始打架**，服务器沦为一个仲裁外挂。

权威模型的釜底抽薪：**客户端对世界只有一个权利——提需求**（"我按了前进"），裁决权全部上收。于是上行流量天然只剩输入。这就是"上行只有输入"六个字的全部由来，不需要背。

### 2.2 代码怎么分：RoboCat 三兄弟

服务器和客户端要的东西不一样（血量：服务器要拿它判死亡，客户端只要拿它画血条），所以同一个游戏对象分成三层继承：

```
RoboCat（共享：两端跑同一份移动模拟）
 ├── RoboCatClient（仅客户端：画自己、读键盘）
 └── RoboCatServer（仅服务器：消费输入、做权威裁决）
```

**认端口的口诀**：类名无后缀 = 两端共用；`×××Client` = 仅客户端；`×××Server` / `ClientProxy` = 仅服务器。

### 2.3 入会握手：丢包处理是免费的

UDP 不可靠，但入会握手（HELO → WLCM）**不需要写任何重传代码**：

```
客户端                              服务器
  │── HELO{我的名字} ─────────────▶│ 分配玩家ID
  │  （没等到 WLCM？继续发 HELO）    │
  │◀──────────── WLCM{你的ID} ─────│
```

妙在哪：WLCM 丢了 → 客户端反正会**再发** HELO → 服务器一看"这地址我认识"，**再回一次** WLCM 就行。两个包都幂等（发多少遍效果一样），**状态机 + 幂等 = 重传机制白送**。

### 2.4 客户端代理：服务器给每人开的档案袋

服务器同时伺候 32 个客户端，怎么记住"谁交了什么作业"？**给每人开一个档案袋**（ClientProxy）：

- 收到的输入塞进袋子（**输入缓冲**：这个玩家想干什么的时间线）；
- 袋子决定给他发哪些状态（视野内的才发——**复制挂点**）；
- 袋子记下"他当时看见什么"（第 8 章延迟补偿回放用的就是它——**补偿锚点**）。

一个通用形状值得记住：**对世界一份的东西**（世界状态、碰撞）放全局；**对每个客户端一份的东西**（输入、待确认、视野）放档案袋。

### 2.5 一个类，两份实例，两种身份 ⚠️（高频困惑点）

`MoveList` 在两端都存在，但身份完全不同：

| | 客户端那份 | 服务器那份（藏在档案袋里） |
|---|---|---|
| 语义 | **待发货**队列 | **待消费**队列 |
| 谁往里放 | 键盘采样 | 网络收包 |
| 清空时机 | 发出后（第6章版，不可靠） | 模拟消费完 |

同一个类、两种人生。第 8 章的改造（客户端保留到服务器确认为止，才能重放）改的就是客户端那份的身份。

### 2.6 原文没画的那条路：输入包怎么找到它的档案袋 ⚠️（原文叙述断层）

原文清单 6.6 演示到客户端 `SendInputPacket` 就停了，服务器收包侧一个字没给。这条路（源码补注，见原书 `NetworkManagerServer.cpp`）是：

```
客户端发出：[kInputCC 包类型标记 | 2bit 条数 | N 条 Move]
                │ UDP 数据报（注意：里面没有任何"我是谁"字段！）
                ▼
服务器 ProcessPacket(fromAddress)
  │ 用【数据报的源地址】查哈希表 mAddressToClientMap
  │ → UDP 无连接，源地址本身就是身份证明
  ▼
找到对应的 ClientProxy（档案袋）
  ▼
HandleInputPacket：逐条反序列化 Move，AddMove 进袋
  ▼
服务器每 tick 从袋里取输入 → RoboCatServer::Update 消费
```

两个要点：**`kInputCC` 是分拣器**——所有包共用一个端口，靠头部第一个字段分拣到不同 handler；**源地址即身份**——这就是"客户端代理"这个名字的由来：服务器对该客户端的一切认知，都从这个地址索引进门。

### 2.7 教材清单 6.4–6.8 归属表 ⚠️（原文按数据流叙述，不标注哪端）

| 清单 | 类 | 归属 | 谁在动它 |
|---|---|---|---|
| 6.4 | `InputState` | 共享 | 客户端写，服务器读 |
| 6.5 | `Move`（InputState+时间戳） | 共享 | 客户端创建，服务器读 |
| 6.6 | `MoveList::AddMove` + `SendInputPacket` | 共享类 / **客户端侧**代码 | 客户端入队、发送 |
| 6.7 | `ClientProxy` | **纯服务器** | 服务器收包时写 |
| 6.8 | `RoboCatServer::Update` | **纯服务器** | 服务器消费输入 |

另有一个隐蔽细节：清单 6.8 里 `ProcessInput(deltaTime, currentState)` 用的是 **Move 自带的 deltaTime**，不是服务器帧时长——因为服务器一个 tick 可能收到一堆积压的 Move，逐条按各自的步长重演，才能复现客户端当时的轨迹。

## 3. §6.3 锁步 P2P：齐步走

### 3.1 为什么 RTS 不传状态？

反事实：一场 RTS 有 500 个单位。若走状态复制路线，服务器每帧要算并广播 500 个单位的位置、朝向、血量……而 P2P 锁步只传**命令**："3 号玩家命令 5 号单位向东北移动"。带宽对等且极小——**这就是 RTS 选锁步的原因**。（精确一点：C/S 的状态是**存在的**，只是只从服务器流向客户端；锁步是把这条下行流也整个砍掉，见 §2.0 的全图。）

但天下没有免费的午餐：每人电脑里都跑着完整模拟，"状态一致"从服务器的一条断言，变成了**全体机器必须算出逐位相同结果**的分布式共识问题。所以锁步的一切设计都围绕一句话：**相同的输入序列，必须产生相同的输出**。

### 3.2 锁步怎么走：命令晚两轮生效

时间切成 100ms 一轮（10 轮/秒）。规则：

1. 每轮结束时，把你这轮产生的**命令列表**广播给所有人；
2. **第 x 轮产生的命令，第 x+2 轮才执行**——留出的 200ms 就是收包窗口；
3. 进入第 x+2 轮前，先确认**所有人**的第 x+2 轮数据都到齐了，缺谁的就全体等。

三条里最反直觉的是第 3 条：**节奏由最慢的缺席者决定**。快的人陪慢的人等——这就是"锁步"（lockstep，齐步走）的字面意思。200ms 的命令延迟听起来很糟？但它**恒定**——RTS 的操作粒度下，恒定的延迟无感，忽快忽慢才致命。

### 3.3 双钟：渲染一个钟，模拟另一个钟 ⚠️（原文一句带过）

**现象**：低配电脑玩锁步游戏，画面变卡，但游戏不乱——只是整体变慢，且所有人进度依然一致。

**因为渲染和模拟是两个钟**。渲染是放电影的：好机器 33ms 一帧，破机器 50ms 一帧，随缘。模拟是下棋的：它不看放映机转速，**每放一帧固定走 1/3 步棋**（一个 33ms 子轮，3 个子轮凑成 100ms 一轮）。放映机慢了，棋也走得慢——游戏整体变慢，但棋谱和谁都一样。

反过来想就明白为什么必须如此：如果模拟步长跟着各自机器的实际帧耗时走，8 台机器同样的命令会推出 8 条不同的时间线——**确定性当场死亡。固定步长是锁步的前提，慢是它交的税。**

### 3.4 开局倒计时的骗局：发令枪声要飞一段时间 ⚠️（源码补注级细节）

主机按回车 → 广播 STRT 包 → 各自 3 秒倒计时归零开赛。听起来公平，其实**倒计时是在每台机器本地跑的，而发令枪声（STRT 包）要飞一个单程延迟 d 才到达别人耳朵里**：

```
墙钟时间        主机                        Peer A（RTT=100ms，d=50ms）
t₀             发 STRT，倒计时 3.00s 开始
t₀+50ms                                   才听到枪响，倒计时 3.00s 开始
t₀+3.00s       开赛 ✅                    （还差 50ms）
t₀+3.05s                                  开赛 ⏰ 晚了
```

补偿：让 Peer A 的倒计时**剪短 50ms**（2.95s），两头正好抵消，同一瞬间开赛。为什么是"RTT 的一半"？因为单程延迟没法直接测（UDP 包里没有时钟），只能拿可实测的 RTT/2 当估计值——NTP 等时钟同步协议同款假设。离主机越远剪得越多；主机自己剪 0。

那不补偿会出大事吗？不会——锁步兜着底（命令晚两轮执行、收齐包才推进），主机的"先开赛"只是开局头几轮**干等**别人。所以原文说这是"更好地同步"而非"完全同步"：RTT/2 假设了去程=回程，路由不对称时还有残差。

### 3.5 确定性的两根支柱

大家各算各的，不同步的根源只有一类：**任何一处"相同输入产生不同输出"**。书里布了两道防线。

**支柱一：同步伪随机数**。游戏里到处是随机（暴击、AI 决策），要让所有人"随机"得一样，必须**同种子 + 同调用序**：

- 主机在开始包里带一个种子，全员开局统一重置；
- 每轮每人生成一个随机数放进轮数据包当**心跳**——谁的随机序列跑偏，下一轮就对不上（哨兵）；
- C 的 `rand()` 整体出局：C 标准根本不规定算法，Windows 和 Linux 的 `rand()` 可以是完全不同的序列——**种子相同也没用**。替代：C++11 的 MT19937。

**支柱二：全局校验和**。更隐蔽的敌人：浮点运算**跨硬件不保证逐位一致**（SIMD 与标量结果可能不同）。防线：每轮结束把整个世界状态算一个 CRC，随轮包发送，逐轮比对——分歧当场暴露，而不是演变成"大家在玩两个不同的游戏"。

实现上有个容易踩的坑：算 CRC 时对象必须**按网络 ID 升序**写入——否则遍历顺序一变，相同的世界也算出不同的校验和，警报白响。

**分歧了怎么办？** 不挽救，直接终局（源码里 `CheckSync` 失败就退出游戏）。因为锁步下任何分歧都意味着两边已经活在不同的世界里，没有"就近修正"的可能。

## 5. 判据速查

| 你在纠结 | 判据 |
|---|---|
| 选 C/S 还是 P2P | 要统一裁决、可中心化 → C/S；人数少、要低延迟直连、养得起确定性工程 → P2P |
