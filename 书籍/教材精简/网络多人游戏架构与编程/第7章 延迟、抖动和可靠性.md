## 7.1–7.3 延迟、抖动与丢包：三份账单

### 各类游戏的延迟容忍度（§7.1 开篇）

延迟 = 从可观察的原因到看到结果之间的时间。三档基准：

| 游戏类型 | 延迟上限 | 原因 |
|---|---|---|
| VR | **< 20ms** | 头转了眼睛就期望看到新画面 |
| 格斗/FPS/快节奏动作 | 16–150ms | 输入与响应强耦合 |
| RTS | 可达 500ms | 操作粒度粗（锁步能成立的前提之一，[[第6章 网络拓扑和游戏案例|第6章]]） |

### 非网络延迟：Carmack 的著名抱怨

「我给欧洲发送一个 IP 数据包都比向屏幕发送一个像素还快」——**网络不是延迟的主要来源**。五类本地延迟，多数不可控：

| 来源 | 机制 | 量级 |
|---|---|---|
| **输入采样** | 帧首采样：按下按钮的时刻错过采样点就要等一帧 | 平均**半帧** |
| **渲染流水线** | CPU 发命令 → 驱动入队 → GPU 稍后执行 → 下一帧才显示 | **1 帧** |
| **多线程渲染** | 模拟线程与渲染线程各差一帧 | **再 +1 帧** |
| **垂直同步** | 帧耗时哪怕超 1ms，也要等下一个垂直消隐（1/60s） | **最多 +1 帧** |
| **显示延迟** | HDTV/LCD 的去隔行、缩放、降噪等图像处理 | **几十 ms**（「游戏模式」可缓解但不默认开） |

加起来，单机游戏屏幕上就背着 3–4 帧的固有延迟。多人联机能优化的只有网络那份。

### 网络延迟的四种成分（§7.1.2）

1. **处理延迟**：路由器读包头、查路由表、转发。现代路由器快，量最小；
2. **传输延迟**：把比特写进物理介质的时间，由链路带宽决定。**在互联网边缘最大**——终端用户的接入链路是瓶颈；
3. **排队延迟**：包到达快于处理速度时在队列里等。突发流量直接推高它；
4. **传播延迟**：光速上限，0.3ns/m——**穿美国至少 12ms**，物理定律，只能挪服务器。

可操作的优化，按成分对号入座：**发大包**（1400B 一个包与 200B 七个包经历同样的处理延迟，后者还要多等六次）；**服务器离玩家近**；Riot 为《英雄联盟》自建全美骨干网是极限案例——巨资，但一次性买断全部四项。

口径统一：网络语境的「延迟」被四种成分共用，**游戏开发者改说 RTT**——它反映双向全部四项，还包含对端帧率；正因两向不对称，「½RTT 近似单向」只是近似（[[第8章 改进的延迟处理|第8章]] 的警告）。

### 抖动（§7.2）：RTT 的方差

RTT 不是常数，围绕均值波动——这个偏差叫**抖动**。四项成分里，处理项贡献最小；**传输/传播随路由波动**（拥塞时路由器动态改路），**排队随流量突发波动**。

抖动的两个后果：**RTT 估计失准**（插值周期、外推步长全部跟着歪）；**乱序到达**——包 1 走 45ms、包 2 赶上拥塞走 60ms、包 3 走 30ms，到达顺序 3、1、2。要么用可靠有序传输（[[#7.4|§7.4]] 的代价），要么自建包重组（[[#7.5|§7.5]]）。减抖动与减延迟同款：少发包、服务器近玩家、**帧率别抖**。

### 丢包（§7.3）：最严重的那个

「到得慢」和「永远不到」是两码事。三层不可靠各有各的丢法：

| 层 | 丢包机制 |
|---|---|
| 物理介质 | 电磁干扰损坏数据 → 链路层校验失败**弃帧**（微波炉、松动接头都是真实原因） |
| 链路层 | 信道满，按协议规定**直接丢**——合法行为，不是故障 |
| 网络层 | 路由器队列满，**丢尾或丢新** |

缓解：近的数据中心、稳的连接，外加**包数经济学**——多数路由器的队列按**包的个数**分配：7 个 200B 小包占 7 个队列槽，1 个 1400B 大包只占 1 个，**少而大的包天然抗丢**。两条反注：有的路由器按**带宽**分配（小包反而占优）；路由器会按 QoS 优先级丢包，**有的甚至先丢 UDP 保 TCP**——UDP 游戏的丢包率可能高于直觉。

## 7.4 可靠性：TCP 还是 UDP

决策问题只有一句话：**游戏发送的每个数据，都需要被接收、且需要完全有序地处理吗？** 两个都答「是」（回合制）→ TCP；只要有一个「否」（大多数动作游戏）→ UDP + 应用层自建可靠性。

TCP 买到的东西很实在：经得起时间考验的可靠性 + 按序交付 + 拥塞控制，零工程成本。但它在**三种具体情景里产生真实伤害**，根因都是同一个门——按序交付语义（**字节 N 未确认之前，N 之后的所有字节都不许交给应用层**）：

1. **低优先级数据挡住高优先级数据**：远处的火箭爆炸（丢了无所谓）和敌人对你开火先后发出，爆炸包丢了、开火包没丢——但开火包**直到丢失的爆炸包重传成功才被交给游戏**。玩家根本不在乎那声爆炸，却被它卡住了敌人的动作。
2. **两条独立的数据流互相干扰**：把爆炸换成聊天消息——聊天只需相对其他聊天消息有序，用 TCP 聊天的丢失照样挡住爆头数据包。两条语义上独立的流被焊进了同一条按序字节流。
3. **重传过时的游戏状态**：玩家 B 从 x=0 跑向 x=100，途中某包丢失，TCP 忠实地重传——**重传的是 x=0 附近的旧状态，而此刻玩家 B 已经在 x=100**。带宽花在过期数据上。

**由此推论**：情景 3 的伤害可以被应用层结构化解——如果流上跑的是**自足的全量快照**（[[第5章 对象复制|第5章]]），重传的旧快照只是浪费带宽，不会污染状态；情景 1/2 则无解，它们伤害的是「到达的顺序」本身。

### 边缘代价：三条次级账单

| 代价 | 内容 | 缓解 |
|---|---|---|
| **Nagle 算法** | 为凑满包可把小包**延迟长达半秒**——对每帧都有小数据要发的游戏是致命的 | `TCP_NODELAY` 禁用它；**用 TCP 就必须设，没有商量余地** |
| **拥塞控制不可配置** | 丢包自动降速是好事，但**不是所有平台都统一可配置** | 只能接受；选 UDP 的又一票 |
| **内存管理在 OS 手里** | OS 必须保存所有已发未确认数据用于重传，游戏无法接入自定义内存管理器 | UDP 一侧由应用层决定「什么值得保存、什么立即丢弃」 |

UDP 侧的风险原文同样列明：自建系统不成熟（可用 RakNet/Photon 换灵活性）、**路由器可能被配置为优先丢弃 UDP 包**。

**表 7.1 的判据浓缩**：需要一切可靠且有序 → TCP；快节奏动作游戏的数据天生分优先级、分时效，按序交付的门反而是伤害来源——**选 UDP 不是嫌 TCP 慢，是不接受「一个过期的包挡住全队」。**

## 7.5 数据包传递通知：自建可靠层的第一块砖

UDP 自己不做任何可靠性，「送达」必须由应用层自己记账。`DeliveryNotificationManager`（DNM，受《星际围攻：部落》连接管理器启发）的定位原文说得极准：

> 它自己**不实现重传**，而是允许每个依赖模块**仅仅重传它决定重传的数据**——这是「基于 UDP 的可靠传输所提供的灵活性的主要来源，而 TCP 并不能提供」。

### 7.5.1 发送侧：序列号不表示字节位置

```cpp
InFlightPacket* DeliveryNotificationManager::WriteSequenceNumber(
    OutputMemoryBitStream& inPacket)
{
    PacketSequenceNumber sequenceNumber = mNextOutgoingSequenceNumber++;
    inPacket.Write(sequenceNumber);
    ++mDispatchedPacketCount;
    mInFlightPackets.emplace_back(sequenceNumber);
    return &mInFlightPackets.back();
}
```

借 TCP 的技术但不是 TCP 的语义：**序列号只为每个包提供唯一标识符，不像 TCP 那样表示流中的字节数**。工程批注：位宽（本例 `uint16_t`）用 typedef 收口，原则是**尽可能少用比特**（减少回绕撞车）；**开发期用展开的 32 位序列号便于调试，发布版删掉**。

### 7.5.2 接收侧：三路判包 + 确认攒批

`ProcessSequenceNumber()` 按接收端自己的「下一个期望值」三路判定：

| 来包序号 | 判断 | 处理 | 确认 |
|---|---|---|---|
| **== 期望值** | 正好接上 | 处理；期望值 +1 | 是 |
| **< 期望值** | 可能比已到达的包老 | **静默丢弃** | **否**（只确认处理过的包） |
| **> 期望值** | 有包丢失或延迟 | **仍然处理**；期望值 = 该号 + 1 | 是 |

第三条划界原文原话：**「与 TCP 不同，DNM 没有承诺按序处理每个单独的数据包。它仅仅承诺不乱序处理，并且当数据包丢失时发出报告。」**——`>` 期望值的包照常确认和处理是安全的；期望值设为「最近接收包的序号 + 1」以防旧包混入。回绕边界（期望值接近最大值而来包接近最小值）按 `>` 处理。

⚠️ **原文的一处代码-正文矛盾（实现时必踩）**：清单 7.2 里 `< 期望值` 分支是无条件 `return false`，**没有回绕判断**——照抄代码实现不出正文承诺的回绕语义，需自己补分支。

**确认攒批**：不为每个包单独发确认（「即使是 TCP，也允许每隔一个数据包才确认一次」）。`AddPendingAck` 把确认攒进 `vector<AckRange>`，`AckRange = {mStart, mCount}`——**只在序列中断时才需要多个段**（`ExtendIfShould` 连续就延续）。序列化的熵设计：先写 1 bit 存在标志（丢包是例外不是常规）→ 只写**一个** AckRange（写全部要多一个计数字段）→ 个数用 8 位、`hasCount` 为真才写（期望值是 1）。原文的自评：「8 位对这个计数已经很多了，还可以再少」。

### 7.5.3 接收确认并传递状态：确认缺失 ≠ 包丢失

§7.5.3 的警告是整节的地基：

> **确认的缺失并不真正表示数据包的丢失。** 数据可能已经成功到达，但是**包含确认的数据包丢失了。原始发送数据的主机没有办法区分这两种情况。**
> 在 TCP 中这不是问题——重传复用同一序列号，收到重复忽略即可。**DNM 的序列号不会被重用**，所以**由依赖模块唯一地识别数据本身以防止重复**（爆炸管理器要保证不会爆炸两次）。

两个对账入口，都利用在途队列**按序号有序**的性质只扫队头：

- **`ProcessAcks()`**（清单 7.6）：AckRange 之前的在途包报失败、范围内报成功、范围之后的直接成功并退出——「没有必要检查每个单独的 InFlightPacket」；
- **`ProcessTimedOutPackets()`**（清单 7.7）：**每帧调用**，判据 `GetTimeDispatched() < now - kAckTimeout`——队列有序，遇第一个未超时即 `break`。`kAckTimeout` **原文未给数量级**：太小误判好包、太大恢复变慢，按自己的 RTT 实测。

状态跟踪两个计数器（`mDroppedPacketCount / mDeliveredPacketCount`）不只是统计：**丢失率高 → 通知模块降低传输率或提示用户网络出错**；且可断言 **送达 + 丢弃 + 在途 == 已发出**。

**扩展点 `TransmissionData`**：每个 InFlightPacket 持有 `map<key, TransmissionData*>`，key 是模块自定类型号。依赖模块写可靠数据时挂自己的子类实例，送达/失败回调时按记录决定怎么补——**重传什么的决定权从 DNM 传递给了依赖模块**（§7.6 就是它的第一个大用户）。工程批注：`unordered_map` 迭代有缓存缺失——类型少用专用成员/定长数组，类型多用排序 vector。

**架构前提**：**每对通信主机一对 DNM**——服务器对 10 个客户端要 10 个 DNM。

⚠️ **一处被跳步的因果（§7.6 会打破它）**：原文说在途队列「因为新的加到队尾，所以已按序列号排序」——`push_back` 只保证**分配与入队严格同步**时成立；§7.6 改成「往周期性提供的待发包里补写数据」后两者解耦，排序不再自动成立，`ProcessTimedOutPackets` 的 `break` 随之失效。

## 7.6 对象复制可靠性：丢包后重批「最新状态」

用 DNM 做可靠传输最直接的用法是：包丢了 → 把包里**所有数据原样重传**。这与 TCP 同构——但浪费了通知系统的全部潜能。§7.6 的主张一句话：

> **丢的不是字节，是「一次状态通报」；补发时应该补「对象的最新状态」，而不是当时写进包里的旧字节。**

原文的量化对比：重传最新状态可能比原始包里的状态**新半秒钟**。

### 架构前提：复制管理器从「序列化器」变成「账本」

第 5 章的 `ReplicationManager` 接口是被动的（游戏代码准备好流、调 `ReplicateCreate/Update/Destroy` 写入）——它不掌控「哪个包装了什么」，结构上不支持可靠性。改造是**控制权反转**：游戏代码不再创建数据包，**只通知**复制管理器「什么变了」；主机程序**周期性地**把待发数据包递给它（频率按带宽/丢包率定），由它决定往里写什么。三层收益：游戏与网络解耦、复制管理器能挑「最该发的」、丢包时它手里有重新生成的全部上下文。

### 复制命令账本：map + 脏状态位

游戏系统批量提交复制请求，复制管理器记在 `mNetworkIdToReplicationCommand`（网络 ID → 最新命令，清单 7.10）：

```cpp
void BatchCreate(int inNetworkId, uint32_t inInitialDirtyState); // 建账
void BatchDestroy(int inNetworkId);        // mAction = RA_Destroy
void BatchStateDirty(int inNetworkId, uint32_t inDirtyState);    // mDirtyState |= inState
```

三个语义细节：**更新用 OR 合并**（连续多次变更同一对象的不同属性，脏位累积）；**销毁覆盖一切**（给已销毁对象发更新毫无意义）；**写完不清账只清位**（清单 7.11 的 `ClearDirtyState`——脏位清零等下次变更，但 destroy 动作在写包后**降级回 update**：「销毁」这个事实可能丢在途中，必须留在账上直到被确认）。

### 两个方向的闭环

**发送时**：`WriteBatchedCommands` 每写一条复制数据，就在该包的 `InFlightPacket` 里登记 `(networkId, action, dirtyState)`——**这个包对这个对象写了什么**的完整记录。

**丢包时**：`HandleDeliveryFailure`（清单 7.12）拿着记录逐条重批，**每条都先查对象现在的状态**：

| 原动作 | 重批动作 | 关键检查 |
|---|---|---|
| RA_Create | 重新 BatchCreate | **对象还存在吗**——期间已销毁的话，重发 create 就是复活死者 |
| RA_Update | BatchStateDirty(原脏位) | 同上——对象还在才值得重脏 |
| RA_Destroy | BatchDestroy | 无条件——销毁必须送达 |

`HandleDeliverySuccess` 的对偶动作：create 被确认后**降级为 update**——第一次到达后，后续都是对已知对象的更新。

### 适用边界

| 数据类型 | 走这套吗 | 原因 |
|---|---|---|
| **值语义的状态**（位置/血量/属性） | ✅ 完美适配 | 「最新值」永远合法，旧值自动作废；无需回滚 |
| **一次性事件**（爆炸音效/聊天/击杀播报） | ❌ 不适用 | 事件的「最新版本」不是它自己——重批依赖「对象当前状态里仍包含该信息」，事件没有这个性质。事件要走显式重传 |
| **创建/销毁** | ✅ 但要分类 | 销毁无条件重批；创建可被销毁作废；更新尽力而为也行 |

一句话：**状态与事件的可靠性必须分流——状态丢包用「重批最新」零成本自愈，事件丢包只能「原样重传直到确认」；把事件混进状态重批，丢的不是包，是那条事件本身。**

## 7.7 模拟真实世界的条件

真实世界的恶劣条件只在发布后才遇到就太晚了——**本地局域网测试永远全绿，上线即翻车**。解法：在套接字与游戏其余部分之间插一个测试模块。两个动作（清单 7.14）：

**收包时**：①**丢包判定**——随机数 < 丢包率直接丢弃；②**模拟到达时间** = `now + 延迟 + (随机−0.5)×双倍最大抖动`；③按**模拟到达时间**插入有序列表。

**每帧**：只处理模拟到达时间 ≤ 当前时间的对首包——包在队列里「睡」到它该到的时刻。

三个参数就是整个模拟器的配置面：丢包率、平均延迟、抖动幅度。两个补精度批注：**丢包是成串的**（丢弃命中时再用一个随机数决定连坐多少个后续包——纯独立随机会低估最坏情况）；模拟用的随机数必须与游戏随机数**分离**（P2P 锁步里全体对等体会同时「随机」丢包，[[第6章 网络拓扑和游戏案例|第6章]] §6.3.3 的反向纪律）。它同时是回归工具的蓝本——网络条件参数化后，回归可以指定「30ms±10ms、5% 丢包」跑一遍。

## 章末判据

| 问题 | 第一反应 |
|---|---|
| 延迟高 | 分清四成分：挪服务器（传播）、合大包（传输/排队）、剩下靠第 8 章补偿 |
| 延迟不稳 | 抖动——插值参数要吃方差；乱序要有重组层 |
| 丢包 | 大包少发、服务器近、知道路由器可能偏爱丢你的 UDP |
| 协议选型 | 一切皆命令且有序 → TCP（必设 `TCP_NODELAY`）；动作游戏 → UDP + 自建 |
| 自建可靠层 | DNM 只管「通知」，重传决定权在依赖模块；确认缺失 ≠ 丢失，去重责任在应用层 ID |
| 丢包补什么 | 状态重批最新、事件原样重传——分流 |
| 测试 | 三参数模拟器（丢包/延迟/抖动）+ 成串丢包；随机数与游戏分离 |

一句话结论：**本章是一条完整的因果链——互联网的三个物理事实（延迟四成分、抖动、三层丢包）逼出协议选型（TCP 的按序门 vs UDP 的白纸），选 UDP 逼出自建两层记账（包级 DNM + 复制级重批最新），全部做完再用模拟器把恶劣环境搬回开发机——每一步都是上一步的必然。**
