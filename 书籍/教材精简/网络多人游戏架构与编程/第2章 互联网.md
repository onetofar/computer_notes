## 2.1 起源：分组交换

阿帕网（1969，四节点）用**分组交换**取代了电路交换，这个选择定义了后来互联网的一切性格：

- **电路交换**：把沿途短线路拼成一条连续电路，通话结束前始终独占。服务质量高，但线路一个时刻只能服务一个目的——为「最合适的地方」之外的场景浪费；
- **分组交换**：把信息拆成小块（分组），各节点**存储转发**——收到分组、看目的地、转发给离目的地更近的节点。**多条通话可以同时共享同一线路**，可用性大幅提高。

1822 协议（阿帕网的打包/转发规则集）多年演化后成为 **TCP/IP 协议族**。对游戏开发者的含义：你发的每个包都可能走不同路径、与陌生人的流量共享链路——第 7 章的延迟/抖动/丢包三份账单都从这里来。

## 2.2 TCP/IP 模型

原文对协议族的评价值得先记下：「美丽是因为抽象得极好的独立层；可怕是因为抽象往往被协议作者以性能、可扩展性的理由破坏」——游戏开发者的工作是理解它的美与丑。

本书用**五层组合模型**（RFC 1122 的四层 + 物理层，比 OSI 七层更贴游戏开发者）：

```text
        数据流 ↓
  应用层  |·····················| 应用层数据
  传输层  |······|传输层报文段报头|········
  网络层  | 网络层数据包报头 |············
  链路层  |链路层数据帧帧头|··············|链路层数据帧帧尾
  物理层  |··········· 物理介质 ·············|
```

每层的职责套路（对上下两层相同）：**收上一层的数据 → 加头部（有时尾部）封装 → 转发给下一层**；反向是去头解封装、上交。原文给的类比很准：**层是接口，协议是接口的实现**——理想中上层不该知道实现，实际上经常被破坏（§2.8 的 NAT 就是把传输层端口当 IP 地址一部分改写的著名破坏）。

## 2.3 物理层

最底层的支持层：Cat 6 双绞线、同轴电缆、光纤——以及**不可触摸的无线电波**（手机/平板证明无线也是合法物理媒介）。原文的玩笑话里有真意：只要带宽和延迟够，量子缠绕也会被接受为物理层实现。

## 2.4 链路层

负责**同一链路内**的帧传输：以太网帧由帧头（含源/目的 **MAC 地址**）+ 载荷 + 帧尾（**FCS 帧检验序列**——链路层自带的完整性校验，IPv4 头部检验和因此只保头部）构成。MAC 地址是链路层唯一认识的地址——网络层的 IP 包要出网卡，必须先翻译成 MAC（§2.5.1.2 的 ARP 就是这个翻译）。**Ethernet/802.3 是游戏服务器的默认链路层**，它的 1500 字节 MTU 是全书「1300 字节安全载荷」建议的最终来源（[[第3章 伯克利套接字|第3章]] §3.4 / [[第7章 延迟、抖动和可靠性|第7章]] §7.3）。

## 2.5 网络层：IPv4

IPv4 定义三件事：**逻辑寻址**（每主机唯一 IP）、**子网分段**（地址空间的逻辑划分）、**路由**（子网间转发）。

### 2.5.1.1 IP 地址与数据包结构

IPv4 地址 = 32 位，点分四段十进制表示（`128.125.253.146`）。数据包 = 头部 + 数据，头部逐字段（图 2.5）：

| 字段 | 位 | 语义与游戏含义 |
|---|---|---|
| 版本号 | 4 | IPv4 = 4 |
| 包头长度 | 4 | **单位是 32 比特**（可选项使头长可变，最大 15×4=60 字节，最小 5×4=20） |
| 服务类型 | 8 | 拥塞控制/差异化服务 |
| 包总长 | 16 | 以字节计——**IP 包最大 65535**，数据部分最大 65515 |
| 片标识/标记/片偏移 | 16+3+13 | 分片重组三件套（见下） |
| 生存时间 TTL | 8 | 限制转发次数 |
| 协议 | 8 | 上层是什么（TCP/UDP）——类似以太网的 EtherType |
| 头部检验和 | 16 | **只保头部**——数据完整性交给上层/链路层 FCS |
| 源/目的地址 | 32+32 | 目的地址也可以是多播特殊地址 |

原文有一个专为游戏程序员写的批注：**包头长度单位是 32 比特而总长单位是 8 比特**——因为头长永远是 4 的倍数、后两比特恒为 0，用 32 比特当单位能省 2 比特。「**尽可能节约带宽是多人游戏编程的黄金法则**」——协议设计者与游戏程序员守同一条法则。

### 2.5.1.2 直连路由与 ARP

网络层只认 IP，链路层只认 MAC——从 IP 到 MAC 的翻译由 **ARP** 完成：查映射表（IP→MAC）→ 表里没有就**广播** ARP 请求（目标 MAC 填 `FF:FF:FF:FF:FF:FF`）→ 匹配 IP 的主机单播应答 → 双方互存对方映射。两个批注：

- **顺手的优化**：ARP 请求是广播的，网内所有主机都会顺手把「请求者的 IP→MAC」记进自己的表——之后不用再问；
- **安全漏洞（原文点出）**：ARP 应答没有真实性验证——恶意主机可以冒答任意 IP，路由器会把别人的包发给它（嗅探）或让包消失（断网）。这就是 [[第10章 安全性|第10章]] 威胁模型里「链路内不可信」的一个具体形态。

### 2.5.1.3 子网与间接路由

直接把两个公司网络用以太网电缆相连 = 每个广播包发给全部 200 台主机，流量翻倍+无隐私。网络层的解法：**路由器**（多网卡主机，每网卡一个 IP）连接子网——子网内直接路由（ARP），跨子网**间接路由**：目的 IP 的网络前缀不在本子网 → 交给默认网关 → 逐跳转发。**子网掩码**定义「前缀到哪里为止」。**TTL** 每过一跳减一，到 0 丢弃——路由环路的保险丝。前缀规划的意义：**把设计边界焊进地址结构**（游戏服务器集群按子网规划，ACL 与路由都跟着走）。

### 2.5.2 IPv6

128 位地址（IPv4 的 4 倍）解决地址枯竭；对游戏开发者当前要务是**双栈支持**——`AF_INET6` 的 socket 与 IPv4 并存（[[第3章 伯克利套接字|第3章]] §3.1）。

## 2.6 传输层

### 2.6.1 UDP

8 字节头，四个字段：**源端口 / 目的端口 / 数据报长度（含头）/ 检验和（可选，0=未算）**。原文的比喻精确得可以直接引用：

> UDP 是一张**明信片**——投进信箱，然后忘记。

每个数据报独立、两台主机间无共享状态、不保证顺序与到达、不做流量限制。**这正是第 7 章 §7.5 自建可靠层必须存在的全部理由。**

### 2.6.2 TCP

关键词是**可靠**：保证所有数据按序抵达。代价是更大的头部 + 每连接的跟踪状态。数据单元是**报文段（segment）**——大字节流被切成段封装发送。头部五关键字段（图 2.11）：

| 字段 | 位 | 语义 |
|---|---|---|
| 序列号 | 32 | 单调递增，**每个字节都有连续序号**——报文段的序号=其数据首字节的序号（三次握手时是例外） |
| 确认号 | 32 | 期望收到的下一个字节序号——**确认的是所有小于它的字节**（累积确认） |
| 数据偏移 | 4 | TCP 头长（32 位单位；头可变长 20–64 字节） |
| 接收窗口 | 16 | 剩余缓冲容量——**流量控制**的入口（`SO_RCVBUF` 是它的上限，[[第3章 伯克利套接字|第3章]] §3.7） |
| 控制位 | 9 | SYN/ACK/FIN/RST 等元数据 |

**可靠性机制骨架**（图 2.12 的停等循环）：发送唯一标识的包 → 等确认 → 超时未确认**重发** → 循环直到全部确认。这是最小骨架；滑动窗口、快重传、拥塞控制的完整机制地面由卷一覆盖（[[4-1 流量控制以及滑动窗口]] / [[4-2 拥塞控制]]）。

格雷泽视角的关键洞察留在第 7 章 §7.4：**可靠性+按序是 TCP 的强制捆绑**——游戏数据天然分优先级与时效，这道门反而成为伤害来源。

## 2.7 应用层

**DHCP**（主机接入时自动获取 IP/掩码/网关/DNS）与 **DNS**（域名→IP；调用侧的阻塞警告见 [[第3章 伯克利套接字|第3章]] §3.3.2 的 getaddrinfo——秒级阻塞，主线程外调用）。概览即可。

## 2.8 NAT 与 NAT 穿越

### 核心结论

NAT 是边界设备（家用路由器）做的**地址 + 端口双重重写**：让一整个家庭网络共享一个公开 IP。代价是它单方面销毁了「从外部主动连进来」的能力——出站不受限制，但入站必须先有映射表项，而表项**只由出站产生**。所以「谁能连上谁」不由防火墙策略决定，由**谁先发过包**决定。

UDP 因此需要 STUN 打洞这类补丁；TCP 因为三次握手本身就是一次客户端发起的入站报文，**天然就完成了打洞**——这一条直接解释了为什么 TCP 权威服务器架构不需要任何打洞中继，而 UDP P2P 架构绕不开（[[第6章 网络拓扑和游戏案例|第6章]] §6.3.1 的 rendezvous 服务器就是那个补丁）。

### 为什么需要它

IPv4 只有 32 bit = 42.9 亿个地址，早就发完了。NAT 让一整个私有子网共享一个公开 IP，把「地址不够用」变成「端口不够用」。私有地址段（RFC 1918）：

| 段 | 范围 | 用途 |
|---|---|---|
| 10.0.0.0/8 | 10.0.0.0 – 10.255.255.255 | 私有 |
| 172.16.0.0/12 | 172.16.0.0 – 172.31.255.255 | 私有 |
| 192.168.0.0/16 | 192.168.0.0 – 192.168.255.255 | 私有 |
| 127.0.0.0/8 | — | 环回 |
| 169.254.0.0/16 | — | 链路本地 / APIPA（DHCP 失败时自动分配，开发中真会撞上） |

关键性质是**可重复**：不同家庭可以用同一个 `192.168.1.1`，因为公网路由器没有到这些段的路由信息。措辞要紧：「私有地址不可路由」≠「这个地址不存在」——准确含义是「路由器**没有**到它的路由信息」。

### 三步递进

**第一步 · 没有 NAT.** 游戏机 `192.168.1.2:100` 向服务器发包，源地址是私有地址。服务器能收到，但回包时公网路由器查不到到 `192.168.1.2` 的路由信息——回不来。

**第二步 · 只重写 IP.** 路由器把源 IP 换成自己的公开 IP。服务器能回包到路由器了，但路由器不知道该转给内网哪台——它没记过是谁发出去的。

**第三步 · 同时重写 IP 和端口.** 路由器在 NAT 表里记一行 `(内网源 IP:端口, 外网端口, 目的 IP:端口)`，源 IP 和源端口一起换成 `(路由器公开 IP, 随机分配的外网端口)`，回包按外网端口查表还原。随机端口是必须的：只按源 IP 建表的话，内网多台主机连同一个外部服务器就分不开。

**这一步的真正意义是它直接穿透了网络层与传输层之间的抽象**——NAT 在 IP 层动不了传输层语义，只好把传输层的端口当成 IP 地址的一部分来改写。

现代路由器还会在表项里记下**原始目的地址**：回包时先按源端口查表，再校验回包的源 IP:端口是否等于当初发出去时的目的 IP:端口，不一致就丢弃。所以「外网端口可达」不等于「能被打」。

### 补出的前提（原文省略、实现时必撞）

| 前提 | 内容 |
|---|---|
| **表项会老化** | UDP 映射通常几分钟不刷新就回收。**打洞成功不等于永久通**——不持续发包，链路自己断（「玩着玩着掉线」的一种成因；`SO_KEEPALIVE` 与心跳是对策，[[第3章 伯克利套接字|第3章]] §3.7） |
| **NAT 只挡入站** | 出站完全不受限，而且**正是出站流量创建映射表项**——没先发过包的一方天然不可达 |
| **NAT 分型** | **端口保持**（cone，外网端口不随目标变化，STUN 可穿透）vs **端口不复用**（symmetric 对称型，每个目标给不同端口，**STUN 直接失效**需 TURN 中继）。原文只在注释顺带提了对称 NAT——判断自家路由器属于哪类直接决定方案选型 |
| **TCP 天然打洞的机理** | 三次握手本身就是一次由客户端发起的入站报文，SYN 一到表项就建好。客户端不需要任何辅助就完成 UDP 侧 STUN 那一整套；UDP 无连接没有握手报文，所以才需要补丁 |
| **端口分配失败** | 外网端口空间 65535 有限，分配失败时表项建不出来，表现为「偶尔连不上」 |

### 失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| NAT 端口保持（cone 型） | STUN 可穿透 | 对称 NAT 下 STUN 失效，需 TURN 中继 |
| 应用持续发包 | 表项持续刷新 | 空闲超时后链路静默断开 |
| 客户端先出站 | 自动建表 | **纯被动等待入站的服务器永远建不出表项** |
| TCP 三次握手正常完成 | 入站映射自动建立 | 中间设备严格拦 SYN 时需要 TCP 打洞（RFC 5128） |

⚠️ **原文的一处错译**：§2.8 注释「TCP 使用不同的端口分配系统，所以传输数据必然使用与侦听连接不同的端口」——直译后是错的。TCP 连接不存在「数据端口与侦听端口分离」的问题（握手后那条连接的端口就是客户端临时端口），译者把 UDP/TCP 端口复用策略的差异拧成了端口不等的断言。

### 对服务器部署的直接含义

TCP 权威服务器架构：**不需要 STUN/TURN/中继**；玩家在家用宽带主动连服务器，映射自动建立；心跳持续刷新表项（1Hz 心跳即可覆盖老化周期）。**唯一要撞的墙在服务器侧**：纯被动入站的服务器必须有公网可达地址——本地演示要么租 VPS，要么跑在有公网地址的机器上。
