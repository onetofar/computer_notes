# 第9章 可扩展性

> **小节地图**：§9.1 对象范围与相关性 / §9.2 服务器分区 / §9.3 实例化 / §9.4 优先级和频率——全章精读。
> 全章是一条杠杆序列：先决定「发谁」（§9.1），再决定「世界怎么切」（§9.2–9.3），最后决定「先发谁」（§9.4）。

## 9.1 对象范围和相关性：规模是开关

**对象在范围内（相关）= 应该通知该客户端关于它的更新。** 三个支柱认知：

1. **小规模可以全员相关**：「小规模游戏中，可以所有对象对所有客户端都是在范围内或相关」——相关性集合 = 全部对象，这正是第 5 章全量快照成立的前提（[[第5章 对象复制|第5章]]）。原文的转折数字是 **64 个玩家**：几公里外的玩家不值得发。
2. **相关性不是二元命题**：记分牌要显示所有玩家的健康指数——对象的其他属性不相关，健康值永远相关。商业游戏的相关性集合常常是「按属性、按优先级拼接的」。
3. **空间方法（距离裁剪）很脆**：原文的狙击步枪故事——按射程定相关性，测试时带宽刚好；设计后来加了一把射程两倍的枪，相关集合直接翻倍。距离阈值是把设计参数焊进了网络层。

§9.1.1 静态区域（MMO 按区域切分，加载屏过渡；软肋是玩家分布不均——小镇挤爆偏僻区没人）；§9.1.2 视锥裁剪（只看前方、穿墙即失效、快速转身会露出延迟）；§9.1.3/9.1.4 其他技术与不可见时的相关性。**这些手段共同的问题是都假设玩家均匀分布**——下一节直接把进程也切了。

## 9.2 服务器分区（sharding）

**分区 = 同时跑多个服务器进程，每个进程承载一局独立游戏。** 动作游戏的天然形态：每局 8–16 人上限是设计决定的，技术红利是**任何单进程负载永不过重**（《使命召唤》《英雄联盟》《战地》全走这条路）。三个要点：

- 进程间**无玩法交互**，但统计/经验/等级写**共享后端数据库**——那属于游戏服务（[[第12章 玩家服务|第12章]]）；
- 一台机器常跑**多个进程**，主进程负责「往负载最小的机器上开新局」——进程退场前写完永久数据（infra 侧的完整答案在 [[第13章 云托管专用服务器|第13章]]）；
- MMO 把静态区域升级成进程单位：《魔兽世界》每块大陆一个进程，跨大陆有加载画面、大陆内部跨区域无缝——**分区边界 = 加载屏边界**。

**软肋同 §9.1**：前提是玩家大致均匀。对策谱系：硬上限+排队；《Eve Online》的**时间膨胀**——不踢人，把全服时间步长放慢，用慢动作换连接存活。

## 9.3 实例化（instancing）

实例化 = **同一台服务器上的共享世界，同一时刻存在多个并行副本**（地城是典型）。与分区的区别：分区切的是进程，实例切的是「同一世界里的可见集合」——两个玩家可能站在同一坐标却互相看不见（不同实例）。

- 拥挤区自动分裂第二实例（《星球大战：旧共和国》），代价是「想见面的两人落到不同实例」——解法是允许跳到队友的实例；
- 设计收益：内容可以按单机/小队粒度定制；性能收益：**任一时刻的相关玩家数有硬上界 X**；
- 可与分区叠加：进实例必然过加载屏，所以实例完全可以直接落在另一台服务器进程上——《魔兽世界》大陆就是这么跑的。

## 9.4 优先级和频率

相关性裁剪之后带宽还超，就轮到**发送排序**：高优先级对象先复制。两个纪律防止这套机制自己咬自己：

1. **低优先级必须偶尔漏过去**——永远轮不到 = 永远不更新 = 客户端上永远过期；
2. **频率与优先级合成动态优先级**：重要对象每秒更新几次，不重要的几秒一次；低优先级对象**饿了越久，优先级越抬越高**——饥饿驱动的加权。

同样的优先级逻辑也适用于 RPC：与游戏状态相关性弱的 RPC，带宽不够时**直接在传输中丢弃**——和第 1 章四类数据里「非保障数据」的待遇一致（[[第1章 网络游戏概述|第1章]]）。

## 章末判据

| 场景 | 手段 |
|---|---|
| 每局人数有上限的对抗游戏 | 分区：一局一进程，主进程调度机器 |
| 共享世界的拥挤区域 | 实例化：自动分裂，允许跳队友实例 |
| MMO 单区过载 | 硬上限排队 / 时间膨胀（保连接保体验降速度） |
| 带宽总量超预算 | 优先级 + 频率 + 饥饿加权的动态优先级 |
| 弱相关 RPC | 带宽不足直接丢 |

一句话结论：**分区管进程负载（一局一进程），实例管可见集合（平行小房间），优先级管发送顺序（饥饿加权防饿死）——三级杠杆都在回答同一个问题：有限的机器与带宽，先给谁。**
