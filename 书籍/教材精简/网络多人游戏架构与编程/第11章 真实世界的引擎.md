## 商业引擎网络 —— 第 1–10 章机制的工业封装

> 原文锚点：第 11 章「真实世界的引擎」§11.1–§11.2。
> 两个引擎都只支持 C/S 拓扑（不支持 P2P）——**第 1–10 章的每个概念都能在这里找到对应物**，本章的读法是「照镜子」：自研协议拿它们当参照系。

### 0 概念映射总表

| 本书概念 | Unreal | Unity (UNET) |
|---|---|---|
| 平台套接字封装（§3） | `ISocketSubsystem`（按平台实现，TCP/UDP 共用 `FSocket`） | 传输层 API（不选协议，**选 QoS 档位**） |
| NetworkManager（§6.2） | `UNetDriver`（收/滤/发，按传输层 IP/Steam 分实现） | `NetworkManager`（专用/监听/客户端三模式） |
| 复制相关性（§5.3/§9.1） | actor 相关性 + `bAlwaysRelevant` 等标志 | `SyncVar` 自动同步 |
| 权威边界（§6.1） | **角色系统**（authority/simulated/autonomous proxy） | 服务器 Spawn 才能复制（客户端无复制权） |
| 输入验证（§10.2） | **owner-only RPC**（归属校验引擎化） | Command 只对玩家控制的对象有效 |
| 四类数据（§1.2） | RPC 可标记可靠/不可靠 | **QoS 四档** |
| 游戏服务（§12） | 平台服务封装（Steamworks 等） | `NetworkMatch` 比赛安排 |

### 1 Unreal：角色系统与 owner-only RPC

**Actor 层次**：`Actor`（万物基类）→ `Pawn`（可控制）↔ `Controller`（`PlayerController`/`AIController`）。单人按键的路径：空格 → PlayerController → 通知 Pawn → Pawn 生成 DodgeBall(Actor)。

**三种角色**（§11.1.3）——每个实例对每个 actor 独立查询，**同一个 actor 在不同实例上角色不同**：

| 角色 | 语义 |
|---|---|
| **权威** authority | 本实例是该 actor 的最终裁决者（服务器对大多数 actor 持有；但客户端本地生成的粒子效果 actor，服务器根本不知道它存在） |
| **模拟代理** simulated proxy | 客户端只镜像模拟，无裁决权 |
| **自治代理** autonomous proxy | 模拟代理 + 接收本地玩家输入（本地玩家的 Pawn）——移动预测的挂点 |

复制是**单向的**：服务器 → 相关客户端；客户端没有任何办法把 actor 复制上去。属性级可配置（条件复制、属性到达即回调），移动预测有内置默认实现（`bReplicateMovement`）。

**RPC 三型**（§11.1.4），其中藏着第 10 章输入验证的引擎化：

- **服务器函数**（客户端调、服务器执行）：**只有 actor 的拥有者能在该 actor 上调**——拥有者 = 关联的 PlayerController，不是权威方。客户端 A 对别的 Pawn 调扔球 RPC 直接被忽略——**归属校验不再是应用层纪律，是引擎行为**；
- **客户端函数**（服务器调、发给拥有者客户端执行）；
- **多播函数**（服务器调、服务器+全体客户端执行——「每个客户端本地生成一个粒子」就靠它）。

可标记可靠/不可靠——低优先级事件在丢包时让路，四类数据思想的引擎落地。

### 2 Unity：QoS 四档与 SyncVar 的粒度陷阱

**传输层不选协议选 QoS**（§11.2.1）——`QosType` 枚举就是四类数据（§1.2）的成品化：

| 档位 | 语义 | 对应四类数据 |
|---|---|---|
| `Unreliable` | 无任何保证 | 非保障数据 |
| `UnreliableSequenced` | 不保证到达，**乱序即丢** | 最近的状态数据（电话语义） |
| `Reliable` | 保证到达 | 保障数据 |
| `ReliableFragmented` | 可靠 + 分片重组 | 大文件的保障数据 |

**复制与 RPC**：`NetworkServer.Spawn` 生成可复制对象（客户端预注册 prefab 保证数据齐备）；组件必须继承 `NetworkBehaviour` 才能复制。变量同步两条路**互斥**：

- `[SyncVar]`：自动同步，零簿记——但**结构体整包复制**：10 个成员变 1 个也传 10 个，带宽白费；
- 手写 `OnSerialize/OnDeserialize`：细粒度脏标记自己管。

粒度取舍和自研协议里「状态掩码 vs 整对象序列化」是同一道题（[[第5章 对象复制]] / [[第7章 延迟、抖动和可靠性]] 的脏状态位）。

RPC 命名即语义：`[Command]` + `Cmd` 前缀 = 客户端→服务器（**只对玩家控制的对象有效**——与 Unreal 的 owner-only 同一条输入验证纪律）；`[ClientRpc]` + `Rpc` 前缀 = 服务器→客户端。

### 3 自研协议照镜子清单

| 照镜子问题 | 引擎答案的启示 |
|---|---|
| 权威边界在代码里看得见吗 | Unreal 用**角色枚举**让它成为类型系统的一部分，不是注释里的口头约定 |
| 谁有权发命令 | 引擎级 owner 校验——应用层验证（§10.2）可以内建到 API 里 |
| 可靠性配置面 | QoS 档位化：不给「可靠/不可靠」二选一，给四档语义 |
| 同步粒度 | SyncVar 的整包陷阱 = 自动化便利与带宽精度的固有权衡 |

一句话结论：**商业引擎没有发明新机制——它们把第 1–10 章的东西做成了类型和属性（角色枚举、QoS 档、SyncVar、owner-only RPC）；自研协议该照的不是功能清单，是这种「把纪律灌进 API 形状」的做法。**
