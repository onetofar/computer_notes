# 第4章 账号登录与验证

> **小节地图**:§4.1 登录流程 / §4.2–4.5 验证接口搭建(PHP 模拟平台)/ §4.6 结果测试 / §4.7 消息过滤机制 / §4.8–4.10 测试机器人与批量登录——全章精读(搭建类小节收骨架)。

## 4.1 登录三步:为什么游戏不自己验账号

真实发布的游戏**没有自己的账号验证接口**——验证外包给平台(SDK)。流程三步(图 4-1):

1. **客户端**经平台 SDK 取到该账号的 token + 账号 ID,token **有时效性**(几秒几分);
2. **客户端**把 token 发给游戏服务端;服务端通过平台的 HTTP 接口把 token+ID 回传平台验证;
3. 服务端收到平台反馈:失败通知客户端,成功**加载玩家数据**。

**为什么不能拿自己的 DB 直接验**:平台不允许游戏里直接输账号密码(密码泄露风险),所以平台的方案是「SDK 验证接口 + 时效 token」。本章用两个 PHP 文件模拟平台的验证接口——**账号密码验证与 token 验证在原理、流程上完全一致**,内测用账密,上外网同一框架直接换。

## 4.7 消息过滤机制:按归属筛选协议

问题:框架早期的消息机制是 `MessageList` 挂一个回调,**无差别接收**所有协议——多 Robot 并存时互相收到对方的包。改造:

```cpp
class MessageCallBackFunctionInfo {          // 基类:两虚函数
    virtual bool IsFollowMsgId(Packet*) = 0; // 这条包我关心吗
    virtual void ProcessPacket() = 0;
    std::mutex _msgMutex;  std::list<Packet*> _msgList;
};
class MessageCallBackFunction : ...          // 旧:无差别接收(map<MsgId, handler>)
template<class T>
class MessageCallBackFunctionFilterObj : ... // 新:按对象筛选
    HandleGetObject GetPacketObject;         // 按 SOCKET 找到归属对象
    bool IsFollowMsgId(Packet*) override;    // 只有归属对象的包才进队
```

**机制要点**:`FilterObj` 版把「协议进谁的队列」变成**可插拔的谓词**——`IsFollowMsgId` 判关心与否,`GetPacketObject` 按 SOCKET 把包路由到正确的对象(Robot 实例)。这是**消息从广播走向寻址**的一步,也是 ECS 框架(第 6 章)消息系统的前身。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.3]] 的 ClientProxy 是同构思想的服务器版:**每个连接一份**的处理上下文,包按归属路由,不是全员广播。

## 4.8–4.10 测试机器人与批量登录

测试机器人(Robot)= **自己当自己的客户端**:批量起 Robot 实例走完整登录流程压测服务端(§4.8 单机多实例、§4.10 批量登录)。这一段的工程价值不在登录本身,在**「用进程内机器人代替真人做回归」**的测试姿势——与本知识库 `cli_client.cpp` 的验收客户端是同一思路。

⚠️ **§4.9 不可引用**:该节有一处与 `epoll_wait(2)` 行为矛盾的性能归因(把 select 的 fd 上限问题错归到 epoll 的实现上),结论错误——引用本章时跳过该节,详见多人网络-MOC「元」分区条目。

## 章末判据

| 决策点 | 判据 |
|---|---|
| 账号验证 | 外包平台(SDK+时效 token),游戏侧只做「回传验证+加载数据」;自己 DB 直连验密是泄露面 |
| 消息路由 | 多实例并存时必须按归属筛选(IsFollowMsgId+GetPacketObject),无差别广播 = 状态串门 |
| 压测 | 进程内 Robot 批量走真流程,替代真人回归 |

一句话结论:**本章把「登录」拆成两件可迁移的事——验证外包(token 流程)与消息按归属路由(过滤器);前者是每个上线游戏都要重走一遍的流程,后者是 ECS 框架消息系统的地基。**
