# 第10章 分布式登录与Redis内存数据库

> 本章把第 9 章的拓扑补全为五进程,并解决两个分布式登录的真问题:**同账号双登**与**进程间连接何时建立**。

## 进程拓扑(五角色)

```
客户端 ──HTTP──▶ appmgr(唯一,择优分派 login)
客户端 ──TCP───▶ login(多个,验证+发 token+择优 game)
客户端 ──TCP───▶ game(多个,大厅+中转网关)──▶ space(多个,真正的地图 World)
                     └──────▶ dbmgr(唯一,DB 存储面)
```

**完整登录四步**(原文脉络):

1. 客户端经 HTTP 从 appmgr 拿到一个可用 login 的 IP:端口;
2. 连 login 验证账号 → 建角色/选角色 → login **分析所有 game 的状态择优**、发 token;
3. 客户端持 token 连 game,正式开始游戏;
4. 进地图:game 向 appmgr 查该地图实例是否已存在——没有就在合适的 space **创建地图实例**,同时 game 侧生成 **WorldProxy**(地图代理),之后所有数据转发至 space,**game 退化为网关**;建好后客户端才加载地图。

## Redis:解「同账号双登」

**问题**:同一账号同时在 login1 与 login2 登录怎么办?各 login 的内存状态互相不可见——这类**跨进程的共享事实**没有地方放。

**解法:Redis 内存数据库**作为五进程共享的外部内存:登录态写 Redis,任何 login 验证前先查 Redis——双登在数据层面被看见,处理(踢旧/拒绝)才有依据。

> 📖 [[第7章 MySQL数据库|第7章]] 的 DB 是**持久面**(慢、可靠);Redis 是**共享事实面**(快、易失)——两者的分工与 [[第13章 云托管专用服务器|格雷泽第13章 §13.2]] 的「共享后端数据库(统计/等级)」是同一张架构图:分区之间无玩法交互,但**事实必须共享**。

## 全连接 vs 按需连接:一个被权衡过的取舍

| 方案 | 问题 |
|---|---|
| **按需连接**(game 与 space 需要时才建) | 建连接有时间差 → **Packet 缓存问题**:包要缓存到连接建好才能发——缓存即风险 |
| **初始化时全连接**(本书选择) | 进程一启动就两两连好;space 宕机时 game **立刻收到断线协议**,跳转请求当场可判异常——**故障可检测** |

本书选全连接的理由值得原文引用:按需连接的 Packet 缓存「需要缓存到它依赖的网络创建好了再发送」,而全连接让「异常」以断线协议的形态**第一时间暴露**。代价是常驻连接数 O(进程数²)——进程规模小时这是正确的价格。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.3.1]] 的 rendezvous 与本节的取舍是同一族问题:**连接拓扑是分布式系统的第一张设计图**,先画它,再谈协议。

## 章末判据

| 决策点 | 判据 |
|---|---|
| 跨进程共享事实 | 放 Redis(快/易失)而不是各进程内存互猜;DB 只放持久面 |
| 进程间连接 | 初始化全连接:故障可检测;按需连接的 Packet 缓存是隐性复杂度 |
| 进程职责 | game=网关(WorldProxy 中转),space=真地图;职责分离让扩容各走各的 |

一句话结论:**分布式登录的难点不在流程长,在「事实放在哪」——登录态放 Redis、地图真身放 space、择优决策放 appmgr;进程间的连接拓扑宁可全连,也要让故障以协议形态第一时间暴露。**
