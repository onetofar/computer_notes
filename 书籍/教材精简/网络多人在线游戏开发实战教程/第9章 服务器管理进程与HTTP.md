# 第9章 服务器管理进程与HTTP

> **小节地图**:§9.1 启动多个 login 进程 / §9.2 appmgr 管理进程 / §9.3–9.4 HTTP 与 Mongoose / §9.5 为 Packet 定义网络标识 / §9.6 HTTP 分块 / §9.7 机器人批量登录——全章精读。

## 9.1–9.2 问题与解法:谁来知道「所有进程都活着」

**问题**:单 login 进程成为登录瓶颈 → 起多个 login 进程 → **谁来给客户端挑一个合适的 login**?各 login 互不知道彼此的存在与负载。

**解法:appmgr 管理进程**(全服唯一实例):

```
login₁ ┐
login₂ ├──── 连接 appmgr ────▶ appmgr 汇总所有进程状态
login₃ ┘                        (HTTP 端口对外,供客户端/运维查询)
```

- 各 login 连上 appmgr,**上报自己的状态**;
- appmgr 对外开 HTTP 端口:客户端的 HTTP 请求到达时,appmgr **择优**分派一个 login;
- 运维视角:appmgr 就是「全服进程状态的一张表」——进程增减、负载变化都有单一观测点。

> 📖 [[第13章 云托管专用服务器|格雷泽第13章 §13.3]] 的「比赛安排服务与部署系统分离」同构:appmgr ≈ 安排/注册面,「启动哪些进程」≈ 部署面——**中心化的状态表 + 去中心化的工作进程**,是分布式游戏服务的通用骨架。

## 9.3–9.4 HTTP:一个游戏服务端为什么要会说 HTTP

- **对外面**:客户端选择接入点、运维健康检查、平台验证回传(第 4 章的 token 验证走的就是 HTTP)——这些都不适合用游戏的自定义 TCP 协议;
- **协议格式**:请求行 + 头部 + 空行 + 体;Mongoose(嵌入式 HTTP 库)负责解析——**游戏服务端嵌一个 HTTP 服务器**而不是另起 nginx,为的是少一个部署单元;
- §9.6 **HTTP 分块**(chunked):响应体分块传输——对游戏侧的意义是「解析器必须支持流式收块」,不能假设一次 recv 拿到完整响应。

## 9.5 为 Packet 定义新的网络标识

多进程互联后,Packet 流动于不同进程之间——需要**网络级标识**区分「这条包属于哪个进程连接」(进程间连接与客户端连接共用 net 层)。这是第 4 章 §4.7「消息按归属筛选」的跨进程升级版。

## 9.7 机器人批量登录

第 4 章的 Robot 压测扩展到**多进程拓扑**:批量 Robot 走完「HTTP 进 appmgr → 分派 login → 验证 → 进 game」全链——**压测的对象从服务端逻辑变成进程拓扑本身**(appmgr 分派是否均衡、login 是否线性扩容)。

## 章末判据

| 决策点 | 判据 |
|---|---|
| 多实例的入口选择 | 中心化管理进程(appmgr)持有全量状态并择优分派;进程间互知 = 网状复杂度爆炸 |
| HTTP 的位置 | 对外面(选点/健康检查/平台验证)走 HTTP,游戏内协议走 TCP——两栈并立 |
| 解析器 | chunked 等流式格式必须流式解析;「一次收全」的假设上线即碎 |

一句话结论:**本章把单进程服务端推向多进程:appmgr 用一张中心状态表解决「谁活着、选谁进」,HTTP 用对外面与游戏内协议解耦;进程管理的最小闭环 = 状态上报 + 择优分派 + 可观测。**
