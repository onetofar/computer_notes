## 游戏主循环 —— 服务端每一帧的两件事

> 原文锚点：第 3 章「线程、进程以及Actor模型」§3.4。
> 网络层的配合见 [[第2章 网络IO多路复用|2.2 epoll-Reactor工程纪律]]。

### 0 不论多少进程，每个进程一个主循环

§3.4 的起点是一句普适断言：**不论服务端框架有多少个进程，每个进程一定要有一个游戏主循环**。单线程结构下，主循环只做两件事：

1. **数据收集**——服务端的「操作」来自网络层，所以要不断探测网络层有没有新数据；
2. **更新世界**——根据收集到的数据推进游戏世界，并把更新广播给一个或多个终端。

```cpp
while (Game.IsRun) {
    UpdateNetwork();      // 输入：服务端不能用鼠标，网络 IO 就是它的输入模块
    UpdateAllWorlds();    // 推进：按收到的协议更新地图
}
```

客户端比服务端多做两件：监听设备输入、绘制（世界/NPC/模型/UI）。

### 1 两个概念锚点

**「网络层即输入」**：原文把 `UpdateNetwork` 定性为输入——服务器没有鼠标键盘，网络数据就是它的输入流。这个定性把「IO 与逻辑分离」从口号变成了结构事实：输入是主循环的一个阶段，不是散落在逻辑里的回调。

**「地图」的广义性**：3D 场景是地图，棋牌的房间也是地图。更新顺序**自底向上**：先地图内所有 Player 的状态，再 NPC、再 AI——依赖关系决定更新次序。

### 2 单线程循环的缺点与线程化的动机

顺序执行的结构缺陷原文点得很直接：**每次更新地图前，必须等网络层 IO 处理完成**——函数一个接一个执行，IO 的耗时直接吞掉逻辑的帧预算。最直接的改进就是把两件事拆到两个线程：一个 `UpdateNetwork`、一个 `UpdateAllWorlds`。

这正是第 3 章标题（线程、进程）的动机位置——主循环给不出并发，线程才有；而一旦引入线程，互斥与数据竞争随即登场（§3 后半的全部 mutex 话题都从这里长出来）。

### 3 判据表

| 决策点 | 判据 |
|---|---|
| 主循环形态 | 每进程必有；`while(IsRun) { IO; Logic; }` 是一切服务端框架的骨架 |
| IO 的身份 | 网络层 = 服务端的输入模块，与逻辑同帧序贯或异线程并行 |
| 世界更新次序 | 自底向上：Player → NPC → AI |
| 拆线程的时机 | IO 耗时开始挤压逻辑帧预算时；拆了就要面对互斥 |

一句话结论：**主循环把「服务端是什么」压缩成两行伪代码——收输入、推世界；它同时是并发的起点（IO 阻塞逻辑）和一切互斥问题的起点（拆线程之后）——骨架简单，边界难守。**

> **边界声明**：本节原文不含固定步长/补帧上限等内容——那些是项目层的帧结构设计，教材层不为其背书。原文层面，§3.4 就是「两功能 + 线程化动机」。
