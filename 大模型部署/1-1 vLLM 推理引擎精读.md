# vLLM 推理引擎精读

> **一句话**：vLLM 是模型与显卡之间的中间层，用「分页显存管理 + 连续批处理 + 前缀缓存 + 量化」四件套，把一张 GPU 能同时扛的请求数抬高一个数量级。
> **来源**：[《Vibe知识大赏 | 大模型推理引擎vLLM 是什么？》](https://www.bilibili.com/video/BV1Q8HP69EEB)（白/debug，13 分 08 秒，2026-10-24，属「硅基文明简史」合集第 17 集）
> **本篇定位**：按视频原有 8 个章节顺序讲透原理，**不重排、不扩写**；每一节末尾标出该节对应的视频时间戳，可回看核对。

---

## 0. 问题起点：为什么需要中间层

**视频原话**（00:00–01:17）：用 Hugging Face Transformers 把模型加载进来、对外提供 HTTP 接口，"能跑是能跑，但请求一多，后面的请求就只能排队干等，导致性能很差"。

于是问题变成：**在不增加 GPU 的前提下，怎么提升模型性能？**

> **视频原话**："没有什么是加一层中间层不能解决的，如果有，那就再加一层。"

vLLM 就是这一层。它的用法是执行一行 `vllm serve` 命令，起一个与 OpenAI 格式相同的 HTTP 服务；不同启动参数给出不同性能效果。

**关键认知（视频反复强调的因果链）**：
GPU 天生是并行计算的，内部几千个计算核心，"一次算一个请求跟一次算几十个请求耗时差不多"。所以提升吞吐的根本不是让单次计算更快，而是**让 GPU 一次算更多请求**。vLLM 的全部优化都指向这一点。

## 1. KV Cache：省计算的代价是吃显存

**视频原话**（01:17–03:01）：大模型生成文字是一个 token 一个 token 往外蹦。模型给每个 token 算两组数，K 和 V。可以把一句话抽象成一个"词块数据库"，查询键 Key 就是词块本身（K），Value 是词块背后的含义（V）。

生成的每个新 token 含义都依赖前面整句话说了什么，所以整个生成过程会不断查这个数据库。比如生成第 500 个 token 时，模型要拿着这个新 token 去前面 499 个 token 的 K、V 里查一遍，算出该重点参考谁。

> **视频原话**："而前面那些 token 的 K、V 算一次就定下来了，没必要每生成一个新 token 都重算一遍，存起来直接复用就行，每步只算新 token 自己那一份。"

这份按 token 存起来的 K、V 缓存就是 **KV Cache**。

### 1.1 它到底有多吃显存（视频给的数字）

| 场景 | 数值 | 出处 |
|---|---|---|
| LLaMA-13B，一个 2048 token 的请求，光 KV Cache | **1.6 GB** | 视频 01:40 |
| A100 40G 装完模型权重后剩余 | 十几 G | 视频 01:50 |
| 划出去的显存真正被使用率 | **两到四成** | 视频 02:50 |

### 1.2 内存碎片：Orca 式连续分配的代价

**视频原话**（02:00 起）：模型一次会生成多少 token 事先谁也不知道，所以像 Orca 这样的推理框架，会**一次性划一整块能放 2048 个 token 的连续显存**给每个请求。

问题随之而来：

> **视频原话**："如果输出的内容写不满，比如只写了 200 个 token，剩下 1800 多个位置就一直空着。就算空闲显存加起来明明足够下一次请求，但由于找不到一块完整且连续的显存，导致别人也用不了，需要等待请求跑完，显存释放，才能被再次利用起来。"

这种**空着却用不上的显存**就是常说的**内存碎片**。后果是划出去的显存只有两到四成被真正使用。

> 💡 **与操作系统同构**：这正是 OS 里「连续分配 → 外部碎片」的经典问题。视频的解法也正是 OS 的解法（见下节）。弹幕里大量"死去的操作系统知识开始攻击我的大脑"正是因为这条同构关系。

## 2. PagedAttention：把 OS 的分页搬进显存

**视频原话**（03:01–05:14）：操作系统内存管理以前也遇到过类似问题，解法是在物理内存之上抽象一层**虚拟内存**。程序申请内存时拿到的是一整块看起来连续的地址，可这些地址背后的数据实际被切成固定大小的小页，散落在物理内存各个角落。虚拟地址和物理地址的对应关系记在一个叫**页表**的地方。

### 2.1 vLLM 的对应翻译

| 操作系统 | vLLM | 说明 |
|---|---|---|
| 物理内存 | 显存 | 真正存放 KV 数据的空间 |
| 固定大小内存页 | **显存小块** | 每块存几个 token 的 K、V |
| 页表 | **块表** | token 的逻辑位置 → 显存实际位置的映射 |
| 虚拟地址空间 | 逻辑连续地址 | 对上层看起来连续，实际散落各处 |

**具体机制**（视频原话）：每块放 4 个 token，7 个 token 的 prompt 就占两块，第二块空着的一个留给下一个要生成的 token。将分散在显存各处的小块连起来，抽象出一层看起来连续的地址，然后把 token 的逻辑位置和显存实际位置的对应关系记在块表里。

模型生成新 token、需要用前面所有 token 的 K、V 做注意力计算时，就可以通过块表把需要的块逐个读出来。

> **视频原话**："效果其实就跟显存连续存放时一样，但好处是每个请求最多浪费最后一块没写满的几个，而且由于块大小一致，也就不存在空洞对不上的问题。显存利用率大大提高。"

这套把 KV Cache 按页分块存放、按块表读取的注意力算法就是 **PagedAttention**。

### 2.2 显存池：块被统一收集、反复复用

这些散落的块会被统一收集起来管理，形成**显存池**。请求需要块就从池子里领，用完归还，不断复用，省去反复申请和释放显存的开销。

### 2.3 两个关键参数

| 参数 | 视频给出的值 | 作用与调优判据 |
|---|---|---|
| `--gpu-memory-utilization` | 默认 **0.92** | 显存池大小。设小了，高并发时池子里的显存块会被快速分光，正在生成的请求需要新块时只能**先踢出一个请求**，把它的块腾出来给别人用——这个机制叫**抢占**。频繁出现抢占日志就说明池子设太小了，调大一点就好。 |
| `--max-model-len` | 可设 `auto` | 每次请求输入输出的最大长度。设成 `auto` 会自动选一个放得下的值。**业务用不到那么长就主动调小，这样能同时装的请求就更多。** |

> ⚠️ **与视频原话的一处出入**（官方文档核对）：`gpu-memory-utilization` 默认值 **0.92 准确**（vLLM 源码 `gpu_memory_utilization: float = Field(default=0.92, gt=0, le=1)`）。但 `max-model-len` 段落的「设成 auto」在当前 vLLM 版本中并非通用推荐——`auto` 取的是模型最大上下文，而模型最大上下文通常远大于业务实际需求，**照字面设 auto 等于放弃了这一层的调优**。视频那句「业务用不到那么长就主动调小」才是要点，此处顺序不能颠倒。

## 3. 前缀缓存：让相同开头的请求别重复算

**视频原话**（05:14–06:02）：到这里我们知道显存块是各请求自己领自己用的，但多个请求之间很可能有可复用的内容。

> **视频原话**："比如类似"你是一个专业设计师"这类系统提示词，每个请求的开头都是它，1000 个用户来问，这段开头就被算了 1000 遍，存了 1000 份。"

**机制**：给每个写满的块，按「它前面的全部内容 + 它自己的 token」算一个**指纹**。新请求进来先按指纹查，前面有一模一样的块就直接复用，**连计算都省了**。

开关是启动参数 `--enable-prefix-caching`。

> ⭐ **视频划的重点**："基于这个原理，我们写提示词时，如果能把**固定内容放前面，变化内容放后面**，缓存的命中率就能更高，性能也就更好，提升效果很明显。"

（视频配图给出该结构的示意：✅「固定在前」命中率 75%、耗时更短；❌「穿插」命中率 25%、耗时更长。）

## 4. 连续批处理：把批的单位从「一轮」缩到「一个 token」

**视频原话**（06:02–08:02）：有了 PagedAttention 和前缀缓存加持，单次请求的计算速度是更快了，但请求一多，后面的请求依旧只能排队干等。怎么提升并发度？

### 4.1 静态批处理的问题

最简单的办法是凑够一批一起跑，跑完再换下一批，这叫**静态批处理**。

> **视频原话**："可一批里有的请求生成 10 个 token，有的生成 500 个 token，短的跑完了也得占着位置等长的跑完，新请求需要等整批结束才能被处理，所以就会慢很多。"

### 4.2 连续批处理

既然模型本来就是一个 token 一个 token 生成的，那就把批的单位从一整轮缩到一个 token。

> **视频原话**："每生成一个 token，跑完的请求马上离场，归还显存块，新请求下一步就补进来。这种每生成一个 token 就重新排一次队的批处理策略就是连续批处理。"

每一步负责决定谁进谁出的组件叫**调度器**。

> 💡 **与操作系统同构**：这就是**时间片轮转**的翻版——一个请求只占一个 token 的时间片，跑完就换下一个。弹幕在 442 秒处直接刷了"时间片轮转"。

### 4.3 长 prompt 抢占：chunked prefill

即使有连续批处理调度，在较高并发场景下，**若某个用户输入超长 prompt**，它会长时间占用 GPU，导致其他请求干等。效果上就是大量用户看到回答吐到一半突然卡住。

解法是把长 prompt 拆成多个小段（chunk）分几轮处理，调度器在中间不断穿插其他请求，这样就不用非得等这个长 prompt 全部读完才轮到别人。

| 参数 | 视频给出的值 | 作用 |
|---|---|---|
| `--enable-chunked-prefill` | 模型支持的话**默认就开** | 拆段开关 |
| `--max-num-batched-tokens` | 官方建议追求吞吐时设到 **8192 以上** | 控制长 prompt 拆段时**每轮最多读多少 token**。设小一点输出更流畅，设大一点首字更快、吞吐更高。 |
| `--max-num-seqs` | A100、4090 等卡默认 **256**；H100、H200 默认 **1024** | 控制**一步最多同时算多少个请求** |

> ⚠️ **与视频原话的一处出入**（官方文档核对）：`max-num-seqs` 的「A100/4090 → 256，H100/H200 → 1024」**准确**（当前 vLLM 按设备分档：H100/H200/B200 为 1024，A100/L40S 及显存 < 70 GiB 的卡为 256）。但 `max-num-batched-tokens` 的默认值是 **2048**，视频说的「8192」是**追求吞吐时的建议值而非默认值**——两者不能混为一谈。

## 5. 量化：让小显存的卡也装得下大模型

**视频原话**（08:02–09:13）：大模型本质上是一大堆数字组成的网络，训练完的参数存在这些数字里，业内管它们叫**权重**。这堆数字动辄几十 G，其实不是所有显卡都装得下。

**降精度的账**：权重每个数原本需要两字节（FP16），压到一字节（FP8），**显存就减半**；由于计算位数变少，性能也会更快。代价是损失一些精度，但按经验来说精度损失一般影响不大。

| 参数 | 用法 |
|---|---|
| `--quantization` | 量化方式。下载的已量化模型一般能自动识别，**不用手动传参**。只有原版模型想现场压成 FP8 时才传 `fp8`。可选值还有 **AWQ、GPTQ** 等。 |
| `--kv-cache-dtype` | 设为 `fp8` 能把 KV Cache 也压成一字节，**显存池能放的 token 数翻倍**。 |

> ⭐ **视频的实战判断**："按我多年调优的经验来看，它是所有优化手段里提升最明显的方法，没有之一。"

（注意与上一节的区分：`quantization` 压的是**权重**，`kv-cache-dtype` 压的是**KV Cache**。前者省的是模型装不装得下，后者省的是能同时塞多少请求。）

## 6. GPU Worker 与 Engine Core：两个进程角色

### 6.1 GPU Worker

**视频原话**（09:13–09:53）：到这里我们已经用 KV Cache 和前缀缓存避免了大量重复计算，用 PagedAttention 大大提升显存利用率，让一张卡能同时装下更多请求，通过连续批处理把 GPU 利用率打满，再通过量化让小显存的卡也装得下大模型。

**这些能力可以通过一个进程封装起来，就叫 GPU Worker**。它主要负责将模型权重加载到 GPU 中，并进行一系列计算操作。**默认一个 GPU Worker 负责一张 GPU 卡。**

### 6.2 单卡装不下怎么办

对于超大 MoE 模型（比如满血版 DeepSeek），单张卡显存就是放不下。

| 方案 | 参数 | 视频的评价 |
|---|---|---|
| CPU offload | `--cpu-offload-gb`，传 20 就是借 20GB 内存放权重，用到哪块搬哪块 | "搬来搬去很慢，**自己体验还行，正经对外服务扛不住**" |
| 张量并行 | `--tensor-parallel-size`，传 2 就是两张卡一起分摊 | 把每一层的计算切开，多张卡各算一部分、各存一部分权重。**代价是每层算完卡之间都要通信**，所以最好有 NVLink 这种高速互传。 |
| 流水线并行 | `--pipeline-parallel-size`，传 4 就是模型切成 4 段放在 4 张卡上 | 按层切，前一半层放一张卡，后一半放另一张，只在交接时传数据，**通信少，但请求要依次走过所有卡，延迟高一些**。 |

### 6.3 Engine Core

多张卡意味着有多个 GPU Worker，这时候需要一个角色负责**分配请求到多个 GPU Worker**，负责**协调长 prompt 的分段、显存块的分配和抢占**。

> **视频原话**："于是，我们就可以将这些调度和管理的能力从 Worker 里抽出来，集中放到一个叫 Engine Core 的进程组件里，让它负责调度器和相关的管理功能。多个 GPU Worker 由它统一指挥，屏蔽了多卡并行的复杂度。"

### 6.4 加上 API Server 就是 vLLM

有了 Engine Core 和 GPU Worker 的加持，不管是单张卡还是几十张卡的集群，都能轻松把大模型跑起来。在这个基础上加入 **API Server**，对外暴露跟 OpenAI 一样格式的 HTTP 接口，也就成了熟悉的大模型 API。

> **视频原话**："这些能力共同构成了一个高性能大模型推理服务引擎——vLLM。"

## 7. 一个完整请求的全程

**视频原话**（11:00–12:40）串起来的完整链路：

1. 用户发来一句话 → 请求先打进 vLLM 的 **API Server**，被切成 token 交给 **Engine Core**。
2. Engine Core 里的**调度器**拿到 token，**先查前缀缓存**，开头相同的部分直接复用。
3. 剩下的 token 按需从**显存池**里领 **KV Cache 块**。
4. 调度器用**连续批处理**让这个请求跟其他几十个请求挤在同一步里，一起交给 **GPU Worker** 去算。
5. GPU Worker 开始用 **PagedAttention** 逐步推理。算注意力时按**块表**把块在显存里的散落位置找出来读出来算。
6. 每生成一个 token 就把它追加到序列末尾，作为下一轮计算的输入。
7. 大模型逐 token 往外生成，**写满一块就再领一块**，直到生成结束，**把手上所有的块都还回显存池**。

## 8. 调优：用 `/metrics` 观测，而不是猜

**视频原话**（12:40–13:08）：调用 API Server 提供的 `/metrics` 接口可以观察到很多内部指标。通过观察指标和调整参数，可以更方便地实现性能调优。

### 8.1 症状 → 病因 → 处方

| 症状（观测到的） | 病因 | 处方（视频给出） |
|---|---|---|
| KV Cache 使用率接近 1、排队请求一直不为 0、**抢占次数持续上涨** | 池子不够用 | ① 把 `--gpu-memory-utilization` 调大，给池子多分配显存；② 或把 `--max-model-len` 调小，卡住请求长度上限，**超长的请求直接拒掉**，同样大的池子就能装下更多请求；③ 实在不行开 `--kv-cache-dtype fp8`，让每个显存块能存放更多 token。 |
| **前缀缓存命中率偏低** | 提示词顺序问题 | 检查提示词顺序：**固定内容放前面，变化内容放后面**。 |

> 💡 这张表是本篇最实用的部分——它把「指标异常」直接映射到「改哪个参数」，是可直接照做的调优路径。

## 9. 评论区勘误与补充

> ⚠️ **本节内容全部来自 B 站评论区读者，不是 UP 主在视频中的原话**，也未经官方文档背书。已尽量标注来源与可信度。凡与第 1–8 节（视频原话）冲突处，以视频原话 + 官方文档为准；本节仅作补充视角。

### 9.1 LMCache：把淘汰的 KV 存到硬盘

**来源**：评论区高赞评论（用户「取名咱这么难」，91 赞）。

> 原文："vllm 可是一個大坑，裡面的深度太可怕了，這個引擎是幾乎所有資料中心都在用的基礎。我們不會拿 llamacpp 來提供服務，因為他不像 vllm 為了大規模服務設計。順帶一提，vllm 還有一個好朋友 lmcache，可以把顯存中淘汰出的 kv 放到硬碟，這也是資料中心提供服務的一大重點設施，因為從硬碟把 kv 讀回來遠比重新 prefill 要快也更省電。"

**扩展要点**：

- **为什么需要**：vLLM 的显存池快满时，**算好的 KV 会直接报废**（视频第 8 节说的「抢占」的另一面）。LMCache 的作用是把被淘汰的 KV 存起来，下次请求进来直接命中缓存，不用重新 prefill。
- **为什么值**：从硬盘读 KV **远比重新 prefill 更快也更省电**——prefill 是算力密集的，硬盘读是 IO 密集的。
- **定位**：这是**数据中心**做大规模服务的重点设施，不是家用场景的必要件。

### 9.2 TP 的真实效率：PCIe 是瓶颈，NVSwitch 才是答案

**来源**：同一条评论 + 其下回复（用户「取名咱这么难」）。

> 原文："至於雙顯卡 TP2，pcie4.0 16x 足夠，並行效率約 87%，四張顯卡在 pcie4.0 才會撞到 all reduce 通訊瓶頸讓 decode 效率只剩下 55%（家用 3090 在 pcie4.0 64x 基板上 每卡 16x 的實測數值）。真正的並行方案是伺服器 SXM 顯卡的板上 NVswitch，這個東西是更好的 NVlink，可以把 4 或 8 或更多伺服器顯卡，用 all2all 與 900GB/s 的頻寬連接起來，遠比 pcie4.0/5.0 16x 的 32, 64GB/s 要快，突破通訊瓶頸，讓記憶體頻寬的堆疊效率可以接近相加。例如 H200 單張 4.8TB/s 在 switch 下四張並行推理可以到約 16TB/s，家用級顯示卡不可能到達這種速度，光是 pcie 通訊瓶頸就要你命。"

**扩展要点（带宽账）**：

| 互连方式 | 带宽 | 4 卡并行可达 |
|---|---|---|
| PCIe 4.0 x16 | 32 GB/s（单向） | 撞 all-reduce 瓶颈，decode 效率剩约 55% |
| PCIe 5.0 x16 | 64 GB/s（单向） | 仍不及 NVSwitch |
| PCIe 4.0 x16（家用 3090，每卡 16x） | — | 双卡 TP2 并行效率约 87% |
| **SXM 板载 NVSwitch（all2all）** | **900 GB/s** | H200 单卡 4.8 TB/s × 4 ≈ **16 TB/s**，带宽堆叠效率接近相加 |

> 💡 **与视频的关系**：视频第 6.2 节只说「张量并行的代价是每层算完卡之间都要通信，最好有 NVLink」，评论区把这句话量化成了具体数字，并指出**家用显卡的真正天花板是 PCIe 而不是算力**。

### 9.3 `max-model-len` 不该设小（对视频第 2.3 节的修正）

**来源**：同一条评论。

> 原文："有一個沒說好的地方是 max-model-len，基本上只需要直接設為模型最大值，因為 vllm 的處理是依照 kv 池子分配，假設池子有 500K，那麼可以塞 100 個 1k 請求，10 個 50k，或是 1 個 256k+一個 200k，所以限制上下文並沒有意義，引擎會自己管理好。"

**扩展要点**：视频说「业务用不到那么长就主动调小」，评论区认为这说法有问题——vLLM 按 KV 池子分配而非按请求长度预留，池子 500K 时可以塞 100 个 1k 请求、10 个 50k 请求，或 1 个 256k + 1 个 200k，**限制上下文没有意义，引擎会自己管理好**。

> ⚠️ **两说法的取舍**：视频的原意是「`max-model-len` 调小可以卡住上限、超长请求直接拒掉，避免单个长请求吃掉整个池子」（见第 8 节的处方②）；评论区的意思是「**不必**人为压低到业务用不到的长度」。二者并不完全矛盾——**保守做法是设成模型最大值以获得引擎的灵活调度，但保留对超长请求的拒绝策略**。视频第 8 节的「超长请求直接拒掉」正是补上了评论区没提的那一半。

### 9.4 PD 分离：视频没提的调度器真正解法

**来源**：同一条评论。**这是视频完全没覆盖的一块，也是评论区认为最关键的补充。**

> 原文："還有視頻沒提到的一個 PD 分離，是調度器的真正解決方案，具體來說是 prefill 的時候會和 decode 搶工作，導致 llm 的輸出看著'卡'，因為調度器在不斷切換 P 和 D，而 prefill 一次比 decode 一次的時間慢數百倍。PD 分離就是拆兩個 vllm 引擎出來，一個引擎專門做算力密集的 prefill，即時把算好的 kv 快取傳送到另一組專門跑記憶體頻寬密集的 decode。不過家用的話根本沒有這種預能搞兩組引擎，那就沒有做 PD 分離的必要了，本地多 agent 併的時候發卡卡的多有耐心一點就好。"

**扩展要点**：

- **问题根源**：prefill 和 decode 抢同一批 GPU。调度器在 P 和 D 之间不断切换，而 **prefill 一次比 decode 一次慢数百倍**——这会让用户感到「输出卡住」。
- **解法**：拆成两个 vLLM 引擎。引擎 A 专做**算力密集的 prefill**，算好的 KV 缓存即时传送给引擎 B；引擎 B 专做**显存带宽密集的 decode**。
- **为什么这个分工成立**：prefill 是矩阵乘、吃算力；decode 是访存密集、吃显存带宽。两者对硬件资源的诉求正好相反，拆开就能各自跑满。
- **落地条件**：需要两组引擎、跨组 KV 传输带宽，**家用场景做不到，也没必要**——本地多 agent 并发时「发卡卡的多有耐心一点就好」。

> 📌 评论区另有读者就该架构提问（是否需要在两个 vLLM 引擎上再包一层网关，会不会通信又成瓶颈，要考虑多机/单机拓扑）——**该问题截至抓取时未见 UP 主或高赞回复定论，此处仅记录，不作结论**。

### 9.5 TP 与 PP 的量化差异

**来源**：评论区回复（用户「skiuniverse」提问 → 「取名咱这么难」补充）。

> 原文："PP（流水线并行）比 TP（张量并行）延迟高，我的理解是：显卡的计算单元不足以并发完成单层网络的所有计算，所以仍是分多轮算。TP 下，每张卡只用承担单层的 1/N 计算量，计算轮数与耗时也就相当于 1/N（此次忽略显卡间同步耗时）；PP 下，每层计算耗时相比串行不变，因此总计算耗时仍与串行一致（忽略显卡间通信耗时），仅在请求均匀地利用上流水线上每张卡时，才能将平均耗时降为 1/N。"

补充要点：

- **PP 的流水线气泡**：PP=4 时，当同时只有 1 个请求进入，显卡会有 **25% 的时间在发呆**；当有 4 个或更多请求进入，显卡才会在 100% 时间工作。
  （⚠️ 评论区就"25% 还是 75% 发呆"有过一次往返追问，最终按字面表述记为 25% 发呆 = 75% 忙。）
- **TP 的带宽可加性**：算力与带宽在数学上看会**直接相加**——四张卡 TP4 等效于四倍算力与四倍带宽（理想无通信损耗），prefill 快 4 倍，decode 也快 4 倍。**实际上因为 all-reduce 导致 decode 远到不了 4 倍，不过 prefill 倒是能接近 4 倍。**
- **组合用法**：卡多时 TP 与 PP 搭配使用，依显卡通信延迟和带宽决定：**同主机内做 TP，不同主机上做 PP**，形成巨大集群。例如 16 张卡、4 台主机每台 4 张，就用 TP4 + PP4。
