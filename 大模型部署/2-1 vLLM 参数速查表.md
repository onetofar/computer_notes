# vLLM 参数速查表

> **来源说明**：下表参数与默认值整理自 [[1-1 vLLM 推理引擎精读|vLLM 推理引擎精读]]（视频原话），并逐项与 vLLM 官方文档核对。
> **标注约定**：
> - ✅ = 视频说法经官方文档核对**准确**
> - ⚠️ = 视频说法需要**加限定**才成立（见下方「出入说明」）
> - 📌 = 评论区读者补充，**未经官方文档背书**

---

## 一、显存与缓存

| 参数 | 默认值 | 作用 | 调优要点 |
|---|---|---|---|
| `--gpu-memory-utilization` | **0.92** ✅ | 显存池占整卡显存的比例 | 设小了→池中显存块被快速分光→正在生成的请求需新块时**抢占**（踢掉一个请求腾地方）。日志频繁出现抢占即说明池子太小，应调大。 |
| `--max-model-len` | 模型最大上下文（`auto` 取此值）⚠️ | 单请求输入+输出的最大长度 | **业务用不到那么长就主动调小**，能同时装的请求就更多。也可用来**直接拒掉超长请求**，防止单请求吃满池子。 |
| `--block-size` | 视版本 | 连续缓存块大小（以 token 计） | 视频举例「每块放 4 个 token」。块大小一致是 PagedAttention 不产生空洞的关键。 |
| `--kv-cache-dtype` | `auto` | KV Cache 存储精度 | 设 `fp8` 可把 KV Cache 压成一字节，**显存池能放的 token 数翻倍**。 |
| `--kv-cache-memory-bytes` | `None` | 手动指定每 GPU 的 KV 缓存字节数 | 未设时由 `gpu-memory-utilization` 推断。**一旦显式设置，此参数会忽略 `gpu-memory-utilization`**。 |
| `--enable-prefix-caching` | 视版本 | 前缀缓存开关 | 开销极小。开启后**提示词必须「固定内容在前、变化内容在后」**，否则命中率上不去。 |

---

## 二、批处理与调度

| 参数 | 默认值 | 作用 | 调优要点 |
|---|---|---|---|
| `--enable-chunked-prefill` | 模型支持则默认开 | 把长 prompt 拆成 chunk 分轮处理 | 不开的话，超长 prompt 会长时间独占 GPU，其他请求只能干等，用户侧表现为「回答吐到一半卡住」。 |
| `--max-num-batched-tokens` | **2048** ⚠️ | 每轮批处理最多处理的 token 数 | 视频给的是**吞吐建议值 8192 以上**（≠ 默认值）。**设小→输出更流畅；设大→首字更快、吞吐更高**。需与 chunked prefill 配合。 |
| `--max-num-seqs` | **A100/L40S/小显存卡 → 256**；**H100/H200/B200 → 1024** ✅ | 一步最多同时算多少个请求 | 按设备分档。**调到理论最大值**。显存够但利用率卡住时，优先动这个而不是动显存比例。 |

---

## 三、多卡并行

| 参数 | 默认值 | 作用 | 调优要点 |
|---|---|---|---|
| `--tensor-parallel-size`（TP） | 1 | 把每一层的计算切开，多卡各算一部分、各存一部分权重 | 每层算完**卡间要通信**，依赖 NVLink / NVSwitch。家用 PCIe 下双卡 TP2 效率约 87%，四卡撞 all-reduce 瓶颈后 decode 效率约剩 55% 📌。**prefill 接近线性加速，decode 受通信拖累** 📌。 |
| `--pipeline-parallel-size`（PP） | 1 | 按层切分，模型切成 N 段放 N 张卡 | 只在层间交接时通信，**通信少但请求要依次走过所有卡，延迟高**。⚠️ **流水线气泡**：PP=4 时仅 1 个请求进入则显卡约 25% 时间发呆，需 ≥4 个并发请求才能打满 📌。 |
| `--cpu-offload-gb` | 0 | 借用 CPU 内存放权重，用到哪块搬哪块 | 传 20 = 借 20GB。**自己体验还行，正经对外服务扛不住**（搬运开销）。 |

**TP / PP 组合规则** 📌：依显卡通信延迟和带宽决定——**同主机内做 TP，不同主机上做 PP**。16 张卡 / 4 台主机每台 4 张 → TP4 + PP4。

## 四、量化

| 参数 | 默认值 | 作用 | 调优要点 |
|---|---|---|---|
| `--quantization` | `auto` | 权重精度与量化格式 | 下载的**已量化模型一般自动识别，不用手动传**。原版模型想现场压成 FP8 才传 `fp8`。可选 **AWQ、GPTQ** 等。视频评价：「所有优化手段里提升最明显的方法，没有之一」。 |
| 权重精度 | FP16（2 字节/参数） | 基线 | 压到 **FP8（1 字节）→ 显存减半**，且计算位数变少→更快。代价是精度损失，但按经验影响不大。 |

> ⚠️ **别混淆两处量化**：`--quantization` 压的是**权重**（决定模型装不装得下）；`--kv-cache-dtype fp8` 压的是 **KV Cache**（决定能同时塞多少请求）。

## 五、观测与接口

| 接口 / 指标 | 用途 |
|---|---|
| `POST /v1/chat/completions` | OpenAI 兼容接口（`vllm serve` 默认提供） |
| `GET /metrics` | Prometheus 指标。**调优的唯一依据**——看指标异常再改参数，不要凭感觉调 |
| `vllm:gpu_cache_usage_perc` | KV Cache 使用率。**接近 1 + 排队请求不为 0 + 抢占次数持续上涨** → 池子不够用 |
| `vllm:num_requests_running` | 当前实际并发的请求数（= 你真实跑的 batch） |
| `vllm:num_requests_waiting` | 排队中的请求数 |

## 六、调优决策树

```
启动后先拉 /metrics
│
├─ 抢占日志频繁出现 / gpu_cache_usage_perc ≈ 1 / num_requests_waiting 不降
│   └─ 池子不够用，三选一（按代价从小到大）：
│       ① --max-model-len 调小，卡住上限，超长请求直接拒掉
│       ② --gpu-memory-utilization 调大（注意别超 0.95 太多，留峰值余量）
│       ③ --kv-cache-dtype fp8，每个块能放更多 token
│
├─ 前缀缓存命中率偏低
│   └─ 检查提示词顺序：固定内容放前面，变化内容放后面
│
├─ 显存只用了 60% 但 util 卡在 30% / QPS 上不去
│   └─ 优先调 --max-num-seqs（而不是显存比例）
│
└─ 输出吐到一半突然卡住
    └─ 确认 --enable-chunked-prefill 已开（长 prompt 独占 GPU）
```

> 💡 **一句话判据**：显存占得多**不等于**利用率高。瓶颈可能在**并发数上限**（`max-num-seqs`），不在显存。
