## 一、模型身份类

### 参数 / 参数量(Parameter)

模型里可训练的数字个数。`8B` = 80 亿个。写进文件名,如 `Qwen3-14B`。

- **参数量 ≠ 显存占用**。显存 ≈ 参数量 × 每权重字节数 + KV Cache + 计算缓冲。
- **参数量 ≠ 能力**。8.2B 的 Q6_K 比 14.8B 的 Q4_K_M 快,但理解力弱一档;两个维度要一起看。
- 名字里的 `14B` 是**取整值**。实测精确值是 14,768,307,200——算显存要用精确值,别用名字。

### 量化(Quantization)

把 16 位浮点权重压成更低位宽的整数。**唯一目的是让模型进得了显存**,不是"优化速度"。

| 档位 | 约 bpw | 相对 FP16 |
|---|---|---|
| `Q2_K` | 2.6 | 16% |
| `Q3_K_M` | 3.4 | 21% |
| `Q4_K_M` | 4.85 | 30% |
| `Q5_K_M` | 5.7 | 36% |
| `Q6_K` | 6.56 | 41% |
| `Q8_0` | 8.5 | 53% |

> 💡 在小显存卡上,**量化的意义是"把权重压到能放下,把省下的空间还给 KV Cache"**,
> 而不是"省显存换速度"。细节见 [[5-1 模型文件名怎么读：Qwen3-14B Q4_K_M 逐段拆解|5-1]]。

### bpw(bits per weight)

平均每个权重占多少比特。**是平均值,不是每个权重都一样**(K-quant 会混合位宽)。
反算公式:`bpw = 文件字节数 × 8 ÷ 参数量`——手上有文件和参数量就能验证厂商有没有虚标档位。

### K-quant

llama.cpp 的分块量化方案:按 super-block(256 权重)切块,块内分小组各带缩放系数,
**对误差敏感的张量升级位宽**。所以 `Q4_K_M` 的实际 bpw 是 4.876 而不是 4.0。

### GGUF

llama.cpp 的模型容器格式。一个文件装权重 + 元数据(分词器、量化参数、架构描述)。

## 二、推理过程类

### 上下文窗口(Context Window)

模型一次能"看见"的 token 总量。**输入 + 输出都算在里面。**

- 超了会怎样:要么报错(`prompt is too long`),要么**悄悄降级**——把部分层移出显存、层间走 PCIe,速度掉一个数量级但**不报错**。这是最容易被忽略的坑。
- 「上下文长度」和「模型能记多少东西」是两回事:它是**硬容量**,不是记忆力。

### KV Cache

自回归生成时,每一层为每个历史 token 缓存的 Key/Value 向量。

- **它决定上下文长度和并发数**,不决定模型聪不聪明。
- 占用 ≈ `2 × 层数 × 头数 × 头维度 × 序列长度 × 每元素字节数`,上下文翻倍它就翻倍。
- 量化它(`q8_0` / `fp8`)是**在小卡上换上下文最有效的一招**:精度损失小,省下的空间直接变成上下文长度。
- 日志里 `K (q8_0): 1360.00 MiB, V (q8_0): 1360.00 MiB` 是硬证据——看到 `q8_0` 才说明量化真生效了。

### Prefill / Decode(预填充 / 解码)

- **Prefill**:处理输入 prompt 的阶段。**并行**,吃的是算力,长 prompt 时它占大头。
- **Decode**:逐 token 生成。**串行**,吃的是显存带宽。
- ⚠️ 这解释了一个反直觉现象:**输入越长,首字越慢**;而"生成速度"看起来很稳,其实被 decode 带宽锁死了。

### FlashAttention

一种 attention 的计算实现:分块计算 + 在线 softmax,避免把整个 attention 矩阵写进显存。
**省的是显存和带宽,不是精度**。日志里的 `flash_attn = enabled` 是开关生效的证据。

### CPU 卸载(CPU Offload)

显存不够时,把部分层放主机内存、按需搬运。

- ⚠️ **被卸载的层每个 token 都要过 PCIe**。掉几层是"慢一点",掉三分之一是"换了个量级"。
- 看到 `ollama ps` 显示 `x%/y% CPU/GPU` 就说明已经在卸载了。**它不会报错,只会变慢。**

## 三、模型能力类

### 思考模型(Reasoning Model)

输出前先有一段内部推理的模型(Qwen3、DeepSeek-R1 等)。

- 格式上通常带 `<think>...</think>` 或独立的 `thinking` 块。
- ⚠️ **思考内容吃 `output` 预算**。`max_tokens` 给小了会出现「content 为空、finish_reason=length」——不是模型没答,是思考把额度用完了。
- 关闭方式**因协议而异**:`/api/chat` 支持参数 `think:false`;**`/v1/chat/completions` 不认这个参数**,只能靠提示词加 `/no_think`。
- ⚠️ 两套协议字段名不同:OpenAI 兼容端点叫 `reasoning`,Anthropic 端点叫 `thinking` 块。

### 工具调用 / Function Calling

模型不直接执行动作,而是输出一个「我要调用 f(参数)」的结构,由宿主去执行。

- 能力档位:**能输出结构** ≠ **会选对工具** ≠ **参数填得对**。
- 小模型常见的失败:被无关上下文带跑(把元数据当指令)、凭空捏造不存在的参数。
- ⚠️ **工具返回值要带单位**。模型做 bytes→GB 的心算会错(实测两次算错);服务端算好再返回,模型只转述。

### MoE(Mixture of Experts)

把 FFN 拆成多个"专家",每个 token 只激活其中几个。参数量大但**每 token 的计算量小**。

- 显存按**全部权重**算,速度按**激活部分**算——所以 MoE 是"显存换速度"的另一种形态。
- 常见误解:MoE 不等于"参数多所以更强",它换来的是**同等激活量下更大的知识容量**。

### LoRA / 微调

低秩适配:冻结原模型,只训练一对小矩阵。适配层通常几十 MB,不用重训全模型。

- 常见误区:**LoRA 训不了"新知识"**,它擅长的是**风格/格式/特定任务的行为**。
- 想要新知识,要么继续预训练,要么 RAG(检索增强)。

## 四、接口与部署类

### OpenAI 兼容 / Anthropic 兼容

同一套请求格式的不同实现。Ollama 两种都提供:

| 端点 | 协议 | 客户端 |
|---|---|---|
| `/v1/chat/completions` | OpenAI | 通用客户端 / MCode |
| `/api/chat` | Ollama 原生 | `ollama` CLI |
| `/v1/messages` | Anthropic | Claude Code |

### `keep_alive` / `OLLAMA_KEEP_ALIVE`

模型在显存里待多久。`0` = 立刻卸载,`-1` = 永不。

- ⚠️ **API 里传 `keep_alive: "-1"` 会 400**——只能**在服务端**设环境变量。
- 默认 5 分钟:空闲后踢出显存,下次请求白等 20s 重载。

### `num_ctx`

单次请求的上下文大小。**超过模型原生训练长度会被钳回**,并打一条 WARN。
(实测:Qwen3 请求 65536 → 钳回 40960。)

### 吞吐 / 并发相关

| 词 | 含义 |
|---|---|
| **tokens/s** | 生成速度,通常指 decode 阶段 |
| **TTFT** | Time To First Token,首字延迟;长 prompt 时它才是体验瓶颈 |
| **batch / 连续批处理** | 把多个请求拼成一批算,**并发吞吐**的关键;单流场景收益有限 |
| **prefix caching** | 复用相同前缀的 KV,多轮对话省算力 |
| **PagedAttention** | 把 KV Cache 像分页内存一样管理,消除碎片 |

> 💡 **单流 vs 并发是两种完全不同的优化方向。**
> vLLM 的长处在后者,llama.cpp 的长处在前者(单请求延迟低、显存占用可控)。
> 选引擎前先确认自己是哪一种场景。

## 五、随手查的速查表

| 问自己 | 去哪看 |
|---|---|
| 这个模型多大?装得下吗? | 参数量 × 量化档位 → 权重 GiB,再加 KV + 缓冲 |
| 上下文能开到多少? | `ollama ps` 的 CONTEXT 列 + PROCESSOR 列是否 `100% GPU` |
| 为什么变慢了? | PROCESSOR 列出现 `CPU/GPU` = 掉层 |
| 思考内容在哪? | OpenAI 端点 `message.reasoning`;Anthropic 端点 `thinking` 块 |
| 为什么 content 是空的? | 思考吃光了 `max_tokens`;给足额度或 `/no_think` |
| KV 量化生效了吗? | 日志里 `K (q8_0)` / `V (q8_0)` |
