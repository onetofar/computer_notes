# Windows 原生推理选型:从约束到参数的决策链

> 这篇回答一个问题:**在这台机器上跑本地大模型,每个决策是怎么定下来的。**

## 零、先认约束（约束决定后面每一步）

| 约束 | 事实 | 来源 |
|---|---|---|
| 显存 | RTX 3080 **12 GB** | `nvidia-smi` |
| 桌面占用 | 桌面已搬到**核显**,3080 空闲基线 **151 MiB** | 用户 2026-10-28 |
| 引擎平台 | vLLM **无原生 Windows 支持** | vLLM 官方 |
| 目标场景 | **单人 / 单流 / 短任务**,不是多用户并发 | 4-2 的分工表 |
| 网络 | HuggingFace 不可达 → 模型走 ModelScope | 3-1 已踩过 |

> 💡 这五条里,**「单人单流」是最关键的一条**。它直接否掉 vLLM 的主战场(多请求并发),
> 也决定了后面选 14B 而不是 30B——把省下来的并发余量全换成模型能力。

## 一、引擎:为什么是 Ollama

### 1.1 候选与否决理由

| 候选 | 否决 / 选中理由 |
|---|---|
| **vLLM** | ❌ 无原生 Windows;且它的四个核心机制(PagedAttention / 连续批处理 / 前缀缓存)全是为**多请求并发**设计的,单人单流用不上;留它就得留在 WSL,而 WSL 已退役 |
| **llama.cpp 直跑** | ⚠️ 实测可行(8B Q6_K、ctx 32768、104.5 tok/s),但缺模型管理层:多模型切换、别名、采样参数固化都得自己写脚本 |
| **Ollama** | ✅ **底层 runner 就是 llama.cpp**(`ollama ps` 的 RUNNER 列实测为 `llamacpp`),所以**不是拿性能换便利**,只是在同一个后端上加了 Modelfile / 模型注册 / 别名这一层 |
| **LM Studio** | ❌ GUI 为主、CLI 弱;工作流是命令行,不需要带界面的壳 |
| **TabbyAPI / exllamav2** | ❌ 吞吐向,Windows 支持差;单人单流不需要 |

### 1.2 一个副产品:它同时说两种协议

Ollama 0.40.11 除了 OpenAI 兼容的 `/v1/chat/completions`,**还实现了 Anthropic 的 `/v1/messages`**:

```
POST /v1/messages  (anthropic-version: 2023-06-01)
→ 200 {"type":"message","content":[{"type":"thinking",...}]}
带 tools:
→ stop_reason: "tool_use"
   block type=tool_use  name=list_dir  input={"path":"F:\\LLM\\models"}
```

⇒ **Claude Code 这类只讲 Anthropic 协议的客户端可以直连 Ollama,不需要 claude-code-router / LiteLLM 转译层。**
这条改变了引擎选型的成本计算:原本「用 vLLM 就得留在 WSL」的隐含理由是**协议与平台绑死**;
现在一个原生 Windows 的引擎同时说两种协议,换客户端的边际成本从「加一层代理」降到「改一个环境变量」。

⚠️ 两套协议各说各的,别混:`/v1/chat/completions` 里思考内容在 `message.reasoning`,
`/v1/messages` 里是标准 Anthropic 的 `thinking` 块。

## 二、模型:14B 是 12G 整卡的天花板

| 候选 | 结论 |
|---|---|
| **Qwen3-14B Q4_K_M**(选) | 权重 8.38 GiB,总占 **10442 MiB**,**41/41 层全上卡**,**82.1 tok/s** |
| Qwen3-8B Q6_K(保留) | 6.26 GiB / 8986 MiB / 112.4 tok/s;快 37%,质量低一档 |
| 14B Q5_K_M 及以上 | 权重 ≥9.8 GiB,KV 只剩不到 1G → 上下文开不满,回到 3-1 那个死结 |
| 20B / 30B / 32B | 权重远超 12G → 必须 CPU 卸载,**被卸载的层走 PCIe,速度掉一个数量级** |

> 💡 判据:**在 12G 卡上「更大的模型」是假升级**。
> 真正决定体验的是「权重 + KV + 计算缓冲」能不能**同时**留在卡里;留不住的层不是"稍慢",而是被 PCIe 接管了。
> 14B Q4_K_M 正好卡在这个边界内——再大一档就越界,小一档就浪费。

**速度实测**(三次复测,抖动 <1 tok/s):

| 模型 | 量化 | 上下文 | 速度 | 显存 | 上卡 |
|---|---|---|---|---|---|
| qwen3-14b | Q4_K_M | 20480 | **82.1 / 82.2 / 82.1** | 10442 MiB | 41/41 |
| qwen3-8b | Q6_K | 32768 | 112.4 / 112.3 / 112.7 | 8986 MiB | 37/37 |

## 三、参数:每个值都对应一个已测事实

| 参数 | 值 | 依据 |
|---|---|---|
| `OLLAMA_HOST` | `0.0.0.0:11434` | 默认只绑 127.0.0.1,局域网(以及跨机调 Claude Code)连不上 |
| `OLLAMA_KV_CACHE_TYPE` | `q8_0` | KV 量化,把省下的空间还给上下文;日志实测 `K (q8_0) / V (q8_0)` |
| `OLLAMA_FLASH_ATTENTION` | `true` | 日志实测 `flash_attn = enabled` |
| `OLLAMA_KEEP_ALIVE` | `-1` | 默认 5 分钟空闲就踢出显存,下次请求白等 20s 重加载 |
| `OLLAMA_MAX_LOADED_MODELS` | `1` | 多模型同驻要算双份显存 + 双份内存 |
| `OLLAMA_NUM_PARALLEL` | `1` | 单人场景,不给并发槽分 KV |
| `num_ctx`(模型级) | 14B: **20480** / 8B: **40960** | 见下一节 |

### 3.1 上下文上限是实测出来的,不是拍出来的

Ollama 按保守显存预算决定上卡层数,**越过边界不会报错,只会悄悄把几层踢回 CPU**:

| num_ctx | 上卡层数 | 判定 |
|---|---|---|
| 16384 / 18432 / **20480** | 41/41 | 全上卡 |
| 21504 | 40/41 | 开始掉层 |
| 22528 | 40/41 | 7% CPU |
| 24576 | 39/41 | 9% CPU |
| 32768 | 36/41 | 16% CPU |

**判据永远看 `ollama ps` 的 PROCESSOR 列**:`100% GPU` 才算过;
出现 `x%/y% CPU/GPU` 就已经掉层了。**别用速度去感觉**——32K 时模型照样回话,只是部分层在走 PCIe。

### 3.2 Qwen3 的天花板是 40960,再往上没意义

```
WARN "requested context size too large for model" num_ctx=65536 n_ctx_train=40960
```

请求 49152 与 65536,服务端**都钳回 40960**——两次结果显存完全相同(9636 MiB / 37/37 层)。
所以 14B 换不来更大上下文,只能换来更慢:**14B @ 40960 是 34/41 层、27.8 tok/s**。

## 四、代价:这张卡上的真实账

| 项 | 数值 |
|---|---|
| 权重 14B Q4_K_M | 8.38 GiB |
| KV Cache(q8_0 @ 20480) | ~2.6 GiB |
| 计算缓冲 | ~0.3 GiB |
| **合计** | **10442 MiB / 12288 MiB**(余 ~1.8G) |
| 系统内存占用(`llama-server` WS) | ~4.2 GiB(含 mmap 页缓存) |
| 整机物理内存 | 30.8 GiB |

⚠️ **即使显示 `100% GPU`,也仍有 486.86 MiB 权重留在系统内存**(`CUDA_Host model buffer`)——这是 llama.cpp 的正常行为,不是配置错。
但 14B @ 40960 掉层那次是 **1773.91 MiB 在内存**,每个 token 都要过一遍 PCIe——**速度从 82 掉到 27.8 就是这个原因**。

> 💡 判据:**显存决定"放不放得下",内存决定"掉层时还活不活",磁盘决定"第二次能不能秒开"**。
> 三者里只有显存是无法用参数绕过的硬墙,另外两个可以靠"少驻留、按需加载"缓解。

## 五、失效条件

| 条件 | 后果 |
|---|---|
| **桌面搬回 3080** | 可用显存少 ~0.9G,20480 会掉层 → 回退 16384 |
| **换 16G 卡**(4080 / 4070Ti Super) | 14B Q5_K_M 甚至 32B Q4 可全上卡,这张选型表要重算 |
| **需要多用户并发** | 回 vLLM(在 Linux 上),Ollama 不是干这个的 |
| **Ollama 支持 `/v1` 的 `think=false`** | 提示词 `/no_think` 那套 workaround 可以去掉 |
| **Ollama 修了 `ollama create` 的复制行为** | 磁盘翻倍那条消失 |
