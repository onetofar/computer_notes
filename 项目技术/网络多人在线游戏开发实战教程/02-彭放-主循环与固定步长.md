## 原理

两种主循环写法：

```cpp
// ✗ 睡固定时长，跑一帧
//    （工程经验；彭放 §3.4 给的循环里并没有 sleep，是原书省略了等待）
while (running) {
    do_io();
    update_world();
    std::this_thread::sleep_for(10ms);   // 实际帧长 = 10ms + 收包耗时 + 逻辑耗时
}
```

```cpp
// ✓ 固定步长累加器
while (running) {
    const int64_t now = steady_clock_ms();
    const int timeout = clamp(next_tick_ms - now, 0, 50);
    reactor.Poll(timeout);                    // 睡到下一个 tick，或有事件就提前醒
    while (scheduler.NextTickMs() <= now) {  // 补帧
        tick_all(scheduler.TickIndex());
        scheduler.Advance();
    }
    flush_snapshots(now);
}
```

关键差别：

1. **累加而非重置**：`next += TICK`，不是 `next = now + TICK`。
   重置会丢掉超出的时间片，长期累积成"逻辑时间走得比墙钟慢"。
2. **补帧循环在 while 里，不在 if 里**：一帧内可能需要追多个 tick。
3. **Poll 的 timeout 来自"距下一个 tick 多久"**，于是**网络等待和逻辑等待合并成一次**——
   有包就提前醒，没包就睡到点，两者不互相拖累。

## 成立条件 / 失效边界

| 条件 | 说明 |
|---|---|
| 时间源是**单调钟** | 必须 `steady_clock`，不能用 `system_clock`——后者会被 NTP 校时回拨，回拨一次 `now < next` 永远成立，补帧死循环 |
| 步长与玩法参数**整除** | 前摇 0.6s / tick 0.05s = 12 tick、攻击 5、硬直 8、CD 50——全部整除，无余数误差 |
| 快照频率**整除** tick 频率 | 20 Hz / 10 Hz = 每 2 tick 发一次。跨 tick 边界的快照会让"这个 tick 的状态"没有唯一时刻 |
| **补帧有上限** | 卡顿 1 秒后最多追 N 帧（5 帧 / 250ms），其余丢弃 |

**补帧上限是必须的**，理由：进程被换出 30 秒后唤醒，
不设上限就要跑 600 个 tick 才开始收下一个包——客户端已经超时断线了。
宁可快照跳变（丢几帧，画面跳一下）也不雪崩（服务不可用）。

## 明确拒绝的做法

| 做法 | 来源 | 为什么拒绝 |
|---|---|---|
| `sleep_for(10ms)` 驱动主循环 | 工程经验 | 没有固定步长累加器，掉帧会让 tick 号随机漂移。表现为"全端同一事件的 `effective_tick` 对不上"，且只在负载高时出现 |
| `next = now + TICK` 重置式 | 常见写法 | 丢掉超出的时间片，逻辑时间长期慢于墙钟。表现为"玩久了 Boss 动作越来越顿" |
| `system_clock` | 常见写法 | NTP 回拨会让 `now < next` 恒成立，补帧死循环 |
| 补帧不设上限 | 直觉写法 | 进程唤醒后追几百帧才收下一个包，客户端已超时。**宁可跳变不可雪崩** |

## 易错点

- **"固定步长"不等于"每帧固定耗时"**。它固定的是**逻辑时间片**，
  实际帧耗时可以抖动。搞混会写出"把逻辑绑到渲染帧上"的错误架构。
- **整除关系要双向检查**：不仅"tick 能整除 0.6s"，还要"快照频率能整除 tick 频率"。
  后者被忽略时症状很隐蔽——快照在 tick 边界上随机落点，
  同一 tick 的世界状态没有唯一快照时刻，插值会算出不存在的时间点。
- **丢包外推必须有上限**（例如 200ms）。无上限外推比卡住更糟：
  实体一路飞到墙里，看起来像 bug 而不是网络问题。
