## 机制

### 第 1 层：传输保密（§10.1）

- **中间人攻击**：路由路径上的机器（公共 Wi-Fi 同网段、网关、ISP）可读全部流量。对策 = 公钥加密：客户端持服务器公钥，登录凭证用其加密，只有服务器私钥能解。RSA 的可行性建立在大半素数分解无多项式时间算法上（1024/2048 位暴力不可行）；**用 OpenSSL 等经过验证的实现，不要自己造**。
- **加密的适用边界（原文的决策树）**：有微交易/登录账户 → 相关数据必须加密（PCI DSS 可能是法律要求）；只传输复制状态 → 中间人截获无所谓，可不加密。
- **主机嗅探防不住**：游戏可执行文件总含有解密逻辑，客户端可被逆向。加密 + 定期换钥匙/换包格式只是**抬高逆向成本**的拖延术。必须接受"主机上的一切数据都可被作弊者读取"。
- **因此真正的对策是信息作弊的对价**：玩家嗅探是为了**信息作弊**（拿不该知道的信息）。唯一结构性对策 = 服务器**只发该客户端需要知道的数据**（例：隐身角色的位置更新干脆不发）。这在 C/S 上可行，P2P 上做不到（全量状态本来就发给每个人）。

### 第 2 层：输入验证（§10.2）

原则一句话：**不盲目执行来自网络的任何操作**。两层验证：

1. **动作有效性**：收到"玩家 A 开火"先查——A 有武器吗、有子弹吗、冷却结束了吗。任一不满足就拒绝。
2. **命令归属**：C/S 下每个主机地址绑定一个客户端代理，移动命令只允许应用到自己的代理上；P2P RTS 下命令与发出者绑定，执行时拒绝操控他人单元的命令。

**假阳性宽容**是本层最容易被忽略的准则。原文的完整反例链：玩家 A 被"沉默"→ 服务器发出沉默更新包 → **包还在路上**时 A 施了一法 → 服务器按当前时刻验证：无效操作，但毫无恶意。归因不是"玩家撒谎"而是**验证时刻错位**——按动作发生时刻验就没事（延迟补偿与输入验证是配套的）。踢掉他是错的，默认动作是**保守地拒绝**，并把误杀率当作与漏杀率同级的设计参数。

**服务器坏数据的验证死角**：客户端几乎无法验证来自权威服务器的命令（客户端间不能直连、信息也不全）。玩家自己托管服务器时，P2P 交叉验证的补丁（B 扔球时同时广播给所有人，A 收到服务器版本可与 B 的副本对证）有两个结构性漏洞：①客户端间未必互相可达（NAT/防火墙）；②对等包不保证比服务器包先到——要么等（加延迟）要么放弃验证。**唯一干净的解：不要让玩家托管，用云托管专用服务器**（§13）。

### 第 3 层：软件作弊检测（§10.3）

主动性防守：扫描游戏进程内存、检测已知作弊程序。作弊软件的四种形态（原文分类）：**嵌入游戏进程**的、**重写游戏进程内存**的、**第三方自动化程序**（外挂 bot）、**修改游戏数据文件**的——软件检测对四类都有覆盖。能抓到前两层抓不到的：

- **地图黑客**（lockstep 全量状态在每个对等体内存里，迷雾只是本机渲染开关——传输层证据完全正常，只有客户端完整性检测能抓）；
- **机器人外挂**（MMO 挂机打金、FPS 自瞄）。

两个工业实例：

- **VAC（维尔福）**：扫描内存查已知作弊；命中**不当场禁**，记账后择日一次性**禁止波**（ban wave）——让作弊者无法定位是哪次行为暴露的，最大化抓捕面。配套的**纯服务器**（pure servers）：校验客户端文件校验和，发生在**连接时与换图时两处**（原文明确两处）；有定制外观类玩法就把那些文件路径加白名单，其余不匹配即踢。
- **Warden（暴雪）**：同样扫内存，但检测逻辑**运行时动态更新**——补丁日不发作的老外挂，可能在 Warden 静默更新后被抓。

### 第 4 层：保护服务器（§10.4）

- **DDoS**：让服务器连接饱和或算力耗尽，对合法用户不可用——原文断言"几乎每一个主流网络游戏或在线游戏服务器都曾经受到过 DDoS 的影响"。自有硬件 = 与 ISP 密切合作 + 潜在硬件升级 + 流量分摊；云托管可把一部分防护交给云商（内置分级防护 + 可购专项服务），但**不能假设云商全包**——准备与演练仍是自己的事。
- **坏数据**：恶意畸形包让服务器崩溃或借缓冲区溢出执行代码。对策 = **模糊测试**：向服务器灌大量非结构化数据，同时用"预期签名 + 随机负载"的**结构化模糊**——后者命中率更高。迭代修复。
- **时序攻击**：任何"期望签名 vs 收到签名"的比较代码都暴露在它面前——提前返回的比较函数，返回时间泄露了第一个不匹配的位置，逐字节试出完整密钥。对策 = **常时比较**（见下方代码）。
- **入侵**：全软件保持最新（旧版本的已修复漏洞是现成的入侵方案）、限制服务数量（缩小入侵面）、双因素认证（"只知道密码"不再够用）、防**鱼叉式钓鱼**（先打开发者的个人机再跳板进中央服务器——开发机也是防线）、敏感数据按行业标准存储、日志与审计（最大威胁常是**内部人**：心怀不满的员工）、**线下备份**（最坏情况下损失从"永久失去所有数据"降级为"一次恢复操作"）。

**常时比较的两版代码（清单原文）**：

```cpp
bool Compare(int a[8], int b[8])
{
    for (int i = 0; i < 8; ++i)
    {
        if (a[i] != b[i])
        {
            return false;
        }
    }
    return true;
}
```

```cpp
bool Compare(int a[8], int b[8])
{
    int retVal = 0;
    for (int i = 0; i < 8; ++i)
    {
        retVal |= a[i] ^ b[i];
    }
    return retVal == 0;
}
```

## 原书的数字与工程建议

| 原文位置 | 数字 / 建议 |
|---|---|
| §10.1.1 | RSA 典型 **1024/2048 位**半素数；用 OpenSSL，不自研 |
| §10.4.3 | 常时比较的标准写法：逐元素 XOR 再 OR 归约，看结果是否为 0 |
| §10.4.2 | 模糊测试要**随机数据与结构化数据并用**（结构化 = 预期签名 + 随机负载） |
| §10.2 | 无效输入默认**拒绝**而非踢人——延迟/丢包造成的假阳性很常见 |
| §10.3.1 | 禁止波策略：延迟禁止、一次性批量执行；纯服务器在连接与换图两处校验 |
| §10.4.4 | 密码必须用**慢**哈希（原文推荐河豚 bcrypt）+ 不存明文；审计 + 线下备份是底线 |
| §10.1.1 | 公共 Wi-Fi 场景 = 最容易复现的 MITM 课堂 |

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| C/S 拓扑 + 服务器做相关性过滤 | 信息作弊面 = 该客户端收到的子集 | P2P：全量状态人手一份，只能靠客户端检测兜底 |
| 加密只承诺"传输保密" | MITM 门槛抬高 | 对主机嗅探**无效**——别把加密当反作弊 |
| 输入验证按动作发生时刻的状态 | 合法的延迟操作不被误杀 | 按当前时刻验证 → 假阳性，错踢正常玩家 |
| 云托管服务器 | 坏数据验证死角消失（服务器是自己的）、DDoS 有云商分担 | 玩家托管 → 服务器命令不可验证，安全模型降级 |

## 与原文的出入

| 类型 | 原文说 | 实际应为 | 依据 |
|---|---|---|---|
| 表述错（概念混列） | "不要使用简单的哈希算法，例如 SHA-256、MD5 或 DES，来保护你的密码" | 方向对但概念混乱：**DES 是分组密码不是哈希**；SHA-256/MD5 的问题不在"弱"而在**快**（GPU 每秒数十亿次尝试），密码存储要的是**慢哈希**（bcrypt/argon2/scrypt，带盐）；SHA-256 用于完整性校验/签名本身没问题 | 密码学常识；原文自己推荐的 bcrypt 才是正解 |
| 译名 | "河豚加密算法" | 即 **bcrypt**（Blowfish 派生的密码哈希函数），是哈希不是加密——存储密码的用途上它不"解密"回来 | §10.4.4 上下文 |
