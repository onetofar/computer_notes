## 机制

**问题：原样重传在状态复制上是错的。** 第 7.5 节的 `DeliveryNotificationManager` 已经能知道哪个包丢了；最直接的用法是给丢失包里的所有数据记一份 `ReliableTransmissionData`，失败就原样重发——这确实就是 TCP 的做法。但对持续变化的对象状态，丢失的那份数据在重发时往往已经过时（原书例子：0.9 秒时发的位置包丢了，200 毫秒后重传时汽车都停了）。第 5 章的 `ReplicationManager` 接口还堵死了另一条路：调用方自己准备包、自己调 `ReplicateCreate/Update/Destroy`，复制管理器**既不能决定包里写什么，也没有记录写过什么**，想重发都没有依据。

**第一步：控制反转。** 把"谁准备包"倒过来——宿主程序周期性地把一个待发包**递给** `ReplicationManager`，问它有没有数据想写。游戏系统从此不再创建数据包、不再关心网络，只在数据变化时**通知**复制管理器；复制管理器在下次拿到包时负责把变化写进去。提供包的频率（带宽估计、丢包率或别的触发条件）是宿主的决策，不是复制管理器的。

**第二步：命令缓存。** 每个网络对象在复制管理器里挂一条最新命令 `{动作, 脏状态位}`（`mNetworkIdToReplicationCommand` 映射）。游戏系统批量提交：创建 / 追加脏位（按位或）/ 销毁。销毁**取代**之前的一切批命令——给已销毁对象发状态更新没有意义。

**清单 7.10 批量处理复制命令**

```cpp
void ReplicationManager::BatchCreate(
    int inNetworkId, uint32_t inInitialDirtyState)
{
    mNetworkIdToReplicationCommand[inNetworkId] =
        ReplicationCommand(inInitialDirtyState);
}

void ReplicationManager::BatchDestroy(int inNetworkId)
{
    mNetworkIdToReplicationCommand[inNetworkId].SetDestroy();
}

void ReplicationManager::BatchStateDirty(
    int inNetworkId, uint32_t inDirtyState)
{
    mNetworkIdToReplicationCommand[inNetworkId].
        AddDirtyState(inDirtyState);
}

ReplicationCommand::ReplicationCommand(uint32_t inInitialDirtyState):
    mAction( RA_Create), mDirtyState(inInitialDirtyState) {}

void ReplicationCommand::AddDirtyState(uint32_t inState)
{
    mDirtyState |= inState;
}

void ReplicationCommand::SetDestroy()
{
    mAction = RA_Destroy;
}
```

**第三步：写包并登记。** 宿主递来包时，`WriteBatchedCommands()` 遍历命令映射：有脏状态（脏位非零，或动作是销毁）就写 `ReplicationHeader` + 状态数据；同时把"这个包里写了什么"登记进 `ReplicationManagerTransmissionData`，挂到这个包的 `InFlightPacket` 上（注册键 `'RPLM'`）。登记是**惰性**的——确定真的有东西要复制才创建传输数据。写完后清除脏位：同样的变化不写第二遍，直到它再次变化。

**清单 7.11 写批处理命令**

```cpp
void ReplicationManager::WriteBatchedCommands(
    OutputMemoryBitStream& inStream, InFlightPacket* inFlightPacket)
{
    ReplicationManagerTransmissionDataPtr repTransData = nullptr;
    //run through each replication command and rep if necessary

    for(auto& pair: mNetworkIdToReplicationCommand)
    {
        ReplicationCommand& replicationCommand = pair.second;
        if(replicationCommand.HasDirtyState())
        {
            int networkId = pair.first;
            GameObject* gameObj =
                mLinkingContext->GetGameObject(networkId);
            if(gameObj)
            {
                ReplicationAction action =
                    replicationCommand.GetAction();
                ReplicationHeader rh(action, networkId,
                                    gameObj->GetClassId());
                rh.Write(inStream);

                uint32_t dirtyState =
                    replicationCommand.GetDirtyState();
                if(action == RA_Create || action == RA_Update)
                {
                    gameObj->Write(inStream, dirtyState);
                }
                //create transmission data if we haven't yet
                if(!repTransData)
                {
                    repTransData =
                        std::make_shared<ReplicationManagerTransmissionData>(
                            this);
                    inFlightPacket->SetTransmissionData
                        ('RPLM',repTransData);
                }
                //now store what we put in this packet and clear state
                repTransData->AddReplication(networkId, action,
                                             dirtyState);
                replicationCommand.ClearDirtyState(dirtyState);
            }
        }
    }
}
void ReplicationCommand::ClearDirtyState(uint32_t inStateToClear)
{
    mDirtyState &= ~inStateToClear;
    if(mAction == RA_Destroy)
    {
        mAction = RA_Update;
    }
}
bool ReplicationCommand::HasDirtyState() const
{
    return (mAction == RA_Destroy) || (mDirtyState != 0);
}
```

**第四步：按包的命运响应。** `DeliveryNotificationManager` 判定包 ACK 或丢失后回调传输数据。失败 = 把命令**重新入批**（不是重发旧字节）：丢失的 Create 且对象还活着 → 重新 `BatchCreate`；丢失的 Update → 把对应脏位标回脏；丢失的 Destroy → 重新 `BatchDestroy`。成功 = 两件收尾：Create 被 ACK 后降级为 Update（下次脏了只发更新，不再重复创建）；Destroy 被 ACK 后从命令映射里删除条目。

**清单 7.12 响应数据包投递状态通知**

```cpp
void ReplicationManagerTransmissionData::HandleDeliveryFailure(
    DeliveryNotificationManager* inDeliveryNotificationManager) const
{
    for(const ReplicationTransmission& rt: mReplications)
    {
        int networkId = rt.GetNetworkId();
        GameObject* go;
        switch(rt.GetAction())
        {
            case RA_Create:
            {
                //recreate if not destroyed
                go = mReplicationManager->GetLinkingContext()
                        ->GetGameObject(networkId);
                if( go )
                {
                    mReplicationManager->BatchCreate(networkId,
                                                    rt.GetState());
                }
            }
                break;
            case RA_Update:
                go = mReplicationManager->GetLinkingContext()
                        ->GetGameObject(networkId);
                if(go)
                {
                    mReplicationManager->BatchStateDirty(networkId,
                                                         rt.GetState());
                }
                break;
            case RA_Destroy:
                mReplicationManager->BatchDestroy(networkId);
                break;
        }
    }
}

void ReplicationManagerTransmissionData::HandleDeliverySuccess
    (DeliveryNotificationManager* inDeliveryNotificationManager) const
{
    for(const ReplicationTransmission& rt: mReplications)
    {
        int networkId = rt.GetNetworkId();
        switch(rt.GetAction())
        {
            case RA_Create:
            //once ackd, can send as update instead of create
                mReplicationManager->HandleCreateAckd(networkId);
                break;
            case RA_Destroy:
                mReplicationManager->RemoveFromReplication(networkId);
                break;
        }
    }
}
```

**第五步（优化）：在途去重。** 丢包判定有延迟（见下表：0.9 秒丢的包，约 200 毫秒后才发现）。这期间后续更新包早已发出——丢失状态的新版本**可能已经在路上**。重发前先扫一遍所有在途包的 `'RPLM'` 传输记录：同对象的同状态位已经被别的未确认包覆盖，就从待重批的脏位里减掉（按位与非）。只对 `RA_Update` 做——销毁/创建是命令语义，没有"更新的新值"。代价是每次丢包要遍历全部在途包 × 各自的复制记录；原文的权衡是丢包低频、带宽比处理能力宝贵，划算，但"根据你的游戏的具体情况来权衡"。

**清单 7.13 避免多余的重传**

```cpp
void ReplicationManagerTransmissionData::HandleDeliveryFailure(
    DeliveryNotificationManager* inDeliveryNotificationManager) const
{
    ...
    case RA_Update:
        go = mReplicationManager->GetLinkingContext()
                ->GetGameObject(networkId);
        if(go)

            //remove written state from dirty state
            uint32_t state = rt.GetState();
            for(const auto& inFlightPacket:
                inDeliveryNotificationManager->GetInFlightPackets())
            {
                ReplicationManagerTransmissionDataPtr rmtdp =
                    std::static_pointer_cast
                        <ReplicationManagerTransmissionData>(
                    inFlightPacket.GetTransmissionData('RPLM'));

                        rmtdp->mReplications )

                        }
                    }
                }
            }
            //if there's still any dirty state, rebatch it
            if( state )
            {
                mReplicationManager->BatchStateDirty(networkId, state);
            }
            break;
```

## 作者省略的前提

> [!note] 本节是补出来的，不在原文里。
> 每条句尾标来源：`（推演）` / `（见 §X.X）` / `（工程经验）`

| 省略了什么 | 补出来是什么 | 来源 |
|---|---|---|
| "重传最新状态"对什么数据成立、对什么不成立 | 对**值语义**状态（位置、血量、朝向）恒成立——最新值永远是正确答案；对**一次性事件**（结算、成就、击杀公告）不成立——"最新的事件"这个说法无意义，事件必须逐条达成。所以本机制重批的是**命令**（create/destroy 幂等），事件类流量需要可靠队列或确认水位线。决定你把什么东西接进这套机制 | 推演 |
| 旧字节重传为什么有害（原文只说"过时"） | 重传发生在丢包判定之后（例子中 ≈200ms），这期间**更新的包已按序到达并被应用**；此时旧值后到，会把对象**回滚**到旧状态。"值语义重传"天然杜绝这一类回滚——这也是它相比 TCP 的本质优势，不只是省带宽 | 推演 |
| `ClearDirtyState` 为什么把销毁动作降级回更新 | 销毁写进包后命令仍留在映射里（等 ACK 才删）；若保持销毁动作，`HasDirtyState()` 恒真，判死之前的**每个**后续包都会重写一遍销毁头。降级后只有脏位能触发重写；真丢了，`HandleDeliveryFailure` 会重新入批销毁。降级是"在途期间不重复、丢失后有兜底"的两半 | 推演，对照清单 7.11/7.12 |
| `HandleCreateAckd` 为什么必要 | 创建命令被 ACK 前，命令的动作保持 Create；若不降级，之后每次脏位变化都会重写一遍 **Create 头**，客户端会重复创建对象。ACK 后降级为 Update，"创建"这件事就只会发生一次 | 见清单 7.12 注释 `once ackd, can send as update instead of create` |
| 为什么在途去重只做 Update、不做 Create/Destroy | Create/Destroy 重发无害且必要（幂等命令，丢了必须重批）；Update 重发的旧**值**才有害（见上）。去重针对的是"值已在途"这一浪费，命令不存在"新值" | 推演 |
| 这套机制与全量快照的分工 | 全量快照天然幂等（丢了等下一个，见 §5.3/§9.1），**状态通道不需要可靠层**；本节机制的用武之地是**离散命令/事件通道**。两者组合：状态走周期快照，事件走命令重批 | 见 §5.3/§9.1 + 工程经验 |

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 被复制的数据是"最新值语义" | 重传最新状态恒正确，且免疫旧值回滚 | 一次性事件不能走这套——"最新的事件"无意义，需可靠队列/水位线 |
| 复制命令幂等（create/destroy） | 失败重批安全，无需去重 | 非幂等命令（如"扣一次钱"）需要序列号去重，见 §7.5.3 的重复处理 |
| 丢包率低 + 带宽比 CPU 贵 | 在途去重划算 | 高丢包下每次丢失都全量扫在途包，成本膨胀，需限制扫描范围或放弃优化 |
| 接收端状态机支持"create 只达一次" | Create ACK 降级 + 失败重批闭环自洽 | 若接收端重复创建无副作用，降级逻辑可以省——但发送端仍会浪费带宽 |

## 原文证据

> 引文均出自 §7.6，用于证明上面两处关键判断，不是复述。

> "相比于 TCP，这是一个巨大的提升，因为 `Replication Manager` 并不使用原始的、可能过时的数据来写新数据包，而是使用目标对象的最新状态，可能比原始数据包中的状态要新半秒钟。"

> "上述优化在每次数据包丢失时，都需要相当多处理。但是，鉴于通常情况下丢包是低频率的事件，同时带宽往往比处理能力更宝贵，所以这样做是有利的。与往常一样，根据你的游戏的具体情况来权衡。"
