## 机制

### 拓扑账：C/S 与 P2P 的带宽/延迟对比（§6.1）

| 维度 | 客户端-服务器 | 对等网络 |
|---|---|---|
| 连接数 | 服务器 O(n)，客户端 1 | 每人 O(n−1)，全网 O(n²) |
| 带宽 | 服务器收 b×n 发 c×n；客户端恒为 c↓/b↑ | 对称，随人数线性涨 |
| 延迟 | 对端间最坏 = A 的 RTT/2 + 服务器处理 + B 的 RTT/2 | 无中介，最坏 = RTT/2 |
| 权威 | 服务器说了算（权威服务器模型） | 模糊 → 输入共享模型 |
| 断线 | 服务器挂 = 全局灾难（地址只在服务器手里） | 暂停几秒、移除对等体、继续 |

- **权威服务器语义**：客户端发现状态与服务器不符 → 以服务器为准。扔线球不是客户端判定命中——客户端发请求，服务器决定"允不允许扔、砸没砸中"。
- **专用 vs 监听服务器**：专用 = 无头进程、数据中心；监听 = 玩家机器兼任。原文纠正了一个常见误称：监听服务器**不是**对等网络，是"对等托管（peer hosted）"——仍然有台权威服务器，只是恰巧在玩家手里。监听服务器的两个坑：托管者可看全量状态作弊；服务器断线 = 地址簿消失，**主机迁移**（host migration）需要客户端间通信，等于把 C/S 和 P2P 缝成混合拓扑。
- P2P 的锁步同步（200ms 轮、PRNG、校验和）详见 [[11-格雷泽-四类数据与双原型]] 与本篇姊妹篇。

### 服务器/客户端代码分离（§6.2.1）

```
共享库（RoboCat）          服务器可执行（RoboCatServer）   客户端可执行（RoboCatClient）
GameObject/Yarn/RoboCat/Mouse 基类   →   各自的 Server/Client 派生类
```

- 同一个 `mHealth`：服务器持有**权威版本**（0 → 重生），客户端持有**显示版本**（HUD）——变量同名、版本分家。
- 手段 = 继承 + 虚函数（原文自评：性能不是最高，易用性最好）。编译成**三个目标**：共享库 + 服务器 exe + 客户端 exe；服务器无头，命令行 `RoboCatServer 45000` / 客户端 `RoboCatClient 127.0.0.1:45000 John`。

### 握手：四字符包状态机（§6.2.2）

```cpp
static const uint32_t kHelloCC   = 'HELO';
static const uint32_t kWelcomeCC = 'WLCM';
enum NetworkClientState { NCS_Uninitialized, NCS_SayingHello, NCS_Welcomed };
```

四步：①客户端**持续**发 `HELO`+名字（间隔 `kTimeBetweenHellos` 节流）直到收到应答；②服务器查 `mAddressToClientMap`（SocketAddress → ClientProxy），陌生人且包是 HELO → 建代理、回 `WLCM`+playerId；③客户端存 ID，状态进 `Welcomed`，开始收发复制；④稍后服务器把新对象广播给所有人。

**重传免费**：welcome 丢了 → 客户端反正还在发 hello；已知地址又收到 hello → 服务器重发 welcome。没有专门的可靠层，靠状态机的循环闭合。`HandleWelcomePacket` 先查 `mState == NCS_SayingHello` 才处理——已入场的客户端再收 welcome 不会出错。

### 输入流与客户端代理（§6.2.3）

- **客户端只上报输入**（`INPT` 包）：`InputState` = 四向移动量 + 是否投掷（delta 式：右−左、前−后）；`Move` = `InputState` + 时间戳 + **Δt**；`MoveList` 累积，发包时**只发最后 3 个**（计数字段只有 2 bit），发完清空。

**清单 6.4 / 6.5 —— 输入快照与动作封装**

```cpp
class InputState
{
public:
    InputState():
    mDesiredRightAmount(0),
    mDesiredLeftAmount(0),
    mDesiredForwardAmount(0),
    mDesiredBackAmount(0),
    mIsShooting(false)
    {}

    float GetDesiredHorizontalDelta() const
    {return mDesiredRightAmount - mDesiredLeftAmount;}
    float GetDesiredVerticalDelta() const
    {return mDesiredForwardAmount - mDesiredBackAmount;}
    bool IsShooting() const
    {return mIsShooting;}
    bool Write(OutputMemoryBitStream& inOutputStream) const;
    bool Read(InputMemoryBitStream& inInputStream);

private:
    friend class InputManager;
    float mDesiredRightAmount, mDesiredLeftAmount;
    float mDesiredForwardAmount, mDesiredBackAmount;
    bool mIsShooting;
};
```

```cpp
void RoboCatServer::Update()
{
    RoboCat::Update();
    // Code omitted
    // ...

    ClientProxyPtr client = NetworkManagerServer::sInstance->
            GetClientProxy(GetPlayerId());
    if( client )
    {
        MoveList& moveList = client->GetUnprocessedMoveList();
        for( const Move& unprocessedMove: moveList)
        {
            const InputState& currentState = unprocessedMove.GetInputState();
            float deltaTime = unprocessedMove.GetDeltaTime();
            ProcessInput(deltaTime, currentState);
            SimulateMovement(deltaTime);
        }

        moveList.Clear();
    }
    HandleShooting();
    // Code omitted
    // ...
}
```
- **ClientProxy 是服务器的瑞士军刀**（清单 6.7）：地址/名字/ID + `mUnprocessedMoveList` + **每客户端独立的 `ReplicationManagerServer`**——服务器"对这个客户端已经发过什么、还没发什么"的账本，增量复制与按客户端重发的全部前提。
- **按输入的时间线模拟**（清单 6.8）：`RoboCatServer::Update()` 消费未处理 MoveList，对每个 Move 调 `ProcessInput(deltaTime, state)`——**Δt 用 Move 自带的，不用服务器帧的**。于是服务器和客户端帧率解耦，一包多个 Move 也能正确重放。原文警告：固定步长物理对象要把物理帧率单独锁住。
- **承认的缺口**：输入包只发一次，丢了就永远丢（"扔"没生效）→ 第 7 章给每个动作三倍冗余 + 服务器去重。

## 原书的数字与工程建议

| 原文位置 | 数字 / 建议 |
|---|---|
| §6.1.1 | RTT 理想 ≤ **100 ms**；对端间最坏延迟 = 双方 RTT/2 + 服务器处理 |
| §6.1.1 | 服务器带宽：入 b×n、出 c×n；客户端带宽理论上不随人数涨（实际因复制对象变多微涨） |
| 清单 6.1 | 客户端是双态状态机（SayingHello / Welcomed），收发包都按状态分发 |
| §6.2.2 | 包类型用**四字符常量**（`'HELO'`/`'WLCM'`/`'STAT'`/`'INPT'`）写在包首 |
| §6.2.2 | hello 发送有节流（`kTimeBetweenHellos`），不是无限洪泛 |
| 清单 6.6 | 输入包只带**最后 3 个 Move**（2 bit 计数），发完清空 MoveList |
| §6.2.3 | 服务器按 **Move 自带 Δt** 逐条模拟；物理对象需要锁独立帧率 |
| §6.2.3 | 服务器不每帧给每客户端发包 → **每客户端独立复制管理器**是增量复制的结构前提 |

## 作者省略的前提

> [!note] 本节是补出来的，不在原文里。
> 每条句尾标来源：`（推演）` / `（见 §X.X）` / `（工程经验）`

| 省略了什么 | 补出来是什么 | 来源 |
|---|---|---|
| ClientProxy 的三重身份 | 原文分三处各讲一半：输入缓冲（mUnprocessedMoveList）、每客户端复制账本（独立 ReplicationManager）、（§8.4 将用到的）延迟补偿锚点。三者是同一个对象——服务器眼中"这个客户端"的完整替身。设计自己的服务器时把它们拆开会重复造状态 | 见 §6.2.3 + §8.4 |
| 按 Move 的 Δt 模拟的本质 | 服务器在**重放客户端的输入时间线**——模拟的时间基准跟着输入走。这与 §8.4 的"服务器回退到开火时刻"是同一机制的正反两面：一个用 Δt 顺放，一个用时间戳回溯 | 推演 |
| "地址即身份"的脆弱性 | `SocketAddress → ClientProxy` 会被 NAT 重映射/地址漂移打断（原文自己提了 NAT 不处理）。生产服务器用**会话令牌/player_id** 做身份，地址只做路由——加入房间时分配的 player_id 就属于这种令牌话而非按地址路由的依据 | 工程经验 |
| 连续输入流 vs 离散动作的冗余差异 | 移动输入是**流语义**（丢一帧被下一帧覆盖，无须重传）；"投掷"是**事件语义**（丢了就永远丢）——原文的三倍冗余其实只为事件类。区分两类可以少做一半冗余 | 推演（见 [[10-格雷泽-复制可靠性]] 同一区分） |
| welcome 重发的幂等性条件 | "已知地址的 hello → 重发 welcome"成立的前提是**建代理幂等**（查表已存在就不重建）。实现时漏掉这个判断会在 hello 风暴下重复建代理 | 推演（对照清单 6.3 的查表顺序） |

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 服务器带宽买得起 b×n 入 + c×n 出 | 人均带宽常数，可线性扩 | 人数涨 → 先炸服务器带宽，再做增量/AOI（§9） |
| 客户端逻辑可拆成共享基类 + 双端派生 | 代码路径清晰、双端不串味 | 逻辑双端强耦合的游戏（如纯物理模拟）→ 拆分会造出大量回调胶水 |
| 输入可序列化为小快照 | Move 流可行 | 输入本身巨量（语音/指针轨迹）→ 输入共享模型不划算 |
| 服务器权威 + 客户端可接受校正延迟 | 一致性最强 | 手感敏感 → 必须配客户端预测（§8.3），复杂度上台阶 |

| 类型 | 原文说 | 实际应为 | 依据 |

| 表述错 | "在客户端-服务器的拓扑结构中，给定 n 个客户端，总共会有 O(n²) 个连接。但这种结构是不对称的，服务器有 O(n) 个连接" | **自相矛盾**：星形拓扑总连接数 = O(n)（n 条链路），O(n²) 是 P2P 的量级（§6.1.2 自己写对了）。应为"总连接 O(n)，服务器承担 O(n) 条、客户端各 1 条" | 图 6.1（星形）；§6.1.2 |

## 原文证据

> "客户端代理是服务器用于跟踪特定客户端的一个对象。……服务器负责发送复制更新数据包（被分配为文本'STAT'），同时客户端在必要时负责处理复制命令。"（§6.2.3）

> "需要注意的是，每次调用 ProcessInput 和 SimulateMovement 时传入的增量时间是根据两次动作之间的增量时间，而不是服务器帧的增量时间。这使得服务器即使在一个数据包中收到多个动作，也可以试图保证尽可能模拟客户端的行为。"（§6.2.3）
