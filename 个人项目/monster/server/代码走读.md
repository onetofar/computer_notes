## 0. 先看全程：这个程序的一生只有三幕

```
第一幕 启动（一次性）     main → 装信号 → 打协议摘要 → Run() 准备段
第二幕 心跳（每一帧）     while 循环：回收 → Poll → 固定步长 → 世界结算 → 指标
第三幕 报文（每个包）     字节进来 → 解帧 → 分发 → 入房/输入 → 世界结算 → 快照出去
```

第三幕不是独立时间线——它**寄生在第二幕的循环里**。服务器启动后 99.99% 的生命都在 `while` 那一圈里打转，每个网络包的到来只是循环中某一次 `Poll` 的返回值变了。记住这个结构，全文就不会迷路。

### 1.2 `InstallSignalHandlers()`：先学会怎么死

📍 `main.cpp:58`，标志位定义在 `main.cpp:51`

这个函数装了三种信号处理，每种的「为什么」都是一课：

**① Ctrl-C（SIGINT）与 kill（SIGTERM）→ 只置一个标志位**

```cpp
volatile std::sig_atomic_t g_running = 1;              // 全局运行标志：1=继续跑，0=请求退出
extern "C" void OnStopSignal(int) { g_running = 0; }   // 信号处理器：只做这一件事，别的什么都不碰
```

信号处理器里**只允许**做这一件事：把全局标志改成 0。不写日志、不加锁、不分配内存——然后主循环的 `while (g_running != 0)` 下一圈自然退出。

> 🎓 **新人点拨**：`extern "C"` 告诉编译器「这个函数用 C 的方式命名修饰」——信号机制是 C 时代的遗产，处理器函数必须按 C 约定注册。`std::sig_atomic_t` 是 C++ 保证「读写它不可能被信号打断到一半」的唯一类型。

> ⚠️ **事故现场**（`main.cpp:49` 注释原文）：如果去掉 `volatile`，编译器会把 `while (g_running != 0)` 优化成 `while (true)`——因为它看不出这个变量会被「别人」（信号处理器）改。**症状**：Ctrl-C 没反应，必须 `kill -9`（强制杀死进程的命令，信号处理器拦不住它），而且编译、运行毫无异常。这是新人最容易写出、最难排查的 bug 之一：代码全对，死在优化器手里。

**② 不设 `SA_RESTART`**

`sigaction` 的 `sa_flags = 0`（`main.cpp:63`）。先解掉这串名词：**sigaction** 是 Linux **注册**信号处理器的系统调用（系统调用 = 程序请内核代办事的入口；§1.2① 那个「装处理器」的动作就是它干的）；**glibc** 是 Linux 下的 C 标准库（`sigaction`/`signal` 这些函数的家）。glibc 的默认行为会自动重启被信号打断的系统调用——那样 `epoll_wait`（§2.2 讲的 epoll 等待调用，此处提前露面）被打断后会**继续睡**，退出要等满一个超时窗口。显式清零：信号打断后让它正常返回 `EINTR`（「被信号打断」的错误码），主循环立刻检查 `g_running`。

**③ 忽略 SIGPIPE——防猝死**

> ⚠️ **事故现场**（`main.cpp:69` 注释）：TCP 对端已经断开时，往它 `write()` 会触发 SIGPIPE 信号，**默认动作是直接终止进程**。也就是说：一个玩家在服务器发包的一瞬间断线，就足以打死整个服务器——而且症状是「毫无日志的猝死」，最难查的一类。修法是忽略它（`SIG_IGN`），让 `write` 返回 `-1/EPIPE` 错误码，由发送函数的错误分支去正常关闭连接。

**职场习惯①**：新人写工具程序从不装信号处理，因为它「暂时用不上」。真实服务器第一课就是：**进程怎么死，和怎么活一样重要**。

> 🔍 **想挖机制**：[[00-信号机制详解|信号机制详解]] 把本节每个写法展开成「事故 → 机制」——volatile 为什么不是锁（与「可见性」辨析）、`sig_atomic_t` 与 volatile 各管哪一半、`sa_mask` 防什么、SA_RESTART 为什么会让标志位永远轮不到被检查、SIGPIPE 事故链与 fail-fast 分档。

### 1.3 `PrintProtocolSummary()`：自报家门

📍 `main.cpp:195`

把 tick 率、快照率、帧头大小、消息号、协议哈希全部打到 stdout（这五个名词后文都会正式讲，先给个速览：**tick** = 服务器推进世界的一拍，§2.3；**快照** = 定期发给客户端的世界「合影」，§3.7；**帧头** = 每条网络消息开头那段公共字节，§3.2；**消息号** = 每条消息的「类型编号」，§3.3 的 switch 靠它分发；**协议哈希** = 整张协议定义算出的指纹，用来核对两端协议版本）。这不是废输出——它是「协议常量可读」的现场核对：**联调**（客户端和服务器连起来调）时客户端连不上，第一件事就是对比两边打印的 `kProtocolHash`。

这里有个值得注意的细节在 `Run()` 里（`main.cpp:222-231`）：`kProtocolHash == 0` 时打 **warn** 而不是静默——「不能让人以为握手校验已生效」（哈希为 0 = 生成脚本没跑过或跑了失败，此时两端核对等于形同虚设）。协议哈希现在真值是 `0xc6c1d34f`（`protocol.h:249`），由 `tools/gen_protocol_hash.py` 从协议头文件生成；**改了协议忘了重生成哈希，客户端会全员被拒**，启动日志里的这行就是第一现场。

### 1.4 `Run()` 准备段：两个端口、三个回调、一只注入的钟

📍 `main.cpp:215`（函数体前半，233-289 行）

```cpp
net::TcpTransport transport(config::kListenAddr, config::kListenPort);   // 游戏端口
net::Metrics metrics;
net::MetricsServer metrics_server(metrics, config::kMetricsPort);       // 指标端口
```

**两个端口**：游戏流量和监控指标（Prometheus 抓取）走不同端口。混用的代价是「监控请求打进游戏逻辑」这类事故，分开是零成本的干净。

接下来是本文第一个重要的架构决定——**三个回调**（`main.cpp:267-286`）：

```cpp
// 有新连接进来 → 会话层建一个匿名会话（还没报房号的状态）
transport.set_on_accept([&sessions](net::ConnId id) {
    sessions.OnConnectionOpen(id);
    log::info_f("新连接", log::Fields{.fd = id});   // 真实代码里还有一行日志，一并不省
});

// 有字节到达 → 记账，转交会话层解帧
transport.set_on_bytes([&bytes_recv, &sessions](net::ConnId id, const std::uint8_t* data, std::size_t n) -> bool {
    bytes_recv += n;
    return sessions.OnBytes(id, data, n);   // false = 流不可信，net 层自行关闭
});

// 连接断了 → 会话层查房间表，决定座位进不进 10s 重连窗口
transport.set_on_close([&sessions](net::ConnId id) { sessions.OnConnectionClosed(id); });
```

网络层（`net/`）只负责一件事：**投递字节**。它不认识「房间」「玩家」「消息」——收到字节就调 `on_bytes`，连接断了就调 `on_close`。解帧、建会话、进房间，全是上层（`session/`）的事。这里第一次出现「**会话**（session）」：一条连接在服务器里的**登记记录**——谁连着、在哪个房间、最近活跃是什么时候。连接是网络层的概念（一条 TCP 管道），会话是它的业务影子（这个人在哪）；连接断，会话不一定立刻销毁（§3.4 关 3 的重连窗口就是给会话留的后路）。

> 🎓 **新人点拨**：`[&sessions]` 是 **lambda 的引用捕获**——匿名函数里用到外部变量 `sessions`，按引用抓进来。⚠️ 引用捕获有生命周期陷阱：如果被捕获的变量先于 lambda 死亡，悬垂引用。这里安全是因为 lambda 的寿命不超过 `Run()` 的局部变量。什么时候值捕获（`[=]`/`[x]`）、什么时候引用捕获，是 code review 高频题——捕获列表的完整规则（值/引用/隐式/可变）见 [[A cpp第二部分_cpp标准库#10.3.3 Lambda 捕获与返回|你的 C++ Prime 笔记 §10.3.3]]。

**回调注册必须发生在 `Poll` 之前**（`transport.h` 的契约）——先上岗再立规矩，第一天来的包就没有人接待了。

还有一只「注入的钟」（`main.cpp:258-260`）：

```cpp
std::int64_t wall_now_ms = 0;   // 「现在几点」：主循环每拍刷新它
auto now_ms_fn = [&wall_now_ms]() { return wall_now_ms; };   // 会话层问时间，答案从这来
// ……（此处省略 TransportSink 适配器与 SessionManager 的构造——
//      两者只是把上面的回调装配进会话层，与主线无关，不展开）
sessions.set_clock(now_ms_fn);  // 注入：会话层从此自己不读时钟，只调这个函数
```

会话层自己**不读时钟**——它要「现在几点」，就调这个注入进来的函数，而主循环每拍负责更新 `wall_now_ms`。为什么要绕这一下？

> 🎓 **新人点拨**：这叫**依赖注入**。测试要验证「5 秒无包判死」「10 秒座位回收」，难道真等 5 秒、10 秒？注入假时钟后，测试把「时间」直接拨快，10 秒的窗口在毫秒内验证完（`test_session_room.cpp` 就是这么写的）。**「能被毫秒级单测」不是一个测试技巧，是设计出来的属性**——它逼着代码把「读时钟」这个副作用从逻辑里剥出去。

📖 **教材落点**：这套「net 只投递、session 只决策」的分层，就是[[第6章 网络拓扑和游戏案例（讲义）#2. §6.2 权威服务器落地：机器猫行动|第 6 章 §6.2 权威 C/S 架构]]里「服务器内部还得分层」——教材只画了客户端和服务器的边界，真实服务器内部还有 net/session/world 三层，每层职责单一才可单测。（「**权威**（authoritative）」是全文反复出现的词，首次出现就讲清：游戏状态由服务器说了算——客户端只发「我想干嘛」，结果是啥服务器裁。C/S = 客户端-服务器架构的缩写，与 P2P（玩家互连、没有服务器）相对，见 §3.7。）

## 2. 第二幕：心跳线——`while` 循环的一圈

📍 `main.cpp:293-378`。程序的一生都在这 85 行里，逐段走。

### 2.1 `ReapGuard`：删不得的那一行，用析构函数锁死

📍 `main.cpp:296-302`，实现 `src/app/reap_guard.h`

```cpp
while (g_running != 0) {
    app::ReapGuard reap_guard(transport);   // 每轮开头构造
    // ……（循环主体：Poll、补帧、结算——§2.2 起逐段讲）
}   // ← 离开作用域时，析构函数自动调 transport.ReapClosed()
```

**回收已断开的连接**（`ReapClosed`，`tcp_transport.cpp:492`）是每轮**必须**做的事——不做，断开的连接就永久滞留，**fd 泄漏**（fd = 文件描述符，Linux 给每条打开的连接发的编号，数量有上限——只开不关，几千个连接之后服务器就再也接不进新人）。但它是那种「看起来删掉也没事」的代码。

> ⚠️ **事故现场**：评审把这列为 U-4 级隐患（U 系列编号是本项目代码评审给隐患编的号，不是通用术语——记住 U-4 就是「ReapClosed 漏调」这条即可）。回收靠的是「有人记得在循环末尾写一行」，任何一次重构（`continue`、`break`、提前 return、异常沿栈展开——「栈展开」= 异常发生时 C++ 逐层退出函数调用的过程，路过每层都会析构局部变量）都可能绕过它。**修法不是加注释提醒**，而是 `ReapGuard`：构造时什么都不做，析构时执行回收。C++ 保证析构在离开作用域时**必然**发生——不管怎么离开。

> 🎓 **新人点拨**：这就是 **RAII**（Resource Acquisition Is Initialization）——C++ 最重要的工程思想：**把「必须配对执行的收尾」绑定到对象析构上**，让语言机制替你保证，而不是靠人的记性。锁的自动释放、文件自动关闭、事务自动回滚，全是同一招。你以后写的每个「try 里 acquire、finally 里 release」，在 C++ 里都应该变成一个 RAII 类。标准库里 RAII 最典型的实例是智能指针——析构即释放，见 [[A cpp第二部分_cpp标准库#12.1 动态内存与智能指针|你的 C++ Prime 笔记 §12.1]]。

### 2.2 `Poll`：epoll 新人版——一个门卫看住一千扇门

📍 `main.cpp:306`（调用点）→ `tcp_transport.cpp:243`（实现）

```cpp
transport.Poll(sched.PollTimeoutMs(now));   // 问内核一次「谁可读」；没人可读就最多睡 timeout_ms
```

新人版解释：服务器同时握着几十上百条连接（每条一个 socket/fd），怎么知道「谁有数据来了」？——不可能挨个去问（那是轮询，浪费 CPU）。**epoll** 是 Linux 提供的批量候问机制：把所有 fd 登记给内核，然后「睡到有事的 fd 醒来」。`Poll(timeout_ms)` 就是问一次：这批连接里，**现在谁可读？** 没人可读就最多睡 `timeout_ms`。

为什么 timeout 有讲究：`sched.PollTimeoutMs(now)` 返回「距下一个逻辑 tick 还有多久」，且被 clamp 到 `[0, 50]`（`main.cpp:308` 注释）。上限 50ms = 一个 tick 周期：哪怕完全没网络流量，世界也必须每 50ms 推进一次——**睡过头 = 游戏停摆**。

📖 **教材落点**：这就是[[markdown/网络/5-2 IO复用相关技术.md#I/O复用|网络笔记 §5-2 I/O 多路复用]]（select/poll/epoll）的实战位置；[[01-网络层领读#1 · 两条主路径，别混（`transport.h:37-42`）|01-网络层领读]] 里有完整版（LT/ET = 电平触发/边缘触发，epoll 的两种通知模式——LT 是「还有数据没读完就每次都提醒你」，ET 是「状态变化时只提醒一次」；以及 EPOLLOUT 的挂法、为什么回调里不能改状态）。

### 2.3 固定步长累加器：为什么不是 `sleep_for(10ms)`

📍 `main.cpp:309-347`，核心 `src/app/tick_scheduler.cpp`

Poll 醒来后，主循环要决定「这一圈该跑几个逻辑帧」。用的是**固定步长累加器**：

```
积累落后量 drift = 当前时间 - 下个 tick 应发生的时间
while (落后量够一帧) { 跑一帧逻辑; 下一个 tick 时间 += 50ms; }
落后太多（> 5 帧上限）→ 只补 5 帧，其余丢弃并 warn
```

为什么要有 5 帧上限：如果上限定为「无上限」，一次 3 秒的卡顿醒来就要一口气补 60 帧——世界在一瞬间瞬移完、所有动画疯转，玩家看到的是鬼影而不是游戏。**丢弃**（宣布破产，直接跳到最新时刻）比**疯狂追赶**（把 3 秒的事塞进一帧演完）体验好得多——上限是「宁可丢帧，不可瞬移」。

> ⚠️ **事故现场**（两起，都在 `main.cpp` 注释里）：
> **① 为什么不用 `sleep_for(10ms)` 驱动循环**——sleep 的实际时长受系统调度影响，负载高时飘到几十毫秒，逻辑帧率随负载下降，这是教材第 6 章 §6.3（RTS 锁步的时间片设计——RTS = 即时战略游戏如星际争霸；锁步 = 所有端按同一节拍齐步走的同步方式，节拍一漂全体错位）明令禁止的漂移。累加器不管睡多久，醒来按「欠了几帧」补——像还债：欠几帧还几帧，欠太多（超过 5 帧）就宣布破产只还 5 帧——帧率恒定。
> **② 为什么 Poll 之后要重新取时间**（`main.cpp:313` `post_poll`）——Poll 可能阻塞了几十毫秒，之前取的 `now` 已经过期。拿旧时间算补帧会**少追帧**，症状是「逻辑帧率随负载悄悄下降」，方向和 ① 相反、同样难查。

还有一个调试彩蛋：环境变量 `OTF_DEBUG_STALL_MS` 能人为让主循环卡住一拍（`main.cpp:92-98`、`317-328`），用来**现场验证**「补帧上限真的生效」——正常运行中上限永远不触发，只靠单测不够，要做故障注入。

> 🎓 **新人点拨**：`main.cpp:84` 的 `SteadyNowMs()` 用 `steady_clock` 而不是 `system_clock`——后者是「墙上挂钟」，会被 NTP（网络对时服务）校时**拨动**，一次时间回拨就能让累加器算出巨大的「落后量」，服务器瞬间疯狂补帧。`steady_clock` 是只进不退的秒表，永远不会回拨。计时永远用单调钟，这是所有服务器代码的铁律。

### 2.4 一拍干两件事：`Tick`（生命周期）与 `TickWorld`（世界）

📍 `main.cpp:332-345`（`sched.Advance` 的回调）

```cpp
const TickScheduler::Result r = sched.Advance(post_poll, [&]() {
    wall_now_ms = post_poll;                 // 刷新注入的钟
    sessions.Tick(post_poll);                // 事一：会话/房间生命周期
    sessions.TickWorld(sched.tick_index());  // 事二：世界状态推进
});
```

两个 Tick **刻意分开**（`session_mgr.h:186-192` 的注释把理由写得很清楚）：

| | `Tick` | `TickWorld` |
|---|---|---|
| 管什么 | 超时判死、座位回收、空房销毁 | 玩家移动、Boss 决策、快照广播 |
| 频率 | 每 tick | 每 tick（快照 10Hz，`tick % 2 == 0`） |

分开的好处是「谁因为没驱动世界而空了」能被**单独看见**。混在一起的话，Boss 站着不动这种 bug，你会怀疑是决策、网络、房间回收三者中的任何一个——排查面凭空扩大三倍。

还有一个新人容易忽略的细节：回调里读帧号用 `sched.tick_index()` 而不是自己计数——`Advance` 内部「先跑 step 再 ++」，回调里拿到的就是**本帧自己的帧号**。帧号从 0 起算，`server_time_ms = tick × 50` 纯算出来，世界层不读时钟。

### 2.5 退出：也要留凭据

📍 `main.cpp:369-383`

循环结束后打一行 `收尾: tick=... uptime_ms=...`，`main()` 返回 0。

> ⚠️ **事故现场**：这行日志的意义在 `main.cpp:229` 注释里写着——gdb/valgrind/strace（三个 Linux 诊断工具：gdb = 断点调试器，valgrind = 内存泄漏/越界检查器，strace = 跟踪程序每一次系统调用）的使用者需要「进程是**走到收尾的**，不是被打死的」这个凭据。没有它，「优雅退出」和「中途崩溃」在日志上无法区分，你就只能靠猜。

**职场习惯②**：启动有启动日志，退出有收尾日志，异常有退出码。进程的一生要「来有影，去有踪」——这不是形式主义，是运维凌晨三点排查事故时唯一的线索。

## 3. 第三幕：一个数据包的一生

这是全文最重要的一节。我们跟着**玩家「小明」敲下的一次攻击键**走完全程——从字节到网络到结算再回到他的屏幕。

### 3.0 全程地图

```
小明客户端
  │ ①TCP 字节流上行（JoinRoom / PlayerInput / HitReport）
  ▼
TcpTransport.Poll ── on_bytes 回调 ──► SessionManager.OnBytes
  │                                      │ ②解帧（粘包/半包）
  │                                      │ ③分发 HandleFrame（switch）
  │                                      ├─④ JoinRoom：五道关 → JoinAccept
  │                                      ├─⑤ PlayerInput：只入缓冲，不算位置
  │                                      └─⑥ HitReport：只入队，不结算
  ▼
下一拍 World::Tick（六步结算）
  │ ⑦移动/决策/扣血/清算 → ⑧ RecordPose
  ▼
tick % 2 == 0 → FillSnapshot → Broadcast（⑨快照下行）
  ▼
TcpTransport.Send →（写不出去就挂 EPOLLOUT 稍后再写）──► 小明屏幕
```

### 3.1 到站：字节从网卡到回调

📍 `tcp_transport.cpp:243`（Poll）→ `main.cpp:269`（on_bytes）

epoll 报告「fd 7 可读」→ `read()` 把字节搬进缓冲 → 调用启动时注册的 `on_bytes` 回调 → `bytes_recv += n`（只记账）→ `sessions.OnBytes(id, data, n)`。

注意回调的返回值契约（`main.cpp:272` 注释）：`false` = 这条字节流不可信，由 **net 层**负责关闭连接——**回调自己不关**。谁的数据谁处理，谁的地盘谁关门，职责不串。

### 3.2 解帧：TCP 是字节流，不是快递

📍 `session_mgr.cpp:146`（`OnBytes`）→ `src/net/frame_codec.*`

新人第一个要打破的错觉：TCP 不会帮你「一条消息一条消息」地送到。你发三条 10 字节的消息，对方可能一次收到 30 字节（**粘包**），也可能先收到 7 字节再收到 23 字节（**半包**）。TCP 只保证字节顺序，不保证分块。

所以必须有**帧编解码器**（FrameDecoder）：会话层把所有字节喂给 `decoder.FeedAll(...)`（`session_mgr.cpp:166`，收包唯一入口），解码器负责在字节流里切出完整的帧——帧头带长度，攒够了就吐一帧，不够就继续攒。**每个会话有自己的解码器**（`Session::decoder`，`session_mgr.h`），不同连接的字节绝不混流。

> 🎓 **新人点拨**：为什么服务器不把收到的包「缓存起来等 tick 再处理」？`OnBytes` 的注释明说：帧解码后**立刻**处理（`session_mgr.cpp:151`）。因为输入晚一拍生效，手感就差一拍——这是教材讲的「客户端代理的输入要尽快消费」在本项目的直接体现。

### 3.3 分发：`HandleFrame` 的 switch 与 fail-close

📍 `session_mgr.cpp:190`

```cpp
switch (f.msg) {
    case MsgId::JoinRoom:     return HandleJoinRoom(s, f);
    case MsgId::Heartbeat:    return true;          // 心跳包（保活）：只刷活跃时间，不回包
    case MsgId::PlayerInput:  return HandlePlayerInput(s, f);
    case MsgId::HitReport:    return HandleHitReport(s, f);
    case JoinAccept: case Rejected: case PlayerJoined:
    case PlayerLeft: case WorldSnapshot: case BossEvent:
    case PlayerStateRetired:      // 7 个下行/退役消息号，源码里全列了（无省略）
        return false;                              // 判死
    default: return false;                         // 表外消息号，判死
}
```

三件事值得停下来看：

**① 下行消息逆行 = 判死**。客户端发来一个 `WorldSnapshot`？说明对端实现错了。为什么不忽略？——忽略的话，两端会一直对着错误的协议说话，**症状是「联调时什么都能连上、什么数据都不对」**。

**② 退役消息也判死**。`PlayerStateRetired`（消息号 3，2026-10-15 退役——客户端上报血量违反「客户端不得上报权威状态」红线）出现在 switch 里专门接住：任何客户端还在发它 = 还在用旧协议，判死让症状从「血量莫名其妙对不上」变成「连接被拒，一眼看出版本问题」。

**③ `default` 必须存在——这是血泪写的**。

> ⚠️ **事故现场**（`session_mgr.cpp:216-232` 注释，原文很长，这里是精华）：`MsgId` 底层是 `uint16_t`，**线上任意两个字节都能构造出表外的值**（比如 msg=99）。重构前 switch 没写 `default`，控制流落空走到函数末尾的 `return true`——一条畸形帧被当正常帧收下，零日志。教材 §4.5 的判据原话：「switch 必须带 default，否则新增消息类型漏实现会静默走空」。本项目把它升级成 **fail-close**：不认识的，一律断开。

**职场习惯③**：处理外部输入的 switch，永远写 `default`，并且 default 的动作是「拒绝」而不是「收下」。宁可误杀一个 bug 客户端，不能放过一个协议漏洞。

### 3.4 `JoinRoom`：一次入房的五道关

📍 `session_mgr.cpp:235-329`。小明第一个包 `JoinRoom{protocol_hash, nickname, room_id}` 到了，五道关按顺序过：

**关 0：帧格式**（L237-243）——解码失败 = 字段表和实际字节对不上，直接断连。注意：**不发 Rejected**。Rejected 只有三个具名含义（哈希错/房间满/服务器满），「你包格式错了」不在其中——新增含义 = 改协议 = 红线。

**关 1：协议哈希**（L253-261）——**必须最先做**。连协议都没对齐的客户端不该占用房间名额，否则一次错误版本的连接洪水能把房间全部占满。不符 → 发 `Rejected{1}` → 断连。

**关 2：服务器满**（L264-276）——判据是「当前会话数 > 上限」。上限 64 = `kMaxSessions`（`server_config.h:61`，全服务器最多 64 条会话）。

> ⚠️ **事故现场**：这条判据有个**双 bug 时间线**（`session_mgr.h:141-149` 注释完整记录）。历史代码是 `count() >= 64`，而且 `count()` 曾直接返回 `sessions_.size()`——那个数组是按 fd 上限**预分配**的，size 恒为 1024。两个 bug 叠加：`1024 >= 64` **第一秒就成立**，**每个客户端都被 Rejected{3}**，而服务器日志、连接数、房间数一切正常。修复先改 count（数**存活会话**而不是数组长度），比较号也定稿为 `>`（`session_mgr.cpp:275`）。症状长得像「服务端拒绝一切」，而不是「一个计数写错了」——这就是容量（capacity，表能装多少）和占用（occupied，现在装了多少）混为一谈的代价。

**关 3：选房占座**（L278-293）——`rooms_.Join(...)` 内部先扫**重连**：小明如果是断线重连（同 nickname），直接回**原座位**。

**关 4：回包与广播**（L295-326）——给小明回 `JoinAccept{player_id, hash, spawn_x, spawn_y}`（spawn = 出生点，这俩字段是出生坐标）；给房里**其他人**广播 `PlayerJoined`（不含小明自己——他的加入他自己知道了，重复通知是浪费）。如果小明是重连，则**不**广播 PlayerJoined（他从没「离开」过），而是标记**补发一包全量快照**。

> 📖 **教材落点**：全量快照 vs 增量补帧——重连补**全量**，因为它**幂等**（发几次效果一样）；补增量帧需要「从哪帧开始」的历史，而服务器不做跨连接的输入持久化。[[第6章 网络拓扑和游戏案例#6.2 客户端-服务器的实现：权威骨架三件套|教材第 6 章「入会状态机的幂等重传」]]说的就是这类设计。

**职场习惯④**：每一关的**顺序就是安全策略**——哈希在最前，格式在格式关之后，占座在名额关之后。顺序错了（比如先占座再验哈希），攻击者用无效哈希就能把所有座位占满。写分支判断时，先问「这一步失败的话，前面做的事要不要撤销」——最便宜的答案永远是「把贵的检查放在前面」。

### 3.5 `PlayerInput`：服务器只收输入，不算位置

📍 `session_mgr.cpp:331-357`

小明的移动包 `PlayerInput{seq, move_x, move_y, action, form}` 到了。会话层做什么？——**几乎什么都不做**：

1. 解码（失败 = 断连，同关 0 的逻辑）；
2. 没入房就发输入？**忽略不踢**（顺序错误通常来自客户端刚重连还没重发 JoinRoom，自愈很快；踢掉一个好好玩着的玩家代价更大）；
3. 把输入塞进世界的输入缓冲：`room->world().QueueInput(player_id, in)`（L354）。

**没有第三步之后的第四步了。** 会话层不积分移动、不算位置（「积分」= 数值积分：拿速度 × 时间逐步累加出位置，物理课的那个积分——不是超市积分；§3.6 的 PlayerSim 会正式用它）——移动是服务器按 tick 统一算的（下一节）。这就是「**上行只有输入**」：客户端对世界的唯一权利是提需求，裁决权全部上收。

> 📖 **教材落点**：这就是[[第6章 网络拓扑和游戏案例（讲义）#2. §6.2 权威服务器落地：机器猫行动|第 6 章 §6.2「客户端代理与 Move 流」]]——服务器眼里每个玩家就是一袋输入。教材里 `ClientProxy.mUnprocessedMoveList`（待消费队列）在你项目里的对应物，就是 `World::QueueInput` 灌进去的那个输入缓冲。

### 3.6 `World::Tick`：一拍的六步结算

📍 `world.cpp:197-375`。前面所有环节都在「收材料」，这里才是「做菜」——每 50ms 一次，顺序写死，一步不许换：

```
① 采集输入 → PlayerSim 积分    （玩家动）
② 仇恨计算 → Boss 决策 → 位移  （Boss 动）
③ 攻击命中 → 服务器扣血 + 事件 （Boss 打人）
④ 清算 HitReport 队列          （玩家打 Boss）
⑤ 胜负判定                     （谁赢了）
⑥ RecordPose 记本帧位姿        （为回退留档）
```

（「仇恨」= Boss 的选敌机制——谁威胁最大它就追谁打，MMO 游戏的通用术语；「位姿」= 位置 + 朝向的合称，一个实体「在哪、脸朝哪」的最小描述。）

每一步背后都有故事，挑四个最有教学价值的：

**「遍历顺序也是协议的一部分」**（L210-213 注释）：玩家遍历按**座位下标升序**，不是风格问题——Boss 仇恨同分时取「先遍历到的」那个，遍历序变了 = 同输入出不同目标 = 行为分叉。凡是影响结果顺序的循环，顺序就是契约。

**「龙消失了」**（L250-254 注释）：Boss 位移后必须 `clamp`（夹住：把数值强制限制在 [min, max] 区间内，超了就取边界值）到地图外框。不 clamp，Boss 会一路走出地图，客户端相机不跟出去——**症状是「龙消失了」，而服务器日志一切正常**。服务器「正确」和客户端「可见」是两回事。

**「多挨一帧打」**（L288-291 注释）：无敌帧（i-frames）先推进、再判本帧伤害——和客户端 `health_component.gd`（客户端 Godot 工程里管血量的组件脚本，跨端对照时两边的文件名都要点出来）的顺序完全一致。顺序反过来会多挨一帧打，或者刚开的无敌帧被自己消掉。**跨端逻辑，顺序也是一致性的一部分**。

**「服务器自己扣血」**（L264-272 注释，2026-10-15 改造）：Boss 的攻击命中判定和伤害值本来就产自服务器（`BossBrain::Strike`），早期却把结果丢给客户端去执行——客户端能靠上报血量决定胜负。现在 `PlayerHp` 是服务器权威，胜负、Boss 索敌都读它，客户端碰不到。

> 📖 **教材落点**：③ 正是讲义[[第6章 网络拓扑和游戏案例（讲义）#2. §6.2 权威服务器落地：机器猫行动|第 6 章 §6.2]]那句「客户端对世界只有一个权利——提需求，裁决权全部上收」的执行现场——「客户端上报权威状态」是权威模型的头号大忌（本项目为此退役了整条消息），「服务器自己扣血」是本项目**红线 2**（「不收客户端上报的权威状态——位置、伤害结果、命中与否，一律服务器算」，四条红线全文见 [[00-项目领读#L7 · 改代码前必读的四条红线|00-项目领读 L7]]）的落地。

### 3.7 快照下行：98 字节的合影

📍 `world.cpp:521`（`FillSnapshot`）→ `session_mgr.cpp`（`TickWorld` 里的广播）→ `tcp_transport.cpp:443`（`Send`）

`tick % 2 == 0` 时（20Hz tick ÷ 2 = 10Hz），服务器给每房间广播一帧世界快照。宽度是个恒等式：

```
9（帧头）+ 33（Boss）+ 14 × 4（玩家）= 98 字节
```

（4 = 每房座位上限：满房 4 名玩家，每人一条 14 字节的位姿记录。）

98B 对 1400B 的单帧上限（`kMaxPayloadSize`，`protocol.h:27`——官方注释就一句「单帧不触发 IP 分片」：以太网链路一次能驮的包有大小上限 MTU 1500 字节，超过的包会在路上被拆成两半（IP 分片），丢一半就得整帧重传；1400 是留足余量、保证一帧一次到家的安全尺寸，更细的推导属于网络课内容不展开）只占 7%——**小世界全量快照随便发**，这是「为什么发全量不发增量」的物质基础。

`Send` 的返回值只有两态：true = 已交给内核；false = **内核缓冲满了**（每条连接在内核里都有一小块「发货暂存区」，`write` 只是把数据搬进暂存区就返回——网络慢时暂存区堆满，再写就得等）。此时 TcpTransport 会给这条 fd **挂上 EPOLLOUT**——epoll 的一种事件通知，含义是「这条连接的暂存区腾出空间了，可以继续写了」，等通知到了再写（`tcp_transport.cpp:358` 的 `FlushWrite`）。**上层不需要也不应该根据返回值分支做事**（`session_mgr.h:99` 注释）：发送的复杂性被 net 层整个吃掉了。

> 📖 **教材落点**：下行这条线就是[[第6章 网络拓扑和游戏案例（讲义）#2. §6.2 权威服务器落地：机器猫行动|第 6 章的 STAT 状态复制包]]——教材里「服务器把模拟结果发给客户端」在你项目里的物理形态就是这 98 字节。上行只有输入（3.5 节）+ 下行只有状态（本节），两条路合起来才是权威 C/S 的完整闭环——只看上行会以为「P2P（点对点，玩家互连没有服务器）和 C/S（客户端-服务器，§1.4 已释）传的东西一样」。

### 3.8 支线：`HitReport` 与回退——为什么「明明砍中了，服务器说没打中」

📍 `session_mgr.cpp:368`（收包入队）→ `world.cpp:319`（清算）→ `world.cpp:377`（`SettleHitReport` 四道工序：① 回退 → ② 合法性 → ③ 数值 → ④ 限流）

小明的攻击包走的是另一条路：会话层**只入队、不做任何校验**（`session_mgr.cpp:369`），结算统一在下一拍 `World::Tick` 第 ④ 步——因为裁决要用**本拍刚算完的** Boss 位姿，提前结算会出现「用上 tick 的位置裁决本 tick 的命中」（L322 注释里 §12 的原话警告）。

裁决时第一道工序是**回退还原**（`world.cpp:381-391`）：

> ⚠️ **事故现场**：客户端判定「砍中了」时，看到的是**插值出来的画面**（插值 = 客户端拿着两帧快照，把中间时刻的画面平滑地算出来演——快照只有 10Hz，直接演就是幻灯片，插值把画面补成丝滑的）——比服务器当前位姿晚了一截。如果服务器用当前位姿校验，一次误报就把合法命中丢掉。**症状：「明明砍中了，服务器说没打中」，且大部分时候是对的、偶发丢命中，极难定位。** 修法：客户端随 HitReport 带上它看到画面的时刻（`snapshot_tick, interp_t`），服务器从位姿历史里**回退**到那一刻再判定（`RecordPose` 在每帧最后存档，`world.cpp:183`——存早了会查到还没走完这一帧的位姿）。

> 📖 **教材落点**：这就是**延迟补偿（lag compensation）**——[[第8章 改进的延迟处理#8.4 服务器端回退：把世界退回到扣扳机的那一刻|教材第 8 章 §8.4 服务器端回退]]的核心主题，「服务器往回看」在你项目里的真实实现。第 6 章精读里「ClientProxy 存下他当时看见的世界」是它的铺垫。

回退（①）之后还有三道（L394 起，源码注释就按 ①②③④ 编组）：

- **② 合法性**：部位（Boss 身上可独立打击、可被永久破坏的部件，各有各的破坏状态）存在且未破坏 → Boss 未死 → 部位在当时朝向下确实暴露；
- **③ 数值**：伤害 ≤ 200（单次命中伤害上限，超出即异常上报）；
- **④ 限流**：**令牌桶**（想象每个玩家有个零花钱罐子，每拍固定塞一枚硬币，上报一次命中花一枚——罐子空了就拒绝，攒多了也不超过罐子容量。防的是「一包里塞 64 条报告」的洪水，而不是正常手速的玩家）。

其中两个判断题值得看注释：

- 部位不合法/不暴露 → **静默丢弃**，不回包不计数——「客户端预测落空」是正常网络行为（客户端预测 = 客户端不等服务器回包就先把「我打中了」演出来，等服务器结果回来对账；落空 = 演的和裁决不一致，退回去重演。网络有延迟，预测错是常态），当错误处理会让正常玩家被踢；
- `damage == 0` → 单独归类，**不计滥用**——它不是超限，是客户端自己算漏了伤害的 bug，计滥用会把有 bug 的正常客户端踢下线。

**职场习惯⑤**：错误要分类到「谁的问题」——对端恶意、对端 bug、自己 bug、正常网络行为，四种处理完全不同。一把抓的校验迟早误伤自己人。

## 4. 这份代码教你的 10 条职场习惯

全部来自源码注释的真实记载，按「新人最常缺」排序：

1. **注释写症状，不写功能**。「// 设置标志位」是废话；「// 没有它 Ctrl-C 没反应且毫无异常」是知识。这份代码的每条长注释都在回答「为什么不是显然的那个写法」。
2. **进程怎么死和怎么活一样重要**。信号只置标志、忽略 SIGPIPE、退出码有含义、收尾有凭据。
3. **fail-close**：不认识的一律拒绝。静默忽略的错误协议 = 「什么都能连上、什么都不对」的联调地狱。
4. **结构性保证优于口头约定**。删不得的代码不靠注释看护，靠 RAII 锁死（ReapGuard）。
5. **能被毫秒级单测是设计属性**。时钟注入、接口注入（FrameSink），副作用从逻辑里剥出去。
6. **容量 ≠ 占用**。`size()` 是容量，`alive` 计数才是占用——数错一个，全员被拒。
7. **顺序就是契约**。校验的顺序是安全策略，遍历的顺序是确定性契约，结算的顺序是裁决正确性。
8. **幂等优先**。重连补全量快照不补增量——补几次效果一样，永远安全。
9. **指标不能说谎**。从真实状态反推增量，而不是指望每处都记得打点（打点 = 在代码里手动埋日志、计数器，靠人记就是「靠自觉」——`main.cpp:131` 注释点名的失败模式）。
10. **跨端逻辑逐行对齐**。i-frames 先推进再扣血、客户端和服务端必须一模一样——顺序差一帧，手感差一截。
