# 01 · 网络层领读（`src/net/`）

> **怎么读**：先读 [[00-项目领读]] 的 L5.2 拿到地图，再来这里看**跨文件的因果链**——
> 单条注释能讲清「这一行为什么这么写」，讲不清「为什么 A 的存在让 B 的测试有资格红」。
> 本篇组织的就是后者。**每一节末尾给「改动地图」：动这里的什么会炸哪里。**
>
> 📖 教材结合的方向与 [[00-项目领读|00]] 相同：项目 → 解读 → 教材，单向。

## 0 · 模块形状：一个契约 + 一个实现 + 两块解码

```
transport.h      抽象契约（224 行,几乎全是注释——契约本身就是文档）
tcp_transport.*  LT epoll Reactor 实现（唯一实现,但接口留 UDP 口子）
frame_codec.*    拆帧（粘包/半包）——由 session 层持有,net/ 不认识它
byte_codec.h     定长字段的读写模板（u16/i32 的序与符号）
metrics*         epoll_ctl 计数器与指标上报
```

**为什么契约里几乎全是注释**：这是刻意的。`transport.h` 的注释是**可执行的规范**——每条契约都对应至少一个测试断言或一个事故记录（「Task 2 为此付了三轮学费」）。读它的顺序：文件头（两条主路径 + UDP 口子的准确范围）→ `Recv` 三态 → `Send` 二态合流 → `Poll` 三契约。

---

## 1 · 两条主路径，别混（`transport.h:37-42`）

```
主循环   ：set_on_* 注册回调 → Poll() 内部分派 → 主循环尾部 ReapClosed()
测试/工具：直接 Accept / Recv / Send（单步拉字节,不经过回调）
```

**解读**:`Accept()/Recv()` 这些单步方法**在主循环路径里根本不会被调用**——它们只为测试存在（不搭 reactor 就能单步拉字节）。判断一段代码走没走对路径,看它调没调 `Poll`。

> 📖 [[第3章 伯克利套接字|格雷泽第3章 §3.6]]：阻塞→非阻塞→多路复用的三级演化,本项目停在「epoll + 回调」级。
> 为什么回调而不是「Poll 返回就绪列表」（`transport.h:71-74`）:让调用方 Poll 之后遍历全表逐个 Recv = 退回轮询,每 tick O(N) 次 syscall——连接数一涨就是性能悬崖（附录 B #5「超过 4 人」正撞这里）。

**改动地图**：往主循环里加「Poll 之后遍历连接」的代码 = 性能悬崖复发；把回调改成返回列表 = net/ 的存在理由消失。

---

## 2 · Recv 三态：0 与 -1 之辨（`transport.h:61-68`）

| 返回 | 语义 | 可否缓存 |
|---|---|---|
| `> 0` | 读到 N 字节 | — |
| `0`（kRecvPeerClosed） | 对端 FIN。**终态** | ✅ 可缓存「这条连接死了」 |
| `-1`（kRecvWouldBlock） | EAGAIN,这次没数据。**非终态** | ❌ 绝不能缓存 |
| `< -1` | 硬错误（RST/EIO）,值留给实现写日志 | 调用方唯一处置:Close |

**解读**：把 −1 当 0 用 = 一次空闲就把好连接判死（静默丢连接）；把 0 当 −1 用 = 已关的连接被反复 Recv（忙等）。实现侧（`tcp_transport.cpp:424-441`）特意把硬错误取 **−2** 而不是 −1——日志里一眼分档；`n == 0` 直接挡掉——否则 `read()` 返回 0 会被**谎报**成对端关闭。

> 📖 [[第3章 伯克利套接字|格雷泽第3章 §3.5.1]]：`recv` 返回 0 的「FIN 之前的字节已全部交付完毕」保证,是 0 可以放心当终态的依据。

**改动地图**：新增返回码 = 调用方按值分支（契约禁止,< −1 只许 Close）；把硬错误改报 0 = 上层缓存终态,好连接被冤杀。

## 3 · Send 二态合流：false 的两种身份（`transport.h:159-165`）

`Send` 只返回 bool,**false = 两种情况合流**：①有残留（字节已排队,等 EPOLLOUT 冲刷）②背压超限已断连（字节没排队）。评审定稿**不为此加第三态**——两者的正确应对都是「别再往这条连接写」,语义等价；区别只在日志。

**EPOLLOUT 由实现内部管**（评审波C 修正）：`Send` 返回 true 后上层不需要 `DisableWrite`（幂等空操作,白耗一次 epoll_ctl）;返回 false 也不需要手动 `EnableWrite`（实现已挂）。

> 📖 [[第2章 网络IO多路复用|彭放第2章]]：EPOLLOUT 按需开关——常开会被 LT 反复唤醒（原文实测无限打印）。这里更进一步：开关这件事**从调用方手里收走**,上层想错都没有机会。

**改动地图**：给 Send 加「已写入多少」出参 = 调用方要自己持有尾巴 = 接口复杂度泄漏；让调用方管 EPOLLOUT = 按需开关纪律退化成口头约定。

## 4 · 承重设计一：epoll_ctl 全文件唯一收口（`tcp_transport.cpp:41-53`）

`RawEpollCtl` 是**全文件唯一**调 `::epoll_ctl` 的地方,而且这个事实是**可 grep 的**：

```bash
grep -n '::epoll_ctl' src/net/tcp_transport.cpp   # 必须只命中这一处
```

**为什么**：测试对「EPOLLOUT 按需开关」的覆盖完全依赖 `epoll_counters()` 的完整性——只要有一处注册绕过 `Ctl` 走裸 syscall,那次注册就不进账,对应断言**静默失去覆盖**（不会红,只会「看起来还在测」）。靠注释提醒不够,它必须是一个可 grep 的事实。

---

## 5 · 承重设计二：EpollCtlCounters 与它的两个边界（`tcp_transport.h:31-52`）

**问题**：`epoll_ctl` **没有**「查询已注册事件」的 API。「EPOLLOUT 是不是常开」从 Conn 里的 `want_write` flag **看不出来**——flag 说 false 而内核真常开的情形,flag 层面测不出来。

**两个必须知道的边界**（`Ctl()` 先记账再调内核）：

1. **syscall 失败也计入**——计数器全绿不代表内核真的收到了那个注册值（变异 M16 验证过：计数器全绿而内核没收到 MOD）。它证明的是「本实现**打算**注册成什么样」；
2. **时序判据抓不到 M2c**（永远挂 EPOLLOUT 变异）：`Poll(60)` 实测仍是 60ms——排空后 socket 真的不可写,LT 就不报 EPOLLOUT。**抓 M2c 的只有本计数器**。

> 📖 [[第2章 网络IO多路复用|彭放第2章]] §「EPOLLOUT 按需开关」：这条纪律在教材里是「写完摘掉」;在这里长成了「摘没摘必须有计量能证明」。纪律 → 观测 → 断言,三层才闭环。

**改动地图**：新增注册路径不走 `Ctl()` = 计数器漏账 = EPOLLOUT 断言失去覆盖;删计数器 = M2c 变异存活（评审做过 A/B,承重不可替代）。

## 6 · 承重设计三：MOD 失败必须回滚 flag（`tcp_transport.cpp:375-392`）

`UpdateEvents` 里 `epoll_ctl(MOD)` 会失败（如 `ENOSPC`:超出 `max_user_watches`）。失败时 **`want_write` 必须回滚成旧值**——否则 flag 说「已挂 EPOLLOUT」而内核没有：

```
flag 假 → 下次 EnableWrite 撞上幂等早退 → 永不重试
→ 发送队列永久滞留 → Send 持续 false → 连接静默僵死,零日志零指标
```

**不变量**：`want_write` 必须始终等于「内核实际收到了什么」。这个不变量同时是 `DisableWrite` 幂等早退（`c.want_write == want_write` 就 return）的正确性前提。

**改动地图**：在 `Ctl` 失败分支里不回滚 flag = 静默僵死链激活;把幂等早退删掉 = 每次 Send 白发一次 MOD（可容忍但浪费）。

---

## 7 · 承重设计四：回调自关的兜底（评审 P0-1,实测泄漏 141,904 字节）

契约（`transport.h:84-87`）只规定「OnBytes 返回 false ⟹ 实现**自行** Close」——**没有**规定「回调内部自己调了 Close 该怎么办」。上层无法自保,**net/ 必须兜住**：`OnReadable` 循环每轮开头 `if (!is_open(fd)) return;`——已判死的连接一字节都不许再读、不许再投递。

**反面形状**（事故记录）：内核里压着 256KB,`on_bytes` 每次都「Close 然后返回 true」——循环继续 read/继续派发,net/ 已决定丢弃的连接却把**攻击者可控的 141,904 字节**交给了上层。

> 📖 [[第10章 安全性|格雷泽第10章 §10.2]]：这就是「不信任网络输入」在 IO 循环里的具体形状——判死后的字节不是错误处理问题,是不可信数据流问题。

**改动地图**：删掉循环开头的 `is_open` 检查 = 该泄漏形状复活；契约新增「回调内不得调 Close」= 把兜底责任推给不可能保证它的上层。

---

## 8 · 承重设计五：延迟销毁与两处「不在这里关」（§6.4.4）

- `Close()` 只挂 `pending_close` 标记 + 入 `pending_ids_`（`tcp_transport.cpp:478-485`）——**正在遍历时删对象 = 悬垂指针**;
- `ReapClosed()` 先把待办**整份 swap 走**再逐个销毁（`:487-500`）——Destroy 触发 `on_close_`,那个回调完全可能反过来再调 `Close()`;边遍历边销毁 = 迭代器失效 = 宕机;
- `Poll()` 内**不调** ReapClosed（`:251` 契约明写）——Poll 返回时这一轮事件遍历才算结束,回收必须在主循环尾部（`main.cpp:308` 的 `ReapGuard` 用 RAII 钉住「一次都不能省」）。

配套不变量（`transport.h:192-194`）：**回收后的 ConnId 可以立刻被 Accept 重新发出去**（id 就是数组下标）——调用方不得持有跨 ReapClosed 的旧 id,否则「旧连接的包算到新玩家头上」。

> 📖 [[第2章 网络IO多路复用|彭放第2章]] §「断连三步同帧」：Dispose/删容器/摘 epoll 一步不漏;本项目把「同帧」落成「帧尾 RAII 统一回收」。

**改动地图**：在回调里真关（free）= 悬垂指针宕机;ReapClosed 不 swap = 回调重入迭代器失效;主循环漏调 ReapClosed = fd 永久泄漏（ReapGuard 析构兜底,但结构上仍要依赖它）。

---

## 9 · 承重设计六：背压超限 = 断连,不是拒收（`tcp_transport.cpp:449-460`）

队列超 `kSendBufCap` 时**断开连接**而不是返回 false 不排入。契约只给了 true/false 两态、**没有「拒收」态**——若超限静默不排入而返回 false：调用方按契约 EnableWrite → EPOLLOUT 触发时队列是空的 → 冲刷 no-op → **这 n 字节静默丢失**,连接还活着,两端错位且无报错可查。

**决策**：宁可掉连接,不可静默丢数据。「对端消费不过来」本身就是异常连接。

**改动地图**：把断连改成「丢弃本次 Send」= 静默丢字节链激活；提高上限不改语义 = 只是把触发条件推迟。

---

## 10 · 承重设计七：errno 的保存点（`tcp_transport.cpp:196-205`）

`Ctl()` 第一行 `saved_errno = errno`——因为 `log::warn / strerror` 要做 I/O,**会覆盖 errno**；构造函数失败路径事后取 errno 会取到错值,异常文案报错因。

**附带的防骗批注**（`:200-204`）：这里曾有句注释写「写锁」,而 **logger 根本没有锁**（只有一句 fprintf）。当前不出问题靠的是「单线程 reactor」这个调用方事实——**哪天改多线程,必须同时给 logger 加同步**,否则 fprintf 交错撕裂日志行。

**改动地图**：在 Ctl 里先 log 再抓 errno = 失败文案错因；把 reactor 改多线程 = 本文件全部「不加锁」前提作废（从线程模型声明开始重新审）。

## 11 · 建连期的「查返回值」清单（构造函数 + AcceptNew）

| 设置 | 失败后果 | 处置 |
|---|---|---|
| `inet_pton`（`:95`） | 失败时 `sin_addr` 保持 0 = **INADDR_ANY**——「地址写错」静默变成「监听所有网卡」,端口被外网扫到 | 必查,失败抛 |
| `SO_REUSEADDR`（`:71`） | 静默失败与没设无区别——「第一次能起、第二次 bind 失败」 | 必查,失败抛 |
| `TCP_NODELAY`（`:305`） | Nagle 保持开启——「偶发 0.5s 卡顿」且日志无异常 | 查 + **warn 并继续**（可降级的性能问题不升级成硬故障） |
| epoll 注册（`:139`） | 服务器起来了却永不 accept——「客户端连不上、日志什么都没有」 | 必查,失败抛 |

> 📖 [[第3章 伯克利套接字|格雷泽第3章 §3.2/§3.7]]：错误码立即检查（覆盖问题）与 SO_REUSEADDR/TCP_NODELAY 的出处。**处置分档**（抛 vs warn 继续）是本项目加的：按「坏了之后是硬故障还是可降级劣化」分。
