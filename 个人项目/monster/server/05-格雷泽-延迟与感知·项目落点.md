#### 三个参数为什么是这些值（§9.1 给了下限，不是建议）

| 参数 | 值 | 性质 |
|---|---|---|
| `interpolation_delay_ms` | 200 | **公式下限**（`≥ (1000/snapshot)×2`），调低必抖 |
| `max_extrapolation_ms` | 200 | **必须有上限**——无上限外推比卡住更糟 |
| `correction_smooth_ms` | 80 | 太短跳、太长飘 |

#### ★ 一个只有真跑起来才会暴露的设计冲突

`interpolation_delay_ms` 和 `max_extrapolation_ms` **都是 200ms**。
第一版把外推量算成"离最后一个快照过了多久"——而渲染目标本来就延迟 200ms，
于是**只要进入外推分支，就一定已经跑满上限**，那个区间形同虚设。

**修法**：外推量必须**从渲染目标算起**，不是从最新快照算起。
这在纸面上看不出来，只有真的把两个数放一起才暴露。

#### 4 端逐字节一致（§13.6）

```
P1=P2=P3=P4 room=5
PASS: 213 个共同 server_tick 上，4 端逐字节完全一致
```

**这条测的不是"广播对不对"，是"没写脏"**——任何端都不得有本地改状态的后门。
它是"权威边界"这条架构决策的**可执行证明**。

#### ★ diff 脚本本身必须先自证（我特意要求的）

一个永远绿的 diff 脚本比没有更糟。所以做了两个方向：

| 自证 | 结果 |
|---|---|
| `--self-test` 造单 bit 差异 | `首个差异在第 2 字节：5a vs 5b` |
| 真机 `-Corrupt 3`（改客户端一个字节） | `共 639 处不一致，定位到第 3 字节` |

**没做这个自证的话，"4 端一致"这句话是不可信的**——它可能只是脚本从来没比较过。

#### 坏网络模拟器（§13.7）

判据是**连续丢 N 个**（burst），不是"丢了几个"——格雷泽特别指出丢包常成串出现。
自愈测试**先断言确实丢了 ≥5 连包**，再验证外推跑满 200ms 后能追回，
而不是直接断言"追回来了"（那样没丢包也会绿）。

> 全量快照的幂等性（§7.3）在**顺利网络下是看不出来的**。
> 只有把包丢掉、把外推跑满上限，才能证明"卡了之后会自愈，不会永久错位"。
