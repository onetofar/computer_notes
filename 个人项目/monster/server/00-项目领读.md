## L0 · 这是什么（30 秒）

**2D 俯视角 4 人共斗狩猎游戏**。客户端 Godot 4，服务端 C++ 独立进程。

| | |
|---|---|
| 玩法 | 4 人一起打 1 个 Boss，Boss 有 5 个可破坏部位，部位破坏**永久**（头破硬直 2s / 腿破永久减速 ×0.6） |
| 难度来源 | 视交差——四个玩家的视野不重叠，必须靠协同 |
| 技术核心 | **服务器权威**。客户端只上报输入与命中意图，命中判定由服务器按开火那一刻的世界状态裁决 |
| 代码规模 | 服务端 46 个源文件（`otf-server/src/`），客户端 71 个 GDScript（`otf-game/scripts/`） |
| 当前状态 | K4–K8 全部完成：网络层 → 会话房间 → 权威 Boss → 战斗闭环 → Godot 接入 |

## L1 · 两个进程，一句话职责

```
otf-game (Godot)                 otf-server (C++)
┌──────────────────────┐        ┌──────────────────────┐
│ view/   表现          │◀──────▶│ session/  会话       │
│ net/    联机          │  TCP   │ room/     房间       │
│ sim/    单机玩法      │        │ world/    世界推进    │
└──────────────────────┘        │ sim/      玩法纯逻辑  │
                                │ net/      epoll IO   │
                                └──────────────────────┘
```

- **服务端是唯一真相**。客户端不提交位置、不提交伤害结果、不提交命中与否。
- **客户端只做两件事**：把本地输入发上去、把收到的状态画出来。

## L2 · 三个闭环

整个系统只有三条数据流。**读懂这三条，图就通了。**

### ① 连接闭环

```
net_client ──JoinRoom──▶ session::JoinRoom
                          ├─ 校验 kProtocolHash（不等则 Rejected{1} + 断连）
                          ├─ room_mgr::Join → 找空位 / 认领重连窗口内的座位
                          └─ 回 JoinAccept{player_id, hash, seed, room, spawn×2}
```
- 协议哈希真值 `kProtocolHash = 1168044926 (0x459ef37e)`，`src/proto/protocol.h:231`
- 座位上限 `kMaxPlayers = 4`，进程房间上限 `kMaxRooms = 32`
- 掉线后座位保留 **10s 重连窗口**，超时才回收（`room_mgr.cpp:161-172`）

> 📖 **教材结合**：握手用「幂等包 + 状态机」白拿重传——[[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.2]]（HELO/WLCM 状态机）；协议哈希防篡改的位置在 [[第10章 安全性|第10章 §10.1]]（校验而非信任）。

### ② 状态闭环（服务器 → 客户端）

```
sim/world ──每 tick──▶ world::Tick ──每 2 tick(10Hz)──▶ 序列化 WorldSnapshot(≤98B)
                                                          │
                                        session::SendFullSnapshot ──▶ net/world_proxy
                                                                        │
                                                          插值 + 有界外推 ──▶ view
```

- 快照**满房 98 B、单人 42 B**，上限 1400 B（`protocol.h:125`，`tests/test_world.cpp:185` 实测钉住）
- 频率关系：`kTickRateHz=20`、`kSnapshotRateHz=10`，整除关系由 `static_assert` 钉死（`config/game_config.h:59-60`）
- 客户端插值延迟 `interpolation_delay_ms = 200` = 公式下限 `≥ (1000/快照Hz) × 2`

> 📖 **教材结合**：为什么发**全量快照**而不是增量——满房 98 B 的小世界下全量每包自足、免簿记，[[第5章 对象复制|格雷泽第5章 §5.3–5.4]]；200ms 插值延迟正是 `½RTT + IP` 公式里 `IP = PP` 的取值，[[第8章 改进的延迟处理|第8章 §8.2]]。

### ③ 命中闭环（客户端 → 服务器 → 客户端）

```
玩家开火 ──HitReport{part, damage, client_tick}──▶ session
                                                    │
                             world 按 client_tick 回退到当时的 Boss 位姿
                             （boss_rewind 纯函数，保留最近 8 tick）
                                                    │
                             四道校验 → 扣血 → 破部位 → BossEvent 广播
```
- 保留窗口 `kPoseHistoryTicks = 8`（`src/config/game_config.h:196`）
- 服务器**不信任客户端声称的命中**，只把它当作"在第 N tick 尝试打部位 P"，
  用**回退后的权威位姿**重新判定

> 这条闭环是本项目最独特的地方：客户端打中的是它**以为**的那一下，
> 不是它**看到**的那一下。

> 📖 **教材结合**：整条闭环就是「服务器端回退」，四个要件一一对位——[[第8章 改进的延迟处理|第8章 §8.4]]；「不信任客户端声称的命中」是输入验证纪律，[[第10章 安全性|第10章 §10.2]]。

## L5 · 关键机制（项目 → 解读 → 教材）

每节三段式：**源码在哪**（项目）→ **为什么这么做**（解读）→ **📖 教材结合**（链到章文档对应节）。

### 5.1 主循环 · `src/main.cpp:303-364`

```cpp
while (g_running != 0) {
  app::ReapGuard reap_guard(transport);          // :308 析构即回收，结构上不可省
  transport.Poll(sched.PollTimeoutMs(now));      // :313 epoll_wait
  const std::int64_t post_poll = SteadyNowMs();  // :318 ★ 重新取时间
  sched.Advance(post_poll, [&]{ sessions.Tick(...); sessions.TickWorld(...); }); // :339
}
```

**两个容易看漏的点**：

1. `ReapGuard` 在**每轮开头**构造而不是结尾调用 `ReapClosed()`——
   于是这一轮无论走到底、`continue`、`break` 还是异常展开，回收都一定发生。
2. `post_poll` 必须在 `Poll` 之后重新取。用 `Poll` 之前的 `now` 算补帧，
   症状是"逻辑帧率随负载下降"，但根因是**拿过期时间戳算的**。

补帧上限与丢帧逻辑：`src/app/tick_scheduler.cpp:40-52`。

> 📖 **教材结合**：`while(IsRun){ IO; Logic; }` 的骨架与「IO 即服务端输入」的定性——[[第3章 线程、进程以及Actor模型|彭放第3章 §3.4 游戏主循环]]。
> 固定步长累加器/补帧上限是**本项目自己的设计**（教材无对应，见节内声明），epoll 的 50ms 超时就是帧节奏旋钮——[[第2章 网络IO多路复用|彭放第2章]]。

### 5.2 连接与帧 · `src/net/`

- 收包**唯一入口**是 `session_mgr.cpp:166` 的 `decoder.FeedAll(...)`，
  它把"喂字节 + 续喂背压 + 榨干"封成一个调用。
- 读干净到 `EAGAIN`：`tcp_transport.cpp:85` 的 `for(;;)`
- 增删延迟应用：`Close()` 只挂 `pending_close`（`tcp_transport.cpp:167`），
  真正关 fd 在 `ReapClosed()`
- 建连处必设：`SO_REUSEADDR`（`tcp_transport.cpp:63-71`，且查返回值）、
  `TCP_NODELAY`（`AcceptNew()` 内，反向验证：删掉就红）

> 📖 **教材结合**：EPOLLOUT 按需 / EAGAIN 义务 / SO_REUSEADDR 查返回值 / 断连三步同帧，每条纪律的原文实测依据——[[第2章 网络IO多路复用|彭放第2章]]；
> socket API 本身（bind/自动绑定/流语义）——[[第3章 伯克利套接字|格雷泽第3章]]；
> `TCP_NODELAY` 为什么必设（Nagle 半秒 + 按序交付这道门）——[[第7章 延迟、抖动和可靠性|格雷泽第7章 §7.4]]。

### 5.3 会话与房间 · `src/session/` `src/room/`

- 收件箱在 IO 阶段投递，在 tick 阶段统一取走——**IO 与逻辑分离**
- 房间回收顺序是硬约束：*先回收座位、再判销毁*（`room_mgr.cpp:177`）。
  反过来会让"所有人都在重连窗口内"的房在座位还没回收时就被销毁
- `room_id` **永不复用**（`room_mgr.cpp:110-114`），复用会让客户端攥着旧 room_id

> 📖 **教材结合**：IO 投递 / tick 统一取走的形状就是「每客户端一个代理、tick 时统一消费」——[[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.3 ClientProxy]]；
> 重连窗口与座位保留是本项目设计（教材的玩家服务在 [[第12章 玩家服务|第12章]]，但座位语义是项目自己的）。

### 5.4 世界推进 · `src/world/world.cpp`

结算顺序**写死**在 `world::Tick` 内部（446 行）。世界层**不读时钟**——
`server_time_ms` 由 `tick × 50` 算出来。

> 📖 **教材结合**：「不读时钟、结算顺序写死」是确定性纪律的服务器版——锁步那套「同输入同输出」的构造时约束，[[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.3.3]]（服务器有权威兜底所以不必做到位，但纪律同源）。

### 5.5 快照广播 · `src/session/session_mgr.cpp:375-390`

```cpp
for (const net::ConnId conn : needs_snapshot_) SendFullSnapshot(conn, tick);  // :387
needs_snapshot_.clear();
rooms_.TickAll(tick);                                                            // :393
```

- 补发重连快照必须在常规广播**之前**（§`TickWorld` 第一步），否则重连的人要等最多 100ms 黑屏
- `SendFullSnapshot` 里 `if (bytes.empty()) return;`（`:377`）——
  房间已销毁时没有真相可发，发一份空的比不发更糟

> 📖 **教材结合**：全量快照「每包自足」让补发天然安全（不存在"补哪个 delta"的账本）——[[第5章 对象复制|格雷泽第5章 §5.3]]；
> 「4 人房间人人全相关」是相关性集合 = 全体的退化形态——[[第9章 可扩展性|格雷泽第9章 §9.1]]（规模上去才需要裁剪）。

### 5.6 命中判定与回退 · `src/sim/boss_rewind.{h,cpp}`

回退是**纯函数**：输入 `(历史位姿窗口, client_tick, 部位)` → 输出判定结果。
服务器保留最近 8 tick 的 Boss 位姿（`kPoseHistoryTicks=8`，每 tick 一份 `BossNet`，共 132 B）。

> 📖 **教材结合**：与四要件逐项对位——远程玩家走插值（客户端 `world_proxy` 就是）、包内带 tick（`HitReport.client_tick`）、服务器存最近几帧位姿（8 tick 窗口）、判定在缓冲重建后做——[[第8章 改进的延迟处理|格雷泽第8章 §8.4 服务器端回退]]。
> 8 tick = 400ms 窗口 > ½RTT+IP 的回退需求，窗口大小怎么定教材给了公式。

### 5.7 客户端预测与插值 · `otf-game/scripts/net/`

| 参数 | 值 | 性质 |
|---|---|---|
| `interpolation_delay_ms` | 200 | **公式下限** `≥ (1000/快照Hz) × 2`，调低必抖 |
| `max_extrapolation_ms` | 200 | 必须有上限，无上限外推比卡住更糟 |
| `correction_smooth_ms` | 80 | 太短跳、太长飘 |

> 📖 **教材结合**：`IP = PP` 是被两侧约束夹死的唯一解、外推必须有界、纠正要平滑——[[第8章 改进的延迟处理|格雷泽第8章 §8.2–8.3]]；
> 本地玩家预测+校正的「漂移容忍」分级也在这节。

## L6 · 协议速查

11 条消息（`src/proto/protocol.h`）：

| 方向 | 消息 | payload |
|---|---|---|
| 双向 | `Heartbeat` | 0 B |
| C→S | `JoinRoom` | — |
| C→S | `PlayerInput` | 8 B：`seq:u16 + move_dir:i16×2 + action:u8 + form:u8` |
| C→S | `PlayerState` | 3 B：`hp:u16 + alive:u8` |
| C→S | `HitReport` | 13 B：`part:u8 + damage:u16 + client_tick:u32` |
| S→C | `JoinAccept` | 21 B：`player_id + hash:u32 + seed:u32 + room:u32 + spawn:i32×2` |
| S→C | `Rejected` | 1 B |
| S→C | `PlayerJoined` / `PlayerLeft` | — / 1 B |
| S→C | `WorldSnapshot` | ≤98 B（满房 4 人） |
| S→C | `BossEvent` | 10 B：`event + part_or_player + extra:u16 + duration:u16 + tick:u32` |

**上限**：`kMaxPayloadSize=1400`（不触发 IP 分片）、`kMaxFd=1024`、
`kFrameQueueDepth=64`、`kSendBufCap=128KB`、`kConnectionTimeoutMs=5000`。

**协议哈希**：`kProtocolHash` 的真值由 `tools/gen_protocol_hash.py` 从协议字段生成，
`gen-hash --check` 一致即证明 `技术参考.md` §8 与代码同步。

> 📖 **教材结合**：上行只有输入（Move 流形状：`PlayerInput.seq` 就是时间戳的角色）、下行只有状态——[[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.3]]；
> 1400 上限 = MTU 1500 扣头部，[[第3章 伯克利套接字|格雷泽第3章 §3.4]]（UDP 侧论据）与 [[第7章 延迟、抖动和可靠性|第7章 §7.3]]（包数经济学）；
> 心跳 5s 超时与 NAT 表项老化的关系——[[第2章 互联网|格雷泽第2章 §2.8]]。

## L7 · 改代码前必读的四条红线

1. **服务器不等客户端**——任何"客户端算好发上来"的字段都要重新在服务器上判一次。
2. **不收客户端上报的权威状态**——位置、伤害结果、命中与否，一律服务器算。
3. **不为绕过权威模型新增协议消息**——要新增先改 `技术参考.md` §8。
4. **协议字段增删改一律先改文档**——`技术参考.md` §8 是唯一权威。

另两条工程硬约束：

- **参数一律走配置**（服务端 `config/game_config.h`、客户端 `GameConfig`），不写字面量。
- **`sim/` 是纯逻辑**：无 IO、无时钟、无全局随机（随机要外部注入种子）。

> 📖 **教材结合**：红线 1/2 的机制依据——权威定义「客户端不能自己决定结果」[[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.1]]；输入验证「拒绝但不踢」的处置纪律 [[第10章 安全性|第10章 §10.2]]；`sim/` 纯逻辑与「确定性 = 同种子同调用序」同源 [[第6章 网络拓扑和游戏案例|第6章 §6.3.3]]。
