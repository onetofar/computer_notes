## 2 · 配置与日志：同一纪律的两种载体

> 📖 教材：[[第6章 搭建ECS框架]] §6.4（YAML 配置）、§6.5（log4cplus）

### 2.1 配置

**教材结论**：配置从硬编码/命令行迁到配置文件（端口、线程数、路径），要点是「读取一次、启动期生效」+
「配置项必须有单一来源」。

**本项目**：纪律同源，载体不同——**header-only 常量，没有运行时配置文件**。

| | 本项目 |
|---|---|
| 服务端 | `src/config/game_config.h`（261 行）+ `server_config.h`（137 行），`inline constexpr` 常量 |
| 客户端 | `otf-game/scripts/config/game_config.gd`，**注册为 autoload**（`project.godot` 的 `[autoload]`）——不注册就只是个普通文件，写 `GameConfig.xxx` 会直接报未定义 |
| 加载时机 | 编译期，无「读取一次」这一步 |

> 📌 **代价要说清**：header-only 换来的是零解析依赖、零配置错误（编译不过就是不过），
> 换来的是**改任何数值都要重新编译**。彭放书里 PyYAML 在 CentOS 环境的可用性问题，
> 是本项目当初不选 YAML 的直接原因之一——**这条因果属于工程经验，不是教材内容**。

### 2.2 日志

**教材结论**：日志是框架级设施，各实体直接调用而不是各自 `printf`——**日志走一个口**。

**本项目**：走一个口，但**那个口是两条路径并存**，不是一条。

| | 位置 |
|---|---|
| 声明 | `src/common/logger.h:16` `Level` 五级 |
| 旧文本路径 | `write()` / `trace|debug|info|warn|error()`（`logger.h:22-28`），给人看 |
| 结构化路径 | `format_line()` / `write_fields()`（`logger.h:64-73`），**单行 JSON**，给采集器 grep 用 |
| 实现 | `src/common/logger.cpp` |

> ⚠️ `logger.h:8` 写得很明确：**「两条路径并存：旧文本格式给人看，新 JSON 格式给采集器看，不要顺手统一」**——
> 因为 `net/tcp_transport.cpp` 已经在调 `log::warn(...)`，统一格式就是破坏既有调用点。
> 这是**有意的双口**，与「日志走一个口」不矛盾：一个出口（stderr），两种编码。

## 4 · 「配置即数据」：本项目最完整的一次落地

> 📖 教材：[[第11章 分布式跳转方案]] §11.1 的「配置即数据 / 清单类信息放数据文件不放代码」
> 与 [[第6章 搭建ECS框架]] §6.4 的「配置项必须有单一来源」同源；
> 原理层见 [[第4章 对象序列化]] §4.5 的「数据驱动的序列化」。

彭放书里这句是针对**地图跳转表**说的：「加一张地图 = 加一行，不改代码」。
本项目把同一纪律落到了游戏数据上，实测结果是：

- **10 份 JSON**（不是原稿写的 7 份，那是更早的快照），位于 `otf-game/resource/data/`：
  `bestiary` · `char_paperdoll` · `drops` · `equipment` · `gathering` · `items` ·
  `monsters` · `recipes` · `skills` · `status`
- 这些文件是**唯一真相源**，客户端加载后驱动表现；对应到 Godot 侧的 autoload 纪律，
  见 [[00-客户端项目领读]] 与 [[02-配置与数据层领读]]。

> 📌 **对照要点**：彭放书里的「数据驱动」说的是**配置表**（跳转表、YAML 参数），
> 格雷泽 §4.5 说的是**序列化布局**（成员偏移表）。本项目落地的是前者的游戏数据形态
> （JSON 内容表），**没有**采用后者的反射式序列化——理由见 [[07-教材对照-序列化与协议]] 对照 4。
> **这两件事经常被混为一谈，但它们要解决的问题不同。**

## 5 · 自建协议 vs 引擎给的协议

> 📖 教材：[[第11章 真实世界的引擎]]（商用引擎的 QoS / SyncVar / owner-only RPC）

彭放书里「客户端与服务端共享同一份表」「协议是两端唯一的契约，客户端引擎换了服务端无感」
这条，在本项目的对照是：

| 商用引擎路线 | 本项目路线 |
|---|---|
| 协议由引擎给（SyncVar 自动同步、owner-only RPC 由引擎保证） | **自建协议**，11 条消息逐字段手写编解码 |
| 引擎帮你处理「什么时候该同步」 | **自己判**：上行只有输入（`PlayerInput` 8 B），下行只有状态（`WorldSnapshot` ≤98 B），详见 [[00-项目领读]] L6 |

**一句话对照**：用引擎时协议是引擎给的，自建时协议是你唯一能控制的真相——
代价是 §4.1 那个「成对手写」的维护负担，本项目目前用「字段表 + 测试钉死」来兜（见 07 对照 4）。

## 6 · 断线语义：彭放「立刻销毁」vs 本项目「先留窗口」

> 📖 教材：[[第12章 断线与动态加载系统]] + [[第6章 网络拓扑和游戏案例]] 格雷泽 §6.2.2（幂等握手）
> + [[第12章 玩家服务]] 格雷泽（断线由平台面兜住）

**教材结论**：单进程时代断线是一个回调，分布式时代断线是**一次跨进程的分布式事务**——
每个持有该玩家状态副本的进程都要参与清理。彭放书里的策略是**立刻销毁**。

**本项目**：多一层宽容，但**四处打扫的清单是同一张**。

| | 本项目 |
|---|---|
| 断线后 | **座位保留 10s 重连窗口**，超时才回收（`room/room_mgr.cpp:161-172`） |
| 与教材的差别 | 「断线 ≠ 清座」——比「立刻销毁」多一层宽容 |
| 房间回收顺序 | **先回收座位、再判销毁**（`room_mgr.cpp:177`）。反过来会让「所有人都在重连窗口内」的房在座位还没回收时就被销毁 |
| **房间空了之后还跑不跑** | **座位回收干净后停 tick**（`room_mgr.cpp:198` 的 `TickAll` 跳过 `occupied_count()==0` 的房间）。规格依据是 `技术参考.md:1227` 的「成员数=0 持续 30s → 房间销毁（**tick 停止**）」——**这条以前没落地**。⚠️ 判据**不能**用 `connected_count()`：§7.2 红线 1「玩家掉线，**房间照跑**」，断线者座位还留 10s，房间仍有成员。详见 [[02-会话与房间领读]] §11 |

## 7 · appmgr 的两种同构：安排面 vs 部署面

> 📖 教材：[[第9章 服务器管理进程与HTTP]] + [[第13章 云托管专用服务器]] 格雷泽 §13.3
> + [[第9章 可扩展性]] 格雷泽 §9.2（服务器分区）

**教材结论**：appmgr ≈ 安排/注册面，「启动哪些进程」≈ 部署面。
**中心化的状态表 + 去中心化的工作进程**，是分布式游戏服务的通用骨架。

**本项目**：`room_mgr` 的「主进程往负载最小的机器开新局」是**同款决策**——
中心那张表是 `rooms_`，去中心的工作进程是各自的 world 推进循环。
规模是单机 `kMaxRooms = 32`（`config/game_config.h`），所以分区那一层在本项目里没有真正长出来；
**同构成立但只走完了第一层**。

## 8 · 两条被搬出原文补注的对照（格雷泽侧）

> 📖 教材：[[第6章 网络拓扑和游戏案例]] 格雷泽（NAT 地址问题）· [[第5章 对象复制]] 格雷泽 §5.3.1（脏状态位掩码）

这两处原先是**写在 `教材原文/` 里的补注**，因为它们问的是「我们项目怎么做的」，
所以一并迁到项目层：

| 教材结论 | 本项目 |
|---|---|
| 用 `SocketAddress` 做键会撞 NAT——**地址不总等于主机** | 本项目用 **TCP 长连接 + ClientProxy 表，键是 `ConnId` 而非地址**。与 [[01-网络层领读]] 的 id 纪律一致：连接身份在一次会话内是稳定的，地址不是 |
| 局部状态复制 = **位域 + 条件写**，读端照位域条件读；`mDirtyState \|= inState` 的 OR 合并是可靠性账本的核心 | 本项目 `BossEvent` 的位掩码 `ECRS_Pose` 与之**同源**——服务端按位判定这次事件要不要广播给谁，客户端按位决定播不播特效 |
