## 1 · 承重设计一：唯一「抽取而非移植」的对象，判据写成了清单

`boss_brain.h:2-26` 的文件头是全项目**移植纪律最完整的一处**，它把「搬什么 / 不搬什么」的判据固化成了可核对的清单：

> ★★ 这是本轮**唯一"抽取"而非"移植"**的对象：boss_ai.gd 在 view 层，是「sim 决策 + 表现执行」的混合体。判据（已确认）：
> 　· 能被 EffectiveTick 驱动的 = **决策**（状态机 / 转向 / 攻击时机 / 选点）→ 搬
> 　· 需要 AnimationPlayer / AudioStreamPlayer / 特效节点的 = **表现** → 不搬

**不搬的清单逐条对应源文件的行**（`:9-16`），而不是笼统一句「表现不搬」。其中两条是**红线级**的：

> · `_rig_steady_on()` —— ★§6.5.3 明文「不搬」：等动画收完才攻击 = 服务器等客户端
> · `_boss.is_turning()` —— 转身动画在播 → 禁位移。§6.5.3 明文「服务器不做转身中禁位移」

这两条的共同形状值得单说：**它们在单机里是「手感更好」的实现，在服务器权威里是「把裁决权交回客户端」的反模式**。`is_turning()` 尤其阴险——它读的是动画播放状态，而动画由客户端的 `AnimationPlayer` 驱动，于是 Boss 的位移会变成「取决于客户端动画播到哪了」。[[04-配置与参数领读|04]] §6 那条判据（两端是否必须一致才能通信）在这里的答案是：**必须一致，而动画状态做不到**，所以只能不搬。

`move_and_slide()` 也在不搬清单里，理由不同：那是客户端地形碰撞，服务器自己做整数像素积分。

**改动地图**：把 `is_turning()` 搬过来 = 引入一条「客户端说了算」的隐藏通道，且**没有任何测试会红**（客户端与服务器跑各自的动画）；把判据从「能不能被 tick 驱动」改成「我觉得重要」= 下次搬家就靠直觉。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.1]]：三层分叉解决的是「同一份代码两端要的东西不同」。本篇是它的**实例级**判据——`boss_ai.gd` 是「sim + 表现」的混合体，分叉动作就是把它拆成 [[03-世界与命中领读|03]] 讲的那两个东西。

## 2 · 承重设计二：时间单位是 tick，因为 `0.05f` 不是精确的 1/20

`boss_brain.h:23-26`：

> ★ 时间单位是 **tick** 不是秒。§9.1「前摇 12 tick / 攻击 5 / 硬直 8 / CD 50，全部整 tick」—— 换算是精确的（0.6s@20Hz=12，0.25→5，0.4→8，2.5→50），而用 float 累加秒数会在 tick 边界抖动出 ±1 tick 的抖动（0.6/0.05 恰好整除，但 **0.05f 的二进制表示不是精确的 1/20**）。

**这句话的价值在于它承认了一个陷阱**：直觉上 0.6/0.05 = 12 是精确的，看起来用秒完全没问题。但 0.05 在 IEEE754 里是无限循环小数，`float` 存的是它的某个近似；反复累加这个近似，误差就会在 tick 边界显现。**「恰好整除」在这层已经不成立。**

于是本模块所有计时都是 `int`：`timer_` / `attack_cd_left_` / `turn_cd_left_` / `stagger_left_`（`boss_brain.h:182-185`），推进是 `--`（`boss_brain.cpp:81-83`）。`dt_seconds` 只在**位移积分**处出现（`boss_brain.cpp:125-126`），那是必须的，而它由调用方按「一个 tick 多少秒」算好注入——**sim 不读时钟**（约束 2）。

**改动地图**：把 `timer_` 换成 float 秒 = ±1 tick 的抖动，且抖动会让前摇在 11.x 和 12.x 之间摆动，症状是「攻击偶尔早一帧」，极难定位。

## 3 · 承重设计三：`ReachTowards` 是所有距离判定的基量（B1 的乘数就在最后一行）

`boss_brain.cpp:272-281` 是全模块**被引用次数最多**的函数：

```cpp
double BossBrain::ReachTowards(const Vec2d& ndir) const {
  double best = 0.0;
  for (const BodyPoint& p : config_.body_points) {
    // 半像素定点还原成像素（见 sim_types.h::BodyPoint）。
    const double px = static_cast<double>(p.x2) * 0.5;
    const double py = static_cast<double>(p.y2) * 0.5;
    best = std::max(best, px * ndir.x + py * ndir.y);
  }
  return best * config_.body_scale;      // ← B1 漏改的就是这一行
}
```

**它在四处被调用，全部是「距离」**：

| 调用点 | 用途 | 行 |
|---|---|---|
| Chase 停步圈 | `stop_dist = ReachTowards(ndir) + attack_gap` | `boss_brain.cpp:115` |
| Strike 扇形 | `hit_r = ReachTowards(nd) + attack_gap + hit_slush` | `:324` |
| BreathCone | `range = ReachTowards(nd) + attack_gap + breath_range` | `:356` |
| RamSweep | `reach = ReachTowards(nd) + attack_gap + ram_width` | `:375` |

**所以 `body_scale` 一旦分叉，四个判定同时变成一半距离**——这就是 B1 的全部机制，见 [[04-配置与参数领读|04]] §1。

**为什么它不是「一个常数」而是「一次投影」**：停步圈是**方向性**的。朝上时龙的头伸得远（轮廓顶端），朝下时龙的脚就在脚下（`best` 从 0 起算，朝下 ≈ 0）。用同一个圆形半径会让 Boss 站着不动时玩家的直觉完全错位——「明明站在龙嘴前面，它却说我还在范围外」。

`best` 从 `0.0` 起算而不是从 `-inf` 起算，是与 GDScript 同款（`test_brain.cpp:77` 的注释明写「best 从 0 起算，与 GDScript 同」）：**轮廓在某个方向上的最大投影永远不为负**，否则负的伸出量会让停步圈变成负数。

**轮廓是半像素定点（×2）**：`BodyPoint` 存 `x2`/`y2`，因为源数据每个分量都是 0.5 的整数倍（-73.5 / -254.5），×2 后全部精确可表示，于是 `kBodyPoints` 这张 69 点的表里**一个浮点字面量都没有**（`game_config.h:117-123`）。

⚠️ **这里有一条与 04 §2 呼应的生成物纪律**：轮廓来自 `boss_zone_metrics.gd`，换素材后**必须重跑生成器**，否则 `_reach_towards` 算的是旧素材的轮廓，症状是「停步距离不对」而**不会有任何报错**（`game_config.h:111-115`）。

## 4 · 承重设计四：迟滞与换向 CD，一起解决「绕斜角每帧翻面」

`boss_brain.cpp:283-297` 的 `DirOf`，注释只有一行但信息密度很高：

```cpp
  // ★ 迟滞（手感机制 ②）：当前是横（纵）向时，纵（横）分量要超过另一轴 ×h
  //   才肯换轴。少了它，玩家绕斜角走时朝向每帧翻面。
```

**没有迟滞会怎样**：玩家在 45° 方向绕圈时，`|vx|` 与 `|vy|` 每帧交替略大，朝向就在左右/上下之间每帧翻转。而每次翻转都要播一次转身动画（1.9~2.2s，见 `:301`），于是**动画永远播不完**——Boss 看起来像原地抽搐。

换向 CD（`FaceTowards`，`boss_brain.cpp:299-305`）是第二道：

```cpp
  // ★ 换向冷却节流（转向动画链长 1.9~2.2s，斜角处不加节流会反复转身卡住）。
  if (dir == last_dir_ || turn_cd_left_ > 0) return;
```

注意 `DirOf` 是**纯函数**（只读 `last_dir_`，不改），而 `FaceTowards` 才改状态且被 CD 节流。这个分离让「算出想要的朝向」与「承诺换向」成为两件事，于是 Chase 里的攻击前置判据可以写得极干净（`boss_brain.cpp:135-136`）：

```cpp
const Direction want_dir = DirOf(d.target_pos, boss_pos);
if (attack_cd_left_ <= 0 && dist <= stop_dist && want_dir == last_dir_) {
```

**三个前置条件**（冷却好 / 已收步进圈 / 朝向已转到）里，第三个用 `want_dir == last_dir_` 表达，而注释说明了它为什么成立：

> ★ want_dir 在 FaceTowards **之后**算 —— boss_ai.gd 就是这个顺序，于是判据等价于「_last_dir 已经等于当前想要的朝向」（没在转身中）。

**这是「顺序即语义」的又一处**（[[03-世界与命中领读|03]] §1 的同款纪律）。把 `want_dir` 的计算挪到 `FaceTowards` 之前，「没在转身中」这个条件就退化成「上一帧不在转身中」——差一帧，而差一帧意味着 CD 最后一帧就能攻击。

**改动地图**：去掉迟滞 = 斜角抽搐；去掉换向 CD = 同上但更频繁；把 `want_dir` 挪到 `FaceTowards` 之前 = 转身最后一帧可以挥爪（玩家看到的是「龙还在转身就打我了」）。

## 5 · 承重设计五：早退分支连仇恨都不累积——位置本身就是语义

`boss_brain.cpp:85-92`：

```cpp
  // ── 已击杀 / 硬直：停脚，**连仇恨都不累积** ────────────────────
  //   boss_ai.gd:70-77 的早退分支。它在 aggro.update 之前 return，
  //   所以硬直期间被动察觉也停 —— 抄的就是这个位置。
  if (defeated || stagger_left_ > 0) {
    out.state = defeated ? BossState::Dead : state_;
    out.facing = last_dir_;
    return out;   // move = (0,0), moving = false, 无命中
  }

  const AggroDecision d = aggro_.Update(players, count, boss_pos, config_.dt_seconds);
```

**「抄的就是这个位置」的含义**：这段逻辑的正确性**不取决于它写了什么，而取决于它在调用图里的位置**。`aggro_.Update` 在早退之后，所以硬直期间**被动察觉也停**（在感知圈里站着也不会累积仇恨）。

如果有人为了「代码整洁」把早退分支挪到 `aggro_.Update` 之后：硬直 2.0s × `passive_threat_per_sec = 8.0` = **16 点被动仇恨**，而一次近战伤害 `threat_per_damage × 140 ≈ 140`。看起来无关紧要——但四个人同时砍时，被硬直打断的那个人会因为「什么都没干」而持续掉仇恨，**仇恨目标在战斗中漂移**。症状是「四个人一起打，龙却一直追着我」，没有任何一条断言会红。

`BeginStagger` 用**赋值**而不是累加也是同款（`boss_brain.cpp:56-60`）：

> ★ 用**赋值**而不是累加：boss_entity.gd 的 stagger() 每次破坏都把余额重置成 GameConfig.boss_stagger_time（连续破两个部位不会叠成 4s）。

## 6 · 承重设计六：确定性三循环，且推进点只有一个

`boss_brain.h:64-67` 给了两条理由，第二条是设计判断不是技术约束：

> ★ **确定性**轮转而不是随机：`sim/` 禁全局随机（约束 2 的随机纪律），回滚重放时随机序列一变状态就分叉。确定性还有一个白拿的好处 ——「连招有规律」这件事本身**可被玩家学会并反制，是设计而非缺陷**。

**推进点唯一**这件事有两处代码保障，注释也点明了为什么位置重要：

```cpp
// boss_brain.h:189-191（成员声明）
/// 轮转游标。**只在一次攻击完整走完（进 Recovery）时 +1**，
///   不在进入前摇时 +1 —— 否则被部位破坏硬直打断会把这一轮吞掉，
///   轮转就不再是"每三招一轮"了。

// boss_brain.cpp:236-238（唯一推进点，在 Attack case 里）
// ★ 轮转**唯一**的推进点。放在这里而不是起手，是为了被打断的前摇
//   （硬直）不吞轮转 —— 三循环必须是「每完整三招一轮」。
rot_index_ = (rot_index_ + 1) % kAttackKindCount;
```

而 `Breath` case 末尾有**同样一行**（`:254`）——严格说有两个推进点，但都是「进 Recovery 时」这一个语义位置。**在 Chase 里读 `rot_index_` 决定 `pending_kind_`（`:139`）而不改它**，这个读写分离是整套轮转的关键：

```cpp
// ★ 轮转在此**读取**但不在此推进：推进点唯一，在下面 Attack/Breath 收尾处。
//   少这一点，被部位破坏硬直打断的前摇会吞掉一整轮。
pending_kind_ = static_cast<AttackKind>(rot_index_ % kAttackKindCount);
```

**三种攻击怎么共用状态机**：`Ram` 走 `ChargeUp`（后退蓄力，`boss_brain.cpp:174-198`），`Claw` 与 `Breath` 共用 `Charge`（`:146-149` 的注释：「客户端的 telegraph 渐亮也在这个态」），进 `Charge` 收尾时再按 `pending_kind_` 分叉进 `Attack` 还是 `Breath`（`:160-171`）。

`AttackKind` 用 `enum class` 而不是裸 int 索引，理由写在 `boss_brain.h:94-96`：

> ★ 刻意用 `enum class` 而不是裸 int 索引：`rot_index_` 是持久成员，一个写错的字面量会静默越界到别的分支去，而症状要等好几秒后的状态错乱才显形（"怎么突然吐息了"），排查成本极高。

**改动地图**：把 `rot_index_` 的推进挪到 Chase 的起手 = 每次硬直吞一轮（玩家永远只看到挥爪）；给轮转加随机 = 回滚重放分叉，且连招不可学。

## 7 · 承重设计七：冲撞用线段不用扇形，用「到站即停」防退化状态

### 7.1 为什么不是扇形

`boss_brain.h:172-177` 一句话说清了：

> ★ 为什么不用扇形：冲撞是直线，被顶的人可以在 Boss 的**侧后方**，沿移动方向的 dot 仍然很高，但人并不在冲撞路径上。扇形会误伤一大圈。

对应的实现 `PointSegDistSq`（`boss_brain.cpp:25-47`）里有一个必须夹取的细节：

```cpp
  double t = ((px - ax) * dx + (py - ay) * dy) / len_sq;
  t = std::clamp(t, 0.0, 1.0);   // ★ 夹取：不夹就是无限直线
```

> ★ 用**投影夹取**而不是无限直线：冲撞的扫掠线段是有**起止**的，拿无限直线去判的话，站在冲撞起点正后方 1px 的人也会被判命中 —— 那人从头到尾没被撞到。

**「投影夹取」和「无限直线」在数学上只差这一个 `clamp`**，而症状是「没被撞到的人挨了打」。同一函数还处理了零长线段（`:35-38`，起终点重合退化成点）——而这**不是假想情况**：`boss_brain.cpp:189` 在蓄力结束那一 tick 就调了一次 `RamSweep(players, count, boss_pos, boss_pos, &out)`，线段长度恰好为 0。

### 7.2 为什么要有「到达」判据

`boss_brain.cpp:206-211` 是全模块注释最长的一段推理，因为它防的是一个**具体的退化状态**：

> ★ 冲撞**到站即停**：一旦进了停步圈就收住。
> 　不收的话会出现一个退化状态 —— 冲撞按 0.4s × 520px/s 要走 208px，停步圈才 146px，于是龙会直接冲过玩家、停在他**身后**（甚至身上）。
> 　那之后 dist(8) < stop_dist(146)，Chase 里 `dist > stop_dist` 恒假 → 龙再也不走路，永久贴着玩家打。「加个到达判据」比「加个脱困行为」小得多，而且更符合直觉：冲撞是「冲过去撞到」，不是「冲过去穿过去」。

**这段的推理结构值得学**：它没有停在「加个 if 就行」，而是把 bug 后的**因果链**写全了——冲撞距离 > 停步圈 → 冲过玩家 → `dist > stop_dist` 恒假 → 永久贴脸。知道链条的终点，才知道判据该加在哪（`:217` 而不是 Chase 里）。

同一段还有一处顺序上的讲究（`:218-219`）：

> ★ 位移**先算**再判 —— 判的是这一 tick 走完的整条路径，否则一 tick 高速位移会把站位直接穿过，中间的人永远碰不到。

冲撞 520px/s × 0.05s = **26px/tick**。一 tick 的位移直接穿越判定是可能的，所以 `RamSweep` 的 `to` 必须是 `boss_pos + out.move`（`:229`）而不是 `boss_pos`。

### 7.3 蓄力期目标丢失就中止

`boss_brain.cpp:177-182`：

> ★ 目标丢失就中止：蓄力本身是**朝反方向**走的，后退会把距离越拉越大，拉到仇恨圈外就会失锁 —— 那时还照原计划前顶，就是对着空气冲一轮。

## 8 · 承重设计八：两处观测口，专治「事件发了但状态没进」

### 8.1 `EnterDead`：症状与成因隔了三层

`boss_brain.h:138-146` 记录了一个只有实机才暴露的 bug 及其修复：

> ★ 为什么需要它（K7 才暴露出来）：`Step` 的早退分支只把**输出**的 `out.state` 设成 Dead，**成员 `state_` 不动**。而 `World::FillSnapshot` 广播的是 `brain_.state()`（成员），不是上一次的输出 —— 于是 BossDied 事件之后，快照里的 Boss 会一直显示成死前那一刻的状态（Recovery / Charge 之类），客户端 HUD 停在「还在挥爪」。
> 　症状与成因隔了三层，不显式同步就会一直没人发现。

**这个 bug 的形状值得记住**：`out.state`（每 tick 的输出，值拷贝）与 `state_`（持久成员）是**两个值**，它们在早退分支上分叉了。绝大多数时候它们相等，所以分叉不产生症状。

修复的代价也要记（`boss_brain.cpp:62-74`）：`EnterDead` 不只是设 `state_`，还要清**全部**计时器并复位轮转游标：

> // ★ 计时器一并清零：留着余额的话，Step 的早退分支之外还有别的分支会读它们
> // 　（比如 attack_cd_left_ 决定它能不能再进 Charge）。已经死了就一条都不该留。
> // 轮转游标一并复位：留着余额的话，同一局第二次 Boss（如果有）会从中途的招数开始，而症状只是「第二轮吐息来得比预期早一点」。

### 8.2 `stagger_left()`：把「规格的一半」变成可断言的

`boss_brain.h:150-153`：

> /// 部位破坏硬直的剩余 tick。★ 只读观测口 —— 「破坏部位会硬直 2.0s」这条
> /// 规格原本只有事件（StunStart/StunEnd）能看见，于是「brain 真的进了硬直」
> /// 这一半没人验：把 `BeginStagger` 调用删掉，事件照样发，全套测试照样绿。

**这是「绿灯不等于在守」的最小标本**。规格「破坏部位 → 硬直 2.0s」有两半：事件发出去（可观测）、brain 真的进硬直（不可观测）。只守一半时，**把实现整个删掉也不会红**。

与 [[架构评审-熵减-2026-10]] 里的 B7a 是同一条纪律的两端：B7a 治的是「守具没跑却报绿」，这条治的是「守具测的东西不是规格本身」。

## 9 · 承重设计九：仇恨表的三条契约，都是「不写下来就一定会坏」

`boss_aggro.h:10-14` 列出移植时**刻意没改**的两处，理由是「看着像可以优化，改了就会与单机不一致」：

> ① `best_score` 初值 -1.0 且用严格大于比较 → **同分时先到的玩家赢**（遍历序 = 调用方给的 players 数组序，§12 要求按 player_id 升序）。
> ② 玩家 `alive=false` 时直接 erase 仇恨 —— 倒地的人从仇恨表除名，「队友倒了，龙转头来找你」就是靠这一行。

**① 是一个跨文件的隐式契约**：`BossAggro::Update` 不知道遍历序的意义，它只知道「按你给的顺序遍历」。所以契约写在两处——`boss_brain.h:123-124`（「**必须按 player_id 升序**」）、`boss_aggro.h:81-82`（同样的话）。**调用方不遵守时不会编译失败，只会静默改变目标选择。**

**② 是玩法而非实现**：`erase` 让倒地玩家从表里消失，于是「最后一个人」自动成为唯一目标——「队友倒了，龙转头来找你」不是特判出来的，是表的自然结果。

### 为什么是小数组而不是 `unordered_map`

`boss_aggro.h:58-62`：

> ★ 用**按 id 升序的小数组**而不是 `unordered_map`：
> 　 sim_types.h 文件头第 ③ 条要求遍历序确定；`unordered_map` 的迭代序依赖插入历史与桶数，虽然本类当前不迭代它，但**快照/恢复会把容器形状一起带进状态**，一旦将来有人遍历它就是回放分叉。

**注意这条理由的时态**：「虽然本类当前不迭代它」——现在不用防，但**快照会把容器形状带进状态**，所以一旦有人开始遍历就已经晚了。这与 [[04-配置与参数领读|04]] §11.1 是同一个道理的两个实例：**为将来的误用预设结构**，和**为将来的误用预设断言**。

`AggroSnap::kSlots = 8 > kMaxPlayers = 4`，注释给了理由（留给单测里 `player_id=9` 那种用例）。

## 10 · 承重设计十：`AggroConfig` 单独传入，因为并进去就是参数双源

`boss_brain.h:116-119`：

> /// @param aggro 仇恨参数**单独传入**，不塞进 BrainConfig —— 因为
> ///   WorldConfig 里也有一份（§12 把 aggro 列为 Boss 的成员）。两处各留一份
> ///   = 参数双源：改一边忘了另一边不会红、只会行为分叉。

**这是一条「因为会双源所以不许双源」的设计**：`WorldConfig` 同时含 `anatomy` / `aggro` / `brain` / `player` 四个子配置（`world_config.h:23-26`），`boss_brain.h:117` 的注释因此专门说明 `aggro` 为什么**不**被 `brain` 吞掉——因为 §12 规定 aggro 是 Boss 的成员而不是 brain 的成员，让 brain 持有它就会产生第二份。

⚠️ 这条设计**没有机器守卫**。`BossBrain::Setup(config, aggro)` 的签名挡住了「只传一个」，但没挡住「两次传不同的 aggro」。真要防，得在 `World::Setup` 里断言 `&config.aggro == &world.aggro` 这种——目前没有。

**与 §12 的关联**：`test_brain.cpp:359` 有一处用 `MakeAggroConfig()` 造了个 `loose` 变体，说明「生产参数组合下 brain 行为如何」是有人想过的问题，但那是一次性的，不是守卫。

## 11 · 承重设计十一：`loot_roll` 的两份实现，禁止抄实现（B2 案发现场）

`loot_roll.h:4-16` 是 B2 的根因记录，结构上分三层：

**第一层 · 为什么不合并**：

> ★ 这个头文件为什么存在：企划 §4 的 P3 拍板把 roll 判定留成**两份实现**（GDScript 阶段一客户端权威 / C++ M6 服务器权威），代价是分叉风险 —— 而分叉是**静默的**（掉率差一点，谁都发现不了）。

注意「掉率差一点，谁都发现不了」——**这就是静默的具体形态**。B1 的静默是距离算错（玩家能感觉到），B2 的静默是掉率差 0.1%（玩家感觉不到，但服务器和客户端永远对不上账）。

**第二层 · 为什么用测试向量而不是只留一份**：

> 对策不是"只留一份"（那要求单机常驻 C++ 进程，把 0.2 剩下五个里程碑全绑死在服务端构建链上），而是**共用一组固定种子 + 期望输出的测试向量**：`loot_roll.json`。本文件与 GDScript 那份各读它、逐条比对 expected；任一边改算法 → 那边红。

**第三层 · 移植纪律**：

> ★ ★ **移植纪律：不许抄 GDScript 那份的实现** —— 抄了就失去交叉验证的意义。本文件独立按 brief §1.1 的规格重写，**只共享规格不共享代码**。

这是**跨语言交叉验证的唯一成立条件**。对比 §12 的 `config_parity.json`（共享**期望值**，各自读各自的值）——两种共享方式：

| | `config_parity.json` | `loot_roll.json` |
|---|---|---|
| 共享什么 | 期望值（参数） | 期望值（**种子 → 输出**） |
| 各自独立什么 | 各自的配置 | **各自的算法实现** |
| 能抓什么 | 两端参数分叉 | 两端算法分叉 |
| 代价 | 改配平要同步改 json | 改算法要重算向量 |

### 为什么禁用 `std::mt19937`

> 同时禁用 std::mt19937 / std::uniform_real_distribution：它们的实现与版本、平台、标准库都绑定，**没有任何跨语言一致性保证**，拿它们当"双实现一致"的基准等于在流沙上盖楼。

所以这里手写 `xorshift32`（`loot_roll.h:66-70`），连种子为 0 的处理都写明（`kZeroSeedReplacement = 0x9E3779B9u`，黄金比例常数）——xorshift 的零状态是**不动点**，会永远停在零。

### 三条遍历/消耗契约

`loot_roll.h:74-84` 把「缺了它两端排序不一致 = **假阳性红**」的契约逐条写出：

```cpp
/// ★ 遍历顺序契约（缺了它两端排序不一致 = **假阳性红**）：
///   1. `parts` 按**部位名 ASCII 升序**，跳过不在 `broken_parts` 里的部位
///   2. `core` 表**恒最后**（必定结算，无部位要求）
///   3. 表内按原序
///
/// ★ 两处"不消耗随机数"的契约（漏了任何一处两端序列立刻分叉）：
///   · 未命中**不**摇第二个随机数
///   · 整张表被跳过（部位没破 / 表为空）时一次都不摇
```

**「假阳性红」与「序列分叉」是两种不同的失败**，前者是测试不可信，后者是实现错——而**契约漏了会先变成前者**（测试报红但代码其实没错，因为两端排序不同），修着修着就麻木了。所以作者选择**先把契约写死再让人写实现**。

`part_order` 排序的职责**故意留在调用方**（`loot_roll.h:45-47`）：

> 本类不做排序，是为了把"顺序是谁的职责"摆在明面上而不是藏起来。

> 📖 [[第8章 改进的延迟处理|格雷泽第8章 §8.4]] 的「状态可复现」在本节变成「随机序列可复现」——两者的判据相同：**只要有一个隐式状态没被记下来，回放就分叉**。区别是回退窗口只有 8 tick（`game_config.h:217`），而 PRNG 状态是**整个 roll 过程**（`RollResult::state` 显式带出，`loot_roll.h:62`）。

## 12 · ★ 本篇实测：三个 Config 结构体，三种不同的命运

`src/sim/` 里的三个 `*Config` 结构体都给字段写了默认值，而真值在 `config/game_config.h`。我把三者逐一比对：

| 结构体 | 默认值与真值的关系 | 生产路径 | 风险 |
|---|---|---|---|
| `BrainConfig`（`boss_brain.h:42-84`） | **19 个字段全部一致**（含 B1 的 `body_scale=3.0`、新收的 `hit_dot_threshold=0.35`） | 全走 `MakeBrainConfig()` | 无 |
| `AggroConfig`（`boss_aggro.h:25-33`） | **3 个不一致**：`aggro_radius` 600 vs **780**、`attack_range` 200 vs **380**、`give_up_dist` 900 vs **1200** | 全走 `MakeAggroConfig()` | **见下** |
| `world::WorldConfig`（`world_config.h:35-43`） | **10 个字段全被覆盖**（见 [[04-配置与参数领读]] §11.1） | 全走 `MakeWorldConfig()` | 误导，无运行风险 |

### 12.1 AggroConfig 这一处已经造成了「两个测试验两个值」——**已修（2026-10-14）**

`config_parity.json` 里 `aggro_radius` 的期望值是 **780.0**，`cpp_key` 指向 `AggroConfig::aggro_radius`。`tests/test_config_parity.cpp:140` 通过 `MakeAggroConfig()` 取值 → 780 → 绿。

而 `tests/test_aggro.cpp:35-45` 的 `GdConfig()` **逐字段抄 `otf-game/test/test_boss_aggro.gd`**，用的是 **600/200/900**——那是客户端那份测试的历史参数，不是生产真值。

**两个测试全绿，验的是两个不同的 `aggro_radius`（相差 30%）。** `test_brain.cpp:54-64` 的 `TestAggro()` 更是混搭：`attack_range` 用生产的 380，`give_up_dist` 拉到 100000（避免测试中 Boss 追出圈），`aggro_radius` 用 600。

**为什么这不是 bug**：`test_aggro` 验的是**算法移植忠实度**（期望值抄 GDScript 那份单测），不是参数新鲜度——与 `test_anatomy.cpp` 同款，这是本项目一贯的刻意设计（见 [[04-配置与参数领读|04]] §1 关于「绿灯证明什么」的判据）。

**已采取的两步**：

1. `AggroConfig` 的三个默认值已对齐真值（780 / 380 / 1200），与 `BrainConfig` 的既有约定一致（[[04-配置与参数领读|04]] §11.0）。
2. `tests/test_config_parity.cpp` 新增「**默认值 == 真值**」断言组（`AggroConfig` 7 + `BrainConfig` 23 + `PlayerConfig` 5 + `WorldConfig` 10 = 45 字段），把「默认值与真值分叉」从**零断言**变成**有守卫**。

**反向验证**：把 `aggro_radius` 默认值打回 600 → 精确命中
`AggroConfig：默认成员值 == MakeXxxConfig 真值（7 个字段）  aggro_radius(600 ≠ 780)`，其余 44 字段零误报。

⚠️ **`AnatomyConfig` 故意不进这组守卫**：它的默认值刻意是全 0 / 只有 Head，因为 sim 的纪律是「参数也是输入」（`boss_anatomy.h` 头注：把真值写进默认成员 = 把参数注入偷偷藏进 sim）。**那边是刻意的，`AggroConfig` 这边不是。** 两者看着同类，判据相反——这正是「顺手统一」的陷阱。

**仍然没被守的**：`BossAggro` 的**算法**从未在**生产的参数组合**下跑过常驻断言。`test_brain.cpp:359` 用 `MakeAggroConfig()` 造 `loose` 变体是唯一一次，但那是一次性手工验证。

### 12.2 原建议与实际处置的差异（一处我没照自己的建议做）

我写这一节时的建议是「**删掉** `AggroConfig` 的三个不一致默认值」，理由是删掉后「忘了填」会变成编译错误。**实现时我推翻了自己**：

**改成对齐默认值 + 加断言组。** 因为删掉默认值之后，将来**新增一个字段**而忘了在 `MakeXxxConfig()` 里赋值，会从「误导」变成「静默未初始化读取」（UB，比误导更难查）。而加断言的方案，新增字段时只会让你**少写一行断言**。

> **修正后的一般判据**：**「消灭分身」听起来比「守住分身」干净，但只有后者是安全的**——因为前者要求你「记得填」，后者只要求你「记得补一条断言」。凡是「消灭之后新增字段会变成 UB」的场合，一律选守住。

本轮实际做了两件（都不需要拍板，因为没改纪律表述）：

1. `AggroConfig` 三个默认值对齐真值 + 头注写清「曾经是 600/200/900，抄自客户端测试」与「与 `AnatomyConfig` 相反」。
2. `test_config_parity.cpp` 加「默认值 == 真值」断言组（45 字段），反向验证过。

**仍未做、且需要拍板的**（要改 `CLAUDE.md` 约束 1 或 `技术参考.md` §2 的**纪律表述**）：

3. 在 `sim/` 层立一条规矩——「`*Config` 结构体的玩法默认成员值**必须等于**真值」，例外只有 `AnatomyConfig` 那种「默认值 = 关闭语义」的。这条最好也最好写成一个 `check_sim_purity` 的新 CHECK 类别（扫 `src/sim/*.h` 的 `= <数字>` 且字段名不在豁免表里）。
4. `config_parity.json` 的 `cpp_key` 从字段名改成**取值路径的显式声明**（例如 `"source": "MakeAggroConfig"`）。好处是「这条期望值从哪儿取」不再靠读 C++ 才能知道。
