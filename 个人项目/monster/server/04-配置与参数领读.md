## 1 · 承重设计一：「两个运行时各有一份」不是参数渗透

`game_config.h:11-13` 的原话，是本项目最容易被误判成「违反了约束 1」的一条：

> ★ 这不是"参数渗透"，是**两个运行时的配置各有一份**，各自的唯一入口：
> 　　客户端改手感 → 改 game_config.gd
> 　　服务器改数值 → 改本文件
> 　 改一个必须同步改另一个

**为什么不能合并**：架构前提是服务器权威（§7.1）——部位的结算规则、仇恨半径、停步圈全在服务器裁决，**服务器不可能去读一个 Godot autoload**（`game_config.h:4-8`）。所以「一个数字一个家」这条纪律在这里的正确形态是「**一个运行时一个家**」，不是「全项目一个家」。

**B1 就是这条纪律第一次被违反的代价**（`game_config.h:153-161`）：

> ★ 2026-10-08 路线 C（全局 32 像素口径）后必须与 game_config.gd::boss_scale 同值。
> 　 客户端把 1.5 翻到 3.0……这里曾漏改 —— `ReachTowards()` 是**所有** Boss 距离判定的基量
> 　 （停步圈 / 扇形攻击半径 / 吐息锥 / 冲撞判定宽度全从它派生），
> 　 于是服务器算出的一半距离。

**为什么它这么贵**（不是因为难，是因为**它没有症状**）：

- 编译器不报错（两边都是合法 float）；
- 服务器不崩（1.5 和 3.0 都能算出一组自洽的距离）；
- 单测全绿（没有一条断言比对过这个值）；
- 唯一症状是玩家主观感受：「看着已经站在龙身上，服务器说还在范围外，Boss 继续走」——而这句话正是 `game_config.gd:98-100` **自己记下来的**。同一份文件里既记着症状又躺着病因。

**防复发不是靠记得，是靠机器**：`resource/otf-resource/data/test_vectors/config_parity.json` 是两端唯一的期望值来源，`tests/test_config_parity.cpp` + 客户端 `test_config_parity.gd` 各 32~33 条断言各读一次。

> ⚠️ **一个必须写进方案里的细节**：这两份断言的期望值**都从共享 json 读**。硬编码期望值就是自证——把 `boss_scale` 在两端同时改成 2.0 而 json 不动，断言会**红**；但把三处一起改成 2.0，它会**绿**。绿灯证明的是「三处一致」，不是「值对」。后者是配平判断，仍归人。

**改动地图**：把两份合并成一个文件 = 服务器要依赖 Godot 运行时（架构前提失效）；让客户端从服务器拉配置 = 阶段一没有配置分发通道；只改一边 = B1。

## 2 · 承重设计二：三层分工，值只住中间层

```
config/server_config.h   进程/部署域：端口、补帧上限、poll 超时、会话数、座位重连窗口、地图几何
        │                            （这些数客户端无从知道，也不该知道）
        ↓ 只提供常量
config/game_config.h     玩法域：部位血量、暴露表、仇恨、Boss 轮廓与决策、玩家、命中校验
        │                            （这些数两端都要一致）
        ↓ MakeWorldConfig() 唯一产地
world/world_config.h     **只有类型定义，不放真值**（world_config.h:3-9 的分工声明）
```

`world_config.h:3-9` 把这条讲得很直白：

> ★ 为什么与 game_config.h 分成两个文件（而且反向是本文件不含数值）：
> 　　 world_config.h = **类型定义**（world 与 sim 之间的契约）
> 　　 config/game_config.h = **数值真值**（GameConfig 的服务器侧镜像）
> 　 sim/ 与 world/ 因此不认识任何玩法数值。数值只在 game_config.h 一处。
> 　 改数值只有一个玩家（CLAUDE.md 约束 1 的服务器对偶）。

「契约 vs 真值」这个切分有个直接好处：`WorldConfig` 这个类型可以在 `sim/` 与 `world/` 之间自由传递而不泄漏任何数值——[[03-世界与命中领读|03]] §「回退的实现是纯函数」能成立，前提就是 sim 侧拿到的是**填好的结构体**，而不是它自己会去读的全局。

> 📖 [[第6章 搭建ECS框架|彭放第6章 §6.4]]：配置项必须有单一来源、读取一次启动期生效。本项目是这条纪律的**跨语言变体**——「一次读取」对应 header-only 常量，「单一来源」被拆成了「每运行时一个源 + 机器对账」两半。

## 3 · 承重设计三：三处 `static_assert`，把跨文件不变量钉在编译期

```cpp
// game_config.h:49
static_assert(config::kTileWorldPx == 96, "世界瓦片边长必须是 96px（32×3）；改 SCALE 要同步这里");

// game_config.h:60-61
static_assert(sync::kTickRateHz % sync::kSnapshotRateHz == 0,
              "快照频率必须整除 tick 频率（§6.3），否则「每 2 tick 发一次」是假的");

// server_config.h:132-133
static_assert(kSpawnTileCount == kMaxPlayers,
              "出生点数必须 == 座位数（§10.2：4 个固定位对应 4 个座位）");
```

三条各钉一类**「改 A 忘了改 B」**，而它们共同的处置是：**让不一致变成编译失败，而不是运行时把 Boss 放出地图外**（`game_config.h:45-46`）。

第二条值得单看：它的错误消息是**假的**——`kTickRateHz % kSnapshotRateHz != 0` 不会让「每 2 tick 发一次」变成假的，而是让 `kSnapshotEveryTicks`（`game_config.h:59`）这个整除算出来的值本身失去意义。断言保护的是**推导的前提**，不是结果。

**改动地图**：删掉这三条断言不会立刻出事，只会在有人把 `snapshot_rate_hz` 改成 7 的那天出事；把断言改成运行时 `if` + 日志 = 把编译期问题推迟到生产环境。

## 4 · 承重设计四：秒 → tick 的换算只在一个地方发生

`dt_seconds` 在两处被算出来，但都是**同一个口径**（`game_config.h:182` / `:193`）：

```cpp
c.dt_seconds = static_cast<double>(kTickIntervalMs) * 0.001;
```

而真正的换算点在装配时（`game_config.h:243-246`）：

```cpp
// ★ 时长→tick 的换算在这里做，且用**同一个** dt_seconds 口径，
//   免得「硬直 2s」在某处按 50ms 算、另一处按 0.05s 算差一 tick。
w.brain.stagger_ticks =
    static_cast<int>(std::lround(kBossStaggerTimeSec / w.player.dt_seconds));
```

**为什么这条值得单列**：`kBossStaggerTimeSec`（`:201`）是**秒**，而 `windup_ticks = 12` / `recovery_ticks = 8` 是**tick**（`:167-169`）——同一个模块里两种单位混用。§9.1 明确要求「全部整 tick」，而秒→tick 的转换一旦散落到多个地方，各自算各自的，就差一个 tick（0.6s 按 50ms 算 = 12，按 0.05s 算 = 12，看着一样；换一个非整除值就露馅）。

`lround` 而不是强转也很关键：强转会截断，截断方向带来的 off-by-one 在「前摇 12 tick」这种数值上会变成「偶发少一帧」，而**偶发**是最难查的一类症状。

**改动地图**：把 `dt_seconds` 改成每个模块自己算 = 差一 tick 的幽灵 bug；改成 `static_cast<int>(2.0 / 0.05)` = 同样的数但换算点散成四处。

## 5 · 承重设计五：`pose_history_ticks = 8` 的算术摊开写在注释里

`game_config.h:208-217` 是全模块**唯一需要算术**的地方，它把推导整段留在注释里：

```cpp
// ★ `pose_history_ticks` 的来历（这是全 K7 唯一需要算术的地方，摊开写明）：
//     客户端画面滞后 = 插值延迟 200ms                     = 4 tick
//   + 报告从客户端飞到服务器的单程（局域网 ~5ms，留 100ms 余量） = 2 tick
//   + 插值段还要**更早**的那一端（快照间隔）                  = 2 tick
//   ────────────────────────────────────────────────────────
//                                                          = 8 tick
//   少了最后那 2 tick，回退就会在「客户端正插值到的那一段」的左端点查不到样本
//   → 恒定退化成「按当前位姿算」，也就是延迟补偿**看起来在、实际没生效**——
//   而那正好是本任务最难自查的失败模式（§8.3：「不做不会崩，只是手感变差」）。
```

**这一段是本模块的文档范本**，三个特征都有：

1. **给出项而不只给结果**——四个加数分别是什么，各自凭什么；
2. **写出「少一项会怎样」**——不是「8 是合适的」，是「少 2 tick 会退化成静默失效」；
3. **承认余量是拍的**——「局域网 ~5ms，留 100ms 余量」直接写出这是估计而非推导。

对比同文件里 `walk_speed_px_s = 73`（只写值 + `// boss_walk_speed`），差距就是**这个数将来会不会被人随手改**。

> 📖 [[第8章 改进的延迟处理|格雷泽第8章 §8.4]]：服务器保存最近若干帧位姿。本项目把这个窗口压到 8 tick，靠的正是这段注释里写下的「快照插值的确定性」——[[03-世界与命中领读|03]] §2 讲的是同一个决定的另一面。

## 6 · 承重设计六：判据 —— 一个参数该不该进 `protocol.h`

`game_config.h:203-206` 与 `server_config.h:16-18` 各写了一遍同一条判据，因为它决定了本模块的**边界在哪**：

```cpp
// ★ 这些数**不在** protocol.h：那里每一个 constexpr 都进协议哈希的输入集合
//   （§8.4），而命中校验参数不是协议（两端不靠它握手）——放进去会让「改一个
//   校验阈值」变成「改协议 + 重算哈希」。它们是玩法/策略参数，唯一的家是本文件。
```

```cpp
// ⚠️ 这些数**不是协议的一部分**，所以它们不在 src/proto/protocol.h 里，
//   也**不在** §8.4 的协议哈希覆盖范围内……
//   客户端无从知道「服务器开多少端口」，把它算进哈希会让改一次部署就全端握手失败。
```

**判据（把两条合起来读）**：

> **两端是否必须对它一致才能通信？**
> 是 → 进 `protocol.h`，进哈希，改了要重算（§8.4）
> 否 → 进本模块，两端各改各的，不重算哈希

`kHitDamageCap`（200）与 `kMaxSessions`（64）看着都是普通常量，但因为「两端不需要为它握手」，落在同一侧。

**特例 · 两端同值但不是协议**（`game_config.h:225-231`）：

```cpp
/// §8.2 HitStop 的两个档位（毫秒）。★ 与客户端 GameConfig 的
///   `impact_hit_ms` / `impact_broken_ms` 同值 —— 但这**不是**协议常量：
///   它不进协议哈希的输入集合，改它不需要重算 §8.4 的 hash，两端各改各的。
///   之所以两端都要有：顿帧强度是**表现**，由服务器裁决后下发（§7.1），
///   客户端只按 duration_ms 映射本地档位。
```

**这是最容易读错的一类**：「两端同值」≠「是协议」。这里两端同值的理由是**服务器裁决表现强度并下发**，不是**双方必须协商才能通信**。若哪天客户端想自己决定顿帧强度，两端不同值反而是对的。

**改动地图**：把命中校验参数搬进 `protocol.h` = 调一次手感阈值就要走完整协议变更流程（含两端同改 + 重算哈希）；反过来把 `sync::kTickRateHz` 搬出 `protocol.h` = 帧率从协议降级成部署参数，两端帧率不一致时**握手通过、行为分叉**，比 B1 更难查。

## 7 · 承重设计七：三份副本，三种不同的「谁在守」

`config/server.yaml` 与 `protocol.h` 的 `namespace sync` 是一对孪生副本，而 `server.yaml:11-22` 自己写下了真相：

> ★ **诚实说明**：这份 yaml 与 protocol.h 之间**当前没有任何自动交叉校验**
> 　（2026-10-07 更正。此前这里写「tests/test_smoke.cpp 会核对 protocol.h 与 §9.1 的数值一致」是**不实陈述** —— 那是"注释说谎"的一个实例）：
> 　· test_smoke **既不读这份 yaml，也不读《技术参考.md》**。它比对的是**自己源码里的硬编码字面量**（如 `check_eq(kMaxPlayers, 4, ...)`），
> 　　守的是「protocol.h 里的值没被人悄悄改掉」，不是「三份副本一致」。

加上 `server.yaml:18-20`：仓库**没有 yaml 加载器**（零第三方依赖是硬约束，PyYAML 禁用），所以这份文件是「给人看的运行时可读副本，**不是生效配置**」。

于是三份副本的守成方式完全不同：

| 副本 | 谁在守 | 守的是 |
|---|---|---|
| `protocol.h` 的 `sync::` | `test_smoke.cpp` 硬编码字面量 | 这一份没被悄悄改掉 |
| `game_config.h` ↔ `game_config.gd` | `config_parity.json` + 两端各 33/32 条断言 | 两端一致 |
| `server.yaml` | **人** | 全部 |

**这一节的价值不在架构，在诊断**：`server.yaml:11-14` 记录的「注释说谎」是一次**自我更正**——项目发现自己上一轮写在注释里的守卫承诺是假的，于是把承诺撤了、换成真实描述。这类更正在代码库里很少见，值得当成范本：宁可写「这里没人守」，也不要留一句让人以为有人守的话。

> 📖 [[第6章 搭建ECS框架|彭放第6章 §6.4]] 记录了原文遇到的正是这个问题（PyYAML 可用性），本项目「后来也因此走 header-only 配置」——教材与项目在这里是同一个约束的两次相遇，只是教材是环境限制，本项目是主动选择（零第三方依赖）。

**待办**（`server.yaml:24-29`）：给 test_smoke 加真正的交叉校验，用 dev.sh 已有的最小 YAML 子集解析读进这份 yaml 与 `sync::` 逐项比对；更彻底的是让 `tools/gen_protocol_hash.py` 在生成哈希前先校验三处副本一致，不一致就非零退出。

## 8 · 承重设计八：规格没给数时的取值判据（`kIdleTimeoutMs`）

`server_config.h:71-81` 是本模块唯一一处「规格没给数、我自己取」的判断题，它把判据整段留在注释里：

```cpp
/// **未 JoinRoom** 的连接的空闲回收（ms）。
/// ⚠️ 判断题：与 §10.3 的 5s（sync::kConnectionTimeoutMs）**不是同一件事**，本文件
///   刻意分成两条 timeout：
///     · 已入房的会话：5s 无任何包即判死（§10.3 明文，照抄）
///     · 还没入房的会话：给 300s（config/server.yaml 的 server.idle_timeout_s: 300）
```

理由写得很具体：

> 两处规格打架时选**不会踢掉正常玩家**的那条……一个加载慢 5 秒以上的客户端会在还没发 JoinRoom 之前就被踢掉 —— 而 §13.5 步骤 1「连上→JoinRoom→JoinAccept」里那个「连上」到「JoinRoom」之间**本来就没有心跳**。

**可复用的取值模板**（本项目规格缺口的通用填法）：① 判据写清楚（这里三条：入房前/入房后、有无心跳）；② 给出被排除方案与**它的具体受害者**；③ 给出拍板原则（「不会踢掉正常玩家」）。

对比 `server_config.h:57-61` 的 `kMaxSessions = 64`——同样是规格没给数（「§10.1 只写了符号」），但那里的注释只给了「16 个满房 × 4」和「若开满 32 间则会话上限会更紧」。**同样的缺口，两处注释质量不同**——这是 §11 说的漂义的另一面。

## 9 · 承重设计九：给双端留的锚点（出生点）

`server_config.h:103-114` 的判据第三条是整篇最「像工程」的一段：

> ③ **player_id=1 的那个逐值等于 otf-game 的 `Level01Map.SPAWN` (29,36)**。
> 　 这一条是给双端留的锚：K8 的客户端落地时，「单人模式出生点」与
> 　 「多人第 1 个玩家的出生点」必须是同一个像素，否则联调时第一条
> 　 「玩家站在哪儿」就会是两边不一致，而那时没人记得起这里做过约定。

**为什么这条值得写**：它防的不是当下的 bug（现在两端本来就一致），而是**未来某个开发者为了让单人/多人表现不同而去改一侧**。规格没明说「必须一致」，所以不写下来就等于默认「可以不一致」。

同一处的 `kSpawnTileCount` 单独具名，理由同样具体（`:119-123`）：

> 写 `idx >= config::kMaxPlayers` 会把「座位数」与「出生点数」两个概念**焊死** —— 哪天座位数改了（8 人）而出生点表忘了加，症状是 5~8 号玩家出生在 (0,0)，而 1~4 号一切正常。

⚠️ **注意这条与待拍板清单的关系**：「是否支持超过 4 人在线」是 `计划进度表.md` 附录 B 里**仍未拍板**的 #5 卡着服务端 M3 容量决策的那一条。拍板之后这里要改的是**三处**（`kMaxPlayers` / `kSpawnTileCount` / `kSpawnTiles` 表），而 `static_assert` 只保证第 2、3 处一致，**保证不了「表够长」**——那要靠 `kSpawnTiles` 数组长度本身。

**改动地图**：把 player_id=1 的出生点改成单人模式专用值 = 上面那条「没人记得起这里做过约定」的场景；给 `SpawnFor` 的越界判据写 `>= kMaxPlayers` = 8 人时 5~8 号出生在 (0,0)。

## 10 · 承重设计十：地图几何的权威在客户端，但编译期钉住

`server_config.h:83-98` 有一段容易看反的声明：

## 11 · ★ 本篇实测扫出的三处漂移（不是引文）

前 10 节全部是对既有设计的复述。**这一节是我这轮通读时扫出来的**，列在这里是因为它们恰好都是「注释/默认值与真值脱钩」，属于本模块的病。**三处已于 2026-10-14 全部修复**，并补上机器守卫。

### 11.0 处置结果（先看这里）

| 项 | 诊断 | 处置 |
|---|---|---|
| §11.1 `WorldConfig` 10 个死值 | 被 `MakeWorldConfig()` 全覆盖，看起来像真值 | **不删**（删了将来新增字段会静默未初始化 = UB）→ 改为在 `tests/test_config_parity.cpp` 加「默认值 == 真值」断言组（10 字段） |
| §11.2 `game_config.gd:215` 推导式过时 | 写 `boss_scale 1.5`，真值 3.0 | 已改为 `3.0 = 1260` |
| §11.3 `game_config.gd:84` 推导式过时 | 写 `玩家(220)`，真值 260 | 已改为 `≈ 玩家(260) 的 0.28`，并注明「220 那个值已不存在」 |
| 连带（见 [[05-Boss决策与仇恨领读]] §12）`AggroConfig` 3 个默认值 | 600/200/900 vs 真值 780/380/1200 | 已对齐真值 + 纳入同一组守卫 |

**新增的守卫是「第二个正交维度」**——原来 `test_config_parity` 只守「C++ 真值 vs GDScript 真值」（B1 那类**跨语言**分叉），新增的这组守「C++ 结构体默认值 vs C++ 真值」（服务器**自己内部**两个家）。后者此前一个断言都没有，而它正是 §11.1 这类问题的藏身处。

**反向验证过**：把 `AggroConfig::aggro_radius` 打回 600 → 精确命中一条
`AggroConfig：默认成员值 == MakeXxxConfig 真值（7 个字段）  aggro_radius(600 ≠ 780)`，其余 44 字段零误报。**绿灯不算验证，打坏能变红才算。**

⚠️ **`AnatomyConfig` 故意不纳入这组守卫**：它的默认值刻意是全 0 / 只有 Head，因为 sim 的纪律是「参数也是输入」（把真值写进默认成员 = 把参数注入偷偷藏进 sim）。**那边是刻意的，`AggroConfig` 这边不是**——两者看着同类，判据相反。别顺手「统一」。

### 11.1 `world_config.h` 的 9 个默认值全是死值

`world_config.h` 给 `hit_damage_cap` / `hit_rate_per_sec` / `hit_rate_burst` / `abuse_window_ticks` / `abuse_threshold` / `pose_history_ticks` / `snapshot_span_ticks` / `impact_hit_ms` / `impact_broken_ms` / `player_max_hp` 全都写了字面量默认值（`world_config.h:35-43` 等）。

但 `MakeWorldConfig()`（`game_config.h:234-257`）**把这 10 个字段全部覆盖了一遍**。而 `WorldConfig` 在全仓只有两个产地：

```
world.cpp:57                  World::World() : World(game::MakeWorldConfig()) {}
test_hit_report.cpp:117       WorldConfig c = otf::game::MakeWorldConfig();
```

**所以那些默认值永远不会被读到。** 危害不是「算错」而是**误导**：有人打开 `world_config.h` 看到 `int hit_damage_cap = 200;` 会合理地认为「这个数就是 200」，而真正的家在 `game_config.h:219`。这正是约束 1 要防的东西，只不过方向反了——不是渗透，是**分身**。

**为什么不删而加断言**（原打算删掉，实现时推翻了）：删掉这 10 个默认值之后，将来**新增一个字段**而忘了在 `MakeWorldConfig()` 里赋值，就从「误导」变成「静默未初始化读取」（UB，且比误导更难查）。所以正确做法是**留着 + 用断言钉住**——这与本篇 §3 的 `static_assert` 同款思路：**让两个家不可能不一致，而不是消灭其中一家**。

> 这是我在写这篇时得到的一条修正：**「消灭分身」听起来比「守住分身」干净，但只有后者是安全的**——因为新增字段时，消灭方案会让你忘了填，守住方案只会让你少写一行断言。

### 11.2 `game_config.gd:215` 的注释曾写着 `boss_scale 1.5`（已修）

```gdscript
##   为什么需要它：龙的精灵高 420px × boss_scale 1.5 = 630 世界像素，而屏幕在
```

而 `game_config.gd:82` 是 `var boss_scale: float = 3.0`。按 3.0 算应该是 1260 而非 630，**结论（相机权重不能大）不受影响，但算式已经不能复现**。

讽刺的是 `game_config.gd:82` 的行尾注释记得写「原 1.5」，而 §11.2 这处忘了。**同一份文件里两个关于 1.5 的注释，一个更新了一个没有。** 现已改为 `boss_scale 3.0 = 1260`。

### 11.3 `game_config.gd:84` 的注释曾写着「玩家(220)」（已修）

```gdscript
var boss_walk_speed: float = 73.0             ## 追击速度 = 玩家(220) 的 1/3
```

而 `game_config.gd:281` 是 `var player32_speed: float = 260.0`。73/260 ≈ 0.28，不是 1/3；`220` 这个值在本文件里已经不存在了。现已改为 `≈ 玩家(260) 的 0.28（73/260；注释曾写 220，那个值已不存在）`。

**三个漂移的共性**：它们都发生在「值改了、旁边的解释没跟着改」的位置——也就是本项目里**最容易改也最容易被顺手改坏**的地方。B1 是同一个位置的**极端版本**（值改了，两端只改了一边）。§11.1 是另一个极端（值根本没生效，但看起来像生效的）。

> **判据**（本轮得到的一条）：注释里的**推导式**比注释里的**结论**危险得多。结论过时了，读者还能靠数字自己发现；推导式过时了，读者会拿一个算错的式子去验证一个对的结论，然后以为自己发现了矛盾。
