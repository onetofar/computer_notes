## 0 · 从两个事故现象开场

一切从"服务器会怎么死"说起。下面两个现象都不是虚构，是 Linux 服务器真实的高频死法：

**现象 A：Ctrl-C 按了没反应，必须 `kill -9`。**
进程照常运行、毫无异常，但就是停不下来。事后查代码，编译零警告、运行零报错——凶手是编译器一次合法的优化（§2）。

**现象 B：毫无日志的猝死。**
进程不是崩溃（没有 core、没有异常栈、没有错误日志），是**当场蒸发**。事后从日志上几乎无从下手。凶手是一个信号：SIGPIPE（§7）。

`InstallSignalHandlers()` 这 38 行代码，就是对着这两类死法逐条设防的。三个信号、三种处置、三种角色：

| 信号 | 谁发的 | 处置 | 角色 |
|---|---|---|---|
| SIGINT | 用户按 Ctrl-C | 自定义处理器：只置标志 | 「请求退出」 |
| SIGTERM | `kill <pid>` / 容器编排停服务 | 同上（共用同一处理器） | 「请求退出」 |
| SIGPIPE | 本进程往已断开的 socket 写数据 | `SIG_IGN` 忽略 | 「写端已关闭」，不是退出请求 |

> 📖 结合 [[代码走读#1.2 \`InstallSignalHandlers()\`：先学会怎么死|09 §1.2]]：那里按代码顺序逐行讲；本文按「问题 → 机制 → 为什么这样解」讲，两篇可以互相跳着读。

## 1 · volatile 是「轻锁」吗——不是

一个常见误解：volatile 是某种"轻量级锁"。**它连一半的锁语义都没有**，它和锁根本不在一个维度上。

volatile 在 C/C++ 标准里只保证一件事：

> **编译器不许把这个变量的读写缓存到寄存器里，每次都必须真的访存。**

对照锁 / `std::atomic` 提供的保证，缺什么一目了然：

| 保证 | 锁 / atomic | volatile |
|---|---|---|
| 读-改-写原子性（`x++` 不被撕开） | ✅ | ❌ |
| 跨线程可见性（缓存一致性、跨核传播） | ✅ | ❌ |
| 内存序（禁止指令重排） | ✅ | ❌ |
| **禁止编译器把读操作提出循环** | ✅ | ✅ 仅此一条 |

（工程经验）这张表的价值不在"背"，在于**反向使用**：看到有人想用 volatile 解决并发问题，逐行对表——他要的到底是哪一行？如果他要的是前三行中的任何一行，volatile 都是错的。

## 2 · 为什么这里只要这一条就够——同线程执行模型

既然 volatile 这么弱，`g_running` 这个场景为什么它就够了？关键在于执行模型：**信号处理器和主循环跑在同一个线程上**。

信号不是另一个 CPU 核发来的数据流。它的机制是：内核**打断本线程**当前的指令流 → 跳去执行 `OnStopSignal` → 执行完跳回来，接着跑原来的代码。逐层检查并发三需求：

| 需求 | 这里存在吗 | 理由 |
|---|---|---|
| 跨核可见性 | **不存在** | 写发生在本线程两条指令之间，本核的寄存器、cache 天然一致 |
| 内存序 | **不需要** | `g_running` 不保护任何其他数据；退出后的收尾是单线程的 |
| 防编译器优化 | **唯一的需求** | 见下面的故障推演 |

故障推演（对应现象 A）：主循环唯一的检查点在 `while` 条件里——

```cpp
volatile std::sig_atomic_t g_running = 1;   // 信号处理器只许碰这个变量
extern "C" void OnStopSignal(int) { g_running = 0; }  // 处理器：一条赋值，无锁无分配

while (g_running != 0) {          // 唯一的检查点
  // ……循环体里没有任何代码写 g_running ……
}
```

没有 volatile 时，编译器看到"循环体内没人写 `g_running`"，就做**循环不变量外提**：读一次进寄存器，之后反复测寄存器，甚至直接把条件判定为常量。信号处理器再怎么改内存，寄存器里的旧值永远是 1——Ctrl-C 失效，进程只能 `kill -9`。

volatile 精确堵死这一条：每次判断都必须重新访存，处理器写下的 0 下一圈就能被看见。

### 2.1 术语辨析：「可见性」这个词在这里为什么危险

口语里说"volatile 让写入被主循环看见了"，听着像可见性——**但可见性在内存模型术语里专指跨线程/跨核**：一个核上的写入，另一个核上的读能否、何时看到。它分两层：

1. **编译器层**：值被缓存在寄存器里，根本不访存——volatile 管这层；
2. **硬件层**：store buffer、多核 cache、乱序执行——volatile **不管**这层。

把这两层混为一谈的实际危害：照着"volatile 提供可见性"的理解写双线程代码，会写出这种经典 bug：

```cpp
// 线程 A                          // 线程 B
data = compute();                  while (!ready) {}   // volatile 只保证这里真的访存
volatile bool ready = true;        use(data);          // ❌ 可能读到写了一半的 data
```

volatile 不禁止 `data` 写入与 `ready` 置位之间的重排（编译器和 CPU 都可能重排），线程 B 看到 `ready == true` 时 `data` 未必就绪。修法是 `std::atomic` + release/acquire 或互斥锁。（推演）这里场景与本项目无关，列出只为划清 volatile 的能力边界。

### 2.2 `sig_atomic_t` 管另一半

`volatile sig_atomic_t` 这对组合是 POSIX 认可的标准写法，两个限定词各管一半：

- **`sig_atomic_t`**：保证单次读写**不可被信号撕开**。信号可能在任意一条指令之间到达，普通类型的"读"或"写"若由多条指令实现（如 64 位值在 32 位环境），处理器恰好在中间改它就得到半新半旧的值。`sig_atomic_t` 是标准承诺"整值一体生效"的最小类型。
- **`volatile`**：保证循环里的读不被优化掉（§2）。

> ⚠️ 但注意它只保"单次读"或"单次写"，不保"读-改-写"：处理器里若写 `g_running--` 当计数用，读和写之间可以再被打断一次，丢更新。所以**处理器里只许置值，不许累加**——这也正是 main.cpp 43–46 行注释"信号只置标志位"的另一半理由。

## 3 · `&OnStopSignal` 是把方法当引用传吗——是函数指针

```cpp
sa.sa_handler = &OnStopSignal;   // 取函数地址，存进函数指针字段——不是 C++ 引用
```

`sa_handler` 字段的类型是 `void (*)(int)`——"接受一个 int、无返回值"的**函数指针**。`&OnStopSignal` 取的是这个函数在代码段里的入口地址，`sa` 里存的是"一个将来可以跳转过去的地址"。

它**不是** C++ 引用。引用的写法是 `void (&ref)(int) = OnStopSignal;`（别名，不能重绑、不能为空）；而 `sigaction` 是 C 结构体，字段只能是指针——引用是 C++ 语言设施，塞不进 C ABI 的结构体传给内核。

两个顺带事实：

- **`&` 可以省**：函数名会自动退化成函数指针（和数组名退化同理），`sa.sa_handler = OnStopSignal;` 编译结果完全相同。写 `&` 是风格选择，让"这里在传指针"在字面上可见。可调用对象族谱（函数指针、`std::function`、成员函数指针的差别）见 📖 [[A cpp第三部分_类设计者的工具#14.8.8 function 类模板|C++ Primer §14.8.8]]。
- **这是注册回调，不是调用**：这行的全部工作是登记地址，真正调用发生在未来某个不确定时刻——由内核在信号送达时发起，而且发起上下文特殊：随时打断主循环任意一条指令、同线程异步跳入。§2 的全部约束都从这个"随时、异步"来。

## 4 · `sigemptyset(&sa.sa_mask)`：给「嵌套打断」留的防线

处理器本身是异步打断进来的，于是有新风险：**处理器执行到一半，又来一个信号，把处理器再打断一次**（信号嵌套）。`sa_mask` 是内核提供的防线：

> 执行处理器期间，把 `sa_mask` 集合里列的信号**临时屏蔽**（挂起不丢），处理器返回后自动解除、再补发。

`sigset_t` 是信号集合（位图）。`sigemptyset` 把它清空——"除默认规则外，我不额外屏蔽任何信号"。默认规则有两条：

1. **本级信号自动屏蔽**：就算掩码为空，SIGINT 的处理器执行期间，内核也自动挡住再次到来的 SIGINT（否则 Ctrl-C 连按两下就是重入）。这条不用你做。
2. **别的信号不挡**：SIGINT 处理到一半来了 SIGTERM，会立刻嵌套进入 SIGTERM 的处理器。想挡就得显式 `sigaddset(&sa.sa_mask, SIGTERM);`。

**这里为什么可以留空**：看处理器的全部动作——`g_running = 0`，一条赋值、无状态、无锁、无分配，**天然可重入**。被 SIGTERM 嵌套打断的后果只是 `g_running` 被再写一次 0，幂等，什么都不坏。留空是经过论证的省略，不是偷懒。

> ⚠️ **易漏点**：`struct sigaction sa` 在此之前被 `memset` 全零，删掉 `sigemptyset` 看起来"结果一样"——但那是**碰巧**：清零是 memset 的功劳。`sigset_t` 必须经 `sigemptyset`/`sigaddset` 初始化是 POSIX 的正式要求（它不承诺零位图等于空集，Linux 上恰好等于）。哪天结构体没被 memset，漏了这行就会拿一块垃圾位图去屏蔽随机信号集。（工程经验）"删掉也一样"的代码分两种：冗余的和**防回归的**——区分标准是删掉后，防护是否依赖上游一个不显眼的巧合。

## 5 · `sa_flags = 0`：SA_RESTART 会让标志位永远轮不到被检查

信号会打断**阻塞中的系统调用**。主循环大部分时间睡在 `epoll_wait` 里，Ctrl-C 到来时内核跳去执行处理器（置 `g_running = 0`），然后面临选择——被打断的 `epoll_wait` 怎么办：

| 选择 | 行为 | 后果 |
|---|---|---|
| 设 `SA_RESTART` | 内核**自动重启**该系统调用，程序无感 | 处理器跑完了、标志已置 0，但主循环**继续睡在 epoll_wait 里**，根本没机会回到 `while` 条件去检查它。服务器空闲时 Ctrl-C 就像没按 |
| `sa_flags = 0`（本项目） | 系统调用返回 `-1`，`errno == EINTR`（"被信号打断"） | `Poll` 返回 → 本轮跑完 → 回到 `while (g_running != 0)` → 立刻开始优雅退出 |

一句话：**SA_RESTART 会让"置标志"这个动作永远轮不到被检查**，因为检查点在系统调用返回之后。这也是 `signal()` 在 glibc 下默认带 `SA_RESTART`、而本项目改用 `sigaction` 显式清零的原因——工具的默认值要能被看见、被推翻。

（本项目规格）补充一个诚实的注脚：就算设了 SA_RESTART，本项目 `Poll` 的超时上限是 50ms（一个 tick 周期），退出最多再等 50ms——所以这是"语义要明确"的选择，不是"不选就坏"的选择。

## 6 · 失败分支：启动期 fail-fast

```cpp
if (::sigaction(SIGINT, &sa, nullptr) != 0 ||      // :: 前缀 = 全局命名空间，防同名遮蔽
    ::sigaction(SIGTERM, &sa, nullptr) != 0) {     // 同一份 sa 装给两个「请求退出」信号
  throw std::runtime_error(std::string("sigaction 失败: ") + std::strerror(errno));
}
```

`::sigaction` 成功返回 0，失败返回 -1 并设 `errno`（`strerror` 把数字翻译成人话）。三个参数：信号号、配好的规格、旧规格的输出位置（`nullptr` = 不关心）。

**为什么 throw 而不是打日志继续跑**：信号处理没装上的服务器是一个**无法被文明关停**的服务器——Ctrl-C 和 kill 都触发默认动作（立即死亡），进行中的收尾（刷日志、关连接）全部没有。缺陷在启动那一刻已注定，越晚暴露越难查，所以能在第一行拦住就拦住。抛出的异常被 `main()` 的 catch 接住，打"启动失败"、退出码 1——失败也走正门。（工程经验）启动期 fail-fast 的分档标准：坏了之后是**硬故障**（无法优雅退出）就抛，是**可降级劣化**才 warn 继续——同一函数里 SIGPIPE 那次 sigaction 没检查返回值（§7），就是这个标准的另一面。

## 7 · SIGPIPE：把「处决」降级成「一次普通写失败」

TCP 对端断开（发过 RST）之后，本进程再往这个 socket `write()`，内核向**本进程**投递 SIGPIPE，**默认动作是终止进程**。这对命令行工具 `prog | head` 合理（读端没了，写端该死），对长期存活的游戏服务器是灾难：

```
玩家 A 断线（TCP 侧 RST）
  → 服务器下一拍广播快照，write() 到 A 的 fd
    → 内核投递 SIGPIPE → 默认动作：整个服务器进程当场死亡
      → 其他三个玩家跟着掉线；且毫无日志（现象 B）
```

修法的思路不是"捕获再处理"，而是**釜底抽薪**：

```cpp
ign.sa_handler = SIG_IGN;   // SIG_IGN = 「忽略此信号」的预定义哨兵（不是函数地址）
```

忽略之后，内核不再处决进程，而是让肇事者自己尝到后果：`write()` 返回 `-1`、`errno == EPIPE`。于是断线从"信号处决进程"降级成"一次普通的写失败"——`TcpTransport::FlushWrite` 本来就有错误分支，拿到 EPIPE 走 `Close()` 正常回收。**一个玩家的断线，从能打死整个服务器，变成只影响他自己。**

两个对照：

- **另一条修法**：`send(fd, buf, len, MSG_NOSIGNAL)` 在单次调用级抑制 SIGPIPE。本项目 `FlushWrite` 用裸 `::write()`（无此 flag），所以走全局忽略这条路。
- **返回值为何不检查**：三个参数都是编译期常量、不涉运行期状态，实际不会失败；失败的最坏后果是退回"默认杀进程"的历史行为，与不写这几行等同，不会造成新损坏。（本项目规格）与 §6 的 throw 分档相对照：同一函数里两次 sigaction，一次抛一次不查——差别不是随意，是"坏了是否硬故障"。

## 8 · 汇总：这段代码教的信号设计四原则

| 原则 | 落点 | 一句话 |
|---|---|---|
| **处理器最小化** | 只置 `g_running`，不写日志/不加锁/不分配 | 处理器在任意指令间异步执行，任何"顺手做的事"都可能在不安全点执行（日志非 async-signal-safe） |
| **值语义选对** | `volatile sig_atomic_t` | volatile 防优化（每次真访存），`sig_atomic_t` 防撕裂（整值生效）——各管一半，缺一不可 |
| **别让默认值替你决定** | `sigaction` 替 `signal()`、`sa_flags = 0` | glibc 默认 SA_RESTART 会让标志位永远轮不到被检查；工具默认要能被看见、被推翻 |
| **让错误降级为数据** | SIGPIPE → `SIG_IGN` → `write` 返回 EPIPE | "信号处决进程"和"一次普通写失败"之间，隔着一句 `SIG_IGN` |

> 📖 结合 [[00-项目领读#L2 · 三个闭环|00-项目领读 L2]]：信号机制服务的是"连接闭环"的**收尾侧**——进程怎么死和怎么活一样重要，因为 gdb / valgrind / strace 的使用者都需要"进程是走到收尾的，不是被打死的"这个凭据（main.cpp:180–182 的收尾行就是为此而写）。
