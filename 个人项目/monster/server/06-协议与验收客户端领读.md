## 1 · 承重设计一：五条铁律，第一条是「禁止 memcpy」

`protocol.h:4-11`：

```cpp
// ★ 铁律（§8.1，违反 = 评审打回）：
//   1. 小端、定长字段、**无隐式 padding**，逐字段显式序列化。
//      禁止把结构体 memcpy 上线 —— 编译器插 padding 后两端内存布局不同，
//      表现是「本机好好的、连上去就乱码」。
//   2. 位置 = i32 整数像素（世界坐标系）。
//   3. 血量 = u16 归一化（改数值平衡不改协议、不因浮点导致两端血条不一致）。
//   4. 变长字段前置 u8 长度。
//   5. 输入方向 move_dir = 两个 i16，值域 [-1000, 1000]。
```

**第 1 条的理由值得单独理解**：「两端内存布局不同」不只是理论——不同的编译器版本、优化等级、目标架构会插入不同的 padding。`kPlayerNetSize = 14`（`protocol.h:139`）按结构体算，如果编译器在 `id:u8` 后面插 3 字节对齐，实际就是 17 而不是 14。**memcpy 上线的话，同一份代码在不同机器上编出来的包长度都不一样。**

**第 3 条（血量归一化）是本项目最省事的一个决策**：`NormalizeHp(int hp, int max_hp)` = `round(hp / max_hp * 65535)`（`snapshot.h:72`）。所以：

- 改 `boss_core_hp` 6000 → 8000 **不改协议**（两端各自用本地 `max_hp` 反归一化，见 `snapshot.h:75`）；
- 没有浮点，所以两端血条不会因为浮点误差不一致；
- u16 精度对血条足够（65535 级）。

⚠️ 归一化放在 **proto 层而不是 world 层**，理由写明（`snapshot.h:74-75`）：「它是**协议规则**不是玩法规则 —— 两端必须用同一个式子」。这与 [[04-配置与参数领读|04]] §6 的判据同源。

**改动地图**：改铁律 3 = 平衡数值变成协议变更（要重算哈希、要两端同改）；在 world 层做归一化 = 两个地方各猜一次公式。

## 2 · 承重设计二：`protocol.h` 零函数，编解码单独一层

`msg_codec.h:4-8`：

> ★ 为什么单独一个 msg_codec 而不是塞进 protocol.h：
> 　protocol.h 是**常量与枚举**的唯一权威（§8.1/§8.2/§8.4），**它不含任何函数**。
> 　本文件是那些常量的**逐字段实现**，仍然受 §8.1 铁律 1 约束。

这个切分有个直接后果：**`protocol.h` 里出现的每个 `constexpr` 都会被哈希生成器扫到**（见 §4、§5）。所以它必须保持「纯声明」，任何「顺手加个辅助常量」都会改变协议——这也是为什么 §5 那条设计那么反直觉。

### 覆盖面是刻意的（`msg_codec.h:9-15`）

> ★ 覆盖面是刻意的：只做协议里实际用到的那些条。**上行**三条（JoinRoom / PlayerInput / PlayerState / HitReport）只解码不编码 —— 服务器不产生它们；下行四条只编码。

⚠️ 注意这里有个**文字与枚举的不一致**：注释说「上行**三条**」，但后面列了**四个**（JoinRoom / PlayerInput / PlayerState / HitReport）。按 `MsgId` 枚举，上行是 5 条（含 Heartbeat 双向）。这是 2026 年 10 月加 `HitReport` 回退字段时漏改的数字。

### 长度判据必须在解的地方判

> 解码器与处理方**分属两层**（session 层解、world 层用），但「这条消息长度对不对」必须在解的地方判：把长度判据散落到使用方是典型的参数渗透（protocol.h 里 wire:: 那些常量的存在意义就是「编解码前自检」），而漏判的症状是「偶发乱码」，极难定位。

**这就是 `namespace wire`（`protocol.h:113-145`）存在的唯一理由**：它们不是「文档里的数字」，是**每个解码器开头都要比对的那个数**。删掉 wire:: 常量、解码器改用字面量，代码照跑、包照发，而少一个断言就是「偶发乱码」。

## 3 · 承重设计三：枚举永不复用永不重排，`BossState` 是活样本

`protocol.h:13-14`：

> ★ 枚举值**永不复用、永不重排，新增只能追加**（§8.2）。
> 　 改任何一个已发线上的值 = 协议版本断裂，等价于换了一种握手。

`BossState` 记录了一次真实的追加（`protocol.h:73-77`）：

```cpp
enum class BossState : std::uint8_t {
  Idle = 0, Chase = 1, Charge = 2, Attack = 3, Recovery = 4, Dead = 5,
  // ★ 2026-10-08 追加（§8.2「值显式编号，永不复用、永不重排；新增只能追加」）：
  //   0-5 是初版六态，**一个都不动**。两个新值只在尾部续号。
  Breath = 6,    ///< 吐息持续中（每 tick 跑锥形判定）
  ChargeUp = 7,  ///< 冲撞蓄力/后退
};
```

**「追加枚举成员会改协议哈希」这件事很容易被忘**——`protocol.h:235-237` 记着它的后果：

```cpp
// ★ 2026-10-08：追加 BossState 6/7（Breath / ChargeUp）后 0x459ef37e → 0x095d7e02。
//   枚举成员**也**进哈希（不是只有帧格式），所以加两个 BossState 就得改这一行。
inline constexpr std::uint32_t kProtocolHash = 157122050;  // 0x095d7e02
```

这条与 [[05-Boss决策与仇恨领读|05]] §6 的攻击轮转是**同一天做的两件事**：为了让 Boss 会吐息，协议里加了两个枚举值，于是哈希变了，于是客户端必须同步。**协议的成本不只在字段，还在枚举。**

**改动地图**：复用 `Dead=5` 给 `Breath` = 老客户端把吐息读成死亡；重排枚举 = 同上；追加成员但忘改哈希 = 全员被 `Rejected{1}` 拒（这是**好**的失败，见 §4）。

## 4 · 承重设计四：哈希的覆盖范围，以及它的反面

`protocol.h:218-234` 定义了哈希：§8.1-§8.3 的「帧格式 + 枚举值 + 消息号 + 字段表 + 同步参数」，SHA-256 取前 32 位。

### 「宁可空着也不能写个假的」

`protocol.h:221-223` 记着这个决定的由来：

> ★ **K8 填真值**（2026-10-07）。此前 M1/K4 两轮刻意留 0 —— 填一个随手编的常数会让「两端哈希一致」变成自欺欺真：两边都写 1234，握手必然通过，而这个校验本来是要抓「双端协议不同步」的。**宁可空着也不能写个假的。**

**这是全项目最值得学的一条关于「守卫」的态度**：当守卫所需的真值还不存在时，**正确的做法是让守卫失效并说清楚，而不是让守卫看起来在工作**。哈希留 0 的那两轮里，握手校验确实形同虚设——但它是**诚实的虚设**（代码注释明写），而不是「看起来在」（`session_mgr.cpp:31-35` 记的正是那个反面案例，见 §12）。

### 哈希的失败模式是「明确拒绝」而不是「怪异故障」

`protocol.h:231-234`：

> ⚠️ 改本文件里**任何一个参与哈希的常量**（帧格式 / 枚举 / 消息号 / 字段表 / namespace sync 下的同步参数）→ 哈希变 → 必须同步改 protocol.gd，否则**所有客户端握手被 Rejected{1} 拒掉**。这是 §8.4 要的行为：**一次明确的拒绝，胜过全服联机时的怪异故障**。

### 反面：三个网络层上限**刻意不算**

`protocol.h:171-180` 是本篇最有价值的一段判据：

> ★ 这三个**不是协议的一部分**，是本进程的资源上限，所以 `tools/gen_protocol_hash.py` 刻意**不把它们算进哈希**……§8.4 列的覆盖范围是「帧格式 + 枚举值 + 消息号 + 字段表 + 同步参数」，里面没有「服务器能开多少连接」。如果把它们算进去：
> 　客户端根本无从知道这两个数（也不该知道），改一个服务器部署参数就会让所有客户端握手失败 —— 那是误报，不是抓到了协议不同步。

被排除的三个是 `kMaxFd` / `kFrameQueueDepth` / `kSendBufCap`（`protocol.h:206-216`）。

**这条与 [[04-配置与参数领读|04]] §6 是同一条判据的两个实例**（是否需要两端一致才能通信 → 决定它进不进哈希），区别在于**网络层上限连「两端同值」都不要求**——它们是纯服务端资源。

⚠️ **排除带来的真实危险已经发生过**（`net/frame_codec.h:49-57`）：

> ★ 默认深度**必须引 kFrameQueueDepth**，不许写字面量（评审 P0-4）。
> 　曾经这里写的是 `= 64`……两个家，改一边就静默分叉，哈希还查不出来（kFrameQueueDepth 在 gen_protocol_hash.py 的 NOT_HASHED 里）。**实测把它改成 8 或 256，全套 8 个测试仍然全绿** —— 因为「守 64」的是 test_smoke 里那一条，两个值之间没有任何联系。

「哈希查不出来」四个字，是排除机制的**全部代价**——它换来的是部署参数自由，代价是这一类分叉必须靠别的机制防。

**改动地图**：把 `kFrameQueueDepth` 算进哈希 = 改一个服务器队列深度就要重算协议并让客户端升级；反向——在 NOT_HASHED 项上留字面量副本 = 回到 §12 那种「静默恒真」。

## 5 · 承重设计五：「编译期检查一律不落具名常量」

这是全仓**最反直觉的一条设计决策**，而它有一份完整的失败史。`protocol.h:195-205`：

```cpp
// ★ 为什么这条检查只能写成 static_assert 表达式、**不能再落一个具名 constexpr**：
//   tools/gen_protocol_hash.py 扫本文件里的**每一个** constexpr（不限命名空间），
//   只按「是否在 NOT_HASHED 表里」豁免，且键是全限定名。曾在这里写过
//   `constexpr std::size_t kMaxFdIsCompileTimeConstant = kMaxFd;` 来做 constness
//   检查 —— 后果是它被**收进协议哈希的输入集合**，而它的值 kMaxFd 是引用、
//   不是十进制整数字面量，生成器按 fail-closed 规则直接 ParseError 崩掉
//   （连累 --selftest 全红）。把它改写成一个字面量更糟：那是往协议里塞一个
//   本不属于协议的常量，客户端哈希跟着变、两端都要跟着填值……
//   结论：**编译期检查一律不落具名常量。**
```

**因果链值得逐段读**：

1. 想给「kMaxFd 是 constexpr」加一条检查；
2. 写成具名 constexpr → **它进了协议哈希**（生成器扫每一个 constexpr）；
3. 生成器 fail-closed（只认十进制整数字面量）→ **构建崩**；
4. 改写成字面量 → 更糟（往协议里塞了不该有的常量，两端都要填值）；
5. 结论：编译期检查只能写成 `static_assert` **表达式**——因为表达式不会被生成器扫。

### 而 `static_assert` 恰好有它该有的力度

`protocol.h:184-194` 解释了为什么不是普通的运行期断言：

> ⚠️ 「它是常量」这条必须**在编译期**钉住，不要写成运行期断言（评审 P0-6）：test_smoke 里曾有一条 `check_eq(kMaxFd, 1024 - 1024 + 1024, ...)`，**编译期折叠成 1024**，是同文件另一条断言的重复，**删掉 constexpr 也照样绿**。
> 　下面这条 static_assert 才有它该有的力度：static_assert 的条件**必须是常量表达式**，所以删掉 kMaxFd 的 constexpr（变成运行期可变的 inline 变量）会**编译失败**。这才是 constness 的等价判据 —— **判据本身同时也是一条真实的规格检查**（fd 表必须装得进 nofile 上限）。

**「判据本身同时也是一条真实的规格检查」这句是全篇最值得抄走的一句**。它解释了为什么该做法比「再加一个测试」好：写 `check_eq(kMaxFd, 655350, "...")` 只能验证一个数；写成 `static_assert(kMaxFd <= 655350, ...)` 同时验证了「它是常量」**和**「它装得进 nofile 上限」。

**改法本身也有一个反直觉的坑**（`protocol.h:192-194`）：

> ⚠️ 别用 `std::is_constant_evaluated(kMaxFd)` —— 它**不接受参数**，那是用来问「我现在是否处于常量求值上下文」的探针，不是问变量的 constness；实测那样写直接 `error: too many arguments to function is_constant_evaluated()`。

> 📖 [[第10章 安全性|格雷泽第10章 §10.2]]：验证的前提是**验证本身无法被绕过**。这里的三层是：constness 检查会被绕过（P0-6）→ 字面量常量检查会崩生成器 → `static_assert` 是唯一同时躲过两者的形状。

## 6 · 承重设计六：`98B` 拆开钉死，因为和式单钉会隐形

`protocol.h:131-144`：

```cpp
// ★ 为什么它们必须与 kWorldSnapshotPayloadMax4 分开钉死：
//   98 是个**和式**（BossNet + PlayerNet×4 + 固定头），单钉它一个数，
//   「BossNet 从 33 长到 40、忘了回头改 98」这类改动会**完全隐形** ——
//   快照实际宽度变了而带宽/单包论证引用的 98 没变，§7.3 条件 1 跟着失效。
//   拆开钉死之后这条恒等式是可测的（test_smoke 第 6 组断言）。
inline constexpr std::size_t kPartNetSize = 4;     // PartNet  : type:u8, state:u8, hp:u16
inline constexpr std::size_t kPlayerNetSize = 14;  // PlayerNet: id:u8, x:i32, y:i32, facing/action/form:u8×3, hp:u16
inline constexpr std::size_t kBossNetSize = 33;    // BossNet : ... parts:PartNet×5(=kPartNetSize*5)
inline constexpr std::size_t kSnapshotFixedBytes = 9;
```

**这是「恒等式分解」的经典应用**：`98 == 9 + 33 + 14×4`。只钉 98，任何一项变化都不会触发任何检查；把三项分别钉死，就可以断言这个恒等式本身。

**同一手法在这个文件里出现了三次**，值得当成一种习惯：

| 对象 | 恒等式 |
|---|---|
| 快照宽度 | `kSnapshotFixedBytes(9) + kBossNetSize(33) + kPlayerNetSize(14)×4 == kWorldSnapshotPayloadMax4(98)` |
| BossNet | `kBossNetSize(33) == 固定头 + kPartNetSize(4)×kBodyPartCount(5)` |
| 部位序 | `BodyPartType` 的 5 个值 与 `boss_anatomy.gd` 的 `BOSS_PARTS` **同序**（`protocol.h:53-54`） |

⚠️ 第三条**没有机器守卫**：它靠两处枚举/字典手写同序，而 [[05-Boss决策与仇恨领读|05]] §9 讲的那个「同序是跨文件隐式契约」是同一个坑。

## 7 · 承重设计七：视图层让「归一化了吗」只有一个产地

`snapshot.h:4-9`：

> ★ 为什么单独一个头文件，而不是把结构体直接塞进 msg_codec.h：
> 　`msg_codec.h` 是**编码器**（输入是 payload 字节、输出是向量），本文件是**被编码的世界状态**。world 层（世界状态）与 proto 层（线上字节）之间只通过这四个视图结构交接 —— 于是「世界状态」与「线上字节」的对应关系有且只有 FillSnapshot 一个产地（world/world.cpp），不会散落成「这个字段归一化了吗」在两个地方各猜一次。

**视图里只有标量与定长数组**（`snapshot.h:11`），玩家数组是变长的例外，因为玩家数按 §8.3 变化。

### 快照宽度随玩家数变化，不能拿 4 人的值断言

`msg_codec.h:118-122`：

> ⚠️ 宽度随玩家数变化（满房 4 人 = 98B，单人 = 42B），所以**不能**拿 kWorldSnapshotPayloadMax4 直接断言。满房宽度由 test_smoke 的恒等式守，这里加一条运行期兜底：编完超 kMaxPayloadSize 就**当场拒绝编码**（调用方随后不发）—— 发超长帧会在对端触发断连，症状极难定位。

「当场拒绝编码」而不是「截断」：截断会产出一个**看起来合法但内容错**的包，拒绝编码则让调用方什么都不知道——**但它知道**（返回时包是空的）。

### 快照里没有相机字段，而且有守卫

`snapshot.h:53-55`：

> ⚠️ **这里没有任何相机字段**（§8.5 显式警告）：相机纯客户端，塞进快照只会浪费带宽并制造一致性问题。谁往这里加相机字段，test_smoke 的宽度恒等式会先红（多了字节 → 98B 对不上）。

**这条是 §6 那个恒等式分解的直接收益**：正因为 98 被拆成 9+33+14×4 且可断言，加一个字段会立刻让恒等式不成立。「不要加相机」这条规矩**不是靠自觉守住的**。

## 8 · 承重设计八：短 payload 报 FAIL，绝不 abort

`msg_codec.h:17-21`：

> ⚠️ 全部函数对**短 payload 一律返回 kMalformed，绝不 abort**：
> 　ByteReader 的越界是 abort()（程序员错误路径，见 byte_codec.h），而这里的输入是**网络来的字节** —— 那不是程序员错误，是「对端还没实现」或「对端发了垃圾」，必须报 FAIL，**不能把整个进程 SIGABRT 掉**。
> 　这一条与 cli_client.cpp 里的处理是同一条纪律，两边都别改。

**这是「同一份代码里的两条错误路径必须区别对待」的典型**：

| 输入来源 | 越界时 | 因为 |
|---|---|---|
| `ByteReader`（程序员直接喂字节） | `abort()` | 程序员 bug，该炸 |
| `msg_codec`（网络来的字节） | 返回 `kMalformed` | 对端的 bug/攻击，不该把服务器带走 |

**把这两者混同的后果是拒绝服务**：一个发半包的攻击就能让服务器 abort。这与 [[03-世界与命中领读|03]] §6「滥用闸」是同一个威胁模型——但这条更靠前，它在**解码层**就把最粗的攻击挡住了。

### 同款处置：越界输入**拒绝**而不是**夹取**

`msg_codec.h:76-78`：

> ⚠️ move_dir 的值域是 `[-1000, 1000]`（§8.1 铁律 5 的定点 0.001）。越界**判为 malformed** 而不是夹取：**夹取会让一个发超界的客户端静默地以 1.0 倍速移动，而拒绝让它在第一包输入就暴露**（症状可见，不是"手感怪"）。

**「夹取 vs 拒绝」的判据就是「症状可见性」**：夹取产生的是「手感怪」这种最难查的症状，拒绝产生的是「第一包就被拒」这种最容易查的症状。与 [[03-世界与命中领读|03]] §6「分档的判据是错误性质」同源。

### 昵称长度：这里反而是截断

`msg_codec.h:59-60`：

> ★ 昵称超长**截断**到 255 而不报错：长度前缀只有 u8 一格可写，与 cli_client 的 MakeJoinRoom 同一处置（那边也有注释）。

**为什么昵称截断而 move_dir 拒绝**：因为超长昵称的失败模式是「名字被截短了」（无害且可见），而超界 move_dir 的失败模式是「以错误速度移动」（不可见）。**同样是输入校验，处置相反，判据是失败模式的可接受度。**

## 9 · 承重设计九：`cli_client` 为什么不是 ctest，为什么用裸 socket

`cli_client.cpp:1-12` 的文件头把两件事的理由都写死了：

> ★ 为什么它不是 ctest：它是**验收工具**不是单元测试。
> 　 §13.5 原话："如果命令行客户端不能独立演示服务器行为，这个项目就退化成'一个 Godot 游戏顺便带个服务器'，**展示价值归零**。"说的是**演示**，不是回归测试。把它 `add_test()` 进 ctest 会让整套回归在「没起服务器」时变红 —— **那是把验收工具的失败冒充代码回归。**

> ★ 为什么用裸 socket（socket/connect/poll/read）而不复用 TcpTransport：
> 　TcpTransport 是**服务端** LT epoll Reactor（bind + listen + accept），它没有 connect 路径 —— 拿它当客户端连过去必然失败。验收工具要的是"像一个外部客户端那样连进来"，所以必须是独立客户端。

**第二条是「独立性换可演示性」**：`cli_client` 自己实现了一套 `ByteWriter` / `EncodeFrame` 的调用（`:75-92` 的 `MakeJoinRoom`），**而不是调用 `msg_codec`**。这意味着它验证的是**线格式本身**，而不是「我的编码器和解码器自洽」。如果它复用 `msg_codec`，那么编码器的 bug 会被解码器的同一个 bug 掩盖。

⚠️ 这是**有意的重复实现**，与 [[架构评审-熵减-2026-10]] 里「重复实现该不该合并」的判断相反——**验收工具与被验收对象的重复是必要的**，因为验收的意义就是独立实现。

### 诚实性铁律

`cli_client.cpp:35-36`：

> ★★ **诚实性铁律**：本工具**如实**报非 0 退出码。把失败路径改成"通过"正是 §13.5 要防住的事 —— **一个永远返回成功的验收工具比没有验收工具更糟**。

代码里 `g_fail` / `ok()` / `bad()`（`:63-66`）就是这条的实现。`--wrong-hash` 存在本身就是为了**证明这个工具会红**（§13.5 步骤 4）。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.1]]：三层分叉解决「同一份代码两端要的东西不同」。`cli_client` 是它的第四种形态——**「同一份协议两端要的东西不同」**，所以它有第三套常量来源（手写 `ByteWriter` 调用）。

## 10 · 承重设计十：`--fight` 为什么值得单独一整套编排

`cli_client.cpp:19-25`：

> ★★ **--fight 为什么值得单独一整套编排**，而不是「在 --demo 上加几行发包」：
> 　步骤 3 要证明的是「**服务器裁决说了算**」，而客户端判定命中是自己的事。
> 　于是脚本必须自己绕着 Boss 站到**该部位暴露的那一面**去打 —— 暴露表（§8.3）决定了尾/翼/腿各自要站到哪个方向，**站在错的一面上打，服务器会正确地把命中丢掉**，于是「打不中」看起来像是服务器坏了。
> 　编排顺序（先绕下方 → 再绕上方 → 打下方 → 打上方 → 打右 → 打左）就是照着那张表写的。

**这段解释了一个验收工具的编排为什么不是随意的**：它必须**按暴露表站到正确的面**，否则服务器「正确地拒绝」与「服务器坏了」在输出里长得一样。`IsExposed(part, facing)`（`:233`）就是这张表在客户端侧的镜像——**又是一处有意的重复实现**（真值在 `game_config.h:83-93` 的 `MakeAnatomyConfig`）。

**编排顺序本身是验收的一部分**：它证明的是「五个部位各自有各自的暴露条件」，而不只是「能打中」。

### §13.5 步骤 2 为什么需要自动走位

`cli_client.cpp:27-33` 是个**把验收条件算出来**的例子：

> ★★ 步骤 2 为什么需要**自动走位**：出生点 (2784,3456) 距 Boss 出生点 (2688,960) 是 **2497px**，而 aggro_radius 是 780 —— **一个站着不动的玩家永远不会进 Boss 的感知圈**，于是「Boss state 在 Idle↔Chase 之间变化」这条验收**在任何时长下都不成立**。

而且走位目标是**从快照里学的**，不是写死的常量——这让它同时成为 §6.5.4 `PlayerSim` 的端到端演示（收输入、位置由服务器按 tick 积分回来）。

⚠️ `cli_client.cpp:1161` 写的是「出生点距 Boss 2497px」，而 [[04-配置与参数领读|04]] §9 说出生点是 `(29,36)` 瓦片 → 世界像素 `(2784, 3456)`。**两者一致**（29×96=2784，36×96=3456），Boss 是 `(28,10)` → `(2688, 960)`。差值 `sqrt(96² + 2496²) ≈ 2497` ✓。这条自洽性是好的。

## 11 · 本模块缺什么：协议里没有「裁决回执」

11 个 `MsgId`（`protocol.h:30-42`）：上行 `JoinRoom / PlayerInput / PlayerState / HitReport` + 双向 `Heartbeat`；下行 `JoinAccept / Rejected / PlayerJoined / PlayerLeft / WorldSnapshot / BossEvent`。

**观察这 11 条能承载什么**：

| 需要的能力 | 现有消息 | 状态 |
|---|---|---|
| Boss 攻击命中玩家 | `S2C_BossEvent{PlayerHit}` | ✅ 有（`:108`） |

| 库存 | — | ❌ 无 |

**`S2C_BossEvent` 的 payload 复用是这套协议当前的承重极限**（`protocol.h:108`）：

> EventType::PlayerHit 的 payload 复用：part 字段改填 player_id，extra 填伤害值。

**一个字段装两种语义**是能省事，但它有边界：加第三种语义（比如库存变更）时，字段名就必须改成 `part_or_player`（`snapshot.h:66` 已经改过一次了），而**语义分支藏在发送方**。

## 12 · ★ 本篇实测：两处注释仍在描述弱化后的哈希校验

### 12.1 现状：`HashMatches` 是严格比对，代码是对的

`session/session_mgr.cpp:36`：

```cpp
bool HashMatches(std::uint32_t client_hash) { return client_hash == kProtocolHash; }
```

`kProtocolHash = 157122050`（`protocol.h:237`，2026-10-07 填的真值）。`main.cpp:224-232` 启动时会把它打进日志，注释明写理由：「**不能让人以为握手校验没生效**——从 0 变成真值之后，服务器每次 JoinRoom 都在拿它与客户端比对」。

`cli_client.cpp:1182` 发的也是真值（`std::uint32_t hash = kProtocolHash;`），不是 0。

**所以：哈希校验现在是满强度的。**

### 12.2 但两处注释说的还是旧的弱化形态

`session_mgr.cpp:25-29`：

> ⚠️ kProtocolHash 现在**仍是 0**（§8.4「宁可空着也不能写个假的」），所以这条校验当前的实际形态是「只拒非 0 的哈希」——客户端（cli_client 默认）发 0 → 通过；--wrong-hash 发 0xDEADBEEF → 拒。

`cli_client.cpp:1165-1168`（**`--help` 的用户可见输出**）：

> ★ kProtocolHash 仍是 0（§8.4：真值由 tools/gen_protocol_hash.py 生成，K8 双端就位时才填进去……）。所以哈希校验当前的实际形态是「只拒非 0 的哈希」：本工具默认发 0 → 通过，--wrong-hash 发 0xDEADBEEF → 拒。

**两处都与 `protocol.h:221-225` 和 `main.cpp:224-232` 直接矛盾。**

### 12.3 为什么这条比一般的注释漂移更值得修

1. **它在一处是用户可见输出**。任何人跑 `--help` 都会读到「哈希校验当前的实际形态是只拒非 0」——**而这是假的**。一个正在评估这个项目的人会据此低估握手校验的强度。
2. **它描述的是「守卫看起来在工作但实际不工作」的形态**，正是 `session_mgr.cpp:31-35` 自己警告的那种：

   > ⚠️ 客户端哈希来自网络，**不是**编译期常量：写成 `client_hash == kProtocolHash || true` 那种「先留个口子」的形状会在 kProtocolHash 填上真值后**静默变成恒真**……症状是「握手校验看起来在、实际谁都能进」。

   **代码没有退化成那种形状，但注释在描述那种形态。** 一旦将来有人照着注释去「修」它（把 `|| true` 加回去以为那是当前设计），就真的会退化。
3. **这是同一个病的第三次发作，且已有前例的修法**。`config/server.yaml:11-14` 在 2026-10-07 做过一模一样的自我更正（「此前这里写……是**不实陈述**——那是"注释说谎"的一个实例」）。**修法就是照抄那次：写明「此前这段说的是 X，2026-10-07 起已改为 Y」。**

### 12.4 处置结果（已修，两处）

两处注释都改成「**不删历史，写清此前说什么、现在是什么**」——照抄 `server.yaml` 在 2026-10-07 做过的同款自我更正：

| 位置 | 改后 |
|---|---|
| `session_mgr.cpp` `HashMatches` 头注 | 陈述当前形态（严格真值比对 157122050），并指明「`cli_client --help` 也已同步改正」；`:31-35` 那段 `|| true` 的反面案例**保留**——它描述的是尚未发生的退化，仍然有效 |
| `cli_client.cpp` `PrintHelp` | 改为「协议哈希校验当前是**双端真值严格比对**……本工具默认就发这个真值」，并注明「2026-10-14 更正：此前这段写……那是 K8 填真值之前的状态。**代码一直是真值比对，注释过期了**」 |

**故意保留「代码一直是真值比对」这半句** —— 它同时纠正了另一个可能的误读（有人可能以为代码也退化过）。诊断和修法分开记，是这类更正该有的形态。

### 12.5 没做的：机器检查

**这三处（`server.yaml` 已修、`session_mgr.cpp` 已修、`cli_client.cpp` 已修）是同一个模式的三次出现**，说明「断言型注释」需要一条机器检查，否则修完一处还会长出第四处。想法是：CI 里扫 `src/**/*.cpp|h` 中形如「**仍是 0**」「待填」「TODO 填真值」的断言型注释，逐条对着 `protocol.h` 核。

**这属于 [[架构评审-熵减-2026-10]] 里 T1/T6/T15「check 助手收敛」的范畴，本轮没做** —— 它要动 `CLAUDE.md` 常用命令那一节（新增一条 check），需要拍板。
