## 对照 1 · 字段级序列化 vs 消息级定长 payload（格雷泽 §4.1–§4.2.1）

> 📖 教材：[[第4章 对象序列化]] §4.1–§4.2.1

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| **不要按内存块发送，每个字段单独序列化** | **已在用** | `otf-server/src/proto/protocol.h` 的 `wire::` 命名空间逐条声明每个消息的**定长字节数**（`kHitReportPayload = 13` 等）与字段构成，**全仓库无任何 `sizeof(对象)` 上线**。编解码在 `src/proto/msg_codec.{h,cpp}` |
| 缓冲区可复用、避免每包分配 | **✅ 已实现**（2026-10-14 重验，原表写的是「尚未实现」） | 待发缓冲是连接的**成员**而非每次分配：`net/tcp_transport.h:110` `std::vector<uint8_t> out;`；发送完在 `net/tcp_transport.cpp:369-370` 复位 `c.out.clear(); c.out_sent = 0;`，**保留 capacity 复用** |
| `kMaxPacketSize = 1470` | **同量级不同值** | 本项目 `kMaxPayloadSize = 1400`（`protocol.h:27`，注释「单帧不触发 IP 分片」）——比原书小 70 字节，给帧头和封装留余量 |
| 引入「流」抽象 | **有意不引入，但**理由已改 | 本项目走**消息级定长 payload**：7 个 Encode + 4 个 Decode（`msg_codec.h:49/55/61/65/68/122/125` 与 `:46/86/97/113`）。字段少时比字段级流省事，**但一旦某个消息要带变长数据（字符串、列表）就必须引流**——格雷泽 §4.2.1 已给出答案 |
| 帧头写明「小端」 | **潜在隐患，仍未处理** | `protocol.h:25` 帧格式注释标「小端」。这只在**两端同架构同字节序**时成立，是**部署前提而非协议保证**。跨架构部署前必须补 `htons`/`ntohs` 或显式移位 |

> ⚠️ **本项目自己的取舍代价**：编解码是**成对手写**的（Encode 7 个、Decode 4 个，
> 同一个字段表要在两个方向各写一遍）。格雷泽 §4.5 说的「改了写法必须改读法」
> 这个痛点在本项目**依然存在**，缓解手段见对照 4。

## 对照 2 · 字节序与比特流（格雷泽 §4.2.2–§4.2.3）

> 📖 教材：[[第4章 对象序列化]] §4.2.2–§4.2.3

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| **流决定字节序** | **已采纳（隐式）** | `protocol.h:5` 铁律 1 写死「小端、定长字段、无隐式 padding、逐字段显式序列化」。两端同架构时成立，**但这是部署前提** |
| 只有基本类型需字节交换、大小要匹配 | **已在用** | `MsgId : std::uint16_t`（`protocol.h:30`）、`PartState : std::uint8_t`、`RejectReason : std::uint8_t`（`protocol.h:44`）——**枚举显式定宽**，避开 `enum` 底层类型平台相关 |
| **比特流** | **当前不适用，建议不做**（有依据） | payload 都很小：`kHitReportPayload = 13`、`kPlayerStatePayload = 3`、`kWorldSnapshotPayloadMax4 = 98`（`protocol.h:120/116/129`）。98 B × 10 Hz 相对 1400 的预算占比极低，**位打包省下的带宽远抵不上两端必须同步写入顺序的维护成本**。等 payload 出现**枚举 + 布尔 + 稀疏字段**再考虑 |
| 抗分片上限按**字节**判定 | **已满足** | `tests/test_smoke.cpp:94` 断言 `kWorldSnapshotPayloadMax4 + kFrameHeaderSize <= kMaxPayloadSize`。比特流下要按字节长度判，不能拿比特数直接比 |

## 对照 3 · 嵌入 vs 链接、熵编码（格雷泽 §4.3–§4.4）

> 📖 教材：[[第4章 对象序列化]] §4.3–§4.4

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 嵌入 vs 链接的判据 | **已内建，但走的是第三条路** | 本项目**不做指针序列化**，一律「**引用改 ID**」：`Direction`、`PartState`、`BodyPartType` 都是值类型；`kPlayerStatePayload = 3`（`hp:u16 + alive:u8`）里连指针都没有。**这比链接更简单——快照语义本来就允许整表覆盖** |
| 「必须容忍有 ID 但无对象的引用」 | **靠全量快照天然免疫** | 见 [[05-Boss决策与仇恨领读]] 与 [[00-项目领读]] ② 状态闭环：全量快照**幂等**，上一帧没出现的对象下一帧出现即可，**不需要引用修复例程**。这是选全量而非增量的隐性收益（教材依据：[[第5章 对象复制]] §5.3–5.4） |
| 熵编码 / 定点 / 几何压缩 | **一律不做，且是有依据的不做** | `kWorldSnapshotPayloadMax4 = 98`，10 Hz，单帧远小于 `kMaxPayloadSize = 1400`。**省下的那几十比特相对 1400 的预算是噪声**，而定点化会引入量化误差、**污染客户端插值**。等 payload 数量级上来再说 |

## 对照 4 · 可维护性：抽象序列化与数据驱动（格雷泽 §4.5）

> 📖 教材：[[第4章 对象序列化]] §4.5

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 两条解法（虚函数抽象 / 数据驱动） | **都不采用，有依据** | 每个消息只有一个定长 payload。以 `kPlayerInputPayload = 8`（`seq:u16 + move_dir:i16×2 + action:u8 + form:u8`，`protocol.h:115`）为例，**字段就 4 个且全定宽**。为 4 个字段写反射元数据 + 虚调用，**维护成本远超收益** |
| 「改了写法必须改读法」这个痛点 | **换方式规避** | 不用「一个函数写两次」，而是**让字段表成为唯一真相源**：`wire::` 常量与字段构成写在同一处，`tests/test_smoke.cpp:89-95` 断言各 payload 尺寸。**字段一改，测试立刻红**——把同步责任交给测试，而不是靠结构或纪律 |
| `switch` 必须带 `default` | **❌ 未落实（2026-10-14 新发现的缺口）** | 见下 |

### ⚠️ 已变成真问题的判据：`switch` 的 `default`

格雷泽 §4.5 说「`switch` 必须带 `default: assert(false)`，否则新增消息类型漏实现会静默走空」。
**原表写「本项目还没有 `switch`，所以没有这个风险」——这句在 2026-10-14 失效了**：
`src/session/session_mgr.cpp:183` 已经是一个按 `MsgId` 分派的大 `switch`。

现状（实测 `session_mgr.cpp:182-208`）：

- `MsgId` 共 **11 个**枚举值（`protocol.h:30-42`），switch **穷举了全部 11 个**（5 个上行单独处理 + 6 个下行合并成 `return false`），
  所以「新增枚举成员忘写 case」会被编译器 `-Wswitch` 抓到。
- **但没有 `default:`**。`MsgId` 的底层类型是 `std::uint16_t`，**线上的任意字节都能构造出表外值**
  （例如 `msg = 99`）。这类值匹配不到任何 case，直接落到 `session_mgr.cpp:207` 的 `return true` ——
  **fail-open：一条本该被拒的畸形帧被当成正常帧接受，且没有任何日志**。

这正是教材这条判据要防的症状，只是触发路径不是「漏写 case」而是「对端发了表外消息号」。
**结论：这是本项目现存的真实缺口，不是风格偏好。**
本篇只登记事实、不擅自改代码：修法涉及分派纪律（`技术参考.md` §8），
按 [[00-项目领读]] L7 红线 3「要新增先改文档」的同一条口径，需要先改规格再动代码。
