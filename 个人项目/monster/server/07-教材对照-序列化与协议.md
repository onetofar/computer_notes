### 对照 1 补记 · 「payload 长度在编码前已知」这条结构事实（2026-10-20 落地）

> ★ **这是本项目编解码路径最重要的一条结构事实**，也是本轮重构的全部收益来源。
> 教材（§4.1–§4.2.1）只说「每个字段单独序列化」，**没有**说「长度可以先算出来」——
> 而后者才是能不能做到零中间缓冲的前提。

**事实**：本仓库**所有**协议消息的 payload 长度在编码前就已确定 ——
§8.3 消息总表给的是定长；**变长**消息的变长部分在末尾（昵称）、
长度同样能先算出来（`2 + n`）。

**旧形状**（每帧 8 次堆分配）：

```
payload = 空 vector
  → ByteWriter 逐字节 push_back → 容量按 1→2→4→…→128 指数增长 → 8 次 realloc
  → move 进 Frame
  → EncodeFrame 再把 payload 整体 insert 进 out → 又一轮全量搬运
```

**新形状**（每帧 0 次分配）：

```
out 一次 resize 到最终大小（帧头 4 + payload）
  → 写帧头（len 在开帧时就已知）
  → 调用方把 payload 直接写进 out 的最终位置
```

落地方式：`net/byte_codec.h` 的 `ByteWriter` 改成**定长写入器**（`base + len`，
不再增长容器）+ `net/frame_codec.h:53` 的 `BeginFrame`（开帧并返回 payload 写入起点）。

**实测**（`otf-server/tests/bench_data_path.cpp`，主读数是全局 `operator new` 的调用次数）：

| 消息 | 重构前 | 重构后 |
|---|---|---|
| `EncodeWorldSnapshot`（满房 98B） | 129.4 ns · **8.00 次分配** | **24.3 ns · 0.00 次分配** |
| `EncodePlayerJoined` | 49.8 ns · **4.00 次分配** | **6.7 ns · 0.00 次分配** |

**顺带的结构性好处**：「编完再数一遍长度对不对」那个运行期兜底
（原来注释写的是「理论上不可达」）**现在真的不可达了** ——
长度不再是数出来的，是**给定的**。于是那几行可以变成 `static_assert`，
把「编码器与规格表的联系」从运行期搬到**编译期**。

> 📌 **为什么这条属于「教材层没有、项目层独有」**：
> 格雷泽 §4.1 讲的是「不要 memcpy 整个结构体」，那是**正确性**要求；
> 本条讲的是「长度已知 ⇒ 可以一次成型」，那是**性能与熵**要求。
> 两件事的正交，把它们混在一张表里会让人以为「不用 memcpy 就等于零拷贝」。

### 对照 2 补记 · 重组环的拷贝方式（2026-10-20）

**旧形状**（`net/frame_codec.cpp` 的 `RingPush`/`RingPopTo`）：

```cpp
for (std::size_t i = 0; i < n; ++i) {
  ring_[tail_] = data[i];
  tail_ = (tail_ + 1) % ring_.size();     // ← 每字节一次运行时取模
}
```

`cap = 1404` **不是 2 的幂**，所以编译器无法把 `%` 优化成 `&` ——
满帧 1398 字节 = 1398 次循环 + **1398 次整数除法**（x86-64 上 20~40 周期）。

**新形状**：环可能跨尾 → **最多两段 `memcpy`**，切分点是 `cap - tail_`；
`RingUsed()` 的取模换成**条件减法**（`tail_`/`head_` 都 `< cap`，
差值落在 `(-cap, cap)`，「加一次 cap 再减一次 cap」与取模**完全等价**）。

**实测**（同一份基准）：

| 场景 | 重构前 | 重构后 |
|---|---|---|
| 解码 满帧 1398B | 6556.4 ns/帧 | **92.0 ns/帧**（71×） |
| 解码 PlayerInput 8B | 64.9 ns/帧 | **20.9 ns/帧**（3.1×） |

> 📌 **为什么解码侧没有再往下做**（每帧仍有 1.06 次堆分配）：
> 排队语义要求「帧必须独立于重组环」，所以每帧那次分配**不可免**。
> 而解码路径的真实负载是 4 客户端 × 20 Hz = **80 帧/秒** ——
> 为它引入自建帧池（= 引入「谁负责归还缓冲」这个新状态机）**收益为负**。
> **拷贝方式**可以选（memcpy），**分配次数**是排队语义的代价 —— 这两件事要分开看。
> 详见项目内 `docs/数据路径重构-2026-10-20.md` §1「没写进来的怀疑」。

## 对照 3 · 嵌入 vs 链接、熵编码（格雷泽 §4.3–§4.4）

> 📖 教材：[[第4章 对象序列化]] §4.3–§4.4

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 嵌入 vs 链接的判据 | **已内建，但走的是第三条路** | 本项目**不做指针序列化**，一律「**引用改 ID**」：`Direction`、`PartState`、`BodyPartType` 都是值类型；`kPlayerStatePayload = 3`（`hp:u16 + alive:u8`）里连指针都没有。**这比链接更简单——快照语义本来就允许整表覆盖** |
| 「必须容忍有 ID 但无对象的引用」 | **靠全量快照天然免疫** | 见 [[05-Boss决策与仇恨领读]] 与 [[00-项目领读]] ② 状态闭环：全量快照**幂等**，上一帧没出现的对象下一帧出现即可，**不需要引用修复例程**。这是选全量而非增量的隐性收益（教材依据：[[第5章 对象复制]] §5.3–5.4） |
| 熵编码 / 定点 / 几何压缩 | **一律不做，且是有依据的不做** | `kWorldSnapshotPayloadMax4 = 98`，10 Hz，单帧远小于 `kMaxPayloadSize = 1400`。**省下的那几十比特相对 1400 的预算是噪声**，而定点化会引入量化误差、**污染客户端插值**。等 payload 数量级上来再说 |

## 对照 4 · 可维护性：抽象序列化与数据驱动（格雷泽 §4.5）

> 📖 教材：[[第4章 对象序列化]] §4.5

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 两条解法（虚函数抽象 / 数据驱动） | **都不采用，有依据** | 每个消息只有一个定长 payload。以 `kPlayerInputPayload = 8`（`seq:u16 + move_dir:i16×2 + action:u8 + form:u8`，`protocol.h:115`）为例，**字段就 4 个且全定宽**。为 4 个字段写反射元数据 + 虚调用，**维护成本远超收益** |
| 「改了写法必须改读法」这个痛点 | **换方式规避** | 不用「一个函数写两次」，而是**让字段表成为唯一真相源**：`wire::` 常量与字段构成写在同一处，`tests/test_smoke.cpp:89-95` 断言各 payload 尺寸。**字段一改，测试立刻红**——把同步责任交给测试，而不是靠结构或纪律 |
| `switch` 必须带 `default` | **✅ 已采纳（2026-10-20）** | `HandleFrame` 补 `default: return false`（fail-close）——见下节 |

### ✅ `switch` 的 `default`：从缺口到修复（2026-10-20）

格雷泽 §4.5 说「`switch` 必须带 `default: assert(false)`，否则新增消息类型漏实现会静默走空」。
**原表写「本项目还没有 `switch`，所以没有这个风险」——这句在 2026-10-14 失效了**：
`src/session/session_mgr.cpp` 已经是一个按 `MsgId` 分派的大 `switch`。

**2026-10-14 查出的现状**（当时未修）：

- `MsgId` 共 **11 个**枚举值，switch 穷举了全部 11 个，
  所以「新增枚举成员忘写 case」会被编译器 `-Wswitch` 抓到。
- **但没有 `default:`**。`MsgId` 的底层类型是 `std::uint16_t`，**线上的任意字节都能构造出表外值**
  （例如 `msg = 99`）。这类值匹配不到任何 case，直接落到函数末尾的 `return true` ——
  **fail-open：一条本该被拒的畸形帧被当成正常帧接受，且没有任何日志**。

**2026-10-20 已修**：`HandleFrame` 补 `default: return false`（fail-close）。
表外消息号一律判死，与「上行方向不该收到的消息」走同一条处置。

> 📌 **判据**：格雷泽 §4.5 那条「switch 必须带 default」在本项目的等价物是
> 「带 `default: return false`」，不是 `assert(false)` ——
> 因为这里的输入是**网络来的字节**（对端可能发旧协议），`assert` 会把整个进程带走，
> 而正确的处置是**断开这一条连接**（与 `msg_codec.h` 的「短 payload 一律返回 kMalformed，
> 绝不 abort」同一条纪律）。

修完之后，「表外消息号」与「上行方向不该收的消息」得到**同一种处置**：
两条路都判死，两端都不会「对着错误的协议说话」。
