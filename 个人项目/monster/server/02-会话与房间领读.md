# 02 · 会话与房间领读（`src/session/` `src/room/` `src/app/`）

> **怎么读**：[[00-项目领读]] L5.3 给了地图,这里讲**跨层因果**——session 层是全服务端唯一的粘合层
> （依赖图里它横跨 net/room/proto/sim/common/config）,所以「谁不知道谁」的边界纪律在这里最密。
> 📖 教材结合方向与 [[01-网络层领读|01]] 相同:项目 → 解读 → 教材,单向。

## 0 · 三层职责的形状

```
session/  连接 ↔ 玩家 ↔ 房间 的粘合（表驱动:ConnId → Session 槽位）
room/     房间与座位生命周期（room_id → Room,座位 = player_id 1..4）
app/      主循环的调度件（固定步长 + RAII 回收守卫）
```

**分层契约**:net/ 只说「这条 fd 来了字节/没了」,session 层拿着 ConnId 查自己的会话表再路由到 room——**net 不查房间表,room 不认识 fd**（`session_mgr.cpp:470` 原注:网络层只投递「这条连接没了」,是这里拿着 room_id 去查）。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.2.3]]:ClientProxy 的「每客户端一份」形状——本项目把代理拆成「会话槽位（连接态）+ 座位（房内态）」两截,断线时两者解耦（§7 的座位保留）。

## 1 · 承重设计一:会话表与连接表同尺寸（`session_mgr.cpp:19-22`）

会话表下标范围 = `kMaxFd`,与 TcpTransport 的连接表**同一个常量**。

**为什么**:不同尺寸就会出现「本层说有会话、net 层说没这个 fd」,症状是**往一条不存在的连接发包**。`ConnId = fd 直接作下标`这条不变量（[[01-网络层领读|01]] §0）在这里被二次利用——两张表共享同一个下标空间,查表零哈希。

**改动地图**:任何一张表换了尺寸/换了映射 → 下标不变量断 → 症状是幽灵发包;想改就只能两张表一起改,并在两处 static_assert 同一常量。

## 2 · 承重设计二:槽位复位必须逐字段（`session_mgr.cpp:50-77`）

`ResetSlot` 不能写成 `sessions_[i] = Session{}`,两个理由:

1. **编译不过**——Session 内嵌 FrameDecoder,它的构造是 **explicit**(0 是非法队列深度),Session 因此不可聚合初始化。报错落在「converting to FrameDecoder from initializer list」——**看着像解码器的毛病,根因在 Session**。那个 explicit 是故意的,不为迁就这行去掉;
2. **语义上必须重建**——FrameDecoder 要丢掉上一任的**半包残留**就得整体重建,无法原地清空。这正是「fd 复用必须整体复位」:transport 层明确警告回收后的 ConnId 会被立刻发出去(​[[01-网络层领读|01]] §8),槽位里若残留上一任的 nickname/room_id,**新玩家会继承幽灵状态**——症状「新玩家一进来就显示已在 3 号房」,极难复现。

**改动地图**:给 Session 加字段忘了在 ResetSlot 里清 = 幽灵状态链激活;为了让 `Session{}` 能编译而去掉 FrameDecoder 的 explicit = 把「0 是非法队列深度」的防线拆了。

## 3 · 承重设计三:心跳首拍对齐（`session_mgr.cpp:71-75`）

`ResetSlot` 里 `last_hb_ms = now_ms`(建连时刻),**不是留着 0**。

**事故形状**:last_hb_ms 停在 0,而 now 是 steady_clock 绝对值(开机时长)——第一条心跳在建连后第一个 tick 立刻发出。它是那 1 秒里**唯一**的一条,心跳节奏变成 `0s, 1s, 1s, 1s…`(首拍错位)。

**延伸**(Tick 的心跳节,`:499-512`):下行心跳判据用 `last_hb_ms`(**本层发过**的时刻)而非 `last_recv_ms`(对端最后来信)——用错的话,一个只收不发的客户端每 tick 都会收一条心跳。

> 📖 [[第2章 互联网|格雷泽第2章 §2.8]]:下行 1Hz 心跳的存在理由根本不是「客户端要」——是**穿透 NAT/防火墙的空闲表项**(不持续发包映射会老化)兼让客户端测 RTT。

**改动地图**:新增会话路径忘了设 last_hb_ms = 首拍错位;心跳判据换回 last_recv_ms = 心跳风暴。

## 4 · 承重设计四:must_close 延迟返回（`session_mgr.cpp:165-187`）

`FeedAll` 的帧回调里**不能就地 return false**——那个 return 只退出 lambda,外层照样把剩余帧喂完:一条已判死的连接还会被继续投递帧,症状「断连之后又收到几条包」,时序相关极难复现。

正解:回调里收集 `must_close`,**喂完之后**统一 `return !must_close`。且循环开头 `if (must_close) return;`——一次粘包里剩下的 PlayerInput/HitReport 不许再投给已被拒绝的会话(症状:「刚被 Rejected 的连接又让房间动了一下」)。

配套:未知连接喂数据**返回 true**(`:138-143`)——「on_close 还没走到、字节已经来了」是 LT 下的正常时序,判死它 = 「连接莫名其妙被踢」且无日志。

> 📖 [[01-网络层领读|01]] §7 的镜像:net/ 兜「回调里自己 Close 了」;session/ 兜「判死后剩余帧还想进来」。**契约的另一半总在对面层手里。**

**改动地图**:把 must_close 改成回调里直接 return = 断连后继续投帧;把未知连接返回 true 改成 false = 时序竞态踢人。

## 5 · 承重设计五:HandleJoinRoom 的校验顺序与比较符（`:225-252`）

**顺序 = 哈希最先**——「连协议都没对齐的客户端不该占用房间名额,否则一次错版本的连接洪水能把房间全占满」。然后服务器满,然后选房。

**比较符陷阱**:上限判据是 `session_count() > max_sessions_` 且**前提是 count 数的是存活会话**——本会话自己已算在 count 里,max=2 时第 2 条连接 count()==2 → `2 > 2` 假 → 放行;第 3 条 → 拒。**写成 `>=` 会变成「上限 N 只收得下 N−1 条」**——症状「配置说 4、实际只能进 3 个人」,而房间明明还有空位。

**上限管的是连接不是房位**:「超过 max_sessions 就关连接」不放在 OnConnectionOpen(那样客户端连一条 Rejected 都收不到,§10.1 要求「先说再关」),放在 JoinRoom——那才是它有意义的位置。

> 📖 [[第10章 安全性|格雷泽第10章 §10.2]]:校验前置与「先说再关」都是输入验证的处置纪律;哈希校验防错版本连接洪水,[[第10章 安全性|第10章 §10.1]] 的传输保密层之外的第一道闸。

**改动地图**:把哈希校验挪到选房之后 = 洪水占坑;`>` 改 `>=` = 少收一个人;上限判定挪回 OnConnectionOpen = 客户端死得不明不白。

## 6 · 承重设计六:忽略 vs 判死的判据表（全文件统一）

session 层收到异常输入,处置分三档,**每档有明确判据**:

| 情形 | 处置 | 判据 |
|---|---|---|
| 重复 JoinRoom(已入房又发) | **忽略** | 踢掉好好玩着的玩家代价 > 多处理一帧;客户端重连逻辑不干净时很常见 |
| 没入房就发 Input/State | **忽略** | 顺序错误通常来自刚重连还没重发 JoinRoom,自愈快 |
| 帧长度/解码失败 | **判死,且不发 Rejected** | 流不可信;Rejected 只有 3 个具名含义(哈希/满/服务器满),新增含义 = 改协议(红线 3/4) |
| 收到下行方向的消息 | **判死** | 对端实现错了——忽略的话两端一直对错误协议说话,「联调时什么都能连上、什么数据都不对」 |
| 滥用(60s 内 HitReport 超限 10 次) | 判死(走 Close,座位进重连窗口) | 与超时判死同一条路,**不新增第二套赶人逻辑** |

**Rejected 的语义纪律**是这套表的锚:「你这条包格式错了」**不在** Rejected 的三个具名含义里——发一个语义不符的 Rejected = 悄悄扩协议。

> 📖 [[第10章 安全性|格雷泽第10章 §10.2]]:「拒绝但不踢」的处置原则在这里长成了完整判据表——**错误性质(可自愈/不可信/实现错误)决定处置,而不是错误出现的位置**。

**改动地图**:给 Rejected 加第四个含义 = 协议漂移;把「忽略」类改成判死 = 重连风暴下的误杀;滥用断连另起一套踢人逻辑 = 两套状态机互相打架。

## 7 · 承重设计七:session_count 不缓存（`:84-94`）

每帧 O(N) 数存活槽位,**刻意不缓存计数**——缓存就得在 OnConnectionOpen/Closed 两处各维护一次,那正是「漏一处就永久漂移」的失败模式(与 main.cpp「每轮同步增量而不在回调里打点」同一条纪律)。

**解读**:这是**用可预算的 O(N) 买掉一个状态变量**。N = kMaxFd = 1024,每帧一次线性扫完全可接受;而漂移的计数器会让「服务器满」判定在某个未知时刻开始说谎——§5 那条 `>` 判据建立在「count 必须准」上。

**改动地图**:缓存 count = 两个维护点漏一个 = 上限判定漂移;想优化就先写「两处同步维护」的测试,而不是直接缓存。

## 8 · 承重设计八:TickWorld 的四步顺序（`:381-423`）

```
① 补发重连全量快照(needs_snapshot_)   —— 必须最先:重连者不等下一个 10Hz 节拍
② rooms_.TickAll(tick)                —— 世界推进
②' 滥用断连(AbuseTripped → Close)     —— 必须在 TickAll 之后:滥用判定发生在
                                         世界第 5 步清算 HitReport 时,本拍入队本拍生效
③ 10Hz 快照广播(FlushSnapshots)       —— 同一 tick 全员同一份字节(§7.3 条件 3)
```

每一步的「为什么在这个位置」都有事故形状:补发晚了 = 重连者 100ms 黑屏;滥用断连放 TickAll 前 = 本拍的滥用要下一拍才断(窗口里多白打 50ms);广播的字节构造在 RoomManager 只做一次、session 层只发同一份 bytes——**构造一次、全员同字节**是全量快照幂等性的广播侧前提。

> 📖 [[第5章 对象复制|格雷泽第5章 §5.3]]:全量快照的「每包自足」让补发天然安全——不存在「从哪个 delta 补起」的账本;[[第10章 安全性|第10章 §10.2]]:滥用断连走 Close 而不是踢出房间 = 与超时判死同路。

**改动地图**:①③ 对调 = 重连黑屏;②' 挪到 ② 之前 = 滥用生效延迟一拍;广播改为逐人构造 = 同 tick 字节不一致的风险面。

## 9 · 承重设计九:room_id 永不复用 + 建房/销毁必须留痕（`room_mgr.cpp:110-121,185-192`）

- `room_id = next_room_id_++` **单调递增**——复用会引发很难查的一类问题:客户端还攥着上一次的 room_id,服务器已把它发给另一局,「进错房间」且无任何报错;
- 建房与销毁**各打一条日志**——这是「房间回收」这件事**唯一**的外部可观测点:内存里没发生的事在端到端验收里完全不可见(房间里只剩自己时,销毁与否对客户端同构)。曾经以「K6 才需要」为由不加,验收脚本只能空口说「房间应该被回收了」——**那不叫验收**;
- 两者配对后「号不复用」可验收:销毁过 1 号房,下一个建房日志必须是 2 不是 1。

> 📖 [[第6章 网络拓扑和游戏案例|格雷泽第6章 §6.3.2]] 的对照:机器猫 RTS 的玩家 ID 由主对等体统一发,本项目把「ID 单调性」用在房间上——同一件事:**标识符不复用是消除一类幽灵 bug 的结构手段**。

**改动地图**:room_id 改成找最小空号 = 进错房间类 bug 解锁;删建房/销毁日志 = 房间回收规格失去唯一观测口。

## 10 · 承重设计十:Reclaim 的顺序与两批留痕（`room_mgr.cpp:151-194`)

**先回收座位、再判销毁**——反过来时,一间「所有人都在重连窗口内」的房会在座位还没回收时就被销毁,玩家随后重连**找不到座位**,而规格明确要求他们回得来(座位保留 = §10.3)。

**先收集 to_destroy、再统一 erase**——边遍历 map 边删 = 迭代器失效 = UB(随机崩溃/静默错读)。

座位回收同样打日志:「重连窗口到期」这条规格的唯一外部证据——没有它,「玩家莫名其妙消失」这种最典型的现场表现无从归因。

> 📖 [[第12章 玩家服务|格雷泽第12章]] 的对照:Steam 大厅把入会外包给平台,本项目自管房间——「重连窗口」就是自管时必须自己写的那个平台功能。

**改动地图**:对调 ①② = 重连者找不到座位;边遍历边 erase = UB;删座位回收日志 = 重连窗口规格不可验收。

## 11 · 承重设计十一:空房停 tick —— 对齐 §10.1 状态机(2026-10-20 落地)

**规格原文**(`技术参考.md:1227` 状态机):

```
Room ──成员数=0 持续 30s──→ 房间销毁(tick 停止)
```

★ **「tick 停止」这四个字以前没有落地**:`room_mgr.cpp:198` 的 `TickAll`
无条件推进每个房间 —— 于是一间**一个人都没有**的房间,在它那 30s 销毁倒计时里,
仍然以 20Hz 跑完整的 Boss AI(大脑 + 仇恨 + 解剖 + 命中清算)。
32 间房全空 = **每秒 640 次没人看的世界模拟**;最坏一轮(32 间 × 20Hz × 30s)
= **19,200 次**白跑的 tick。

**判据取 `occupied_count()==0`,不是 `connected_count()==0`**:

- §7.2 红线 1「玩家掉线,**房间照跑**」—— 断线者的座位还留着(10s 重连窗口),
  房间里**仍有成员**(`occupied > 0`),世界必须继续演化,
  否则重连回来的人看到的是一个「冻住的世界」;
- 而「成员数=0」在代码里的**唯一**对应就是 `occupied_count()==0`:
  `Room::IsEmptyExpired` 的销毁判据正是它(`room.cpp:129`)。
  **两个判据必须是同一个式子**,否则会出现「还在倒计时却已经停 tick」的空窗。

**为什么停了也没人看得见**:`FlushSnapshots` 早就跳过 `connected_count()==0` 的房间了,
所以空房**本来就不产出任何快照**。唯一可观测的差别是「后来者加入这间房时 Boss 停在哪儿」——
而那本来就是「这间房没人时它在哪儿」的问题,规格的答案是「随房间蒸发,不做持久化」(§10.3)。

> 📌 **这一条的归属**:它不是「优化」,是**让实现回到规格**。
> 判据选错方向(用 `connected_count()`)会**违反红线 1** —— 那是比慢更糟的错。

## 12 · app/:主循环的两个小件

- **`tick_scheduler.cpp:40-52` 补帧上限**:逻辑帧预算恒定,渲染/IO 慢时**丢帧不追帧**——上限防的是「一次卡顿后连环补帧打爆下一拍」。固定步长的漂移一次,全端 effective_tick 就对不上;
- **`reap_guard.h` RAII 回收守卫**:每轮开头构造、析构时 ReapClosed——continue/break/异常展开四条路径回收都发生。**为什么不用 try/finally 风格**:C++ 的 RAII 是唯一四路全覆盖的写法。

> 📖 [[第3章 线程、进程以及Actor模型|彭放第3章 §3.4]]:主循环骨架;固定步长本身是项目设计(教材无对应,00-领读 L5.1 有边界声明)。
