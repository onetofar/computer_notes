## 10-格雷泽-复制可靠性

> 教材篇：[[10-格雷泽-复制可靠性]]

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 全量快照幂等，状态通道不需要可靠层 | `otf-server` 的 `S2C_WorldSnapshot`（10 Hz 全量广播） | 维持现状；丢包自愈靠下一个快照，不给状态包做 ACK/重传（见 [[04-格雷泽-全量快照与增量]]） |
| 离散事件才需要命令重批式可靠 | `S2C_BossEvent`（破部位/击杀，事件驱动） | 若将来做"事件不丢"：给事件加确认水位线或按本节模式重批**事件命令**，事件载荷取服务器最新权威状态，不重放旧字节（`技术参考.md` §6/§10） |
| 在途去重 = 用已知信息削减重复工作 | `C2S_HitReport.client_tick` 延迟补偿口子 | 同一思想：命中回溯时若目标状态已被更晚快照覆盖，不必重放旧帧 |
| 宿主提供包、复制层只收通知 | `otf-server` 主循环的广播层（`FlushSnapshots` 定节奏） | 节奏权在主循环不在模拟层——已按此分层；将来加事件通道时沿用"模拟层记账、广播层带节奏" |

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|

| 「保障」类事件的可靠通道 | `S2C_BossEvent` | 丢失不自愈；可靠化路径见 [[10-格雷泽-复制可靠性]] 的命令重批 |

## 13-格雷泽-权威服务器与客户端代理

> 教材篇：[[13-格雷泽-权威服务器与客户端代理]]

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| ClientProxy 三重身份 | `otf-server` 的 Session/Player 状态 | 输入缓冲（深度 8）+ 每会话快照状态已在会话对象上；延迟补偿锚点 = `HitReport.client_tick`（`技术参考.md` §10） |
| HELO/WLCM 状态机握手 | `C2S_JoinRoom` / `S2C_JoinAccept` | 同构：哈希校验 + 分配 player_id + 重试闭合（TCP 上重传由内核做，状态机只剩语义校验） |
| 四字符包常量 | 帧头 u16 msg id | `'RPLM'` 式助记 → 我们用消息号；语义同：首字段定类型 |
| 按 Move Δt 重放 vs 固定 tick | `otf-server` 20Hz 固定步长 + 输入缓冲 | 两种等价解法：书 = 时间基准跟输入走；我们 = 时间基准固定、输入按 tick 采样。固定步长更适合帧同步广播（`effective_tick`） |
| 每客户端独立复制账本 | 广播层 | 全量快照阶段不需要；转增量快照时按会话记账是结构前提（§7.2 的"增量留口"） |

## 14-格雷泽-P2P锁步实现

> 教材篇：[[14-格雷泽-P2P锁步实现]]

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 确定性纪律（种子外置、调用序稳定） | `otf-game/scripts/sim/` 约束 2 | 已是硬约束：`RandomNumberGenerator` 当参数传、种子外部定——同一纪律的防回滚版本（`CLAUDE.md` §三） |
| 每轮校验值（PRNG 心跳 + CRC） | `tests/diff_snapshots.py` 一致性验收 | 4 端同房逐字节 diff = CRC 校验的更强版本；协议若加状态校验字段，取 CRC32 即可 |
| `mTurnData[轮][玩家]` 缺口检测 | 将来给 `S2C_BossEvent` 做可靠通道 | "到齐才推进"的判定结构可复用为"事件确认水位线"（`技术参考.md` §6/§10） |

## 16-格雷泽-商业引擎网络

> 教材篇：[[16-格雷泽-商业引擎网络]]

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| UNetDriver ≈ NetworkManager 分层 | `otf-server` 的 net/ 与 room/ 分层 | 引擎把"传输无关消息层"单独拆类——与我们的 frame_codec（传输）/session/room（逻辑）分层同构 |
| owner-only 服务器 RPC | `C2S_HitReport` / `C2S_PlayerInput` | 输入与命中声明只认绑定会话的 player_id——服务器已按会话隔离，等价于引擎的 owner 校验 |
| 通道 QoS 四档 | 单一 raw TCP 上的消息语义 | 我们在一条 TCP 上自己区分：快照（丢了等下一个）/事件（要求达成的语义）——引擎的 QoS 通道是这个区分的现成命名法 |
| SyncVar 粒度教训 | 快照负载设计 | 快照按字段量化 + 增量留口（`技术参考.md` §7.2）——避免"动一个传全块"的 SyncVar 陷阱 |

## 17-格雷泽-玩家服务

> 教材篇：[[17-格雷泽-玩家服务]]

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| pImpl 隔离平台服务 | `otf-server`（将来接第三方服务时） | 平台细节关进单个实现文件；`JoinRoom` 的 `player_id`/会话令牌已是服务无关设计，Steam ID 进来时映射到会话而非渗透进协议 |
| 建联预热原则 | 客户端连服流程 | 连接/哈希校验完成后先收首个快照再开打（服务器天然满足：快照 10Hz 持续广播） |
| 服务分配身份 | 不再自造玩家 ID | 服务器分配 player_id（1-4）只在会话内唯一；平台身份在会话层映射，不进协议字段 |
| SteamGameServer 匿名模式 | 部署形态 | 若上 Steam 发行，专用服务器走匿名注册，与 §13 云托管相容 |
