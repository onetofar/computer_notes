## 一、已修（commit `d32848d`）

### [B1] 服务器 `body_scale` 与客户端 `boss_scale` 已分叉 —— Boss 全部距离判定差 2 倍

这是本次审计**唯一一条已经造成实际后果**的发现。

**怎么漏的**：2026-10-08 路线 C 把全局 32 像素口径落地，`boss_scale` 从 1.5 翻到 3.0
（龙图离线降采样 512×288 → 256×144，运行时放大倍数同步 ×2 保持屏幕尺寸）。
`MakeAnatomyConfig()` 的 `core_hp` / `kPartHp` 都同步更新了，
**唯独漏了 `MakeBrainConfig()` 的 `body_scale`**。

**为什么后果重**：`body_scale` 是 `ReachTowards()` 的乘数，而停步圈 / 扇形攻击半径 /
吐息锥 / 冲撞判定宽度**全部**从它派生。服务器算出的是客户端的一半：

```
玩家看着自己已经站在龙身上
  → 服务器判「还在攻击范围外」
  → Boss 继续走
```

这正是 `game_config.gd:98-100` 自己记的那个症状——**「追着推人、永不攻击」**。

**为什么不是"改对就行"**：同一个坑在同一个文件旁边已经栽过第二次。
第一次是 `boss_total_hp` vs `boss_core_hp`（2026-10-08 翻倍时只改了同义的前者，
全工程无人读它 → 客户端核心血停在 3000、服务端 6000，两端不同步且都不报错）。
代码里为此留了防复发注释，但**注释防不住第二个人的第二次核对**。

所以补的是机器守卫，不是纪律：

| 新增 | 作用 |
|---|---|
| `resource/otf-resource/data/test_vectors/config_parity.json` | 跨语言配置的唯一真值 |
| `otf-game/test/test_config_parity.gd`（33 断言） | 逐键比 `GameConfig.*` |
| `otf-server/tests/test_config_parity.cpp`（ctest #18） | 逐键比 `MakeXxxConfig()` |

**关键设计**：两端期望值**都从共享文件读**。硬编码期望值就是自证——
本实现和期望值同源，跑多少遍都绿，真分叉了也绿。（与 `loot_roll.json` 同一纪律。）

**反向验证过**：把 `boss_scale` 打回 1.5 → 精确命中那一条，其余 32 条零误报。
> [!tip] 为什么必须做反向验证
> 一条永远绿的断言看起来和一条有效的断言完全一样。
> 「全绿」本身不证明它在守——只有「故意打坏时它变红」才证明。

顺带把客户端两处硬编码的 `0.35` 收进 `GameConfig.boss_hit_dot_threshold`
（服务端一直是配置字段 `hit_dot_threshold`，**一端可调一端不可调**，改一边必然分叉）。

### [B7a] 约束 2 的机器守卫在缺 bash 时降级为 `skipped` 且**不计入失败**

```powershell
# otf-game/test/run_all.ps1:77（原）
} else {
  $rows += [pscustomobject]@{ Test = 'check_sim_purity.sh'; Result = 'skipped(no bash)' }
}   # ← 不加 $bad，脚本末尾照旧 exit 0
```

> [!danger] 守卫自己静默失效
> 任何没装 Git Bash（或路径改名）的机器上，约束 2 从「每次回归都查」变成
> 「**永远不查**」，而汇总表里那行 `skipped(no bash)` 和 `ok` 长得一模一样。
>
> 这是本项目反复踩的「静默退化」——而这一次它出现在**守卫自己身上**。
> 守卫失效时，没有任何东西会告诉你它失效了。

改成判红。判据：**守卫跑不了 = 没有守卫**，所以不设「环境原因跳过」这条出路。
要临时跳过请显式改代码，别让它自己降级。

## 二、未修 · 第 5 层（服务器权威）必炸链路

> [!warning] 这五条的共同形状
> **全部在客户端本地裁决，且都没有回滚调用方。**
> 协议里一条相关消息都没有——服务器连影子都不存在。
>
> 与 B1 的区别：B1 是**已经漏出去**的分叉，这五条是**架构上还没有接口**。

### [B2] 掉落 roll 的种子来自客户端墙钟

```gdscript
# level_01.gd:340
Game.collect_part(_loot_boss_id(), part, Time.get_ticks_msec() + _loot_seq * 7919, at)
```

向量锁住的是**算法**，不是**种子**。`test_loot_roll.gd` 逐条比对的是
`(seed, table, broken_parts) → (drops, state)`，而生产路径的 seed 是本机毫秒时间戳——
服务器拿不到，也无法推导。

代码里把它写成了刻意设计：
> 「种子由 `Time.get_ticks_msec()` + 本场计数给出，**不用全局随机**」

「不用全局随机」这个理由是对的，但**换成墙钟并没有解决问题**——
它只是把「不可复现」从 PRNG 内部挪到了调用方。回滚重放依然对不上。

**后果**：同一次部位破坏，服务器和客户端**必然** roll 出不同的东西，
而向量锁完全感知不到（它锁的是函数，不是调用点）。
**这是本次最容易被「测试全绿」骗过去的一条。**

**改法**：种子由服务器分配，随 `S2C_BossEvent{PartDestroyed}` 广播；
客户端读不到时**拒绝结算并 `push_error`**，不回落墙钟。

### [B3] 持续状态由客户端 `_physics_process` 推进并直接改血量

```
_physics_process → advance_statuses → StatusMachine.tick → _apply_status_hp → _die()
```

三条独立理由，任何一条都够格：

1. **改血量 = 裁决**（`status_machine.gd:12` 自己写着「联机时持续状态由服务器 tick 推进」），
   而这里是客户端引擎帧驱动。红线 2：不接受客户端上报的权威状态。
2. **时间基准不一致**：`delta` 是引擎 `_physics_process` 的，服务器是固定 50ms tick。
   两边的 DoT 跳点相位会**持续漂移**，不是「差一帧」，是永远对不上。
3. **回滚口缺失，而 CD 有**。这个不对称很说明问题：

```gdscript
# skill_cooldowns.gd:66-72 —— 有
func snapshot() -> Dictionary: return _ready_at.duplicate()
func restore(snap: Dictionary) -> void: _ready_at = snap.duplicate()
```
`StatusMachine` **完全没有** `snapshot()` / `restore()`。
CD 那套「接口按能搬走设计」是真的，状态这套是文件头注释里的**说法**——设计没做。

### [B4] 技能 CD 在客户端本地提交，`cooldowns_snapshot()` 零生产调用方

`try_use()` 立刻把 CD 写进本地状态，然后才执行效果。任何「施放成功」都是客户端单方面宣告的。

联机时若服务器拒绝一次施放（比如 R 还在 CD），客户端**已经放完技能、位移已经发生、
`attack_up` 已经挂上**了，而服务器说「你没放出去」。
`cooldowns_restore()` 只能还原 CD，还原不了已发生的位移和已挂上的状态。

> [!tip] 一个能说明问题的旁证
> `cooldowns_snapshot()` 全工程**只有定义处，没有任何生产调用方**；
> `cooldowns_restore()` 的 11 处调用全在 `test/` 下。
>
> 也就是说这个回滚口写了、被测试用了，但**没有任何非测试代码会因它坏掉而变红**——
> 它现在是装饰。「有接口」和「接口被用」是两件事。

### [B5] 背包 / 仓库 / 装备在客户端本地提交并落盘

`Game` 持有四个**可直接写**的字典，每个写操作都是「本地改 → 立刻 `user://` 落盘」。
联机时这等于**客户端在给自己发存档**：背包满的判定在客户端做，服务器状态不同步时
A 说「装不下」、B 说「装下了」。

`_apply_loadout()` 更麻烦：它把**本地存档算出的装备加成写进全局单例 `GameConfig`**，
而 `apply_server_config()` 按设计正是**服务器下发**的入口。**两个数据源抢同一个全局槽位。**

### [B6] 部位破坏的掉落由客户端事件触发

```gdscript
# boss_entity.gd:604-605（它自己承认了）
## ★ 仍然**不发** `part_event`：那是单机 sim 的事件流，联机下没有 sim 也就没有它。
```

于是联机模式下**部位破坏根本不触发掉落结算**（`part_event` 不发 → 回调不跑）；
或者如果有人为了让它跑而补发 `part_event`，那就是拿客户端事件当裁决信号。
**两个方向都不能要。**

## 三、未修 · 当下就成立的缺陷

### [B8] 玩家装备加成经全局单例下发，AI 队友跟着一起变强

**这条在单机下就已经生效**，不需要等服务器。

```
穿上烈焰刃 → Game.equip() → _apply_loadout()
  → GameConfig.apply_server_config(...)     ← 写进进程级全局单例
  → 全场 4 个 player32 的 hitbox 伤害同时 +X（含 3 个 damage_scale=0.6 的队友）
```

`game_config.gd:528-530` 那条注释「折扣后队友是帮手，主角仍是主要输出」
正好被这个 bug 推翻——主角的变强会被队友按 0.6 复利放大一次，配平全歪。
而且这是**静默**的：数值对、不报错、TTK 面板跟着一起变，看着还挺合理。

架构根因：**per-entity 的属性被路由到 process-global 单例**。
`game_config.gd:394-398` 已经论证过「基础值与最终值不能共用一个字段」
（`boss_total_hp` 教训），但它没意识到「**最终值也不该是全局的**」。

**改法**：`equipment_bonus` 从 `GameConfig` 挪到 `player32` 实例，
`Game._apply_loadout()` 改成像 `_broadcast_loadout()` 那样逐实体下发。

## 四、技术债 · 测试层

### [T7] 12 个**零断言**文件在回归表里显示 `ok`

这 12 个文件里没有任何 `check` / `assert` / `push_error` / `quit(1)`，只 print 时间线然后退出。

**叠加放大**：`$long_timing` 名单里有 **11 个**与这份名单重叠，而
`exit_guard.gd` 在帧预算为空时**完全不武装**。

> 11 项 = 无断言 + 无退出码守卫 + 靠日志里的断言行判定（而它们一条都没有）
> = **无论代码怎么坏都恒绿**。

这正是 138 条断言只剩 17 条、结论行照样打「全部通过」那类事故的温床。
`README.md` §6 只登记了其中 4 项，**漏了 8 项**。

**三选一，逐个定，不许一刀切**：
1. 确属人工核对台（`test_shoot_demo` / `test_skills` 这类逐帧对照）→ 改名 `probe_*.gd`，
   让 `run_all.ps1` 的 `test_*` 通配符自动收不到（与 `crash_probe.tscn` 同一手法）。
2. 本该有断言 → 补断言。
3. 保留但降级出回归表，改由抓帧台承载。

### [T6] 7 个文件成功时不打印 `ok:` 行

`run_all.ps1:52` 靠 `^\s+ok: ` 计数、`:170` 靠中文「共 N 处失败」判定。
**成功时不打印 `ok:` 的文件，日志里没有任何「断言确实跑过」的正向证据**——
`Test-Reconcile` 的核心判据对它们结构性失效。

### [T9] `test_consumables` 实现了全套对账，却没被 `run_all.ps1` 认领 ⭐

**修复成本 1 行，收益是给 81 条断言补上防假绿闸门。**

它已经实现了 `SECTIONS` + `SECTION_ASSERTS` + `EXPECTED_ASSERTS` + `assert_watchdog`，
而且 `:167-169` 确实自己手打了一行格式完全吻合 `run_all.ps1:53` 正则的 `RECONCILE …`。

**即：自证机制已经造好了，只是没人去看。**

而它的文件头 `:19` 写着「`run_all.ps1` 的 `$reconcile_scenarios` 会逐条对账」——**这句话是错的**。

### [T2]+[T10] 存档隔离 8 份手抄，其中 3 份已各自漂移；逐字节还原只验了 2/8

`SAVE_DIR` 逐字重复 8 次、`_remove_tree` 8 份（6 份相同 + 2 份漂移成 14/15 行）、
`_isolate_save` 8 种不同实现。

**最要紧的是 T10**：「跑完回归 `user://save/` 必须逐字节回到原样」这个不变量
只验了 `test_inventory` 与 `test_level_01_flow` 两个文件，而**没验的 5 个恰好是
直写 `Game._storage` 或走完整存档往返的那批**——最可能损坏玩家存档的文件，
恰恰没有那条断言。

> [!note] 这里的历史包袱值得记住
> 项目**已经因为这个坑真出过事**：跑一次回归把玩家存档删了，而 176 条断言全绿、退出码仍是 0。
> 那次还写下了变异测试证明隔离是**承重**的（去掉隔离 → 存档被删 → 断言依然全绿）。

**改法**：建 `SaveGuard`，提供 `isolate()` / `restore()` / `snapshot_sha()` / `assert_restored()`，
8 个文件统一。每个文件各删 40–50 行，同时把「逐字节还原」推广到全部 8 个。

最大重复源不在视图层，在**数据加载层与 sim 层**。

| 重复 | 份数 | 建议 | 风险 |
|---|---|---|---|
| `status_catalog` / `skill_catalog` 的 `_cache`/`invalidate`/`errors`/`_load_defs`/`_validate`/图标 fallback | 2（近乎孪生） | 抽 `data_registry.gd`，保留 skill 专属的 `cd_order` 校验 | medium |

| 秒数格式化 | 2（其中一处未接 i18n） | 抽 `config/duration_fmt.gd` | medium（文案被断言） |

> [!danger] `res://` 前缀那处是**潜在 bug 不是整洁问题**
> `paperdoll_catalog.gd` 的实现最完整，其他几处**遇到已经带 `res://` 的路径会拼出
> `res://res://...`**。这是「顺手写的重复」已经开始互相产生错误值的实例。

### 明确**不建议**动的重复

- **`preload` 常量块重复**：这是 GDScript 的有意设计。无编辑器环境下

- **`test_anatomy.cpp` 里抄 GDScript 的配置值**：看着像没跟上，但它验的是
  **移植忠实度**（同一组输入 → 同一组输出），不是「参数是不是最新」。
  抄 GDScript 正是这个测试的目的。真正缺的是 B1 那个跨语言 parity 测试——
  已补，与它不冲突。

## 六、熵减 · 上帝文件拆分

5 个超 40 KB 的文件。逐个通读后的结论与直觉**不一样**：

| 文件 | 大小 | 结论 | 风险 |
|---|---|---|---|
| `game_config.gd` | 60 KB | ★ **不按域拆**（见下） | high |
| `hud.gd` | 50 KB | 拆两块：`hud_probe`（41 个只读探针）+ `hud_world_overlay` | medium |
| `level_01.gd` | 44 KB | 拆两块：`level_01_tiles`（纯静态、零状态）+ `level_01_gather` | low → medium |
| `player32.gd` | 42 KB | 只拆纸娃娃一块；战斗/受击/移动全留 | medium |
| `game.gd` | 33 KB | 拆 `player_state`（背包/地上/存档）+ `settings_store`，**且放最后** | medium-high |

### 为什么 `game_config.gd` 不按域拆（全场最大文件，却最不该动）

947 行里 40% 是「为什么是这个数」的注释，只有 4 个函数。约束 1 要求
`GameConfig.xxx` 的调用方**零改动**——这是文件头自己的设计前提。拆成
`config/tune/boss.gd` + `config/tune/ui.gd` 之后：

- `GameConfig.boss_core_hp` 要么不存在、要么变成 `GameConfig.Boss.core_hp`，
  后者要改**全工程上百个调用点 + 6 个测试文件**；
- 改成多个 autoload 等于给同一个数建第二个注册名——**直接违反约束 1**；
- `var _ui := preload(...).new()` 门面写法把**解析期报错降级成运行期 null 访问**，
  而本项目最贵的一类 bug 恰恰是静默降级。

> [!tip] 这就是「文件大 ≠ 应该拆」
> 60 KB 里真正可搬的代码只有 21 行（`_ready()` 里的 CLI 解析）。
> 剩下的不是代码坏，是**这一层该有的样子**。

### 推进顺序（每轮可单独提交、单独回滚）

```
第 1 轮  level_01_tiles.gd        ← 无前置，零状态零外部调用者，风险最低
         hud_probe.gd             ← 边界已被三道分隔线画好
第 2 轮  player32_paperdoll.gd    ← 20+ 条断言直接钉住，错了会红
         level_01_gather.gd       ← 唯一风险是 hub 挂不挂，错了 fingerprint 会红
第 3 轮  hud_world_overlay.gd     ← 可选
第 4 轮  player_state.gd          ← 与 use_item/craft/equip 共用 _inventory，回滚成本最高
         settings_store.gd
不排期  cli_args.gd（从 game_config 搬那 21 行）
```

**共通纪律**：新文件**先加不删**，原文件全部保留同名转发，preload 路径零变动。
本方案的落点全在 `ui/` `view/` `game/` `config/`，**没有一个新文件落进 `scripts/sim/`**。

## 八、这次审计的方法论（可复用）

### 一条值得抄的判据

> **「有接口」不等于「接口被用」。**
>
> `cooldowns_snapshot()` 有实现、有测试、有文档，唯独没有生产调用方。

>

> **绿灯本身不证明它在守。**
>
> 本次给 B1 补的守卫，加完之后把 `boss_scale` 故意打回 1.5 跑一遍——

- 静态判定为主，未实机复现 B1 的联机症状（「Boss 确实在追」是从
