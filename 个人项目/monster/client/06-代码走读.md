## 0. 先看全程：客户端的一生也是三幕

```
第一幕 启动（一次性）     --online 参数 → GameConfig → level_01 分岔 → 装配 NetClient → 握手
第二幕 心跳（每一帧）     _process：pump()（IO 五态状态机）→ _drive_self()（输入节拍）→ _apply_world()（画世界）
第三幕 报文（每个包）     字节进来 → 解帧 → 分发 → 快照进缓冲 → 插值采样 → 写进实体
                          （反向）读输入 → 本地预测 → 发包 → 服务器裁决 → 下一包快照对账
```

和服务器（走读 09）一个通天的差别：**服务器的循环是手写的**（`while (g_running)` 累加器补帧），**客户端的循环是引擎给的**（Godot 每帧调 `_process`）——但客户端在 `_process` 里**又手写了一个节拍器**。为什么引擎给的还不够？§2.2 的事故现场就是答案，也是全文最贵的一课。

## 1. 第一幕：启动线

### 1.1 `--online`：一切从一个命令行参数开始

📍 `scripts/config/game_config.gd:938-966`

客户端是**单机游戏长出来的联机功能**（§4.6：联机是并行入口不是替换）。所以整个联机世界由一个开关掀开：

```gdscript
var online_mode: bool = false          # 默认 false：不加参数 = 完全单机，一行网络代码都不跑
var net_host: String = "127.0.0.1"     # 服务器地址（默认本机）
var net_port: int = 7777               # 服务器端口
var net_room: int = 0                  # 房间号
var net_nickname: String = "hunter"    # 昵称
# ……（解析段省略的是对 --host=、--port= 等参数的字符串切分，与主线无关）
if a == "--online":                    # 命令行里出现 --online 才掀开联机
    online_mode = true
```

> 🎓 **新人点拨**：`GameConfig` 是 **autoload**（§0 词汇表）——全局单例。命令行参数在 autoload 的 `_ready` 里用 `OS.get_cmdline_user_args()` 读出来解析，之后全工程任何脚本都能直接写 `GameConfig.online_mode`，不用传引用。代价是它成了全局变量：谁都能改、改了哪都生效——所以本项目纪律是「参数只有一处真相」（约束 1），写它只有启动解析这一处。

> ⚠️ **事故哲学**（`game_config.gd:936-939` 注释原文）：这个开关**必须在 autoload 的 `_ready` 里解析，不能放到关卡的 `_ready` 里**——Godot 的 `_ready` 是**子先父后**（§0 词汇表），关卡的 `_ready` 跑起来的时候，Boss 实体**早在自己的 `_ready` 里把本地 sim（BossAnatomy）建好了**——那时再想「联机、别建本地 sim」就晚了。**开关的解析时机必须早于一切按它分岔的构造**——这和服务器走读 09 §1.4「回调注册必须发生在 Poll 之前」是同一条时序纪律的两副面孔。

**联调**（客户端和服务器连起来调）时的完整命令长这样：`godot --online --host=127.0.0.1 --port=7777`。单机老玩家什么都输入不加，行为与昨天完全一致——这是「并行入口」的物理含义。

### 1.2 `level_01._ready`：单机/联机的分岔口

📍 `scripts/view/level_01.gd:147-148、217-221`

`level_01.tscn` 是打 Boss 的关卡场景。它自己的 `_ready` 里有一个三行的分岔：

```gdscript
if GameConfig.online_mode:          # 联机：挂上装配层
    _setup_online()
# （单机分支：什么都不做——本地 sim 自己管一切，那是 01-sim层领读的世界）

func _setup_online() -> void:
    _online = LevelOnline.new()     # new 一个装配层（scripts/net/level_online.gd）
    _online.name = "Net"
    _online.setup($Entities/Player, $Entities/Boss, $Entities, $Projectiles, _hud_panel)
    add_child(_online)              # 挂进场景树，_ready 随之触发
```

注意 `setup(...)` 传了**五个引用**：本地玩家、Boss、实体容器、弹幕容器、HUD。为什么**先 setup 再 add_child**？——因为 Godot 的 `_ready` 是**子先父后**：`add_child` 的那一刻 `_online._ready` 就开始跑，它要在里面立刻用到这五个引用。先注入再入树，是 Godot 装配层的固定次序（装配层自己也在注释里强调了这一点，`level_online.gd:72`）。

### 1.3 `LevelOnline._ready`：装配——从这一帧起，物理不再说了算

📍 `scripts/net/level_online.gd:82-108`

装配层是**协议层与现有关卡之间唯一的接线点**。它的 `_ready` 干三件事：

```gdscript
client = NetClientScript.new()      # ① 建 NetClient（唯一碰网络 IO 的层）
client.name = "NetClient"
client.enabled = true
add_child(client)                   # 挂进树，它自己的 _process 从此被引擎每帧调用
client.predictor.speed_px_s = GameConfig.player32_speed   # ② 预测参数对齐玩法配置
                                                            #    （约束 1：数值只有一处真相）
_player.set("net_driven", true)     # ③ 本机玩家改由网络驱动——从这一帧起
client.connect_to_server(GameConfig.net_host, GameConfig.net_port,
        GameConfig.net_nickname, GameConfig.net_room, 0)
```

第 ③ 步是整条启动线**最重要的一行**：

> ⚠️ **事故哲学**（`level_online.gd:100-103` 注释原文）：联机模式下**一律不由本地物理驱动玩家**——从挂上这一层的第一帧起。没连上服务器时玩家就是站着不动：「那正是『没有权威就没有位置』，比让本地物理先跑着、连上后再瞬移到出生点诚实得多。」

这句话是整个客户端的**世界观**：单机时代你的位置由本地物理说了算；联机时代位置的唯一来源是服务器。宁可站着不动，也不演一个「假的自己在走」。服务器走读 09 §3.5 讲的「上行只有输入」——就是这句话的另一半：客户端交出了位置的决定权，换来的权利是**自己的输入立刻被本地演出**（§3.4 的预测）。

### 1.4 `NetClient` 的五态状态机：CONNECTING 必须先站好岗

📍 `scripts/net/net_client.gd:42、135-141`

`NetClient` 用一个枚举管住连接的一生：

```gdscript
enum State { DISCONNECTED, CONNECTING, CONNECTED, JOINING, IN_ROOM }
```

连接动作本身只有两行，但藏着本文第一个事故：

```gdscript
func _open() -> void:
    _peer = StreamPeerTCP.new()
    _state = State.CONNECTING      # ★ 先置状态，再发起连接——顺序是故意的
    _peer.connect_to_host(host, port)
```

> ⚠️ **事故现场**（`net_client.gd:137-139` 注释原文）：`StreamPeerTCP.connect_to_host` 是**非阻塞**的——函数返回时连接**还没建立**（TCP 握手要在网络上跑一个来回，§1.5）。不先置 `CONNECTING` 的话，`pump()`（§2.1）会在第一帧就以为「连上了」，然后去发 JoinRoom——**「那是发给空气的」**。症状：连接必然失败，且毫无报错——包发出去了，只是没人收。

> 🎓 **新人点拨**：非阻塞 = 调用立刻返回，「成没成」以后再说。网络世界里几乎所有发起类调用（连接、发送）都是非阻塞的：一次跨网络的往返至少几毫秒，而一帧只有 16ms，不能让你卡在原地干等。**「调用返回 ≠ 事情办成」**是网络编程的第一课，服务器的 epoll（走读 09 §2.2）和客户端的这个状态机，本质都是同一件事的两端：**等通知，别傻等**。

### 1.5 JoinAccept：握手完成，但要「核对面签」

📍 `scripts/net/net_client.gd:269-293`

TCP 连上后（`CONNECTING` → `JOINING`），客户端发 `JoinRoom{protocol_hash, nickname, room_id}`，服务器走完五道关（走读 09 §3.4）回 `JoinAccept`。客户端收到后的处理有两处值得停：

```gdscript
_player_id = r["player_id"]            # 服务器分给你的座位号，此后快照里靠它认领自己
if r["hash"] != Proto.PROTOCOL_HASH:   # ★ 服务器在回包里**回显**了它用的哈希
    push_warning("[net] 服务器协议哈希 0x%08X 与本地 0x%08X 不一致")
predictor.reset(r["spawn"])            # 预测器从出生点起算（§3.4 的主角）
_state = State.IN_ROOM
_reconnect_delay_ms = 1000             # 连上了，把退避计时器归位（§2.1）
joined.emit(r)                         # 广播信号：进房了
```

> ⚠️ **事故哲学**（`net_client.gd:280-282` 注释原文）：JoinRoom 时双方各报各的哈希，一致就放行——但**双方都填了错值时**（比如两边都手写 1234），这个校验仍然通过，「那正是『两边都写 1234』的假校验场景」。所以服务器把哈希**回显**在 JoinAccept 里，客户端核对它：能看到服务器**实际用的**到底是多少。「校验要做真校验」——测「我的配置对不对」和测「对方的配置对不对」是两件事，只测前者会双双裸奔。

> 📖 **教材落点**：这套「握手 + 版本核对 + 拒绝时说人话」就是[[第6章 网络拓扑和游戏案例（讲义）#2. §6.2 权威服务器落地：机器猫行动|第 6 章 §6.2 权威 C/S 架构]]里入会流程的项目落地；「协议哈希不匹配就拒」的取舍（宁可明确拒绝、不做静默兼容）在协议设计里叫 fail-fast，与服务器走读 09 §3.3 的 fail-close 是一家思想。

## 2. 第二幕：心跳线——`_process` 的一圈

启动线走完，引擎每渲染帧调用装配层的 `_process`（`level_online.gd:113-121`），它干三件事：

```gdscript
func _process(delta: float) -> void:
    client.predictor.advance(ms)    # 事一：推进平滑校正（渲染 delta——80ms 的视觉过渡，§3.4）
    if _joined:
        _drive_self(delta, ms)      # 事二：按 tick 节拍发输入 + 本地预测（§2.2-2.3）
    _apply_world()                  # 事三：把服务器广播的世界插值画出来（§3.3）
```

而 IO 的一切（收包、心跳、超时、重连）在 `client` 自己的 `_process` 里，叫 `pump()`。

### 2.1 `pump()`：一帧里做所有 IO

📍 `scripts/net/net_client.gd:163-197`

```gdscript
func pump() -> void:
    if not enabled: return            # 单机上帝开关：enabled=false 时一行 IO 都不跑
    match _state:                     # 按五态分发
        State.CONNECTING:
            _peer.poll()              # 问一次「连接成了吗」——非阻塞调用的「等通知」
            if st == StreamPeerTCP.STATUS_CONNECTED: ...   # 成了 → JOINING + 发 JoinRoom
            elif st == StreamPeerTCP.STATUS_ERROR:
                _fail_now("连接失败（服务器没起？）")
        State.JOINING, State.IN_ROOM:
            _peer.poll()
            _read_available(now)      # 有字节就收（§3.1）
            _tick_clock(now)          # 心跳到点就发（§2.4）
            # 超时判死：JOINING 等 JoinAccept、IN_ROOM 等任何包，都是 5000ms
        _:
            # DISCONNECTED：等退避计时器到点，重连
```

断线重连的策略在 `_fail_now` 里（`net_client.gd:200-208`）：

> ⚠️ **事故现场**：重连延迟是**指数退避**（1s → 2s → 4s → 8s 封顶）。注释原话：「太短会在服务器长时间不可用时疯狂重连（刷日志、占 fd——fd 的解释见服务器走读 09 §2.1），太长会让『服务器刚起来』要等好几秒。」注意「被拒绝」（Rejected）**不重连**（`net_client.gd:300-303`）：拒绝 = 明确失败（版本不对/房间满），重连只会再被拒一次——**退避留给网络故障，不给协议故障**。错误要分类，这个思想服务器走读 09 §3.8 的「错误分四种人」已经讲过，这里是它在客户端的影子。

### 2.2 `_drive_self`：墙钟节拍——全文最贵的一课

📍 `scripts/net/level_online.gd:124-163`

服务器按 20Hz 的 tick 积分移动（走读 09 §3.6），客户端**预测**要和它对上拍，就必须**每 50ms 发一步输入**。这个节拍怎么计？第一直觉是「反正每帧调 `_process`，一帧发一步呗」——**这正是事故本身**：

> ⚠️ **事故现场**（`level_online.gd:126-133` 注释原文，全文最贵的一课）：预测节拍曾挂在渲染帧的 delta 上。headless（无窗口）主循环能跑到 **1700fps**——实测一次 40 秒的验收里**客户端发了 45980 条输入，而服务器只消费 800 步**。预测瞬间甩出去上千像素，然后被硬切拽回来，症状是「角色每 0.1 秒瞬移一次」。有垂直同步的窗口游戏里 60fps 与 20Hz 相差不大，**挂 delta 看不出问题——只在 headless 验收里炸，而 headless 验收恰恰是本项目的证据来源**。修法：节拍走**墙钟**（`Time.get_ticks_msec()`），与服务器「按真实时间积分」同源。

于是 `_drive_self` 里手写了一个**累加器**（`level_online.gd:139-150`）：

```gdscript
var tick_ms := int(Proto.TICK_DT * 1000.0)       # 一个 tick = 50ms（TICK_DT = 1/20 秒）
var due := int((now - _last_tick_ms) / tick_ms)  # 距上次发了几个 tick 的欠账
if due > MAX_CATCHUP_TICKS:                      # 欠账超过 5 拍 → 只补 5 拍，其余丢弃
    due = MAX_CATCHUP_TICKS
    _last_tick_ms = now - MAX_CATCHUP_TICKS * tick_ms   # 节拍对齐到现在
for i in due:
    client.send_input(move, ...)                 # 每欠一拍，发一条输入（+本地预测一步）
```

眼熟吗？**这就是服务器走读 09 §2.3 的固定步长累加器**——「欠几帧还几帧，欠太多宣布破产」。连**上限的数字都一样（5）**、连**动机都一样**：一次 3 秒的卡顿醒来一口气补 60 条输入，「那会把服务器输入缓冲冲爆」（服务器输入环形缓冲只有 8 格，`protocol.gd:182`），玩家还会在画面上瞬移好几米。**宁可丢帧，不可瞬移**——两端用同一个哲学各写了一遍。

> 🎓 **新人点拨**：三个节拍器放在一张桌子上比较——
> | 节拍器 | 谁的 | 步长 | 用在哪 |
> |---|---|---|---|
> | 手写累加器 | 服务器 main.cpp | 50ms 墙钟 | 世界结算 |
> | 手写累加器 | 客户端 `_drive_self` | 50ms 墙钟 | 发输入+预测 |
> | 引擎 `_physics_process` | Godot 内置 | 60Hz 固定 | 单机物理（联机时闲置） |
>
> Godot 其实自带固定步长（`_physics_process`），为什么联机不用它？——因为服务器的 tick 是 **20Hz**，而 `_physics_process` 钉在 60Hz；且引擎节拍的真值随项目设置走，与「必须和服务器逐拍对齐」的硬约束隔了一层。**当你的节拍必须和另一台机器对表时，用自己手写的钟**——这就是 §2.2 事故的全部教训。

### 2.3 `send_input`：先预测，再发包，同一个 seq

📍 `scripts/net/net_client.gd:377-389`

```gdscript
func send_input(move: Vector2, action: int, form: int) -> Vector2i:
    if _state != State.IN_ROOM:      # 还没进房：不发也预测不了，原地返回
        return predictor.pos
    var seq: int = predictor.next_seq()   # 取序号——★必须在发包**前**取
    predictor.step_local(move, seq, action, form)   # ① 本地立即演一步（§3.4）
    _send(MC.encode_player_input(seq, move, action, form))   # ② 发给服务器
    return predictor.pos
```

顺序是硬约束（`net_client.gd:384-386` 注释）：**本地预测与发出去的包必须用同一个 seq**——服务器裁决后，快照对账时靠这个序号对齐「哪条输入对应哪次预测」（§3.4）。`next_seq()` 的注释同样强调「必须在发包前取」，因为先发包后取号的话，发出去的和本地用的就岔开了。

### 2.4 心跳与 `server_tick()`：客户端自己推算「服务器现在第几拍」

📍 `scripts/net/net_client.gd:363-374`

```gdscript
func _tick_clock(now: int) -> void:
    if now - _last_heartbeat_ms >= Proto.HEARTBEAT_INTERVAL_MS:   # 每 1000ms
        _send(MC.encode_heartbeat())    # 发保活包（协议里 Heartbeat 是双向的）
```

心跳是客户端语境的第二个含义（§0 词汇预警）：不是「主循环像脉搏」，而是**每秒一发、证明还活着的包**——和服务器走读 09 §3.3 switch 里那个「只刷活跃时间」的 Heartbeat 是同一种东西的两端。

更有意思的是 `server_tick()`——客户端**并不等服务器告诉它现在第几拍**，而是自己推算：

```gdscript
func server_tick() -> int:
    var elapsed: int = Time.get_ticks_msec() - _server_tick_anchor_ms
    return _server_tick + int(elapsed * Proto.TICK_RATE_HZ / 1000)
    # 上次快照带来的 tick 号 + 本地流逝时间折算的拍数 = 「现在大概第几拍」
```

每收一包快照就校准一次锚点（`_on_world_snapshot`，`net_client.gd:336-338`）。为什么敢推算？——tick 率是协议常量（20Hz，两端都写在 `protocol.gd:178`），服务器按真实时间走，本地时钟推算最多差一个网络延迟，而插值（§3.3）恰恰不需要绝对准、只需要相对顺序对。**「能推算的别等通知」**：等服务器逐包报 tick，就把节拍绑死在网络延迟上了。

### 3.1 到站：`_read_available` 与解帧器

📍 `scripts/net/net_client.gd:223-266` → `scripts/net/frame_codec.gd`

字节到达后先判断流是否可信，再喂给解帧器：

```gdscript
var chunk: Array = _peer.get_data(avail)   # 从 TCP 收 N 个字节（N = 当前可读量）
if err != OK:
    _fail_now("读取错误 %d" % err)          # 读错误 = 流已不可信（对端 RST 等）
                                            # 必须断连，不能在半截字节流上继续攒帧
_dec.feed_all(data, frames2, consumed2)     # 喂解帧器：粘包拆开、半包攒着
if code2 != FC.OK:
    _fail_now("流不可信（帧头非法/超长）—— 已断连")   # 声明长度超 1400 等 → 拒收断连
```

「帧头非法/超长 → 断连而不是跳过」的理由，客户端解帧器注释与服务器说的是同一句话（`frame_codec.gd:17-20`）：**跳过意味着字节流已经错位**——你不知道那一帧的真实边界在哪，后续每一帧都是垃圾，症状表现为「偶发乱码」极难定位。断连是最诚实的处理：让对端重新握手。

`feed_all` 的退出判据是解帧器**最容易写错且错了完全静默**的一行（`frame_codec.gd:191-213` 注释记载了完整复现步骤）：

> ⚠️ **事故现场**：退出条件若写成「字节喂完了就算完」（`off >= n`）——缓冲队列容量 3 时喂 40 个帧：第一轮推完字节、队列塞满 3 帧就停，**环里还压着 37 个完整帧**，而函数已上报「200 字节全处理完」。调用方拿不到、也不报错——**静默丢帧**。实测只还原出 3 帧。正确写法是退出判据**同时看字节和帧**：「还有字节要推 **或** 环里还压得出帧，就再来一轮」（`frame_codec.gd:213` 的 `while off < n or _pending_in_ring()`）。

**职场预演**：「没崩」和「处理完了」是两件事。测试要数**帧数**、要比对**字节**，只断言「不崩」的测试没有牙齿（本文件注释里还有一节「变异自证」讲怎么验证测试有牙齿，§4 习惯 9 展开）。

### 3.2 `_dispatch`：未知消息号——客户端忽略，服务器判死

📍 `scripts/net/net_client.gd:269-333`

分发的 match 与服务器走读 09 §3.3 的 switch 长得像，但结尾**相反**：

```gdscript
match msg:
    Proto.MSG_JOIN_ACCEPT: ...       # 解码 → 校哈希 → IN_ROOM（§1.5）
    Proto.MSG_WORLD_SNAPSHOT: ...    # 解码 → WorldProxy.push + 校正自己（§3.3-3.4）
    Proto.MSG_BOSS_EVENT: ...        # 解码 → 翻译成表现（部位破坏/受击/击杀，§3.6）
    Proto.MSG_HEARTBEAT:
        pass                         # 收到即证明连接活着，别的什么都不做
    _:
        pass                         # ★ 未知消息号：忽略，不断连
```

服务器的 `default` 是**判死**（「表外消息号，一律断开」），客户端的 `_` 是**忽略**。为什么两端纪律相反？——**角色不同**（`net_client.gd:331-333` 注释原话）：「未知消息号：忽略而不是断连。**协议向前兼容靠这一条**——新版服务器加的消息不该让旧客户端掉线。」服务器面对的是「可能恶意构造任意字节」的外部输入，必须 fail-close（走读 09 §3.3）；客户端面对的是「服务器升级了、多了个新消息」的正常世界，忽略它才能继续玩。

> 📖 **教材落点**：这正是[[第6章 网络拓扑和游戏案例（讲义）#2. §6.2 权威服务器落地：机器猫行动|第 6 章 §6.2]]里「谁是权威，谁定纪律」的微观呈现——权威端（服务器）的默认动作是拒绝，被服务端（客户端）的默认动作是容忍。把两端写反了，服务器会被一个畸形包打死，客户端会因为服务器的一个新字段全员掉线。

### 3.3 快照下行：WorldProxy 的 200ms 延迟插值

📍 `scripts/net/world_proxy.gd`——客户端表现层的核心，也是事故密度最高的一节

快照 10Hz = 每 100ms 一包。**直接播会一顿一顿**（每 100ms 跳一次位置）。办法是**延迟约 200ms 渲染**：永远渲染「200ms 之前」的世界，这样手上通常有前后两包，可以在中间平滑地插值（§0 词汇预警：插值 = 两帧之间取中间值）。为什么是 200？——10Hz 的间隔 100ms × 2 = 200ms，是**公式下限**：调低就没有两帧可插，画面会抖（`world_proxy.gd:7-9`，教材 §9.1 的原话）。

**第一道工序：收包入缓冲**（`push`，`world_proxy.gd:85-99`）——`server_tick` 不比上一包新的直接丢（TCP 保证有序，重复/乱序只可能来自网络条件模拟器的刻意注入），缓冲上限 16 帧（1.6 秒），超了丢最老的。

**第二道工序：采样**（`sample`，`world_proxy.gd:142-169`）——渲染时刻 = 当前推算 tick − 4 拍延迟，然后找「渲染时刻落在哪两帧之间」，算出插值进度 t。这里有两起真实事故：

> ⚠️ **事故现场 ①**（`world_proxy.gd:114-119`）：找帧的比较对象曾写成「这一帧的 tick ≤ 延迟拍数（4）」而不是「≤ 渲染时刻」。前者**恒假**，于是永远返回第 0 帧，画面变成「第 0 帧与第 1 帧之间永恒地插值」——**看起来在动，完全没跟着时间走**，延迟与外推两条路径的测试都验不出来。
> **事故现场 ②**（`world_proxy.gd:160-168`）：插值进度 t 曾按 `cur_tick` 算而不是按「渲染时刻」算。由于 a 本来就是按渲染时刻选出来的，渲染时刻正好落在 a 上时这个差值恒等于延迟拍数，t 被 clamp 成 1.0——**每帧都取到下一帧，200ms 延迟形同虚设**，而画面照样「在动」。实测渲染 tick = 138 而非 136 才暴露。
>
> 两起事故的共同点：**画面看起来都正常**。插值代码的 bug 不会让游戏崩，只会让「平滑」悄悄变成「假的平滑」——这就是为什么这两个函数的注释比代码还长。

**第三道工序：兜底**（`_extrapolate`，`world_proxy.gd:172-222`）——渲染时刻越过了最新一帧（丢包了）怎么办？沿最近两帧的速度**继续猜一小段**，硬上限 200ms；超过就**冻结**在最后一帧。注释里那句教材原话值得抄在工位上：「必须有上限——**无上限外推比卡住更糟**」。这里还埋着第三个事故：`interpolation_delay_ms` 和 `max_extrapolation_ms` **都是 200**，外推量若按 `cur_tick` 算，只要进了外推分支就必然已经跑满上限，「那 200ms 的外推区间形同虚设」——所以外推量必须按**渲染时刻**算（延迟 200 与外推上限 200 是**两件不同的事**）。另有一次 a/b 两帧传反，位置往回退（实测 x 从 40 退到 30）——**外推变成了倒放**。

**离散量不插值**（`_blend`，`world_proxy.gd:225-243`）：位置是连续量可以插；朝向、状态、部位血量是**离散量**，取「离渲染时刻更近的那一帧」——「插值一个部位状态（0/1）会得到 0.5 这种不存在的状态」，UI 会显示 0.4999 血这种没意义的数。

采样结果里带着两个数——`server_tick`（插值出来的**渲染** tick，四舍五入到帧间位置）和 `interp_t`（插值进度 0-1000）。记住它们，§3.5 里它们就是 HitReport 的「回退键」。

### 3.4 自己的位置：预测、校正、补间——「平滑有边界」

📍 `scripts/net/player_predictor.gd`——§2.3 里「先预测再发包」的另一半

**为什么预测**：输入发出到快照回来至少一个往返（几十到几百毫秒），照服务器权威值演就是「按键之后角色隔一拍才动」——手感稀碎。所以**自己这一行，客户端是权威**（教材 §7.1 的 Authority 角色表）：按下方向的**当帧**本地就演一步，服务器稍后对账。

**预测的铁律：与服务器逐位一致**（`player_predictor.gd:14-24`）：

```gdscript
var speed: float = speed_px_s * (roll_speed_mult if action == Proto.ACTION_ROLL else 1.0)
var step: float = speed * Proto.TICK_DT          # dt 必须是服务器 tick 的 dt（50ms），
                                                  # 不是渲染帧的 delta（§2.2 的教训）
var nx: int = pos.x + _round_half_away_from_zero(move.x * step)
pos = Vector2i(clampi(nx, 0, map_size.x), clampi(ny, 0, map_size.y))   # 与服务器同一口径
```

> ⚠️ **事故哲学**（`player_predictor.gd:14-21` 注释原文）：预测与服务器积分**只要差一点点，校正就变成永不停歇的抖动**——角色每 tick 被往回拽一点、又立刻被预测推出去，表现为「人物持续轻微抽搐」，而日志里一切正常。所以连**取整口径**都要两端摆在明面上：服务器用 `std::lround`（half away from zero），客户端显式写一个同名函数 `_round_half_away_from_zero`，「避免『两边都以为对方取整方式一样』」。
> 📖 **教材落点**：这就是服务器走读 09 §3.6「遍历顺序也是协议的一部分」的镜像命题——**跨端重复实现的逻辑，逐位一致本身就是契约**。顺序、取整、clamp 边界（客户端注释特意写明「上界取 w/h 本身而不是 w-1」，与服务器同口径），任何一处漂移都会以抽搐的形式出现在玩家屏幕上。

**校正三模式**（`apply_authoritative`，`player_predictor.gd:188-225`）：每包快照到达，拿**自己那一条**权威位置对账——

| 偏差 | 动作 | 理由 |
|---|---|---|
| > 96px（hard_cut_px） | **硬切**：立刻跳到目标 | 「偏差大不是抖动，是真的错了，再『平滑』就是撒谎」 |
| 0.5px ~ 96px | **平滑**：80ms 内匀速拉回 | 小偏差是网络波动，硬切会看得见 |
| ≤ 0.5px | **不动** | 「动了只会引入抖动」 |

对账前还有一道**过期丢弃**：协议里没有 ack_seq 字段（「服务器不允许等待客户端」——§7.2 红线 1，快照是全量的、不带「这是第几条输入的结果」），所以 `net_client` 调 `apply_authoritative(pos, **-1**)`——传 -1 表示「不知道」，**不过滤**。这是个**已知缺口**，注释原话（`net_client.gd:350-352`）：「宁可校正一次也别让玩家卡在旧位置。这是已知缺口，在报告里写明。」——**把缺口写出来，比假装没有强一万倍**。

**渲染层「一律补间」**（`level_online.gd:152-163`）：预测器对大偏差是**立刻**改 `pos` 的（硬切），但渲染层**不跟着硬对齐**——那一次纠正会在画面上变成 150px 的瞬移（「实测过」）。所以渲染位置 `_render_pos` 永远用一个时间常数（一拍）向目标 `lerp`（线性插值追赶），不分叉。副作用也如实记录：服务器真把玩家传送时（将来的复活），客户端会**滑过去**而不是跳过去——「滑比跳更符合手感下放的取舍」。

> ⚠️ **对照记忆**：§2.2 的补帧上限、§3.3 的外推上限、这里的「一律补间」——三个不同的函数，同一个哲学：**任何纠正都要么平滑、要么有上限，永远不瞬移**。你以后写表现层代码，凡是「把一个值改成另一个值」的地方，先问一句：这一步在屏幕上是滑过去的，还是跳过去的？

### 3.5 HitReport 上行：回退键的诞生

📍 `scripts/net/level_online.gd:382-394` → `scripts/net/net_client.gd:399-404`

小明挥刀砍中 Boss 的翅膀（客户端本地判定命中——**判定可以 locally 做，落地必须服务器裁**），客户端上报：

```gdscript
func _on_net_hit(part: String, damage: int, skill_id: int) -> void:
    var idx := GameConfig.BOSS_PARTS.find(part)   # 部位名 → 协议编号（同序是硬要求）
    if not _sample.get("ok", false):
        return                        # 还没收到任何快照，回退键不存在：这一发丢掉
    client.report_hit(idx, damage, int(_sample["server_tick"]),
            int(_sample["interp_t"]), skill_id)
```

上报带的 `(snapshot_tick, interp_t)` 正是 §3.3 采样结果的两个数——**「玩家正看着的那一帧」**。服务器收到后按它**回退**到那一刻的 Boss 位姿再裁决（服务器走读 09 §3.8 的「明明砍中了，服务器说没打中」事故），两边在协议层面严丝合缝地咬合上了：**客户端负责描述「我看见了什么」，服务器负责核实「那时到底中没中」**。这一对字段，就是教材第 8 章延迟补偿在两端各留的那半把钥匙。

> 📖 **教材落点**：[[第8章 改进的延迟处理#8.4 服务器端回退：把世界退回到扣扳机的那一刻|教材第 8 章 §8.4 服务器端回退]]——服务器往回看的那个「那一刻」，由客户端在 [[代码走读#3.8 支线：`HitReport` 与回退——为什么「明明砍中了，服务器说没打中」|服务器走读 §3.8]]的裁决入口交付。

还有一个 GDScript 特有的语法坑值得记住（`net_client.gd:395-398` 注释）：`report_hit` 的 `skill_id` 参数**没有默认值**——「GDScript 的默认参数只接受**常量表达式**，`= Proto.SKILL_NONE` 会让整个文件编译失败」（preload 常量不算常量表达式）。线格式还没有这个字段，参数先留着是为了调用方单一路径，T10 补字段时不必回头改调用点——**为将来留口子，但口子要带说明**。

### 3.6 血量对账：「摆上服务器的值」，不是回滚

📍 `scripts/net/level_online.gd:226-244`

快照里自己那一条还带 `hp`（14 字节 PlayerNet 结构的尾部字段）。客户端把它反归一化后灌进本地血条：

```gdscript
func _reconcile_self_hp(p: Dictionary) -> void:
    var max_hp := float(GameConfig.player32_max_hp)
    if max_hp <= 0.0:
        return                        # 配置没就位就什么都不做（fail-closed：不猜一个默认值）
    _player.call("sync_hp_from_authority",
            MC.denormalize_hp(int(p["hp"]), max_hp))   # 归一化值 × 本地 max_hp = 真血量
```

三点说明（`level_online.gd:229-237` 注释原文概括）：**①** 这不是「预测 + 回滚」——联机时客户端一拍 Boss 逻辑都不跑（§1.3 的权威边界），本地血量在快照到达前一直是满的，这里是「摆上服务器的值」；**②** 没有为它新增任何协议字段——`hp` 本来就在广播里，「它一直是**发出来但不用**的」，退役 C2S_PlayerState（服务器走读 09 §3.3 的退役消息）后这个字段接上了班；**③** 反归一化用**客户端本地配置**的 max_hp（协议线上只传归一化值——服务器走读 09 §3.7 的 98 字节里有它），两端 max_hp 一致由配置核对文件钉住。

Boss 的血量与部位走同一条路（`_apply_boss`，`level_online.gd:248-273`）：快照的 `core_hp`/`parts` 反归一化灌进 Boss 实体，快照里 `state` 字段驱动攻击特效——注释记载它「以前没人读」，缺了这行的症状是「新攻击在联机里**完全没有特效**，而服务器照样在扣血：**被看不见的攻击打了**」。

## 4. 这份代码教你的职场习惯

全部来自源码注释的真实记载，挑客户端侧最值钱的十条：

1. **节拍必须与权威同源**。跟另一台机器对表的事，用墙钟，不用本地随便什么 delta（§2.2 的 45980 条输入）。
2. **「调用返回 ≠ 事情办成」**。非阻塞世界里一切都是「发起 + 等通知」，状态机就是为这个生的（§1.4）。
3. **校验要做真校验**。「两边都写 1234」的哈希必然通过——要核对对方**实际用的**值（回显面签，§1.5）。
4. **谁的角色，定谁的纪律**。服务器面对恶意输入：default 判死；客户端面对版本演进：未知号忽略。照抄任何一端都是错的（§3.2）。
5. **逐位一致是设计出来的，不是巧合**。取整口径、clamp 边界、dt 取值，两端都摆在明面上同名同义（§3.4）。
6. **任何纠正都要么平滑、要么有上限**。硬切只留给「真的错了」，平滑只给小偏差，「一律补间」拒绝瞬移（§3.4）。
7. **退出判据要同时看两个维度**。只看「字节喂完」会静默丢 37 帧——「没崩」不等于「处理完了」（§3.1）。
8. **已知缺口写进代码**。ack_seq 传 -1 是个缺口，注释原话「在报告里写明」——缺口不可怕，装没有才可怕（§3.4）。
9. **测试要有牙齿**。frame_codec 注释里的「变异自证」：故意把小端改成大端看测试红不红——第一次改错了写法（位或可交换），**全套测试全绿**，那是个假变异；真正改变语义的变异实测 35 处失败。「一个没有真的改变语义的变异，会让你误以为测试有牙齿」（`frame_codec.gd:145-151`）。
10. **读协议的那份和写协议的那份，不能是同一份代码**。客户端解帧器是服务器 FrameDecoder 的**独立实现**，不是拷贝——同一份代码的两端，会把共同的 bug 一起带到线上还互相验证「没问题」（`frame_codec.gd:8-10`）。
