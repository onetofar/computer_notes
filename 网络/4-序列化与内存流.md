> [!info] 核心结论
> **不能把对象的内存块直接 `send` 出去。** 一个带虚函数、指针、`vector` 的类，
> 按字节复制会同时破坏三样东西：**vtable 指针、指针域、`vector` 的内部结构**。
> 解法不是「给每个字段发一个包」（那会浪费包头带宽、打乱连接），
> 而是**把对象的每个字段按顺序写进一个自己管理的缓冲区**，再把缓冲区当整体发出去。
> 这个缓冲区就是**流**——它同时是「序列化」和「网络发送」之间的解耦层。

## 机制

### 一、序列化要解决什么（§4.1）

序列化 = **把对象从内存中的随机访问格式转换为比特流格式**。
这些比特流可以存硬盘、可以走网络，之后再恢复成原始格式。

**天真做法与它为什么在简单情况下能用：**

```cpp
void NaivelySendRoboCat(int inSocket, const RoboCat* inRoboCat)
{
    send(inSocket,
        reinterpret_cast<const char*>(inRoboCat),
        sizeof(RoboCat), 0 );
}

void NaivelyReceiveRoboCat(int inSocket, RoboCat* outRoboCat)
{
    recv(inSocket,
        reinterpret_cast<char*>(outRoboCat),
        sizeof(RoboCat), 0);
}
```

`sizeof(RoboCat)` 在这个例子中是 **8**（两个 `int32_t`）。

**表 4.1　示例 RoboCat 的内存布局**

| 地址 | 字段 | 源主机取值 | 目的主机初始值 | 目的主机最终值 |
|---|---|---|---|---|
| Bytes 0—3 | `mHealth` | `0x00000005` | `0x0000000A` | `0x00000005` |
| Bytes 4—7 | `mMeowCount` | `0x00000002` | `0x00000003` | `0x00000002` |

传输三步：①源主机调 `NaivelySendRoboCat`；②目的主机**创建或找到一个已存在的 RoboCat** 来接收状态；③目的主机调 `NaivelyReceiveRoboCat` 传入那个指针。
第 5 章会展开第 ② 步。**前提是两台主机运行在相同硬件平台上。**

### 二、真实类会坏在哪（§4.1）——本节的核心

更实际的 RoboCat 多了虚方法、指针、字符数组、`vector`：

```cpp
class RoboCat: public GameObject
{
public:
    RoboCat(): mHealth(10), mMeowCount(3), mHomeBase(0)
    {
        mName[0] = '\0';
    }
    virtual void Update();

    void Write(OutputMemoryStream& inStream) const;
    void Read(InputMemoryStream& inStream);

private:
    int32_t                 mHealth;
    int32_t                 mMeowCount;
    GameObject*             mHomeBase;
    char                    mName[128];
    std::vector<int32_t>    mMiceIndices;
};
```

**表 4.2　内存中的一个复杂 RoboCat**

| 地址 | 字段 | 源主机取值 | 目的主机初始值 | 目的主机最终值 |
|---|---|---|---|---|
| Bytes 0—3 | `vTablePtr` | `0x0A131400` | `0x0B325080` | `0x0A131400` |
| Bytes 4—7 | `mHealth` | `0x00000005` | `0x0000000A` | `0x00000005` |
| Bytes 8—11 | `mMeowCount` | `0x00000002` | `0x00000003` | `0x00000002` |
| Bytes 12—15 | `mHomeBase` | `0x0D124008` | `0x00000000` | `0x0D124008` |
| Bytes 16—143 | `mName` | “Fuzzy\0” | “\0” | “Fuzzy\0” |
| Bytes 144—167 | `mMiceIndices` | ?????? | ?????? | ?????? |

**问题 1 · 虚函数表指针被重写。**
RoboCat 开头 4 个字节现在是虚函数表指针（**32 位系统；64 位系统上应该是 8 个字节**）。
因为有虚方法 `RoboCat::Update()`，每个实例都要存一个指向虚方法实现表位置的指针。
**那张表的位置在每个实例的进程中都不一样。**
直接把收到的状态写进目标 RoboCat，会把正确的 vtable 指针**改写成错误的**。
之后目标 RoboCat 调 `Update()`，原文给的两种结局是：
**最好的情况是出现内存访问异常，最坏的情况是导致调用随机位置的代码。**

**问题 2 · 指针域被重写。**
`mHomeBase` 有同样的问题。原文的定义：
**「指针，就其本质而言，指的是一个特定进程的内存空间中的一个位置。**
**盲目地从一个进程复制一个指针域到另外一个进程，同时希望这个指针引用目标进程相关的数据是不安全的。**」
鲁棒的代码必须**复制相关的数据并让指针域指向复制出来的数据**，
或者**在目标进程中找到已经存在的数据并让指针域指向那里**（§4.3 讨论）。

**问题 3 · 不必要的数据也被复制。**
`mName` 有 128 字节，但 RoboCat 例子中只等于 “Fuzzy”。
原文的要求：**好的序列化系统应该在可能的情况下避免序列化不必要的数据**
——需要系统知道 `mName` 是以 null 结尾的 C 字符串，
**仅仅序列化包含 null 在内的字符即可**。（§4.4 会展开这类压缩技术。）

**问题 4 · `vector` 是黑匣子。**
**STL 中 `vector` 类的内部结构在 C++ 标准中没有详细的定义**，
所以不清楚从进程 A 直接复制这个字段的内存到进程 B 是否安全。
原文的判断是**十有八九是不安全的**：内部可能存在指向元素的一个或多个指针，
且这些指针在设置后**必须运行初始化代码**。
推广开来——**可以假设简单的序列化在复制任何黑匣子数据结构时都会失败**，
因为内部没有被详细说明，按位复制不安全。

**由这四条得到的结论**：**不应该给 socket 发送一个单独的 RoboCat 二进制数据块，
而是应该每个字段单独序列化。**
但**不能给每个字段创建一个数据包**——原文给的理由是那样会
**导致网络连接的混乱，为不必要的包头数据浪费带宽**。
正解是：**收集所有相关数据到一个缓冲区，然后把该缓冲区作为该对象的代表发送。**
→ 引出「流」。

### 三、流是什么（§4.2）

**流（stream）= 封装了一组有序数据元素、允许对其读写的接口。**

- **输出流**（output stream）：用户数据的输出槽，**只顺序插入、不能读**。
- **输入流**（input stream）：数据源，**只顺序提取、不能插入**。
- 两者兼有时，插入和读取都提供。

原文举的两个例子点出了流的本质——**流通常是别的数据结构或计算资源的接口**：
**文件输出流**封装一个已打开准备写的文件；
**网络流**封装一个 socket，提供 `send()` / `recv()` 的封装，专用于用户相关的特定数据类型。

### 四、输出内存流（§4.2.1 · 清单 4.1）

**输出内存流**封装内存缓冲区（通常是动态分配的）。
它提供顺序写入的方法，**同时提供对缓冲区本身的只读访问器**——
通过访问器，用户可以立即把全部数据交给别的系统，比如 socket 的 `send`。

```cpp
class OutputMemoryStream
{
public:
    OutputMemoryStream():
    mBuffer(nullptr), mHead(0), mCapacity(0)
    {ReallocBuffer(32);}
    ~OutputMemoryStream()    {std::free(mBuffer);}

    //get a pointer to the data in the stream
    const    char*    GetBufferPtr()    const    {return mBuffer;}
              uint32_t  GetLength()      const    {return mHead;}

    void      Write(const void* inData, size_t inByteCount);
    void      Write(uint32_t inData) {Write(&inData, sizeof( inData));}
    void      Write(int32_t inData)  {Write(&inData, sizeof( inData));}

private:
    void      ReallocBuffer(uint32_t inNewLength);

    char*     mBuffer;
    uint32_t  mHead;
    uint32_t  mCapacity;
};

void OutputMemoryStream::ReallocBuffer(uint32_t inNewLength)
{
    mBuffer = static_cast<char*>(std::realloc( mBuffer, inNewLength));
    //handle realloc failure
    //...
    mCapacity = inNewLength;
}

void OutputMemoryStream::Write(const void* inData,
                               size_t inByteCount)
{
    //make sure we have space...
    uint32_t resultHead = mHead + static_cast<uint32_t>(inByteCount);
    if(resultHead > mCapacity)
    {
        ReallocBuffer(std::max( mCapacity * 2, resultHead));
    }

    //copy into buffer at head
    std::memcpy(mBuffer + mHead, inData, inByteCount);

    //increment head for next write
    mHead = resultHead;
}
```

`Write(const void*, size_t)` 是**基本方法**；重载版本替调用者决定字节数。
原文建议：**建立一个辅助函数来自动选择字节数，有助于防止因用户输入不正确的字节数而导致的错误。**

如果改用模板，还要**防止非基本类型被序列化**——静态断言是一种安全做法：

```cpp
template<typename T> void Write(T inData)
{
    static_assert(std::is_arithmetic<T>::value ||
                    std::is_enum<T>::value,
                    "Generic Write only supports primitive data types");
    Write(&inData, sizeof(inData));
}
```

**扩容策略（原文）**：每当空间不够，缓冲区自动扩展为
**当前容量的两倍**和**容纳新数据所需空间**两者中的最大值——
代码即 `std::max(mCapacity * 2, resultHead)`。
原文称这是一种常见的内存扩展技术，**倍数可按目的调整**。

> **警告（原文）**：
> 尽管 `GetBufferPtr` 提供了对内部缓冲区的只读指针，**流仍然保留缓冲区的所有权**。
> **一旦流被释放，指针就无效了。**
> 如果需要该指针在流释放后仍可用，缓冲区可以用
> `std::shared_ptr<std::vector<uint8_t> >` 实现——**原书把这条留作本章末尾的练习题。**

### 五、把字段写进流（§4.2.1）

```cpp
void RoboCat::Write(OutputMemoryStream& inStream) const
{
    inStream.Write(mHealth);
    inStream.Write(mMeowCount);
    //no solution for mHomeBase yet
    inStream.Write(mName, 128);
    //no solution for mMiceIndices yet
}

void SendRoboCat(int inSocket, const RoboCat* inRoboCat)
{
    OutputMemoryStream stream;
    inRoboCat->Write(stream);
    send(inSocket, stream.GetBufferPtr(),
            stream.GetLength(), 0);
}
```

给 RoboCat 加 `Write` 的收益，原文说了两条：
**①能访问私有的内部字段；②把序列化任务从网络发送任务中抽象出来。**
后者让调用者能把一个 RoboCat 当作「众多元素中的一种」写入流——
复制多个对象时很有用（§5 展开）。

### 六、输入内存流与接收（§4.2.1 · 清单 4.2）

```cpp
class InputMemoryStream
{
public:
    InputMemoryStream(char* inBuffer, uint32_t inByteCount):
    mCapacity(inByteCount), mHead(0)
    {}

    ~InputMemoryStream()   {std::free( mBuffer);}

    uint32_t GetRemainingDataSize() const {return mCapacity - mHead;}

    void     Read(void* outData, uint32_t inByteCount);
    void     Read(uint32_t& outData)  {Read(&outData, sizeof(outData));}
    void     Read(int32_t& outData)   {Read(&outData, sizeof(outData));}

private:
    char*    mBuffer;
    uint32_t mHead;
    uint32_t mCapacity;
};

void RoboCat::Read(InputMemoryStream& inStream)
{
    inStream.Read(mHealth);
    inStream.Read(mMeowCount);
    //no solution for mHomeBase yet
    inStream.Read(mName, 128);
    //no solution for mMiceIndices
}

const uint32_t kMaxPacketSize = 1470;

void ReceiveRoboCat(int inSocket, RoboCat* outRoboCat)
{
    char* temporaryBuffer =
        static_cast<char*>(std::malloc(kMaxPacketSize));
    size_t receivedByteCount =
        recv(inSocket, temporaryBuffer, kMaxPacketSize, 0);

    if(receivedByteCount > 0)
    {
        InputMemoryStream stream(temporaryBuffer,
                static_cast<uint32_t>(receivedByteCount));
        outRoboCat->Read(stream);
    }
    else
    {
        std::free(temporaryBuffer);
    }
}
```

流程：创建临时缓冲区 → `recv` 填充 → **把缓冲区的所有权转交给输入内存流**
→ 流用户**按写入顺序提取**数据元素，`RoboCat::Read` 负责塞进对应字段。

`kMaxPacketSize = 1470` 是个具体数字。

> **小窍门（原文）**：
> 整个游戏采用这种模式时，**你不会每次数据包到达都为流分配内存，因为内存分配很慢**。
> 而是有**一个预分配的最大尺寸的流**，每当数据包到达就直接接收到该预分配流的缓冲区，
> **读完并处理完数据后把 `mHead` 设回 0**，这样下一个包到达时流已经就绪。
> 做法是给 `InputMemoryStream` 加功能让它管理自己的内存：
> 以最大容量为参数的构造函数分配 `mBuffer`，再返回一个 `mBuffer` 访问器，
> 让缓冲区能被直接传给 `recv`。

### 七、流解决了第一个问题

原文的收束句：流提供了一种简单方法来**创建缓冲区、用源对象各字段的值填充缓冲区、
发送缓冲区、顺序提取数据、插入到目标对象合适字段**——
**而且这个过程没有干扰到目标对象中不应该被改变的任何字段，例如虚函数表指针。**

## 作者省略的前提

> [!note] 本节是补出来的，不在原文里。

- **「两端同硬件平台」这个前提有多重？** 至少三层，§4.1 只说了第一层：
  ①**字节序**（§4.2.2 会正式讲）；②**类型宽度**——`int32_t` 之所以安全是因为它
  名字里就写死了 32 位，若换成 `int`/`long`，同一份源码在两个平台宽度可能不同；
  ③**指针宽度与 vtable 布局**（原文提了 32/64 位差异，但没说这会让表 4.2 的偏移全变）。
- **`GetBufferPtr()` 返回的指针为什么不能存着晚点用**（原文警告给了结论没给场景）：
  典型踩法是 `std::vector<const char*> pkts; pkts.push_back(stream.GetBufferPtr());`
  然后发出去——**第一个包就可能指向已释放内存**。正确做法是**发完立刻拷走**，
  或者按警告里说的改用 `shared_ptr` 持有所有权。
- **`send` 的返回值没被检查**（原文两个示例都漏了）：
  TCP 下 `send` 可能只发出一部分（返回小于请求长度），也可能因缓冲区满返回 −1。
  **直接把 `GetLength()` 当作已发送量是错的**，需要循环推进偏移量。

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 只写基本类型（arithmetic / enum） | `Write` 模板可安全泛化 | 必须为每个自定义类型手写 `Write`/`Read` |
| 字段顺序在两端**完全一致** | 顺序提取能对上 | 读出来全是垃圾，且**不会报错** |
| 不把指针 / 容器按位复制 | 目标对象的 vtable、指针域不被破坏 | 内存异常或调用随机代码（§4.1） |
| 发送缓冲区在 `send` 返回前保持有效 | 数据正确 | 流析构后指针悬空（`GetBufferPtr` 警告） |

## 与原文的出入

| 类型 | 原文说 | 实际应为 | 依据 |
|---|---|---|---|
| **正文与代码矛盾** | §4.1：「需要序列化系统知道 `mName` 字段是一个以 null 结尾的 C 字符串，**仅仅序列化包含 null 以内的字符即可**」 | 清单 4.1 里的 `RoboCat::Write` 实际是 `inStream.Write(mName, 128);`——**仍然全量写 128 字节**，优化没有落实 | §4.1 正文 vs §4.2.1 清单。照抄这段代码得不到正文承诺的带宽收益，要省字节必须自己改成写 `strlen(mName)+1` |
| **代码缺陷** | 清单 4.2 的 `InputMemoryStream(char* inBuffer, uint32_t inByteCount)` 只在初始化列表里设了 `mCapacity` 和 `mHead` | **`mBuffer` 从未被赋值为 `inBuffer`**；而析构函数 `std::free(mBuffer)` 会 **free 一个未初始化指针** | 清单 4.2 原文代码。构造函数应补 `mBuffer(inBuffer)`；另外所有权已转交给流，就不该在析构里 `free`（那是 `ReceiveRoboCat` 的 `else` 分支在做的事） |
| **表述不严谨** | §4.1：`vector` 内部「可能存在**一个或多个指针**指向元素」 | 标准只保证 `vector` 的**拷贝语义**，不保证布局；能不能按位复制取决于**具体标准库实现**，不是「有没有指针」 | C++ 标准未规定 `vector` 的对象表示；任何 libstdc++/MSVC 布局都可能不同 |

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| **不要按内存块发送，每个字段单独序列化** | **已在用** | `otf-server/src/proto/protocol.h` 用 `wire::kXxxPayload` 常量逐条声明每个消息的**定长字节数**（如 `kHitReportPayload = 13`）与字段构成，**不出现任何 `sizeof(对象)`** |
| 缓冲区可复用、避免每包分配 | **尚未实现** | `main.cpp` 目前只写帧头（`kFrameHeaderSize = 4`），payload 编解码还没落地；将来落地时应按 §4.2.1 的小窍门预分配 + 复位，而不是每包 `malloc` |
| `kMaxPacketSize = 1470` | **同量级不同值** | 本项目是 `kMaxPayloadSize = 1400`，注释「单帧不触发 IP 分片」——比原书小 70 字节，给帧头和封装留了余量 |
| **本项目尚无「流」抽象** | **架构取舍，非疏漏** | 现在的做法是「消息级定长 payload」而不是「字段级流」：`wire::` 只给出**字节数**，编解码代码待写。字段少时这更省事，**但一旦某个消息要带变长数据（字符串、列表），就必须引入流** —— 这一点 §4.2.1 已经给出答案 |
| 帧头注释写明「小端」 | **潜在隐患** | `protocol.h` 帧格式注释标了「小端」。这只在**两端同架构同字节序**时成立；这正是 §4.2.2 要解决的问题，**跨架构部署前必须补 `htons`/`ntohs` 或显式移位** |
