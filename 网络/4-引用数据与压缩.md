> [!info] 核心结论
> **两个问题，两个判据。**
>
> **引用数据**：数据**完全由这个对象拥有** → **嵌入**（写内容）；
> 数据**被多个指针共享** → **链接**（写 network ID）。
> 判错的后果不对称：共享数据用嵌入会**生成多份副本**，反向引用用嵌入会**无限递归直到堆栈溢出**。
>
> **压缩**：诀窍是**去掉不需要通过网络发送的信息**，靠的是「利用平均情况」。
> 三条递进路线：**稀疏容器只写实际长度 → 高频取值用 1~2 bit 标识 → 定点压缩把范围映射成整数**。
> 每一步都要求你**先跟设计师问出真实范围和精度**，否则无从下手。

## 机制

### 一、引用数据是内存流的死穴（§4.3）

内存流能处理各种基本数据和 POD，**但在需要处理通过指针或其他容器引用的间接数据时将会崩溃**。
RoboCat 在本章又长出了两个成员：

```cpp
class RoboCat: public GameObject
{
    ...
private:
    int32_t             mHealth;
    int32_t             mMeowCount;
    GameObject*         mHomeBase;
    char                mName[128];
    std::vector<int32_t> mMiceIndices;

    Vector3             mPosition;
    Quaternion          mRotation;
};
```

**两个成员是当前内存流实现不能序列化的：`mHomeBase` 和 `mMiceIndices`。**
每个都需要一种不同的序列化方法。

### 二、内联 / 嵌入：数据完全属于你（§4.3.1）

`mMiceIndices` 是一个整型 `vector`，跟踪 RoboCat 感兴趣的老鼠索引。
**因为 `std::vector<int>` 是一个黑匣子，用标准 `OutputMemoryStream::Write`
从它的地址复制到流中是不安全的**——结果是**把 `vector` 里所有指针的值也序列化了过去**，
在远程主机反序列化时将指向错误的地方。

**正确的做法：只写 `vector` 所包含的数据，而不是序列化 `vector` 本身。**

原文对这个机制的解释：**RAM 中的数据可能实际上与 RoboCat 本身的数据相差很远**；
但**自定义函数序列化它时，会把数据嵌入到 RoboCat 中一起写入流**——
所以这个过程被称为**内联（inlining）或嵌入（embedding）**。

```cpp
void Write(const std::vector<int32_t>& inIntVector)
{
    size_t elementCount = inIntVector.size();
    Write(elementCount);
    Write(inIntVector.data(), elementCount * sizeof(int32_t));
}
```

**第一步必须是长度。** 原文的理由：**这样对应的 `Read` 方法在反序列化内容之前，
可以使用它来给 `vector` 分配合适的空间。**
因为只含基本类型，这里用 `memcpy` 一次写完；复杂类型则逐元素：

```cpp
template<typename T>
void Write(const std::vector<T>& inVector)
{
    size_t elementCount = inVector.size();
    Write(elementCount);
    for(const T& element: inVector)
    {
        Write(element);
    }
}

template<typename T>
void Read(std::vector<T>& outVector)
{
    size_t elementCount;
    Read(elementCount);
    outVector.resize(elementCount);
    for(const T& element: outVector)
    {
        Read(element);
    }
}
```

逐元素版本**支持 vector 的 vector，或者包含 vector 的类的 vector**，等等。

**判据（原文原话）**：新增专门的 Read/Write 可以支持其他容器或指针引用的任何数据，
**只要这个数据完全由被序列化的父对象拥有**。
**如果数据需要与其他对象共享或者被其他对象引用，就需要链接。**

### 三、链接：数据被共享就写 ID（§4.3.2）

**共享的例子**：如果两个 RoboCat 共享一个大本营（`GameObject* mHomeBase`），
**使用目前的工具是没有办法表示的**——
**嵌入方法在序列化时仅仅把同一个大本营的副本嵌入进去，反序列化时将生成两个不同的大本营。**

**反向引用的例子（原文给的死法）**：

```cpp
class HomeBase: public GameObject
{
    std::vector<RoboCat*> mRoboCats;
};
```

想象只用嵌入序列化 RoboCat：
**序列化 RoboCat → 嵌入它的 HomeBase → HomeBase 嵌入它所有活跃的 RoboCat，
也包括当前正在序列化的那个 RoboCat → 无限递归导致堆栈溢出。**
原文的结论：**很明显需要另外一种工具。**

**解法**：**给每个多处引用的对象一个唯一的标识符，然后通过序列化标识符实现引用的序列化。**
反序列化时，**修复例程可以用该标识符查找引用对象，并把它插入到对应的成员变量**。
**正是由于这个原因，这个过程通常被称为链接（linking）。**

**清单 4.7　链接上下文**

```cpp
class LinkingContext
{
public:

    uint32_t GetNetworkId(GameObject* inGameObject)
    {
        auto it = mGameObjectToNetworkIdMap.find(inGameObject);
        if(it != mGameObjectToNetworkIdMap.end())
        {
            return it->second;
        }
        else
        {
            return 0;
        }
    }

    GameObject* GetGameObject(uint32_t inNetworkId)
    {
        auto it = mNetworkIdToGameObjectMap.find(inNetworkId);
        if(it != mNetworkIdToGameObjectMap.end())
        {
            return it->second;
        }
        else
        {
            return nullptr;
        }
    }

private:
    std::unordered_map<uint32_t, GameObject*>
        mNetworkIdToGameObjectMap;
    std::unordered_map<GameObject*, uint32_t>
        mGameObjectToNetworkIdMap;
};
```

**双向 map 是这个类的全部**——两个方向都要查，所以写和读各走一条：

```cpp
void Write(const GameObject* inGameObject)
{
    uint32_t networkId =
        mLinkingContext->GetNetworkId(inGameObject);
    Write(networkId);
}

void Read(GameObject*& outGameObject)
{
    uint32_t networkId;
    Read(networkId);
    outGameObject = mLinkingContext->GetGameObject(networkId);
}
```

第 5 章会讲怎么分配 ID、怎么维护 ID 与对象的映射。

> **注释（原文，这是链接系统最难的一环）**：
> 当完全实现之后，链接系统和使用它的游戏代码**必须容忍收到这样的网络 ID，即没有与之映射的对象**。
> **因为数据包可以丢失，游戏可能收到一个对象，它的成员变量引用了一个尚未发送的对象。**
> 有许多不同的方法来解决这个问题——
> **游戏可以忽略整个对象，或者反序列化这个对象并链接任何可用的引用，将丢失的引用置为空。**
> 更复杂的系统**可以跟踪空链接的成员变量**，这样收到给定网络 ID 的对象时可以链接它。
> **具体如何选择取决于游戏设计的细节。**

### 四、压缩的动机（§4.4）

原文给的背景数字：**多人游戏早期，游戏不得不凑合使用每秒传输量为 2400 或更少字节的网络。**
现在工程师们幸运地拥有**快出多个数量级**的高速连接，
**但是他们必须仍然关心如何尽可能高效地使用带宽。**

**「一个大型游戏世界可以有上百万个运动物体，即使是最高速的带宽连接，
给数以百计的连接玩家发送这些对象的所有实时数据也足以将之耗尽。」**

第 9 章讲更高层的问题（谁该看到什么数据）；**本节讲的是：一旦决定了要发哪些数据，
如何用尽可能少的比特把它发出去。**

### 五、稀疏数组：只写实际长度（§4.4.1）

**诀窍是去除任何不需要通过网络发送的信息。** 一个好地方是稀疏的、未被完全填充的结构——
回到 `mName[128]`。原文的推理链很完整：

> **考虑到英文中的典型名字和游戏设计，用户大概率不会使用全部的 128 个字节来命名 RoboCat。**
> **对于数组来说也是一样，无论它的长度是多少；正因为数组需要为最坏的情况分配空间，
> 而序列化代码不需要假设每个用户都是这一最坏情况。**

```cpp
void RoboCat::Write(OutputMemoryStream& inStream) const
{
    ...//serialize other fields up here

    uint8_t nameLength =
        static_cast<uint8_t>(strlen(mName));
    inStream.Write(nameLength);
    inStream.Write(mName, nameLength);
    ...
}
```

**和序列化 `vector` 一样，先写长度，再写数据本身**，接收端才知道该读多少。
**长度用单独一个字节是「唯一安全的」——因为整个数组保存了最多 128 个字符。**

原文还顺手给了一条与序列化无关的观察：
**如果名字相比于 RoboCat 的其他数据不经常访问，用 `std::string` 表示名字从缓存角度更高效**，
让整个 RoboCat **需要更少的 cache line**。

**结论：稀疏容器是压缩中最容易实现的目标。**

### 六、熵编码：高频取值用 1~2 bit 标识（§4.4.2）

**熵编码（entropy encoding）利用数据的不确定性进行压缩。**
原文用信息论解释：**含有期望数据的数据包比含有非期望数据的数据包蕴含更少的信息或者熵；
因此代码在发送期望数据时应当比发送非期望数据需要更少的比特数。**

**取舍前提（很重要，原文放在最前面）**：
**在大多数情况下，花费 CPU 周期模拟实际游戏比计算数据包中熵的确切取值达到最佳压缩率更重要。**

**有用的那一种形式**：序列化某个成员变量时，**它的某一特定取值比其他取值的频率都高**。

例子是 `Vector3 mPosition`：X/Z 是猫在地面上的位置，Y 是离地高度。

```cpp
void OutputMemoryBitStream::Write(const Vector3& inVector)
{
    Write(inVector.mX);
    Write(inVector.mY);
    Write(inVector.mZ);
}
```

**这个简单写法需要 3×4 = 12 字节**，而且**没有充分利用猫经常活动在地面上这个情况**——
**大部分 mPosition 的 Y 坐标是 0**。

```cpp
void OutputMemoryBitStream::WritePos(const Vector3& inVector)
{
    Write(inVector.mX);
    Write(inVector.mZ);

    if(inVector.mY == 0)
    {
        Write(true);
    }
    else
    {
        Write(false);
        Write(inVector.mY);
    }
}
```

**关键在于算平均，而不是看最坏情况。**
原文先承认一个反直觉的点：
**在最坏情况下现在需要 33 位（1 位标识 + 32 位数值），乍看起来比之前的 32 位更差。**

**怎么知道概率？** 原文给的是**实测路径**：
**游戏中的测量技术可以记录一个用户的猫在地面上的时间——
从测试人员现场的实况，或者实际用户玩游戏的早期版本并通过互联网提交分析报告。**

假设玩家 **90%** 的时间在地面上：

```
P_OnGround × Bits_OnGround + P_InAir × Bits_InAir = 0.9 × 1 + 0.1 × 33 = 4.2
```

**序列化 Y 分量的平均比特数从 32 降为 4.2：每个位置节省了 3 字节。**
原文的规模感：**如果一秒钟有 32 名玩家变换位置 30 次，
那么仅这一个成员变量就能节省一大笔资源。**

**再加一个常见值。** 假设分析表明猫不在地上时**通常就在天花板上，高度是 100**：

```cpp
void OutputMemoryBitStream::WritePos(const Vector3& inVector)
{
    Write(inVector.mX);
    Write(inVector.mZ);

    if(inVector.mY == 0)       { Write(true);  Write(true); }
    else if(inVector.mY == 100) { Write(true);  Write(false); }
    else                        { Write(false); Write(inVector.mY); }
}
```

**仍然是 1 bit 表示「是不是常见取值」，再加 1 bit 表示「是哪个常见取值」。**
原文指出这条路的天花板：**常见的取值是写死在函数里的，
如果有太多的取值，这种方法会非常混乱。**
那种情况下**赫夫曼编码的一种简化实现可以使用一个常见取值的查找表，
用一些比特来存储查找表的索引**。

**要不要做第二次优化，要算。** 假设猫在天花板上的时间占 **7%**：

```
0.9 × 2 + 0.07 × 2 + 0.03 × 33 = 2.93
```

**平均 2.93 比特，比第一次优化少了 1.3 比特，因此该优化是值得的。**

原文的收尾：**熵编码有许多形式，从简单的写死在函数中的，
到复杂的赫夫曼编码、算术编码、gamma 编码、行程编码等。
分配给熵编码的 CPU 与分配给其他方面的 CPU 之间的权衡是设计决定。**

### 七、定点：把浮点范围映射成整数（§4.4.3）

**前提判断**：**32 位浮点数的快速计算是当前计算时代的基准。
然而，仅仅游戏模拟执行浮点运算这个因素并不意味着通过网络发送时需要所有的 32 位。**

**方法**：**检查已知的范围和被发送数字所需要的精度，然后将它们转换为定点格式。**
原文强调这一步的性质：**你必须和设计师与游戏工程师坐下来一起找出游戏真正需要的。一旦知道了，
就可以开始构建一个尽可能高效的系统。**

以 `mPosition` 的 X 为例，和设计者谈出来的结果是：

- **世界尺寸 4000 × 4000 游戏单位**，**以原点为中心**
  → **X/Z 的最小取值 −2000，最大取值 2000**
- **客户端的位置只需要精确到 0.1 个游戏单位**
  （原文特意澄清：**这不是说权威服务器中的位置不能更精确，只是给客户端发送数值时仅需要精确到 0.1 单位**）

**取值总数的公式**：

```
(MaxValue − MinValue) / Precision + 1 = (2000 + 2000) / 0.1 + 1 = 40001
```

**序列化 X 分量时有 40001 个可能取值。**
只要有一个「整数 → 浮点」的映射，就能直接序列化那个整数。

```cpp
inline uint32_t ConvertToFixed(
    float inNumber, float inMin, float inPrecision)
{
    return static_cast<uint32_t> (
        (inNumber - inMin)/inPrecision);
}

inline float ConvertFromFixed(
    uint32_t inNumber, float inMin, float inPrecision )
{
    return static_cast<float>(inNumber) *
        inPrecision + inMin;
}
```

**log₂40001 = 15.3，所以只需要 16 位。**

```cpp
void OutputMemoryBitStream::WritePosF(const Vector3& inVector)
{
    Write(ConvertToFixed(inVector.mX, -2000.f, 0.1f), 16);
    Write(ConvertToFixed(inVector.mZ, -2000.f, 0.1f), 16);
    ... //write Y component here ...
}
```

游戏内存里 `vector` 的分量仍是完整浮点数，**但发送到互联网时会被转换成 0 到 40000 之间的定点数，
只用 16 位**。

> **注释（原文，别忽略）**：
> **一些 CPU，例如 Xbox 360 和 PS3 的 PowerPC，实现浮点数和整数之间的转换计算是非常昂贵的。**
> **但是，与所节省的带宽相比，这往往也是值得的。**
> **正如大多数的优化，这是一个权衡，由所开发游戏的特性决定。**

### 八、几何压缩：四元数 128 位 → 49 位（§4.4.4）

原文先把 §4.4.3 的道理推广：**因为变量的可能取值有了约束，
所以需要较少的比特就可以表示那个信息**——
**序列化任何数据结构时，只要它的内容有约束，就可以使用这种技术。**

**四元数的约束**：表示旋转的四元数是**归一化的**，
**每个分量都在 −1 和 1 之间，所有分量的平方和是 1**。
**因为所有分量的平方和是固定的，所以序列化四元数只需要序列化四个分量中的三个，
同时使用一个比特表示第四个分量的符号。**
反序列化时**可以通过 1 减去其他分量的平方来得到最后一个分量**。

再叠加定点：**所有分量取值都在 −1 到 1 之间**，
**如果不影响游戏的前提下有一个可接受的精度损失，定点表示可以进一步提高压缩率**。
**通常 16 位的精度是足够的，所以使用 65535 个可能的取值来表示范围 −1 到 1。**

**「在内存中需要 128 位的四元数用 49 位就可以精确地序列化」**（16×3 + 1）：

```cpp
void OutputMemoryBitStream::Write(const Quaternion& inQuat)
{
    float precision = (2.f / 65535.f);
    Write(ConvertToFixed(inQuat.mX, -1.f, precision), 16);
    Write(ConvertToFixed(inQuat.mY, -1.f, precision), 16);
    Write(ConvertToFixed(inQuat.mZ, -1.f, precision), 16);
    Write(inQuat.mW < 0);
}

void InputMemoryBitStream::Read(Quaternion& outQuat)
{
    float precision = (2.f / 65535.f);
    uint32_t f = 0;

    Read(f, 16); outQuat.mX = ConvertFromFixed(f, -1.f, precision);
    Read(f, 16); outQuat.mY = ConvertFromFixed(f, -1.f, precision);
    Read(f, 16); outQuat.mZ = ConvertFromFixed(f, -1.f, precision);

    outQuat.mW = sqrtf(1.f -
                       outQuat.mX * outQuat.mX -
                       outQuat.mY * outQuat.mY -
                       outQuat.mZ * outQuat.mZ );

    bool isNegative;
    Read(isNegative);
    if(isNegative)
    {
        outQuat.mW *= -1;
    }
}
```

**仿射变换矩阵同理**：**变换矩阵由 16 个浮点数组成，
但为了满足仿射的要求，它必须能够分解成用 3 个浮点数表示的平移变换、
用四元数表示的旋转和 3 个浮点数表示的缩放变换，共 10 个浮点数。**
原文接着给了同样的模式：**如果序列化的典型矩阵有更多的限制，熵编码可以帮更多忙**——
**如果矩阵通常是未缩放的，程序用一个比特标识这一点；
如果缩放是均匀的，再用另外一个不同的比特标识，然后只序列化一个分量，而不是所有三个。**

| §4.4.2 | 常见取值写死在函数里；**取值太多会很混乱** → 赫夫曼查表 + 索引比特 |
| §4.4.3 | 世界 **4000×4000**，**以原点为中心** → X/Z 范围 **−2000 ~ 2000** |
| §4.4.3 | 客户端精度 **0.1 单位**（**服务器可以更精确**） |
| §4.4.3 | 取值数 **40001**；**log₂ = 15.3 → 16 位** |
| §4.4.3 | 注释：**Xbox 360 / PS3 的 PowerPC 上浮点↔整数转换很贵** |
| §4.4.4 | 四元数归一化 → 平方和为 1 → **只发 3 个分量 + 1 bit 符号** |
| §4.4.4 | −1~1 用 **65535 个取值**（16 位）→ **128 位压到 49 位** |
| §4.4.4 | 仿射矩阵 **16 浮点 → 3 平移 + 四元数 + 3 缩放 = 10 个浮点** |

## 作者省略的前提

> [!note] 本节是补出来的，不在原文里。

- **`LinkingContext` 的「找不到就返回 0」和「合法 ID 就是 0」撞车**（推演）。
  `GetNetworkId` 查不到时 `return 0`，`Write(const GameObject*)` 会**把这个 0 原样写进流**。
  若网络 ID 空间包含 0，接收端会把「未知引用」误认成一个真实对象。
  **实际实现应保留 0 作为哨兵、ID 从 1 起分配**；更稳妥的是返回 `bool GetNetworkId(..., uint32_t& out)`，
  **让「对象没注册过」在序列化侧就暴露出来，而不是变成一个合法数字**。
- **`RoboCat` 含 `std::vector` 成员 ⇒ 不能当 POD 整体拷贝，这个坑在嵌入方案里重现**（推演）。
  §4.3.1 的逐元素 `Write`/`Read` 只解决了**顶层** `vector`；
  若类内嵌 `vector<HomeBase*>`，仍然要落回链接方案，**且 HomeBase 里若又有 `vector<RoboCat*>` 就直接环了**——
  **环检测必须在这一层做，不是递归时补**。
- **定点编码会引入 ±0.05 单位的量化误差，且不可逆**（推演）。
  原文只说「客户端只需 0.1 单位」，**没说什么时候重算**——
  发送方按固定步长量化，接收方解量化后位置**不会精确落在发送方那一帧的浮点值上**。
  **客户端预测/插值链路里必须知道这件事**，否则会表现为「位置抖动」而不是「精度不足」。
- **`sqrtf(1 − x² − y² − z²)` 的根号内可能为负**（推演）：
  浮点误差下四元数分量平方和可能略大于 1，此时 **`sqrtf` 返回 NaN，且 NaN 会沿预测链路污染后续所有状态**。
  工程实现应 `max(0.f, ...)` 夹一下再开方。

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 嵌入：数据**完全由父对象拥有** | 副本唯一、语义正确 | 共享数据生成多份；反向引用**堆栈溢出** |
| 链接：两端 ID 分配规则一致 | 引用能还原成对象 | 解析到错对象或 `nullptr` |
| 链接：**允许悬空引用** | 丢包不致命 | 一个丢包导致整个对象被丢弃 |
| 熵编码：**高频取值确实高频** | 平均比特数下降 | 比朴素编码**更费**（多花 1 bit 标识） |
| 熵编码：概率来自**实测**而非猜测 | 优化成立 | 算出来的收益是假的 |
| 定点：范围与精度**由设计师拍板** | 位数可确定 | 拍错了就是协议错，两端不一致直接错位 |
| 定点：CPU 上浮点↔整数转换便宜 | 压缩纯赚 | PowerPC 类平台要用带宽换 CPU，**需实测权衡** |

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 嵌入 vs 链接的判据 | **已内建，但走的是第三条路** | 本项目**不做指针序列化**，一律走「**引用改 ID**」：`Direction`、`PartState`、`BodyPartType` 都是**值类型**；`kPlayerStatePayload = 3`（`hp:u16 + alive:u8`）里连指针都没有。**这比链接更简单——因为快照语义本来就允许整表覆盖** |
| 「必须容忍有 ID 但无对象的引用」 | **靠全量快照天然免疫** | 见 [[04-格雷泽-全量快照与增量]]：全量快照**幂等**，上一帧没出现的对象下一帧出现即可，**不需要引用修复例程**。这是选全量而非增量的一个隐性收益 |
| 熵编码 / 定点 / 几何压缩 | **当前一律不做，且是有依据的不做** | `kWorldSnapshotPayloadMax4 = 98` 字节，10 Hz，单帧远小于 `kMaxPayloadSize = 1400`。**省下的那几十比特相对 1400 的预算是噪声**，而定点化会引入 §4.3 补前提里说的量化误差，**污染客户端插值**。等 payload 数量级上来再说 |
