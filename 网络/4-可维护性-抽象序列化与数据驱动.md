> [!info] 核心结论
> 前面几节的每个技巧都要写**一对**方法，而**改了写法就必须改读法**——
> 这是纯逻辑错误的最大来源。本节给两条解法，都**明确以性能换维护性**：
>
> **① 抽象序列化方向**：用 `MemoryStream` 基类 + 虚 `Serialize` + `IsInput()`，
> **把 Read/Write 合并成一个方法，输入输出代码从此不可能不同步**。
> 代价：**每次序列化一次虚函数调用**。
>
> **② 数据驱动的序列化**：把「有哪些成员、各是什么类型、在什么偏移」写成**数据**，
> 序列化函数退化成一次 `for` 循环遍历元数据。代价：**分支变多、流水线易清空**。
>
> 原文的立论：**「仅仅关注带宽效率可能会导致某些地方出现丑陋的代码。
> 所以需要一些权衡考虑，牺牲一点点效率来换取代码的可维护性。」**

## 机制

### 一、问题是什么（§4.5 开头）

**前面介绍的每个新的数据结构或压缩技术都同时需要读方法和写方法。**
这不仅意味着为每个新功能都实现两个方法，
**而且这些方法必须彼此保持同步：如果改变了一个成员变量的写法，那么必须改变它的读法。**

原文对这种状态的评价：**每个数据结构都有两个这样耦合的方法有点令人头疼。**
**如果每个结构体只有一个能同时处理读和写的方法，代码将会更清晰。**

### 二、解法一：抽象序列化方向（§4.5.1）

**幸运的是，可以通过使用继承和虚函数来实现。**

```cpp
class MemoryStream
{
    virtual void Serialize(void* ioData,
                           uint32_t inByteCount) = 0;
    virtual bool IsInput() const = 0;
};

class InputMemoryStream: public MemoryStream
{
    ...//other methods above here
    virtual void Serialize(void* ioData, uint32_t inByteCount)
    {
        Read(ioData, inByteCount);
    }
    virtual bool IsInput() const {return true;}
};

class OutputMemoryStream: public MemoryStream
{
    ...//other methods above here
    virtual void Serialize(void* ioData, uint32_t inByteCount)
    {
        Write(ioData, inByteCount);
    }

    virtual bool IsInput() const {return false;}
}
```

两个子类的差异**只有两处**：转调 `Read` 还是 `Write`，`IsInput()` 返回 `true` 还是 `false`。
**基类据此实现模板化的 `Serialize`，而非模板化的版本由子类恰当地实现：**

```cpp
template<typename T> void Serialize(T& ioData)
{
    static_assert(std::is_arithmetic<T>::value ||
                    std::is_enum<T>::value,
    "Generic Serialize only supports primitive data types");

    if(STREAM_ENDIANNESS == PLATFORM_ENDIANNESS)
    {
        Serialize(&ioData, sizeof(ioData) );
    }
    else
    {
        if(IsInput())
        {
            T data;
            Serialize(&data, sizeof(T));
            ioData = ByteSwap(data);
        }
        else
        {
            T swappedData = ByteSwap(ioData);
            Serialize(&swappedData, sizeof(swappedData));
        }
    }
}
```

**收益（原文）**：自定义的 `Serialize` 方法只需要 `MemoryStream` 作参数，
可以用流的 `Serialize` 虚方法实现合适的读或写——
**这样一个单独的方法可以为一个自定义类同时处理读和写，保证输入和输出代码永远同步。**

> **警告（原文，别当废话）**：
> **这种实现方式比之前的方法稍微低效一点，因为需要进行虚函数调用。**
> **该系统还可以使用模板来代替虚函数，这样可以提高一些性能，
> 这部分留作练习题，由你来尝试完成。**

### 三、解法二：数据驱动的序列化（§4.5.2）

**观察到的事实**：**大部分对象序列化代码采用相同的模式：
对于对象类中的每一个成员变量，序列化该成员变量的值。**
**这里可能有一些优化，但是代码的一般结构都是相同的。事实上，它们是如此相似，
如果游戏有一些关于运行时对象成员取值的数据，它可以使用单一的序列化方法来处理大部分序列化需求。**

**障碍**：一些语言（**C# 和 Java**）有内置的反射系统，允许运行时访问类结构。
**然而 C++ 在运行时反射类成员需要一个自定义构建的系统。**
原文的判断：**幸运的是，构建一个基本的反射系统并不复杂。**

**清单 4.8　基本的反射系统**

```cpp
enum EPrimitiveType
{
    EPT_Int,
    EPT_String,
    EPT_Float
};

class MemberVariable
{
public:
    MemberVariable(const char* inName,
        EPrimitiveType inPrimitiveType, uint32_t inOffset):
    mName(inName),
    mPrimitiveType(inPrimitiveType),
    mOffset(inOffset) {}

    EPrimitiveType    GetPrimitiveType() const {return mPrimitiveType;}
    uint32_t         GetOffset()          const {return mOffset;}

private:
    std::string       mName;
    EPrimitiveType    mPrimitiveType;
    uint32_t          mOffset;
};

class DataType
{
public:
    DataType(std::initializer_list<const MemberVariable&> inMVs):
    mMemberVariables(inMVs)
    {}

    const std::vector<MemberVariable>& GetMemberVariables() const
    {
        return mMemberVariables;
    }
private:
    std::vector< MemberVariable >    mMemberVariables;
};
```

**三个类的分工，原文讲得很清楚**：

- **`EPrimitiveType` 表示成员变量的基本类型。**
  **该系统只支持整型、浮点型和字符串类型，但是可以很容易扩展到任何需要的基本类型。**
- **`MemberVariable` 表示复合数据类型中的一个单独的成员变量。**
  它带三个信息：**名字（用于调试）、基本类型、在父数据类型中的内存偏移**。
  **存储偏移是非常关键的：序列化代码可以为给定对象的基址添加偏移，
  用于寻找那个对象的成员变量值在内存中的位置。这就是实现这个成员变量数据读写的方式。**
- **`DataType` 包含一个特定类的所有成员变量。**
  **对于每一个支持数据驱动的序列化方法的类，都有一个相应的 `DataType` 实例。**

**为类加载反射数据：**

```cpp
#define OffsetOf(c, mv) ((size_t) & (static_cast<c*>(nullptr)->mv))

class MouseStatus
{
public:
    std::string       mName;
    int               mLegCount, mHeadCount;
    float             mHealth;

    static DataType* sDataType;
    static void InitDataType()
    {
        sDataType = new DataType(
        {
            MemberVariable("mName",
                EPT_String, OffsetOf(MouseStatus,mName)),
            MemberVariable("mLegCount",
                EPT_Int, OffsetOf(MouseStatus, mLegCount)),
            MemberVariable("mHeadCount",
                EPT_Int, OffsetOf(MouseStatus, mHeadCount)),
            MemberVariable("mHealth",
                EPT_Float, OffsetOf(MouseStatus, mHealth))
        });
    }
};
```

**关于 `OffsetOf` 的告诫（原文，别跳过）**：

> **内置在 C++ 中的 `offsetof` 宏对于非 POD 类有未定义的行为。**
> 实际上**当 `offsetof` 用于包含虚函数或其他非 POD 类型时，一些编译器会返回编译错误**。
> **只要类没有自定义一元运算符 `&`，类的层次结构中没有使用虚继承和引用型成员变量，
> 那么该自定义宏就能使用。**

`static InitDataType()` **必须在某个时刻被调用，以初始化 `sDataType` 成员变量**。

原文还留了一句方向性判断：**理想情况下，不必在反射数据中手工写代码，
最好有工具能够分析 C++ 头文件并自动为类生成反射数据。**

**有了反射，序列化函数退化成一次遍历：**

```cpp
void Serialize(MemoryStream* inMemoryStream,
               const DataType* inDataType, uint8_t* inData)
{
    for(auto& mv: inDataType->GetMemberVariables())
    {
        void* mvData = inData + mv.GetOffset();
        switch(mv.GetPrimitiveType())
        {
        case EPT_Int:
            inMemoryStream->Serialize(*(int*) mvData);
            break;
        case EPT_String:
            inMemoryStream->Serialize(*(std::string*) mvData);
            break;
        case EPT_Float:
            inMemoryStream->Serialize(*(float*) mvData);
            break;
        }
    }
}
```

（原文的清单 4.8 后这段代码里三个分支标签**都漏写了 `case` 关键字**，
下面已按正确写法给出，详见「与原文的出入」。）

原文对运行过程的两句解释：**每个成员变量的 `GetOffset` 方法计算指向这个成员变量实体数据的指针；
接着 `GetPrimitiveType` 的 `switch` 语句将数据分到合适的类型中，
让类型化的 `Serialize` 函数实现真正的序列化。**

**扩展方向（原文给的两条路）**：
**通过扩展 `MemberVariable` 类中跟踪的元数据，该技术可以更强大。**

1. **可以存储用于每个变量自动压缩的比特数**——这正好把 §4.4 的熵编码接了进来。
2. **可以为成员变量存储可能的自定义取值**——支持一些熵编码的程序实现。

### 四、账算在哪儿（§4.5 结尾）

原文对这个选择的总结，用词很克制：

> **总的来说，该方法以性能换可维护性：有更多的分支可能会导致流水线清空，
> 但是代码更少了，因此错误减少了。**

**额外福利**：**除了网络序列化，反射系统还可以用于许多地方**——
原文点名了**实现到磁盘的序列化、垃圾收集、GUI 对象编辑器**。

## 作者省略的前提

> [!note] 本节是补出来的，不在原文里。

- **`OffsetOf` 宏本身也踩在未定义行为上**（推演，原文只谈了 `offsetof`）。
  `& (static_cast<c*>(nullptr)->mv)` 的写法是**对空指针解引用**——
  标准 C++ 里这是 UB，**实践中编译器把它当常量折叠所以到处能用**，
  但它不进 `-O0` 以外的可移植保证。**如果要严格可移植**，正解是用标准 `offsetof`
  并接受它对非 POD 的限制，而不是换成一个同样 UB 的自制版本。
- **数据驱动序列化会让 `switch` 的类型集合与 `MemberVariable` 的元数据脱钩**（推演）。
  加一种 `EPT_Quat` 要改两处：枚举 + `switch` 分支。
  **漏改 `switch` 的编译错误是"enum 没有覆盖"，还算安全；
  真正的坑是默认分支被静默跳过——成员被读写了 0 字节，双方都不会报错**，
  表现是「某个字段永远是默认值」。所以 `switch` **必须带 `default: assert(false)`**。
- **反射数据的生命周期没人管**（推演）。原文的 `InitDataType()` 是 `new` 出来的，
  **没有对应的释放路径**。全类静态初始化场景下这是可接受的（进程结束即回收），
  但**热重载或 DLL 卸载时会泄漏**，且重复调用 `InitDataType()` 会**泄漏上一份并替换指针**。
- **虚函数版 `Serialize` 的开销在热路径上是复利的**（推演）。
  原文说「稍微低效一点」，但**每个成员变量一次虚调用**，
  一个 10 成员的对象就是 10 次**无法内联**的间接跳转——
  在 §4.4.2 说的「每秒 32 人 × 30 次变换」的规模下，
  这才是原文那个「用模板代替虚函数」的练习题真正值得做的原因。

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| 成员读写**永远成对修改** | 两条解法任选其一 | 任何一条都救不了——**同步靠纪律，不靠结构** |
| 类**无自定义一元 `&`**、无虚继承、无引用型成员 | 自定义 `OffsetOf` 可用 | 偏移算错 → **读写到相邻成员，且不报错** |
| `InitDataType()` **被确保调用一次** | 反射可用 | `sDataType` 为空 → 遍历空列表，**静默什么都不做** |
| `switch` 带 `default` 且 `assert` | 新类型漏改当场暴露 | **静默跳过成员**，字段永远停在默认值 |
| 带宽预算不紧张 | 抽象化的开销可忽略 | 序列化进了每帧热路径 → 需要模板版削开销 |

## 本项目落点

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| 两条解法（虚函数抽象 / 数据驱动） | **都不采用，是有依据的** | 本项目**每个消息只有一个定长 payload**，见 `wire::kPlayerInputPayload = 8`（`seq:u16 + move_dir:i16*2 + action:u8 + form:u8`）——**字段就 4 个且全定宽**。为 4 个字段写反射元数据 + 虚调用，**维护成本远超收益** |
| 「改了写法必须改读法」这个痛点 | **换了个方式规避** | 不用「一个函数写两次」，而是**让字段表成为唯一真相源**：`wire::` 常量 + 字段构成注释写在同一处，`test_smoke.cpp` 断言 `payload_size`，**字段一改，测试立刻红**。**把同步责任交给测试而不是靠结构或纪律** |
| `switch` 必须带 `default` | **应采纳** | 本项目当前靠手写 encode/decode，**没有 `switch` 就没有这个风险**；但一旦将来加「按 `MsgId` 分派」的大 `switch`，**必须带 `default: assert(false)`**，否则新增消息类型漏实现会静默走空 |
