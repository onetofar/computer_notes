# 前置知识 · SIGALRM信号与升序链表定时器

> 本笔记是学习高性能定时器之前必须了解的基础。先理解最简单的定时器实现——升序链表——以及SIGALRM信号如何触发定时任务，才能对比理解时间轮为什么能把插入从O(n)降到O(1)。

---

## 一、SIGALRM信号：定时器的触发源

### 1.1 核心定义

**SIGALRM信号**是内核在实时闹钟超时后向进程发送的信号，由`alarm()`或`setitimer()`函数设置。闹钟一旦超时，内核向进程发送SIGALRM信号，触发信号处理函数。定时器就是在这个信号处理函数中执行到期任务的。
#### `alarm` — 只设置一次超时

```c
unsigned int alarm(unsigned int seconds);
```

- **作用**：在 `seconds` 秒后向进程发送 **一次** SIGALRM 信号
    
- **不是周期**：信号只发一次，不会自动重复
    
- 若 `seconds = 0`，取消之前设置的闹钟

---

#### `setitimer` — 可设置周期，但不直接用于定时器任务

```c
int setitimer(int which, const struct itimerval *new_value, struct itimerval *old_value);
struct itimerval {
    struct timeval it_interval;  // 重复间隔（周期）
    struct timeval it_value;     // 第一次超时时间
};
```

- `it_value` 是**第一次超时时间**，到期后内核发送 SIGALRM 信号
    
- 若 `it_interval` 非零，内核会**自动重复**，每隔 `it_interval` 时间再发一次信号
    
- 所以 `setitimer` **可以设置周期**，且是内核自动重复，不需要信号处理函数手动重设

---
### 1.2 行为规则
1. 信号按照**固定频率**生成，由`alarm`或`setitimer`设置的定时周期T保持不变。如果某个定时任务的超时时间不是T的整数倍，实际执行时间与预期会有偏差。T反映了定时的精度。
	- **用 `alarm`**：在信号处理函数中重新调用 `alarm(T)`，设置下一次超时
	- **用 `setitimer`**：把 `it_interval` 设为周期 `T`，内核自动重复
>无论哪种方式，效果都一样：**每隔 T 秒，进程收到一次 SIGALRM 信号**。这个 T 就是定时器的精度——定时任务的执行时间只能是 T 的整数倍，偏差 ≤ T。如果你没有做任何设置，就没有这个固定频率，因为 `alarm` 只产生一次信号。
2. 内核在信号处理函数执行期间**自动屏蔽**同种信号，不需要担心嵌套调用。
3. 信号处理函数应尽可能简短，避免执行耗时操作——否则会阻塞其他信号的到达。

### 1.3 与I/O复用的区别

| 维度   | select/epoll             | SIGALRM信号   |
| :--- | :----------------------- | :---------- |
| 触发来源 | socket上的I/O事件（数据到达、连接建立） | 时间到达（闹钟超时）  |
| 阻塞位置 | epoll_wait等待fd就绪         | 信号处理函数被内核触发 |
| 用途   | 检测网络I/O事件                | 执行周期性定时任务   |

SIGALRM信号触发机制负责“何时执行定时任务”，而定时器数据结构（升序链表、时间轮）负责“如何组织所有定时任务”。两者配合：信号触发回调，回调遍历定时器链表，找到到期任务并执行。

### 1.4 统一事件源模式

后续实现中，SIGALRM信号将被集成到epoll服务器中。核心思路是：把信号事件当作I/O事件处理——信号处理函数通过`socketpair`或`eventfd`向主循环发送通知，主循环在epoll_wait中统一等待所有事件，包括定时器事件。这样信号处理函数就不需要执行复杂逻辑，只需要通知主循环即可。

## 二、升序链表定时器：最简单的实现

### 2.1 核心定义

所有定时任务按照**超时时间从小到大**排序。插入时按顺序找到正确位置（O(n)），触发时只需要检查链表头（O(1)）。

### 2.2 数据结构

```
链表头                                             链表尾
┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
│ Timer A │───→│ Timer B │───→│ Timer C │───→│ Timer D │
│ 超时:100│    │ 超时:200│    │ 超时:350│    │ 超时:500│
└─────────┘    └─────────┘    └─────────┘    └─────────┘
```

每个节点包含该连接的超时时间（`expire_time`）和对应的任务回调函数。

### 2.3 插入操作（O(n)）

```
新增 Timer E（超时:300）
→ 从链表头开始遍历
→ 比较每个节点的超时时间，找到 B（200）和 C（350）之间的位置
→ 插入 E
```

新连接建立时为该连接创建一个定时器，需要遍历链表找到正确的插入位置。连接的排列顺序不由建立顺序决定，而是由各自的超时时间决定——这决定了插入必然是O(n)。

### 2.4 触发操作（O(1)）

信号处理函数周期性触发（如每1秒）：

1. 检查链表头节点
2. 若链表头的超时时间 ≤ 当前时间 → 执行该定时任务，将其移出链表
3. 继续检查新的链表头，直到链表头的超时时间 > 当前时间

每次只需要看链表头，因为升序链表保证了头节点就是下一个要超时的任务。

### 2.5 应用示例：踢掉非活动连接

服务器为每个客户端连接设置一个定时器，超时时间为“最后一次收到数据的时间 + 超时阈值”（如15秒）。

- **收到客户端数据**：更新该连接的超时时间（调整节点在链表中的位置）
- **信号处理函数触发**：遍历链表头，将超时的连接踢掉并释放资源

这是时间轮出现之前处理非活动连接的标准方案。

## 三、升序链表的瓶颈：插入O(n)

| 操作 | 升序链表 | 瓶颈分析 |
|:---|:---|:---|
| **插入** | O(n) | 每次新连接都要遍历链表找到插入位置 |
| **触发** | O(1) | 只需检查链表头 |

游戏服务器有数万个连接，每个连接至少有一个定时器（心跳检测、超时断开）。每次新建连接时O(n)插入会成为性能瓶颈。这就是时间轮要解决的问题——用哈希桶替代单一链表，把插入降到O(1)。

---

## 四、时间轮的改进方向

时间轮将时间划分为固定长度的槽位，每个槽位对应一个链表。插入定时器时，通过超时时间直接计算它应该落入哪个槽位（哈希定位），O(1)。触发时，指针移动到当前槽位，执行该槽链表上所有到期的定时器。

| 维度 | 升序链表 | 时间轮 |
|:---|:---|:---|
| **插入** | O(n) 遍历找位置 | O(1) 哈希定位槽位 |
| **触发** | O(1) 检查头节点 | O(1) 执行当前槽链表 |
| **适用场景** | 定时任务数量少 | 大规模连接，游戏服务器标配 |
