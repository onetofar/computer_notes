# 工具分工&极简使用手册（WSL2+Docker + C++游戏服务端）
   整体分层：**实时观测（找进程）→ 性能剖析（查瓶颈）→ 专项辅助（解细分问题）**，各工具职责明确、无功能重叠。
   ## 一、实时观测层（第一步：定位高负载进程/线程）
   ### 1. btop（主力首选）
   **职责**：交互式全维度监控，查看进程树、线程状态、CPU/内存/网络一体化视图
   **核心操作**
   ```bash
   btop
   ```
   - `c`：按CPU排序 | `m`：按内存排序
   - `f`：过滤进程（输入服务名，如 `game-server`）
   - 选中进程 + `Enter`：进入线程详情（定位单线程死循环、线程负载不均）
   | 快捷键    | 功能                                  | 游戏服场景用途                            |
   | 
---

   | **f**     | 进程过滤（支持正则）                  | 输入`game-server`/`node`快速定位服务进程  |
   | **Enter** | 查看进程详情                          | 查看线程级 CPU / 内存占用，定位线程死循环 |
   | **c**     | 按 CPU 排序                           | 瞬间找到 CPU 飙升的进程                   |
   | **m**     | 按内存排序                            | 发现内存泄漏 / 异常占用进程               |
   | **e**     | 展开 / 折叠进程树                     | 分析父进程与子进程资源关系                |
   | **p**     | 切换视图预设                          | 聚焦 CPU / 内存 / 网络 / 进程单一维度     |
   | **1-4**   | 单独显示 CPU / 内存 / 网络 / 进程面板 | 全屏监控核心指标                          |
   | **r**     | 修改刷新间隔                          | 高负载时调至 500ms，低负载时 1-2s         |

   ### 2. pidstat（量化统计）
   **职责**：精确输出线程CPU/IO数值，做量化对比
   ```bash
   # 每秒刷新，监控指定进程所有线程
   pidstat -t 1 -p 进程PID
   ```

   > 补充：`htop` 功能与 btop 高度重叠，二选一即可，日常优先 btop。

   ---

   ## 二、深度性能剖析层（第二步：进程内部找代码瓶颈 | 核心工具：perf）
   **职责**：内核级采样，定位**函数、调用栈、内核开销**，专治「CPU高但不知道哪段代码慢」
   > 环境：直接在 WSL2 宿主使用，无需安装到 Docker 容器

   ### 1. 实时热点查看（即时排查）
   ```bash
   # 查看进程内CPU占用最高的函数
   perf top -p 进程PID
   # 仅展示业务代码，过滤内核函数
   perf top -p 进程PID -e cycles:u
   # 连带调用栈一起显示
   perf top -p 进程PID -g
   ```

   ### 2. 离线采样报告（深度复盘）
   ```bash
   # 采样10秒并记录调用栈
   perf record -g -p 进程PID sleep 10
   # 解析采样数据
   perf report
   ```

   ### 3. 系统调用整体统计
   ```bash
   # 统计各类系统调用的耗时、次数
   perf stat -p 进程PID sleep 10
   ```

   ### 4. 火焰图（复杂调用栈可视化）
   ```bash
   # 采样30秒
   sudo perf record -F 99 -g -p 进程PID sleep 30
   # 生成SVG火焰图（浏览器打开查看）
   perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
   ```

   ### 5. 轻量系统调用追踪
   ```bash
   perf trace -p 进程PID
   ```

   ## 三、专项辅助层（第三步：解决细分问题，各司其职）
   ### 1. strace
   **职责**：完整抓取系统调用、参数与耗时，定位**进程阻塞、调用失败**
   > 区分：`perf trace` 偏统计，`strace` 偏调用细节，程序卡死优先用它
   ```bash
   # 追踪运行中进程，显示调用耗时
   strace -T -p 进程PID
   ```

   ### 2. lsof
   **职责**：排查**端口占用、文件句柄溢出**，解决 `too many open files`、端口冲突
   ```bash
   # 查看进程所有打开的文件/套接字
   lsof -p 进程PID
   # 查看指定端口被哪个进程占用
   lsof -i :端口号
   ```

   ### 3. valgrind
   **职责**：专属内存检测，定位**内存泄漏、野指针、重复释放**
   > 区分：perf 只管CPU性能，内存问题必须用 valgrind；建议在容器内运行
   ```bash
   # 完整内存泄漏检测
   valgrind --leak-check=full ./服务程序
   ```

   ### 4. tcpdump
   **职责**：网络报文抓包，排查 TCP 粘包、丢包、协议解析异常
   ```bash
   # 抓取指定端口报文
   tcpdump port 服务端口
   # 保存抓包文件，可配合 Wireshark 分析
   tcpdump -w net.pcap port 服务端口
   ```

   ## 四、极简标准排查流程（串联全工具）
   1. `btop` → 找到高负载进程/线程，记录 **PID**
   2. `perf top` → 快速定位热点函数
   3. 调用栈复杂 → 生成 **perf火焰图** 深度分析
   4. 进程卡死/调用异常 → 追加 `strace`
   5. 内存持续上涨/野指针崩溃 → 使用 `valgrind`
   6. 端口报错/句柄溢出 → 使用 `lsof`
   7. 网络丢包/粘包 → 使用 `tcpdump`

   ---

   ## 五、Docker+WSL2 专属：获取容器进程PID
   ```bash
   # 通过容器名，直接拿到宿主机可监控的PID
   PID=$(docker inspect --format '{{.State.Pid}}' 容器名)
   ```

   ## 六、工具分工速查表
   | 工具     | 核心定位               | 典型使用场景               |
   | -------- | ---------------------- | -------------------------- |
   | btop     | 进程/线程实时观测      | 快速锁定高CPU/内存进程     |
   | pidstat  | 线程负载量化统计       | 多线程负载数值对比         |
   | perf     | 函数/调用栈CPU性能分析 | 代码级性能瓶颈定位         |
   | strace   | 系统调用细节+阻塞排查  | 进程卡死、接口调用失败     |
   | lsof     | 端口/文件句柄排查      | 端口冲突、句柄数超限       |
   | valgrind | 内存错误&泄漏检测      | 内存暴涨、非法内存访问崩溃 |
   | tcpdump  | 网络报文分析           | 丢包、粘包、网络协议异常   |
