> [!info] 核心结论
> NAT 是边界设备（家用路由器）做的**地址 + 端口双重重写**：让一整个家庭网络
> 共享一个公开 IP。代价是它单方面销毁了「从外部主动连进来」的能力——
> 出站不受限制，但入站必须先有映射表项，而表项**只由出站产生**。
> 所以「谁能连上谁」不由防火墙策略决定，由**谁先发过包**决定。
> UDP 因此需要 STUN 打洞这类补丁；TCP 因为三次握手本身就是一次客户端发起的
> 入站报文，**天然就完成了打洞**。

## 机制

### 为什么需要它

IPv4 只有 32 bit = 42.9 亿个地址，早就发完了。NAT 让一整个私有子网共享一个
公开 IP，把「地址不够用」变成「端口不够用」。

### 私有地址空间

| 段 | 范围 | 用途 |
|---|---|---|
| 10.0.0.0/8 | 10.0.0.0 – 10.255.255.255 | 私有 |
| 172.16.0.0/12 | 172.16.0.0 – 172.31.255.255 | 私有 |
| 192.168.0.0/16 | 192.168.0.0 – 192.168.255.255 | 私有 |
| 127.0.0.0/8 | — | 环回 |
| 169.254.0.0/16 | — | 链路本地 / APIPA |

关键性质是**可重复**：不同家庭可以用同一个 `192.168.1.1`，
因为公网路由器没有到这些段的路由信息。

> 注意措辞：「私有地址不可路由」≠「这个地址不存在」。
> 准确含义是「路由器**没有**到它的路由信息」——这个区别在排障时很要紧，
> 一个「ping 不通私网地址」的现象可能根本不是地址的问题。

### 三步递进

**第一步 · 没有 NAT.** 游戏机 `192.168.1.2:100` 向服务器 `12.5.3.2:200` 发包，
源地址是私有地址。服务器能收到，但回包时公网路由器查不到到 `192.168.1.2`
的路由信息 —— 回不来。

**第二步 · 只重写 IP.** 路由器把源 IP 换成自己的公开 IP `18.19.20.21`。
服务器能回包到路由器了，但路由器不知道该转给内网哪台——它没记过是谁发出去的。

**第三步 · 同时重写 IP 和端口.** 路由器在 NAT 表里记一行
`(内网源 IP:端口, 外网端口, 目的 IP:端口)`，把源 IP 和源端口一起换成
`(路由器公开 IP, 随机分配的外网端口)`。回包按外网端口查表还原。

随机端口是必须的：只按源 IP 建表的话，内网多台主机连同一个外部服务器就分不开。
**这一步的真正意义是它直接穿透了网络层与传输层之间的抽象**——
NAT 在 IP 层动不了传输层语义，只好把传输层的端口当成 IP 地址的一部分来改写。

### 安全性补充

现代路由器还会在表项里记下**原始目的地址**。回包时先按源端口查表，
再校验回包的源 IP:端口是否等于当初发出去时的目的 IP:端口，不一致就丢弃。
所以「外网端口可达」不等于「能被打」。

## 作者省略的前提

> [!note] 本节是补出来的，不在原文里。

| 省略了什么 | 补出来是什么 | 来源 |
|---|---|---|
| 从没说 NAT 表项**为什么会消失** | 表项有老化超时。UDP 映射通常几分钟不刷新就回收。**打洞成功不等于永久通**——不持续发包，链路会自己断 | 推演 |
| 从没明说 NAT **只挡入站** | 出站完全不受限，而且**正是出站流量创建了映射表项**。这是 NAT 后面所有「连不上」问题的根源：没先发过包的一方天然不可达 | 推演 |
| 只在注释里顺带提了「对称 NAT」 | 完整分类是**端口保持**（cone，外网端口不随目标变化，STUN 可穿透）与**端口不复用**（symmetric，每个目标给不同端口，STUN 失效）。**判断自家路由器属于哪类，直接决定方案选型** | 见 §2.8 注释 + RFC 3489 分类 |
| 只说「TCP 使用不同的端口分配系统」 | **TCP 三次握手本身就是一次由客户端发起的入站报文**，SYN 一到，NAT 表项就建好了。客户端不需要任何辅助就能完成 UDP 侧 STUN 的那一整套。UDP 无连接、没有握手报文，所以才需要补丁 | 推演 |
| 「随机选取一个没有被使用的端口号」没说满了怎么办 | 外网端口空间有限（65535），每个内网 IP 都要分到端口。**分配失败时表项建不出来，表现为「偶尔连不上」** | 推演 |
| 「私有地址」的定义含混 | 见上文「注意措辞」——不可路由 ≠ 不存在 | 推演 |

其中「TCP 三次握手天然打洞」这一条会直接改变实现方式：
它解释了为什么 TCP 权威服务器架构**不需要任何打洞中继**，而 UDP P2P 架构绕不开。

## 成立条件与失效边界

| 条件 | 满足则 | 不满足则 |
|---|---|---|
| NAT 做端口级重写（而非只重写 IP） | 端口映射可用 | 极端配置下内网多主机无法并发对外通信 |
| NAT 端口保持（cone 型） | STUN 可穿透 | 对称 NAT 下 STUN 直接失效，需 TURN 中继 |
| 应用持续发包 | 表项被持续刷新 | 空闲超时后链路静默断开，表现为「玩着玩着掉线」 |
| 客户端先出站 | 自动建表 | **纯被动等待入站的服务器永远建不出表项** |
| TCP 三次握手正常完成 | 入站映射自动建立 | 中间设备严格拦 SYN 时需要 TCP 打洞（RFC 5128） |

## 与原文的出入

| 原文说 | 实际应为 | 依据 |
|---|---|---|
| 注释：「第 3 章将介绍 TCP 使用不同的端口分配系统，所以传输数据必然使用与侦听连接不同的端口」 | **这句直译后是错的。** TCP 连接不存在「数据端口与侦听端口分离」的问题——握手之后那条连接的端口就是客户端临时端口。原文想说的应是 UDP/TCP 端口复用策略的差异，被译者拧成了端口不等的断言 | 与 RFC 793 连接四元组的定义矛盾；且与上表「TCP 三次握手天然打洞」直接冲突 |

## 原文证据

> 「为了能够给真正的内部主机返回响应，路由器需要一些机制来识别传入数据包的内部接收者。
> 一种直观的方式是建立一个表来记录每个发出去的数据包的源 IP 地址……但是，如果多台内部
> 主机向同一台外部主机发送数据时，这种方法就失效了。」
> ——《网络多人游戏架构与编程》§2.8

> 「并不是所有的 NAT 都使用上述的 NAT 穿越技术。有些 NAT 给内部主机分配不一致的外部端口，
> 这样的 NAT 称为对称 NAT……这破坏了 STUN。」
> —— 同上，§2.8 注释

## 本项目落点

otf-server 走 **raw TCP 权威服务器**（M2，epoll LT）。NAT 在这个架构里的位置：

| 教材结论 | 落到哪 | 怎么落 |
|---|---|---|
| TCP 三次握手天然完成入站打洞 | `otf-server` 传输层选型 | **不需要 STUN / TURN / 中继服务器**——这是选 raw TCP 之外的额外收益，原文没点破 |
| 表项靠出站创建 | 客户端侧 | 玩家在家用宽带下主动连服务器，映射自动建立；**服务端不需要处理 NAT 表** |
| 表项会老化 | `技术参考.md` §10.3 断线 | 已有 **心跳 1Hz、5s 无包判死**，映射每秒刷新一次 → 空闲老化不会发生。**这条前提已被现有设计覆盖** |
| 纯被动入站的服务器建不出映射 | 演示环境 | 开发机在家里就是私有 IP。**成功标准第 1 条「4 人联机」演示最先撞的是这堵墙**：要么租一台有公网 IP 的 VPS，要么把服务器跑在有公网地址的机器上。此事 `技术参考.md` **目前没有记录** |
