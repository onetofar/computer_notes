### 核心结论
您的抓包结果**完全符合网络底层逻辑**，没有任何异常！
*   **WSL 抓到分片**：因为您将 MTU 设为 1500，2000 字节的 UDP 数据在 WSL 内核 IP 层被强制分片。
*   **Windows 抓到完整包**：因为 Windows 的 Hyper-V 虚拟交换机在内核中**静默重组**了分片，Wireshark 挂载在重组点之上，因此只看到重组后的完整大包。
### 一、 为什么 WSL/Docker 内抓到的是分片？
**前提条件**：您将 WSL 和 Docker 的 MTU 设置成了 1500。
1.  **发送端触发分片**：您的客户端代码 `src/udp_echo_client.cpp` 中 `#define MTU_LEN 2000`，调用 `sendto` 发送了 2000 字节的数据。
2.  **内核执行切片**：由于出口网卡 MTU 为 1500，WSL 内核的 IP 层在将包递交给网卡驱动前，执行了 IP 分片。将 2000 字节切成了 1480 + 520（加上 IP 头后分别为 1500 和 540，加上以太网帧头 14 字节即 1514 和 554）。
3.  **tcpdump 挂载点**：`tcpdump` 工作在内核协议栈和网卡驱动之间，它抓到的是**切片后**的数据包，因此明确显示 `Fragmented IP protocol`。
### 二、 为什么 Windows 抓到的是完整包？（最关键的反转）
这是 WSL2 虚拟化网络架构导致的经典“障眼法”。
1.  **Hyper-V 虚拟交换机的重组**：WSL2 并非通过真实网线与 Windows 相连，而是通过 Hyper-V 虚拟交换机（vSwitch）。当 Windows 内核接收到来自 WSL 的两个 IP 分片时，**Windows 的 IP 协议栈会在内核层自动将它们重组 (Reassemble) 回 2000 字节的完整 UDP 包**。
2.  **Wireshark 挂载点**：Wireshark 使用的 Npcap 驱动挂载在 Windows 内核协议栈的**上方**。因此，Wireshark 看到的是内核重组后的结果，直接显示为 `UDP Len=2000`。
3.  **虚拟链路 MTU 极大**：Windows 端的 `vEthernet (WSL)` 虚拟网卡默认 MTU 高达 65535，重组后的 2000 字节大包在 Windows 内部向应用层传递时，完全不需要再次分片。

### 三、 代码层面的隐患与建议

结合您的代码仓，虽然网络逻辑已通，但存在一个潜在的截断风险：

在 `src/udp_echo_client.cpp` 中：
```cpp
// PATH: src/udp_echo_client.cpp
#define MTU_LEN 2000
// ...
    char buffer[2048] = {0}; // 接收缓冲区
    ssize_t n = recvfrom(sockfd, buffer, sizeof(buffer) - 1, 0, ...);
```
您定义了 `MTU_LEN` 为 2000，接收缓冲区 `buffer` 为 2048。目前刚好够用，但如果未来您测试更大的包（如 4000 字节），`recvfrom` 将截断数据。建议将缓冲区放大：
```cpp
    char buffer[65535] = {0}; // 防止重组后的大包被截断
```

### 四、 如何在 Windows 上看到分片？

如果您想在 Windows 端也验证分片的存在，只需在 Wireshark 中关闭 IP 重组功能：
1. 点击菜单栏 `Edit` -> `Preferences`。
2. 展开 `Protocols` -> 找到 `IPv4`。
3. **取消勾选 `Reassemble fragmented IPv4 datagrams`**。
4. 此时您将在 Windows 端也看到那两个 `Fragmented IP protocol` 数据包。
