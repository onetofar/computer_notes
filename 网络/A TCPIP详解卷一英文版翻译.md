# 第 13 章 TCP 连接管理
## 13.1 引言
TCP 是一种面向连接的单播协议。在任意一端向另一端发送数据之前，必须先在两者之间建立连接。在本章中，我们将详细探讨 TCP 连接是什么、如何建立连接，以及如何终止连接。回顾一下，TCP 的服务模型是字节流。TCP 会检测并修复 IP 层（或更低层）可能引入的几乎所有数据传输问题，包括丢包、重复或错误。
由于 TCP 需要管理连接状态（两端端点维护的与连接相关的信息），它比 UDP（参见第 10 章）要复杂得多。UDP 是无连接协议，无需建立或终止连接。两者的主要区别之一是，正确处理各种 TCP 状态（连接创建、正常终止和异常重置）所需的细节量。在后续章节中，我们将介绍连接建立后的数据传输过程。
在连接建立过程中，两端点之间可以交换多个与连接参数相关的选项。有些选项仅允许在连接建立时发送，其他选项则可以在后续发送。回顾第 12 章，TCP 首部用于存放选项的空间有限（40 字节）。
## 13.2 TCP 连接的建立与终止
TCP 连接被定义为包含两个 IP 地址和两个端口号的四元组。更准确地说，它是一对端点（或套接字），每个端点由（IP 地址，端口号）对标识。
连接通常会经历三个阶段：建立、数据传输（称为已建立状态）和拆除（关闭）。我们将看到，创建健壮的 TCP 实现的难点之一是正确处理这些阶段之间及阶段内部的所有状态转换。图 13-1 展示了一次无任何数据传输的典型 TCP 连接建立与关闭过程。
图 13-1 正常 TCP 连接的建立与终止
![[md_pict/image-20260530141216520.png]]
通常，客户端发起三次握手，交换客户端和服务器 SYN 段中携带的初始序列号（分别为 ISN(c)和 ISN(s)）。连接在双方都发送 FIN 并收到对应的确认后终止。
该图展示了连接建立过程中发生的事件时间线。要建立 TCP 连接，通常会发生以下事件：
1. 主动打开方（通常称为客户端）发送一个 SYN 段（即 TCP 首部中 SYN 比特位置 1 的 TCP/IP 报文），指定其想要连接的对端端口号，以及客户端的初始序列号 ISN(c)（参见 13.2.3 节）。此时它通常还会发送一个或多个选项（参见 13.3 节）。这是第 1 个段。
2. 服务器回复一个包含其初始序列号 ISN(s)的 SYN 段。这是第 2 个段。服务器还会通过确认 ISN(c) + 1 来确认客户端的 SYN。一个 SYN 会占用一个序列号，若丢失则会被重传。
3. 客户端必须通过确认 ISN(s) + 1 来确认服务器的这个 SYN。这是第 3 个段。
这三个段完成了连接的建立过程，通常称为 **三次握手**。其主要目的是让连接的两端都知道连接即将启动、选项中携带的特殊细节，以及交换初始序列号。
发送第一个 SYN 的一端被称为执行 **主动打开**。如前所述，这通常是客户端。接收该 SYN 并发送下一个 SYN 的另一端执行 **被动打开**，通常称为服务器。（13.2.2 节将介绍一种受支持但不常见的同时打开场景，此时双方同时执行主动打开，同时成为客户端和服务器。）
> 注意：TCP 支持在 SYN 段中携带应用层数据。不过这一功能很少被使用，因为伯克利套接字 API 不支持该特性。
图 13-1 还展示了 TCP 连接如何关闭（也称为清除或终止）。任意一端都可以发起关闭操作，也支持同时关闭，但这种情况很少见。传统上，客户端发起关闭最为常见（如图 13-1 所示）。不过，其他服务器（如 Web 服务器）也会在完成请求后发起关闭。通常，关闭操作始于应用层表明其希望终止连接（例如调用 close()系统调用）。发起关闭的 TCP 会发送一个 FIN 段（即 FIN 比特位置 1 的 TCP 段）。完整的关闭操作在双方都完成关闭后发生：
1. 主动关闭方发送一个 FIN 段，指定接收方期望看到的当前序列号（图 13-1 中为 K）。该 FIN 还包含一个 ACK，用于确认另一端之前发送的最后一个数据（图 13-1 中标记为 L）。
2. 被动关闭方回复 ACK 值 K + 1，表明已成功收到主动关闭方的 FIN。此时，应用层会收到通知，告知其对端已终止该方向的数据流。这通常会导致应用层发起自身的关闭操作。随后被动关闭方实际上会变为另一个主动关闭方，并发送自己的 FIN，序列号等于 L。
3. 为完成关闭过程，最后一个段包含对最后一个 FIN 的 ACK。注意，如果 FIN 丢失，它会被重传，直到收到对应的 ACK 为止。
建立连接需要 3 个段，而终止连接需要 4 个段。连接也可能处于半开状态（参见 13.6.3 节），不过这种情况并不常见。这是因为 TCP 的数据通信模型是双向的，即两个方向中可以仅有一个方向处于工作状态。TCP 的半关闭操作仅关闭数据流的一个方向。两次半关闭操作共同完成整个连接的关闭。规则是，任意一端在发送完数据后都可以发送 FIN。当 TCP 收到一个 FIN 时，它必须通知应用层，对端已终止该方向的数据流。发送 FIN 通常是应用层发起 close 操作的结果，这通常会导致两个方向的连接都被关闭。
我们看到的这 7 个段是任何正常建立和“优雅”清除的 TCP 连接的基线开销。（还有更粗暴的方式使用特殊的复位段来终止 TCP 连接，我们将在后续介绍。）当需要交换少量数据时，现在很容易理解为什么有些应用程序更倾向于使用 UDP——它无需建立连接即可收发数据。不过，这类应用程序随后需要自行处理错误修复、拥塞管理和流量控制。
### 13.2.1 TCP 半关闭（TCP Half-Close）
正如我们前文所述，TCP 支持半关闭操作。但极少有应用需要这一能力，因此它并不常见。要使用该特性，API 必须为应用提供一种方式，让应用可以向对端表明：“我已经完成数据发送，请向对端发送 FIN，但我仍希望接收来自对端的数据，直到它向我发送 FIN 为止。”伯克利套接字 API 支持半关闭：当应用调用 `shutdown()` 函数而非更常见的 `close()` 函数时，即可启用该功能。不过，大多数应用都会通过调用 `close()` 终止连接的双向传输。图 13-2 展示了一个半关闭的使用示例，图中左侧的客户端发起了半关闭，但任意一端都可以发起半关闭。
![[md_pict/image-20260530155853110.png]]
半关闭的前两个报文段与常规关闭流程相同：发起方发送 FIN，接收方随后对该 FIN 回复 ACK。此后流程与图 13-1 不同：接收到半关闭请求的一端仍可发送数据。**图中仅展示了一个数据段及其对应的 ACK，但实际上可以发送任意数量的数据段**（我们将在第 15 章详细讨论数据段与确认报文的交互）。当接收到半关闭请求的一端完成数据发送后，会关闭自身的连接端并发送 FIN，这会向发起半关闭的应用传递文件结束（EOF）指示。当第二个 FIN 被确认后，连接完全关闭。
### 13.2.2 同时打开与同时关闭（Simultaneous Open and Close）
两个应用同时向对方执行主动打开操作是可能的，但除非特意安排，否则这种情况发生的概率极低。双方必须在收到对方的 SYN 之前，先发送自己的 SYN；这两个 SYN 报文必须在网络中交错传输。该场景还要求双方的 IP 地址和端口号都被对方知晓，这种情况并不常见（第 7 章介绍的防火墙“打洞”技术除外）。这种情况被称为 **同时打开（simultaneous open）**。
例如，当主机 A 上使用本地端口 7777 的应用向主机 B 的 8888 端口发起主动打开，同时主机 B 上使用本地端口 8888 的应用向主机 A 的 7777 端口发起主动打开时，就会发生同时打开。这与“主机 A 的客户端连接主机 B 的服务器，同时主机 B 的客户端连接主机 A 的常规服务器”的场景不同：在后一种场景中，两台服务器执行的是被动打开而非主动打开，客户端会分配不同的临时端口，因此会形成两条独立的 TCP 连接。图 13-3 展示了同时打开过程中交换的报文段。
![[md_pict/image-20260531124005734.png]]
同时打开需要交换四个报文段，比常规的三次握手多一个。注意，此时无法将任何一端称为客户端或服务器，因为双方同时扮演客户端和服务器的角色。**同时关闭（simultaneous close）** 的情况与之差异不大。我们之前提到，通常由一端（通常是客户端，但并非总是如此）执行主动关闭，发送第一个 FIN；而在同时关闭中，双方都会主动发送 FIN。图 13-4 展示了同时关闭过程中交换的报文段。

同时关闭过程中交换的报文段数量与常规关闭流程相同，唯一的实际区别是报文段的传输顺序是交错的，而非顺序执行的。后续我们将看到，同时打开和同时关闭操作会用到 TCP 实现中一些不常被触发的特定状态。

### 13.2.3 初始序列号 (ISN)
当连接处于打开状态时，只要报文段包含正确的两端 IP 地址和端口号，且序列号有效（即处于接收窗口范围内）、校验和正确，就会被视为有效报文并被接收。这就引出了一个问题：网络中是否可能出现延迟到达的 TCP 报文段，混入后续的连接并干扰正常通信？这一风险可通过精心选择初始序列号（ISN）来规避，本节将详细探讨这一机制。
在通信双方发送 SYN 报文建立连接前，会为该连接选择一个初始序列号（ISN）。ISN 需随时间变化，确保每个连接的 ISN 均不相同。[RFC0793] 规定，ISN 应被视为一个每 4 微秒自增 1 的 32 位计数器。这样设计的目的，是避免同一连接的报文段序列号与新的、相同的连接的序列号发生重叠。尤其需要确保：同一连接的不同实例（或称为“化身”）之间，新的序列号不能与旧序列号重叠。
理解“同一连接的不同实例”这一概念，需要回顾 TCP 连接的标识方式：TCP 连接由一对端点定义，即一个由两个地址/端口对组成的四元组。假设一个连接的某个报文段在网络中长时间滞留，随后该连接被关闭，又以相同的四元组重新打开，那么滞留的旧报文段就可能作为有效数据混入新连接的数据流中，引发严重问题。通过避免不同连接实例之间的序列号重叠，可将这种风险降至最低。不过，这也提示：对数据完整性要求极高的应用，应在应用层使用自定义的循环冗余校验（CRC）或校验和，确保数据传输无误。这是通用的良好实践，在大文件传输场景中尤为常见。
后续章节会说明，伪造一个对接收端有效的 TCP 报文段，只需知道连接的四元组、当前活动的序列号窗口即可。这构成了 TCP 的一个安全漏洞：攻击者若能猜测出序列号、IP 地址和端口号，就可伪造 TCP 报文段并中断现有连接 [RFC5961]。抵御此类攻击的方法之一，是让初始序列号（或临时端口号 [RFC6056]）变得难以猜测；另一种方法是使用加密机制（详见第 18 章）。
在现代系统中，ISN 通常以半随机方式生成。关于正确实现这一机制的细节，CERT 公告 CA-2001-09 [CERTISN] 中有详细讨论。Linux 系统的 ISN 生成流程较为复杂：它采用基于时钟的方案，但每个连接的时钟起始值会加入随机偏移量。该随机偏移量由连接标识符（四元组）经过密码学哈希函数计算得出，且哈希函数的密钥输入每 5 分钟更新一次。ISN 的 32 位中，最高 8 位与密钥的序列号相关，其余位由哈希计算生成。这种方式生成的 ISN 既难以被猜测，又能随时间递增。据报道，Windows 系统采用了基于 RC4 流密码的类似方案 [S96]。

### 13.2.4 例子

了解 TCP 连接的建立与释放流程后，我们来看具体的报文级交互细节。我们通过 Windows 上的 Telnet 客户端，向 IPv4 地址为 `10.0.0.2` 的本地 Web 服务器发起 TCP 连接：

```cmd
C:\> telnet 10.0.0.2 80
Welcome to Microsoft Telnet Client
Escape Character is 'CTRL+]'
... wait about 4.4 seconds ...
Microsoft Telnet> quit
```

`telnet` 命令会向 `10.0.0.2` 的 80 端口（HTTP/Web 服务的知名端口）发起 TCP 连接。当 Telnet 客户端连接到非 23 端口（Telnet 协议的知名端口 [RFC0854]）时，不会执行 Telnet 应用层协议，仅将用户输入的字节复制到 TCP 连接中，同时将从 TCP 连接收到的字节输出到终端。Web 服务器收到连接请求后，会等待客户端发送网页请求；本示例中我们未发送任何请求，因此服务器不会返回数据。这一场景非常适合我们的分析需求，因为我们只需关注连接建立和终止过程中的报文交互。图 13-5 展示了该命令产生的报文段的 Wireshark 抓包结果。

![[md_pict/image-20260531135220592.png]]

从抓包结果可见：
客户端首先发送一个 SYN 报文，其中包含初始序列号（ISN）`685506836`，窗口通告值为 `65535`，报文还包含多个 TCP 选项（详见第 13.3 节）。
第二个报文段是服务器的 SYN 报文，同时也是对客户端 SYN 的确认报文：服务器的初始序列号为 `1479690171`，确认号为 `685506837`（比客户端的 ISN 大 1），表明服务器已成功接收客户端的 SYN。该报文还包含窗口通告值，表明服务器最多可接收 `64240` 字节的数据。
第三次握手由第三个报文段完成，其确认号为 `1479690172`。注意：确认号是 **累计确认** 的，始终表示确认方期望收到的下一个字节的序列号（而非最后收到的字节的序列号）。

约 4.4 秒的停顿后，用户通过 `quit` 命令关闭连接，客户端 TCP 层随即发送 FIN 报文（第 4 个报文段），其序列号为 `685506837`，服务器在第 5 个报文段中对该 FIN 进行确认（确认号为 `685506838`）。随后，服务器发送自身的 FIN 报文（序列号为 `1479690172`），该报文还会再次对客户端的 FIN 进行冗余确认。注意，此时 PSH（推送）标志位被置为 1，这对连接关闭无实际影响，但通常表示服务器没有更多数据需要发送。最后一个报文段包含确认号 `1479690173`，对服务器的 FIN 进行确认。

> **注**：[RFC1025] 将启用了所有特性（如标志位和选项）的报文段称为“神风特攻队报文（Kamikaze packet）”，其他形象的称呼还包括“恶意报文（nastygram）”“圣诞树报文（Christmas tree packet）”和“灯测试报文（lamp test segment）”。

从图 13-5 中我们可以看到，SYN 报文段包含一个或多个选项。这些选项会占用 TCP 头部的额外空间。例如，第一个 TCP 头部的长度为 44 字节，比最小长度大 24 字节。TCP 支持多种选项，我们将在了解连接建立失败的情况后详细说明这些选项。

### 13.2.5 连接超时建立

TCP 连接可能因多种原因无法建立，最常见的情况是服务器主机宕机。为模拟这一场景，我们向同一子网内一个不存在的主机发起 Telnet 连接：

- 若不修改 ARP 表，客户端会因 ARP 请求未收到任何回复而直接退出，并提示“No route to host（无法到达主机）”错误（详见第 4 章 ARP 协议）。
- 若先在 ARP 表中添加一个不存在主机的静态 ARP 条目，系统将不会发送 ARP 请求，而是直接尝试通过 TCP/IP 与该主机通信。

相关命令如下：

```bash
Linux# arp -s 192.168.10.180 00:00:1a:1b:1c:1d
Linux% date; telnet 192.168.10.180 80; date
Tue June  7 21:16:34 PDT 2009
Trying 192.168.10.180...
telnet: connect to address 192.168.10.180: Connection timed out
Tue June  7 21:19:43 PDT 2009
Linux%
```

此处使用的 MAC 地址 `00:00:1a:1b:1c:1d` 仅为局域网中未被使用的地址，无特殊含义。从执行初始命令到连接超时，大约经过了 3.2 分钟。由于没有主机响应，所有产生的报文段均来自客户端。清单 13-1 展示了连接建立超时过程中的 Wireshark 抓包结果（文本模式的报文摘要）：

| No.  | Time      | Source         | Destination    | Protocol | Info               |
| ---- | --------- | -------------- | -------------- | -------- | ------------------ |
| 1    | 0.000000  | 192.168.10.144 | 192.168.10.180 | TCP      | 32787 > http [SYN] |
| 2    | 2.997928  | 192.168.10.144 | 192.168.10.180 | TCP      | 32787 > http [SYN] |
| 3    | 8.997962  | 192.168.10.144 | 192.168.10.180 | TCP      | 32787 > http [SYN] |
| 4    | 20.997942 | 192.168.10.144 | 192.168.10.180 | TCP      | 32787 > http [SYN] |
| 5    | 44.997936 | 192.168.10.144 | 192.168.10.180 | TCP      | 32787 > http [SYN] |
| 6    | 92.997937 | 192.168.10.144 | 192.168.10.180 | TCP      | 32787 > http [SYN] |

抓包结果中值得关注的是客户端 TCP 发送 SYN 报文的频率：第二个报文在第一个报文发送 3 秒后发出，第三个在第二个报文发送 6 秒后发出，第四个在第三个报文发送 12 秒后发出，以此类推。这种行为称为 **指数退避（exponential backoff）**，与以太网 CSMA/CD 介质访问控制协议中的退避机制类似（详见第 3 章），但两者存在差异：TCP 的退避时间是确定性的（始终为前一次的两倍），而以太网中是最大退避时间加倍，实际退避时间随机选择。

部分系统支持配置初始 SYN 报文的重试次数，通常默认值较小（如 5 次）。在 Linux 系统中：

- `net.ipv4.tcp_syn_retries`：系统配置变量，定义主动打开连接时重发 SYN 报文的最大次数。
- `net.ipv4.tcp_synack_retries`：对应变量，定义响应对端主动打开请求时重发 SYN+ACK 报文的最大次数。
也可通过 Linux 特有的 `TCP_SYNCNT` 套接字选项，针对单个连接设置重试次数，默认值为 5 次，与本示例一致。这些重传之间的指数退避机制，是 TCP 拥塞控制的一部分，后续讨论卡恩算法（Karn's algorithm，详见第 16 章）时会详细说明。

### 13.2.6 连接与地址转换设备（Connections and Translators）

第 7 章我们讨论了传统 NAT 如何对 TCP、UDP 等协议使用的地址和端口号进行转换，也分析了 IPv6 与 IPv4 之间的 IP 报文转换方式。当 NAT 与 TCP 配合使用时，伪首部校验和通常需要重新计算调整（使用校验和中立的地址修改器的情况除外）。对于其他使用伪首部校验和的协议而言，情况同样如此，因为伪首部校验和的计算同时涉及传输层和网络层的信息。

当 TCP 连接首次建立时，NAT（或 NAT64）可通过报文段中的 `SYN` 标志位识别这一事件；它也可通过后续携带正确序列号的 `SYN+ACK` 和 `ACK` 报文段，判断连接是否已完全建立。连接终止过程同理。NAT 中通过实现部分 TCP 状态机逻辑（例如见 [RFC6146] 的 3.5.2.1 和 3.5.2.2 节），即可对连接进行跟踪，包括连接当前状态、双向的序列号以及对应的确认号。这类状态跟踪是 NAT 实现中的典型做法。

当 NAT 作为 “编辑者” 修改传输层协议数据载荷的内容时，会带来更多复杂问题。对于 TCP 而言，这类操作可能涉及向数据流中添加或删除字节，进而影响序列号（以及报文段长度）。这一操作必然会影响校验和，同时也会改变数据的序列。如果 NAT 在数据流中插入或删除了数据，上述字段的值都需要进行相应调整。这类调整机制本身较为脆弱：一旦 NAT 的状态与终端主机的状态失去同步，连接将无法正常工作。

# 第 14 章 TCP 超时与重传（TCP Timeout and Retransmission）

## 14.1 介绍（Introduction）

效率与性能是我们迄今为止尚未深入讨论的话题。此前我们主要关注的是 TCP 的操作正确性。在本章及接下来的两章中，我们不仅会探讨 TCP 的基础任务，还会分析其执行这些任务的性能表现。TCP 协议通过底层可能丢失、重复或乱序交付数据包的 IP 网络层，为两个应用提供可靠的数据交付服务。为了实现无差错的数据交换，TCP 会重传它认为丢失的数据。为了确定需要重传哪些数据，TCP 依赖接收方持续向发送方发送确认报文流。当数据段或确认报文丢失时，TCP 会触发对未确认数据的重传。TCP 有两种独立的重传机制：**一种基于时间，另一种基于确认报文的结构**。第二种方式通常比第一种高效得多。

TCP 在发送数据时会启动定时器，如果定时器超时数据仍未得到确认，就会发生超时或基于定时器的重传。超时发生在一个称为 **重传超时（Retransmission Timeout, RTO）** 的时间间隔之后。TCP 还有另一种触发重传的方式，称为 **快速重传（fast retransmission）**，通常无需延迟即可触发。快速重传的原理是：通过观察一段时间内收到的累积确认（ACK）没有向前推进，或者携带选择确认（Selective Acknowledgment, SACK）信息的 ACK 表明接收方存在乱序报文段，来推断数据丢失。一般来说，当发送方认为接收方可能缺失某些数据时，需要在发送新的（未发送过的）数据和重传数据之间做出选择。本章我们将深入探讨 TCP 如何判断报文段是否丢失，以及在这种情况下应发送什么内容。关于“发送多少数据”的问题，将推迟到第 16 章讨论，届时我们将介绍 TCP 的拥塞控制机制——这一机制通常在怀疑数据包丢失时被触发。我们将研究 RTO 如何基于连接的往返时间（Round-Trip Time, RTT）测量值进行设置，基于定时器的重传机制如何工作，以及 TCP 的快速重传机制如何运作。我们还将探讨 SACK 如何帮助 TCP 发送方确定接收方缺失的数据，IP 数据包的乱序与复制对 TCP 行为的影响，以及 TCP 重传时如何调整报文段大小。此外，我们还会简要介绍一些试图欺骗 TCP 使其表现得更激进或更被动的攻击方式。

1. 第 8 章的 ICMP 目的不可达（端口不可达）场景中，我们看到使用 UDP 的 TFTP 客户端采用了一种简单（但效果不佳）的超时与重传策略：它假设 5 秒是一个合适的超时周期，每 5 秒重传一次。
2. 第 13 章中，当 TCP 尝试连接不存在的主机时，我们看到它每次重传 SYN 报文段的延迟会越来越长。
3. 第 3 章中，我们看到以太网发生冲突时的处理机制。
所有这些机制，都是由定时器到期触发的。

```
Connection closed by foreign host.
```

从逻辑上看，TCP 有两个阈值，决定了它重传同一报文段的持久程度。这些阈值在《主机需求 RFC》[RFC1122] 中有定义，我们在第 13 章也简要提到过：

- **阈值 R1**：TCP 在向 IP 层传递“负向建议”（例如触发 IP 重新评估路由）之前，重传报文段的次数（或等待的时间）。
- **阈值 R2**：大于 R1，决定了 TCP 应该放弃连接的时间点。RFC 建议，对于连接建立阶段（发送 SYN 报文段），R1 至少为 3 次重传，R2 至少为 100 秒；对于数据报文段，这些值可能不同，SYN 报文段的 R2 值至少为 3 分钟。

在 Linux 系统中，普通数据报文段的 R1 和 R2 值可由应用修改，也可通过系统配置变量 `net.ipv4.tcp_retries1` 和 `net.ipv4.tcp_retries2` 分别修改，单位为重传次数，而非时间。`tcp_retries2` 的默认值为 15，根据连接的 RTO 不同，对应约 13-30 分钟；`net.ipv4.tcp_retries1` 的默认值为 3。对于 SYN 报文段，`net.ipv4.tcp_syn_retries` 和 `net.ipv4.tcp_synack_retries` 变量限制了 SYN 报文段的重传次数，默认值为 5 次（约 180 秒）。Windows 系统也有一系列影响 TCP 整体行为的变量，包括对应 R1 和 R2 的值，可通过修改以下注册表项设置：

```
HKEY_LOCAL_MACHINE\System\CurrentControlSet\Services\Tcpip\Parameters
HKEY_LOCAL_MACHINE\System\CurrentControlSet\Services\Tcpip6\Parameters
```

需要重点关注的是名为 `TcpMaxDataRetransmissions` 的参数，它对应 Linux 中的 `tcp_retries2` 配置项，默认值为 5。即便在我们目前看到的简单重传示例中，TCP 也需要为其重传定时器分配一个超时值，以指定它应等待发送数据的 ACK 多久。如果 TCP 仅在单一静态环境中使用，就可以为超时值确定一个特定的正确数值。但由于 TCP 需要在多种环境中运行，且这些环境本身可能随时间变化，TCP 需要根据当前情况动态确定超时值。例如，如果网络链路故障，流量被重新路由，RTT（往返时间）就会发生变化（甚至可能是大幅变化）。换句话说，TCP 需要动态确定其 RTO（重传超时时间）。接下来我们将探讨这一问题。

---

## 14.3 设置重传超时时间（RTO）（Setting the Retransmission Timeout (RTO)）

TCP 超时与重传机制的核心，是如何基于特定连接的 RTT（往返时间）测量值来设置 RTO。如果 TCP 重传报文段的时间早于 RTT，可能会不必要地向网络中注入重复流量；反之，如果在流量丢失时，延迟远大于一个 RTT 再发送，整体网络利用率（以及单连接吞吐量）会下降。准确掌握 RTT 的难度很大，因为随着路由和网络使用情况的变化，RTT 可能会随时间改变。TCP 必须跟踪这些变化，并相应调整超时时间，以维持良好的性能。

由于 TCP 在收到数据时会发送确认报文，因此可以发送一个带有特定序列号的字节，并测量收到覆盖该序列号的确认报文所需的时间。每次这样的测量称为一次 **RTT 样本**。TCP 面临的挑战是，如何根据随时间变化的样本，为一系列 RTT 值建立一个良好的估计。第二步是如何基于这些样本设置 RTO。正确设置 RTO 对 TCP 的性能至关重要。

每个 TCP 连接都会单独估计 RTT，并且只要有消耗序列号的数据（包括 SYN 和 FIN 报文段）处于传输中，就会启动一个重传定时器。如何正确设置该定时器的问题已经研究多年，相关改进也在不断推出。在本节中，我们将探讨计算 RTO 所使用的方法的一些重要里程碑，首先介绍 [RFC0793] 中详细描述的第一种（“经典”）方法。

---

### 14.3.1 经典方法（The Classic Method）

原始 TCP 规范 [RFC0793] 规定，TCP 应使用以下公式更新平滑往返时间估计器（称为 SRTT）：

$$
\text{SRTT} \leftarrow \alpha(\text{SRTT}) + (1 - \alpha) \text{RTT}_s
$$

这里，SRTT 会根据其现有值和新的样本 $\text{RTT}_s$ 进行更新。常数 $\alpha$ 是平滑因子（或比例因子），推荐取值在 0.8 到 0.9 之间。每次进行新的测量时，SRTT 都会更新。使用推荐的 $\alpha$ 值时，每次新估计值的 80%到 90%来自之前的估计值，仅 10%到 20%来自新的测量值。这种平均方法也被称为 **指数加权移动平均（EWMA）** 或低通滤波器。出于实现便利，它只需要存储一个之前的 SRTT 值即可维护运行估计。

基于随 RTT 变化的估计器 SRTT，[RFC0793] 建议将 RTO 设置为以下值：

$$
\text{RTO} = \min(\text{ubound}, \max(\text{lbound}, (\text{SRTT})\beta))
$$

其中 $\beta$ 是延迟方差因子，推荐取值在 1.3 到 2.0 之间；`ubound` 是 RTO 的上限（例如建议为 1 分钟）；`lbound` 是 RTO 的下限（例如建议为 1 秒）。我们将这种赋值过程称为 **经典方法**。它通常会导致 RTO 被设置为 1 秒，或约为 SRTT 的两倍。对于相对稳定的 RTT 分布，这种方法是足够的。然而，当 TCP 在 RTT 波动较大的网络（例如早期的分组无线网络）上运行时，它的表现并不理想。

---

### 14.3.2 标准方法（The Standard Method）

在 [J88] 中，Jacobson 进一步详细说明了经典方法的问题——基本上，[RFC0793] 规定的定时器无法跟上 RTT 的大幅波动（特别是当实际 RTT 远大于预期时，会导致不必要的重传）。不必要的重传会在网络已负载较高时增加网络负载，这一点可以通过不断增大的样本 RTT 体现出来。

为了解决这个问题，用于分配 RTO 的方法得到了增强，以适应 RTT 测量值中更大的波动。这是通过除了估计 RTT 的平均值外，还跟踪 RTT 测量值的可变性估计来实现的。基于平均值和可变性估计值设置 RTO，比仅将 RTO 计算为平均值的固定倍数，能更好地响应往返时间的大幅波动。

[J88] 中的图 5 和图 6 展示了实际往返时间对应的 [RFC0793] 的 RTO 值，与我们接下来展示的考虑了往返时间可变性的 RTO 计算值的对比。如果我们将 TCP 进行的 RTT 测量视为统计过程的样本，估计平均值和方差（或标准差）有助于更好地预测该过程未来可能取的值。对 RTT 可能取值范围的良好预测，有助于 TCP 在大多数情况下确定一个既不过大也不过小的 RTO。

正如 Jacobson 所描述的，**平均偏差** 是标准差的良好近似，但计算起来更简单、更快速。计算标准差需要对方差执行平方根运算，这在当时被认为对于快速 TCP 实现来说成本过高（这并非全部，可参考 [G04] 中关于“这场辩论”的有趣历史）。因此，我们需要同时维护平均值和平均偏差的运行估计。这就得到了以下应用于每个 RTT 测量值 $M$（前面称为 $\text{RTT}_s$）的公式：

$$
\text{srtt} \leftarrow (1 - g)(\text{srtt}) + (g)M
$$

$$
\text{rttvar} \leftarrow (1 - h)(\text{rttvar}) + (h)(|M - \text{srtt}|)
$$

$$
\text{RTO} = \text{srtt} + 4(\text{rttvar})
$$

这里，`srtt` 实际上替代了之前的 SRTT 值，而 `rttvar`（作为平均偏差的 EWMA）替代了 $\beta$，用于帮助确定 RTO。这组公式也可以写成传统计算机上实现时运算次数更少的形式：

$$
\text{Err} = M - \text{srtt}
$$

$$
\text{srtt} \leftarrow \text{srtt} + g(\text{Err})
$$

$$
\text{rttvar} \leftarrow \text{rttvar} + h(|\text{Err}| - \text{rttvar})
$$

$$
\text{RTO} = \text{srtt} + 4(\text{rttvar})
$$

如前所述，`srtt` 是平均值的指数加权移动平均（EWMA），`rttvar` 是绝对误差 $|\text{Err}|$ 的指数加权移动平均。`Err` 是测量值 $M$ 与当前 RTT 估计值 `srtt` 之间的差值。`srtt` 和 `rttvar` 都用于计算随时间变化的 RTO。增益 $g$ 是给予新 RTT 样本 $M$ 在平均值 `srtt` 中的权重，设置为 $1/8$；增益 $h$ 是给予新平均偏差样本（新样本 $M$ 与运行平均值 `srtt` 的绝对差）在偏差估计 `rttvar` 中的权重，设置为 $1/4$。偏差估计的增益更大，使得当 RTT 变化时，RTO 上升得更快。$g$ 和 $h$ 的值被选为 2 的负幂，允许使用定点整数算术，通过移位和加法运算而非乘法和除法来实现整体计算。

> **注**：[J88] 在 RTO 计算中指定了 $2 \times \text{rttvar}$，但经过进一步研究，[J90] 将该值改为 $4 \times \text{rttvar}$，这出现在 BSD Net/1 实现中，并最终成为标准 [RFC6298]。

将经典方法与 Jacobson 的方法进行比较，我们发现 RTT 平均值的计算是相似的（$\alpha$ 是 $1$ 减去增益 $g$），但使用了不同的增益。此外，Jacobson 的 RTO 计算同时依赖于平滑的 RTT 和平滑的偏差，而经典方法仅使用平滑 RTT 的简单倍数。这是如今许多 TCP 实现计算其 RTO 的基础，并且由于其被采纳为 [RFC6298] 的基础，我们将其称为 **标准方法**，尽管 [RFC6298] 中还有一些细微的改进，我们现在将讨论这些改进。

---

#### 14.3.2.1 时钟粒度与 RTO 边界（Clock Granularity and RTO Bounds）

TCP 在进行 RTT 测量时使用一个持续运行的“时钟”。与初始序列号一样，真实 TCP 连接的时钟并非从零开始，也没有无限精度。相反，TCP 时钟通常是一个随系统时钟推进而更新的变量，不一定是一一对应的。TCP 时钟“滴答”的长度称为其 **粒度**。传统上，这个值相对较大（约 500ms），但更多近期实现使用更细粒度的时钟（例如 Linux 的 1ms）。

粒度会影响 RTT 测量的细节以及 RTO 的设置方式。在 [RFC6298] 中，粒度被用于细化 RTO 更新的方式。此外，还对 RTO 设置了下限。使用的公式如下：

$$
\text{RTO} = \max(\text{srtt} + \max(G, 4(\text{rttvar})), 1000)
$$

其中 $G$ 是定时器粒度，$1000\text{ms}$ 表示 RTO 的总下限（由 [RFC6298] 的规则(2.4)推荐）。因此，RTO 始终至少为 1 秒。还允许设置可选的上限，前提是其值至少为 60 秒。

---

#### 14.3.2.2 初始值（Initial Values）

我们已经看到估计值如何随时间更新，但我们还需要知道如何设置它们的初始值。在第一次 SYN 交换之前，TCP 不知道使用什么值来设置初始 RTO，也不知道使用什么值作为估计器的初始值，除非系统在此时提供了提示（某些系统会在转发表中缓存此信息；参见第 14.9 节）。根据 [RFC6298]，RTO 的初始设置应为 1 秒，不过当初始 SYN 报文段发生超时时，会使用 3 秒。当收到第一个 RTT 测量值 $M$ 时，估计器的初始化如下：

$$
\text{srtt} \leftarrow M
$$

$$
\text{rttvar} \leftarrow M/2
$$

现在我们有足够的细节来了解估计器的初始化和维护方式。这些过程依赖于获取 RTT 样本，这看起来很简单。现在我们来讨论为什么情况并非总是如此。

#### 14.3.2.3 重传歧义与卡恩算法（Retransmission Ambiguity and Karn’s Algorithm）

当一个报文段被重传时，测量 RTT 样本会出现一个问题。假设一个报文段被发送，发生超时，报文段被重传，随后收到了对应的确认。这个确认是针对第一次传输还是第二次传输的？这就是 **重传歧义问题**。它的发生是因为除非使用时间戳选项，否则确认仅提供确认号，无法指示正在确认的是某个序列号的哪一个副本（例如第一次还是第二次）。

论文 [KP87] 规定，当发生超时和重传时，我们不能在重传数据的确认最终到达时更新 RTT 估计器。这是 **卡恩算法（Karn's Algorithm）** 的第一部分。它通过消除计算 RTT 估计时的歧义来解决确认歧义问题。这是 [RFC6298] 中的一项要求。

然而，如果我们在设置 RTO 时完全忽略重传的报文段，我们将无法利用网络提供的一些有用信息（即网络可能正经历某种形式的无法快速交付数据包的问题）。在这种情况下，降低重传率以减轻网络负载是有益的，至少在数据包不再丢失之前是这样。这种推理是我们在图 14-1 中看到的指数退避行为的基础。

TCP 会对 RTO 应用退避因子，每次后续重传定时器超时时，退避因子翻倍。翻倍会持续到收到未重传的报文段的确认为止。此时，退避因子被重置为 1（即二进制指数退避被取消），重传定时器恢复为正常值。对后续重传翻倍退避因子是卡恩算法的第二部分。请注意，当 TCP 超时时，它还会调用拥塞控制过程来改变其发送速率（拥塞控制将在第 16 章详细讨论）。因此，卡恩算法实际上由两部分组成。正如 1987 年论文 [KP87] 中直接引用的：
> 当对已发送多次（即至少重传过一次）的数据包的确认到达时，忽略基于该数据包的任何往返时间测量，从而避免重传歧义问题。此外，该数据包的退避后的 RTO 会为下一个数据包保留。只有当它（或后续数据包）在没有中间重传的情况下被确认时，RTO 才会从 SRTT 重新  计算。

该算法作为 TCP 实现的必需流程已经有一段时间了（自 [RFC1122] 起）。不过，当使用 TCP 时间戳选项时（参见第 13 章）存在例外。在这种情况下，可以避免确认歧义问题，卡恩算法的第一部分不适用。

#### 14.3.2.4 带时间戳选项的往返时间测量（RTTM）

TCP 时间戳选项（TSOPT）除了可作为我们在第 13 章介绍的 PAWS 算法的基础外，还可用于往返时间测量（RTTM）[RFC1323]。TSOPT 的基本格式已在第 13 章中介绍。它允许发送方在 TCP 报文段中包含一个 32 位数值，该数值会在对应的确认报文中被返回。

时间戳值（TSV）包含在初始 SYN 报文段的 TSOPT 中，并在 SYN+ACK 报文段的 TSOPT 的 TSER 部分被返回，这正是 `srtt`、`rttvar` 和 RTO 初始值的确定方式。由于初始 SYN 会被视为“数据”（即如果丢失会被重传，且会消耗一个序列号），因此其往返时间会被测量。其他报文段中也会携带 TSOPT，因此可以持续估计连接的往返时间。这看起来足够直接，但由于 TCP 并非总是为每个收到的报文段单独发送确认，情况会变得更复杂。例如，传输大量数据时，TCP 通常会对每隔一个报文段发送一次确认（见第 15 认机制意味着报文段与其确认之间不一定存在固定的对应关系。为应对这些挑战，使用该选项的 TCP 实现（如今大多数实现都支持，包括 inux 和 Windows）采用以下算法采集 RTT 样本：

1. 发送方 TCP 会在其发送的每个 TCP 报文段的 TSOPT 的 `TSV` 部分包含一个 32 位时间戳值。该字段的值为报文段发送时发送方 TCP“时钟”的数值。
2. 接收方 TCP 会记录两个值：一个是要在下次生成的确认报文中发送的已接收 TSV 值（通常存储在名为 `TsRecent` 的变量中），另一个是上一次发送的确认报文中的确认号（存储在名为 `LastACK` 的变量中）。请回忆：确认号表示接收方（即确认报文的发送方）期望收到的下一个按序序列号。
3. 当新的报文段到达时，如果其序列号与 `LastACK` 变量的值匹配（即它是下一个预期接收的报文段），则该报文段的 TSV 值会被保存到 `TsRecent` 变量中。
4. 每当接收方发送确认报文时，都会在报文中包含 TSOPT，并将 `TsRecent` 变量中的时间戳值填入确认报文 TSOPT 的 `TSER` 部分。
5. 发送方收到推进其窗口的确认报文后，会用当前 TCP 时钟值减去 `TSER` 值，并将该差值作为样本值，用于更新其 RTT 估计器。

在 FreeBSD、Linux 以及后续版本的 Windows（当对端使用时间戳时）中，时间戳选项默认是启用的。在 Linux 系统中，系统配置变量 `net.ipv4.tcp_timestamps` 控制该选项是否启用（值为 0 表示不启用，值为 1 表示启用）。在 Windows 系统中，该选项的启用状态由前面提到的注册表项中的 `Tcp1323Opts` 值控制：若该值为 0，则时间戳选项禁用；若值为 2，则时间戳选项启用。该注册表项无默认值（默认情况下不存在于注册表中）。Windows 的默认行为是：如果连接发起方在建立连接时使用时间戳选项，则系统也 A 用该选项

### 14.3.3 Linux 方法（The Linux Method）

Linux 的 RTT 估计流程与标准方法略有不同。它使用 **1ms 时钟粒度**（比多数其他实现更细），同时配合 TCP 时间戳选项（TSOPT）使用。频繁的 RTT 采样与细粒度时钟的结合，让 RTT 估计更精准，但长期来看也会压低 `rttvar` 的数值 [LS00]——这是因为大量平均偏差样本会相互抵消，使波动估计值被低估。这是 Linux 在设置 RTO 时与标准方法的一个关键差异点。

另一个差异点在于：标准方法会在 RTT 样本显著低于当前 `srtt` 时增大 `rttvar`，而 Linux 对此做了特殊处理。

要理解这一问题，需要回顾 RTO 的核心公式：
$\text{RTO} = \text{srtt} + 4(\text{rttvar})$
可以看到，`rttvar` 的任何大幅变化都会直接导致 RTO 增大，**无论新的 RTT 样本是高于还是低于 `srtt`**。这违背直觉：**如果实际 RTT 显著下降，RTO 反而被拉高**，会降低传输效率。Linux 通过限制 RTT 样本大幅下降对 `rttvar` 的影响，解决了这个问题。下面我们来看 Linux 设置 RTO 的完整流程，它同时解决了上述两个问题。

Linux 方法保留了标准算法中的 `srtt` 和 `rttvar`，并新增了两个关键变量：`mdev` 和 `mdev_max`：

- `mdev`：使用标准算法维护 RTT 平均偏差的运行估计值；
- `mdev_max`：保存单次数据窗口内 `mdev` 的最大值，且 **不允许低于 50ms**；
- `rttvar` 会定期更新，确保其值不小于 `mdev_max`。

这一约束最终保证：**Linux 的 RTO 永远不会低于 200ms**。

> **注**：
> 最小 RTO 可通过内核配置常量 `TCP_RTO_MIN` 修改（需重新编译内核），部分 Linux 版本也支持通过 `ip route` 命令动态调整。
> 在数据中心网络中，RTT 可能仅几微秒，200ms 的最小 RTO 会导致交换机丢包后 TCP 恢复缓慢，引发所谓的 **TCP incast（入站流量汇聚）问题**。目前已有多种解决方案，包括将 TCP 时钟粒度和最小 RTO 调整为微秒级 [V09]。但这种极小的 RTO 不建议在公网使用。

---

Linux 会在 `mdev` 的最大值更新时，将 `rttvar` 同步为 `mdev_max` 的值。它始终将 RTO 设置为：
$\text{RTO} = \text{srtt} + 4(\text{rttvar})$
并确保 RTO 不超过 `TCP_RTO_MAX`（默认值为 120 秒），更多细节请参考 [SK02]。

在图 14-2 中，我们可以看到使用时间戳选项的 TCP 连接启动过程：发送方为 Linux 2.6 系统，接收方为 FreeBSD 5.4 系统。为简化阅读，序列号和时间戳以相对值表示，且未按精确时间比例绘制。基于本例中的初始 RTT 测量值，Linux 执行以下更新：

- `srtt = 16ms`
- `mdev = (16/2)ms = 8ms`
- `rttvar = mdev_max = \max(mdev, TCP_RTO_MIN) = \max(8, 50) = 50ms`
- `RTO = srtt + 4(rttvar) = 16 + 4(50) = 216ms`

初始 SYN 交换完成后，发送方会为接收方的 SYN 发送确认，接收方则以窗口更新作为响应。由于这两个报文都不包含数据（或 SYN/FIN 标志字段，这些字段会被视为“数据”），因此它们不会被计时，窗口更新的确认返回时也不会触发 RTT 估计器更新。

不包含数据的报文段不具备可靠交付特性——如果丢失，它们不会被重传。因此这类报文段不需要设置重传定时器。

> **注**：
> TCP 选项本身也不会被重传或可靠交付。只有当选项被封装在数据报文段（包括 SYN、FIN 报文段）中时，才会在丢失时被重传（这只是数据重传的附带效果）。

当应用程序执行第一次写入时，发送方 TCP 会发送两个报文段，它们的 TSV 值均为 127（因为发送方 TCP 时钟粒度为 1ms，两次发送之间时钟前进不足 1ms，因此时间戳相同）。在“背靠背”发送多个报文段时，时钟停滞或前进幅度很小是常见现象。

接收方的 `LastACK` 变量保存了上一次发送的确认号。本例中，`LastACK` 初始值为 1（因为连接建立时最后一个确认是 SYN+ACK 报文）。当第一个全尺寸报文段到达时，其序列号与 `LastACK` 匹配，因此 `TsRecent` 变量会更新为该报文段的 TSV 值 127。第二个报文段的序列号与 `LastACK` 不匹配，因此不会更新 `TsRecent`。对这两个报文段的确认会在 TSER 字段中携带 `TsRecent` 的值，同时接收方会将 `LastACK` 更新为确认号 2801。

---

当该确认报文到达时，TCP 会进行第二次 RTT 测量：用当前 TCP 时钟值减去报文的 TSER 值，得到样本 `m = 223 - 127 = 96`。基于该样本，Linux TCP 更新连接变量如下：

- `mdev = mdev(3/4) + |m - srtt|(1/4) = 8(3/4) + |80|(1/4) = 26ms`
- `mdev_max = max(mdev_max, mdev) = max(50, 26) = 50ms`
- `srtt = srtt(7/8) + m(1/8) = 16(7/8) + 96(1/8) = 26ms`
- `rttvar = mdev_max = 50ms`
- `RTO = srtt + 4(rttvar) = 26 + 4(50) = 226ms`

如前所述，Linux TCP 对经典 RTT 估计算法做了几处关键修改：

- 早期算法设计时，TCP 时钟粒度通常为 500ms，且时间戳选项未普及，典型做法是每个窗口仅进行一次 RTT 测量，这一做法在无时间戳时仍在使用；
- 当每个窗口仅一次采样时，`rttvar` 变化缓慢；但启用时间戳后，每个窗口可进行大量采样，由于同一窗口内 RTT 波动很小，大量样本会因大数定律导致 `rttvar` 被压得极低（接近 0）。

为解决这一问题，Linux 维护 `mdev` 作为平均偏差估计，但基于 `rttvar` 设置 RTO：`rttvar` 会被提升为一个数据窗口内 `mdev` 的最大值，且不低于 50ms；同时 `rttvar` 每个数据窗口仅允许降低一次。

标准方法对 `rttvar` 赋予了较高权重（×4），即使 RTT 下降，RTO 仍会增大。在 500ms 粗粒度时钟下，这一问题影响不大（RTO 可取的值有限），但在 Linux 的 1ms 细粒度时钟下，这一问题会被放大。

为解决 RTT 下降时 RTO 异常增大的问题，Linux 引入了条件权重调整：如果新样本低于估计 RTT 范围的下限（`srtt - mdev`），则大幅降低其对 `mdev` 的权重。完整逻辑如下：

```c
if (m < (srtt - mdev))
    mdev = (31/32) * mdev + (1/32) * |srtt - m|;
else
    mdev = (3/4) * mdev + (1/4) * |srtt - m|;
```

该条件判断新 RTT 样本是否低于预期 RTT 范围的下限。如果是，则表示连接的 RTT 可能正在显著下降。为避免此时增大 `mdev`（进而拉高 `rttvar` 和 RTO），新样本的偏差项 `|srtt - m|` 权重会降低 8 倍。这一调整解决了 RTT 下降时 RTO 异常增大的问题。更多细节请参考 [LS00] 和 [SK02]。在 [RKS07] 中，作者评估了 280 万条 TCP 流中不同操作系统的 RTT 估计算法，结论是 Linux 的估计器收敛速度快、调优性强，是所有被研究算法中最有效的。

回到图 14-2，当接收方生成确认号为 7001 的确认报文时，其 TSER 携带的不是最近到达报文段的 TSV，而是最早未被确认的报文段的 TSV。该确认返回发送方后，会基于最早的报文段计算 RTT 样本，而非最后发送的报文段——这就是时间戳算法处理延迟或异常确认的方式。

此时，RTT 样本反映的是发送方应等待接收确认的时间，而非实际网络 RTT。这一点至关重要：发送方需要基于“可预期的确认到达速率”设置 RTO，该速率可能低于报文发送速率。

### 14.3.4 RTT 估算器的行为

正如前文所述，TCP 的 RTO 超时取值逻辑、RTT 往返时延估算方案经过了大量技术创新与工程优化。图 14-3 在一套人工合成数据集上，演示了当下主流的两类估计算法（RFC 标准算法、Linux 自研算法）的运行效果。为方便对比演示，**本案例移除了 RFC6298 规定的 1s 最小 RTO 限制**；现实里绝大多数商用 TCP 实现，实际上都没有遵守这项规范 [RKS07]。

图表时序数据共 200 个合成采样点，数据来自两组高斯分布：前 100 个样本取自正态分布 $\boldsymbol{N(200,50)}$，后 100 个样本取自 $\boldsymbol{N(50,50)}$；第二组分布生成的负数样本统一取反转为正数。图里每个 `+` 标记代表单次实测 RTT 采样值。
第 100 个样本后，采样 RTT 出现断崖式下跌；可以清晰观察：**Linux 算法在第 100 个样本后几乎立刻下调 RTO**，但 RFC 标准算法需要再多累计 20 个样本，才能完成同等幅度的 RTO 回落。

单独观察 Linux 的 `rttvar` 曲线能够发现，该指标数值整体波动很小、基本保持平稳。
原因是 Linux 给 `mdev_max` 设置了 **50ms 硬性下限**，连带 `rttvar` 也被该下限约束。这套机制等效把 Linux 的 RTO 最低锁定在 200ms，从根源规避无谓的冗余重传（弊端：超时定时器触发偏慢，发生丢包时会小幅拖累传输性能）。
反观 RFC 标准算法在第 78、191 号样本处存在设计缺陷，极易触发无意义的虚假重传，该问题后文详述。

### 14.3.5 往返时延测量(RTTM)在丢包、报文乱序场景下的鲁棒性

已验证：**无报文丢失时，无论接收端是否启用延迟 ACK，TSOPT（TCP 时间戳选项）均可正常工作**。该算法在下面两类场景同样能够正确运行：

- **乱序报文场景**
接收端收到乱序报文（大多由前置报文丢失引发）时，需要立刻回复 ACK，保障快速重传算法（14.5 节）正常运行。**这类 ACK 携带的 TSER（回显时间戳），取自最近一份有序抵达、推动接收窗口前移的报文的 TSV（发送时间戳），而非当前这份乱序到达的报文**。
如果误用乱序报文自身的时间戳，会造成发送端 RTT 采样值异常偏大，最终 RTO 同步抬升。在链路出现报文乱序时，该设计反而具备正向收益：发送端 RTO 变大，会预留更长观测窗口，优先判定为乱序、延后触发重传，规避误重传。

- **重传报文成功落地场景**
  接收端收到重传报文、补齐接收缓冲区空缺时，接收窗口会大幅向前滑动。此时对应 ACK 的 TSER，依然取自最新有序抵达的报文。
  该规则的价值：如果选用年代过久报文的 TSV，该时间戳与当前时刻间隔甚至会超过 1 个 RTO，导致发送端 RTT 测算出现严重正向偏差（时延虚高）

![[md_pict/image-20260602162609573.png]]

> 配图前置案例说明（图 14-4）：
> 共 3 段报文，单段载荷 1024 字节：S1(字节 1~1024)、S3(字节 2049~3072)先行抵达接收端，S2(字节 1025~2048)延后到达，构成报文乱序。

报文发生乱序时，ACK 回显的时间戳取自 **上一次推动接收窗口向前扩容的报文**，并非接收端最晚抵达的报文。该机制使得报文乱序阶段发送端 RTT 测算值偏高、RTO 同步抬升，降低发送端重传的激进程度。

图 14-4 里一共返回三条 ACK：

1. ACK 1025：携带 S1 的时间戳（有序报文的常规确认）；
2. 第二条 ACK 1025：同样携带 S1 时间戳（收到窗口内的乱序 S3 报文，回复重复 ACK）；
3. ACK 3073：携带 S2 的时间戳（S2 迟到补齐空洞，窗口更新至 3073，**不取最晚抵达 S3 的时间戳**）。

这套逻辑带来的结果：报文乱序/疑似丢包场景下 RTT 被高估，RTO 随之变大，发送端重传行为变得保守。在报文乱序频发环境中该特性尤为关键，激进重传极易造成不必要的虚假冗余发包。

综上：TCP 时间戳选项，让发送端在报文延迟、丢包、乱序共存的复杂链路中依旧可以精准测算 RTT。发送端可自主定义时间戳计量单位，但单位必须和真实物理时间成正比例、且时间粒度合理，以适配 TCP 序号与常规链路速率（详细规范见 RFC1323）。
针对 TCP 时钟有两条硬性约束：

1. 下限：任意合理的 RTT 时长内，时钟至少完成 1 次计数跳变（保证能够采集到往返时延）；
2. 上限：时钟单次跳变间隔不得短于 59ns。若计数过快，承载 32 位 TSV 的时间戳字段，会在 IP 报文最大生存时长(255 秒)内发生数值绕回溢出（参考 ID1323b）。

在全部约束满足后，依靠测算得出的 RTO 即可安全驱动重传定时器。

# 第 15 章 TCP 数据流与窗口管理

## 15.3 延迟确认（Delayed Acknowledgments）
在很多情况下，TCP不会对每个收到的数据包都立即回复ACK。这要得益于TCP的**累积确认字段**（见第12章）：利用累积确认，TCP可以故意延迟一段时间发送ACK，期望能将需要发送的ACK与本地应用要向对方发送的数据合并（这种方式属于“捎带确认”，常见于批量数据传输场景）。

不过TCP不能无限延迟ACK——否则对方可能会误以为数据丢失，从而触发不必要的重传。


#### 注意
《主机需求RFC》（RFC1122）规定：TCP应实现延迟确认，但延迟时间必须小于500毫秒。多数实现会将最大延迟设为200毫秒。


延迟确认能减少网络流量（因为ACK数量更少），在批量传输中，“数据段数:ACK数”达到2:1的比例很常见。TCP允许等待发送ACK的最长时间，可根据主机操作系统进行配置：
- **Linux**：采用动态调整算法，可在“每个段都确认（即‘快速确认’模式）”和传统延迟确认模式之间切换。
- **Mac OS X**：通过系统变量`net.inet.tcp.delayed_ack`控制延迟确认的使用方式，取值含义为：0（禁用延迟）、1（始终延迟）、2（对每个数据包都确认）、3（自动检测何时回复），默认值是3。
- **Windows（新版本）**：需在对应网络接口的注册表项（路径为`HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\IG`，其中`IG`是具体网络接口的GUID）中配置：
  - `TcpAckFrequency`（需手动添加）：取值0-255，默认2，用于设定“未确认数据段的数量达到多少时，延迟ACK计时器会被忽略”。若设为1，相当于每个收到的段都会触发ACK。
  - `TcpDelAckTicks`：取值2-6，默认2，代表延迟发送ACK前要等待的时间（单位：百毫秒）。

基于前面提到的原因，TCP 通常会在特定情况下延迟发送 ACK，但不会延迟太久。在第 16 章我们会看到，当分析 TCP 拥塞控制在大包批量传输中的表现时，延迟确认的应用会很广泛。

而当使用较小的数据包（比如交互式应用的场景）时，就会涉及另一种算法。如果处理不当，这种算法和延迟确认的组合可能会导致性能下降，所以接下来我们会更详细地分析这一问题。

## 15.4 Nagle 算法

在上一节中我们看到，在 SSH 连接中，客户端往往会每次只向服务器发送一个按键输入。在使用 IPv4 时，单次按键会生成约 88 字节的 TCP/IPv4 数据包（以示例中的加密和认证方式计算）：20 字节的 IP 首部、20 字节的 TCP 首部（假设无选项），以及 48 字节的数据。这类小数据包（称为 **小包**）的网络开销非常大——也就是说，相比数据包其他部分，其包含的有效应用数据占比很低。

这种高开销的数据包在局域网（LAN）中通常不成问题，因为大多数局域网负载不高，且数据包无需长距离传输。但在广域网（WAN）中，这些小包会加剧拥塞，导致带宽利用效率低下。约翰·内格（John Nagle）提出了一个简洁巧妙的解决方案，该方案在 RFC0896 中被描述，也就是我们现在所说的 **Nagle 算法**。接下来我们会介绍它的工作原理，然后讨论它与延迟确认（delayed ACKs）结合使用时可能出现的一些问题。


Nagle 算法的规则是：当 TCP 连接存在未被确认的小数据段（小于 SMSS 的段）时，不能发送新的小数据段；相反，TCP 会将小数据量累积起来，待确认到达后再合并成一个段发送。这个过程会强制 TCP 进入 **“停等”行为**——即，在任何未确认数据的 ACK 到达前，停止发送新数据。

该算法的巧妙之处在于它是 **自调节的**：ACK 返回得越快，数据发送速度就越快。与高延迟广域网相比，这一点尤为突出——在广域网中，减少小包数量是很有必要的（每个段的延迟会降低）。换句话说，往返时间（RTT）会控制数据包的发送速率。


我们在图 15-3 中看到：单个字节的发送、确认和回显过程耗时可短至 15 毫秒以内。要想让数据生成速度超过这个水平，我们每秒需要输入 60 多个字符。这意味着，当在同一局域网内的两台主机之间发送数据时（RTT 很小），我们很少会遇到该算法带来的明显影响。


为了说明 Nagle 算法的效果，我们可以对比开启和关闭该算法时应用程序的行为。我们修改了 SSH 客户端以实现这一目的：在 RTT 约为 190 毫秒的连接中，能明显看到差异。首先，我们分析 Nagle 算法关闭时的情况（这是 SSH 的默认设置），如图 15-4 所示。

## 15.5 流量控制与窗口管理

回忆第 12 章内容，**可变滑动窗口** 可用于实现流量控制。在图 15-8 中，TCP 客户端与服务器正在交互，双方互相提供数据流相关信息，包括报文段的序号（Sequence Number）、确认号（ACK Number）和窗口大小（即接收方的可用缓冲区空间）。



![[md_pict/image-20260612141517307.png]]

> 图 15-8 说明：每条 TCP 连接都是双向的。数据沿一个方向传输时，会触发对端回复 ACK 和窗口通告；反向传输同理。

------

图 15-8 中的两个大箭头代表数据流方向（即 TCP 报文段的发送方向）。由于每条 TCP 连接都是双向传输数据，因此有两个箭头：一个是客户端到服务器方向（C→S），另一个是服务器到客户端方向（S→C）。

每个报文段都包含 ACK 和窗口信息，也可能携带用户数据。TCP 头部中的字段会根据其描述的数据流方向高亮显示：例如，C→S 方向的数据包含在沿底部箭头传输的报文段中，而该数据的 ACK 号和窗口通告则通过沿顶部箭头传输的报文段返回。

除连接建立阶段交换的报文段外，所有 TCP 报文段都包含有效的 **序号字段**、**确认号（ACK 号）字段** 和 **窗口大小字段**（用于携带窗口通告）。

本章前面的 SSH 示例中，我们看到 TCP 对等方之间传递的窗口通告值是固定的，例如 8320 字节、4220 字节和 32900 字节。这些数值代表 **报文段发送方为存储对端发来的数据而预留的缓冲区空间大小**。

当基于 TCP 的应用程序不忙于处理其他任务时，通常能及时处理 TCP 接收并缓存的所有数据，因此连接过程中窗口大小字段不会发生变化。

但在性能较慢的系统上，或应用程序有其他任务需要处理时，数据可能已到达、被 TCP 确认，但仍留在队列中等待应用程序读取或 “消费”。当 TCP 开始这样缓存数据时，接收缓冲区中可容纳新数据的剩余空间会减少，这一变化会通过 **窗口大小字段值的减小** 反映出来。

最终，如果应用程序完全不读取或消费数据，TCP 必须采取措施让发送方停止发送新数据 —— 因为数据到达后将没有缓冲区空间存储。实现方式是发送 **窗口大小为 0 的通告**（表示无可用空间）。

每个 TCP 头部中的 **窗口大小字段**，表示接收缓冲区中剩余的空闲空间大小（单位：字节）。该字段在 TCP 中为 16 位，因此理论最大值为 65535 字节；但通过 **窗口缩放（Window Scale）选项**，可支持更大的窗口值（详见第 13 章）。

报文段发送方愿意在反向连接上接收的最大序号，等于 TCP 头部中 **确认号字段** 与 **窗口大小字段** 的和（需按窗口缩放选项进行适当换算）。

### 15.5.1 **滑动窗口**

TCP 连接的两端均可发送和接收数据。连接中收发数据的总量由一组 **窗口** 结构进行管控。对于每一条处于活跃状态的连接，TCP 两端都会分别维护一套 **发送窗口** 结构与 **接收窗口** 结构。这类结构与第十二章介绍的基础窗口模型原理一致，本节将展开更为详尽的阐述。图 15-9 展示了 TCP 发送窗口的结构示例。

![[md_pict/image-20260612145008738.png]]

TCP 以 **字节** 而非数据包作为窗口管理的最小单位。在图 15-9 中，我们将字节依次编号为 2 至 11。接收方对外公布的窗口称为 **通告窗口**，该窗口覆盖第 4 至第 9 号字节。这意味着接收方已确认第 3 号及之前所有字节，并对外通告了一个大小为 6 字节的窗口。回顾第十二章内容，窗口大小字段记录的是相对于确认号的字节偏移量。发送端会计算自身的 **可用窗口**，即当前可以立即发送的数据量。**可用窗口** 的大小等于 **通告窗口** 大小减去已发送但尚未收到确认的数据总量。变量 **SND.UNA** 用于记录窗口左边界，**SND.WND** 用于记录接收方通告的窗口尺寸。变量 **SND.NXT** 存储下一个待发送字节的序号，因此可用窗口的计算方式为：`SND.UNA + SND.WND − SND.NXT`。

随着接收方不断对数据进行确认，滑动窗口会逐步向右移动。窗口两侧边界的相对位移会改变窗口的整体大小，行业内使用三个专用术语描述边界的移动形态：

1. **窗口关闭**：窗口左边界向右移动。当已发送的数据收到确认，且窗口可用范围缩小时，就会出现该现象。
2. **窗口打开**：窗口右边界向右拓展，允许发送更多数据。当接收端应用程序读取已缓存的数据、释放 TCP 接收缓冲区空间时，便会触发窗口打开。
3. **窗口收缩**：窗口右边界向左回缩。RFC 1122《主机需求规范》明确不建议使用该方式，但 TCP 协议仍必须具备对应的兼容处理能力。15.5.3 节关于 **糊涂窗口综合征** 的内容中，会举例说明通信方尝试通过右边界左移实现窗口收缩，却受到协议规则限制的场景。

由于每一个 TCP 报文段都会同时携带确认信息与窗口通告信息，TCP 发送端在收到报文段时，会结合这两类信息同步更新窗口结构。窗口左边界无法向左移动，该边界由对端发送的累计确认号决定，而确认号只会单调递增，不会出现回退。最常见的情况是确认号推进、窗口尺寸保持不变，这种情况被称作窗口向前滑动。如果确认号正常推进，但后续确认报文携带的通告窗口变小，窗口左边界会逐步靠近右边界。当左右边界完全重合时，就进入 **零窗口** 状态，发送端将停止一切数据传输。出现零窗口后，TCP 发送端会持续探测对端窗口状态（详见 15.5.2 节），等待对方通告窗口恢复可用。

接收端同样会维护一套窗口结构，其逻辑相比发送端更为简单。接收端窗口会记录已接收并完成确认的数据，以及自身能够接纳的最大字节序号，依靠这套机制保障数据接收的准确性：避免重复接收已确认的字节，同时拒绝接收超出窗口范围的无效字节。接收端窗口结构如图 15-10 所示。

![[md_pict/image-20260612155123208.png]]

该结构同样划分左右边界，窗口内的字节无需像发送端那样区分传输状态。对于接收端而言：序号小于窗口左边界 **RCV.NXT** 的字节，会被判定为重复数据并直接丢弃；序号超出窗口右边界（`RCV.NXT + RCV.WND`）的字节，会被判定为越界数据并直接丢弃；序号落在接收窗口范围内的字节，会被正常接收并缓存。

受 TCP **累计确认** 机制限制，只有当紧贴窗口左边界的连续数据到达时，接收端的确认号才会向前推进。借助 **选择性确认（SACK）** 选项，窗口内非连续的报文段可以被单独确认，但最终的累计确认号，依旧仅在收到紧邻窗口左边界的连续数据时才会向前移动。关于选择性确认的详细规则，可参考第十四章。



### 15.5.2 零窗口与 TCP 持续计时器

我们已经了解到，TCP 通过接收方指定 **可接收的数据量**（即接收方的 **通告窗口**）实现流量控制。当接收方通告的窗口大小变为零时，发送方会被强制停止数据传输，直到窗口恢复非零状态。

当接收方重新获得可用缓冲区空间时，会向发送方发送 **窗口更新报文**，告知发送方可以恢复数据传输。但这类报文通常不携带数据（属于「纯确认报文」），TCP 不保证其可靠传输。因此，TCP 必须处理「窗口更新报文丢失导致窗口无法打开」的场景。

如果携带窗口更新的确认报文丢失，会导致双方陷入死锁：接收方等待接收数据（因为它向发送方通告了非零窗口，预期收到数据），而发送方等待接收窗口更新以恢复发送。为避免这种死锁，发送方会使用 **持续计时器（Persist Timer）**，定期查询接收方的窗口大小是否已增加。持续计时器超时后，会触发发送 **窗口探测报文（Window Probes）**——这类报文会强制接收方回复确认，而确认报文中必然包含窗口大小字段。RFC1122《主机需求规范》建议：第一次探测应在一个 RTO（重传超时时间）后发送，后续探测采用指数退避间隔（类似第 14 章讨论的卡恩算法的第二部分）。

窗口探测报文携带 1 字节数据，因此即使丢失，TCP 也会对其进行重传，从而消除窗口更新报文丢失导致的潜在死锁。每当 TCP 持续计时器超时，就会发送探测报文；报文中的这 1 字节数据可能被接收方接受，也可能被拒绝，取决于接收方当前的缓冲区可用空间。与 TCP 重传计时器类似，持续计时器的超时计算也可采用常规指数退避机制。但二者存在一个关键差异：普通 TCP 可能会放弃重传，却 **永远不会停止发送窗口探测报文**，这可能导致资源耗尽漏洞，相关内容将在 15.7 节讨论。

#### 15.5.2.1 示例

为演示 TCP 动态窗口调整与流量控制的工作机制，我们建立了一条 TCP 连接，并让接收进程在从网络读取数据前暂停一段时间。实验中，发送方为 Mac OS X 10.6 系统，接收方为 Windows 7 系统，接收方运行带 `-P` 参数的 `sock` 程序，命令如下：

该命令会让接收方在消费网络数据前暂停 20 秒，最终接收方的通告窗口会逐渐关闭，如图 15-11 中第 125 个报文所示。![[md_pict/image-20260612160011042.png]]

### 15.5.3 糊涂窗口综合征（Silly Window Syndrome, SWS）

基于窗口的流量控制机制，尤其是不使用固定大小报文段的 TCP，可能会陷入 **糊涂窗口综合征（SWS）**。当该问题发生时，连接上会交换小段数据而非全尺寸报文段 [RFC0813]，导致严重的效率低下：每个报文段的数据字节数远小于头部字节数，产生极高的传输开销。

糊涂窗口综合征可由 TCP 连接的任意一端引发：接收方可能会通告过小的窗口（而非等待直到可以通告更大的窗口），发送方可能会发送小段数据（而非等待额外数据以发送更大的报文段）。要避免该问题，TCP 无论作为发送方还是接收方，都必须实现专门的规则。TCP 无法提前获知对端的行为，因此会应用以下规则：

1. **作为接收方时：不会通告过小的窗口**
    RFC1122 规定的接收算法是：除非窗口可以增大，否则不发送通告比当前窗口更大的报文段；窗口增大的条件为：增加量为一个完整的 **MSS（最大报文段长度）**，或增加量为接收方缓冲区空间的一半，取两者中的较小值。该规则会在两种场景下触发：应用程序从网络读取数据后，接收缓冲区空间变得可用；TCP 响应窗口探测报文时。

2. **作为发送方时：不会发送小段数据，由 Nagle 算法控制发送时机**
    发送方会避免发送小段数据，除非满足以下任一条件：
    a.  可以发送一个全尺寸（发送 MSS 字节）的报文段；
    b.  TCP 可以发送至少 **对端在此连接上曾通告过的最大窗口大小的一半** 的数据；
    c.  TCP 必须发送所有待发数据，且满足以下任一条件：（i）没有待确认的 ACK（即无未确认数据）；（ii）此连接上已禁用 Nagle 算法。

条件(a)最直接，可避免高开销的小段报文问题；条件(b)处理始终通告极小窗口（甚至小于报文段大小）的主机场景；条件(c)防止 TCP 在存在未确认数据且启用 Nagle 算法时发送小段数据。如果发送应用程序执行小于报文段大小的小数据写操作，条件(c)可避免糊涂窗口综合征。

这三个条件也让我们可以回答：“如果 Nagle 算法防止在存在未确认数据时发送小段数据，那么‘小’的定义是什么？”从条件(a)可知，“小”指字节数小于 SMSS（发送方最大报文段大小，即不超过路径 MTU 或接收方 MSS 的最大数据包大小）；条件(b)仅在使用旧主机或因接收缓冲区有限而通告小窗口时生效。

条件(b)要求发送方跟踪对端曾通告过的最大窗口大小，这是发送方试图猜测对端接收缓冲区大小的方式。虽然连接建立期间接收缓冲区大小可能减小，但实际中这种情况很少见，且 TCP 会避免窗口收缩。

#### 15.5.3.1 示例

我们通过一个详细示例演示糊涂窗口综合征避免机制的实际运作，该示例还涉及持续计时器。我们使用 `sock` 程序，以 Windows XP 为发送主机、FreeBSD 为接收主机，向网络执行三次 2048 字节的写操作。发送方命令如下：

```cmd
C:\> sock -i -n 3 -w 2048 10.0.0.8 6666
```

接收方对应命令为：

```sh
FreeBSD% sock -i -s -P 15 -p 2 -r 256 -R 3000 6666
```

该命令将接收缓冲区固定为 3000 字节，在从网络读取数据前引入 15 秒初始延迟，每次读取之间注入 2 秒延迟，并设置每次读取量为 256 字节。初始暂停的目的是让接收方缓冲区被填满，最终迫使发送方停止发送；后续让接收方执行小读取操作，以观察 SWS 避免机制的运作过程。图 15-14 是 Wireshark 捕获的流量。

连接的整个过程都显示在图中，报文长度按每个 TCP 段包含的有效载荷字节数描述。连接建立期间，接收方通告了 3000 字节的窗口，MSS 为 1460 字节。发送方在 0.052 秒发送了一个 1460 字节的报文段（第 4 个报文），在 0.053 秒发送了 588 字节的报文段（第 5 个报文），两者大小之和等于应用程序的 2048 字节写大小。![[md_pict/image-20260612164509189.png]]

>图 15-14 发送方因遵循 **发送端 SWS 规避规则**，在 0.053 秒时没有填充接收方通告的窗口，而是一直等待到 5.066 秒才发送数据，此时发送的报文同时起到了窗口探测的作用。从第 14 号报文可以观察到 **接收端 SWS 规避规则** 的体现：尽管接收方已经消费了部分数据，却依然通告了零窗口。

第 6 个报文确认了两个数据报文，并通告了 952 字节的窗口（`3000 - 1460 - 588 = 952`）。

952 字节的窗口小于一个完整的 MSS，因此发送方的 Nagle 算法会阻止立即填充该窗口。发送方会等待 5 秒，直到持续计时器超时后才发送窗口探测报文。此时发送方无论如何都要发送报文段，因此会将允许的 952 字节数据添加进去，填充可用窗口，这一点由第 8 个报文中的零窗口通告确认。

收到第一个零窗口通告约 2 秒后，TCP 在 6.970 秒发送了一个窗口探测报文。探测报文包含 1 字节数据，Wireshark 标记为“TCP ZeroWindowProbe”，但对该报文的 ACK 并未推进确认号（Wireshark 标记为“TCP ZeroWindowProbeAck”），说明接收方并未保留该字节。约 4 秒后（10.782 秒）和 8 秒后（18.408 秒）分别发送了另一个 1 字节探测报文，体现了典型的指数退避超时机制。在最后这个探测报文中，接收方确认了该单字节数据。

在 25.061 秒，应用程序完成了六次间隔 2 秒的 256 字节读取操作后，窗口更新报文指示接收方缓冲区现在有 1535 字节的可用空间（加上确认号的 1 字节偏移），这一大小已满足接收方侧 SWS 避免规则的“足够大”要求。发送方开始填充窗口，在 25.064 秒发送了一个 1460 字节的报文段，导致 25.161 秒收到对 4462 号字节的确认，其中仅通告了 75 字节的窗口（第 17 个报文）。该通告看似违反了“通告窗口大小应至少为一个 MSS（或 FreeBSD 系统中总缓冲区的四分之一）”的规则，其原因是为了避免窗口收缩：上一次窗口更新（第 15 个报文）中，接收方通告的右窗口边界为 `3002 + 1535 = 4537`；如果当前 ACK 按规则要求通告小于 75 字节的窗口，右窗口边界将左移，这是 TCP 不允许的行为。因此，75 字节的通告是一种覆盖：避免窗口收缩的优先级高于避免 SWS。

我们再次看到发送方侧 SWS 避免机制的效果：报文 17 和 18 之间有 5 秒延迟。发送方被迫发送 75 字节的报文段，接收方再次回复零窗口通告。几秒钟后，第 20 个报文发送了另一个窗口探测报文，此时窗口为 767 字节。新一轮发送方侧 SWS 避免机制再次导致 5 秒延迟；发送方填充窗口，再次导致零窗口通告，该模式不断重复。当发送方没有更多数据要发送时，该模式最终终止。第 30 个报文是发送的最后一个数据段，连接最终在接收应用每次读取之间的 2 秒延迟过去约 20 秒后关闭。

为了理解应用程序行为、通告窗口和 SWS 避免之间的关系，我们可以将连接的动态过程整理成表格形式。表 15-1 列出了发送方和接收方的操作，以及接收主机执行读取操作的估计时间。![[md_pict/image-20260612180737799.png]]

![[md_pict/image-20260612180835178.png]]

在表 15-1 中，第一列是跟踪中每个操作的相对时间点。小数点后有三位数字的时间取自 Wireshark 输出（参见图 15-16）；小数点后无数字的时间是接收主机上操作的推断时间，这些时间未在跟踪中体现。

接收方缓冲区中的数据量（表中标记为“Data”）在发送方数据到达时增加，在应用程序从缓冲区读取（消费）数据时减少。我们需要关注的是接收方发送给发送方的窗口更新报文，以及这些报文中包含的窗口通告值，这能让我们看到接收方是如何避免 SWS 的。

如前所述，**第 6 和第 7 个报文之间的 5 秒延迟是 SWS 避免的第一个证据**：发送方避免在窗口为 952 字节时发送数据，直到被强制发送为止。当发送方这样做时，接收方的缓冲区被填满，导致一系列零窗口通告和窗口探测交互。我们可以看到持续计时器的指数退避机制：在发送方首次收到零窗口通告（5.160 秒）后的约 **2 秒、4 秒和 8 秒，分别发送了探测报文**（6.970 秒、10.782 秒和 18.408 秒）。

尽管应用程序在 15 秒和 17 秒读取了数据，但到 18.408 秒时，仅读取了 512 字节。接收方侧的 SWS 避免规则规定，由于可用的 512 字节缓冲区空间既不是总缓冲区（3000 字节）的一半，也不是至少一个 MSS（1460 字节），因此不应向发送方发送窗口更新报文。由于没有窗口更新，发送方在 18.408 秒发送了一个窗口探测报文（第 13 个报文）。该探测报文被接收，且接收方保留了该字节数据，这一点通过第 12 和 14 个报文之间递增的确认号得到验证。

尽管接收方缓冲区中有 511 字节的可用空间，但接收方侧的 SWS 避免机制再次生效。FreeBSD 实现的接收方侧 SWS 避免机制区分了“何时发送窗口更新”和“如何响应窗口探测”：虽然它遵循 RFC1122 的规则，仅当至少可以通告总接收缓冲区的一半（或一个 MSS）时才发送窗口更新，但在响应窗口探测报文时，只要窗口大小至少为一个 MSS，或至少可以通告总接收缓冲区大小的四分之一，就会通告更大的窗口。在这两种情况下，511 字节都小于一个完整的 MSS，也小于 `3000/4=750` 字节，因此这种形式的接收方侧 SWS 避免机制规定，对第 13 个报文的 ACK 中包含的窗口通告值必须为 0。

到 25 秒时，应用程序完成了第六次读取操作，接收方缓冲区有 1535 字节的可用空间（超过了总 3000 字节的一半），因此发送了窗口更新报文（第 15 个报文）。发送方继续发送一个全尺寸段（第 16 个报文），对此收到了确认，但窗口通告仅为 75 字节。接下来的 5 秒内，发送方和接收方侧的 SWS 避免机制同时生效。发送方等待更大的窗口更新，应用程序在 27 秒和 29 秒执行读取操作，但释放的 587 字节接收缓冲区空间不足以发送窗口更新报文。因此，发送方必须等待完整的 5 秒，最终发送了 75 字节的数据，再次迫使接收方进入 SWS 避免状态。

由于接收方未提供窗口更新，发送方的持续计时器导致在 31.548 秒发送了一个窗口探测报文。此时，FreeBSD 接收方回复了一个非零窗口通告，大小为 767 字节（大于总接收缓冲区的四分之一）。但这个窗口大小仍不足以满足发送方的 SWS 避免机制，因此发送方再等待了 5 秒，该过程重复进行。最后，在 43.486 秒发送了最后的 71 字节数据并收到确认，确认报文中包含了 696 字节的窗口通告。尽管该值小于接收方总缓冲区大小的四分之一，但为了避免窗口收缩，接收方侧的 SWS 避免机制没有将其置零。

连接终止始于第 32 个报文，该报文不包含数据。它立即被确认，同时附带了 695 字节的窗口通告（FIN 报文消耗了接收方的一个序号）。应用程序完成另外六次读取操作后，接收方提供了窗口更新，但发送方已完成发送并保持静默。应用程序又执行了四次读取操作，其中三次返回 256 字节，最后一次返回空值，表示没有更多数据到达。此时，接收方关闭连接，向发送方发送 FIN 报文。发送方回复最终 ACK，完成连接的双向关闭。

由于发送应用程序在三次 2048 字节写操作后执行了关闭操作，发送方在发送第 32 个报文后，连接状态从 ESTABLISHED 转为 FIN_WAIT_1；收到第 33 个报文后，转为 FIN_WAIT_2 状态。虽然在该状态下收到窗口更新报文，但发送方不会采取任何操作，因为它已经发送了 FIN 并收到了确认（该状态下无计时器）。因此，发送方仅会保持该状态，直到收到对端的 FIN 报文（第 35 个报文），这就是为什么在收到 FIN 报文之前，我们不会看到发送方有进一步的传输。





# 第16章 拥塞控制

### 16.2 经典算法
当一个新的TCP连接刚建立时，它通常不知道`cwnd`（拥塞窗口）的初始值应该设为多少——毕竟它不清楚当前网络有多少可用容量来传输自己的数据（也有例外情况，比如有些系统会缓存之前确定的性能值，第14章中称这种机制为“目的度量”）。

TCP通过与接收方的一次数据包交互来获取`cwnd`的初始值，但由于没有显式的信号通知，它能找到合适`cwnd`的唯一方法，就是不断提高发送速率，直到遇到数据包丢失（或其他拥塞指示）。这既可以通过“直接以最大速率发送（受`awnd`限制）”实现，也可以从较低速率开始。

但如果一开始就以全速发送，会对共享同一条网络路径的其他TCP连接性能造成不利影响，所以TCP通常会用一种算法来避免启动时速率过快，以此平稳进入稳定状态；而进入稳定状态后，它会切换到另一种算法。


TCP发送方的拥塞控制操作是由**ACK的接收**来“驱动（或说‘计时’）”的。当TCP处于稳定状态（`cwnd`值合适）时，收到ACK意味着网络中已移除了一个或多个数据包，因此出现了可以发送更多数据的机会。

基于这一逻辑，稳定状态下的TCP拥塞行为会尝试实现“网络中的数据包守恒”（见图16-1）。这里的“守恒”和物理学中的概念类似——指某个量（比如这里的网络中的数据包）不会凭空消失或出现，只要做好统计，它的总量是可控的。

![[md_pict/image-20260612223544922.png]]

 >图 16-1 说明:TCP 拥塞控制遵循 “数据包守恒” 原则：数据包（\(P_s\)）从发送方发往接收方时，会因链路容量受限而在时间上被 “拉开间隔”；到达接收方后，数据包的间隔变为\(P_r\)，由此生成的 ACK 也会被接收方按相应间隔（\(A_r\)）发回发送方。当 ACK 到达发送方时，其间隔变为\(A_s\)，这些 ACK 的到达相当于一种 “信号”（即 “ACK 时钟”），用来告知发送方可以发送更多数据。在稳定状态下，整个系统可称为 “自计时” 的。该图改编自文献 [J88]，并引用自 S. Seshan 于 2005 年 3 月 22 日的卡内基梅隆大学讲义。

我们可以把图中的上下两部分称为 “漏斗”：

- 上方漏斗承载着（较大的）数据包，它们沿路径从发送方传向接收方。漏斗相对较窄的宽度，体现了数据包在通过低速链路时，时间间隔被 “拉开” 的状态；漏斗在发送方和接收方两端的区域代表数据包在进入 / 离开路径前的队列。
- 下方漏斗承载着 ACK，这些 ACK 从接收方返回发送方，与上方漏斗中的数据包一一对应。

在稳定状态下高效运行时，上下漏斗中都不会出现数据包堆积，同时上方漏斗中的数据包之间也没有明显的多余间隔。需要注意的是：当一个 ACK 到达发送方时，会 “释放” 一个新的数据包进入上方漏斗，且这一过程发生的时机恰好是网络能够接收新数据包的时候。这种关系有时被称为 “自计时”—— 因为 ACK 的到达（即 “ACK 时钟”）会触发系统执行发送下一个数据包的动作。

接下来我们介绍 TCP 的两个核心算法：**慢启动**和**拥塞避免**。这两种算法基于 “数据包守恒” 和 “ACK 时钟” 的原则，最早在 Jacobson 的经典论文 [J88] 中被正式阐述。

几年后，Jacobson对拥塞避免算法做了更新[J90]。这两种算法（慢启动与拥塞避免）不会同时运行——TCP在任一时刻只会执行其中一种，但会在两者之间来回切换。接下来我们会更详细地分析这两种算法，探讨决定它们何时被启用的因素，以及自最初实现以来它们是如何被修改和扩展的。每个TCP连接都可以独立执行这些算法。


#### 16.2.1 慢启动
慢启动算法会在**新TCP连接建立时**、**因重传超时（RTO）检测到丢包时**，或**发送方TCP空闲一段时间后**被触发。它的作用是：在通过拥塞避免算法探测更多可用带宽、建立ACK时钟之前，帮助TCP确定`cwnd`（拥塞窗口）的初始值。

通常，TCP连接会以慢启动开始，先发送一个数据包，随后切换到拥塞避免算法进入稳定运行状态（见16.2.2节）。引用RFC5681中的描述：
> “向网络状况未知的网络发起传输时，TCP需要缓慢探测可用带宽，以避免用过量数据拥塞网络。慢启动算法就是用于传输初始阶段，或修复重传计时器检测到的丢包后的场景。”


TCP在慢启动阶段（完成SYN交互后）会先发送一定数量的段，这部分被称为**初始窗口（IW）**。最初IW的值是1个SMSS（发送方最大段大小），但在RFC5681中，IW被允许设为更大的值，具体公式如下：
- 若SMSS > 2190字节：\( \text{IW} = 2 \times \text{SMSS} \)，且不超过2个段
- 若2190 ≥ SMSS > 1095字节：\( \text{IW} = 3 \times \text{SMSS} \)，且不超过3个段
- 其他情况：\( \text{IW} = 4 \times \text{SMSS} \)，且不超过4个段


尽管这种IW设置允许初始窗口包含多个数据包（比如3或4个），但我们先讨论`IW = 1 SMSS`的情况：此时TCP连接启动时，初始`cwnd`为1个SMSS，初始可用窗口W也等于SMSS（注：多数情况下，SMSS等于接收方MSS与路径MTU（减去首部大小）中的较小值）。


假设第一个发送的数据包未丢失，接收方会返回一个ACK，允许发送方TCP再发一个段。而慢启动的运行规则是：**每收到一个有效ACK，就将`cwnd`增加`min(N, SMSS)`**（其中N是本次 ACK 新确认的、之前未被确认的字节数）。这里的“有效ACK”指的是ACK号比之前收到的更高的ACK。

> 注意
>
> ACK确认的字节数用于支持“适当字节计数（ABC）”机制（RFC3465），这是RFC5681推荐的实验性规范，可用于抵御16.12节中描述的“ACK拆分攻击”——这种攻击会用大量小ACK诱使TCP发送方以超出正常的速率发送数据。
> 在Linux中，可通过布尔型系统配置变量`net.ipv4.tcp.abc`来决定是否启用ABC（默认禁用）；在新版Windows中，ABC默认是开启的。

因此，当一个段被确认后，`cwnd`通常会增加到2xSMSS，此时可以发送两个段。如果这两个段都触发了新的有效ACK返回，`cwnd`会从2增加到4，再从4增加到8，以此类推。一般来说，假设无丢包且每个包都能得到ACK，经过k次往返交互后，窗口W的值会是\( W = 2^k \)。换算一下，我们可以得出：要达到运行窗口W，需要的RTT次数为\( k = \log_2 W \)。
这种增长看似“很快”（呈指数函数增长），但比起“让TCP直接发送与接收方通告窗口大小相当的包”来说，还是“慢”的（要记得W始终不能超过`awnd`）。

假设接收方的通告窗口非常大（比如无限大），那么`cwnd`就是发送速率的主要限制因素（前提是发送方有数据可发）。如前所述，`cwnd`（以及W）会随着连接的RTT呈指数增长。最终，`cwnd`可能变得过大，导致发送的数据包窗口超出网络承载能力（回想一下：TCP的吞吐量与\( W/RTT \)成正比）。当这种情况发生时，`cwnd`会大幅减小（变为之前的一半）。此外，此时TCP会从慢启动模式切换到拥塞避免模式，切换的节点由`cwnd`与一个名为“慢启动阈值（ssthresh）”的值之间的关系决定。

图16-2（左）展示了慢启动的运行过程（图中数值以连接的RTT为单位）。假设连接初始发送1个包（顶部），收到1个ACK后，第二个RTT可以发送2个包。这2个包会触发2个ACK返回，TCP发送方会将`cwnd`增加到4。这个过程不断持续，`cwnd`随时间的指数增长在图的右侧有所体现。
第二条线展示了“每隔一个包才确认”（延迟ACK常用的方式）时`cwnd`的增长情况：这种场景下增长依然是指数级的，但速度会慢一些。正因如此，有些TCP会等慢启动完成后再使用延迟ACK。在Linux中，这被称为“快速确认（quickack模式）”，自2.4.4版本内核起就成为了TCP/IP基础栈的一部分。

#### 16.2.2 拥塞避免
前文所述的慢启动，会在连接初始传输数据时、或因超时触发丢包事件后被使用。它会快速增大`cwnd`，并帮助确定`ssthresh`（慢启动阈值）。不过，一旦连接的网络容量被探明，就始终存在一种可能：如果立刻用大流量突发占用这些容量，共享同一路由器队列的其他TCP连接很可能会遭遇严重丢包，进而导致网络中大量连接同时丢包并触发重传。


为解决“试探额外容量时过于激进”的问题，TCP实现了**拥塞避免算法**。当`ssthresh`确定、且`cwnd`至少达到该阈值后，TCP会运行拥塞避免算法——它通过**每成功传输一个窗口的数据，就将`cwnd`增加成功传输的数据段大小**的方式来寻找额外容量。这种增长速率比慢启动慢得多：慢启动是指数增长，而拥塞避免在时间维度上近似线性增长。

更精确地说，对于每个收到的重复ACK，`cwnd`的更新公式通常为：
\[ \text{cwnd}_{i+1} = \text{cwnd}_i + \text{SMSS} * \text{SMSS} / \text{cwnd}_i \]

我们先简单分析这个关系式：假设初始时`cwnd₀ = k*SMSS`字节（对应k个段）被发送到网络中。当第一个ACK到达后，`cwnd`会增加`1/k`倍：
\[
\begin{align*}
\text{cwnd}_1 &= \text{cwnd}_0 + \text{SMSS} * \text{SMSS}/\text{cwnd}_0 \\
&= k*\text{SMSS} + \text{SMSS} * (\text{SMSS}/(k*\text{SMSS})) \\
&= k*\text{SMSS} + (1/k)*\text{SMSS} \\
&= (k + 1/k)*\text{SMSS} \\
&= \text{cwnd}_0 + (1/k)*\text{SMSS}
\end{align*}
\]

由于`cwnd`的值会随每个新ACK的到达略有增长，而这个值又出现在上述第一个公式的分母中，所以`cwnd`的整体增长速率略低于线性。不过，我们通常认为**拥塞避免阶段的窗口是随时间线性增长的**（见图16-3），而慢启动是随时间指数增长的（见图16-2）。这种（拥塞避免的）增长方式也被称为“加法增长”——因为每成功传输一个窗口的数据，就会给`cwnd`增加一个特定值（这里约为1个包）。

这里有个假设：由比特错误导致的丢包概率非常低（远低于1%），因此丢包就意味着网络中某处出现了拥塞。但在无线网络中，这个假设并不成立——即便没有拥塞，丢包也会拖慢TCP。此外，`cwnd`需要经过很多个RTT才能增长到较大的值，而这对于高效利用高容量网络是必要的。解决TCP的这些问题一直是热门研究方向，我们之后会讨论相关的各种方案。


#### 16.2.3 慢启动与拥塞避免的切换
在正常运行中，TCP连接始终会执行慢启动或拥塞避免中的一种流程，但不会同时运行两者。现在我们来探讨：是什么决定了TCP在特定时刻使用哪种算法？

我们已经知道，慢启动会在新连接建立时、或超时重传发生时被启用。接下来我们看这两种算法的切换逻辑。


之前我们提到了`ssthresh`（慢启动阈值），它是`cwnd`的一个限值，用于决定当前运行的算法：
- 当`cwnd < ssthresh`时，使用慢启动；
- 当`cwnd > ssthresh`时，使用拥塞避免；
- 当两者相等时，可任选其一。

慢启动与拥塞避免最关键的区别在于：新ACK到达时，二者修改`cwnd`的方式不同（这一点我们已经看到）。而让TCP的逻辑更复杂有趣的是：`ssthresh`的值并非固定，而是会随时间变化——它的主要作用是“记住”操作窗口的上一次“最佳”估计值，换句话说，它保存着TCP对最优窗口大小的最低估计值。

`ssthresh`的初始值通常会设得很高（比如设为`awnd`或更高），这会让TCP总是从慢启动开始。当重传发生时（无论是超时重传，还是执行快速重传），`ssthresh`会按如下方式更新：
\[ \text{ssthresh} = \max(\text{在外数据值}/2, 2*\text{SMSS}) \tag{1} \]


#### 注意
在微软最新的（“下一代”）TCP/IP栈中，这个公式被修改为了更保守的形式：
\[ \text{ssthresh} = \max(\min(\text{cwnd}, \text{awnd})/2, 2*\text{SMSS}) \quad [NB08] \]

从这里可以看到：如果需要重传，TCP会认为当前操作窗口对网络来说过大了。将最优窗口大小的估计值减半，对应的操作就是把`ssthresh`调整为当前窗口大小的一半（但不会低于2倍SMSS）。这通常会降低`ssthresh`，但也可能反过来让`ssthresh`增大——比如在拥塞避免流程中，若一整个窗口的数据都成功传输，`cwnd`会增加约1个段；如果`cwnd`在很长时间内持续变大，将`ssthresh`设为飞行数据量的一半，就可能让它随之增长。这种情况会在TCP发现更多可用带宽时发生。

`ssthresh`与`cwnd`的相互作用，再结合慢启动和拥塞避免的运行逻辑，构成了TCP应对拥塞时的典型行为。接下来我们会分析这些算法结合后的完整流程。


#### 16.2.4 Tahoe、Reno与快速恢复
到目前为止讨论的慢启动和拥塞避免算法，是TCP最早的拥塞控制算法。它们于20世纪80年代末，随加州大学伯克利分校的4.2版BSD UNIX系统被引入，从此开启了以美国城市（尤其是博彩业城市）命名TCP不同版本的惯例。


4.2版BSD（称为**Tahoe**）所包含的TCP版本，会以慢启动开启连接；若检测到丢包（无论是超时还是快速重传机制触发），就会重新启动慢启动流程。Tahoe的实现逻辑是：一旦丢包，就将`cwnd`重置为初始值（当时是1个SMSS），同时强制连接进入慢启动，直到`cwnd`增长到`ssthresh`的值。


这种方式的一个问题是：对于**大带宽时延积（BDP）**的路径，会导致连接严重无法充分利用可用带宽——因为发送方TCP需要重新通过慢启动，才能回到丢包前的运行状态。为解决这个问题，人们重新考虑了“丢包就重启慢启动”的逻辑：最终，若丢包是通过重复ACK检测到的（触发快速重传），`cwnd`会被重置为`ssthresh`的最新值（而非仅1个SMSS）。（不过，超时发生时仍会启动慢启动，这是大多数TCP变体的常见逻辑。）这种方式能让TCP将速率降至之前的一半，同时无需重新走慢启动流程。


在研究大BDP路径的问题时，结合之前提到的数据包守恒原则，人们发现：丢包恢复过程中收到的ACK，依然是向网络注入新包的机会。这催生了**快速恢复**流程，它随流行的4.3版BSD UNIX（Reno版本）一同发布。快速恢复允许在恢复阶段，每收到一个ACK就将`cwnd`（临时）增加1个SMSS，因此拥塞窗口会在一段时间内“膨胀”：每收到一个ACK，就可以额外发送一个新包，直到收到有效ACK为止。任何非重复的（“有效”）ACK都会让TCP退出恢复阶段，并将拥塞窗口恢复到膨胀前的值。TCP Reno变得非常流行，最终成为了所谓“标准TCP”的基础。


#### 16.2.5 标准TCP
尽管“标准”TCP的定义存在一些争议，但我们目前讨论的算法，构成了被广泛认可的标准TCP操作流程。慢启动和拥塞避免这两个核心算法通常会被一同实现，其基准整体行为在RFC5681中有规定。该规范并不强制要求使用这些 exact 算法，但要求任何TCP实现的激进程度不能超过这些算法。


为总结RFC5681中的组合算法：TCP以慢启动开启连接（`cwnd`初始值为IW），同时`ssthresh`会被设为一个较大的值（通常至少等于`awnd`）。当收到有效ACK（即确认了新数据的ACK）时，TCP会按如下方式更新`cwnd`：
- 若`cwnd < ssthresh`：`cwnd += SMSS`（慢启动）
- 若`cwnd > ssthresh`：`cwnd += SMSS*SMSS/cwnd`（拥塞避免）


当收到**第三个重复ACK**（或未使用传统快速重传触发方式时的其他信号）而触发快速重传时，会执行以下操作：
1. 将`ssthresh`更新为不超过公式[1]给出的值；
2. 执行快速重传算法，并将`cwnd`设为`ssthresh + 3*SMSS`；
3. 每收到一个重复ACK，就临时将`cwnd`增加SMSS；
4. 当收到有效ACK时，将`cwnd`重置回`ssthresh`。


步骤2和步骤3共同构成了**快速恢复**：步骤2先调整`cwnd`（通常会将其减至之前的一半），然后临时膨胀它——这是为了考虑“每个重复ACK都意味着有一个包离开了网络，因此应该允许注入另一个包”；这一步也是**乘法减小**发生的地方（`cwnd`通常会乘以某个值，这里是0.5，得到新值）。步骤3会继续膨胀`cwnd`，让发送方可以发送更多包（假设`awnd`未被耗尽）。在步骤4中，TCP被认为已完成恢复，临时的膨胀会被移除（因此这一步有时被称为“放气”）。慢启动通常会在两种场景下被使用：一是新连接建立时，二是发生重传超时的时候。另外，当发送方长时间处于空闲状态，或是有其他理由怀疑当前`cwnd`无法准确反映网络拥塞状况时（见16.3.5节），也可能触发慢启动。这种情况下，`cwnd`的初始值会被设为“重启窗口（RW）”。在RFC5681中，推荐的RW取值为`min(IW, cwnd)`。除此之外，其他场景下触发慢启动时，`cwnd`会被设为初始窗口（IW）的值。
