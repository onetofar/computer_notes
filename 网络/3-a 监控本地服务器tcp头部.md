## 为什么 P6服务端发送数据到客户端,客户端没有立即 ACK 确认

1. P4：客户端→服务端（PSH=1，上行数据）
2. P5：服务端→客户端（纯 ACK，ack=4144723317，**确认完 P4 全部上行数据**，无应用载荷）
3. P6：服务端→客户端（同 Seq=148248699、PSH=1、携带下行业务数据）

> 疑问：客户端收到 P6 下行数据，为什么没立刻回单独 ACK？

### 原因 1：RFC1122 延迟 ACK（Delayed ACK，Linux 默认 200ms 延迟窗口）

Linux TCP 规范：收到对端数据，**不立刻回复独立 ACK**，等待两个触发条件之一：

1. 等待最多`200ms`超时，强制发纯 ACK；
2. 本地应用要发送新数据，**把 ACK 捎带在发往服务端的业务报文头部（捎带确认 piggyback）**。

本链路后面没有客户端新业务发包，**还没到 200ms 延迟 ACK 超时，连接就进入四次挥手流程**。

### 原因 2：P6 的 ACK 最终被【挥手报文捎带确认】

回看挥手报文：

- P7：服务端发 FIN（主动关写）
- P8：客户端回 ACK 报文 `ack=148248760`

> 这个 P8 的 ACK 同时完成两件事：
>
> ① 确认 P6 服务端下发的全部业务数据；
>
> ② 确认服务端 FIN 标志。

**TCP 是累计确认：一个 ACK 号一次性确认所有序号＜ack 值的全部数据，不用分多次单独 ACK**。

也就是：客户端收到 P6 数据后，把 ACK 缓存，等到需要回复 FIN 的确认时统一捎带输出，省去单独空 ACK 小包。

## 为什么 p5服务端是单独确认的ack,和上个问题的捎带不同?

| 包   | 方向                           | 行为                                             |
| ---- | ------------------------------ | ------------------------------------------------ |
| P4   | 客户端(Docker)→服务端(Windows) | 发**上行业务数据**                               |
| P5   | 服务端(Windows)→客户端(Docker) | **单独发纯ACK**（确认P4，无数据）                |
| P6   | 服务端(Windows)→客户端(Docker) | 发**下行业务数据**                               |
| P7   | 服务端(Windows)→客户端(Docker) | 发FIN（主动关闭）                                |
| P8   | 客户端(Docker)→服务端(Windows) | **1个包干2件事**：确认P6数据 + 确认P7FIN（捎带） |



| 对比项               | 服务端（Windows）<br>收到P4数据 → 单独发P5纯ACK              | 客户端（Docker/WSL Linux）<br>收到P6数据 → 不单独发ACK，捎带到P8 |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **操作系统底层行为** | Windows TCP：**默认关闭延迟ACK**<br>收到数据 → 立刻回复ACK，不等 | Linux TCP：**默认强制开启延迟ACK**<br>收到数据 → 先等200ms，能不单独发就不发 |
| **有没有捎带机会**   | 服务端要回下行数据，但**数据生成比ACK慢**<br>ACK先发出，数据后发（拆成P5+P6） | 客户端收到P6后，**完全没有数据要回**<br>没有任何包可以捎带ACK |
| **后续发生了什么**   | 发完ACK+数据后，服务端正常发数据                             | 刚收到P6没几毫秒，**服务端直接发FIN(P7)**<br>延迟ACK还没超时 |
| **最终ACK怎么发**    | 等不及，只能**单独发一个空ACK包**                            | 直接把「P6数据的ACK」合并到「FIN的ACK」里，**1包顶2包**      |

1. **Windows 服务端（P5单独ACK）**
   Windows 收到数据就**立马回ACK**，不会等；它想回数据，但数据没准备好，所以ACK先单独飞出去了。

2. **Docker 客户端（P8捎带ACK）**
   Linux 收到数据**习惯等200ms**，能不发空包就不发；结果还没等到超时，服务端直接发FIN了，客户端干脆在回复FIN的时候，**顺便把P6的数据确认一起带过去**。

## p6-p10 ack seq的推进分析

| 报文 | 流向 | 本方 SEQ                             | ACK (对端) | 报文类型          | 本方发送游标变化    | 对端接收游标变化    | 关键备注                               |
| ---- | ---- | ------------------------------------ | ---------- | ----------------- | ------------------- | ------------------- | -------------------------------------- |
| P6   | S→C  | 148248699                            | 4144723317 | 带 60B 数据 + PSH | S_NXT=+60→148248759 | C_RCV=+60→148248759 | 消耗 60 序号，只传业务                 |
| P7   | S→C  | 148248760                            | 4144723317 | FIN 标志(自占位)  | S_NXT=+1→148248761  | C_RCV=+1→148248761  | FIN 独占 1 序号，无载荷                |
| P8   | C→S  | 4144723317(ack还是要占位,只是不消耗) | 148248760  | 纯 ACK(不占位)    | C_NXT 不变          | S_RCV 不变          | 不消耗 SEQ，仅确认 P6 数据，跳过 FIN   |
| P9   | C→S  | 4144723317(真正的使用了该seq)        | 148248761  | ACK+FIN           | C_NXT=+1→4144723318 | S_RCV=+1→4144723318 | FIN 消耗当前 SEQ，ACK 补上 P7 FIN 确认 |
| P10  | S→C  | 148248761                            | 4144723318 | 纯 ACK            | S_NXT 不变          | C_RCV 不变          | 确认客户端 FIN，挥手闭环               |
