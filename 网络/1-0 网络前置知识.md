# 《TCP/IP 卷一》了解 概述
## 1.1 体系结构原则
### 1.1.1 分组、连接和数据报
网络中数据从一台主机传送到另一台主机，有两种基本方式：**电路交换**和**分组交换**。

|          | 电路交换               | 分组交换                             |
| :- | :--------------------- | :----------------------------------- |
| 工作原理 | 通信前建立独占物理通路 | 数据切分成小块，每个分组独立选择路径 |
| 资源占用 | 独占，即使空闲也占用   | 共享，统计复用，按需分配             |
| 代表     | 传统电话网络           | **TCP/IP 的基础**                    |
TCP/IP 采用分组交换。数据被切分成一个个“包裹”（IP 数据报），每个包裹独立传输，可能走不同的路径，到达目的地后重新组装。“分组”和“数据报”即由此而来。
### 1.1.2 端到端论点和命运共享
**端到端论点**是网络设计中最重要的哲学原则：
> 如果某个功能只能在通信端点完整实现，就不应放在通信子网（中间路由器/交换机）中。
举例：文件传输的可靠性。如果在每一跳路由器上都做数据校验和重传，表面更可靠，但有两个致命问题——中间节点不理解文件完整语义，无法检测应用层错误；即使如此，最终端到端校验仍然必须存在，形成重复工作。因此，正确做法是让两端主机保证可靠性，中间路由器只负责尽力转发。
**命运共享**是端到端论点的推论：
> 状态信息应与依赖它的实体共存。实体崩溃时，状态也随之消失。
这意味着 TCP 连接的状态完全由通信的两台主机维护，任何一台崩溃，连接自然终止，无需网络中间设备去清理状态。
### 1.1.3 差错控制和流量控制
网络中传输数据，必须处理两类基本问题：
**差错控制**：数据损坏、丢失或重复怎么办？
- TCP 的应对：校验和验证完整性，序列号检测丢失和重复，确认和重传恢复丢包
- UDP 的应对：仅有可选的校验和，无可靠交付保证，将差错处理交给应用层
**流量控制**：发送方速度超过接收方处理能力怎么办？
- TCP 的应对：滑动窗口协议。接收方通告自己还能接收多少数据，发送方据此调整速率。窗口变为 0 时发送方停止发送——这正是你 D17 要实现的“零窗口探测”
- UDP 的应对：无流量控制，应用层自行处理
TCP 将差错控制和流量控制都放在传输层，由端点主机之间协调完成，完美体现了端到端论点。

## 1.2 设计和实现

### 1.2.1 分层

**为什么要分层？** 直接将网络通信实现为一个庞大的程序不可行。分层将宏大问题分解为若干相对独立的子问题，每个子问题由一个“层”负责。

分层的三大核心价值：**模块化**（每层可独立开发和测试）、**互操作性**（只要层间接口一致，不同厂商实现可互换）、**独立演化**（某一层技术升级不影响其他层）。

分层的黄金法则：**每一层只使用下层提供的服务，每一层只向上层提供服务。层与层之间通过严格定义的接口通信。**

### 1.2.2 分层实现中的复用、分解和封装

这是理解数据如何“走通”整个协议栈的核心。场景：浏览器输入 `http://www.example.com`。

**封装过程（发送端，自上而下）**：

```
# HTTP请求的封装过程（发送端，自上而下）
> 锚定：TCP/IP卷一 · 链路层/网络层封装 | 标记：🛜链路层 | 🐧网络层 | 📘编码层

【前置步骤】ARP解析（独立流程，非IP封装的一部分）
┌───────────────┐     ┌───────────────┐
│ ARP请求帧      │     │ ARP应答帧      │
│ 类型=0x0806   │     │ 类型=0x0806   │
│ 目标MAC=广播FF:FF:FF │ │ 目标MAC=本机MAC │
└───────────────┘     └───────────────┘
作用：获取目标IP对应的MAC地址，为封装以太网帧做准备

【正式封装流程】
┌──────────┬───────────────────────────────────────────┐
│ 层级      │ 内容                                         │
├──────────┼───────────────────────────────────────────┤
│ 应用层    │ HTTP请求报文                                 │
├──────────┼───────────────────────────────────────────┤
│ 传输层    │ TCP头部（源端口:52341，目标端口:80，协议=TCP） + HTTP数据 │
├──────────┼───────────────────────────────────────────┤
│ 网络层    │ IP头部（协议=6代表TCP，源IP/目标IP） + TCP段（TCP头+HTTP数据） │
├──────────┼───────────────────────────────────────────┤
│ 链路层    │ 以太网帧头部（目标MAC/源MAC/类型=0x0800） + IP数据报 + FCS（硬件层，编码不可见） │
├──────────┼───────────────────────────────────────────┤
│ 物理层    │ 转换为比特流发送                             │
└──────────┴───────────────────────────────────────────┘
```

**解封装过程（接收端，自下而上）**：与上述完全相反。每一层剥掉属于自己的头部，检查头部中的标识符，根据标识符将数据向上传递给正确的协议处理器。

**复用与分解的本质**：发送方将多个上层协议的数据通过同一个下层协议发送（复用）；接收方根据头部标识字段精确交付给正确的上层协议（分解）。每一层的复用/分解规则都是相同的——通过特定字段标识上层协议。

关键的三种标识字段：

| 层级            | 标识字段               | 示例                             |
| :-------------- | :--------------------- | :------------------------------- |
| 链路层 → 网络层 | EtherType              | 0x0800 → IPv4, 0x0806 → ARP      |
| 网络层 → 传输层 | IP 协议字段 (Protocol) | 6 → TCP, 17 → UDP                |
| 传输层 → 应用层 | 端口号 (Port)          | 80 → HTTP, 443 → HTTPS, 53 → DNS |

## 1.3 TCP/IP 协议族结构和协议

### 1.3.1 ARPANET 参考模型

TCP/IP 体系架构脱胎于 ARPANET。ARPANET 分为应用层、传输层、网络层、链路层、物理层。今天的 TCP/IP 模型将链路层和物理层合并为“网络接入层”，形成四层模型。

### 1.3.2 TCP/IP 中的复用、分解和封装

本节将 1.2.2 的概念具体映射到 TCP/IP 协议族中。核心递归逻辑：每一层的复用/分解规则相同——通过特定字段标识上层协议。你可以发明新的应用层协议（如 QUIC），只需分配一个新的端口号，而不需修改传输层或 IP 层的任何代码。

### 1.3.3 端口号

端口号是 16 位整数（0 ~ 65535），分为三类：

| 范围          | 名称          | 用途                                | 示例                         |
| :------------ | :------------ | :---------------------------------- | :--------------------------- |
| 0 ~ 1023      | 知名端口      | 分配给标准服务，需系统权限绑定      | 80=HTTP, 443=HTTPS, 22=SSH   |
| 1024 ~ 49151  | 注册端口      | IANA 分配给特定应用，普通用户可绑定 | 3306=MySQL, 6379=Redis       |
| 49152 ~ 65535 | 动态/私有端口 | 客户端临时使用，操作系统自动分配    | 浏览器发起连接时使用的源端口 |

你 D4 写 TCP 客户端连接百度 80 端口时，源端口会被操作系统自动分配一个 49152-65535 之间的数字。

### 1.3.4 名称、地址和 DNS

| 概念               | 定义                                   | 示例                              |
| :----------------- | :------------------------------------- | :-------------------------------- |
| **名称** (Name)    | 人类可读的标识符，便于记忆             | `www.baidu.com`                   |
| **地址** (Address) | 机器可处理的数字标识符，用于路由和寻址 | `192.168.1.1` (IPv4)              |
| **DNS**            | 分布式数据库系统，将名称解析为地址     | `www.baidu.com` → `110.242.68.66` |

**为什么需要名称？直接用 IP 地址不行吗？** 人类不擅长记忆长串数字；服务器 IP 地址可能因扩容、迁移而变化；名称提供了一层稳定的抽象。DNS 负责维护这份“名称→地址”映射表。你 D38 会亲自实现一个 DNS 解析器。

## 1.4 Internet、内联网和外联网

三者在技术上使用相同的 TCP/IP 协议栈，区别仅在于访问范围和安全边界：

| 术语                   | 定义                                           | 特点                         |
| :--------------------- | :--------------------------------------------- | :--------------------------- |
| **Internet（互联网）** | 全球范围内通过 TCP/IP 协议族互联的所有网络集合 | 公有，任何人可接入           |
| **内联网 (Intranet)**  | 企业/组织内部使用 TCP/IP 技术的私有网络        | 防火墙隔离，外部无法直接访问 |
| **外联网 (Extranet)**  | 将内联网有控制地扩展到外部合作伙伴             | 部分权限开放给供应商、客户   |

## 1.5 设计应用

### 1.5.1 客户机/服务器模型 (C/S)

这是你 D4 写 TCP 客户端、D6 写 UDP Echo 服务器、D31 设计游戏网关时都在使用的模型。

```
┌──────────┐
│  服务器   │  总是在线，被动等待，拥有固定 IP:Port
└────┬─────┘
     │ 接受连接，为每个客户端创建新 socket
     │
┌────┼────┬──────────┐
│    │    │          │
▼    ▼    ▼          ▼
客户端A  客户端B  客户端C   主动发起连接，请求服务
```

交互流程：服务器启动 → 绑定端口 → 进入监听 → 客户端发起连接 → 服务器接受并创建新 socket → 双方交换数据 → 任一方关闭连接。

典型应用：Web（浏览器/服务器）、游戏（游戏客户端/服务器）、数据库（应用/数据库服务器）。

### 1.5.2 对等模型 (P2P)

网络中每个节点地位相等，既是服务提供者也是服务消费者，没有严格的“服务器”和“客户端”之分。典型应用：文件分享 (BitTorrent)。

设计挑战：NAT 穿透（对等节点可能都在内网中）、节点动态加入和离开的处理、无中心节点的资源定位。

### 1.5.3 应用程序编程接口 (API)

API 是应用层进入传输层的入口。**你通过 socket API 告诉传输层：“把这份数据，用 TCP，传给 192.168.1.5 的 8080 端口。”** 传输层完成所有封装和可靠性保证，应用层不关心这些细节。

你将在 D4（B §1.7）和 D8（B §5.1-5.7）深入学习 socket API 的具体调用。

## 1.6 标准化进程

### 1.6.1 RFC

RFC (Request for Comments) 是 TCP/IP 协议族的事实标准文档。

| RFC      | 定义内容                                    |
| :------- | :------------------------------------------ |
| RFC 791  | IPv4 协议                                   |
| RFC 793  | TCP 协议                                    |
| RFC 768  | UDP 协议                                    |
| RFC 6298 | TCP 重传超时计算（正是你 D13 要实现的内容） |
| RFC 826  | ARP 协议（你 D1-D2 的主角）                 |

RFC 不是法律，是共识。所有网络设备制造商、操作系统开发者、应用开发者都遵循 RFC，才能实现全球互联互通。遇到协议细节争议时，RFC 是最终裁判。

### 1.6.2 其他标准组织

| 组织 | 制定内容                 | 示例              |
| :--- | :----------------------- | :---------------- |
| IETF | TCP/IP 协议标准 (RFC)    | TCP, IP, HTTP     |
| IEEE | 底层物理网络标准         | IEEE 802.3 以太网 |
| W3C  | Web 标准                 | HTML, CSS         |
| ISO  | OSI 七层模型（理论参考） | OSI 模型          |

## 1.7 实现和软件分发

> **不存在“一个 TCP/IP 程序”。** TCP/IP 功能分散在操作系统内核（负责协议处理逻辑）、库函数（提供 socket API）和应用程序（调用 API）中。

## 1.8 与 Internet 体系结构相关的攻击

| 攻击类型     | 目标层 | 原理                                        |
| :----------- | :----- | :------------------------------------------ |
| ARP 欺骗     | 链路层 | 伪造 ARP 响应，将 IP 地址映射到攻击者的 MAC |
| IP 欺骗      | 网络层 | 伪造 IP 数据报的源地址，隐藏真实身份        |
| SYN 泛洪     | 传输层 | 发送大量 SYN 报文耗尽服务器的半连接队列     |
| DNS 缓存污染 | 应用层 | 向 DNS 解析器注入伪造的域名-IP 映射         |

学习建议：现在不需要深入理解每种攻击。随着你 D2（ARP 报文）、D10-D20（TCP 连接管理、状态机、序列号）的学习，你会自然地理解这些攻击的原理。当你能自己实现 ARP 欺骗检测或 SYN flood 防御时，说明你已经真正掌握了协议的本质。

## 1.9 总结

进入第三章链路层细节之前，确保脑中已有以下完整骨架：

1. **分组交换是基石**：数据切块，独立路由，统计复用
2. **分层是管理复杂性的手段**：四层模型将大问题分解，每层独立演化
3. **封装和解封装是数据传输的机制**：层层打包，层层拆包；每层通过标识字段实现复用和分解
4. **端到端论点是设计哲学**：将复杂性放在网络边缘，保持网络核心简洁
5. **C/S 和 P2P 是两种基本通信模型**：你要写的所有代码都属于 C/S 模型
6. **API 是应用层与协议栈的接口**：socket 编程就是对这个接口的直接使用
7. **RFC 是协议的事实标准**：遇到争议，查 RFC
