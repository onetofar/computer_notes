```mermaid
sequenceDiagram
    title MTU=1500以太网链路上的UDP分片/不分片完整时序（含分片语法+重排序原理）
    participant 发送方 10.0.0.5
    participant 接收方 10.0.0.3
    Note over 发送方,接收方: 基础前提：IPv4头20B + UDP头8B = 28B<br/>IP分片规则：非最后分片数据长度必须为8B倍数；DF=1禁止分片；+代表MF=1(还有后续分片)

    %% 组1：1471字节UDP，不分片
    发送方 10.0.0.5->>接收方 10.0.0.3: 23:42:43.562452<br/>UDP 1471B (DF=1)<br/>总IP长度1499B<br/>不分片，单包发送
    Note right of 接收方 10.0.0.3: 1471B ≤ 1472B上限，DF位开启，无需分片，完整携带UDP端口

    %% 组2：1472字节UDP，不分片
    发送方 10.0.0.5->>接收方 10.0.0.3: 23:42:50.267424<br/>UDP 1472B (DF=1)<br/>总IP长度1500B<br/>不分片，单包发送
    Note right of 接收方 10.0.0.3: 1472B = 上限，刚好填满MTU，DF位开启，无需分片，完整携带UDP端口
 Note over 发送方,接收方: ⚠️发送方**主动重排序**：人为颠倒分片发送顺序<br/>先发偏移更大的【最后分片】→后发偏移0的【首分片】<br/>目的：接收方提前获取总长度，预分配最大重组缓存
    %% 组3：1473字节UDP，分片，重排序先发后片
    发送方 10.0.0.5->>接收方 10.0.0.3: 23:42:57.814555<br/>分片1 frag 37671:1@1480<br/>IP总长度21B(20B头+1B数据)<br/>偏移1480，最后1B数据
    Note right of 接收方 10.0.0.3: 语法拆解：1=数据长度1B；@1480=字节偏移；无+→MF=0(最后分片)<br/>无UDP头部，tcpdump无法显示端口
    发送方 10.0.0.5->>接收方 10.0.0.3: 23:42:57.814715<br/>分片2 frag 37671:1480@0+<br/>IP总长度1500B(20B头+1480B数据)<br/>偏移0，前1472B数据
    Note right of 接收方 10.0.0.3: 语法拆解：1480=8B UDP头+1472B数据(8B倍数)；@0=起始偏移；+→MF=1(还有分片)<br/>携带完整UDP端口
   %% 组4：1474字节UDP，分片，重排序先发后片
    Note over 发送方,接收方: 复用相同**主动重排序**逻辑，非首分片均无UDP端口信息
    发送方 10.0.0.5->>接收方 10.0.0.3: 23:43:04.368677<br/>分片1 frag 37672:2@1480<br/>IP总长度22B(20B头+2B数据)<br/>偏移1480，最后2B数据
    Note right of 接收方 10.0.0.3: 语法拆解：2=数据长度2B；@1480=字节偏移；无+→MF=0(最后分片)<br/>无UDP头部，tcpdump无法显示端口
    发送方 10.0.0.5->>接收方 10.0.0.3: 23:43:04.368838<br/>分片2 frag 37672:1480@0+<br/>IP总长度1500B(20B头+1480B数据)<br/>偏移0，前1472B数据
    Note right of 接收方 10.0.0.3: 语法拆解：1480=8B UDP头+1472B数据(8B倍数)；@0=起始偏移；+→MF=1(还有分片)<br/>携带完整UDP端口

```

## ICMPv4分片实战(未重排序)

<img src="./md_pict/image-20260520163346899.png" alt="image-20260520163346899" style="zoom:67%;" />

层次结构:

```c++
# 原始完整IP报文（总长度1501字节）
┌─────────────────────────────────────────────────────────────┐
│ IPv4头部(20B)                                              │
├─────────────────────────────────────────────────────────────┤
│ ICMP报文(1481B)                                            │
│   ├─ ICMP头部(8B)  (ping回显请求)                           │
│   └─ ICMP数据(1473B)  (ping -s 1473指定的负载)              │
└─────────────────────────────────────────────────────────────┘

# 分片1（MTU=1500B，MF=1 还有后续分片）【先发】
┌─────────────────────────────────────────────────────────────┐
│ IPv4头部(20B) 【设置MF标志位】                              │
├─────────────────────────────────────────────────────────────┤
│ ICMP头部(8B) + ICMP数据前1472B （1480B，8B对齐）           │
└─────────────────────────────────────────────────────────────┘

# 分片2（最后分片，MF=0）【后发】
┌─────────────────────────────┐
│ IPv4头部(20B)              │
├─────────────────────────────┤
│ ICMP数据剩余1B              │
└─────────────────────────────┘
```



```mermaid
sequenceDiagram
    title MTU=1500以太网链路上的ICMP(ping)分片完整时序（标准顺序、无重排序）
    participant 发送方 192.168.1.108
    participant 接收方 192.168.1.110
    Note over 发送方,接收方: 基础前提：IPv4头20B + ICMP头8B = 28B<br/>IP分片规则：非最后分片数据长度必须为8B倍数；+代表MF=1(还有后续分片)<br/>ping -s 1473：ICMP数据1473B，总IP长度1501B，强制分片<br/>✅标准顺序：先发首分片，后发最后分片，**无重排序**

    %% ICMP唯一分片组：正常顺序发送
    发送方 192.168.1.108->>接收方 192.168.1.110: ping分片1<br/>ip id 61197:1480@0+<br/>总IP长度1500B<br/>偏移0，前1472B ICMP数据
    Note right of 接收方 192.168.1.110: 语法拆解：1480=8B ICMP头+1472B数据(8B倍数)；@0=起始偏移；+→MF=1(还有分片)<br/>携带完整ICMP头部，tcpdump识别ping请求
    发送方 192.168.1.108->>接收方 192.168.1.110: ping分片2<br/>ip id 61197:1@1480<br/>总IP长度21B<br/>偏移1480，最后1B ICMP数据
    Note right of 接收方 192.168.1.110: 语法拆解：1=数据长度1B；@1480=字节偏移；无+→MF=0(最后分片)<br/>无ICMP头部，tcpdump仅识别为icmp
    Note over 发送方,接收方: 标准默认行为：分片按顺序发送，不做重排序
```

| 案例                     | 发送顺序                  | 行为类型                         |
| ------------------------ | ------------------------- | -------------------------------- |
| UDP 分片（前面的）       | 先发最后分片 → 后发首分片 | **主动重排序（特殊优化实现）**   |
| ICMP ping 分片（本案例） | 先发首分片 → 后发最后分片 | **标准默认顺序（常规系统行为）** |

```mermaid
sequenceDiagram
    title IPv4 ICMP分片重组超时&DoS攻击风险 完整时序
    participant 发送方 10.0.0.5 (攻击者)
    participant 接收方 10.0.0.3
    Note over 发送方,接收方: 核心规则：收到任意分片即启动计时器<br/>收到新分片**不重置**计时器；超时默认30s；残缺分片可发起缓存耗尽攻击;
    Note over 发送方,接收方: 核心规则：380 ÷ 8 = 47.5 → 不是 8 的整数倍，<br>内核强制截断到376 字节（47×8=376，最大的 8 倍数多出来的 4 字节，<br>必须放到下一个分片里,所以第二个数据报偏移为376
    %% 步骤1：发送第一个分片，触发计时
    发送方 10.0.0.5->>接收方 10.0.0.3: 17:35:59<br/>分片1 frag 28519:380@0+<br/>偏移0，MF=1(还有分片)
    Note right of 接收方 10.0.0.3: 收到首分片 → 启动30s重组计时器

    %% 步骤2：20s后发送第二个分片，计时器不重置
    发送方 10.0.0.5->>接收方 10.0.0.3: 17:36:19(间隔20s)<br/>分片2 frag 28519:380@376+<br/>偏移376，MF=1(还有分片)
    Note right of 接收方 10.0.0.3: 收到后续分片 → 计时器**不重置**，继续倒计时

    %% 步骤3：攻击者停止发送剩余分片
    Note over 发送方,接收方: ⚠️攻击行为：发送方停止发送剩余所有分片<br/>接收方永远收不到最后分片

    %% 步骤4：30s计时器到期，超时丢弃
    Note over 接收方 10.0.0.3: 17:36:29(首分片接收后满30s)<br/>计时器超时 → 丢弃所有缓存分片

    %% 步骤5：接收方回复ICMP重组超时报文
    接收方 10.0.0.3->>发送方 10.0.0.5: 17:36:29<br/>ICMPv4 重组超时(类型11 代码1)<br/>告知：分片超时、报文丢失
    Note over 发送方,接收方: 安全意义：计时器抵御残缺分片DoS攻击<br/>未收到首分片时，接收方通常不回复ICMP错误
```
