## 以太网帧 = 标准结构 + 可选扩展
以太网帧就像一个快递包裹，有一个**所有包裹都有的标准外壳**，和一些**特殊服务才需要的可选标签**。
### 核心名词
### 链路层核心名词
| 名词                                    | 一句话解释                                              | 你需要知道的边界                                             |
| :-------------------------------- | :------------------------------------------------------ | :----------------------------------------------------------- |
| **以太网帧 (Ethernet Frame)**           | 链路层传输的数据单元，包含 MAC 地址、上层协议标识和数据 | 你写 `arp_sniffer` 抓到的就是帧。libpcap 给你的帧从“目标 MAC”开始，不包含前导/SFD/FCS |
| **MAC 地址**                            | 48 位物理地址，唯一标识一个网络接口                     | 帧里有两个 MAC：源和目的。ARP 协议就是用来通过 IP 找 MAC 的  |
| **EtherType (类型字段)**                | 帧头部的 2 字节字段，标识上层协议                       | `0x0800`=IPv4，`0x0806`=ARP。你的代码里用 `ntohs(eth->ether_type)` 读的就是它 |
| **前导 (Preamble)**                     | 7 字节 `0xAA`，网卡用来恢复时钟同步                     | 纯硬件层面，libpcap 不给你看，不需要学                       |
| **SFD (帧起始分隔符)**                  | 1 字节 `0xAB`，标记“前导结束，数据开始”                 | 类比 `CAFEBABE` 之于 Java class 文件。同样是硬件处理，不需要学 |
| **FCS (帧校验序列)**                    | 4 字节 CRC32 校验，检测帧是否在传输中损坏               | 网卡硬件自动校验/丢弃，libpcap 不给你看                      |
| **CRC(循环冗余校验)**                   | 一种算法                                                |                                                              |
| **MTU (最大传输单元)**                  | 以太网帧数据部分的上限，通常 1500 字节                  | 你 D7 做 IP 分片实验时需要用到                               |
| **CSMA/CD (载波侦听多路访问/冲突检测)** | 早期共享以太网解决“多人同时说话”问题的机制              | 现代交换机已淘汰，只需知道名字。你的知识边界在这里           |
### 网络设备名词
| 名词                   | 一句话解释                                   | 你需要知道的关键点                                          |
| :--------------------- | :------------------------------------------- | :---------------------------------------------------------- |
| **交换机 (Switch)**    | 工作在链路层，只看 MAC 地址转发帧            | 自学习端口-MAC 映射表。转发/泛洪/过滤三种行为               |
| **PDU (协议数据单元)** | 每一层协议处理的数据包的通称，各层有自己名字 | 应用层=消息，传输层=段，网络层=包，链路层=帧，物理层=比特流 |
### 标准与协议名词
| 名词                 | 一句话解释                                     | 你需要知道的边界                                     |
| :------------------- | :--------------------------------------------- | :--------------------------------------------------- |
| **IEEE 802.3**       | 以太网的标准定义，规定帧格式和物理层规范       | 所有你现在学的帧格式都由它定义                       |
| **IEEE 802.1Q**      | VLAN 标准，在帧里插入 4 字节标签区分虚拟局域网 | 游戏服务器部门内部可能会用，个人开发用不到           |
| **IEEE 802.1p**      | 在 VLAN 标签里定义 3 位优先级字段              | QoS 相关，个人开发用不到                             |
| **IEEE 802.2 (LLC)** | 逻辑链路控制，解耦上层协议和下层物理网络       | 理解它在链路层内部做了分层设计，屏蔽不同硬件差异即可 |
| **RFC**              | TCP/IP 协议的事实标准文档                      | 遇到协议争议时查 RFC 是最终裁判                      |
### 地址与标识名词
| 名词             | 一句话解释                                 | 关键细节                                                     |
| :--------------- | :----------------------------------------- | :----------------------------------------------------------- |
| **Magic Number** | 协议或文件头部的固定值，触发接收方识别格式 | 以太网前导/SFD 是硬件的 Magic Number，`CAFEBABE` 是 JVM 的，你 D31 设计 TLV 协议时也要定义自己的 |
| **端口号**       | 16 位数字，标识传输层上是哪个应用程序      | 0-1023 知名端口，1024-49151 注册端口，49152-65535 客户端临时用 |
### 加密与安全名词
| 名词         | 一句话解释                           | 你的计划节点                   |
| :----------- | :----------------------------------- | :----------------------------- |
| **ARP 欺骗** | 伪造 ARP 响应，IP 映射到攻击者的 MAC | D2 学到 ARP 协议时自然会理解   |
| **ARP 泛洪** | 发送大量 ARP 请求耗尽交换机资源      | 了解攻击类型即可，D39 可选深究 |
### 关键认知结论
- **CSMA/CD**：共享线路时代的冲突解决方案，现代交换机已淘汰
- **前导/SFD**：硬件时钟同步机制，网卡处理，你看不到
- **FCS**：硬件校验，网卡处理，你看不到
- **载体扩展**：半双工时代的历史包袱，已死
### 标准外壳（每个帧都有）
```
┌─────────┬─────┬──────────┬──────────┬────────────┬──────────────┬─────┐
│  前导    │ SFD │ 目标MAC  │  源MAC   │ 长度/类型   │    数据      │ FCS │	+载体拓展
│ (7字节)  │(1B) │  (6字节) │ (6字节)  │  (2字节)   │ (46-1500字节)│(4B) │
└─────────┴─────┴──────────┴──────────┴────────────┴──────────────┴─────┘
```
| 字段                | 含义                                    | 你不需要记住细节的事                                         |
| :------------------ | :-------------------------------------- | :----------------------------------------------------------- |
| **前导 (Preamble)** | 7 字节，固定模式 `0xAA`                 | 这是**硬件层面的事**，网卡用它来同步时钟。你写 `arp_sniffer` 时，libpcap **根本不给你看这个字段**——网卡已经处理完了。 |
| **SFD**             | 1 字节，固定值 `0xAB`                   | "帧开始分隔符"，就是告诉网卡："前导结束，后面是正经数据了"。同样，**libpcap 不给你看**。 |
| **目标 MAC (DST)**  | 6 字节，接收方的 MAC 地址               | 你抓 ARP 包时打印的第一个 MAC 地址就是这个                   |
| **源 MAC (SRC)**    | 6 字节，发送方的 MAC 地址               | 你抓 ARP 包时打印的第二个 MAC 地址                           |
| **长度/类型**       | 2 字节，`0x0800` = IPv4，`0x0806` = ARP | 这就是你的 `arp_sniffer` 里 `ntohs(eth->ether_type)` 读到的值 |
| **数据**            | 46-1500 字节                            | 里面装着 IP 包或 ARP 报文（是以太网数据区的**字节数上下限**） |
| **FCS**             | 4 字节，CRC32 校验                      | 网卡自动校验，**libpcap 不给你看**                           |
**fcs功能：**
**CRC 会提前约定一个二进制数作为除数（叫生成多项式），比如图里的 `10011`（对应 CRC4 标准），它的长度是 `n+1` 位（这里 n=4，所以除数是 5 位）。**
**结合图里的 CRC4 例子，秒懂过程**
1. **原始数据**：`1001111000101111`（16 位）
2. **约定除数（生成多项式）**：`10011`（5 位，CRC4 标准）
3. **补零扩展**：原始数据 + 4 个 0 → 被除数 `10011110001011110000`
4. **模 2 除法**：按图里的步骤做异或运算，最后得到 4 位余数 `1111`
5. **生成校验码**：余数取反 → `0000`，把它追加到原始数据后面，组成最终发送的数据
因为生成多项式是精心设计的，能检测绝大多数常见错误：
- 单比特错误（某一位翻转）
- 双比特错误（两位同时翻转）
- 奇数个错误（任意奇数位翻转）
- 突发错误（连续多位翻转）

------

**帧大小分析：**

**以太网帧（从目标 MAC 到 FCS）的固定开销：**

- 目标 MAC（6B）+ 源 MAC（6B）+ 类型 / 长度（2B）= 14 字节（帧头）

- 尾部 FCS 校验（4B）

  固定开销合计：

  ```
  14 + 4 = 18字节
  ```

最小帧长约束：`帧头 + 数据区 + FCS ≥ 64字节`

代入固定开销计算：`18 + 数据区长度 ≥ 64` → `数据区长度 ≥ 64 - 18 = 46字节`

------

**前导的设计思想**：
以太网的 `0xAA 0xAB` 比 `CAFEBABE` 多承担了一个职责：**时钟恢复**。`0xAA` 在二进制下是 `10101010`，在物理线上是一个完美的重复方波信号——这是有意选择的，因为它最大限度地为接收方的锁相环电路提供了跳变参考。网卡利用这串方波调整自己的采样时钟，确保接下来采集 `0xAB`（`10101011`）时能精确区分这个 bit 究竟是 0 还是 1。`0xAB` 的最后两 bit 突然打破规律（`11` 而非 `10`），这就是在通知网卡：“同步结束，接在后面的第一个 byte 就属于目标 MAC 地址了。”

**结论**：你实际能用 libpcap 抓到的，只有 **DST + SRC + 类型 + 数据**。前导、SFD、FCS 都是网卡硬件处理的，你看不到也摸不到。不需要纠结它们。

### 可选标签（只有特殊需求时才出现）

你截图里的 "P/Q 标签" 和 "其他标签" 就是这类的。

**802.1p/q 标签（VLAN 标签）**

```
┌──────────┬────┬───┬───────┐
│ 标签协议ID│优先级│CFI│ VLAN ID│
│ (2字节)  │(3位)│1位│ (12位) │
└──────────┴────┴───┴───────┘
```

| 字段             | 含义                                      |                                            |
| :--------------- | :---------------------------------------- | :----------------------------------------- |
| **标签协议 ID**  | 固定值 `0x8100`，表明"这是一个 VLAN 标签" | 不关心                                     |
| **优先级 (PCP)** | 3 位，0-7 优先级                          | 802.1p QoS。游戏服务器的语音流量可能会用到 |
| **CFI**          | 1 位，兼容标志                            | 历史遗留，基本忽略                         |
| **VLAN ID**      | 12 位，标识这是哪个虚拟局域网             | 公司网络隔离时用，你个人开发环境用不到     |

**"其他标签"（信封帧）**：这是更晚出现的扩展标签，最长可以到 482 字节。用来在帧里塞一些额外的元数据（比如运营商网络里的服务链信息）。

### 载体扩展（仅半双工）

图里最后那个 "(仅半双工)" 的载体扩展，是**历史遗留问题**。早期以太网是半双工的（共享线路，需要 CSMA/CD），为了让冲突检测能正常工作，帧不能太短。到了 100Mbps 以上，如果帧太短，发送方发完了它还没听到冲突信号。于是标准允许在帧尾补一些无用的 bit（载体扩展）来拖长时间。

**现代交换机全是全双工的，CSMA/CD 已死，载体扩展已死。** 你连看都不需要看。

## 以太网帧与 ARP 报文：封装关系与字段重复解析（核心补充）

> 锚定：TCP/IP 卷一 3.4 ARP 协议 | 解决你疑惑的**重复字段、层级归属、封装顺序**

### 1. 层级与定位（彻底分清内外）

- **外层：以太网帧** → 🛜**链路层容器**：负责硬件寻址、帧转发，给网卡 / 交换机看
- **内层：ARP 报文** → 🐧**网络层载荷**：负责 IP→MAC 地址解析，给操作系统协议栈看
- **关系**：ARP 报文是以太网帧**数据字段**里的内容，不是平行关系，是**封装关系**

### 2. 完整封装 / 解封装流程（纠正顺序偏差）

**发送（自上而下封装）**

1. 🐧网络层：构造 ARP 请求 / 应答报文
2. 🛜链路层：将 ARP 报文放入以太网帧**数据区**，填写类型 =`0x0806`，补全源 / 目的 MAC
3. 🌏硬件层：追加前导 / SFD，发送比特流；接收时剥离前导 / SFD、校验 FCS
4. 协议栈：按类型字段将数据区交给 ARP 协议解析

**接收（自下而上解封装）**

1. 网卡只识别以太网帧，**不解析 ARP**
2. 类型 =`0x0806` → 交给 ARP 协议
3. 类型 =`0x0800` → 交给 IP 协议

### 3. 字段重复现象与本质（你观察到的关键）

| 以太网帧（外层） | ARP 报文（内层） | 重复状态                 | 核心原因                                                     |
| ---------------- | ---------------- | ------------------------ | ------------------------------------------------------------ |
| 源 MAC 地址      | 发送端以太网地址 | **完全一致**             | 分层解耦、双重校验、协议通用                                 |
| 目的 MAC 地址    | 目的端以太网地址 | 请求：不一致；应答：一致 | 请求时未知目标 MAC，帧用广播`FF:FF:FF:FF:FF:FF`，报文填`00:00:00:00:00:00` |

**重复不是冗余，是分层设计必然：**

1. **职责分离**

   - 帧 MAC：给**硬件 / 交换机**用，负责链路层转发
   - 报文 MAC：给**ARP 协议栈**用，负责地址映射数据传递

2. **协议通用性**

   ARP 不绑定以太网，支持令牌环 / ARCnet 等，必须自带地址字段，不依赖链路层头部

3. **安全校验**

   帧源 MAC ≠ 报文发送 MAC → 判定为 ARP 欺骗，直接丢弃

### 4. 关键认知修正

- ❌ 错误：网卡解析 ARP → 生成以太网外壳
- ✅ 正确：**网卡只处理以太网帧，不理解 ARP**；ARP 报文被封装进帧的数据区，由操作系统协议栈解析

## ARP 和 IP 数据报的真实关系

以你 tcpdump 里的例子（`ernest-laptop` 要和 `Kongming20` 通信），完整流程是这样的：

### 1. 前置步骤：ARP 地址解析（独立流程）

1. 主机 `ernest-laptop` 要给 `192.168.1.109` 发 IP 包，先查本地 ARP 缓存，没有找到对应的 MAC 地址；
2. 构造一个 **ARP 请求报文**（内容：“谁是 192.168.1.109？请告诉我你的 MAC 地址”）；
3. 把这个 ARP 报文放进以太网帧的数据区，设置：
   - 目标 MAC：广播地址 `FF:FF:FF:FF:FF:FF`
   - 类型字段：`0x0806`（告诉网卡 “数据区是 ARP 报文”）
4. 发送这个 ARP 请求帧，等待应答；
5. 收到 `Kongming20` 的 ARP 应答帧（类型也是`0x0806`），拿到 MAC 地址 `08:00:27:53:10:67`，存入 ARP 缓存。

### 2. 正式步骤：IP 数据报封装流程

1. 构造 IP 数据报（比如 TCP/HTTP 数据）；

2. 把 IP 数据报放进以太网帧的数据区，设置：

   - 目标 MAC：刚才拿到的 `08:00:27:53:10:67`
   - 类型字段：`0x0800`（告诉网卡 “数据区是 IP 数据报”）

3. 发送这个 IP 帧，完成通信。

## ARP补充

### 1. ARP 报文的具体格式（补充封装内层细节）

ARP 报文作为以太网帧数据区的载荷，其自身有固定结构（总长度 28 字节），字段定义如下：

| 字段                   | 长度（字节） | 含义                                                         |
| :--------------------- | :----------- | :----------------------------------------------------------- |
| **硬件类型 (hrd)**     | 2            | 标识底层硬件类型，`0x0001` = 以太网（最常用）                |
| **协议类型 (pro)**     | 2            | 标识上层协议类型，`0x0800` = IPv4（和以太网帧的 EtherType 对应） |
| **硬件地址长度 (hln)** | 1            | 硬件地址（MAC）的长度，固定为 6                              |
| **协议地址长度 (pln)** | 1            | 协议地址（IP）的长度，固定为 4（IPv4）                       |
| **操作码 (op)**        | 2            | `0x0001` = ARP 请求，`0x0002` = ARP 应答                     |
| **发送方 MAC 地址**    | 6            | 发送端的硬件地址（和以太网帧源 MAC 一致）                    |
| **发送方 IP 地址**     | 4            | 发送端的 IP 地址                                             |
| **目标 MAC 地址**      | 6            | 接收端的硬件地址（请求时为 `00:00:00:00:00:00`，应答时为真实 MAC） |
| **目标 IP 地址**       | 4            | 接收端的 IP 地址                                             |

### 2. libpcap 抓包实操：解析以太网帧 + ARP 报文（代码示例）

以下是 `arp_sniffer` 中核心解析逻辑的简化示例，直观展示如何从抓包数据中提取帧和 ARP 字段：

```c
#include <pcap.h>
#include <netinet/ether.h>
#include <arpa/inet.h>

// 定义以太网帧头部结构体（仅包含 libpcap 能抓到的部分）
struct eth_header {
    u_char dst_mac[6];  // 目标 MAC
    u_char src_mac[6];  // 源 MAC
    u_short ether_type; // 类型字段
};

// 定义 ARP 报文结构体
struct arp_header {
    u_short hrd;        // 硬件类型
    u_short pro;        // 协议类型
    u_char hln;         // 硬件地址长度
    u_char pln;         // 协议地址长度
    u_short op;         // 操作码
    u_char src_mac[6];  // 发送方 MAC
    u_char src_ip[4];   // 发送方 IP
    u_char dst_mac[6];  // 目标 MAC
    u_char dst_ip[4];   // 目标 IP
};

void packet_handler(u_char *user_data, const struct pcap_pkthdr *pkthdr, const u_char *packet) {
    // 1. 解析以太网帧头部（从 packet 起始位置取 14 字节）
    struct eth_header *eth = (struct eth_header *)packet;
    if (ntohs(eth->ether_type) != 0x0806) {
        return; // 只处理 ARP 帧
    }

    // 2. 解析 ARP 报文（以太网帧头后偏移 14 字节）
    struct arp_header *arp = (struct arp_header *)(packet + 14);

    // 3. 打印关键字段
    printf("以太网帧源 MAC：%s\n", ether_ntoa((struct ether_addr *)eth->src_mac));
    printf("以太网帧目标 MAC：%s\n", ether_ntoa((struct ether_addr *)eth->dst_mac));
    printf("ARP 操作码：%s\n", ntohs(arp->op) == 1 ? "请求" : "应答");
    printf("ARP 发送方 IP：%s\n", inet_ntoa(*(struct in_addr *)arp->src_ip));
    printf("ARP 目标 IP：%s\n", inet_ntoa(*(struct in_addr *)arp->dst_ip));
}

int main() {
    char errbuf[PCAP_ERRBUF_SIZE];
    pcap_t *handle = pcap_open_live("eth0", 65535, 1, 1000, errbuf);
    if (!handle) {
        printf("抓包初始化失败：%s\n", errbuf);
        return -1;
    }
    pcap_loop(handle, -1, packet_handler, NULL);
    pcap_close(handle);
    return 0;
}
```

### 3. 字节序问题：ntohs/htonl 的使用原因（补充编程细节）

- 以太网帧/ARP 报文中的多字节字段（如 EtherType、ARP 操作码）均采用**网络字节序（大端序）** 传输；
- 大多数主机 CPU 采用**主机字节序（小端序）**，因此需要通过 `ntohs`（网络字节序转主机字节序，16 位）/`ntohl`（32 位）转换后才能正确解析；
- 反向封装发送数据时，需用 `htons`/`htonl` 将主机字节序转回网络字节序。

### 4. ARP 缓存管理（补充实操知识）

- **查看 ARP 缓存**（Linux/macOS）：`arp -a` 或 `ip neigh`；
- **手动添加静态 ARP 条目**：`arp -s 192.168.1.109 08:00:27:53:10:67`（避免 ARP 欺骗）；
- **ARP 缓存超时**：Linux 下默认动态 ARP 条目超时时间为 180 秒（可通过 `/proc/sys/net/ipv4/neigh/default/gc_stale_time` 调整）；
- **清空 ARP 缓存**：`ip neigh flush all`（Linux）、`arp -d *`（macOS）。

### 5. 以太网帧常见异常场景（补充排障知识）

| 异常类型                      | 现象                                   | 原因分析                                                     |
| :---------------------------- | :------------------------------------- | :----------------------------------------------------------- |
| 帧长度小于 64 字节            | 抓包看到长度 <64 字节的帧              | 非法短帧（攻击）或硬件故障，正常帧会通过载体扩展补到 64 字节（半双工） |
| 帧长度大于 1518 字节          | 抓包看到长度 >1518 字节的帧（巨型帧）  | 开启了 Jumbo Frame（巨型帧），MTU 调整为 9000 字节（服务器/数据中心常用） |
| EtherType 字段异常            | 读到非 0x0800/0x0806 的值（如 0x86DD） | 0x86DD = IPv6 协议，0x88CC = LLDP 协议（交换机设备发现）     |
| 源 MAC 与 ARP 发送 MAC 不一致 | 帧源 MAC ≠ ARP 报文中的发送方 MAC      | 典型 ARP 欺骗行为，操作系统会丢弃此类报文（部分系统需手动开启校验） |

### 6. 抓包长度（snaplen）的设置原则（补充 libpcap 实操）

- `pcap_open_live` 的第二个参数为 snaplen（抓包长度），建议设置为 65535（最大以太网帧长度）；
- 若设置过小（如 100），会截断超过长度的帧，导致无法解析完整的 ARP/IP 报文；
- libpcap 抓包默认不包含前导/SFD/FCS，因此 snaplen 只需覆盖“目标 MAC + 源 MAC + 类型 + 数据”即可。
